## 追查：持锁方为什么能握 8 秒（只读排查，根因已锁定）

用户追问"到底为什么会持锁这么久"。**根因：一个慢查询被 autoflush 关进了写事务里。**

### 完整机制链

1. `RelationshipWorker._run`（`services/relationship_worker.py:93`）每 60 秒
   （`RELATIONSHIP_BATCH_SECONDS=60`）调 `process_once()`
2. `process_once` → `jobs.claim(limit=10)`
   （`persistence/relationship_repository.py:489`）
3. `claim` 在 `async with session.begin()` 里**循环处理每个 job**：
   - `session.get(ChatEventModel, ...)` 取 trigger
   - `external_accounts_for_person` / `bindings_for_person`
   - **对每个 job 查一次"最近 5 条事件"**（`recent_query`，line 516-558）
   - `row.status = "processing"` 标记 dirty
4. **关键**：job1 标记 dirty 后，job2 的 `session.get()` 触发 **autoflush**
   → 提前发出 `UPDATE relationship_jobs` → **拿到 SQLite 写锁**
5. 之后 job2/job3 的慢查询**全部在写事务内执行**，写锁全程不释放
6. 其他写者全部堵死 → 5 秒 `busy_timeout` 到点 → `database is locked`

### 慢查询为什么慢（实测）

`recent_query` 形态：
```sql
SELECT * FROM chat_events
WHERE id <= ? AND group_id = ?
  AND (sender_user_id IN (...) OR author_person_id = ?)
ORDER BY id DESC LIMIT 5
```

实测（job 2833 / trigger 58785 / 群 1049765710）：

| 变体 | 耗时 |
|---|---|
| **A 完整 claim 查询（冷）** | **2.304s**（另一次测得 5.163s） |
| A 同一查询（热缓存） | 0.060s |
| C `id<=? AND group_id=?` | 0.772s |
| B `id<=?` 单条件 | 0.001s |
| D `id<=? AND author_person_id=?` | 0.002s |

根因三重叠加：

- **优化器选错索引**：`EXPLAIN QUERY PLAN` 输出
  `SEARCH chat_events USING INDEX ix_chat_events_group_time (group_id=?)` +
  **`USE TEMP B-TREE FOR ORDER BY`**（该索引是 `(group_id, occurred_at)`，
  按 id 排序只能临时排序）
- **主群占 73% 数据**：chat_events 53215 行，群 1049765710 独占 **38677 行**，
  其中 `id<=58785` 的有 38609 行 → 索引扫描 ≈ 全表扫描
- **页缓存只有 2 MB**：`PRAGMA cache_size = -2000`，DB 173 MB，
  机器内存 1.6 GiB → 冷缓存时每次都要读盘，2~5 秒；热了就 0.06 秒
  （这解释了为什么这个坑**时有时无**）

补充：`author_person_id` **全库 0 个索引**（`instr(sql,'author_person_id')` 计数为 0），
OR 条件无法走索引。

### 放大因素

- `PRAGMA busy_timeout = 5000`，**小于持锁时长 7.98s** → 必然失败，
  不是"刚好卡在边界"
- `PRAGMA synchronous = 2`（FULL）→ 每次 commit fsync
- WAL 4.3 MB / `wal_autocheckpoint=1000`（= 4 MB）→ checkpoint 频繁触发
- 并发写者众多：subagent_scheduler / work_scheduler / plugin_background_turns /
  notification_delivery / emoji.worker 同时抢

### 是偶发不是常态

自 17:53 重启到排查时，**`sqlite_write_contended` 全库只有 7 条**，
全部集中在 18:02:24~27 这 3 秒；holder 100% 是 `RelationshipWorker._run` /
`UPDATE relationship_jobs`，held_seconds 5.163 → 7.983 单调上升。
→ **不是系统性锁饥饿，是单次慢查询撞上了冷缓存。**

### 与项目自身纪律的冲突（3 条全中）

`docs/architecture/development-contract.md` §7「SQLite 写事务必须短」：

- 「`session.add()` 后的 SELECT 可能触发 autoflush，提前占住写锁」← **正是本次**
- 「**不得持写锁扫描历史消息**」← **正是本次**（写锁下扫 38609 行历史消息）
- 「**不要通过增大 busy timeout 掩盖慢查或扩大事务范围**」← 提示不能只调 timeout

对照：`persistence/control_query.py:539` 里专门设了 `session.autoflush = False`
并挂了 `before_flush` 拒绝钩子——**项目知道这个坑，但只在控制查询适配器做了防护**，
`relationship_repository.claim()` 未做。
