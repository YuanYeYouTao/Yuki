### 根因分析：两个隔离批次为何失败（最终裁定：无需干预）

失败签名（容器日志）：
`memory_self_reflection_proposal_rejected run_id=496|484 operation=create error_category=ValueError`
→ 随后 `memory_self_reflection_failed ... error_category=mutation_failure`。
三次尝试输入指纹不变、每次都同一处炸，属**确定性失败**，所以 3 次后必然隔离。

**run 484（119 事件）——根因已确认：**
提案 `visibility=global` 但 `category=self_fact`。`memory/self_reflection/service.py:874`
`_validate_global` 只允许 `{self_preference, self_reflection, self_principle}` 设为 global，
于是抛 `ValueError("only abstract self memory may be global")`。即模型把"我有联网搜索能力"
这条能力事实标成了全局，而全局只允许抽象自我记忆。

**run 496（200 事件）——已排除若干可能，未完全定论：**
提案 `group_chat_no_markdown`，current_scope、category self_preference、kind preference。
已排除：
- 不是别名解析失败——`evidence_refs[0]=event_60` 确实在 event_map 里（id 56309）；
- 不是请求模型校验——在容器内按原字段构造 `MemoryMutationRequest` 成功；
- 不是 mutation 层拒绝——那一层抛 `MemoryMutationRejected`，会另记
  `mutation_rejected ... reason_code=`，日志里没有这条；
- 回执表里 `trigger_event_id=56309` **无任何记录**，也没有
  `group_chat_no_markdown` 这个 fact，说明在写回执之前就炸了。
→ 结论：ValueError 发生在 `mutate_resolved` → `_prepare` 的早期，写回执之前。
  episode 部分正常提交（fact 1777），只有这条 create 提案失败。

**排查受阻的直接原因（值得单独记）：**
`service.py:346` 捕获 `(ValueError, RuntimeError)` 后只记 `type(exc).__name__`，
**不记异常消息、不记 traceback**——和 issue #102 里 `processor.py` 只记
`type(exc).__name__` 是同一个毛病。这是这次无法一步定位到行的根本原因。

## 选型咨询：国产便宜 token plan + Responses API（2026-09-18）

### Yuki 现状（服务器上查到的实际配置）

`LLM_PROVIDER=deepseek`、`LLM_BASE_URL=https://api.deepseek.com`、
`LLM_MODEL=deepseek-flash`、`LLM_REASONING_EFFORT=low`、`LLM_THINKING_ENABLED=true`、
`LLM_MAX_OUTPUT_TOKENS=8192`。即**主模型已经在用 DeepSeek 原生 Responses API**。
（embedding 与 vision 走 dashscope。）

### 从代码读出的 Responses API 硬约束（换 provider 前必须验证）

- `llm/openai_responses.py:22-23` 发 `store=false` + `include=["reasoning.encrypted_content"]`，
  注释写明"Yuki replays its own ordered transcript, rather than a remote stored thread"
  → **不依赖服务端状态和 previous_response_id**，因此"兼容层不支持 previous_response_id"对 Yuki 无影响。
- `llm/deepseek_responses.py` 的 DeepSeek 分支不发 include，用 `_reasoning_text` 取纯文本推理。
- `deepseek_responses.py:423` `continuation_output = output` —— 把 output 数组**原样重放**回
  下一轮 input。这是换 provider 最容易炸的点（重放 reasoning item 是否被服务端接受）。
- 六种 output item 类型：message / reasoning / function_call / function_call_output /
  web_search_call / custom_tool_call（后者直接抛 LLMNativeToolError）。

### 候选结论（2026-09 口径，价格随时变）

- **DeepSeek 官方**：最契合。原生 Responses API，无兼容层。官方明确不支持
  previous_response_id / store / include / background / metadata —— **恰好 Yuki 都不用**。
- **阿里云百炼** `/compatible-mode/v1/responses`：支持模型最多（qwen3.8 系列、
  deepseek-v4-pro/flash、glm-5.2、kimi-k3）；注意非列表模型不支持内置工具。
- **腾讯云 TokenHub** `/v1/responses`：服务端把 Responses 转成 Chat Completions，
  支持 GLM-5.x / Kimi K3 / DeepSeek-V4；built-in 工具受限但对 Yuki 无妨。
- **百度千帆** `/v2/responses`、**火山方舟** `/responses`：待验证。
- Coding Plan 类包月（GLM/Kimi/MiniMax/火山/百炼）多为编程客户端订阅，
  能否拿给 bot 当通用 API key 用**必须先核 ToS**，不要默认可行。
