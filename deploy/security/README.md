# Code Mode container isolation

The seccomp baseline is Moby profiles revision `2ceae35d351c156cb5a8efc0fdc4a08cf94569d8`, downloaded from [the official repository](https://github.com/moby/profiles/tree/2ceae35d351c156cb5a8efc0fdc4a08cf94569d8). Its Apache 2.0 license is `MOBY-PROFILES-LICENSE`. `scripts/build_codemode_seccomp.py --check` verifies both its exact SHA256 and the generated profile. AppArmor derives from the same revision's `apparmor/template.go` and retains the default Bot restrictions.

`docker-compose.codemode.yml` adds this policy only to `bot`. Combine it with the existing deployment Compose files. It does not apply to a gateway, Manager, or other service. Before creating the Bot container, a host administrator must install the reviewed `yuki-bot-codemode.apparmor` profile under `/etc/apparmor.d/` and load it with `apparmor_parser -r`. The 2026-10-08 deployment-host canary installed this new profile; existing production containers continued using their original profiles. An absent profile fails container creation; do not substitute an unconfined profile.

The generated seccomp profile retains Moby's default deny action, architecture map, conditional capability rules, and existing syscall restrictions. AMD64 additions permit only the launcher's observed complete namespace clone flags, the second user-namespace unshare, seven exact mount flag combinations, lazy umount, and pivot_root. No generic clone3/unshare/setns permission or Docker capability is added. Seccomp cannot inspect pointed-to paths; AppArmor supplies the filesystem boundary.

The main AppArmor profile keeps `deny mount` and does not grant user namespace creation. Only the root-owned `/opt/yuki-monty/monty-isolated` executable transitions to the `launcher` child. That compiled program accepts only literal `subprocess`, clears its environment and executes the fixed bwrap configuration. Its profile allows the required mount paths and namespace setup, then stacks the capability-free, network-denied worker profile on the launcher at `/worker/monty`, limiting the worker to its binary, runtime libraries and sandbox-local paths without reducing restrictions after no-new-privileges. Only the fixed launcher may create a Unix datagram socket and a raw netlink socket to initialize loopback inside its new network namespace. The worker profile denies both. These profiles require AppArmor 4.0 with userns mediation. Runtime library updates or bubblewrap changes require repeating the syscall and enforced AppArmor matrix.

The existing image entrypoint starts as root to set volume ownership, then uses setpriv to launch the Bot as UID/GID 10001. The Compose overlay does not add capabilities or change this startup contract. Do not add container-wide no-new-privileges without separately proving the AppArmor launcher transition: it may reject a transition which grants namespace setup rights. bwrap itself sets no-new-privileges before launching its unprivileged worker. Existing `init: true` is required to reap orphaned children after cancellation.

## Deployment acceptance sequence

1. Review the exact policy diff and install/load `yuki-bot-codemode.apparmor` as a host administrative deployment step. Keep its previous installed version for rollback. No Docker daemon-wide defaults or unprivileged-userns sysctls need changing.
2. Use `scripts/verify_codemode_container.sh IMAGE_DIGEST` against the intended image. This creates one disposable, network-disabled container with no Bot data/config/socket mount. It tests the combined enforced profile, root-owned launcher, and real worker; a parser success cannot replace this step.
3. Repeat the native pytest matrix in the isolated test container using the same image and security options, with only the source/test checkout mounted. Include worker, worker_entrypoint, memory_authority, recovery, lifecycle, snapshot publication, and disabled-worker recovery cases. Any AppArmor denial must be explained against the fixed launcher paths; do not use complain/unconfined or blanket mount rules to pass it.
4. With those gates passed, render the actual production Compose combination including `docker-compose.codemode.yml`, preserve existing mounts/routes, and deploy only Bot. Verify its UID and effective capabilities after the ownership-setting entrypoint, loaded profile name, seccomp mode and actual worker/native acceptance. The source/tests/Compose render and local seccomp results do not substitute for this final combined enforcement gate.

## Deployment-host enforced canary on 2026-10-08

The dedicated canary on Ubuntu kernel `6.8.0-136-generic` uses a network-disabled, read-only container, UID/GID 10001, all capabilities dropped, 1 CPU, 1 GiB RAM, PID limit 64 and a 256 MiB tmpfs. It mounts only the reviewed verifier and root-owned replacement launcher, with no production data/configuration or Docker socket. Existing Bot/gateway containers and host sysctls were untouched.

The kernel correctly rejects a nested procfs mount because Docker's outer procfs has masked paths. The fixed launcher no longer exposes procfs: the native interpreter does not require it, and the verifier asserts `/proc` is absent from the worker root while retaining all six namespace, UID, capability, mount, environment and resource-limit checks through the Host's original process IDs. No host procfs binding, systempaths bypass, privileged mode or added capability is used. The seccomp rule for the now-unused proc mount flags was also removed.

The enforced probe passed. The actual worker label was `yuki-bot-codemode//launcher//&yuki-bot-codemode//launcher//worker (enforce)`. Original descendants disappeared after shutdown and parent death. After confirming the real native process entered `T (stopped)`, the separate Host watchdog discarded it in 0.503 seconds for a configured 0.5-second deadline. Waiting for the stopped state removes a signal-delivery race from the probe; it does not change the engine.
