## 1. 要修什么

普通 Main A 运行期间，新消息 C 同时进入当前轮的后续输入和 ordinary worker 的待尝试机会。当前轮已经回应 C，但没有登记 C 归属于 A；A 结束后，worker 又用 C 新开 Main，产生第二次请求链和重复回复。

目标是把输入交接做完整：**当前轮明确接纳的补充归当前轮，排队入口读同一份接纳记录，不再重复启动；没有接纳的输入继续保留原合法机会。**

这里的 steer 指普通补充交给当前业务执行的明确接纳，不等于公共历史可见，也不把所有轮内聊天观察都改成指令。普通聊天仍可以没有 Work。接纳记录证明谁接下输入，不证明模型已经回答、效果成功或任务完成。

## 3. 补查发现的实施缺口

### F01 观察与接纳是两条事实链

原 projection、`observed_event_ids` 和 `observation_watermark` 只说明材料被采用或已经观察。它们包含普通群观察、其他作者及外发事实，不能整批当成人类新请求。不能按最大事件号、时间或公共历史覆盖点消费 ordinary。

现有 admission 是输入归属的事实源。本修复复用它，保留事件主键和每条来源，不另建“已回复集合”或“已消费 revision”。

### F02 候选注册可能晚于观察

账本先在 `processor.py:875` 落事件，observed 注册还要经过 notify、开放群语音准备等步骤；continuation 分类又在其后异步进行。`_ObservedHumanTurn` 中也包含尚未被判定为 ordinary 的事件。

因此，不能遍历 observed map 就接纳，也不能用 A 的旧观察水位追认后来才获得资格的 C。每次业务请求只接纳当次明确提供、准备完成且真实选中的 ordinary 候选；晚到的分类或来源保留自己的合法机会。旧 C 的迟到结果不得覆盖新 D。

### F03 事件可见不证明音频、图片和附件已准备

开放群路径在 observed 注册前做 ASR；continuation 的无 Work 延后路径可能在原语音、visual 准备完成前返回。`_ObservedHumanTurn` 不保存完整准备结果，`PreparedOrdinaryAdmission.prepare()` 只冻结来源和身份，不证明材料完整。

如果仅凭边界中的事件 ID 给 C 写 admission，后续 worker 会退出，而 C 原本需要的转写、当前图片或附件材料可能从未交给模型。

必须复用原普通输入的准备及已有结果，确认本次实际业务请求带入了获准正文与相应材料，随后冻结一致的来源版本。语音失败、部分附件失败仍可按原合同提供真实失败材料；不能增加“所有媒体必须成功才能接纳”的门槛。不能按媒体类型另设拒绝名单，也不能为补一份归属重复购买 ASR 或重发媒体效果。

### F04 接纳、派发与响应不能混记

`_PrimaryDispatch.admit()`、boundary publication/finalize 均可能在 HTTP 前执行；Provider 配置、序列化、容量或取消仍可能阻止实际派发。收到正常响应后才有相应响应事实。Fake Provider 不记录真实 HTTP，`physical_request_count=0` 也不能泛化成“模型没有运行”。

接纳提交前，准备或历史曝光不夺走 C 的普通机会；明确接纳给 A 后，即使之后取消、失败或结果未知，也不能默认新建 C activation 重发。admission 仍只表示归属，不宣称已回答。不把诊断 trace、调用次数或一段模型正文升级为接纳权威，也不为本修复新建普通轮完整 journal/冷恢复系统。

### F05 A 在中途接受 Work，原路由会变化

`runtime_work_enabled=True` 和存在 `WorkControl` 不等于已经接纳 Work。A 第一个响应也可能接受 Work，C 在下一个请求前到达。

承接时须读取当前真实 Work 状态，沿现有 Work/wait 的 mailbox、publisher 和确认合同处理。不能一直沿装配时的 `current=None` 假设；也不能把 C 同时记为 ordinary 接管和独立 Work 输入。不同 actor 的公共群聊补充保留自己的来源，不借此取得另一人的 Work、私人资料或管理授权。

### F06 一个 activation 的多个输入不能复制效果归因

`participation_ordinary.observe_main_response()` 沿原 `effective_trigger_event_id` 找 admission，以 activation 作 run 引用；Social 效果仍按原 source、call 与真实发送回执关联。

给 C 登记同一 activation，不表示 A 的既有发送、自报或成功自动属于 C。不能把一次效果广播给所有同 activation 的输入，也不能为匹配 C 伪改原 ToolActor、触发事件、Memory session 或发送来源。后续首次接受 Work及其恢复仍保原 ID、真实来源、预算和私有协议。

### F07 三种执行标识不是同一个 ID

`ordinary_turn_admissions.activation_id` 是原 prepare 保存的接纳 UUID；`RuntimeTurnCorrelation.turn_id` 用于观测关联，Provider `TurnTranscript.chain_id` 属于请求链。普通 `ToolRuntime.effective_execution_id` 还可能是 `event:<内部事件号>`。

A 的归属必须从原 `inbound.source_event_id` 关联原 OrdinaryAdmission 获取。不能拿 trace ID、请求链、Work lease owner 或 `event:<id>` 字符串替代接纳 UUID回填 C，也不能给 C 另造 UUID 却声称仍归 A。

### F08 接纳输入不改变原执行授权

现有 ToolActor 能表示 C 的真实身份，但原 Main 后端仍持有 A 的 ToolRuntime、Memory 范围、来源 guard 和超管位；整批 invocation 共用原 runtime。仅给 C 写 actor/Presence 字段，不会把某次业务调用可信地归给 C。

这符合原执行隔离合同，本身不是故障。A 在原群里回应 C 的公开补充，无需切换 ToolActor；C 的 admission 只证明输入归属，不授予 C 或 A 新权限。源码没有通用的按新增输入切换调用身份接口，也不能据此推定存在越权。

不同成员的公开插话继续正常可见和参与群聊，不增加“只有同一说话人能插话”的入口禁令。确需 C 本人身份、私人 Memory 或另一个 Work 授权的独立动作，仍沿原合法入口或已有交接处理，不能凭公共补充或 admission 改绑权限。自动化 DelegatedAuthority、原生搜索的 allowed_capabilities 和记忆 evidence_event_id 都不是通用的身份替换接口；本修复不新增这种接口。

## 4. 最小修复设计

### 4.1 复用现有输入准备和接纳

由已经完成普通入口分类的原路径提供精确候选，沿已有 `source_event_id`、原 record、snapshot、reason 和 binding 传递。复用现有准备结果，确需准备的部分在 SQLite writer 外完成。不要从公共历史反推资格，不按平台消息号重建来源。

在 Host 内部衔接原 Processor、Main 和边界 publication 即可；需要提取共享准备函数时迁移真实调用者，不复制两份 ASR、身份、策略或媒体规则。不创建另一套消息队列和调度器，也不向模型暴露新的工具、提示块或“消费消息”动作。

目前没有可直接使用的“完整 ordinary 载荷”对象。I02 应从原 Processor 准备段提取共享结果，包括清洗后的正文/引用、AudioInput、VisualTurnState 和重读的原 record，而不是给 observed/admission 人为补一个 ready 布尔值。共享原件必须同时服务当前轮和原 worker，不能启动 C 的第二套 Main 装配来准备 steer。

业务材料沿当前获准的私有输入尾部处理；公共 projection 仍只冻结原事件渲染，不 dump 准备对象、当前图片、运行资料或私有附件状态到 FrozenFragments。仍使用 A 已固定的 Provider/Profile、system 和工具，不因候选改变模型路由或工具声明。

内部候选准备回调可以沿原 `handle_turn → Chat._build_messages → MainAgentTurnService.compose` 和 observation-boundary 闭包传递，避免再向 ToolRuntime、AgentRuntime、InvocationContext 各复制一套候选状态。函数与返回类型以真实调用者需要确定，不先建立新的管理层。

### 4.2 在实际选中的业务请求接纳确切输入

每次有原业务请求可继续时，将当次候选与最终选中的边界逐项匹配。只有原普通入口仍允许接纳、来源/代次有效且完整材料确实进入该请求的输入，才能登记归属。初次装配历史、显式历史工具读取、公共/私有 Compact 维护请求不因此取得普通输入。

本方案选择一次明确的业务接纳截点：仅接纳该次接纳前已经完成原资格/准备、实际材料仍在最终请求中的候选。晚于截点才完成分类/准备、且此前仅被观察的 C 保留原 ordinary 机会，不在后续请求按旧水位追领。若未来需要追接已观察的晚就绪消息，须另沿真实 event→fragment 关联设计；当前的 observed 集合不是这个接口。

复用 A 已有 ordinary admission 的 activation/coordinator 身份，C 仍保存自己的 event、actor、Presence、source revision 与原 binding。不要再次提升 coordinator、伪造一个新 activation，或覆盖已有其他真实归属。

普通输入 admission 和所选 projection 沿既有 `ContextBoundary` publication 共用原短 writer，防止只提交一边。外部准备、历史扫描和来源摘要计算都在 writer 前；事务内只做既有索引来源/身份/代次核验和必要条件写入。`finalize()` 继续负责本地快照与水位，不被解释成模型已经处理。

同一逻辑请求被 guard 多次检查或按原允许协议重试时，复用同一归属，原 `before_model_request` 仍逐次核验。现有 `commit()` 对任何已有行都返回 False，包装调用必须区分“同一 A 和同一 C 来源的原接纳”与“其他 activation/Work 已取得归属”，不能把 False 一概解释为已归 A，也不能覆盖旧行。

在冻结业务候选前排除不具备资格的输入；若已冻结业务输入在提交时失去来源或归属，沿原来源冲突、抢占或请求未开始出口处理，不能原样带着失去归属的业务载荷继续派发。只回滚本次未提交准备和本地 guard stage，不重跑先前模型、工具或已确认效果。真实授权和隐私失效保留原保护语义。

### 4.3 worker 不需要第二份消费状态

C 接纳后保留原 attempt。worker 之后调用它时，`promote_committed_event()` 的既有 admission 查询直接返回 `ordinary_already_admitted`，不再提升版本、开启 Main 或请求模型。

D 如果已覆盖 latest slot，原 revision/changed 交接继续把 D 交给后续合法尝试。不得清整个 Conversation slot、`changed`、按事件号扫掉旧机会，或把 `ordinary_attempt=None` 当成消费；`None` 会让该状态转入 legacy 自主路径。

删除 `consumed_revision` 字段及两处无效分支，不恢复旧 `consume_rollup_history`，不新增替代水位。

### 4.4 保持当前上下文与效果合同

保留轮内新公开聊天观察、实际采用的 FrozenFragments、合法 current 输入和原请求顺序。不给已采用历史去重、裁剪或重渲染；不移动私有思考、签名及工具调用/结果，不改变固定完整工具合同和显式发送出口。

接纳 C 后，正常 final、空 final 和 `NO_REPLY` 都可正常结束；不增加“必须发送才算消费”的条件。不同真实输入即使正文和发送 payload 相同，仍可独立执行。取消或结果未知沿原身份和回执核查，已确认发送不重做。

### 4.5 身份回归的范围

本修复处理普通输入的接纳归属，不改变原执行主体。跨成员公开补充可以由 A 的原执行正常回应，仍使用 A 的 ToolRuntime、Memory 范围、来源 guard、工具授权和效果回执；给 C 保存 admission 不要求把这些字段换成 C。

目前已复现的是双激活与重复发送，没有复现跨成员越权。固定的原 runtime 证明身份没有自动切换，不能单独证明授权出错，也不能推出“必须新增逐项调用的多主体绑定接口”。缺少这种通用能力不是关闭 #439 的门槛。

I06/V13 只验证原主体、执行处权限和 Work/wait 路由不被这次改动破坏：公开接话正常，接纳记录不提升或改绑权限，媒体与私人资料仍在原授权范围；不同主体需本人授权的独立操作保留其原合法入口/交接，不能以仅观察或填入 admission 字段冒充已经代办。

不为此新增 Host 的正文意图分类、actor 相等限制或多主体调度框架。若实施回归发现具体操作被错误归属，记录实际调用、原来源与授权结果，再按该故障选择最小修复；不把尚未证实的泛化风险扩大为先决架构任务。
