# Yuki 主 Agent 全入口执行、恢复与交付统一任务书

状态：已交付；下列审计事实描述修改前基线。线上缓存暖链指标仍待自然样本，不把设计目标写成实测结果。

审计日期：2026-09-13（Asia/Shanghai）；代码基线：`b612125cbf8991a3f8cc9fad7d23dad970fc49cc`。
本任务书补齐此前统一入口和异常恢复的遗漏，不重做已经存在的 Runner、监督器、任务日志和交付器。
实施以 [共同架构约束](development-contract.md) 为准，并同步维护现行模块文档。

## 1. 目标与完成定义

凡代表 Yuki 生成、工作或发言的入口，统一使用提示词编译、固定工具合同、核心工具执行器、
预算账本、异常分类和恢复协议。调用入口只负责提供可信来源、已获授权的上下文范围、触发资料与交付方式。

“共用一个 Runner”或“工具声明哈希相同”不足以验收。必须验证真实工具能够执行、等待后能够
恢复原工作、预算没有相互矛盾、已发送内容不会被外层再次发送。

用户可观察的结果：

- 自动化写日记可以按授权读取聊天历史和记忆，使用工作区、终端、联网及其他普通工作能力；
  不能因入口是自动化而落入只能生成一段文字的后端。
- 插件发起的 Yuki 工作与普通主 Agent 使用相同工具实现；合法权限不足时得到真实、明确的回执，
  不再因后端没有接线而返回 `unknown_tool`。
- 第一次单段到限后，存在剩余根预算且恢复条件成立时，自动继续第二段；等待、重启不重置累计预算。
- 成功、失败、未知结果回到原 Agent。普通业务结果不强制替写正文，也不强制增加总结请求。
- 同一执行不会因为调用方重试而重复操作或发送；与旧任务无关的新消息不会自动继承旧目标。

本计划覆盖已确认的代码缺口和相关事故回归，不承诺消除所有模型幻觉、Provider 故障或 SQLite 等待。
未复现的风险须保留为风险，不能在交付报告里写成已证实、已修复的事故原因。

## 3. 公共执行边界

在应用层提供一个公共的主 Agent 执行准备与恢复接口，供普通聊天、主动群聊、自动化、
插件生成、插件自主轮及对应续跑调用。不要让插件或自动化导入聊天服务私有后端来制造新的反向依赖。

公共执行上下文至少明确：

- `origin`、稳定 `execution_id`、原 `work_id/root_work_id`、恢复所有者及父调用身份；
- 内部来源事件（确实存在时）、Conversation、generation、Person/Space/Presence；
- 可信授权和读取范围、委托目标、已批准 capability；
- 固定合同与 Provider 版本、检查点/continuation、根预算关联；
- 交付所有者和模式：由原调用方消费结果，或由公共交付器向获准目标发送。

定时执行使用自己的 automation run 身份；不能伪造新的用户消息或拿 QQ 消息 ID 重建来源。
插件不能自己填写 Host 可信身份或管理员标志。恢复时重新验证当前权限与取消状态，不能只信旧快照。

主 Agent 工作能力和外部副作用授权分开处理：

- 工作区、终端、安装、artifact 等普通工作能力不能因为使用了简化后端而缺失。
- 聊天历史和记忆按真实来源及委托确定可读范围，不默认为全库可读。
- QQ 发送、撤回、戳人、长期记忆写入、自动化创建仍保留各自执行边界。
- 不默默扩大旧插件批准项或旧自动化委托；必要的迁移须明确标记为需重新授权，而非反复让 Agent 试错。
- 有图片、读过网页和外部不可信内容本身不清空能力；保留内容信任标记和逐工具授权。

## 4. 上下文、工具和缓存

所有主入口共享同一版本的固定提示词、完整工具名称/顺序/schema 与原生工具设置。
首次构造上下文复用正常 assembler 和投影机制；插件意图、自动化目标作为固定部分之后的触发资料，
不再用空历史的手工上下文代替 Yuki 主上下文。可读范围不同允许选入不同资料，不意味着固定声明不同。

普通续跑继续原实际请求历史，只追加新事件、工具结果与改向输入。不能因插件重新调用或定时 worker
再次接管而重注入变化后的时间、short_state、目录或摘要到历史前部。

Rollup、权限收窄、合同/Provider 变化使用现有显式链边界，保留执行关联和预算；
不能一概作为用户中断或丢掉检查点。保留已有 Rollup 消息合并逻辑，不改成逐条积压补答。
不同根任务允许有不同动态历史；验收不能要求所有入口整个请求字节完全相同。

主入口不允许 `tools=None` 静默进入短期状态专用后端。独立辅助调用如确需专用后端，必须有明确身份，
不加载主 Agent 完整工具合同；先盘点调用方，再移除不可达或不再需要的兼容分支。

## 5. 预算、等待与恢复

复用现有 WorkSupervisor、journal、效果回执和根预算，避免再建第二本账。

- 主 Agent 默认每段 24 次模型请求、32 次业务工具；根与子任务共享 120/160，子任务保留主任务 8/8。
- 每次真实模型尝试与业务工具按现有口径计账，失败请求也不能漏记；一次调用穿过多层不能重复计费。
- 自动化“执行一个 Agent 步骤”只计一次编排步骤，实际模型/工具消耗进入原工作账本；
  统计汇总可以保留，但不能再拿生成器的旧 `1/2` 预算对内层结算并追判失败。
- 明确配置的更低配额仍可生效，但须在执行前进入同一预算模型，标明是单段还是任务总额。
- 单段到限保存后重新排队；根总额到限暂停。待命、重连和恢复不重置额度或无进展检测。
- 繁忙等待、等待命令、等待父任务、Rollup/历史边界、明确取消、授权失效、可重试故障、
  不确定副作用和不可恢复错误，分别映射到现有状态与结构化原因，不统一包装成 capability 失败。
- `WorkConflict` 按实际原因判断：容量/租约竞争可以延期，身份或执行归属冲突不能无限重试。

各入口保留传输/触发队列，但它们只接纳、唤醒、消费结果；模型循环与任务结算统一。

| 入口 | 持久关联与恢复要求 |
| --- | --- |
| 普通聊天、主动群聊 | 原内部事件与 work；现有 WorkScheduler 接管 |
| 自动化 | 原 automation run、步骤游标、work；恢复原步骤，不重新执行已完成发送步骤 |
| 插件自主轮 | 原通知事件、job、work；忙时延期保留预算，收到完成结果后只生成一次交付意图 |
| 插件同步生成/运行 | Host 返回稳定结果句柄、work 和状态；pending 不是文本。恢复凭 Host 持久来源与当前授权，不依赖已退出的临时 invocation 对象 |
| 子 Agent | 保留现有父子租约与通信；使用公共预算和故障语义，不取得主 Agent 对外发送权限 |

插件调用方只能消费自己拥有的结果；可提供显式查询/恢复接口，不能靠再次提交同一段 instruction
猜测是否在恢复。同步调用转等待前必须登记恢复所有者；无恢复承载能力时明确拒绝后台接纳，不能留下孤儿工作。
调用方消费结果与工作继续执行是两件事：插件返回控制权后，已合法接纳的工作应由 Host 负责调度。

## 6. 普通回复、工具回执与交付

移除普通闲聊/知识回答必须调用 `task_control.answer` 的纠正流程。
模型自然产生的正文可以作为最终回答；若要执行工作，仍须在首个副作用之前原子登记工作。
可以保留显式 answer 接口供调用方使用，但不能因没使用它而强制追加一轮请求。
不要用关键词判断一句话是闲聊还是任务，不增加“必须汇报成功/失败”的固定模板。

统一结果合同应结构化表达：工作状态、可恢复 ID、正文、产物引用、交付意图和已接受回执。
不能用“正文已通过任务回复发送，本轮无需重复”之类字符串代替状态，也不能通过过滤这些字符串
来冒充交付状态修复。失败/未知工具回执回到 Agent；Agent 仍可继续、询问或报告。

同一输出的交付所有者在接纳时确定：

- 返回调用方模式：结果由调用方消费；外层发送是唯一交付动作。不要同时安排一个自动最终发送。
- 主 Agent 交付模式：外层只观察状态，不再把 `result.text` 无条件发一遍。
- Agent 显式工具发送也进入统一效果/交付账本；外层根据该输出的关联回执处理，不能简单按
  “这轮发过任何消息”吞掉后续不同的有效正文。
- 插件 outbox 和自动化发送步骤与同一输出建立稳定关联，保留各自传输重试，不重新请求模型生成。
- 网关结果未知先核对，不能承诺平台不支持的严格 exactly-once；禁止换新 ID 盲目重发。

保留显式 `/ai` 管理命令和模型不可用时的必要运维反馈，它们不是普通工具成功回执。
在模型仍可继续的正常路径，不额外调用总结模型、不把 JSON 当正文、不强制终结整个任务。

## 7. 重复自动化与旧目标串入

本次同时收齐自动化创建的原子幂等和目标归属，但不增加语义分流器：

1. 普通创建与委托创建使用同一创建服务。为真实创建操作保存稳定来源/调用幂等键与参数摘要，
   数据库原子复用同一操作；同键不同参数明确冲突，不能“先查后插”留下竞争窗口。
2. 一个事件可以合法要求多个任务，不能简单对 `source_event_id` 唯一约束。键须区分事件内不同创建操作，
   同一 call 的重放复用原结果；不把新 call 的不同业务意图猜成相同。
3. 对跨事件的完全等价待执行自动化提供候选查询和明确的已有任务结果；比较结构化目标、
   所有者、时间/时区和交付范围，不仅比较名称，也不因同一时间而合并不同任务。
   用户明确要求额外任务时允许显式创建独立实例。
4. 近义但不同描述不能保证靠幂等键自动识别。公共上下文提供有界的当前工作及已兑现操作信息，
   工具支持查重；Agent 决定复用、修改或创建，运行时不按关键词擅自解释授权。
5. 新输入默认保持中性；恢复旧目标必须关联明确 work。普通讨论不能被旧任务的待收尾状态强行继承。

72/73 的历史记录保留为事故证据，不在迁移中重新执行，也不在本任务书阶段改动。
回归可确定保证重放幂等和正确归属；模型面对近义请求是否选择重复创建需另记行为评估结果。

## 8. 不纳入统一主聊天的路径

- `ctx.agent_sessions` 的游戏、独立插件计算历史继续隔离，保留声明、批准与请求的能力交集。
- Rollup、记忆提取、重排、媒体识别等辅助模型保持专用合同，不加载完整主工具或聊天人格。
- 子 Agent 保留固定工作者提示词、独立请求链及对外工具限制。
- RSS、QQ、Manager、持久环境的生命周期不随本次入口重构改变。
- 不修改用户 `system_prompt.md`；必要执行规则放在代码管理的公共合同中。
- 不引入新 Agent 框架、Provider 内容路由或 DeepSeek 审查报告提出的额外策略。

## 8A. 第二轮反查补充：入口外层也必须收齐

本节为同日第二轮代码反查补充。以下区分已确认代码行为与需要定向复现的风险，
纳入 A/B 阶段实施，不留作部署后的可选补丁。

### 插件工具本身仍有附件限制

`plugin_host/capability_adapter.py::_allowed_for_turn` 根据当前消息或引用中的附件，
直接禁止 `SEND/MUTATE/DESTRUCTIVE` 工具。这是独立于 `agent.run` 能力清空的另一处代码；
仅修改 SDK 生成 Facade 不能修掉它。

删除“存在附件即禁止”的推断，继续校验真实来源、批准权限、工具风险与委托目标。
对来自附件或网页的指令仍保持不可信标记；“按用户要求处理附件”和“执行附件内自带的命令”
不能混为一谈。验收须覆盖图片输入后编辑工作区、发布文件及获准发送，包含引用附件。

### 外层超时、handler 重试和未知副作用

- `automation/executor.py` 使用 `timeout_seconds - active_before` 包住整个步骤循环。
  这是累计活动时间上限，并非只限制单次网络请求；不能在修复调用次数后仍默默用旧 120 秒
  截断长任务。明确区分单次外部调用超时、一次激活时间片、用户配置的任务总时限；
  普通 generated 编译模板的旧默认值不继续充当持久工作的隐含总时限。
- `plugin_host/event_bus.py`、`command_adapter.py`、`automation_adapter.py` 和
  `capability_adapter.py` 都有回调超时。保留对插件 handler 的有界限制，但已交给 Host
  持久接纳的 Agent 工作必须独立于回调协程存活；回调结束、超时或调用者断开不是自动取消任务。
  接纳前取消不得遗留工作，接纳后必须能够查询稳定 ID，不能只加 `shield` 而没有持久所有权。
- `capability_adapter.py` 的 `TRANSIENT_ONCE` 会在 `TimeoutError/OSError` 后再次执行 handler，
  此处没有按本次实际效果是否已提交作判断。修改为统一的重试判定：只读或有可证明幂等协议的操作
  可以有界重试；写入、发送、删除结果未知先查询原执行回执。不能把异常类型当成“没有执行”。
- `automation_adapter.py` 把 `PluginResult` 转成普通 data 或通用 RuntimeError；必须显式传递
  pending、work/result 句柄、可重试原因、已提交/未知效果和累计消耗。不能把接纳成功当成步骤完成，
  也不能只从 `status == sent` 推断全部发送计数。

显式插件管理命令可以保留自己的命令反馈；若回调返回的是 Agent pending/结果句柄，
`command_adapter.py` 不得再回退 `json.dumps(result.data)` 输出内部工作信息或误报“已完成”。
普通插件业务错误与模型不可用分开归类，不把所有异常拍平成同一种失败。

### 嵌套主 Agent 调用、预算继承和重入

`MainAgentTurnService.run` 会读取 `current_work_control`；插件 SDK 的 `_ACTIVE` 仅防止
插件生成路径自身递归，不能据此证明所有“主 Agent → 插件工具 → 主 Agent”调用都安全。
`ConversationTurnCoordinator.hold` 是计数式占用记录，不是互斥锁，不能把其嵌套直接认定为死锁。

公共入口必须在接纳时区分外部发起和执行中的嵌套调用：

- 同一主执行中插件工具又请求 Yuki 主入口时，不直接递归开启一个模型循环。
  在无副作用前返回明确的重入不支持回执，或显式登记后续工作供安全点接管；不能等待自己释放名额。
- 需要独立计算的插件使用隔离会话；需要委派工作的主 Agent 使用现有子任务合同。
  隔离计算若嵌入一个主任务，其真实消耗须按明确关系计入预算，不能偷偷绕过根限额。
- 新独立调用不能意外继承上一个调用的 ContextVar 工作、取消标志、预算或发送权限；
  合法子调用也不能丢掉父关联。使用主 Agent 调用插件工具的真实集成路径验证。

### 模型路由与缺依赖兜底

`automation/handlers.py` 仍构造 `ModelTask.AUTOMATION_AGENT` Runner；正常绑定主合同后
`_main_turn_service()` 返回共享服务，只有合同缺失时才新建独立 MainAgentTurnService。
这证明存在另一条缺依赖兜底，不证明生产自动化正在使用不同模型。

清理主入口缺依赖时静默新建服务的路径；启动/接纳时明确验证公共依赖。
统一核对实际 ModelTask、配置快照、模型/协议、原生联网能力、输出/思考预算、并发名额与缓存设置。
不只检查 tool schema，也不把当前未使用的独立 Runner 当成线上分流事实。
保留明确的辅助模型与独立插件模型配置，不能借统一之名全部改成聊天模型。

### 租约、排队、公平性与停用

长任务接入后复核自动化与插件队列的 claim/lease：现有自动化 worker 按到期项创建协程，
插件后台 worker 逐项等待执行；不能假定现有短任务的租约时长和等待方式适合长任务。

- 原 work 的恢复要有稳定唤醒时间/原因，避免 pending 后每几秒空跑一次模型或轮询数据库。
- 活动执行具有明确租约续期和提交围栏；租约到期重领不能与仍在运行的旧执行一起提交结果。
- 后台接纳和运行都受有界容量约束，保留前台模型名额；一个等待父任务的插件工作不能堵住全部通知。
- 停止 Bot/插件时先保存检查点并释放可恢复租约，不能无界等待当前长任务退出。
- 插件禁用、卸载、批准版本变更和自动化取消分别影响新接纳、活动任务及未发送结果；
  对已失效授权停止新的副作用，保留原执行回执，迟到结果不得自行发送。

以上为必须验证的生命周期风险，不代表已经复现多 worker 重复执行事故。

### 可观测性与维护边界

统一记录 execution/work/root、来源 run/job、激活段、等待原因、累计消耗、交付意图和真实回执。
插件自主轮的观察记录当前使用固定 `sent_messages=0`，不能拿它当成最终未发送证明；
队列生成完成、outbox 待发和网关已接受须能关联查询，生产日志不保存提示词正文。

结果句柄和任务保留策略须协调：父调用尚未消费时不能清掉唯一结果；超过保留期明确返回已归档。
启动校验与迁移版本同一次修改更新，但不以删除校验来掩盖模型服务、执行器或恢复所有者缺失。

新增验收：handler 已写入后超时不重写、回调超时后按句柄找回、相同主执行重入被正确处理、
并发预算不会串账、租约过期双接管只有一方提交、插件停用后迟到结果不发、等待任务不阻塞其他后台任务、
累计时间片与用户总时限能明确区分。两种 Provider 均核对实际配置与前缀，不能只 mock 返回状态。

## 9. 实施顺序与模块责任

按三个可验收阶段实施，避免大量零碎热补丁：

### A. 公共执行合同和接线

提取公共上下文/工具后端构造，定义来源、授权、交付与恢复所有者；迁移自动化、插件生成与运行，
删除短后端静默回退及媒体/联网能力清空。同步 SDK 返回/恢复协议、Fake、类型和插件调用方。
固定工具合同只进行本次确需的版本更新；启动验证公共执行器依赖及每个主入口的恢复接线。

### B. 生命周期、预算与交付

接通各入口的原 work 恢复、统一结算与等待；修复自动化预算，替换插件“两次中断放弃”；
删除普通回答强制登记，关联外层发送与持久交付回执；补齐自动化创建原子幂等和当前工作投影。
若需要新增字段、索引或约束，新增迁移，不能修改已发布迁移。

### C. 定向验收、文档与交付准备

完成下面的跨入口验证，更新架构合同、插件 Facade/迁移说明、自动化说明和实际恢复所有者表。
旧任务书标明历史基线，删除导航中过时的“尚未实施”声明；不能把新任务书当成现行能力说明。
确认无调用方后删除退出的兼容路径，不留默认回退到旧后端的开关。

## 10. 定向验收矩阵

使用真实公共执行器与持久数据库路径，外部发送使用隔离网关。只模拟必要的外部响应，
不能仅 mock Runner 返回成功来证明入口统一。集中运行有关测试，不反复跑无关全量。

| 验收 | 必须观察到的结果 |
| --- | --- |
| 各主入口执行相同基础任务 | 普通聊天、主动群聊、自动化、插件生成、插件运行、自主轮及续跑均能执行获准的历史/记忆读取、文件读写、终端和 artifact；声明中已接入工具不报伪 `unknown_tool` |
| 权限负例 | 未获准历史、发送、管理或记忆写入返回结构化拒绝；不扩大旧授权、不动态修改工具声明；媒体/联网不会清空其他合法能力 |
| 两段以上工作 | 各恢复所有者至少覆盖第 25 次请求，公共调度覆盖第三段；原 work/journal 不变，预算累计且预留有效 |
| 自动化日记事故 | 同时到期两项合法任务时忙者排队；生成使用多次工具不撞旧 1/2 限额；同 run/步骤恢复，完成后仅交付一次 |
| 插件同步与自主轮 | pending 不是文本；调用返回、Host 重启或重复查询后可按句柄恢复；原通知事件与结果不重复消费 |
| 新消息与 Rollup | 保存事件；恢复依据明确原因处理，不能两次历史变化后无声放弃；无逐条爆发补答，无未经选择继承旧任务 |
| 故障与竞争 | Provider 错误、SQLite 繁忙、租约竞争、安装/终端等待、reset、取消、迟到通知均有正确状态；写事务中无外部等待或历史扫描 |
| 交付 | 普通答案无需 task_control 往返；文件加说明、分片、返回调用方和工具直接发送均有唯一归属；部分成功或未知时不重复发已接受片段 |
| 创建幂等 | 同 call 重放和并发创建只登记一次；同事件合法两项任务保留；不同目标同时间不误合并；讨论消息不自动接回旧目标 |
| 实际请求前缀 | 两种现有 Provider 协议比较真实 messages/input、完整 tools/native_tools 和设置；普通恢复保留历史前缀 100%，媒体恢复不重建旧链 |
| 缓存统计 | 分入口报告暖链与冷启动、未命中 token；沿用暖链目标至少 95%、低于 90% 或较同条件主链低超过 5 个百分点须定位的门槛；指标缺失标未知，不以哈希宣称命中 |
| 迁移 | 旧预算、work、执行回执、游标、artifact 和交付记录保留；不能恢复的旧调用明确暂停，不能新建任务冒充恢复 |

已解决事故采用固定响应回放定位机制问题；模型自然语言行为另做小规模评估，不把偶然一次
“没有重复创建”当成逻辑证明。现有相关测试与 CI 在交付前集中完成，失败按实际影响修复。

## 11. 上线、回退与报告

验收完成后按已授权交付流程进行：

1. 完成定向验收及相关 CI，提交并提 PR；报告实际合并提交与镜像版本。
2. 用一致性数据库副本验证迁移、启动校验和遗留工作分类；不直接在生产试错。
3. 更新前暂停新接纳并收拢活动工作，停止 Bot 后保存最近可用恢复点；迁移并更新 Bot。
4. 检查普通聊天、自动化 worker、插件自主轮、子 Agent、QQ、RSS、Manager 和持久环境健康。
   线上发送验收只使用明确测试范围，不重跑历史日记任务或广播测试消息。
5. 回退先停止新接纳，保留上线后写入的文件、预算和执行回执；使用兼容新存储合同的镜像，
   不恢复旧数据库覆盖新数据。无法安全恢复的工作标记暂停并保留查询入口。

交付必须分别列明：已修复的复现故障、通过的入口矩阵、仍未证明的模型行为风险、
本地修改/测试/提交/推送/合并/上线状态。只有完成矩阵后，才能称为全入口收齐。
