## 3 已确认的问题和完整链路

以下为源码事实，不能统一解释成生产延迟的已证实原因。

| 问题 | 原实现和连带位置 | 实际影响 |
| --- | --- | --- |
| 小型研究结果也只剩目录 | `capabilities/results.py` 中 `external_research` 同时影响归档与展示；`web_search/read_webpage` 即使未超预算也走 manifest | 已拿到的标题、URL、摘录或正文需要另一次模型决定和读取才能看到 |
| 多层预算不一致 | Main 与公开 reader 优先使用 `result_token_budget × 4`；Memory 和 CodeHost 只读 agent 字符预算 | 外层放宽后，内层仍可能先删正文或按另一预算展示 |
| Memory 在共同入口前丢结果 | `agent_tools.py::_memory_list_result` 逐条删尾；`_capture_memory_tool_result` 包装证据后可能返回 `result_too_large` | 通用 Artifact 只能保存已被裁过的结果，甚至拿不到原始成功读取 |
| Code 先用半预算裁一次 | `codemode/driver.py::_result_view` 按 `result_limit // 2` 提前归档和截取，之后 `_bounded_result` 再按整页预算处理 | 完整父结果可能本来放得下，却提前变成预览 |
| 读取默认操作忽略路径 | `services/chat.py` 公开 reader 省略 operation 时取 text；给了 path 也不会按结构取值 | 模型看似精确读取，实际读到整个 JSON 文本片段 |
| 公开读取另有旧帽 | reader 默认 8000、schema 最大 32000；agent 默认 24000，管理声明另有 1000 下限和 32000 上限 | 只改配置默认值不能贯通实际可读页；schema 与运行预算互相掣肘 |
| 路径说明互相矛盾 | `tool-results.md` 示例从 `data` 开始，但结构 reader 已把标准信封的 data 作为逻辑根 | 模型可能额外添加一层 `data`，读错路径 |
| 联系人混合两类对象 | `find_contacts(view=subjects|entries)` 同时承载当前主体发现和历史 Conversation 目录 | 参数含义随 view 改变，主体与历史入口的范围容易混淆 |
| 参数错误藏掉错误字段 | `capabilities/validation.py::_validation_detail` 对额外字段只报不允许未声明字段；`tool-kernel.md` 还明确要求隐藏未知字段名 | 模型不知道该删除或改正哪个参数 |
| 发送说明只认 Binding | `social/tools.py`、`prompting/contracts.py`、`agent_tools.py` 的错误指引及现行文档只强调 binding_id；服务实际也接受 conversation_id | 说明比执行合同更窄，可能多做查询或反复选择入口 |
| around 回显未应用条件 | `social/history.py` 的 around 不应用搜索筛选，却照抄日期与 request.order；实际邻文按事件 ID 升序拼接 | 返回看似已按日期过滤或按 recent 排序，实际没有 |

主要调用链：

- Core / Plugin → 固定能力目录和 schema 校验 → `MainAgentBackend` → typed outcome 与 capture → `ToolResultBudgeter` → 当前模型结果及原效果回执。
- Code 子调用 → 同一执行后端 → `receipt_view` → VM；Code 程序父结果另经 `driver._result_view/_bounded_result`，需核对父子两层展示。
- 超长结果 → 共享 `ToolArtifactRepository` → 公开 `read_tool_artifact` → 同一结果预算；reader 页不能再次套娃归档。
- Work accepted 回执 → `work_journal.effect_result` 原样恢复当时保存的结果字符串，同时保留独立执行证据和 Artifact 句柄；恢复不会重新跑新版 Budgeter。
- 联系人／会话声明 → `SOCIAL_TOOL_NAMES` → Core metadata → 社交适配器与读取 scope → 目录服务；Code 直调名单和固定 manifest 是另外两个消费者。

## 4 新结果交付合同

### 4.1 有效预算和默认值

本任务书拟定默认值为 **64000 个序列化工具结果 JSON 字符**，包括信封、正文、转义和分页元数据。它是可调整的展示政策，不是实测最优值、UTF-8 字节数或真实 Token 数。

有效字符预算 `B` 继续沿现有配置优先级：显式 `tooling.result_token_budget` 非空时取其四倍，否则取 `agent.tool_result_max_characters`。这里的四倍是已有近似换算，不冒充 tokenizer 结果。Main、公开 reader、Memory 结果交付和 CodeHost 使用同一有效预算来源，不再各写一套公式。token 覆盖默认继续为空，不同时设置一个新的默认 token 预算来盖掉人物／群的字符配置。

修改 `config.py`、`.env.example`、管理配置声明及真正读取预算的消费者。管理端把 1000 的经验下限改为表达正整数的 `minimum=1`，删除 32000 的经验上限；公开 reader 删除 32000 的 schema 帽。不能只删管理 minimum 后假定 `settings_domains.py` 的 gt=0 会约束热覆盖：当前 registry adapter 读取的 Settings 注解只是 int。复用现有配置校验 owner 表达正整数，不再增设另一层校验。`result_item_limit` 继续采用现有可空配置，默认不另设条目帽。

已持久化的 runtime override 仍优先于环境和默认值，不偷偷覆盖用户设置。今后若获准部署，应报告实际生效预算；改了默认值不能写成生产已上调。

64,000 相比 24,000 允许更大的结果一次进入模型，但也可能增加请求 Token 和模型处理时间。本任务减少的是可避免的“已有正文还要再读一轮”，不保证总延迟或内存占用降低。

### 4.2 完整结果和超长预览

预算内直接返回真实结果，保留原工具信封、数据、错误和完整可见内容对应的 `evidence_state`。Web 研究结果继续按原来源保存完整研究原件；保存原件与模型是否看见正文分别决定。不能简单删除研究归档条件，导致原件、capture 或后续来源读取一并消失。

超出字符或显式条目预算时：

- 保存本次工具实际取得的完整结果；模型收到真实内容的有界预览，而不是固定只返回类型、键名、数量和目录。
- 沿用顶层 `truncated`、`artifact_handle` 等实际消费者已经识别的字段。执行状态与正文展示完整性分开，不能把部分预览当成业务失败或完整内容。
- 预览给出实际 `path`、已展示范围和下一段读取参数；路径相对逻辑根，继续位置必须对应原件。可采用直接能传给 `read_tool_artifact` 的 `handle/operation/path/offset`，不新增签名游标、持久页状态或另一套分页协议。
- 字符串按原文 Unicode 字符计数；数组按完整子项；字典部分页沿 reader 现有稳定键序。不能用插入序预览的数量去续读排序后的字典。
- 内容仍可分页时展示实际内容。单个完整项放不下时，给出真实 oversized／预算不足事实和原路径；存在可下钻节点时再给具体更深路径。已经是标量叶或预算连一个字符也放不下时不伪造更深路径，不切坏 JSON，不用空页冒充 EOF。不能把所有超长结果重新退化成统一的空目录。
- 业务 `next_cursor/has_more/returned_count` 继续表示原查询结果；展示分页的 offset 不能冒充下一批聊天、记忆或搜索结果的查询游标。

复用 `tool_results/artifacts.py` 的结构与字符串分页语义、`tool_results/json_length.py` 的计量原语。从当前内存原值形成预览，不为了取预览先写完整原件再读回来；不为每个 Provider 复制一套截断器。

### 4.3 执行事实和来源

先安排必要错误与执行事实，再使用剩余预算展示正文。保留原 status、exit_code、pending、uncertain／unknown、原 operation_id／run_id、错误码和有用错误说明；不能认为现有 `_execution_envelope` 与 `_important_fields` 完全等价后直接删除后者。必要执行信封沿原软预算语义保留，不能因经验字符目标不足再否定已确认效果。

终端顶层 `ok` 可以只表示查询成功，进程非零退出、运行中或未知状态必须可见。发送、文件发布、附言等原分步回执不被预览抹掉；Artifact 保存失败不把已经成功的外部效果改成失败，也不提供重发资格。

Artifact 关闭或确实写入失败时，仍交付真实的有界内容和存储失败事实；没有成功保存的句柄就不承诺可续读。来源、身份或隐私拒绝沿原拒绝处理，不能被通用异常捕获转换为直接展示旧正文。

完整来源集合仍保存在 capture、typed outcome、原效果回执及 Artifact 的授权与来源元数据中。`ArtifactAccess` 继续只表达它现有的读取身份与范围，不为本次展示扩展另一份来源集合。完整 inline 保原证据；部分预览不宣称未展示的全文来源已经可见。延迟发布、读取后授权复核、跨会话副本清退及隐私删除保持原合同，不新增全局来源锁或影子账本。

### 4.4 Memory 和 Code

Memory 删除结果进入共同 Budgeter 前的逐条删尾及纯长度 `result_too_large` 否决。查询实际返回多少条、原证据和来源先按事实形成；展示长度交由共同入口处理。不因展示超长把成功读取统计成 unavailable，不改变检索算法、查询条目语义或记忆持久化模型。

Code 删除 `result_limit // 2` 的提前展示裁剪，由现有最终父结果计量决定是否需要 Artifact 和预览。完整子回执、composition 关联、stdout 截断事实与控制结果仍保存；模型需要据此查证的原 uncertain operation ID 等必要身份，不能只换成 hash 来凑预算。

区分两种原件：现有程序 `result_ref` 指程序返回值，`summary_ref` 指完整父结果。删除半预算裁剪后，如复用完整父结果作为原件，续读必须指向其中实际 result 路径；不能把两个引用当成同一种内容，也不要求为保留旧展示方式继续保存两份相同结果。旧 accepted 内容保持原样。

`codemode/api_projection.py::receipt_view` 目前从顶层 `truncated/result_unavailable` 推导 `complete`，从 `artifact_handle` 得到 `result_ref`，优先取 `data`。新格式必须贯通这些语义，不能只把截断标记藏在 data 内导致 VM 误认完整。这里只调整真正不一致的消费者，不另建 Code 结果协议。

## 5 读取与参数合同

### 5.1 read_tool_artifact

公开模型工具省略 `operation` 时默认 `get`，提供的 `path` 必须实际生效。结构路径使用相对逻辑根的字符串／整数数组；例如逻辑根是原信封的 data 时，读取其中 sources 使用 `["sources"]`，不能额外加一层 `data`。

`inspect`、`search`、`text`、`image` 继续按实际用途显式选择。工具说明不把 inspect 写成每次 get 的前置步骤；已有路径或续读参数时允许直接读。`text` 继续支持现有 query 与原文字符偏移，不新增自动猜操作或失败转模式的后备链。

公开入口省略 `limit` 时使用当前有效预算，不另设固定 8000。显式 limit 在 inspect／get 集合读取中表示键／子项数，在 search 中表示匹配对象数，在 get 字符串和 text 中表示原文字符数；实际整页仍受包含信封的 `B` 约束。声明、handler、字段说明、示例和分页结果必须一致。

底层 `ToolArtifactRepository.read()` 的历史 text／8000 默认属于内部 reader，不机械修改。已接受调用、旧 Code 回填和原持久结果按原合同只读恢复；不为新公开默认值改写旧参数或重派工具。reader 页本身不生成下一层 Artifact。

### 5.2 参数校验反馈

保留固定 schema 的真实校验。错误应明确字段路径、校验类别、缺少字段、预期类型或允许值；额外字段错误应指出实际多余的字段名称，便于模型直接修正，不只说“不允许未声明字段”。

直接修改 `_validation_detail` 及 `tool-kernel.md` 中“隐藏未知字段名”的旧规则，沿现有有界错误结果返回定位信息。不要回显整份参数值或底层异常正文，不新增字段脱敏服务、自动补参、猜测改名、自动重试或另一次模型调用。

错误格式化不改变 executed=false、mutation_committed=false、原 admission 和真实尝试预算的含义。已有缺参／类型／枚举反馈可用的部分复用，不为风格统一重写整个校验器。

### 5.3 send 的入口说明

按现有执行事实修正工具说明、字段说明、共享程序规则和错误修正提示：App/ACP 显式发送给 person 时，可用 `conversation_id` 或 `binding_id` 明确入口；不是只能提供 Binding。

保持既有路由语义：原已准备请求继续使用其保存路由；新请求明确指定 Conversation 时选该入口，否则再按 Binding／既有当前会话和人物主动路由处理。Conversation 与 Binding 同时提供时，如实说明当前 Conversation 优先，不新增二者必须相同的防御性校验或额外目录查询。

省略 target 仍回复当前入口；已知人物 ID 不新增强制 find_contacts。身份归属、当前授权、原发送 Presence、内部 reply_to_event_id 和未知发送禁止盲目重发的事实保持原样。

### 5.4 query_chat_history 的 around

保留一个历史查询工具及现有 around 合同：event_id／原 operation 锚点定位中心，target/source 取真实交集，before/after 读取原会话邻文，继续应用 event_kind 与实际读取授权。邻文按事件 ID 升序呈现前文、中心、后文。

现行说明已经明确 around 不应用关键词、作者、日期和附件筛选。本轮不把它改成会漏邻文的过滤查询，也不为了不同 view 重构全体 History DTO、SDK 或数据库查询器。

修正结果构造：around 不回显没有应用的 start_at/end_at，也不照抄未采用的 request.order；如保留 order 字段，则报告实际 `oldest`。字段说明与示例明确 cursor/limit/order 属于查询页，context_before/context_after 沿现有 recent/search 结果邻文语义，around 用 before/after；不新增 ignored-fields 状态、条件校验协调器或无必要的拒绝分支。recent/search 的现有筛选与原游标保持，不意外删掉 recent 已支持的邻文能力。

顶层 person_id 作为作者筛选、target.person_id 作为私聊范围的区别继续明确，不借此全局改名迁移无关 DTO。

### 9.3 结束时保留可复现产物

每个 E2E 场景结束时留下可核验的执行产物：复现命令、代码提交、固定输入与有效配置、实际模型可见结果／续读页、原件的 SHA-256 和长度、重组内容及核对结果、相关执行 ID 与必要的回执记录。按场景保存实际涉及的内容，不复制全库或全量诊断。

原件文件摘要与续读值核对分别处理：JSON 页重组后比较同一逻辑根或路径的结构值，字符串比较原文字符；需要摘要对照时双方采用同一序列化方式，不拿带信封的原件文件字节与 data 值直接比 hash。

复用现有简单 evidence.json 写法即可，不另建验收工作流、运行时状态或证据服务。证据必须由本轮测试实际写出；仅扩大 upload 路径、只保存在内存或只 print 不算接通。成功与失败都保留当时已取得的数据，可在选定场景的 finally／fixture teardown 写出；不吞掉原测试异常，不重跑业务来制造成功产物。目录与复现命令随产物说明保存。重跑通过也不能覆盖原失败证据或被描述成已定位原失败原因。

Host 捕获的 ChatRequest 只证明 Host 载荷。需要证明协议实际发送内容时，复用真实 Provider 序列化与 `httpx.MockTransport` 捕获 HTTP JSON，不能用 FakeLLMProvider 的请求记录冒充 wire。Code 真 worker 的结果与离线 fake 分支分别记录；环境缺少实际 worker 时保留未验收事实，不用跳过当通过。

现有 `test_plugin_result_access.py` 的小研究结果场景仍要保原 scope、句柄和完整归档；其新增正文可见预期优先并入完整 E2E。`test_memory_result_grounding.py` 的业务层裁剪断言及 `test_codemode_composition.py` 的半预算展示期望随新合同修正，保留完整事实和原回执覆盖，不新增写完实现再补的单测。

最新 main 已删除的 `test_tool_result_json_length.py` 等纯局部测试不恢复；JSON 计量和续读正确性由真实 Main→归档→公开 reader 往返及原件核对证明。其他现存单元测试是审查线索，不是要求逐文件补测的施工清单。

先安排上述 E2E，再做匹配最终 diff 的受影响回归与静态检查；有新失败再扩展必要范围，不重复无关全量验证。真实 Provider 耗时、自然流量、生产资源和部署各自另记；减少读取轮次不独立证明任务完成或上游提速。

## 10 删除清单和实施顺序

应明确删除或改写：

- Web 研究结果因工具名称而强制只返回 manifest 的展示条件；保留归档。
- Memory 在共同结果预算前的删尾和纯展示长度否决。
- Code 的半预算提前展示裁剪。
- 公开 reader 默认 8000、schema 32000，以及管理端 1000／32000 的重复经验门槛。
- 公开 reader 省略操作却走 text、导致 path 被忽略的旧默认；保留内部历史 reader。
- 现行文档错误的 data 路径示例、每次先 inspect 的误导性指引。
- `find_contacts` 新调用中的 subjects／entries 混合 view 和对应动态参数分支；不删除旧事实与只读回执。
- 错误反馈隐藏未知字段名的规则，以及发送只能通过 binding_id 明确入口的矛盾说明。
- around 未实际应用的日期与 request.order 回显。
- 冻结上述限制的测试断言；不删除真实授权、分页、来源和恢复覆盖。

建议实施顺序：

1. 先定义并写出第 9 节 E2E 场景的输入、预期、失败分支和结束产物，明确旧断言的目标行为与 CI 收集／输出路径；确需隔离的部分先列全失败情况。不得先写实现再补单元测试。
2. 再统一预算来源与公开 reader 合同，调整完整／超长交付和 Memory／Code 消费，用同一套端到端输入与原件验证。联系人拆分和参数反馈可独立推进，随后贯通固定 manifest、直调、授权与原恢复；对应测试夹具、旧调用和 CI 接线与各项改动同时落实。
3. 修正 send／around 的说明和回显，同步现行文档与配置示例；优先在实际入口完成 E2E，不以局部 helper 通过代替，也不把测试及 CI 留到最后补救。
4. 完成场景产物、与最终 diff 匹配的受影响回归和静态检查，记录本地修改、验证、提交、PR、合并和上线各自的实际状态。

先前停下的草稿只能逐项对照本任务书评审，不能整包视为获批；尤其核对它是否丢了执行字段、准确续读位置或存储失败事实。

## 11 本轮不扩展的范围

本轮提高的是模型可见结果和 Artifact 读取页，不按比例扩大独立资源策略：工具原件目前单件 64 MiB／总登记 512 MiB，终端单页 32768 字节、滚动日志约 8 MiB，Code VM 结果 256 KiB／stdout 64 KiB。它们各有不同 owner 和生命周期，本任务不把这些数值当成模型字符预算，也不宣称这些经验策略永久不可调整。

附件文档 inspect 目前还有提取前缀 20000 字符／20 页，并已提供截断覆盖信息；它是原件提取范围，不是本次 24000 字符预算的消费者。不得声称扩大通用预算后就读取了整份文档；本轮不改提取器。

结构化图片候选搜索与原图下载、终端网络故障、上游模型排队／生成、上下文缓存、人物资料加载、JEV／engage、任务调度和数据库性能另行处理。本任务不以新增这些能力、全量工具改名或重构所有提示词作为完成条件。
