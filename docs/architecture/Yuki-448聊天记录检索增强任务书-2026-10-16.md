## 0. 結論摘要

1. **問題主要在查詢表達與中文匹配，其次是粒度與回應合同。**多關鍵詞被包成一個短語；兩字詞無法進入 trigram 索引，放進 `NOT` 也不排除；沒有繁簡與全半形正規化；時間篩選有 8 小時偏移；私聊人物篩選會混入 Yuki 自己的發言；結果是孤立消息，也不告知是否截斷（§2.3，〔實驗 E1、E3〕）。
2. **字面匹配定義與候選完整性是第一不變量。**凡符合當前匹配定義的消息都必須進入候選集合；原文核驗只剔除多召回的候選，不能補救漏召回（§6.2）。首版設計（CJK 單字＋雙字詞元＋英數整詞）違反此不變量，`phone` 找不到 `iPhone`，已撤回〔實驗 E2〕。
3. **推薦索引：正規化文字上的 1／2／3 字元 n-gram，存於 contentless-delete FTS5 表。**一字查單字詞元，兩字查雙字詞元，三字以上查全部三字詞元的 AND。400 條隨機與針對性查詢上漏召回為 0〔實驗 E2〕。
4. **「哪些消息共同滿足查詢」與「回傳多少上下文」完全分開。**證據組是命中序列上的最小覆蓋窗口，只受證據組跨度限制；上下文只影響展示，不改變是否命中。審查提出的 25 條命中反例，現在回傳證據組 {#12, #13}〔實驗 E6〕。
5. **掃描以「最密集需求決定下界」推進。**每次請求的工作量有上限；結果狀態分為「確認還有更多」「搜尋未完成」「已窮盡」三種；預設排序改為 `recent`。罕見詞不會被常見詞擠出〔實驗 E7〕。
6. **排序不使用 BM25。**FTS5 `bm25()` 越低越好，對無關文件的插入敏感，按消息累加時偏好消息多的組合〔實驗 E5〕。`relevance` 改用穩定的局部特徵，以字典序比較。
7. **索引生命週期只用一套機制。**純 SQL 觸發器寫入待索引佇列，單一索引器寫入 FTS；首次建置、匹配定義改版與損壞重建都由「由新到舊的回填前沿」處理。前沿以上走索引，前沿以下在每次請求的工作量內直接核驗。遷移只有 DDL，不在寫交易中掃描歷史〔實驗 E4〕。
8. **詞法檢索列為本任務的優先方案。**語義召回是否必要，由 P0 評估集中的「改寫類」查詢量化後決定（P4）；本文不預先斷言它不必要。

## 1. 問題、目標與邊界

### 1.1 問題

使用者和 Yuki 需要「找回原話、核對誰在何時說過什麼」。目前 `search_chat_history` 只做字面匹配，經常查不到；查到時也只是孤立消息，Agent 還得逐條呼叫 `get_chat_history_around` 補上下文。

### 1.2 目標

以可驗證的指標描述「一流水準」，缺乏實測時不宣稱已達成：

| 維度 | 驗證方式 |
| --- | --- |
| 檢索完整性 | 候選完整性的性質測試（V12–V14）；評估集上完整必要證據的取得率（§10.2） |
| 檢索品質 | 在相同的回傳消息數或字元預算下，比較現有實作、詞法強基線與各消融版本 |
| 上下文完整性 | 必要上下文覆蓋率、誤合併率、發言歸屬正確率 |
| 查詢效率 | 合成資料上各查詢類別的 p50／p95 延遲；每次請求的工作量上限 |
| 維護成本 | 不新增服務與外部套件；索引寫入成本、回填與重建耗時、磁碟占用可量測 |

### 1.3 職責邊界

| 能力 | 職責 | 本任務是否修改 |
| --- | --- | --- |
| `search_chat_history`／`get_chat_history_around`／`get_recent_chat_history` | 找回原始聊天、核對證據 | 是，主要對象 |
| `search_memory` 與 Memory 事實 | 抽取後的長期事實，各有證據與權限 | 否；只重用其正規化與向量儲存的做法 |
| 公共 Compact 檢查點與摘要 | 上下文壓縮 | 否；摘要不作為檢索證據 |
| Work 任務日誌與執行回執 | 執行事實 | 否 |
| `read_conversation_history`（社交工具） | 從 OneBot 即時讀取明確的人或群 | 否；跨會話搜尋另由 D01 決定 |

### 2.4 設計審查實驗（合成資料）

**方法與環境。**腳本為 [`chat_search_probe.py`](experiments/chat-search-448-2026-10-16/chat_search_probe.py)，只用 Python 標準庫與 `sqlite3`（E3 另用倉庫 `.venv` 中的 SQLAlchemy 確認實際綁定行為），不讀真實聊天、不連網。原始輸出為 [`results.json`](experiments/chat-search-448-2026-10-16/results.json)，重現方式見[實驗說明](experiments/chat-search-448-2026-10-16/README.md)。

| 項目 | 值 |
| --- | --- |
| 機器 | Apple M4，macOS 26.6.2（arm64） |
| 軟體 | Python 3.12.7（倉庫 `.venv`），SQLite 3.45.3 |
| 資料 | `generate(200000, seed=448)`：4,000 個由 1–4 個漢字組成的詞（字池含繁體與簡體），依 Zipf 權重每條取 1–9 個；12% 插入英數、型號或網址，8% 插入表情、組合字元或相容字元，0–2 個標點或空白；分佈在 20 個會話 |

| 計時口徑 | 預熱 1 次後重複 30 次，取中位數與第 95 百分位；單執行緒、本地 SSD、rollback journal；索引大小 = `VACUUM` 後檔案大小減去只含原表時的大小 |
| 統計限制 | 合成分佈不代表真實群聊；延遲數字只用於方案間的相對比較，不作為生產效能承諾 |

**結果。**計數類結果（漏召回、候選數、證據組、分頁迭代）在兩次完整執行中相同；耗時取第二次執行。

| 編號 | 問題 | 結果 |
| --- | --- | --- |
| E1 | 現行 trigram 的實際行為 | `"电吉他 三千"` 無結果；未加引號的 `电吉他 三千` 回傳 #1、#8（兩字詞「三千」被忽略）；`"三千"`、`"报销"`、`"報銷单"` 無結果；`"电吉他" NOT "不买"` 仍回傳 #8，`NOT "不买电"` 才排除；`"PR #448"` 與 `"pr #448"` 都命中 #6，但都不命中全形的 #7 |
| E2 | 候選完整性與成本 | 見 §5.2。v1 定義下，`ngram123`、`trigram_plus_12`、`ngram23_prefix` 在 400 條查詢上漏召回為 0；首版 `cjk12_words` 有 61 條查詢漏召回（如 `phone`、`15pro`、`#448`）；現行 trigram 有 181 條（它使用 v0 定義，差異主要來自正規化與一兩字詞）。v0 定義下，現行 trigram＋`instr(lower())` 在 50,000 條、300 條查詢上漏召回為 0。高亮偏移示例見 §6.1 |
| E3 | 時間參數綁定 | SQLAlchemy 存為 `2026-10-09 16:30:00.000000`（UTC，即 UTC+8 的 10-10 00:30）。以 `text()` 綁定 `2026-10-10T00:00:00+08:00` 或無時區的 `2026-10-10T00:00:00` 作為 `after`，都查不到這條消息；換算成 UTC 無時區文字後可以查到 |
| E4 | contentless-delete 操作與遷移持鎖 | 支援以 rowid `DELETE`、`INSERT OR REPLACE`、`integrity-check`、`optimize`、`delete-all`；`rebuild` 報錯「may not be used with a contentless fts5 table」，FTS5 `delete` 命令報錯；不能讀回欄位值。100 萬列窄表上，單一 `INSERT…SELECT` 持鎖 0.12 秒；以 5,000 列 keyset 分 201 批，每批中位數 0.62 毫秒、最大 2.54 毫秒 |
| E5 | `bm25()` | 越低越相關（`ORDER BY rank` 先回傳 −6.49，再回傳 −6.33）；插入 50 條無關文件後，同一文件由 −6.33 變為 −6.55；同時含兩詞的一條消息為 −11.01，兩條各含一詞的消息累加為 −12.65，累加後反而排得更前 |
| E6 | 證據組 | S14 反例：新演算法得 [#12, #13]；首版「在最大間隔切開後丟棄」得空集合；首版在間隔都相等時得 [#1, #24] 這種過寬的片段。`A B A` 得 [#1,#2]、[#2,#3]；三需求得 [#2, #9]；A、C 交替後出現 B 只得 [#28, #31]，不遞移串連 |
| E7 | 分頁推進（機制模擬） | 20 萬條、常見詞 30%、罕見詞 3 次（#500、#40000、#199990）、每需求預算 2,000：31 次迭代掃完，三次罕見命中都進入已取全的區間；只取「最新 2,000 個候選」只含 #199990 |

完整 `ngram123` 等方案的成本與延遲表見 §5.2。

### 4.2 使用情境（S）

所有對話皆為合成資料。

**S01 碎句與交錯發言**

```text
#101 甲 10:00 我想买电吉他
#102 乙 10:00 我先去吃饭
#103 甲 10:01 预算大概三千
```

查詢 `terms=["电吉他","三千"]`：證據組為 {#101, #103}（最小覆蓋窗口）。#102 位於兩個必要命中之間，以 `context` 出現，不計命中、不歸甲。`terms_by_sender` 為 `{甲: [电吉他, 三千]}`。把 `context_before`／`context_after` 設為 0 時，證據組不變，片段只少了窗口外的上下文；#102 仍作為核心內的消息顯示（§6.5）。

**S02 同詞不同事**：「电吉他」與「三千」相隔超過證據組跨度上限（§6.4）時不成組；回應 `fragments=[]`，並以 `term_hits` 回報各詞命中數。

**S03 繁簡**：「報銷」與「报销」互相命中；回傳原文不改字。

**S04 空白與全半形**：`PR #448`、`PR#448`、`ＰＲ＃４４８` 互相命中（v1 刪除全部空白、NFKC 折疊全形）；`PR 448` 不命中 `PR #448`，因為 `#` 保留。

**S05 英數內部子串**：`phone` 命中 `iPhone15Pro`；`15pro`、`example.com`、`a?b=1` 命中對應原文。

**S06 「上週某人提過的餐廳」**：Agent 把「上週」解析為時間範圍，把「某人」以 `find_contacts` 解析為 `sender`，再以 `any_of=["餐厅","饭店","店","吃"]` 搜尋。工具回顯 `time_range` 與 `sender`。

**S07 更正前後**

```text
#301 甲 9/01 预算三千
#350 甲 9/05 不对，预算改成五千
```

查詢 `terms=["预算"]` 回傳兩個證據組，預設 `recent` 讓 #350 在前；工具不去重、不判斷哪個為真。

**S08 排除**：`terms=["电吉他"], exclude=["不买"]` 不把「不买电吉他了」作為命中；它若落在其他片段的上下文中，仍以 `context` 出現。

**S09 相近金額**：查「三千」命中「三千五」（子串），不命中「两千九」「3000」「3k」。

**S10 無結果與預算用完**：無命中且已掃到 floor 時 `result_state="exhausted"`；常見詞用完本次請求的工作量時 `result_state="incomplete"`，附游標（§6.7）。

**S11 索引建置中**：前沿以下的舊消息在工作量內直接核驗；本次未掃完時 `result_state="incomplete"`，續查可完成（§7.4）。

**S12 刪除與遺忘**：遺忘的事件從帳本、索引、佇列中刪除；後續查詢、上下文、回填與重建都不再出現。

**S13 generation 重置**：floor 之前的事件不作命中、上下文或被回覆原文；舊游標回 `cursor_stale`。

**S14 審查反例**：25 條連續命中，#1–#12 只含 A，#13–#25 只含 B，相鄰命中都在跨度規則內，最大時間間隔在 #12、#13 之間。證據組為 {#12, #13}，與上下文設定和片段上限無關〔實驗 E6〕。

## 6. 匹配定義與查詢合同

### 6.1 匹配定義與正規化

一條消息的可匹配欄位為 `content` 與 `audio_transcript`，分別匹配，不跨欄位拼接。`visual_summary` 不參與（D04）。

**`casefold_ascii_v0`（P1 至 v1 索引上線前）**

- `fold0(x)` = 去掉首尾空白後，把 ASCII `A–Z` 轉小寫，其他字元不變。
- 詞 t 命中欄位 f ⇔ `fold0(t)` 非空且是 `fold0(f)` 的子串。

**`normalized_v1`（P2 起）**

- `norm(x)`：把原文以貪婪方式切成**最小正規化單元**：從當前位置起，單元 u 持續吸收下一個字元 c，條件是 `fold(u + c) ≠ fold(u) + fold(c)`。組合字元、半形濁音符號、連接型諺文字母因此留在同一單元。
- 每個單元套用 `fold`，順序固定：
  1. NFKC；
  2. `str.casefold()`；
  3. 再做一次 NFKC（casefold 的輸出可能不是 NFKC）；
  4. 繁轉簡逐字映射：OpenCC `ver.1.4.2`（commit `025f371d`）的 `data/dictionary/TSCharacters.txt`。4,148 個來源字皆為單一字元；其中 996 個有多個候選，一律取第一個，第一個候選皆為單一字元；
  5. 刪除所有 Unicode 空白字元（`str.isspace()` 為真者，含換行與全形空白）。
- 詞 t 命中欄位 f ⇔ `norm(t)` 非空且是 `norm(f)` 的子串。

**刪除空白的產品含義**〔審查〕：`PR #448`／`PR#448`、「報 銷」／「报销」、跨換行的同一句都能互相找到；代價是英文詞界消失，`new york` 也會命中 `renewyorkshire`。聊天搜尋中，空白不一致造成的漏查比英文詞界誤命中更常見；誤命中由 Agent 閱讀原文與高亮辨別。若 P0 評估顯示英文誤命中明顯（X06），可在 v2 改為「空白折疊為單一空格」，屬匹配定義改版（§7.5）。

**高亮偏移**：每個正規化輸出字元記錄其所屬單元在原文中的 `[start, end)`。一個匹配的高亮區間為「第一個輸出字元所屬單元的起點」到「最後一個輸出字元所屬單元的終點」。字元展開（`㎏`→`kg`）時，查 `k` 會高亮整個 `㎏`；字元合併（`e`＋`◌́`→`é`）時高亮兩個原字元；被刪的空白若位於匹配中間，會落在區間內。偏移單位是 Unicode code point。〔實驗 E2〕：`PR #448` 在 `see ＰＲ＃４４８ ok` 得 `[4,10)`；`k` 在 `5㎏` 得 `[1,2)`；`é` 在 `cafe◌́!` 得 `[3,5)`；`报销` 在 `報 銷單` 得 `[0,3)`；`ガ` 在 `ｶﾞｲﾄﾞ` 得 `[0,2)`。

### 6.2 候選完整性不變量

> **C-INV**：對當前範圍內任一消息 m、任一詞 t，若 t 依當前匹配定義命中 m，則 m 屬於 t 的候選集合。

候選可以多召回，由原文核驗剔除；不得漏召回。

| 定義 | 候選來源 | 為何成立 |
| --- | --- | --- |
| v0，`len(fold0(t)) ≥ 3` | 現行 trigram 表的短語查詢 `"t"` | trigram 的大小寫折疊對每個字元一對一且涵蓋 ASCII，fold0 的子串關係在逐字映射下保持〔審查〕；〔實驗 E2〕300 條查詢無漏召回 |
| v0，長度 1–2 | `instr(lower(f), lower(t))`，在工作量內掃描 | SQLite 未編譯 ICU 時 `lower()` 只折疊 ASCII，與 fold0 一致 |
| v1，已索引事件 | 長度 1 查單字詞元；長度 2 查雙字詞元；長度 ≥ 3 查全部三字詞元的 AND，限定在同一欄位 | 若 s 是 `norm(f)` 的子串，s 的每個 n-gram 都是 `norm(f)` 的 n-gram |
| v1，佇列中或前沿以下的事件 | 直接讀原文、以 `norm` 核驗（§7.4） | 不依賴索引 |

C-INV 以性質測試驗收（V12–V14）：隨機生成語料與查詢，與暴力比對結果相比，漏召回必須為 0。

```json
    "context_before": {"type": "integer", "minimum": 0},
    "context_after":  {"type": "integer", "minimum": 0},
    "limit":   {"type": "integer", "minimum": 1, "description": "證據組數"},
    "cursor":  {"type": "string"}
  }
}
```

**文字規則**（執行處核驗；錯誤一律回 `invalid_arguments` 並指出欄位）：

| 編號 | 規則 |
| --- | --- |
| A-1 | 至少需要一個條件：`terms`、`any_of`、`sender`、`has`、`after`、`before` 之一。只帶 `exclude` 不算條件 |
| A-2 | 陣列欄位若出現，必須非空；`has=[]`、`terms=[]` 都無效，不視為省略 |
| A-3 | 詞在當前匹配定義下折疊後為空（例如只有空白）時無效 |
| A-4 | 同一陣列內折疊後相同的詞合併為一個；回應 `query` 回顯折疊、去重後的列表 |
| A-5 | 同一詞同時出現在 `terms` 與 `exclude` 時照常執行（結果必為空），不另設拒絕 |
| A-6 | `after` 不早於 `before` 時無效 |
| A-7 | 只帶篩選而無詞（純時間、純發言人、純 `has`）時，每條符合篩選的消息自成一個證據組 |
| A-8 | `limit` 大於 `chat_search_max_limit` 時以上限執行，回應 `limit_applied` 註明；**這本身不代表還有更多** |
| A-9 | 續查時，匹配相關欄位（`terms`、`any_of`、`exclude`、`match_within`、`sender`、`after`、`before`、`has`、`order`）必須與首頁相同；`limit`、`context_before`、`context_after` 可以改變。不一致時回 `cursor_stale` |
| A-10 | `sender` 不唯一時回 `sender_ambiguous` 與候選；查無時回 `sender_not_found`；不猜測 |

**時間解讀**：帶時區照用；不帶時區按 `default_timezone`（UTC+8）；換算為 UTC 後，以與 `occurred_at` 儲存格式相同的無時區文字綁定（修正 G07，〔實驗 E3〕）。

**發言人**：解析為 canonical Person（以 `author_person_id` 篩選）或 Yuki（`author_kind='yuki'`），不再使用 `private_peer_user_id`（修正 G08）。

工具說明文字（約束 Agent 用法，不放進人格提示）：

> 在當前會話帳本中查找原話。terms 須全部出現在同一證據組，any_of 出現其一即可，兩者都是字面子串，不做同義擴展；需要同義詞、別名或數字寫法時自行列入 any_of。只搜尋當前會話。result_state 為 exhausted 時才代表本次條件已查完；為 incomplete 時可用 next_cursor 續查。role=hit 的消息才是命中，context 只是鄰近原文；引用時以各消息自己的發言人為準。

### 6.4 證據組：哪些消息共同滿足查詢

**定義**：

- **需求集合 Q**：`terms` 中每個詞各為一個需求；若有 `any_of`，整個 `any_of` 合為一個需求。只帶篩選時 Q 為空。
- **命中消息 H**：範圍內、符合時間／`sender`／`has` 篩選、至少滿足 Q 中一個需求、且不含任何 `exclude` 詞的消息，依 `event_id` 排序。每條命中 h 有 `covers(h) ⊆ Q`。
- **跨度**：兩條消息之間的**消息距離** = 兩者之間（不含兩端）的範圍內 keeper `message` 事件數＋1；**時間跨度** = 兩者 `occurred_at` 之差。

**證據組**：

| 情形 | 證據組 |
| --- | --- |
| `match_within=message`，或 Q 為空，或 \|Q\| = 1 | 每條覆蓋全部 Q 的命中自成一組 |
| `match_within=group`（預設）且 \|Q\| ≥ 2 | H 上的**最小覆蓋窗口** `[l, r]`：窗口內命中的 covers 聯集等於 Q，且去掉左端或右端都會失去覆蓋；同時 l 到 r 的消息距離 ≤ `chat_search_group_max_messages`、時間跨度 ≤ `chat_search_group_max_minutes` |

**必要命中**：左端、右端，以及左右端都未覆蓋的需求各取窗口內最早覆蓋它的命中。必要命中數 ≤ |Q|。

**性質**〔審查〕：

1. **不漏組**：若存在一組命中在跨度限制內共同覆蓋 Q，則從它的範圍兩端收縮得到的最小覆蓋窗口也在限制內，且會被枚舉到。因此「先按覆蓋枚舉最小窗口，再以跨度過濾」不會漏掉任何可成立的證據。
2. **不遞移**：證據組彼此獨立，不因中間命中相連而串成長鏈。〔實驗 E6〕A、C 每 10 分鐘交替、最後出現 B 時，只得到靠近 B 的窗口 #28–#31。
3. **與上下文無關**：證據組的定義不含 `context_before`／`context_after`、片段上限或展示合併。
4. **反例**〔實驗 E6〕：S14 得到唯一證據組 {#12, #13}；首版「合併後在最大間隔處切開再丟棄」得到空集合。
5. **重疊**：`A B A` 得到兩個證據組 [#1,#2] 與 [#2,#3]，展示時合併（§6.5）。

**演算法**：在已取得的命中上以雙指標掃描（右指標前進、左指標盡量收縮，只記錄右端也必要的窗口），時間 O(|H|·|Q|)。窗口的消息距離以範圍限定的計數查詢求得，以 `LIMIT group_max_messages + 1` 封頂。

### 6.5 展示片段：回傳多少上下文

每頁選出的證據組依下列步驟組成片段。這些步驟只影響展示，不改變 §6.4 的結果。

1. **核心**：第一個到最後一個必要命中之間的全部消息。超過 `chat_search_fragment_max_events` 時只保留必要命中，其餘以 `gap_before`（被省略的消息數）標示。
2. **上下文**：核心之前取 `context_before` 條、之後取 `context_after` 條（同 Conversation、floor 之後、keeper、`message`）。
3. **被回覆原文**：每個必要命中若有 `reply_to_event_id`，且原消息在範圍內、floor 之後，就加入，每個必要命中最多一條。
4. **合併**：同一頁的片段，事件範圍重疊或相鄰時合併（只是展示上的遞移合併）；合併後若超過上限，只省略上下文，**不省略必要命中**，必要時以 `gap_before` 標示。
5. **角色與去重**：每個事件在整個回應中只出現一次，角色優先順序為「必要命中」＞「非必要命中」＞「被回覆原文」＞「上下文」。一個事件可放入多個片段時，放在它角色最高的片段；角色相同則放在排名較前的片段，其他片段以 `see_also_event_ids` 引用。
6. **排列**：片段內事件按 `event_id` 正序；片段之間依其中最前的證據組排名。

### 6.6 排序

| `order` | 鍵（依序比較） | 範圍 |
| --- | --- | --- |
| `recent`（預設） | 證據組最後一個必要命中的 `event_id` 遞減 | 全局精確（§6.7） |
| `oldest` | 證據組第一個必要命中的 `event_id` 遞增 | 全局精確 |
| `relevance` | ① 消息距離遞增；② 時間跨度遞增；③ 必要命中所在欄位的正規化字元總數遞增（越短越聚焦）；④ 最後一個必要命中的 `event_id` 遞減；⑤ 第一個必要命中的 `event_id` 遞減 | 回報 `ranking_scope` 為 `complete` 或 `scanned_range` |

**不使用 BM25 的理由**〔實驗 E5〕：

- FTS5 `bm25()` 越低越相關。同一組資料插入 50 條無關文件後，同一文件的分數由 −6.33 變為 −6.55；分頁期間新增消息會改變排名。
- 按消息累加時，兩條消息的組合（−12.65）比一條同時含兩詞的消息（−11.01）分數更低，因而被排得更前，偏好消息多的組合。
- 單詞查詢時證據組都是單條消息，BM25 主要反映消息長度；鍵 ③ 以穩定的方式表達同一訊號。

**`single_sender_cover` 不作排序鍵**〔審查〕：甲問「預算多少？」、乙立刻答「三千」，與甲在 15 條之外自己補一句「三千」相比，前者往往更相關。此欄位只作為事實回報；它作為平手鍵的效果由 P0 消融比較（V62）。

**預設改為 `recent`**〔審查〕：它在分頁上全局精確，與微信的查找順序一致；需要按鄰近度挑選時，Agent 再指定 `relevance`。

### 6.7 掃描、預算、結果狀態與游標

**快照上界**：首頁取當前範圍內最大的 message `event_id` 為 `U`，寫入游標；之後各頁只看 `event_id ≤ U`。新消息需要新查詢才能看到。

**每次迭代**（以 `recent` 為例；`oldest` 方向相反）：

1. 設當前上界 C（首頁為 U＋1）。對 Q 中每個需求（只帶篩選時為「篩選本身」），取 `event_id < C` 的候選，按 `event_id` 遞減，讀取上限為 `chat_search_term_budget`。候選來源依 §6.2：索引查詢讀的是候選列；v0 短詞與前沿以下的直接核驗讀的是掃描列，同一段掃描由所有需求共用。`any_of` 需求的候選是各成員詞候選的聯集，它的覆蓋下界取各成員下界的最大值。時間、`sender`、`has` 篩選在候選查詢中一併套用；`exclude` 在原文核驗時套用，不另行取候選。
2. 某來源讀滿上限時，它的覆蓋下界是最後讀到的 `event_id`；否則是 floor。**區段下界 L = 各需求覆蓋下界的最大值。**區間 (L, C) 內每個需求的候選都已取全。
3. **邊界補取**：從 L 往下，在 `chat_search_group_max_messages` 條消息的範圍內補取各需求的候選（每需求最多這麼多）。如此，最後必要命中位於 (L, C) 的證據組，其全部命中都已知。
4. 原文核驗、套用 `exclude`、計算證據組，輸出最後必要命中位於 (L, C) 的證據組，按排序鍵排列。
5. 若已得 `limit + 1` 組就停止；否則若 L > floor 且本次請求讀取的候選與掃描列數合計未超過 `chat_search_request_budget`，以 C = L＋1 重複。

**常見詞不會擠掉罕見詞**：區段下界由最密集的需求決定，罕見需求在 (L, C) 內一定取全。每次迭代至少前進「最密集需求的一個預算量」，不會停在原地重查同一批候選。〔實驗 E7〕20 萬條消息、常見詞占 30%、罕見詞 3 次、預算 2,000 時，31 次迭代掃完全部，三次罕見命中都被找到；若只取「最新 2,000 個候選」，只找得到最新的一次。

**結果狀態**：

| `result_state` | 條件 | `next_cursor` |
| --- | --- | --- |
| `more` | 已實際找到第 `limit + 1` 個證據組 | 有；指向本頁最後一組之後 |
| `incomplete` | 本次請求工作量用完，L 尚未到 floor；本頁可能少於 `limit` 組，甚至為 0 組 | 有；指向 L＋1 |
| `exhausted` | 已掃到 floor，本頁之後沒有其他證據組 | `null` |

`limit_applied` 只說明實際採用的上限，不影響狀態。

**`relevance` 的排名範圍**：從 U 往下掃描，直到工作量用完或到達 floor。到達 floor 時，對範圍內全部證據組排名，`ranking_scope="complete"`；否則只在已掃描區間 [L, U] 內排名，`ranking_scope="scanned_range"` 並回報區間，此時的排名是局部的。續頁在游標記錄的固定區間 [L, U] 內重算排名並接續輸出；該區間輸出完畢後，再往下掃下一段並另行排名。重算成本受同一工作量上限約束。

**游標內容**：格式版本、匹配欄位的雜湊、`conversation_id`、`generation`、floor、`match_definition`、U、方向，以及續查位置（`recent`／`oldest` 為最後輸出證據組的端點 `event_id` 或區段下界；`relevance` 為區間與最後輸出的排序鍵），以 base64url 編碼的 JSON 傳遞。範圍由執行處依當前 runtime 重新核驗；游標只表示位置，不授予權限，因此不另加簽章。

**分頁期間的變化**〔審查〕：

| 變化 | 行為 |
| --- | --- |
| 新消息 | 不出現在已有游標的續頁中（快照上界 U） |
| 刪除、遺忘 | 被刪事件不再出現。依端點分頁不會重複輸出同一證據組；若被刪事件改變了某組的端點，該組可能被略過 |
| ASR 轉錄更新 | 新命中若形成端點在游標之前的組，可能被略過；不會重複 |
| floor、generation 改變；`match_definition` 切換；`conversation_id` 不符；匹配欄位改變 | `cursor_stale`，需重新查詢 |
| FTS 統計變化 | 排序不使用 BM25，不受影響 |

**完整性邊界**：`exhausted` 表示在首頁快照與當前匹配定義下已查完。上表的「可能被略過」只在分頁期間資料發生變更時出現，重新查詢即可得到當前的完整結果。

### 6.10 插件 API

Plugin API 3.5 的 `search_history(query, limit)` 簽名與語義保留：

- `query` 作為單一詞（`terms=[query]`），使用當前匹配定義。
- `limit` 仍是**消息數**，沿用 `_bounded_limit`；回傳型別仍為 `tuple[CurrentMessage, ...]`。
- 範圍仍是當前會話 scope 與 floor。
- 回傳最近的 `limit` 條命中消息，按時間正序，與現行行為一致。
- 內部以 `order=recent` 呼叫共用服務並展平命中；不回傳片段、上下文或游標。若一次請求的工作量用完時仍不足 `limit` 條，回傳已找到的部分，因為插件 API 無法表達續查狀態。

## 7. 索引與生命週期

### 7.1 資料關係

```text
chat_events（原始證據，唯一真源；搜尋不寫入或修改）
  ├── chat_search_index_v1   FTS5 contentless-delete：content_grams, asr_grams（衍生，可由帳本重建）
  ├── chat_search_queue      (seq INTEGER PRIMARY KEY AUTOINCREMENT, event_id INTEGER NOT NULL)，索引 (event_id)
  └── chat_search_state      單列：version, state, frontier_event_id, updated_at

查詢時組裝（不落地）：
  命中（hit）→ 證據組（§6.4）→ 片段 = 必要命中 ∪ 非必要命中 ∪ 被回覆原文 ∪ 上下文（§6.5）
```

證據組與片段只存在於一次工具回應中，不建表、不持久化，因此刪除與遺忘不需要另外清理它們。

### 7.2 詞元（v1）

1. 對欄位文字計算 `norm`（§6.1）。
2. 對 `norm` 結果的每個位置輸出 1、2、3 字元 n-gram。詞元以「類型字母＋UTF-8 十六進位」編碼（`u`／`b`／`t`），只含 ASCII 英數，避開 tokenizer 對標點、表情、空白的切分。
3. `content` 的詞元寫入 `content_grams` 欄，`audio_transcript` 的寫入 `asr_grams` 欄。查詢以欄位過濾 `{content_grams}: (…)` 與 `{asr_grams}: (…)` 分別查詢，避免跨欄位拼出的假候選。

### 7.3 觸發器、佇列與索引器

| 事件 | 處理 | 持鎖 |
| --- | --- | --- |
| 插入 `message` | 觸發器：`INSERT INTO chat_search_queue(event_id) VALUES (new.id)` | 原插入交易內多寫一列 |
| `content` 或 `audio_transcript` 更新 | 觸發器：`DELETE FROM chat_search_index_v1 WHERE rowid = old.id`，再插入佇列 | 同上 |
| 刪除、隱私遺忘 | 觸發器：刪除索引列；`DELETE FROM chat_search_queue WHERE event_id = old.id`。不依賴外鍵（遷移在 `foreign_keys=OFF` 下執行） | 同一刪除交易 |
| 索引器（唯一的索引寫入者） | ① 交易外讀取佇列前 `chat_search_index_batch` 列（`seq` 遞增）與事件原文；② 交易外正規化並產生詞元；③ `BEGIN IMMEDIATE`：對每個事件，若佇列中有比本批讀到的 `seq` 更新的列就跳過；事件已不存在則只刪佇列列；否則 `INSERT OR REPLACE` 索引列，並 `DELETE FROM chat_search_queue WHERE event_id = ? AND seq <= ?` | 每批一個短交易〔實驗 E2：500 列寫交易時間〕 |

觸發器是純 SQL，不依賴 Python 函式；Alembic、sqlite3 命令列與測試建庫寫入 `chat_events` 時都能正常運作。〔實驗 E4〕已確認 contentless-delete 表支援以 `rowid` 執行 `DELETE`、`INSERT OR REPLACE`、`integrity-check`、`optimize`、`delete-all`；不支援 `rebuild` 與 FTS5 `delete` 命令；不能讀回欄位值。

### 7.4 索引狀態與查詢路徑

| `index.state` | 含義 | 查詢路徑 |
| --- | --- | --- |
| `trigram_v0` | P1，尚無 v1 索引 | v0 定義：三字以上走 trigram，一兩字在工作量內掃描 |
| `building` | v1 首次建置：回填前沿 F 由最新往最舊推進 | `event_id ≥ F` 且不在佇列中的事件走索引；佇列中與 `event_id < F` 的事件逐條讀原文以 `norm` 核驗，計入請求工作量 |
| `ready` | 回填完成 | 索引＋佇列中事件的直接核驗 |
| `rebuilding` | 匹配定義改版或索引損壞後重建 | 同 `building` |

**取捨**〔審查〕：

- **索引落後也不漏查**：佇列中與前沿以下的事件都直接核驗，C-INV 在所有狀態成立。
- **不掃整個會話**：`ready` 只直接核驗佇列中的事件，穩態下佇列只有剛寫入的少數列。`building`／`rebuilding` 時，前沿以下的掃描受每次請求的工作量上限約束，超出時回 `incomplete` 並以游標續查。
- **全量在線重建**：不需要停機，也不需要遷移掃描歷史。代價是重建期間的舊範圍查詢較慢，可能需要續查；由新到舊回填，讓最常查的近期範圍最先恢復全速。

### 7.5 正常回填、匹配定義改版與索引損壞

**正常回填（P2 首次上線）**

1. 遷移只執行 DDL：建立索引表、佇列表、狀態表與觸發器，寫入狀態列 `state='building'`、`frontier_event_id = (SELECT max(id) FROM chat_events) + 1`（主鍵查詢）。
2. 回填 worker 以 keyset 由新到舊：讀交易取 `id < F` 的前 `chat_search_backfill_batch` 個 message id；短寫交易把它們插入佇列，並把 F 更新為該批最小 id。佇列長度超過 `chat_search_queue_high_water` 時暫停回填，讓索引器先消化。
3. F 到達最小 id、且佇列中不再有回填產生的列時，以短交易把狀態改為 `ready`。

**匹配定義改版（例如 v1 → v2）**

1. 改版必然伴隨程式碼發布。新遷移只做 DDL：建立 `chat_search_index_v2`、刪除 `chat_search_index_v1`、重建觸發器指向 v2，狀態改為 `rebuilding` 並重設前沿。不同版本的表不並存，查詢只使用一種匹配定義。
2. 回填流程同上。
3. 回應的 `match_definition` 隨之改變，舊游標回 `cursor_stale`。

**索引損壞**

contentless 表的 `integrity-check` 只檢查索引內部結構，不能比對原文。因此另做抽樣自檢：每次啟動與每隔 `chat_search_selfcheck_interval`，隨機抽取若干已索引事件，取其原文中的一個三字詞元查詢，確認回傳該 rowid。

`integrity-check` 失敗或抽樣自檢不符時：

1. 短寫交易：`INSERT INTO chat_search_index_v1(chat_search_index_v1) VALUES('delete-all')`；刪除佇列中 `event_id` 小於當前最大 id 的列；狀態改為 `rebuilding`，前沿設為最大 id＋1。新寫入的消息照常經觸發器入隊。
2. 回填 worker 從帳本重新入隊全部事件，索引器重建索引列。
3. 期間查詢走 `rebuilding` 路徑，結果符合 C-INV。

重新入隊本身不等於修復：修復的關鍵是先以 `delete-all` 清空可能損壞的結構，再從帳本完整重建。`delete-all` 在大型索引上的持鎖時間尚未實測（X04）；若超過短寫交易的要求，改為在維護窗口由遷移以 DDL 刪除並重建該表（同「匹配定義改版」第 1 步）。

### 7.6 遷移持鎖成本

`migrations/env.py` 以單一 `BEGIN IMMEDIATE` 執行全部待執行遷移，所以正規化放在交易外，並不代表遷移沒有在寫交易中掃描歷史。若遷移以 `INSERT INTO chat_search_queue SELECT id FROM chat_events` 一次排入全部事件，它就是在寫交易中掃描全部歷史。

〔實驗 E4〕在 100 萬列窄表上，這個單一 SQL 持鎖 0.12 秒；以 5,000 列一批的 keyset 短交易，每批中位數 0.62 毫秒、最大 2.54 毫秒。0.12 秒只是下限：真實 `chat_events` 列較寬，掃描讀取的頁更多，而且它與同次遷移的其他步驟共用同一個交易。

決策〔審查〕：遷移只做 DDL 與一次主鍵 `max(id)`，歷史回填全部交給 worker 的短交易。理由不是單一 SQL 太慢，而是：① 開發約束禁止在 SQLite 寫交易中掃描歷史；② 損壞重建與匹配定義改版本來就需要在線回填，首次建置共用同一條路徑，不另寫遷移專用的回填；③ 遷移耗時因此與資料量無關。整體耗時以 V48 實測。

### 7.7 兩條建庫路徑

| 路徑 | 現況 | P2 | P3 |
| --- | --- | --- | --- |
| Alembic 遷移 | `0055` 匯入凍結的 `asr/schema.py:CHAT_FTS_0055` | 新增 `conversation/search_schema.py:CHAT_SEARCH_0120`（DDL 與觸發器字串常數），由遷移 `0120` 匯入；此常數凍結，日後改版另立新常數 | 遷移 `0121` 刪除 `chat_events_fts` 及三個觸發器；downgrade 以 `CHAT_FTS_0055` 重建並 `rebuild` |

### 10.1 評估集

- **建立**：T01 生成多個獨立合成會話（群聊與私聊），每個會話有固定角色、口語風格與事件時間線；另手寫困難負例：同詞不同事、同人不同時間、否定、更正、相近金額（「三千」「三千五」「两千九」「3k」）、英文詞界誤命中（`new york`）。
- **標註**：每條查詢標註 ① 意圖文字；② 工具參數；③ **必要證據集合**（共同構成答案的 `event_id` 集合，可能不只一組，例如更正前後各一組）；④ 必要上下文集合；⑤ **錯誤聯合**：雖然覆蓋全部詞、但不構成同一件事的命中組合；⑥ 無答案查詢標 `answerable=false`。
- **類別**：一字、二字、長詞；繁簡；全半形；英數內部子串；型號網址；多詞跨消息；人物、時間、`has` 篩選；排除；更正；無答案；改寫類（意思相同、用詞不同）。
- **切分**：以會話為單位劃分 dev／test，同一會話及其查詢不跨切分；預設值只在 dev 上調整，test 只在階段驗收時跑。

### 10.2 指標與預算對齊

**預算對齊**：比較不同方案時，把各方案的回傳結果按排名展平為事件序列，截斷到相同的**消息數**（10、30）或相同的**字元預算**（1,500、4,000 個 `content` 字元）後再計算指標。不比較「片段數相同但大小不同」的輸出。

| 層面 | 指標 |
| --- | --- |
| 完整證據 | **完整必要證據取得率**：截斷後包含某一完整必要證據集合的有答案查詢比例（主指標） |
| 部分證據 | 必要證據的事件級召回率；只取得部分必要證據的查詢比例（單列，不計入主指標） |
| 誤合併 | 回傳證據組中屬於「錯誤聯合」的比例 |
| 排名 | 以「含完整必要證據」為相關判定的 MRR 與 nDCG@5；只含部分證據的不算相關 |
| 上下文 | 必要上下文覆蓋率；重複率（應為 0）；平均回傳事件數 |
| 歸屬 | `terms_by_sender` 與 `role` 的正確率 |
| 無答案 | 無答案查詢得到 `exhausted` 且無證據組的比例；有答案查詢誤得空結果的比例 |
| 效率 | 各類別 p50／p95 延遲、每次請求的迭代次數與讀取列數、`incomplete` 比例、索引寫入成本、回填與重建耗時、磁碟增量 |
| Agent 使用 | 以腳本化模型回應或經授權的真實模型，評估是否引用正確 `event_id`、是否把 `context` 誤當命中、是否把他人發言歸錯 |

**驗收門檻的訂法**：本任務不預先編造提升數字。P0 量得基線後，於 §12 寫下各階段門檻，原則為：① C-INV 漏召回為 0（正確性）；② 重複率為 0；③ 歸屬正確率 100%；④ 字面類的完整必要證據取得率不低於基線；⑤ p95 延遲與 `incomplete` 比例在合成庫上有書面門檻。

### 10.3 消融

V62 排序：`recent`、`relevance` 字典序鍵、加入 `single_sender_cover` 平手鍵、以 BM25 取組內最小值；V63 證據組跨度：消息 10／20／40、分鐘 10／30／120；V64 索引方案：`ngram123`、`trigram_plus_12`、加入詞典分詞的排序訊號；V65 改寫類：Agent 單查詢、`any_of` 多查詢、（P4）語義召回。全部以 §10.2 的預算對齊比較。
