## 0. 結論摘要

1. **問題主要出在查詢表達與中文匹配，其次是粒度與回應合同。**多關鍵字被包成單一短語而直接查不到；兩字中文詞不能進入 trigram 索引；繁簡與全半形沒有正規化；時間過濾有 8 小時偏移；人物篩選用平台帳號且在私聊會混入 Yuki 的發言；結果是孤立消息，沒有命中位置、聚合與上下文（§2.3）。
2. **推薦方案：在現有 Python／SQLite 內完成「詞法強基線 + 片段聚合」**（§5）。索引單位是單條消息，回傳單位是「片段」：命中消息加上前後文，每條消息保留原發言人。不使用向量模型、向量資料庫、重排模型或獨立查詢改寫器；主 Agent 本身負責改寫查詢，工具負責把結構化條件精確執行。
3. **分四階段施工**：P0 評估集與基線 → P1 查詢語義與回應合同（沿用現有 trigram）→ P2 正規化的衍生索引（CJK 單字＋雙字、繁轉簡、NFKC）→ P3 切換並刪除舊 trigram 路徑。語義召回列為 P4 可選，須評估證據與隱私授權（§9）。
4. **原始事件仍是唯一證據源。**衍生索引只產生候選，最終命中一律以原文正規化後的子字串核驗；片段在查詢時從帳本組裝，不保存副本，因此刪除與遺忘無需另行清理片段。

## 1. 問題定義、目標與範圍

### 1.1 問題

使用者和 Yuki 需要「找回原話、核對誰在何時說過什麼」。目前 `search_chat_history` 只做字面匹配，經常查不到；查到時也只是孤立消息，Agent 還得逐條再呼叫 `get_chat_history_around` 補上下文。

### 1.2 目標

以可驗證的指標描述「一流水準」，不在缺乏實測時宣稱已達成：

| 維度 | 目標的驗證方式 |
| --- | --- |
| 檢索品質 | 評估集上的命中 Recall@k、片段 nDCG@k，對照現有實作與詞法強基線（§10） |
| 上下文完整性 | 標準證據集合被回傳片段覆蓋的比例；發言歸屬正確率 |
| 查詢效率 | 合成 1M／5M 消息庫上的 p50／p95 延遲，按查詢類型分列 |
| 維護成本 | 不新增服務與外部依賴；索引增量成本、重建耗時與磁碟占用可量測 |

### 1.3 職責邊界

| 能力 | 職責 | 本任務是否修改 |
| --- | --- | --- |
| `search_chat_history`／`get_chat_history_around`／`get_recent_chat_history` | 找回原始聊天、核對證據 | 是，主要對象 |
| `search_memory` 與 Memory 事實 | 抽取後的長期事實，有自己的證據與權限 | 否；只重用其正規化與 RRF 程式碼 |
| 公共 Compact 檢查點與摘要 | 上下文壓縮 | 否；摘要不作為檢索證據 |
| Work 任務日誌與執行回執 | 執行事實 | 否 |
| `read_conversation_history`（社交工具） | 從 OneBot 即時讀取明確的人或群 | 否；跨會話讀取另由 Q01 決定 |

### 4.2 使用情境（S）

所有對話皆為合成資料。

**S01 碎句與交錯發言**

```text
#101 甲 10:00 我想买电吉他
#102 乙 10:00 我先去吃饭
#103 甲 10:01 预算大概三千
```

查詢 `terms=["电吉他","三千"]`：

- 命中消息：#101（电吉他）、#103（三千）。
- 聚合片段：#101–#103 合成一個片段，因為兩個命中的上下文窗口重疊、時間差 1 分鐘。
- 補充上下文：#102 標為 `context`，不計命中，不歸入甲的發言。
- `terms_by_sender` 為 `{甲: ["电吉他","三千"]}`，`single_sender_cover=true`，因此排在「兩個詞分別出自不同人」的片段前面。
- 工具從不把多條消息拼成一句；「甲說預算三千」由 Agent 引用 #101 和 #103 得出。

**S02 反例：同詞不同事**

```text
#201 甲 3/01 电吉他好难学
#202 丙 3/20 三千块的耳机值吗
```

兩個命中相隔數百條、時間相差 19 天，不合併；兩個詞都沒有在同一片段出現，因此 `fragments=[]`，`term_hits={"电吉他":1,"三千":1}`，Agent 可自行決定分開查。

**S03 繁簡**：「報銷」與「报销」互相命中；回傳原文不改字。

**S04 符號與全半形**：`PR #448`、`PR#448`、`ＰＲ＃４４８` 互相命中（空白不計、NFKC 折疊全形）。`PR 448` 不命中 `PR #448`，因為 `#` 保留。

**S05 型號與網址**：`iPhone15Pro` 可用 `iphone`、`15pro`、`iphone15` 命中；網址 `https://example.com/a?b=1` 可用 `example.com` 命中。

**S06 「上週某人提過的餐廳」**：Agent 解析「上週」為明確時間範圍，解析「某人」為 `sender`，再以 `any_of=["餐厅","饭店","店","吃"]` 搜尋。工具回顯 `time_range` 與 `sender`，Agent 能檢查自己的解讀。若 `sender` 名稱不唯一，回傳 `sender_ambiguous` 及候選，不猜測。

**S07 更正前後**

```text
#301 甲 9/01 预算三千
#350 甲 9/05 不对，预算改成五千
```

查詢 `terms=["预算"]` 回傳兩個片段，各帶時間；工具不去重、不判斷哪個為真。`order=recent` 讓最新說法排前面；Agent 依時間引用兩者並說明更正。

**S08 否定與排除**：`terms=["电吉他"], exclude=["不买"]` 不回傳「不买电吉他了」作為命中；若它落在其他命中的上下文窗口內，仍作為 `context` 出現，因為它是原始證據。

**S09 相近金額**：查「三千」會命中「三千五」（子串），由 Agent 讀原文判斷；不會命中「两千九」「3000」或「3k」。工具不做數值模糊匹配，需要多種寫法時由 Agent 放進 `any_of`。

**S10 無結果與部分結果**：無命中時 `fragments=[]`、`exhaustive=true`，並附各詞命中數與實際查詢範圍；候選超過預算時 `exhaustive=false`、`budget_reason="candidate_limit"`。

**S11 尚未索引完成**：P2 回填期間，未索引的事件經掃描路徑核驗，結果完整；回應中 `index.pending_scanned` 表示走了多少掃描。

**S12 刪除與遺忘**：某人被遺忘後，其事件從 `chat_events` 刪除；衍生索引同一交易內刪除該 rowid；之後任何查詢、上下文展開與重建都不再出現。

**S13 generation 重置**：會話重置後，floor 之前的事件不被搜尋、不作為上下文，也不作為被回覆原文帶出。

## 5. 方案比較與推薦

| 維度 | A. 修既有字面檢索 | B. 本地全文索引＋片段聚合（**推薦**） | C. B＋語義召回、融合或重排 |
| --- | --- | --- | --- |
| 做法 | 多詞拆開、短詞走 `instr` 掃描、修時間與身份、加上下文 | A 的全部，加上正規化衍生 FTS（單字＋雙字＋詞），BM25 與片段排序 | B＋嵌入向量（本地或外部）＋RRF，可再加重排 |
| 召回 | 繁簡、全半形仍漏；短詞靠掃描 | 字面需求全覆蓋 | 再加上改寫與同義 |
| 誤匹配 | 低（字面） | 低；候選一律以正規化原文核驗 | 語義相近可能混淆人名、金額、否定與型號 |
| 延遲 | 短詞掃描與會話大小成正比（合成：2 萬條計數 13 ms，1M 條全庫 104 ms），大群與冷快取時更慢 | 短詞與長詞都走索引，合成測試 < 1 ms 取候選 | 加上查詢嵌入：本地 CPU 數十至數百 ms，外部 API 加網路往返 |
| 記憶體／磁碟 | 不變 | 合成資料中約為 trigram 的 1.25 倍；P3 刪除 trigram 後淨增量待實測 | 每條消息一個向量；0.6B 級本地模型需數 GB 記憶體 |
| 索引成本 | 無 | Python 正規化連同寫入，單執行緒約 14 萬條／秒（合成） | 每條消息一次嵌入推論或付費 API |
| 依賴 | 無 | 無新套件；附帶 OpenCC 字表資料檔（Apache-2.0） | 模型檔或外部服務 |
| 維護 | 低 | 正規化器版本、待索引佇列、重建程序 | 再加模型版本、向量重建、外送授權 |
| 隱私 | 不變 | 不變（衍生索引在同一資料庫，隨刪除同步） | 外部嵌入須把私人聊天送出 |

**推薦 B。**理由：

1. G01–G10 都能由 B 解決，沒有一項需要語義模型。
2. 微信等產品的聊天記錄搜尋本質上是字面搜尋加篩選加定位，與 B 一致。
3. 原話核對最怕把「三千」配成「三千五百」以外的近似金額、把「不買」配成「買」；語義召回在這類任務上增加的主要是風險。
4. 改寫需求由主 Agent 承擔：它本來就是 LLM，能把「上週那家店」改寫成時間範圍、人物與同義詞列表。QReCC／CONQRR 的改寫器正是為沒有 LLM 主控的檢索系統而設。

**不採用 A 作為終點：**繁簡與全半形無法僅靠查詢端展開乾淨處理；短詞掃描在大群聊中延遲不可控。A 的內容即 P1，作為 B 的第一步。

**不採用 C 作為本輪預設：**MIRACL 中文 BM25 偏弱的結果來自自然語言問題對維基段落，不能代表聊天原話查找；但它提醒我們必須在 P0 評估集中單列「改寫類」查詢，量化缺口後再決定 P4（§9 P4 準入條件）。

### 5.1 特別核實的問題

| 問題 | 結論 |
| --- | --- |
| 中文斷詞、字元 n-gram、trigram 各能處理什麼 | 斷詞（jieba 類）利於排序但對口語、新詞、型號不穩，且切分錯誤會造成漏召回。trigram 能做任意 ≥3 字子串，但一兩字詞無法進索引（實測）。單字＋雙字詞元可覆蓋任意長度：一字查單字欄，二字以上查雙字序列，最後以原文子串核驗保證精度 |
| 短詞怎麼處理 | 一字詞查單字詞元；二字詞即一個雙字詞元；都在索引中，延遲與長詞相同 |
| 索引單位與回傳單位是否不同 | 是。索引單條消息（原始證據的自然最小單位，刪除時一對一），回傳片段 |
| 固定窗口、發言片段、回覆鏈、話題片段 | 採「命中周圍固定窗口＋重疊合併＋時間間隔切分＋回覆原文」。話題分段（SeCom）需要模型，片段邊界不可解釋，不採用；同一發言人連續發言由 `terms_by_sender` 呈現，不另建單位 |
| 需要向量模型、向量資料庫、重排、查詢改寫嗎 | 本輪不需要。P4 若啟用，向量以 BLOB 存於同一 SQLite（沿用 Memory 的存法），不引入向量資料庫 |
| 能否不加獨立服務 | 能。索引器掛在既有啟動後維護任務中（`container.py` 的 maintenance 啟動點），與 Memory 嵌入 worker 同一模式 |
| 如何避免長時間持有寫鎖 | 觸發器只寫一列待索引記錄；正規化在交易外完成；每批短交易寫入並以條件刪除待索引記錄（§7.3） |

### 6.1 `search_chat_history` 新 schema

刪除 `keyword`、`user_id`、`group_id`、`limit` 的舊語義（G09、G08），整體替換。合同變更產生新的合同 revision，需重啟並開啟新鏈；已保存的舊回執仍由原 decoder 讀取，不重跑（[Tool Kernel](tool-kernel.md)）。

```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "terms": {
      "type": "array", "items": {"type": "string", "minLength": 1}, "minItems": 1,
      "description": "必須全部出現的字面詞；各詞獨立匹配，不要求相鄰"
    },
    "any_of": {
      "type": "array", "items": {"type": "string", "minLength": 1}, "minItems": 1,
      "description": "至少出現一個的字面詞，用於同義詞、別名、數字寫法"
    },
    "exclude": {
      "type": "array", "items": {"type": "string", "minLength": 1},

    },
    "match_within": {"type": "string", "enum": ["fragment", "message"], "default": "fragment"},
    "sender": {
      "type": "string",
      "description": "current_speaker、replied_message_author、member_{user_id}、yuki，或 find_contacts 回傳的 person target_id"
    },
    "after": {"type": "string", "description": "ISO 8601，含；無時區時按 UTC+8"},
    "before": {"type": "string", "description": "ISO 8601，不含；無時區時按 UTC+8"},
    "has": {"type": "array", "items": {"type": "string", "enum": ["image", "video", "file", "audio", "link"]}},
    "order": {"type": "string", "enum": ["relevance", "recent", "oldest"], "default": "relevance"},
    "context_before": {"type": "integer", "minimum": 0},
    "context_after": {"type": "integer", "minimum": 0},
    "limit": {"type": "integer", "minimum": 1, "description": "片段數"},
    "cursor": {"type": "string"}
  },
  "anyOf": [{"required": ["terms"]}, {"required": ["any_of"]}, {"required": ["sender"]}, {"required": ["has"]}]
}
```

只帶 `sender`／`has`／時間而不帶詞時，等同「某人在某段時間的發言」或「群裡的圖片」，按時間排序；這對應微信的「按成員、按類型查找」。

工具說明文字（約束 Agent 用法，不放進人格提示）：

> 在當前會話帳本中查找原話。terms 全部須出現，any_of 出現其一即可，兩者都是字面子串，不做同義擴展；需要同義詞、別名或數字寫法時自行列入 any_of。只搜尋當前會話；空結果只代表本次條件下沒有命中，不代表其他會話或更早 generation 沒有。結果中 role=hit 的消息才算命中，context 只是鄰近原文，引用時以各消息自己的發言人為準。

### 6.2 匹配與正規化規則

| 編號 | 規則 |
| --- | --- |
| Q-1 | 正規化 `norm(x)`：NFKC → casefold → 繁轉簡逐字映射 → 刪除所有空白字元。查詢詞與原文使用同一函式與同一版本 |
| Q-2 | 一條消息的可匹配文字 = `content` 與 `audio_transcript`，分欄記錄命中來源（`content`／`asr`）。`visual_summary` 不參與（O02） |
| Q-3 | 詞 t 命中消息 m ⇔ `norm(t)` 是 `norm(m 的某欄)` 的子串。索引只產生候選，最終以 Q-3 核驗 |
| Q-4 | 正規化後為空字串的詞（例如只有空白）回 `invalid_arguments` |
| Q-5 | 命中消息 = 符合時間、`sender`、`has` 篩選，且至少命中一個 `terms` 或 `any_of` 詞，且不含任一 `exclude` 詞的消息。只帶篩選不帶詞時，符合篩選即為命中 |
| Q-6 | `match_within=message`：一條消息須包含全部 `terms` 且至少一個 `any_of`（若有）。`fragment`：片段內的命中消息合計覆蓋全部 `terms` 且至少一個 `any_of` |
| Q-7 | `exclude` 只作用於命中判定；不刪除上下文中的原文 |
| Q-8 | 篩選（時間、`sender`、`has`）只作用於命中消息；上下文不受篩選，包含其他發言人 |
| Q-9 | 時間解析：帶時區照用；不帶時區按 `default_timezone`；比較前轉 UTC，以與儲存格式相同的方式綁定參數，修正 G07。`after` 含、`before` 不含 |
| Q-10 | `sender` 解析為 canonical Person 或 Yuki 作者類型（`author_kind='yuki'`），以 `author_person_id`／`author_kind` 篩選；不再用 `private_peer_user_id`（G08）。名稱多個候選時回 `sender_ambiguous` 與候選；查無時回 `sender_not_found` |

### 6.3 片段組裝演算法

設定值見 §8.3。所有步驟只讀，在一次一致讀快照內完成。

1. **取候選**：依 §7 的索引取得命中候選，套用 Q-5；候選數上限為 `chat_search_candidate_limit`，超過時 `exhaustive=false`。
2. **排序命中**：按 `event_id` 排序（帳本順序）。
3. **聚合**：相鄰兩個命中 h₁、h₂ 合併到同一片段，當且僅當它們之間的消息數 ≤ `context_after + context_before` 且時間差 ≤ `chat_search_fragment_gap_minutes`。否則切開。
4. **補上下文**：每個片段向前取 `context_before`、向後取 `context_after` 條（同 Conversation、floor 之後、keeper、`message` 類）；已屬於其他片段的事件不重複加入。若命中消息有 `reply_to_event_id` 且原消息在範圍內，以 `role=reply_target` 加入，每個命中最多一條。
5. **大小上限**：片段事件數超過 `chat_search_fragment_max_events` 時，在最大時間間隔處切開。
6. **覆蓋判定**：按 Q-6 過濾片段，計算 `matched_terms`、`terms_by_sender`、`single_sender_cover`（是否有某位發言人獨自覆蓋全部 `terms`）。
7. **排序**（`order=relevance`）：依下列鍵字典序比較，不使用加權和：
   1. `single_sender_cover` 為真者在前；
   2. 片段內覆蓋全部詞的最短事件跨度較小者在前；
   3. 命中消息的 BM25 分數總和較高者在前（P1 使用 trigram 的 `bm25()`，P2 使用新索引的 `bm25()`）；
   4. 最後一個命中較新者在前。
   `recent`／`oldest` 只按最後命中時間排序。片段內部永遠按時間正序。
8. **分頁**：取前 `limit` 個片段；`next_cursor` 是對（排序鍵、最後片段的末事件 ID、查詢條件雜湊、Conversation 版本）的不透明編碼。游標與當前條件或 generation 不符時回 `cursor_stale`，Agent 重新查詢。

## 7. 資料關係、索引與生命週期

### 7.1 資料關係

```text
chat_events（原始證據，唯一真源；不因搜尋而寫入或修改）
  │ 1:1 rowid（P2 新增，衍生、可重建）
  ├── chat_event_search_fts   FTS5 contentless-delete：content_uni, content_bi, asr_uni, asr_bi
  │ 0..1 待索引記錄（P2 新增）
  └── chat_event_search_pending(event_id PK → chat_events.id ON DELETE CASCADE, queued_seq)
chat_event_search_state（單列：normalizer_version, queue_seq, created_at）

查詢時組裝（不落地）：
  命中消息（hit） ─┐
  聚合片段（fragment）= 命中 ∪ 補充上下文（context） ∪ 被回覆原文（reply_target）
```

- **命中消息**：符合 Q-5 的原始事件。
- **聚合片段**：§6.3 的組裝結果，只存在於一次工具回應中；沒有表、沒有 ID 持久化。
- **補充上下文**：與片段相鄰或被回覆的原始事件，不代表命中，不改變發言歸屬。

### 7.2 詞元設計（P2）

正規化器 `ChatSearchNormalizer`（版本號整數，初始 1）：

1. NFKC、casefold、繁轉簡逐字映射。字表取自 OpenCC `TSCharacters.txt`，固定版本，以資料檔隨原始碼分發，並在 [Pi/Code 移植來源](pi-port-provenance.md)同類位置登記來源與 Apache-2.0 授權。一對多映射取第一個目標字。
2. 依 Unicode 類別切成連續段：CJK 段、字母數字段；其餘字元（標點、空白、表情）作為分隔，不產生詞元。
3. CJK 段：輸出每個字（`*_uni` 欄）與每對相鄰字（`*_bi` 欄）。
4. 字母數字段：輸出整段；字母與數字交界處再切出子段（`iphone15pro` → `iphone15pro`、`iphone`、`15`、`pro`）。網址依 `://`、`/`、`?`、`#`、`.` 再切出主機與路徑片段（借鑑 Signal 4.0.2 的網址詞元化）。
5. 保存原文字元偏移映射，供 Q-3 核驗與 `highlights` 換算。

查詢詞的候選表達式：一字詞 → `*_uni MATCH "字"`；二字以上的 CJK 段 → 其全部雙字詞元的 AND；字母數字段 → 依字母／數字交界切開，各子段為一個詞元，最後一個子段用前綴 `*`（例如 `15pro` → `"15" AND "pro"*`）。一個查詢詞內各段以 AND 組合；候選再以 Q-3 核驗。

已知限制：字母段內部的非前綴子串不進候選（`phone` 不會找到 `iPhone`），trigram 可以。P0 評估集須含此類查詢，T24 消融據此決定是否為字母段額外輸出 trigram 詞元。

正規化器版本改變（字表、切分規則）時，遷移把全部事件重新放入待索引佇列並更新 `chat_event_search_state`，由索引器在線重建；重建期間查詢走 §7.3 的掃描補足，結果仍完整。

### 7.3 寫入、增量、刪除、遷移與重建

| 事件 | 處理 | 持鎖 |
| --- | --- | --- |
| 新消息插入 | SQL 觸發器 `AFTER INSERT ON chat_events WHEN new.event_kind='message'`：先 `UPDATE chat_event_search_state SET queue_seq = queue_seq + 1`，再 `INSERT OR REPLACE INTO chat_event_search_pending(event_id, queued_seq)` 寫入新的 `queue_seq`。遞增計數保證同一事件再次排隊時序號必然不同 | 與原插入同一交易，多一列寫入與一次單列更新 |
| ASR 轉錄寫入／`content` 變更 | 觸發器 `AFTER UPDATE OF content, audio_transcript`：`DELETE FROM chat_event_search_fts WHERE rowid=old.id`，再重新放入待索引並遞增 `queued_seq` | 同上 |
| 刪除、隱私遺忘 | 觸發器 `AFTER DELETE ON chat_events`：`DELETE FROM chat_event_search_fts WHERE rowid=old.id`；待索引列由外鍵級聯刪除（`database.py` 已啟用 `PRAGMA foreign_keys=ON`） | 同一刪除交易 |
| generation 重置 | 不刪除事件；查詢一律以 floor 過濾，索引無需變動 | 無 |
| 索引器 | 每輪：①讀交易外按 `event_id` 分頁取 `pending`（含 `queued_seq`）與對應原文；②在交易外正規化、產生詞元；③短交易 `BEGIN IMMEDIATE`：對每列 `DELETE` 舊 FTS 列並 `INSERT` 新詞元，再 `DELETE FROM pending WHERE event_id=? AND queued_seq=?`，只刪除未被再次排隊的列；事件已不存在則跳過 | 每批一個短交易；批量以 `chat_search_index_batch` 設定 |
| 查詢 | 已索引事件走 FTS；同一 Conversation、floor 之後仍在 `pending` 的事件逐條讀原文以 Q-3 核驗；`index.pending_scanned` 回報數量 | 只讀 |
| 遷移（P2） | 建表、建觸發器、`INSERT INTO pending SELECT id FROM chat_events WHERE event_kind='message'`、寫入 `state`。不在遷移中做正規化 | 一次 INSERT…SELECT；合成 1M 列量級為秒級，實施時以 T22 實測 |
| 回填 | 由索引器在線完成，期間查詢經掃描補足 | 同索引器 |
| 舊 trigram（P3） | 驗收通過後由遷移刪除 `chat_events_fts` 與其三個觸發器，同時刪除 `ledger.search` 的 `LIKE` 分支 | 一次 DDL |

這套做法不要求修改分散的十多個 `chat_events` 寫入點（`persistence/scoped_event_uow.py`、`identity/canonical_uow.py` 等），也不在寫交易中等待正規化或掃描歷史，符合[開發約束 §6](development-contract.md#6-sqlite-与诊断)。

**健康與修復：**啟動後維護任務對 `chat_event_search_fts` 執行 `integrity-check`（借鑑 Signal）。失敗時記錄並把全部事件重新排入 `pending`，由索引器在線重建；查詢因掃描補足而保持正確，只是變慢。

## 10. 評估與測試

### 10.1 評估集

- **建立**：T01 產生器生成多個獨立合成會話（群聊與私聊），每個會話有固定角色、口語風格與事件時間線；另手寫至少四類困難負例：同詞不同事、同人不同時間、否定（「不買了」）、更正（「改成五千」）、相近金額（「三千」「三千五」「两千九」「3k」）。
- **標註**：每條查詢標註①查詢意圖文字；②工具參數（由標註者寫成 Agent 應下的結構化條件）；③標準答案為**證據集合**：必要命中 `event_id` 集合與必要上下文 `event_id` 集合；④無答案查詢標 `answerable=false`。
- **類別**：字面一字、二字、長詞；繁簡；全半形；型號網址；多詞跨消息；人物篩選；時間篩選；排除；更正；無答案；改寫類（意思相同、用詞不同）。
- **切分**：以**會話**為單位劃分 dev／test，同一會話（及其衍生的查詢）不跨切分，防止相鄰片段洩漏；預設值只在 dev 上調整，test 只在階段驗收時跑。

### 10.2 指標

| 層面 | 指標 |
| --- | --- |
| 檢索 | 命中 Recall@k（k=1,3,5 片段內展平的命中消息）；片段 MRR、nDCG@5（片段含必要命中即為相關） |
| 上下文 | 證據覆蓋率 = 回傳事件 ∩ 必要命中∪必要上下文 ÷ 必要集合；重複率（同一事件出現次數 > 1 的比例，應為 0）；平均回傳事件數（衡量噪音） |
