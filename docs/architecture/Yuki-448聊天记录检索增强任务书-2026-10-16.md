## 0. 結論摘要

1. **問題主要在查詢表達與中文匹配，其次是粒度與回應合同。**多關鍵詞被包成一個短語；兩字詞無法進入 trigram 索引，放進 `NOT` 也不排除；沒有繁簡與全半形正規化；時間篩選有 8 小時偏移；私聊人物篩選會混入 Yuki 自己的發言；結果是孤立消息，也不告知是否截斷（§2.3，〔實驗 E1、E3〕）。
2. **字面匹配定義與候選完整性是第一不變量。**凡符合當前匹配定義的消息都必須進入候選集合；原文核驗只剔除多召回的候選，不能補救漏召回（§6.2）。
3. **匹配定義以整串計算，實作只在安全起點切分。**`normalized_v1` 定義為對整個欄位依序做 NFKC、casefold、NFKC、繁轉簡、刪空白。Unicode 正規化對串接不封閉（UAX #15 §1.4），第二版的貪婪切分在 `a◌̕◌̀` 上與 `à◌̕` 不相等；本版只在「不可能與前文互動」的字元前切分，與整串定義在全部已指派碼位上一致〔實驗 E10〕。
4. **推薦索引：正規化文字上的 1／2／3 字元 n-gram，存於 contentless-delete FTS5 表。**400 條隨機與針對性查詢上漏召回為 0〔實驗 E2〕。
5. **證據組與展示上下文完全分開。**證據組是命中序列上的最小覆蓋窗口，只受跨度限制；上下文只影響展示〔實驗 E6〕。
6. **一次搜尋請求在一個讀交易中完成。**索引、佇列、前沿以下掃描、核驗與上下文讀同一個 WAL 快照，否則「讀索引 → 索引器提交並移出佇列 → 讀佇列」會漏掉事件〔實驗 E9〕。搜尋不寫入、不等待外部工作。
7. **時間順序分頁以半開區間與合併步推進，預算是有公式上界的停止閾值。**`recent`／`oldest` 的游標是（輸出上界 E，掃描上界 S）；每頁至少執行一個合併步，(E, S) 依字典序嚴格下降。範圍掃描只在合併步後判斷預算，單頁計價不超過 `max(B, u·n·M + a₁·u + b)`；靜態資料上續查終會結束、不重不漏〔實驗 E7〕。`relevance` 在固定範圍內以最後排序鍵續頁，輸盡範圍後再推進 (E, S)，其重算上界見下一點。
8. **跨頁一致性綁定既有的 `prompt_source_revision`。**游標記錄首頁讀到的 Conversation 版本（含 revision）、索引 epoch 與上界 U；之後任何刪除、內容或轉錄更新、floor 變化都讓 revision 改變，續頁回 `cursor_stale`。因此各頁要嘛是同一快照結果的精確劃分，要嘛明確失效〔實驗 E11〕。`relevance` 續頁以首頁記錄的前沿凍結讀取計畫，重算計價不超過首頁〔實驗 E14〕。
9. **索引生命週期：佇列＋由新到舊的回填前沿，狀態表只有前沿與 epoch。**索引器以「批內每個事件的最大 seq」處理並刪除 ≤ 該 seq 的列，過期列一併退出，處理期間重新入隊的列保留；索引列只在事件仍存在時於同一寫交易內寫入〔實驗 E8〕。空庫的前沿為 1；建置中／完成由前沿推導，不設完成門檻〔實驗 E12〕。
10. **排序不使用 BM25**〔實驗 E5〕；插件 `search_history` 保留消息數語義，由 facade 內部續頁直到取得 N 條或確認窮盡〔實驗 E13〕。
11. **語義召回列為 P4**，由 P0 評估集的「改寫類」查詢量化後決定。

## 1. 問題、目標與邊界

### 1.1 問題

使用者和 Yuki 需要「找回原話、核對誰在何時說過什麼」。目前 `search_chat_history` 只做字面匹配，經常查不到；查到時也只是孤立消息，Agent 還得逐條呼叫 `get_chat_history_around` 補上下文。

### 1.2 目標

以可驗證的指標描述「一流水準」，缺乏實測時不宣稱已達成：

| 維度 | 驗證方式 |
| --- | --- |
| 檢索完整性 | 候選完整性的性質測試（V12–V14）；評估集上完整必要證據的取得率（§10.2） |
| 檢索品質 | 在相同的回傳消息數或字元預算下，比較現有實作、詞法強基線與各消融版本 |
| 上下文完整性 | 必要上下文覆蓋率、誤合併率、發言歸屬正確率 |
| 查詢效率 | 合成資料上各查詢類別的 p50／p95 延遲；每次請求的工作量上限 |
| 維護成本 | 不新增服務與外部套件；索引寫入成本、回填與重建耗時、磁碟占用可量測 |

### 1.3 職責邊界

| 能力 | 職責 | 本任務是否修改 |
| --- | --- | --- |
| `search_chat_history`／`get_chat_history_around`／`get_recent_chat_history` | 找回原始聊天、核對證據 | 是，主要對象 |
| `search_memory` 與 Memory 事實 | 抽取後的長期事實，各有證據與權限 | 否；只重用其正規化與向量儲存的做法 |
| 公共 Compact 檢查點與摘要 | 上下文壓縮 | 否；摘要不作為檢索證據 |
| Work 任務日誌與執行回執 | 執行事實 | 否 |
| `read_conversation_history`（社交工具） | 從 OneBot 即時讀取明確的人或群 | 否；跨會話搜尋另由 D01 決定 |

### 4.2 使用情境（S）

所有對話皆為合成資料。

**S01 碎句與交錯發言**

```text
#101 甲 10:00 我想买电吉他
#102 乙 10:00 我先去吃饭
#103 甲 10:01 预算大概三千
```

查詢 `terms=["电吉他","三千"]`：證據組為 {#101, #103}（最小覆蓋窗口）。#102 位於兩個必要命中之間，以 `context` 出現，不計命中、不歸甲。`terms_by_sender` 為 `{甲: [电吉他, 三千]}`。把 `context_before`／`context_after` 設為 0 時，證據組不變，片段只少了窗口外的上下文；#102 仍作為核心內的消息顯示（§6.5）。

**S02 同詞不同事**：「电吉他」與「三千」相隔超過證據組跨度上限（§6.4）時不成組；回應 `fragments=[]`，並以 `term_hits` 回報各詞命中數。

**S03 繁簡**：「報銷」與「报销」互相命中；回傳原文不改字。

**S04 空白與全半形**：`PR #448`、`PR#448`、`ＰＲ＃４４８` 互相命中（v1 刪除全部空白、NFKC 折疊全形）；`PR 448` 不命中 `PR #448`，因為 `#` 保留。

**S05 英數內部子串**：`phone` 命中 `iPhone15Pro`；`15pro`、`example.com`、`a?b=1` 命中對應原文。

**S06 「上週某人提過的餐廳」**：Agent 把「上週」解析為時間範圍，把「某人」以 `find_contacts` 解析為 `sender`，再以 `any_of=["餐厅","饭店","店","吃"]` 搜尋。工具回顯 `time_range` 與 `sender`。

**S07 更正前後**

```text
#301 甲 9/01 预算三千
#350 甲 9/05 不对，预算改成五千
```

查詢 `terms=["预算"]` 回傳兩個證據組，預設 `recent` 讓 #350 在前；工具不去重、不判斷哪個為真。

**S08 排除**：`terms=["电吉他"], exclude=["不买"]` 不把「不买电吉他了」作為命中；它若落在其他片段的上下文中，仍以 `context` 出現。

**S09 相近金額**：查「三千」命中「三千五」（子串），不命中「两千九」「3000」「3k」。

**S10 無結果與預算用完**：無命中且已掃到 floor 時 `result_state="exhausted"`；常見詞用完這一頁的工作量時 `result_state="incomplete"`，附游標；續查必定前進（§6.7）。

**S11 索引建置中**：前沿以下的舊消息在工作量內直接核驗；本次未掃完時 `result_state="incomplete"`，續查可完成（§7.4）。

**S12 刪除與遺忘**：遺忘的事件從帳本、索引、佇列中刪除；後續查詢、上下文、回填與重建都不再出現；翻頁中的游標回 `cursor_stale`。

**S13 generation 重置**：floor 之前的事件不作命中、上下文或被回覆原文；舊游標回 `cursor_stale`。

**S14 審查反例**：25 條連續命中，#1–#12 只含 A，#13–#25 只含 B，相鄰命中都在跨度規則內，最大時間間隔在 #12、#13 之間。證據組為 {#12, #13}，與上下文設定和片段上限無關〔實驗 E6〕。

## 5. 方案比較與推薦

### 5.1 檢索方案

| 維度 | A. 修既有字面檢索 | B. 正規化 n-gram 索引＋證據組（**推薦**） | C. B＋語義召回、融合或重排 |
| --- | --- | --- | --- |
| 做法 | 多詞拆開；三字以上走 trigram，一兩字在預算內掃描；修時間與身份 | A 的查詢語義，加上 v1 正規化與 1／2／3 n-gram 索引 | B＋嵌入向量（本地或外部）＋RRF |
| 匹配定義 | `casefold_ascii_v0` | `normalized_v1` | v1＋語義近似（另行標示） |
| 候選完整性 | 對 v0 成立〔實驗 E2〕 | 對 v1 成立〔實驗 E2〕 | 字面部分同 B |
| 短詞延遲 | 隨掃描範圍增長，以工作量上限封頂並續查 | 走索引 | 同 B，加查詢嵌入 |
| 磁碟、寫入 | 不變 | 見 §5.2 | 再加每條消息一個向量 |
| 依賴 | 無 | 無新套件；OpenCC 字表資料檔（Apache-2.0） | 模型檔或外部服務 |
| 隱私 | 不變 | 不變（衍生索引隨刪除同步） | 外部嵌入須把私人聊天送出 |

**推薦 B，A 作為 P1 過渡。**理由〔審查〕：

1. G01–G10 都能由 B 解決，不需要語義模型。
2. 原話核對需要字面精確：「三千」不能被近似成其他金額，「不買」不能被當成「買」。
3. 主 Agent 本身是 LLM，能把口語需求改寫為時間範圍、發言人與 `any_of`；工具負責精確執行並回顯解讀。

**語義召回暫列 P4。**MIRACL 顯示中文自然語言問題上 BM25 明顯弱於稠密模型（論文 13），但任務不同；是否需要，以 P0 的「改寫類」查詢與 Agent 多查詢消融結果決定（V65）。

## 6. 匹配定義與查詢合同

### 6.1 匹配定義與正規化

一條消息的可匹配欄位為 `content` 與 `audio_transcript`，分別匹配，不跨欄位拼接。`visual_summary` 不參與（D04）。

**`casefold_ascii_v0`（P1 至 v1 索引上線前）**

- `fold0(x)` = 去掉首尾空白後，把 ASCII `A–Z` 轉小寫，其他字元不變。
- 詞 t 命中欄位 f ⇔ `fold0(t)` 非空且是 `fold0(f)` 的子串。

**`normalized_v1`（P2 起）**

- **定義**：`fold(x)` 對**整個字串**依序執行：
  1. NFKC；
  2. `str.casefold()`；
  3. 再做一次 NFKC（casefold 的輸出可能不是 NFKC）；
  4. 繁轉簡逐字映射：OpenCC `ver.1.4.2`（commit `025f371d`）的 `data/dictionary/TSCharacters.txt`。4,148 個來源字皆為單一字元；其中 996 個有多個候選，一律取第一個，第一個候選皆為單一字元；
  5. 刪除所有 Unicode 空白字元（`str.isspace()` 為真者，含換行與全形空白）。
- 詞 t 命中欄位 f ⇔ `fold(t)` 非空且是 `fold(f)` 的子串。
- Unicode 資料版本是定義的一部分：本輪核對為 Python 3.12.7 的 `unicodedata` 15.0.0。部署的 Python 升級若改變 `unicodedata.unidata_version`，按匹配定義改版處理（§7.5）。

**為何不能逐單元正規化後串接**〔審查＋實驗 E10〕：Unicode 正規化對串接不封閉（[UAX #15 §1.4](https://www.unicode.org/reports/tr15/#Concatenation)）。NFKC 會依組合類別重排相鄰的組合字元，再與前面的起始字元合成。第二版以「`fold(u+c) ≠ fold(u)+fold(c)` 就併入」貪婪切分：`x = a◌̕◌̀`（U+0061 U+0315 U+0300）先在 `a` 後切開，因為 `a◌̕` 不合成；`◌̕◌̀` 再被重排成 `◌̀◌̕`，卻已無法與 `a` 合成，得到 `a◌̀◌̕`。整串 NFKC 則得 `à◌̕`，與 `y = à◌̕`（U+00E0 U+0315）相同。第二版的結果是 `x`、`y` 互不命中，違反 R04。

**實作：只在安全起點切分**。索引與高亮需要「每個輸出字元來自原文哪裡」，所以實作把原文切成段，逐段計算 `fold` 後串接。切點只放在字元 c 之前，且 c 滿足：

- c、`NFKD(c)`、`NFKD(casefold(NFKC(c)))` 的第一個字元，組合類別都為 0；
- 且都不屬於「可作為標準合成第二元素」的集合。此集合由 `UnicodeData` 中長度為 2 的標準分解取第二個字元，加上諺文中聲 U+1161–U+1175 與終聲 U+11A8–U+11C2 得到；Unicode 15.0.0 下共 133 個。

這樣切出的段，在任何一個正規化步驟中都不會與前一段互動：重排只發生在組合類別非 0 的連續字元之間，合成只發生在起始字元與其後可作第二元素的字元之間；casefold、繁轉簡與刪空白都是逐字映射。因此逐段串接等於整串 `fold`〔審查〕。這一點以實驗而非推理定案〔實驗 E10〕：對 Unicode 15.0.0 全部已指派且判定為安全起點的碼位，各接在 16 種前文（空字串、組合序列、諺文、半形假名、印度系文字的元音附標等）之後，`fold(前文+c) = fold(前文)+fold(c)` 無一例外；200,000 條由組合字元、諺文字母、半形假名、相容字元混合的隨機字串上，分段結果與整串 `fold` 的差異為 0。安全判定偏保守，只會使段變大（高亮變寬），不影響匹配。

**答案與實作分開**：性質測試（V12、V15）的正確答案一律以整串 `fold` 加子串比較產生，不經分段實作。

**高亮偏移**：每個輸出字元記錄其所屬段在原文中的 `[start, end)`；匹配的高亮區間為第一個輸出字元所屬段的起點到最後一個輸出字元所屬段的終點。性質：高亮的原文子串經 `fold` 後一定包含查詢詞〔實驗 E10〕。字元展開（`㎏`→`kg`）時，查 `k` 會高亮整個 `㎏`；合成（`e`＋`◌́`→`é`）時兩個原字元同屬一段；被刪的空白若位於匹配中間，會落在區間內。偏移單位是 Unicode code point。〔實驗 E2〕：`PR #448` 在 `see ＰＲ＃４４８ ok` 得 `[4,10)`；`k` 在 `5㎏` 得 `[1,2)`；`é` 在 `cafe◌́!` 得 `[3,5)`；`报销` 在 `報 銷單` 得 `[0,3)`；`ガ` 在 `ｶﾞｲﾄﾞ` 得 `[0,2)`。

**刪除空白的產品含義**〔審查〕：`PR #448`／`PR#448`、「報 銷」／「报销」、跨換行的同一句都能互相找到；代價是英文詞界消失，`new york` 也會命中 `renewyorkshire`。聊天搜尋中，空白不一致造成的漏查比英文詞界誤命中更常見；誤命中由 Agent 閱讀原文與高亮辨別。若 P0 評估顯示英文誤命中明顯（X06），可在 v2 改為「空白折疊為單一空格」，屬匹配定義改版（§7.5）。

### 6.2 候選完整性不變量

> **C-INV**：對當前範圍內任一消息 m、任一詞 t，若 t 依當前匹配定義命中 m，則 m 屬於 t 的候選集合。

候選可以多召回，由原文核驗剔除；不得漏召回。

| 定義 | 候選來源 | 為何成立 |
| --- | --- | --- |
| v0，`len(fold0(t)) ≥ 3` | 現行 trigram 表的短語查詢 `"t"` | trigram 的大小寫折疊對每個字元一對一且涵蓋 ASCII，fold0 的子串關係在逐字映射下保持〔審查〕；〔實驗 E2〕300 條查詢無漏召回 |
| v0，長度 1–2 | `instr(lower(f), lower(t))`，在工作量內掃描 | SQLite 未編譯 ICU 時 `lower()` 只折疊 ASCII，與 fold0 一致 |
| v1，已索引事件 | 長度 1 查單字詞元；長度 2 查雙字詞元；長度 ≥ 3 查全部三字詞元的 AND，限定在同一欄位 | 若 s 是 `fold(f)` 的子串，s 的每個 n-gram 都是 `fold(f)` 的 n-gram；詞元由分段實作產生，與整串 `fold` 相等（V15） |
| v1，佇列中或前沿以下的事件 | 直接讀原文、以 `fold` 核驗（§7.4） | 不依賴索引 |

C-INV 以性質測試驗收（V12–V14）：隨機生成語料與查詢，與暴力比對結果相比，漏召回必須為 0。

### 6.4 證據組：哪些消息共同滿足查詢

**定義**：

- **需求集合 Q**：`terms` 中每個詞各為一個需求；若有 `any_of`，整個 `any_of` 合為一個需求。只帶篩選時 Q 為空。
- **命中消息 H**：範圍內、符合時間／`sender`／`has` 篩選、至少滿足 Q 中一個需求、且不含任何 `exclude` 詞的消息，依 `event_id` 排序。每條命中 h 有 `covers(h) ⊆ Q`。
- **跨度**：兩條消息之間的**消息距離** = 兩者之間（不含兩端）的範圍內 keeper `message` 事件數＋1；**時間跨度** = 兩者 `occurred_at` 之差。

**證據組**：

| 情形 | 證據組 |
| --- | --- |
| `match_within=message`，或 Q 為空，或 \|Q\| = 1 | 每條覆蓋全部 Q 的命中自成一組 |
| `match_within=group`（預設）且 \|Q\| ≥ 2 | H 上的**最小覆蓋窗口** `[l, r]`：窗口內命中的 covers 聯集等於 Q，且去掉左端或右端都會失去覆蓋；同時 l 到 r 的消息距離 ≤ `chat_search_group_max_messages`、時間跨度 ≤ `chat_search_group_max_minutes` |

**必要命中**：左端、右端，以及左右端都未覆蓋的需求各取窗口內最早覆蓋它的命中。必要命中數 ≤ |Q|。

**性質**〔審查〕：

1. **不漏組**：若存在一組命中在跨度限制內共同覆蓋 Q，則從它的範圍兩端收縮得到的最小覆蓋窗口也在限制內，且會被枚舉到。因此「先按覆蓋枚舉最小窗口，再以跨度過濾」不會漏掉任何可成立的證據。
2. **不遞移**：證據組彼此獨立，不因中間命中相連而串成長鏈。〔實驗 E6〕A、C 每 10 分鐘交替、最後出現 B 時，只得到靠近 B 的窗口 #28–#31。
3. **與上下文無關**：證據組的定義不含 `context_before`／`context_after`、片段上限或展示合併。
4. **反例**〔實驗 E6〕：S14 得到唯一證據組 {#12, #13}；首版「合併後在最大間隔處切開再丟棄」得到空集合。
5. **重疊**：`A B A` 得到兩個證據組 [#1,#2] 與 [#2,#3]，展示時合併（§6.5）。

**演算法**：在已取得的命中上以雙指標掃描（右指標前進、左指標盡量收縮，只記錄右端也必要的窗口），時間 O(|H|·|Q|)。窗口的消息距離以範圍限定的計數查詢求得，以 `LIMIT group_max_messages + 1` 封頂。

### 6.5 展示片段：回傳多少上下文

每頁選出的證據組依下列步驟組成片段。這些步驟只影響展示，不改變 §6.4 的結果。

1. **核心**：第一個到最後一個必要命中之間的全部消息。超過 `chat_search_fragment_max_events` 時只保留必要命中，其餘以 `gap_before`（被省略的消息數）標示。
2. **上下文**：核心之前取 `context_before` 條、之後取 `context_after` 條（同 Conversation、floor 之後、keeper、`message`）。
3. **被回覆原文**：每個必要命中若有 `reply_to_event_id`，且原消息在範圍內、floor 之後，就加入，每個必要命中最多一條。
4. **合併**：同一頁的片段，事件範圍重疊或相鄰時合併（只是展示上的遞移合併）；合併後若超過上限，只省略上下文，**不省略必要命中**，必要時以 `gap_before` 標示。
5. **角色與去重**：每個事件在整個回應中只出現一次，角色優先順序為「必要命中」＞「非必要命中」＞「被回覆原文」＞「上下文」。一個事件可放入多個片段時，放在它角色最高的片段；角色相同則放在排名較前的片段，其他片段以 `see_also_event_ids` 引用。
6. **排列**：片段內事件按 `event_id` 正序；片段之間依其中最前的證據組排名。

### 6.6 排序

| `order` | 鍵（依序比較） | 範圍 |
| --- | --- | --- |
| `recent`（預設） | 證據組最後一個必要命中的 `event_id` 遞減 | 全局精確（§6.7） |
| `oldest` | 證據組第一個必要命中的 `event_id` 遞增 | 全局精確 |
| `relevance` | ① 消息距離遞增；② 時間跨度遞增；③ 必要命中所在欄位的正規化字元總數遞增（越短越聚焦）；④ 最後一個必要命中的 `event_id` 遞減；⑤ 第一個必要命中的 `event_id` 遞減 | 排名範圍內精確；回報 `ranking_scope` 為 `complete` 或 `scanned_range`（§6.7） |

**不使用 BM25 的理由**〔實驗 E5〕：

- FTS5 `bm25()` 越低越相關。同一組資料插入 50 條無關文件後，同一文件的分數由 −6.33 變為 −6.55；分頁期間新增消息會改變排名。
- 按消息累加時，兩條消息的組合（−12.65）比一條同時含兩詞的消息（−11.01）分數更低，因而被排得更前，偏好消息多的組合。
- 單詞查詢時證據組都是單條消息，BM25 主要反映消息長度；鍵 ③ 以穩定的方式表達同一訊號。

**`single_sender_cover` 不作排序鍵**〔審查〕：甲問「預算多少？」、乙立刻答「三千」，與甲在 15 條之外自己補一句「三千」相比，前者往往更相關。此欄位只作為事實回報；它作為平手鍵的效果由 P0 消融比較（V62）。

**預設改為 `recent`**〔審查〕：它在分頁上全局精確，與微信的查找順序一致；需要按鄰近度挑選時，Agent 再指定 `relevance`。

### 6.7 掃描、預算、結果狀態與游標

以 `recent` 描述；`oldest` 把 `event_id` 的方向整體反轉，規則相同〔實驗 E7 以鏡像資料驗證對稱〕。

**記號**：

- 所有區間都是半開區間。floor 為範圍下界（`starts_after_event_id` 之後的第一條）。
- `pos(e)`：事件 e 在範圍內 keeper `message` 序列中的序號，以範圍限定的計數查詢求得。
- `M`：證據組允許的最大消息距離 `chat_search_group_max_messages`。單一需求、`match_within=message` 或純篩選時，每條命中自成一組，`M = 0`。
- **來源**：一條按 `event_id` 遞減、以 keyset（`event_id < 位置 ORDER BY event_id DESC LIMIT p`）讀取的候選流。每個 v1 詞有一條索引來源（`event_id ≥` 前沿 F 的索引候選與佇列中的事件）；前沿以下的直接核驗、v0 短詞的掃描與純篩選，各是一條所有需求共用的掃描來源。`any_of` 的每個成員詞各是一條來源，屬於同一個需求。時間、`sender`、`has` 篩選在讀取來源時一併套用；`exclude` 在原文核驗時套用。
- **快照上界 U**：首頁讀交易內，範圍中最大的 message `event_id`。之後各頁只看 `event_id ≤ U`。範圍內沒有消息時 U 為空，回應直接 `exhausted`，不產生游標。

**游標位置是 (E, S)**：E 是輸出上界（只輸出最後必要命中 < E 的證據組），S 是掃描上界（各來源從 S 往下讀）。首頁 E = S = U＋1。

**工作量合同：軟閾值、固定檢查點、可計算的上界。**`chat_search_request_budget`（下稱 B）不是硬上限。硬上限做不到兩件事：來源數大於 B 時，第一個合併步無法讓每條來源各讀一個候選，前沿就不會下降；上一頁留下的窗口本身就可能超過 B。因此 B 是**停止閾值**：只在檢查點判斷，檢查點之後已開始的工作單元做完；超出部分只來自兩個強制單元，並有公式上界。

**計價單位**（一列 = SQLite 回傳的一列）：

| 工作 | 計價 | 何時計 |
| --- | --- | --- |
| 候選讀取 | 每個候選 `u = 2 + d` 單位：來源列 1（索引 rowid、佇列 `DISTINCT event_id` 或掃描列）＋原文核驗 1＋距離計數預留 d。多需求時 `d = M + 1`，否則 `d = 0` | 讀取時預先扣除 |
| 原文核驗 | 同一事件在一頁內只讀一次原文；前沿以下的掃描列已含原文 | 已含在 u |
| 距離計數 | 每個需要判斷的窗口以 `LIMIT M+1` 計數一次，最多讀 M＋1 列；一頁內同一窗口只計一次。每個右端點只會被判斷一個窗口，所以實際列數不超過預留 | 已含在 u |
| 邊界取位 | 掃描新範圍時，每個合併步最多取 M＋1 條消息定位輸出下界，預留 `b = M + 1` 單位；單一需求時 b = 0。固定排名範圍的重算已知輸出下界，不查詢、不計 b | 掃描合併步結束時 |
| 窗口重讀 | 按候選讀取計價 | 頁首 |
| `relevance` 範圍重算 | `u × 重算候選數`；原文核驗與距離計數預留已含在 u，不增加邊界取位（見下文） | 頁首 |
| 上下文、被回覆原文 | 每列 1，**不參與停止判斷**；只為已輸出的證據組讀取，上界 `limit × (chat_search_fragment_max_events + context_before + context_after + |Q|)` | 停止之後 |

**一次請求**（一個讀交易內完成，§7.8）：

1. 核對游標綁定（見下文「一致性合同」），不符回 `cursor_stale`。已計價 C = 0。
2. **窗口重讀**（強制單元）：讀各來源在 [S, E) 內的候選。窗口只在 `incomplete` 之後存在，且只涵蓋 `pos(f)` 起的 M 條消息，因此最多 `n · M` 個候選（n 為來源數）。
3. **合併步**：設活躍來源數為 a，`R = B − C`。每條活躍來源從自己的位置往下讀 p 個候選，`p = min(chunk, ⌊(R − b) / (a · u)⌋)`；**第一個合併步**是強制單元，p 至少為 1。讀不滿 p 的來源視為已到 floor。之後扣除邊界取位 b。
4. **前沿 f**：未窮盡來源目前位置的最大值；全部窮盡時 f = floor。所有 `event_id ≥ f` 的候選都已讀到。
5. 只用 `event_id ≥ f` 的候選做原文核驗與證據組計算（§6.4）。證據組在本頁**可輸出**，條件是：最後必要命中 < E；且全部來源已窮盡，或其最後必要命中滿足 `pos ≥ pos(f) + M`。後一條保證：尚未讀到的命中（都 < f）不可能再組成一個最後必要命中更大的證據組，因為證據組跨度不超過 M。
6. **檢查點**（每個合併步之後）：可輸出的證據組已達 `limit + 1` 組 → `more`；全部來源已窮盡 → `exhausted`；`B − C < a · u + b`（下一個最小合併步放不下）→ `incomplete`；否則回到第 3 步。
7. 停止後，只為要輸出的證據組讀取片段核心、上下文與被回覆原文（§6.5）。

**上界**：檢查點之後的非強制合併步，p 依剩餘量選取，不會超過 B。因此一頁的搜尋計價

> `C ≤ max(B, u · n · M + a₁ · u + b)`

其中 a₁ 是第一個合併步時的活躍來源數。右項只在窗口重讀與第一個合併步已超過 B 時出現，例如 B = 1、來源數大於 1，或窗口已用完 B。展示讀取另有上表的上界。回應的 `work` 欄位分別回報 B、計價 C 與各類實際列數（§6.8）。

**取消**：一頁是一個讀交易。工具執行或插件呼叫被取消時（`asyncio.CancelledError`），取消在下一次資料庫等待處生效並向上傳遞，session 關閉時回滾；不產生回應，也不產生新游標。游標不在伺服器端保存狀態，原游標仍可重送。

**結果狀態與下一個游標**：

| `result_state` | 條件 | `next_cursor` (E, S) |
| --- | --- | --- |
| `more` | 已得 `limit + 1` 組可輸出的證據組；輸出前 `limit` 組 | (本頁最後一組的最後必要命中, 同一值)：不留窗口，下一頁從該處重新讀取 |
| `exhausted` | 全部來源已到 floor；輸出全部可輸出的證據組（≤ `limit`） | `null` |
| `incomplete` | 下一個最小合併步放不下，且還有來源未到 floor；輸出全部可輸出的證據組（< `limit + 1`，可能為 0） | (min(E, `pos(f)+M` 位置上的事件), f)；`pos(f)+M` 超出 U 時取 U＋1 |

`limit_applied` 只說明實際採用的上限，不影響狀態。

**進展與終止**〔審查＋實驗 E7〕：以 (E, S) 的字典序衡量。`more` 頁至少輸出一組，E 嚴格下降；`incomplete` 頁的第一個合併步讓每個未窮盡來源都至少讀到一個 < S 的候選（讀不到就是已窮盡），所以 f < S，E 不增而 S 嚴格下降。靜態資料上 (E, S) 只有有限個值，反覆續查必定以 `exhausted` 結束。各頁輸出的證據組按 E 劃分，互不重疊。這個論證不依賴 B 的大小，B = 1 也成立。

**第二版的停滯錯誤**：第二版以「讀到的最後一個 id 為下界 L、輸出 (L, C)、下一頁 C = L＋1」推進。C = 4、預算 1、讀到 id 3 時，L = 3，(3, 4) 為空，下一頁 C 仍是 4，永遠停在原地〔實驗 E7 重現〕。原因是讀取的下界（含 L）與輸出區間（不含 L）不一致，下一頁上界又把 L 包回來。本版統一為半開區間：f 本身的候選已讀到並參與計算，下一頁從 S = f 往下讀 `event_id < f`。

**實驗驗證**〔實驗 E7〕：在 300 組隨機資料（0–200 條消息、1–4 條來源、含 `any_of` 兩來源同屬一個需求、命中密度 0–50%、M 取 1／3／10、跨度秒數有限或不限）上，對預算 1、2、3、7、候選總數與「足以一頁讀完」、`limit` 1、2、5，以及 `recent` 與鏡像後的 `oldest`，反覆續查到結束，並在每頁以上式計算上界、比對實際讀取列數：結果列於 §2.4。第三版記錄的「單頁超支最多 19 個候選讀取」只是該組資料的觀察值，不是上界，已刪除；本版的上界是上式。

**一致性合同：同一快照的精確劃分，或明確失效。**

游標綁定以下欄位；任一不符就回 `cursor_stale`，Agent 以相同參數重新查詢：

| 綁定 | 來源 | 失效的情形 |
| --- | --- | --- |
| `conversation_id`、`generation`、`starts_after_event_id`、`prompt_source_revision` | 既有 `ConversationReadVersion`（`event_repository._read_version`），在本頁讀交易內讀取 | revision 由 0119 的 `PROJECTION_TRIGGERS_0119` 維護：同會話事件刪除、`content`／`segments_json`／`visual_summary`／`external_payload_json`／`suppression_status`／`canonical_conversation_id` 更新、`audio_transcript` 更新、generation 或 floor 重置，都會加 1。插入不改變 revision |
| U | 首頁讀交易 | 新消息的 `event_id` > U，不進入任何續頁，也不使游標失效 |
| `match_definition`、索引 epoch | 狀態表（§7.1） | 匹配定義改版或索引損壞重建 |
| 匹配欄位雜湊、`order` | 請求參數 | A-9 |

因此：

- **各頁是首頁快照結果的精確劃分**：revision 與 U 相同時，範圍內 `event_id ≤ U` 的消息與其可匹配欄位都沒有變化，因為本會話的刪除與更新必然改變 revision。新插入的 id 是當時全庫最大 id＋1，必大於 U；只有本會話 id 為 U 的事件先被刪除時，新 id 才可能等於 U，而那次刪除已改變 revision。因此靜態資料上的不重不漏論證直接適用。
- **新消息只被 U 排除**，不使游標失效；需要看到新消息時重新查詢。
- **刪除、轉錄更新、floor 變化**不再有「可能被略過」或「可能重複」的灰區，一律 `cursor_stale`。審查的反例（甲 ASR 6 字、乙 12 字、`relevance` 以 `limit=1` 先回傳甲；甲的 ASR 更新為 30 字後，第二版續查會先回乙、再回甲一次）在本版第二頁即回 `cursor_stale`〔實驗 E11 以倉庫的 0119 觸發器重現〕。
- 代價：會話內任何影響提示來源的更新（例如語音轉錄陸續完成）都會讓翻頁中的游標失效。這是以「重查」換取「不重不漏」，風險見 §13.4。
- 索引器、回填與佇列的寫入不改 `chat_events`，不影響 revision；建置進度不使游標失效。

**`relevance` 的排名範圍**：

1. **發現新排名範圍**：從當前游標 (E, S) 以 `limit = ∞` 執行上面的掃描步驟，含 [S, E) 的窗口重讀，直到預算檢查點停止或全部窮盡。得到**候選重算範圍** [f₁, E) 與其中全部可輸出的證據組；首次 E = S = U＋1。保存輸出下界 L：全部窮盡時為 floor，否則為 `min(E, pos(f₁)+M 位置上的事件)`，該位置超出 E 時取 E。只輸出最後必要命中在 [L, E) 的組；[f₁, L) 保留為組合所需窗口。全部窮盡時 `ranking_scope="complete"`；否則 `ranking_scope="scanned_range"` 並回報範圍。
2. 依 §6.6 的鍵排序，輸出前 `limit` 組。游標記錄範圍（E、f₁、L）、最後輸出的排序鍵、發現該範圍時的索引前沿 F₁，以及 W。
3. **W 的定義**：W 就是發現該排名範圍的首頁回應之 `work.charged`：`u × N首頁 ＋ b × K首頁`。N首頁包括窗口重讀與全部來源讀到的候選，K首頁為掃描合併步數；u 已含原文核驗與距離計數預留。W 與 `work.charged` 同為計價單位，展示讀取不計入。SQL 實際列數另在 `work.rows` 回報，兩者不混用。
4. **續頁凍結讀取計畫，刪除邊界取位**：以 F₁ 而不是當前前沿劃分來源。範圍內 `< F₁` 的事件一律由共用掃描直接核驗（即使已被回填入隊或已建索引）；`≥ F₁` 的事件走索引與佇列，佇列也限定 `≥ F₁`。各來源以 keyset 讀完 [f₁, E)，每批最多 `chunk` 個候選；重算證據組後仍只保留最後必要命中在 [L, E) 的組，按最後輸出的排序鍵續接。E、f₁、L 均已保存，無須重新定位輸出下界，故不執行邊界查詢、不收取 b。重算計價為 `C重算 = u × N重算`，計入續頁的 `work.charged`。恰好讀滿 chunk 後可以用空讀取確認窮盡，該讀取回傳 0 列，不增加候選計價。
5. **為何重算計價不超過 W**：同一 revision 下消息不變；首頁已讀齊 [f₁, E) 中各來源的候選，且 N首頁還可能包括範圍外的預讀。按 F₁ 凍結後，`< F₁` 的共用掃描不變；`≥ F₁` 的事件在同一 epoch 內只會從「佇列」移至「已索引」，候選從每條詞來源都有縮減為只有 n-gram 相符的來源才有；內容更新或重建會先使游標失效。故 `N重算 ≤ N首頁`，從而 `C重算 = u × N重算 ≤ u × N首頁 ≤ W`。證明與重讀批數、是否需要最後一次空探測無關。命中與證據組相同，距離計數各以 M＋1 列封頂、已包含於 u 的預留；不額外掃描全會話來計算消息位置。
6. **修訂反例**〔實驗 E14〕：20 條都含 alpha 與 bravo 時，候選與核驗的 SQL 列數仍為首頁 20、按當前來源重算 60、按 F₁ 重算 20；計價為 W = 20 × 23 ＋ 21 = 481、按當前來源 920、按 F₁ 460。另有 60 條都含兩詞、chunk = 25、B = 1,171 的預算截斷案例：首頁讀 50 個候選，一步後停止，W = 1,171，保存 [f₁, E) = [36, 61)、L = 56，得到 5 組可輸出結果。舊規則重算多做一次空探測並取邊界，計價 1,192；本版重算仍有兩批讀取，但邊界查詢為 0，計價 1,150，保留同樣 5 組。完整與混合範圍、跨消息成組、跨排名範圍續查見 §2.4 E14。
7. **重算是強制單元**：重算做完即輸出，不因 B 中斷、不在同一頁接著掃描新範圍；其計價不超過建立本範圍時受上界約束的 W。範圍內還有未輸出的組時回 `more`；已輸盡時，若範圍為 `complete` 則 `exhausted`，否則回 `incomplete`，游標指向下一範圍 (E = L, S = f₁)，下一頁以當前索引前沿發現新範圍。因此每頁有輸出或結束本範圍；發現新範圍時沿 (E, S) 字典序推進。凍結計畫保證有界，索引完成後按當前來源可能更省，但事先無法據此保證上界，因此仍沿 F₁。
8. 索引 epoch 改變時（重建清空索引，`≥ F₁` 的事件不再有索引列）游標失效，不在凍結計畫不成立時續算。
9. 取消行為同上：重算中被取消時不產生回應，原游標可重送，重送時的重算計價仍不超過 W。

**游標內容**：格式版本、匹配欄位雜湊、`order`、上表的綁定欄位、E、S，`relevance` 另含範圍、最後輸出的鍵、F₁ 與 W；以 base64url 編碼的 JSON 傳遞。範圍由執行處依當前 runtime 重新核驗；游標只表示位置，不授予權限，因此不另加簽章。

### 6.10 插件 API

Plugin API 3.5 的 `search_history(query, limit)` 簽名與語義保留：

- `query` 作為單一詞（`terms=[query]`），使用當前匹配定義；`limit` 仍是**消息數**，沿用 `_bounded_limit`；回傳型別仍為 `tuple[CurrentMessage, ...]`；範圍仍是當前會話 scope 與 floor。
- 回傳**最近的 `limit` 條命中消息**，按時間正序，與現行行為一致。單一詞時每條命中自成一組，證據組數等於消息數。

插件 API 無法表達「還沒找完」，所以 facade 不能在一頁的工作量用完時回傳部分結果。第二版「回傳已找到的部分」讓插件無法分辨「只有這些」與「還沒查到」〔實驗 E13：只用一頁時漏掉最舊的命中〕。本版：

1. **內部續頁**：facade 以 `order=recent` 呼叫共用服務，每頁請求尚缺的條數（受 `chat_search_max_limit` 限制）；尚未取得 `limit` 條且 `result_state` 為 `more` 或 `incomplete` 時，以 `next_cursor` 續查；取得 `limit` 條或 `exhausted` 時停止。每一頁是獨立的讀交易與工作量（§7.8），頁與頁之間不持有交易。P1 的 v0 短詞掃描與 P2 建置、重建期間的前沿以下核驗都走同一段迴圈，不另寫分支。
2. **游標失效**：續頁回 `cursor_stale` 時，丟棄已取得的部分，從首頁重新查詢（新的快照與 U）。
3. **取消**：插件呼叫所在的 task 被取消時（`asyncio.CancelledError`），取消照常向上傳遞，當前頁的讀交易隨 session 關閉而回滾，不回傳部分結果。
4. **真實失敗**：資料庫錯誤、權限錯誤與參數錯誤沿用 facade 現有的例外，不轉成空結果或部分結果。
5. **成本**：最壞情況是單一常見詞在大會話中的多頁掃描，總工作量為「到第 `limit` 條命中為止」的掃描量，每頁的搜尋計價都不超過 §6.7 的上界，寫入者不受影響。

R19 因此統一為：每一頁以預算為停止閾值、計價有公式上界；一頁停止不等於搜尋完成。Agent 得到 `incomplete` 與游標，自行決定是否續查；插件由 facade 在內部續查，對插件呈現完整的「最近 N 條」。

## 7. 索引與生命週期

### 7.1 資料關係

```text
chat_events（原始證據，唯一真源；搜尋不寫入或修改）
  ├── chat_search_index_v1   FTS5 contentless-delete：content_grams, asr_grams（衍生，可由帳本重建）
  ├── chat_search_queue      (seq INTEGER PRIMARY KEY AUTOINCREMENT, event_id INTEGER NOT NULL)，索引 (event_id)
  └── chat_search_state      單列：frontier_event_id, epoch

查詢時組裝（不落地）：
  命中（hit）→ 證據組（§6.4）→ 片段 = 必要命中 ∪ 非必要命中 ∪ 被回覆原文 ∪ 上下文（§6.5）
```

證據組與片段只存在於一次工具回應中，不建表、不持久化，因此刪除與遺忘不需要另外清理它們。

### 7.2 詞元（v1）

1. 對欄位文字以分段實作計算 `fold`（§6.1）。
2. 對 `fold` 結果的每個位置輸出 1、2、3 字元 n-gram。詞元以「類型字母＋UTF-8 十六進位」編碼（`u`／`b`／`t`），只含 ASCII 英數，避開 tokenizer 對標點、表情、空白的切分。
3. `content` 的詞元寫入 `content_grams` 欄，`audio_transcript` 的寫入 `asr_grams` 欄。查詢以欄位過濾 `{content_grams}: (…)` 與 `{asr_grams}: (…)` 分別查詢，避免跨欄位拼出的假候選。

### 7.3 觸發器、佇列與索引器

| 事件 | 處理 | 持鎖 |
| --- | --- | --- |
| 插入 `message` | 觸發器：`INSERT INTO chat_search_queue(event_id) VALUES (new.id)` | 原插入交易內多寫一列 |
| `content` 或 `audio_transcript` 更新 | 觸發器：`DELETE FROM chat_search_index_v1 WHERE rowid = old.id`，再插入佇列 | 同上 |
| 刪除、隱私遺忘 | 觸發器：刪除索引列；`DELETE FROM chat_search_queue WHERE event_id = old.id`。不依賴外鍵（遷移在 `foreign_keys=OFF` 下執行） | 同一刪除交易 |
| 索引器（唯一的索引寫入者） | 見下 | 每批一個短寫交易〔實驗 E2：500 列寫交易時間〕 |

`seq` 為 `AUTOINCREMENT`，同一事件後入隊的列 `seq` 一定較大。

**索引器一輪**：

1. 讀交易：`SELECT event_id, MAX(seq) FROM chat_search_queue WHERE event_id IN (SELECT event_id FROM chat_search_queue ORDER BY seq LIMIT :batch) GROUP BY event_id`，再批量讀這些事件的原文。
2. 交易外：正規化並產生詞元。
3. `BEGIN IMMEDIATE`：對每個 (event_id, s) 執行條件寫入，再刪佇列列：

   ```sql
   INSERT OR REPLACE INTO chat_search_index_v1(rowid, content_grams, asr_grams)
   SELECT :id, :content_grams, :asr_grams WHERE EXISTS (SELECT 1 FROM chat_events WHERE id = :id);
   DELETE FROM chat_search_queue WHERE event_id = :id AND seq <= :s;
   ```

   存在性在同一個寫交易內判斷；詞元已在交易外準備好，寫交易內只有主鍵查詢與寫入。

**刪除競爭**：事件在第 1 步讀取之後、第 3 步之前被刪除時，刪除觸發器已刪掉索引列與佇列列；若第 3 步無條件寫入，索引會留下帳本中不存在的孤兒列。孤兒列不會被搜尋回傳（核驗讀不到原文），但會讓索引與帳本不一致，也違反隱私遺忘「衍生資料一併刪除」的要求〔實驗 E8：無條件寫入殘留孤兒 rowid 1，條件寫入為 0〕。寫交易取得寫鎖之後，刪除不可能再插入到檢查與寫入之間。

**為何這樣推進**：第二版「讀前 `batch` 列，若同一事件有更新的 `seq` 就跳過」在 seq 1–500 與 501–1000 是同一批事件、批量 500 時，每一列都被跳過，佇列永不前進〔實驗 E8〕。本版以事件為單位取該事件在佇列中的最大 seq，讀到的原文不舊於這個 seq 對應的寫入，因此可以把 ≤ s 的列（含過期列）一起移出。讀取之後才入隊的新列 `seq > s`，不會被刪除，下一輪重新處理。最早的列一定屬於本批的某個事件，所以每輪至少移出一列，批量為 1 時也前進。

**佇列中的事件一律直接核驗**：索引列可能比佇列中的最新內容舊（更新觸發器已刪掉舊列，但索引器可能在讀取後寫回較舊的詞元，再由新的佇列列修正）。搜尋對佇列中的事件不使用索引結果，而是讀原文核驗，所以這段期間的索引內容不影響正確性。

**搜尋讀佇列**：以 `SELECT DISTINCT q.event_id … ORDER BY q.event_id DESC` 讀取，同一事件的多列只算一個候選，不會耗盡工作量。

觸發器是純 SQL，不依賴 Python 函式；Alembic、sqlite3 命令列與測試建庫寫入 `chat_events` 時都能正常運作。〔實驗 E4〕已確認 contentless-delete 表支援以 `rowid` 執行 `DELETE`、`INSERT OR REPLACE`、`integrity-check`、`optimize`、`delete-all`；不支援 `rebuild` 與 FTS5 `delete` 命令；不能讀回欄位值。

### 7.4 索引狀態與查詢路徑

狀態表只存兩個值：回填前沿 F（`frontier_event_id`）與索引 epoch。`index.state` 是回應中的推導值，不另存：

| `index.state` | 條件 | 查詢路徑 |
| --- | --- | --- |
| `trigram_v0` | P1，尚無 v1 索引 | v0 定義：三字以上走 trigram，一兩字在工作量內掃描 |
| `building` | 範圍內有 `event_id < F` 的 message | `event_id ≥ F` 且不在佇列中的事件走索引；佇列中與 `event_id < F` 的事件逐條讀原文以 `fold` 核驗，計入工作量 |
| `ready` | 範圍內沒有 `event_id < F` 的 message | 索引＋佇列中事件的直接核驗 |

首次建置、改版與損壞重建都是同一個狀態：前沿以下還有事件。epoch 只用於游標綁定（§6.7），不參與查詢路徑。

**取捨**〔審查〕：

- **索引落後也不漏查**：佇列中與前沿以下的事件都直接核驗，C-INV 在所有狀態成立〔實驗 E12〕。
- **不掃整個會話**：`ready` 只直接核驗佇列中的事件，穩態下佇列只有剛寫入的少數列。`building` 時，前沿以下的掃描受每頁的預算檢查點與計價上界約束，停止時回 `incomplete` 並以游標續查。
- **全量在線重建**：不需要停機，也不需要遷移掃描歷史。代價是重建期間的舊範圍查詢較慢；由新到舊回填，讓最常查的近期範圍最先恢復全速。

### 7.5 回填、空庫、匹配定義改版與索引損壞

**狀態列初始化**：遷移與 `create_schema()` 執行同一句 SQL（凍結於 `CHAT_SEARCH_0120`）：

```sql
INSERT INTO chat_search_state(id, frontier_event_id, epoch)
SELECT 1, COALESCE(MAX(id), 0) + 1, 0 FROM chat_events;
```

`MAX(id)` 是主鍵查詢，不掃描歷史。空庫得到前沿 1。

**回填 worker**（P2 首次上線、改版與重建共用）：

1. 讀交易：讀狀態列 (F, epoch)，取 `id < F` 的前 `chat_search_backfill_batch` 個 message id（遞減）。沒有就閒置，等前沿被重設。
2. 短寫交易：`UPDATE chat_search_state SET frontier_event_id = :min_id WHERE frontier_event_id = :F AND epoch = :epoch`；更新到一列時才把這些 id 插入佇列，否則不寫入、下一輪重讀。
3. 佇列長度超過 `chat_search_queue_high_water` 時暫停回填，讓索引器先消化。這只是節奏控制，不是完成條件。

第 2 步的比對是必要的：若讀取之後、寫入之前發生損壞重建（前沿重設到最新、清空索引），不比對就寫入會把前沿寫回舊位置，舊前沿以上的事件既不在索引、也不再被核驗〔實驗 E12：16 組比對全部不一致；比對後為 0〕。

**沒有完成門檻**：第二版的「F 到達最小 id、且佇列中不再有回填產生的列時改為 `ready`」無法判斷（佇列不記錄列的來源），也不需要：前沿與佇列已足以決定查詢路徑，`ready` 只是推導值。本版刪除 `state` 欄與這個轉換。

**空庫與空會話**：

| 情形 | 行為 |
| --- | --- |
| 空庫建表 | 前沿 1、epoch 0；回填讀到 0 列，閒置 |
| 空會話首次搜尋 | U 為空，`exhausted`，`fragments=[]`，無游標（§6.8） |
| 第一條消息，索引器處理前 | 觸發器已入隊，搜尋經佇列直接核驗找到 |
| 第一條消息，索引器處理後 | 走索引找到；`index.state="ready"` |

〔實驗 E12〕兩條建庫路徑的四種情形都與暴力答案一致。

**匹配定義改版（例如 v1 → v2）**

1. 改版必然伴隨程式碼發布。新遷移只做 DDL：建立 `chat_search_index_v2`、刪除 `chat_search_index_v1`、重建觸發器指向 v2；以主鍵查詢把前沿重設為 `MAX(id)＋1`，epoch 加 1。不同版本的表不並存，查詢只使用一種匹配定義。佇列保留，索引器之後寫入 v2。
2. 回填流程同上。
3. 回應的 `match_definition` 隨之改變，舊游標回 `cursor_stale`。

**索引損壞**

contentless 表的 `integrity-check` 只檢查索引內部結構，不能比對原文。因此另做抽樣自檢：每次啟動與每隔 `chat_search_selfcheck_interval`，隨機抽取若干已索引且不在佇列中的事件，取其原文中的一個三字詞元查詢，確認回傳該 rowid。

`integrity-check` 失敗或抽樣自檢不符時，一個短寫交易：`INSERT INTO chat_search_index_v1(chat_search_index_v1) VALUES('delete-all')`；前沿設為 `MAX(id)＋1`；epoch 加 1。佇列不動，新寫入的消息照常經觸發器入隊。之後由回填 worker 從帳本重新入隊全部事件，期間查詢走前沿以下的直接核驗，結果符合 C-INV〔實驗 E12〕。第二版「刪除佇列中 id 小於最大 id 的列」沒有作用，已刪除。

`delete-all` 在大型索引上的持鎖時間尚未實測（X04）；若超過短寫交易的要求，改為在維護窗口由遷移以 DDL 刪除並重建該表（同「匹配定義改版」第 1 步）。

### 7.6 遷移持鎖成本

`migrations/env.py` 以單一 `BEGIN IMMEDIATE` 執行全部待執行遷移，所以正規化放在交易外，並不代表遷移沒有在寫交易中掃描歷史。若遷移以 `INSERT INTO chat_search_queue SELECT id FROM chat_events` 一次排入全部事件，它就是在寫交易中掃描全部歷史。

〔實驗 E4〕在 100 萬列窄表上，這個單一 SQL 持鎖 0.12 秒；以 5,000 列一批的 keyset 短交易，每批中位數 0.62 毫秒、最大 2.5 毫秒。0.12 秒只是下限：真實 `chat_events` 列較寬，掃描讀取的頁更多，而且它與同次遷移的其他步驟共用同一個交易。

決策〔審查〕：遷移只做 DDL 與一次主鍵 `max(id)`，歷史回填全部交給 worker 的短交易。理由不是單一 SQL 太慢，而是：① 開發約束禁止在 SQLite 寫交易中掃描歷史；② 損壞重建與匹配定義改版本來就需要在線回填，首次建置共用同一條路徑，不另寫遷移專用的回填；③ 遷移耗時因此與資料量無關。整體耗時以 V48 實測。

### 7.7 兩條建庫路徑

| 路徑 | 現況 | P2 | P3 |
| --- | --- | --- | --- |
| Alembic 遷移 | `0055` 匯入凍結的 `asr/schema.py:CHAT_FTS_0055` | 新增 `conversation/search_schema.py:CHAT_SEARCH_0120`（DDL、觸發器與狀態列初始化 SQL 的字串常數），由遷移 `0120` 匯入；此常數凍結，日後改版另立新常數 | 遷移 `0121` 刪除 `chat_events_fts` 及三個觸發器；downgrade 以 `CHAT_FTS_0055` 重建並 `rebuild` |
| 測試建庫 `Database._create_fts_schema()` | 使用 `CHAT_FTS_0055` | 執行同一個 `CHAT_SEARCH_0120`，包括同一句狀態列初始化；不另寫 `ready` 或任何專屬狀態 | 移除 `CHAT_FTS_0055`；`asr/schema.py` 的這個常數只供歷史遷移與 downgrade 使用 |

第二版讓 `create_schema()` 直接寫 `state='ready'`、遷移寫 `building`，兩條路徑行為不同，而 V49 只比較 SQL 文字，比不出這個差異。本版兩條路徑執行同一組語句，狀態由資料推導。

**一致性測試**（V49）分兩部分：

1. **結構**：同一空資料庫分別以「Alembic 升級到 head」與 `create_schema()` 建立，比較 `sqlite_master` 中名稱為 `chat_events_fts%`、`chat_search_%` 的表與 `chat_events` 上的觸發器（類型、名稱、正規化空白後的 SQL）。
2. **行為**：兩個資料庫的狀態列相同；再對兩者執行同一段生命週期腳本（插入、ASR 更新、刪除、索引器、回填、損壞重建），每一步比較搜尋結果、狀態列與佇列內容，必須一致。另以「先寫入歷史再遷移」的資料庫驗證回填路徑。

### 7.8 讀快照與交易邊界

**一次搜尋請求（一頁）在一個讀交易中完成。**實作沿用倉庫既有做法：`async with database.sessions() as session: await session.execute(text("BEGIN"))`（例如 `event_repository.read_scope_context` 先 `BEGIN` 再 `_read_version`）。WAL 模式下，deferred `BEGIN` 在第一次讀取時取得快照，之後同一 session 的所有讀取都看到同一版本；寫入者照常提交，不被阻塞（`Database` 以 `journal_mode=WAL` 連線）。

**為何必要**〔實驗 E9〕：候選來自索引、佇列與前沿以下三處，索引器把事件從佇列移到索引是一個交易。若三處各自在自動提交的語句中讀取，就可能出現「讀索引（事件尚未寫入）→ 索引器提交（寫入索引並移出佇列）→ 讀佇列（事件已移出）」，事件從兩處都漏掉。以倉庫的 `Database` 與 SQLAlchemy 2.0.51／aiosqlite 0.22.1 重現：不下 `BEGIN` 時漏掉；顯式 `BEGIN` 後在佇列中看到並找到。

| 參與者 | 交易 | 交易內做什麼 | 不做什麼 |
| --- | --- | --- | --- |
| 搜尋一頁 | 一個讀交易，結束時 rollback | 游標綁定核對（`_read_version` 的 Conversation 版本、狀態列的前沿與 epoch）、U、`sender` 解析、全部候選來源（FTS、佇列、前沿以下）、原文核驗、距離計數與邊界取位、上下文、被回覆原文 | 不寫入；不等待模型、網路、檔案或其他任務；正規化與證據組計算是純 CPU，受同一工作量約束 |
| 插件與 Agent 續頁 | 每頁各自一個讀交易 | 同上 | 頁與頁之間不持有交易或快照 |
| 寫入 `chat_events` 的既有交易 | 不變 | 觸發器多寫佇列列或刪除索引列 | — |
| 索引器 | 讀交易＋交易外正規化＋短寫交易 | 寫交易只做以事件存在為條件的 `INSERT OR REPLACE`（主鍵查詢）與按 seq 刪佇列 | 寫交易中不讀原文、不正規化 |
| 回填 | 讀交易＋短寫交易 | 寫交易只做前沿比對更新與入隊 | 寫交易中不掃描歷史 |
| 損壞重建 | 一個短寫交易 | `delete-all`、重設前沿、epoch＋1 | 持鎖時間待 X04 |
| 遷移 | `env.py` 的單一 `BEGIN IMMEDIATE` | DDL、觸發器、狀態列初始化（主鍵 `MAX(id)`） | 不掃描歷史 |

讀交易開著時，WAL 不能把它之後的頁檢查點回主檔，WAL 檔會暫時變大；讀交易的長度由每頁的計價上界（§6.7）約束，插件續頁也是一頁一個交易，因此不會長時間持有。

### 10.2 指標與預算對齊

**預算對齊**：比較不同方案時，把各方案的回傳結果按排名展平為事件序列，截斷到相同的**消息數**（10、30）或相同的**字元預算**（1,500、4,000 個 `content` 字元）後再計算指標。不比較「片段數相同但大小不同」的輸出。

| 層面 | 指標 |
| --- | --- |
| 完整證據 | **完整必要證據取得率**：截斷後包含某一完整必要證據集合的有答案查詢比例（主指標） |
| 部分證據 | 必要證據的事件級召回率；只取得部分必要證據的查詢比例（單列，不計入主指標） |
| 誤合併 | 回傳證據組中屬於「錯誤聯合」的比例 |
| 排名 | 以「含完整必要證據」為相關判定的 MRR 與 nDCG@5；只含部分證據的不算相關 |
| 上下文 | 必要上下文覆蓋率；重複率（應為 0）；平均回傳事件數 |
| 歸屬 | `terms_by_sender` 與 `role` 的正確率 |
| 無答案 | 無答案查詢得到 `exhausted` 且無證據組的比例；有答案查詢誤得空結果的比例 |

**驗收門檻的訂法**：本任務不預先編造提升數字。P0 量得基線後，於 §12 寫下各階段門檻，原則為：① C-INV 漏召回為 0（正確性）；② 重複率為 0；③ 歸屬正確率 100%；④ 字面類的完整必要證據取得率不低於基線；⑤ p95 延遲與 `incomplete` 比例在合成庫上有書面門檻。
