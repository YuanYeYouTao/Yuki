## 1. 目标与依据

目标是减少从真实消息进入到首条实际发送的可避免工作：删除重复读取、历史恢复、转换及跨会话无关等待，缩短现有临界区。**本次重点是删掉前台工作；新增并行与 Code Mode 编排评估另开 issue，不作为本任务的实施依赖。** 保留同一 Conversation 普通聊天前台 Main 的现有顺序。既有 Work、SELF、插件、SDK 与子 Agent 沿原执行所有权、scope/child lease、来源及回执合同运行，本轮不扩大其并发，也不将它们一概加到新的全局互斥里。

遵守[开发约束](development-contract.md)、[主 Agent](main-agent-runtime.md)、[语义参与](semantic-participation.md)、[会话 Compact](conversation-compact.md)、[Tool Kernel](tool-kernel.md)、[执行过程](execution-trace.md)及[平台适配](platform-adapters.md)。禁止防御性编程优先：能删重复工作就删除，不为优化添加新调度器、后台队列、outbox、TTL、经验阈值、权限缓存或任务完成门槛。

人物资料认 Person，公共上下文认 Conversation，平台收发认 Binding/Presence，已经发生的事情认原事件与回执。原生提及沿 0135 的原句位置、目标及当时名称快照读取；不能为并行另查当前昵称或改写冻结原文。不同人物、入口、平台不因优化合并上下文。

## 2. 并发会不会让会话分叉

### 2.1 必须分清的三种“一致”

1. **账本统一**：真实消息与确认发送最终属于同一 Conversation 的一份事件历史，不复制聊天档案。
2. **本次请求看到的上下文**：一次模型调用持有派发时确定的输入。HTTP 已经发出后，后来的事件与回复不会自动出现在这次请求里。
3. **模型私有执行轨迹**：工具调用、call ID、结果、签名、opaque continuation、任务检查点属于原执行。公共历史统一不意味着这些材料可以混到另一个执行中。

多个模型同时思考，即使共享一份账本，也不保证看到相同的最新材料，更不保证知道对方正在生成什么。

### 2.2 一个具体例子

共同历史为 H，先后收到 A“周五开会”和 B“改成周六”。若同时派发两个 Main，可能发生：

```text
执行一：H + A ──生成──> “好，周五见。”
执行二：H + B ──生成──> “好，改成周六。”

最终账本仍能保存 H、A、B 及两条实际回复。
执行一已经生成的答案不会因为后来的统一入账自动重想。
```

即使两个请求都看到了 H+A+B，也不知道对方尚未发出的答案；两个独立调用的不同执行身份也不会被原回执自动当成同一次发送。只在出口排队发送，解决的是气泡交错，不解决同时思考时的相互不可见。

这叫**同一会话的模型视图与执行尾部发生分歧**，未必建立永久数据库分支，但已经足以造成重复回答、沿用过时决定或工具动作冲突。已经发出的消息或执行的外部操作，不能靠回滚上下文撤销；所以不能在现有结构中直接解除前台 Main 顺序，再指望出口或 CAS 补救。这是可能的后果，不是“任何并发必然造成不可恢复损坏”。

### 2.3 本任务采用的并发范围

| 范围 | 上下文及顺序 | 本轮决策 |
| --- | --- | --- |
| 不同 Conversation 同时运行 | 各自沿自己的公共历史与执行来源；本来就允许并行，仍共享实际 DB writer 和 Provider 容量 | 保留，删除与另一会话无关的全局串行准备 |
| 同一轮内部的独立只读准备 | 输入及真实依赖确定后，分别读必要资料，按原顺序汇合为一个 Main 请求 | 新增并行移至独立 issue，本次先删重复工作 |
| 同 Conversation 多个普通聊天前台 Main 同时生成 | 可能使用不同尾部，互相看不见尚未完成的回复与工具结果 | 本轮不启用，保留现有前台 Main 顺序 |
| 同一模型响应中的工具并行 | 读取与修改、发送的真实效果次序不同 | 保留现有 `parallel_safe` 与效果屏障，不扩大修改或发送并行 |
| 同 Conversation 的新消息进入正在运行的 Main | 在下一合法请求边界沿原输入接纳，已发出的请求保持原件 | 保留 steer 与排队唯一接纳，不将消息同时做补充和新回复 |

原有有序 Main 不承诺每条后来消息都立即被前一请求看到：能够接入当前激活的输入在下一合法边界接入，其他输入沿原调度处理。不能为“上下文最新”反复取消已付模型、重买请求或重放效果。

### 2.4 当前代码中各机制的职责

- [`ConcurrencyManager.conversation`](../../src/yuki/services/concurrency.py) 是按 Conversation key 的互斥；[`ChatService.respond`](../../src/yuki/services/chat.py) 在普通聊天前台 Main 周期持有它。本任务保留，不声称所有入口都取得这一把锁。
- [`ConversationTurnCoordinator.hold`](../../src/yuki/services/turn_coordinator.py) 是占用登记，**不是另一把整轮互斥锁**；避免阶段间隙被当成空闲。其 version、取消与效果开始保护各有原职责，不能因名称像锁就删除。
- 根 Work 激活沿 [`work_activation.py`](../../src/yuki/runtime/work_activation.py) 的原 scope lease；子 Agent 沿原 child 执行所有权。`generate_origin_turn` 等低层方法依赖调用者，插件 Main 取得 Work lease 也有配置/原 Work 条件；不能只看到 `hold` 就宣称该入口完整互斥。实施时核实际调用边界，当前源码核查不冒充所有入口的并发运行验收。
- 公共 projection 的 generation、来源、隐私、epoch/revision 与原头 CAS 保证候选不会覆盖已改变的公共视图。**CAS 不会合并两个已生成答案，也不能替代 Main 顺序。**
- [`MainAgentTurnService`](../../src/yuki/services/main_agent_turns.py) 只将获准 canonical 事件冻结为共同历史；原工具与私有续跑尾部沿原执行保留。compact/reset 不修改已经付费的请求。

### 2.5 缓存与统一上下文的关系

H+A 与 H+B 可能仍复用共同 H 的上游缓存，但 A/B 之后的尾部不同。共同前缀命中不证明两个执行互相看见了最新回复；模型结果一致也不独立证明缓存命中。

本任务沿用固定 system、当前部署冻结的工具声明、公共历史原件和动态资料位置。等价输入的稳定前缀、媒体次序、原生协议与私有配对应保持；准备路径调整不制造按完成顺序重排的请求。真实新输入、合法 compact 或来源改变导致的必要差异单列，不要求所有真实不同请求字节相同。

### 2.6 Memoh、pi、Codex 的实际并发边界

2026-10-18补充只读调查：Memoh本地 `7e40b52ec46d076c17d93e578f5fc18f88742f97`、pi本地 `3daa20280f6a7c7cbe0935680c9a38fdc3863005`；Codex本机安装未附源码，先核官方文档，再以官方开源 `8c076942cb70fba8e5c4732c23f1faabc4aed484` 独立研究检出核对实际实现。详见[并发实现对照研究](Yuki-多Agent并发实现对照研究-2026-10-18.md)。没有为研究调用模型或启动真实平台实例。

| 实现 | 同一会话/主实例 | 它的其他并发与分支 |
| --- | --- | --- |
| Memoh | 一个内部session只允许一个活动主run；`Manager.Admit`忙时返回`ErrSessionBusy`，PostgreSQL部分唯一索引覆盖accepted/running/waiting_decision/finishing | 不同session、独立子Agent可以并行；一个响应的多个批准工具也可并行。普通新消息不自动fork；显式fork才创建新session/thread |
| pi | 同一Agent实例已有`activeRun`时，`prompt/continue`拒绝重入；新输入用steer/followUp，原主循环按边界接入 | coding-agent 默认直调工具，Code Mode 激活后有 `on/only` 声明模式；脚本内部 `Promise.all` 可并行调用工具。core 原生批次另有 parallel/sequential 策略，两者不是同一派发层。示例子Agent有独立进程/上下文 |
| Codex上述开源CLI/App Server | 普通turn/start优先转steer，活动Regular存在时追加pending input并返回原turn ID，无活动turn才新建；显式Queue沿idle条件启动 | 工具按parallel声明与共享/独占门执行，结果有序归并；子Agent/fork有独立thread，父链接收结果，不共享全部最新私有尾部 |
| Diana对照 | 本次源码默认允许同群3路、私聊2路生成，发送批次再串行 | 这是该产品的具体选择，不能从“其他Agent也有并发”推导Yuki应照搬 |

Memoh证据：[单run接纳](https://github.com/felinics/Memoh/blob/7e40b52ec46d076c17d93e578f5fc18f88742f97/internal/agent/runtime/session/admit.go#L173-L190)、[部分唯一索引](https://github.com/felinics/Memoh/blob/7e40b52ec46d076c17d93e578f5fc18f88742f97/db/postgres/migrations/0001_init.up.sql#L2239-L2243)、[子Agent与显式fork](https://github.com/felinics/Memoh/blob/7e40b52ec46d076c17d93e578f5fc18f88742f97/internal/agent/tool/subagent.go)。入站worker数不代表同session主模型数；忙时重试/队列策略因入口而异，本任务不复制其等待时长、队列帽或持久接纳设计。

pi证据：[同Agent重入检查](https://github.com/earendil-works/pi/blob/3daa20280f6a7c7cbe0935680c9a38fdc3863005/packages/agent/src/agent.ts#L370-L387)、[Code Mode 的启用与 on/only](https://github.com/earendil-works/pi/blob/3daa20280f6a7c7cbe0935680c9a38fdc3863005/packages/coding-agent/docs/settings.md#L42-L60)、[实际请求工具与脚本并行测试源码](https://github.com/earendil-works/pi/blob/3daa20280f6a7c7cbe0935680c9a38fdc3863005/packages/coding-agent/test/suite/agent-session-codemode.test.ts#L141-L245)。该版本不支持“所有配置无条件强制 Code Mode”的结论；本次没有读取用户个人 pi 设置，不推断具体实例的模式。主循环保证针对单 Agent/session runtime，不能外推两个独立实例共享 session ID 也自动互斥。本 checkout 没有 mom 产品源码，不对其历史行为作结论。

Yuki 也已经有程序内并行：默认 direct 的工具批次可并行读取；可选 Code Mode 使用 Monty Python 的 `asyncio.gather`，Host 仍按 `parallel_safe` 与发送、写入、控制屏障执行。Code Mode 的调用语法和同会话开几个 Main 是两个维度；脚本内并行不创建第二份主会话。默认 direct、可选 Code 镜像和固定清单以现行[Tool Kernel](tool-kernel.md)为准。已关闭的 [#256](https://github.com/YuanYeYouTao/Yuki/issues/256) 讨论过持续任务的默认编排指引，本次不将现有能力重新列为待建设项。

Codex证据：[App Server的steer与fork](https://learn.chatgpt.com/docs/app-server)、[子Agent线程](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Queue与Steer说明](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)，以及[开源start_or_steer分支](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/session/turn_input.rs#L374)。此前仅靠公开文档未确定的普通turn/start并发行为，已由该提交源码及现有测试补证；仍不将它外推为用户当前桌面全部内部实现或所有特殊任务的保证。

由此采用的边界是：**单个前台聊天主循环有序运行，同时允许其他会话、独立子任务和必要读取各按原合同工作。** 子Agent的独立上下文是显式分工，结果沿原通道回给父执行；不是把多个私有轨迹拼成一份主会话。独立上下文也不自动提供独立文件系统或外部账号，效果顺序仍须沿本项目原合同处理。

单逻辑owner也不证明远端取消已确认：Memoh的steer与Codex可选采样抢占允许原链继续，但旧请求可能仍在远端收拢。它们不修改已发payload，也不独立证明无重复计费。本任务不采用主动取消后重购请求来提速，不以其他项目支持并发为由扩大Yuki的效果工具并行。

## 3. 已知证据及归因限制

用户确认 Diana 与 Yuki 使用的模型、接口不同。以下仅作定位，不能据此推算程序或语言的提速倍数。

| 记录 | 样本与中位数 | 边界 |
| --- | --- | --- |
| Diana 10-18 本地完整 Runtime 回放，deepseek-flash Responses | 主回复首步 HTTP 21 次，1475ms；输入 token 中位数21643 | 本地 OneBot 模拟平台，真实模型；不是生产入站到首条可见回复 |
| 同一 Diana 回放的发送审核 | 21 次，2779ms | 普通最终回复额外调用，不能遗漏后将主模型首步当整体耗时 |
| Yuki PR #471 后、#472 前自然样本 | 模型传输32次，4702ms；上下文装配7次，48ms；整个 chat preparation 7次，547ms | 传输与 Diana 首步 HTTP 的统计边界也不完全相同 |
| 同一 Yuki 样本 | 参与绑定5次，1264ms；接纳反馈7次，248ms | 单独统计，不包含在48ms装配内；绑定总值尚不能拆出锁、DB、序列化和 event loop 调度 |
| 同一 Yuki 样本 | processing 到首个确认投递6轮，7117ms | 起点是处理阶段，不是完整平台入站时间；组件中位数不能相加或相减代替此值 |

Yuki 的旧线上采样方法、来源与局限另见[诊断任务书](Yuki-诊断删减与SQLite写竞争优化任务书-2026-10-18.md#1-线上事实与归因边界)及[上下文实施记录](../operations/context-pipeline-implementation-20261018.md)。Diana 原始回放与本轮离线分析是本地研究材料，不将私有数据库、报文或凭据提交仓库。实施前须重新取得当前版本的基线；健康检查不能替代延迟验收。

源码已确认：

- Diana 的普通 QQ 最终回复等待完整生成与发送审核，流式 HTTP 不自动逐字投递；`say` 可中途先发。默认同群3路生成、私聊2路，最终回复批次仍串行。这些是可配置默认值，不代表用户比较时的实际配置。
- Diana 在已决定处理的当前轮中并行读取若干独立资料层；这与入站时投机预装配不同。它也有入队、存储与后台工作，不能概括成全内存、无持久化。
- Yuki 首个 `send_message` 沿原 Social 出口实际发送，不等后续 Main 回合才发送；普通纯文本路径没有固定 Manager 网络等待。后续 Main 续接仍可能存在。
- Yuki 明确 @ 不等待普通语义接话去抖或 JEV 评分，但仍同步等待参与绑定。

## 4. 当前缺口与已完成部分

### 4.1 本轮需要处理的路径

1. [`processor.py`](../../src/yuki/services/processor.py) 的显式输入仍先调用 `binding_for_event`。[`participation_ordinary.py`](../../src/yuki/services/participation_ordinary.py) 的 `event_scope` 先读事件与场景、配置、session，再同步近窗 Social 效果、hydrate 最近历史与原接纳、核边界及来源。绑定不是一次简单查询。
2. 上述绑定与部分反馈、自报共用服务 `_lock`；另有 `_session_lock`、`_save_lock` 及共享 snapshot store。Controller owner 已是 `(conversation_id, generation)`，但不能只将一把锁换成群锁就宣称互不影响。
3. [`main_agent_backend.py`](../../src/yuki/services/main_agent_backend.py) 的合法 `<yuki-state>` 自报在 tools 前同步应用。当前普通自报再次进入完整 `event_scope`，然后保存快照；没有自报时该路径立即返回，不能算每轮固定成本。
4. 附件等输入准备只检查尚存的重复读取与转换；新增并行调度、程序编排与吞吐评估移至独立 issue。
5. Social 仍保有 reader 准备、writer 事实复核与真实 dispatch claim；可继续查重复查询，不能将不同阶段的责任一并当成冗余。

### 4.2 不重复施工

- PR #471 已完成增量历史/投影块、同次 compose/容量/编码复用、Guard 内局部证明复用、明确发送路由免成员预检、sequence 批量重建、同入站媒体原件共享等。
- `on_ordinary_admitted` 已改为 `current_sources` 加驻留 Controller 局部应用；冷缺失才恢复。**不能再把热路反馈“第二次整页 hydrate”当成现存缺陷。** 其必要快照保存仍在前台。
- PR #472 已删除重复诊断视图、哈希与来源 reader、旧统计链，并收敛部分业务 writer。这里不恢复旧诊断来测本轮，也不将仍然存在的真实业务回执当旧诊断删除。
- tick 中 hydrate 前、后的效果同步已有不同锚定职责，后次使用 `apply_committed=False` 且已复用 rows；不得只看调用次数删第二次。
- 本轮不重写 ContextAssembler，不新增早到消息预装配，不改变参与去抖、JEV调用频率、Provider路由、历史容量或compact触发值。

## 5. 执行任务

### L01：按真实边界建立当前版本基线

复用现有阶段计时、SQL统计、模型用量与发送回执，补足实际缺少的局部计时；仅保必要聚合和有界研究样本，不恢复整份重复报文诊断，不新增每条持久化观测链。

区分平台入站/内部入账、处理开始、参与锁等待、只读准备、Controller应用、快照编码/保存、Main会话等待、实际模型请求发出/返回、首个真实平台ACK、原效果结算、整轮结束。重放旧回执不是一次新平台ACK；无发送、部分发送、未知ACK与明确失败分别记录。

普通纯文本、明确@、隐式续聊、当前轮steer、已有Work输入、带自报、带附件，以及冷/热Controller分别统计；跨会话负载与同会话忙时单列。报告样本量、输入/输出规模、真实缓存字段覆盖及运行版本。不从不同样本的中位数相减算净收益。

### L02：删减绑定准备中的重复读取与恢复

按原输入准备 owner 组织一次真实准备，复用该阶段已经取得的原事件、Conversation/Space/Presence、配置及来源事实，合并可以批读的依赖。不要在同一激活里依次重新查回自己刚准备的整份材料，也不新建平行的通用上下文DTO或权限状态缓存。

驻留 Controller 优先沿原 committed event、admission、真实效果的增量更新处理；仅新增事实、真实失效依赖和控制器实际需要重新评估的范围进入热路。以扫描行数、字节、SQL往返及同步应用量验证，不将“改成一次SQL”写成O(1)。冷恢复、真实来源变更、账号/人物合并、代次变化保留原恢复事实；不能仅凭最大event ID、行数或时间戳证明旧来源未修改。

显式@的确定性接纳不等待JEV，也不为省时间丢掉原单元/input/自报/效果关联。真正的用户意图与身份来源复核保留在原接纳边界；不将整段binding直接删掉后用空绑定兜底。

### L03：普通自报复用轻路，保留即时quiet与真实恢复

参照当前 `on_ordinary_admitted` 的局部应用范式：按原admission/事件取得原来源，驻留owner直接准备并应用 `SelfReport`；冷缺失才走必要恢复。删除正常热路中与本份自报无关的整页hydrate、近窗回执再同步及配置重读。

必须保留原activation、请求sequence、response ID、source次序、人物及unit basis。合法quiet在 `observe_response` 返回前影响同一Controller，并按既有接口登记所需观察；后来的新输入应读到已接受的quiet。engage意愿继续进入JEV，语义纠偏仍能收起快路；join/stay、实际发送和迟到旧自报不盖过较新quiet或语义否定。同一Main已选择的合法补充不被后来quiet追溯否决，也不中断其原效果。

**本轮不要求将快照保存改成后台任务。** 当前普通admission不是Main journal，不能自行恢复尚未保存的hint；quiet及observer queue的重启恢复仍依赖原snapshot。先保留必要 `_save`，优化其前重复工作和无关等待。解析与不可变资料可在合适的锁外准备，不能对活Controller跨线程编码或在await期间缓存最终授权。

若后续发现现有轮次收尾足以承接保存，也必须核实发送失败、无发送、NO_REPLY、取消、退出和快照前崩溃的原恢复来源；不新建队列/outbox来兑现异步化。没有这样的现有事实承载点，就保持必要保存，不用丢反馈制造快速度。

### L04：缩短参与模块现有临界区

一起检查 `_lock`、`_session_lock`、`_save_lock`、tick、观测回调、pin、session装载/退休、关闭及store revision。删除锁内重复工作，把不访问共享可变状态的准备移出无关的全局临界区；真正的共享状态仍沿原owner保留短应用边界。无需为此新增 fan-out、新队列、锁分片或第二个调度器；若收益必须依赖新的并行方案，将该部分交给独立 issue。

目标是群A的长准备不阻塞群B开始自己的必要准备，同时同一Controller的输入、自报、语义观察和效果保持原次序。不能并发读改同一个活Controller，不能冷启动造出两个同scope Controller，也不能让旧save结果覆盖新的revision。

共享store的真实单连接/写事务约束与SQLite writer仍须按事实处理，不以同时发起多个save宣称消除串行。编码、准备与写事务分别计量；取消时保留原已提交revision的确认和资源收拢，不重发未知提交。

### L05：已拆出——当前轮只读准备并行

### L06：收敛Social剩余重复准备

核对 [`social/repository.py`](../../src/yuki/social/repository.py)、[`social/service.py`](../../src/yuki/social/service.py) 中reader准备、writer复核、claim及结算的实际依赖；复用原route、payload、逻辑发送键及回执，删除同阶段的重复读取与转换。

原call/payload、当前目标与Person/SELF/插件授权、Presence/Binding、租约/fence和唯一dispatch claim保留。模型输出、平台ACK、账本/回执结算是不同边界；不提前报成功，不在writer中等待平台，不跳过原回执来提速。

保持统一Social出口、首条不加人为分段等待、后续原分条节奏与顺序；不将发送改为无owner后台任务，也不以模糊匹配合并不同调用的相似正文。

### L07：仅删减附件准备中的重复工作

ASR等付费或外部调用单独处理原派发与结果恢复，不标为可任意重试的纯读取。逐项保留取消、部分失败与致命失败的语义，收拢转码线程和所属任务；不能因另一项目失败重买已完成ASR。纯文本轮次不因此创建额外工作或等待。

### L08：同步合同、定向验证与交付记录

实现时同步修改主Agent/参与/平台与执行过程的真正受影响说明，删除冻结旧重复路径的测试和陈旧表述，保留真实行为断言。先核当前main与本任务书差异，不能按历史行号强改。

## 7. 施工顺序与收益判定

1. L01先取得当前基线并核main差异，确认频繁路径与真实锁owner。
2. L02、L03先删热路重复准备；必要时重构原输入准备职责，不另建缓存或协调链。
3. L04结合已缩短路径处理现有临界区，确认不再让无关准备长期占锁；L05已拆出，不阻塞本任务。
4. L06、L07分别验证Social与媒体剩余重复工作；无实际重复的候选直接删除，不为勾选任务硬改。
5. L08同步消费者并做受影响定向验证；通过后仅因新改动、失败或未决问题扩大测试，不重复无关全量检查。

按同来源的等价样本对照处理行/字节、SQL与独立写事务、CPU、锁/连接等待和各真实边界。模型网络、平台网络、读连接竞争与持久writer成本分别报告；不降低上下文、隐藏来源、删回执或多买模型来制造改善。

不承诺固定倍数、固定毫秒或缓存百分比；验证的是实际重复工作减少、可控无关阻塞被解除、原业务结果与缓存合同保持。两个不同模型/接口的样本仍不得当成优化前后A/B。

## 8. 明确不采用与后续议题

本轮不采用同Conversation多个普通聊天前台Main生成、不解除其会话锁、不扩大效果工具并行、不复制聊天档案、不将私有tail合并成公共上下文，也不将普通聊天强制升级为Work。既有Work/SELF/插件/SDK/子Agent保持各自原执行合同；没有核实原入口就不宣称它们全被同一把锁保护。

不照搬Diana的并发数量、渐进工具加载、历史硬上限、额外发送审核、无去抖参与策略或开场白次数/字数帽。不调整用户当前模型、Provider、compact触发或发送节奏；保留当前固定工具与严格缓存合同。

不做入站投机预装配、后台预热、消息到达即装整轮请求，也不新增提示词或“必须全部状态处理成功才能回复”的门槛。**优化方向是减少真实前台工作，不是换一组限制。**

独立 issue 研究现有 direct/Code Mode 编排、工具及当前轮资料/附件并行的实际收益、依赖、取消与回执；不预设改默认模式或必须新增机制。它也不包含同 Conversation 多 Main。若以后另行研究多 Main，须先明确它们看见的共同输入、未发送答案、工具副作用、steer去重、compact发布、预算与恢复身份如何统一；当前projection CAS、出口批次锁和原回执不独立提供这些语义。
