# Yuki Work 收尾截断删除任务书

日期：2026-10-15（Asia/Taipei）。源码基线：`origin/main`，`0aea047d42a9650fcc64c690bd8fae8014b73dc8`。

**状态：D01–D13 已实施，本地验证及真实 VM 复审已收口，接着交付 PR、CI、合并与 Bot-only 上线。** 实现、验证、提交、PR、合并和上线分别记录；第 2 节的基线核查保留当时事实，修复证据记在第 8 节。

## 1. 目标与删除范围

删除把 Work 结束提案扩大成整批工具禁用、脚本强制停止的规则。正常完成、等待和请求补充信息只提交生命周期决定，不抢先截断同一份模型响应或同一个 Code Mode 程序中仍获准的工作。原批次、程序和实际回执收拢后，再由现有 writer 结算。

最高约束见 [AGENTS.md](../../AGENTS.md)、[开发合同](development-contract.md)、[主 Agent](main-agent-runtime.md)、[Tool Kernel](tool-kernel.md)和[持久工作者](persistent-subagents.md)。先删除多余判断及其消费者，不加消息特例、允许名单、收尾协调器、补发队列或额外完成检查。

这次删除不扩大授权。真正的取消、撤权、来源失效、隐私删除、租约失效和真实预算拒绝，仍按原领域事实停止旧来源的新效果。正常完成时收拢真正活动的所属执行、保留暂停子任务和实际回执，属于现有有效职责。

保持共同 Main、固定工具合同、统一效果执行与结算出口。不为 Gemini 单独修补，不把执行时序问题归结为 QQ 长消息，不依靠模型必须把 `complete` 写在最后才能工作。

### 2.2 隔离复现与覆盖范围

## 3. 已确认的多余截断

### F01 同批所有工具被结束标记拒绝

位置：[AgentRunner](../../src/qq_ai_bot/services/agent_runner.py) 的 `_execute_tool_batch_impl`，基线 762–784 行。

混合批次只要发现 `control.ending` 或 `handoff_work_id`，就把所有剩余调用统一配成 `work_control_closed`，不检查这些调用自己的来源和授权。只读查询、文件发布、记忆写入、终端清理和子任务通信都受影响。

`complete`、`wait`、`need_input` 都会设置 `ending`。所以这不是“完成后不能开启新任务”，而是尚未收拢的原响应被提前截断。把停止命令放在 `complete` 后面时，停止命令也无法执行，writer 还可能继续等待那个未停止的所属进程。

**删除方向：** 删除根据生命周期提案或交接标记批量拒绝原响应尾部的判断。维持 Provider 原调用顺序和原执行身份，逐项复用已有执行处授权、预算、效果意图与回执；不把所有控制调用重排到最后，也不给 `send_message` 单独放行。

### F02 Code Mode 把控制回执变成整段程序停止

位置：[CodeModeDriver](../../src/qq_ai_bot/codemode/driver.py) 的 `_dispatch_control`、`_terminal_control` 和 `_drive`，基线 704–754、799–806、373–412 行。

`ending` 或交接字段变化，以及命中 `TERMINAL_CONTROL_ACTIONS`，都会制造 `code_stop` 并抛出 `_Stop(host_control)`。Host 随后退出 VM；控制调用之后的计算、工具、输出、返回值和脚本内清理语句都不能继续。

`_terminal_control` 仅按 `task_control.action` 和 `ok` 判断，不核对结束的是哪个 Work。仅取消派生子目标就停止当前程序，已经实际复现。`fail`、`resume` 等操作其他目标的等价路径要在实施中逐项回归。

**删除方向：** 删除按控制动作名称推断当前程序必须停止的集合、辅助判断和普通控制 `code_stop` 生成链。控制回执沿原接口返回给程序。是否还有执行权由真实来源、原目标和实际撤权决定，不能用目标状态变化冒充当前脚本失去授权。

真实撤权和资源拒绝仍走原执行核验；脚本 `try/except` 不能重新授予失效授权。不新增一套“安全收尾工具名单”或新的剩余步骤额度。

### F03 恢复链重新应用旧停止决定

位置：[CodeModeDriver](../../src/qq_ai_bot/codemode/driver.py) 的 `_resume`、`_load_children`，基线 350–368、1108 行；[TurnExecution](../../src/qq_ai_bot/services/turn_execution.py) 的激活恢复与 `finish_tool_turn`，基线 317–320、1480–1511 行。

恢复会读取已保存的 `code_stop`，或者再次按旧控制动作判断停止。只改首次执行不能删除整条限制。普通结束与等待的提案还会让激活在配对后立即退出；它不应成为“原批次或程序尚未完成也可以结束”的依据。

**删除方向：** 同步核对首次执行、未配对响应恢复、程序断点恢复、配对保存和结算。原批次及程序收拢后，合法结束仍可停止本次激活，不为“让模型确认一遍”购买额外请求。

保留历史回执原件。已经终态的旧 Work、已结算且标记未执行的旧调用、已关闭且已配对的旧程序，不因新规则自动复活、补发或重跑。未配对的合法原调用按原执行键查回执和恢复，不能借升级重置预算或换一份身份。

### F04 文档和测试固化了错误行为

现行 [Tool Kernel](tool-kernel.md) 第 137 行规定“生命周期控制接纳结束后停止后续新业务调用”；`work_control_tools()` 的描述要求“接受结束后本次执行立即收尾”。旧日期任务书中的 D04 也曾把停止尾部作为验收成功。

终审还确认 [Code 固定工具合同](../../src/qq_ai_bot/codemode/contract.py) 的 `EXECUTE_CODE_TOOL.description` 明说“task_control 结束/等待”会由宿主停止脚本，原 D06 没有列到这个实际提示词入口。[主 Agent 合同](main-agent-runtime.md) 第 394 行也仍要求结束后的业务调用未执行。只改 Runner 或一处文档，模型仍会收到旧规则。

`test_direct_send_then_complete_pairs_later_calls_without_executing_them` 和 `test_terminal_control_stops_remaining_code` 等用例，明确断言结束后的工具不执行。这些测试通过证明基线行为可复现，不能证明它符合这次确认的目标。

**删除方向：** 更新现行合同、工具描述和相应测试，去掉提前截断的规定。旧日期报告保留其原基线和原验收事实，并明确指向本次纠正；不能把历史“通过”继续当作现行设计理由。

连同 `CODE_MODE_POLICY`、Code API 投影、`STOP_HOST_CONTROL` 的真实消费者和子任务工具的等待说明一起核对；固定声明在部署内保持稳定。真实 VM API 变化按原版本合同处理，旧快照若不兼容就如实保留原回执与恢复限制，不能强载、重建一份已付程序或暗改旧请求。

### F05 同一截断也作用于子任务自己的执行与嵌套工作

位置：[SubagentExecution](../../src/qq_ai_bot/services/subagent_execution.py) 的 `run`，基线 349–389 行；[子任务工具](../../src/qq_ai_bot/runtime/subagent_tools.py) 的 `execute_subagent`，基线 91–109 行。

工作者调用共同 `AgentRunner`，使用自己的 Work、lease、原来源和固定工具。因此 F01–F03 会在每层工作者内再次发生，不限于父任务向子任务调用工具。子任务先完成再汇报，会丢掉显式父通信或外部交付；先向父提问也会设置 `ending=waiting_user`，进而截断它自己的保存、计算或孙任务派发。

工作者的 `finish` 回调在激活结算后保存结果并通知父输入日志，它不经过这一段模型工具尾部。所以“显式父通信没执行”和“完成结果没有保存”必须分别报告；前者已复现，后者在本轮用例中没有发生。内部完成结果仍不能证明子任务已经实际发文件或回复 QQ。

**删除方向：** 共同执行器的修改同时覆盖父、子和孙任务，沿各自原 lease 和调用键执行。不能为工作者另建工具循环、另设结束规则，也不能让父完成变成取消所有后代。D01–D04 的实施与验证必须包括真实 worker 身份的调用。

### F06 子任务真实提问被归为辅助通知，父子可能互相等待

位置：[WorkRepository](../../src/qq_ai_bot/runtime/work_repository.py) 的 `_business_input_clause`，基线 563–575 行；[SubagentRepository](../../src/qq_ai_bot/runtime/subagent_repository.py) 的 `message` 和 `finish`，基线 421–481、617–626 行；[等待扫描](../../src/qq_ai_bot/runtime/work_wait.py) 的 `_observe_due`。

现有判断只把 `payload.child_id == inputs.work_id` 的子任务输入当作业务输入。子任务向父提问时，`child_id` 是子节点，输入 owner 却是父节点，真实 `subagent_question` 因此被排除。它不能撤下尚未结算的结束提案，也不能使父任务的 writer 保留真实新问题。

`message` 仅在父任务为 `waiting_external` 且没有 active wait 时入队。父任务已经登记等待该子任务完成时，真实问题不会唤醒父任务；等待扫描又不把子任务 `waiting_user` 当作已完成，于是父等子完成、子等父回答。现有问题和通知都保留在 SQLite，但没有进入正常消费链。

**删除方向：** 删除把实际子任务提问一概排除在父业务输入之外、又用旧 active wait 挡住真实提问继续入口的判断。沿现有持久输入、原父 Work 和原 writer 接续问题，按原等待 ID 处理被真实新输入替代的等待与结束提案，不重做原执行。

仅区分已授权生产者给出的真实提问与普通进度、完成通知；不按正文关键词或模型猜测分类。普通子结果和辅助通知仍不强迫父任务复活，也不要求所有子任务先成功才能完成。不强制填写 reason、完整问句或额外汇报，既有可选字段继续可选。

### F07 向终态父任务提问仍无条件暂停子任务

位置：[SubagentRepository](../../src/qq_ai_bot/runtime/subagent_repository.py) 的 `message`，基线 409–481 行；[子任务工具](../../src/qq_ai_bot/runtime/subagent_tools.py) 的 `execute_subagent`，基线 91–109 行。

子任务向已 completed 的父任务提交问题会写入输入日志并返回成功，但不会把该父任务重新入队。`execute_subagent` 仍无条件声明 `waiting_parent=true`、设置子任务等待。完成父节点的原调度不消费这条问题，子任务因此停在等待一个没有正常消费路径的回答。

**删除方向：** 删除“只要 ask 就已接纳父等待”的无条件暂停。复用原父目标、持久输入和通信回执的真实可接续事实，问题保存与等待接纳分别如实处理。父无法接续时，不能声称已经有人会消费；子任务应获得实际结果并保留现有继续、查询或显式交付入口。

旧 completed 父任务不自动复活，不复制替代父 Agent，不建立转发协调器或补偿通知队列。普通完成回传仍保存原子结果与父输入，其不自动启动父模型属于真实终态语义，不是需要删除的保护。

### F08 管理原子任务又要求接纳一个新 Work

位置：[子任务工具](../../src/qq_ai_bot/runtime/subagent_tools.py) 的 `execute_subagent`，基线 62–82 行；对照 [Work 查询](../../src/qq_ai_bot/runtime/work_queries.py) 的 `get(local=True)` 和 [Work 控制](../../src/qq_ai_bot/runtime/work_control.py) 的指定目标管理。

当前前台没有 Work 时，入口只有 `subagent_control.resume(child_id)` 能按原来源解析旧父子关系；`list/status/result/cancel` 和对明确 child_id 的补充消息都会先返回 `accept_work_before_execution`。这发生在用户询问旧后台任务、读回结果或要求停止时，原子任务及真实授权还存在，却要先创建另一个任务才能使用管理入口。

隔离验证中，同一控制器的原来源和 lease 能通过已有 Work 查询读到子节点，`task_control.cancel(work_id)` 也能取消它；父节点始终 completed，前台没有创建新 Work。限制来自子任务工具自身的当前 Work 前提，不是来源失效。

**删除方向：** 删除对已有子任务查询、通信和管理的统一接纳前提，复用现有 Work 来源查询、目标解析与原父子关系。列表只返回该来源实际可管理的子任务；明确目标按原内部 ID 处理。取消、消息和恢复分别复用原入口，不让模型换工具别名才能绕过同一个假门槛。

真实 actor、generation、读写范围、任务树与归档事实继续核验。新的 `subagent_start` 仍须有实际目标与预算 owner；不为查询或停止制造空父任务，不复活旧父，不复制子任务或重置共享预算。正在处理另一个 Work 时操作原有子目标，也须按目标本身的原关系解析，不能拿当前无关 Work 冒充它的父节点。

### F09 单项权限拒绝扩大成整个 Code 程序撤权

位置：[Code 固定合同](../../src/qq_ai_bot/codemode/contract.py) 的 `ADMISSION_CLOSING_ERRORS`；[CodeModeDriver](../../src/qq_ai_bot/codemode/driver.py) 的 `_closing`，基线 773–783 行；[实际后端](../../src/qq_ai_bot/services/main_agent_backend.py) 的 `execute_call`，基线 255、350 行；[能力运行时](../../src/qq_ai_bot/capabilities/runtime.py) 的 `validate_call_result`。

后端可对某个名称返回 `capability_not_allowed`；能力运行时按某个名称的当前可执行集合返回 `capability_no_longer_authorized`。这些回执证明这一项不允许执行，不证明整个原来源、Work 或其他工具已经失效。但两者都在 Code 的全局关闭集合里，任一命中都会抛出不可由程序处理的 `admission_closed`，后续合法查询、计算和独立步骤也被停止。

两种回执均已在真实 Host 中复现；原 Work 未结束、lease 有效，另一个独立读取能用同一 Host 成功。普通参数错误却可以返回程序处理，说明这里额外把单项权限错误提升成了整段停止策略。

**删除方向：** 删除把单项工具拒绝自动扩大成全局关闭的错误码归类和消费链。被拒绝的调用继续如实拒绝，其他原调用仍在各自执行处核验权限；无需增设“失败后可以执行哪些工具”的名单或补偿循环。

真正的来源/lease/generation 失效、原执行被取消、全局关闭与预算耗尽仍沿已有事实停止新效果。真实新业务要求仍在原输入边界交回 Main，不把普通辅助通知升级成撤权，也不为通过用例删除全部授权检查。首次执行与已保存拒绝回执的恢复路径均须同步处理。

## 4. 目标执行语义

| 操作或事实 | 当前批次与程序 | 生命周期结算 |
| --- | --- | --- |
| 当前 Work `complete` | 仍获准的剩余原调用按顺序执行，程序收到控制回执后继续 | 原批次和程序收拢后，按原 writer 提交；真正活动的所属执行仍按原 run 等待 |
| `wait`、`need_input` | 保存真实等待或缺失信息，剩余原调用可发送说明、保存资料、查询或清理 | 原批次和程序收拢后进入实际等待；不强制发送、不额外询问模型 |
| 操作另一个目标的取消、失败或恢复 | 只改变目标的真实状态与授权，当前程序继续使用自己的执行权 | 不把另一个目标的状态解释成当前 Work 已结束 |
| 子任务向尚可接续的父任务提出实际问题 | 问题进入原父输入，子任务自己的原批次仍完整收拢 | 真实问题可接续父等待或未结算结束；不与普通完成通知混同 |
| 子任务向已终态父任务提问 | 保存与消费事实如实返回，不无条件截断子任务 | 不自动复活旧父任务，不把没有消费目标说成已接纳等待 |
| 普通前台查询、取消或补充原有子任务 | 以原内部目标和真实来源执行，无需接纳一个新 Work | 原父终态、子任务身份和累计预算保留；权限不能借给其他来源 |
| 单项工具不被允许，但原执行来源仍有效 | 该项如实拒绝，其余原调用各自核验；程序可处理单项回执 | 不将错误码视为整个 Work 被撤权，也不制造额外结束提案 |
| 接纳独立工作或交接 | 剩余调用保留原 Work、actor 和来源；不得借接收方的身份执行 | 原批次收拢后沿现有交接出口让出，后继任务由自己的 owner 执行 |
| 当前目标被真实取消、撤权或来源失效 | 停止旧来源的新效果，收拢已发生事实与原回执 | 使用原 writer、子树撤权和既有进程对账，不宣称远端已经停止或回滚 |
| 真实预算或 Code 资源限制 | 原限制和原累计计量继续生效 | 按既有分段、等待或失败路径退出，不给收尾另发预算 |

`completed` 仍表示生命周期结束。内部 `result` 是 Agent 的结果描述；执行、发送、文件交付与附言是否发生继续由原 typed outcome、Social 回执和内部事件证明。不要为了纠正一次未发送，恢复产出分类器、强制汇报、所有历史效果成功门槛或自动补发。

已配对不等于模型已观察。原结束决定有效且批次完整时，无需额外模型请求；若真实新输入或原合法恢复仍需继续，沿既有 `work_unobserved_tool_round` 接续必要原回执。固定 system、公共历史、原签名和已付请求不能为此重写。

### 8.1 本轮实施与恢复复审

实现位于独立分支 `codex/work-lifecycle-tail`。Codex 与三个 subagent 分工处理共同执行链、Code 程序、持久子任务和合同/上线准备，由主会话收拢复审。

删除普通结束、等待和交接导致的批次拒绝及 Code 停止；单项权限拒绝交回原程序。直接控制复用原 Invocation 和效果回执，首次 Work 接纳、原控制回执和已付模型计量在同一 writer 提交。首次写入前准备原 Invocation 摘要，事务内只绑定实际生成的 Work ID。

恢复继续同一份已付响应和原调用键：已派发或未知效果读取原回执，明确未派发的原项沿原入口执行。Code 分段时，现有 writer 先保存 queued 段和原接纳决定；程序与同批尾部完成后再落实正常结束、等待或交接。真正当前目标取消或失败继续先撤销新效果。

配对只看当前响应边界，Provider 跨响应复用调用 ID 不会删掉新调用。未收拢响应保存完整原调用和 readonly 复用链接；连续分段保留原媒体回执，图片统一在整批结果之后按原顺序预算和附加。复审发现的这些恢复窗口已纳入 D03/D04/D07，复用原 journal、writer、预算及回执。

现行固定 Main 合同为 19，Code API 为 `yuki.codemode.api.v2`。部署内固定声明保持稳定，旧 API 不兼容的未完成 VM 仍按原快照报告事实；原私有请求、签名、公共 FrozenFragments 和预算保持原所有者。
