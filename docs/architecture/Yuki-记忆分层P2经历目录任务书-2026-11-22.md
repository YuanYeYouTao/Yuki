## 1. 要解决什么，不解决什么

### 1.1 现象【实证】

- 经历（`kind=episode`）只能靠模型主动 `search_memory` 想起；GPT 时期主动查记忆的轮次只有 1.4%（架构书 §1.1）。Yuki 不知道"有哪些事可以想起"。
- 经历没有标题字段（`persistence/models.py:519-525`）。active 经历 1142 条：SELF 944 条，`memory_key` 全是哈希（`memory/self_reflection/service.py:484`）；其余 198 条的 key 是英文短语。架构书 R5 的结论是"没有标题来源，目录不可行"。
- SELF 经历 944 条里 880 条正文以日期开头（自省指令要求正文交代绝对日期，`memory/self_reflection/service.py:91-93`），首句长度中位数 53 字。截取正文开头当标题，得到的主要是日期。

### 1.2 P2 做

1. **标题**：经历多一个短标题，由写这条经历的那次模型调用一并给出，存在事实行上（§4）。
2. **经历目录**：system 消息末尾、常驻记忆段之后，多一段确定性渲染的目录：每行一条本会话可见的经历（日期、标题、`fact:ID`），更早的按月只给条数。目录内容只在每日 Dream 批次收尾时变一次（§5）。
3. **今日新经历**（下称"尾部"）：上一次批次之后写入、尚未进入目录的经历，放在请求末尾的当前消息里（TURN 贡献，与当前场景资料一起排在消息正文之前），每轮渲染（§6）。
4. 可见范围沿用 P1 任务书 §5.3 的证据规则：私聊来源的经历不进别人的会话或群聊（§5.3）。
5. 独立的运行时开关 `memory.episode_index_enabled`，默认 false；和 P1 的 `memory.resident_enabled` 互不依赖（§8.1）。

### 1.3 P2 不做

- 不按相似度挑选经历，不按当前消息内容注入任何经历正文。目录只有标题，正文按 `fact:ID` 主动读取。
- 不改 `search_memory`、`save_memory`、`edit_memory` 的声明；固定工具清单修订号不变。
- 不改 Dream 的聚类、分区、簇上限、调度时间和 6 种操作；不改提取的取舍规则（P3）。
- 不新增表；不新增 system 消息条数或缓存断点。
- 不给经历加可见性字段；可见范围仍由证据推出。
- 子 Agent 与插件轮不带目录。

## 3. 设计总览

```
写入（标题）                                  读取（每轮）
自省 episodes ── title ──┐
提取 claim(kind=episode) ─ title ──┼─► memory_facts.title
Dream recompose ── focus ──┤                      │
Dream synthesize ── 沿用锚点标题 ┘                  ▼
存量 ── CLI 回填 ─────────┘      EpisodeIndex.render_conversation(会话)
                                    │  §5.3 过滤；水位 = 最近一次已收尾 Dream 的 snapshot_max_fact_id
                                    ├─ fact_id ≤ 水位 → 目录（system 末尾，静态贡献）
                                    └─ fact_id > 水位 → 今日新经历（当前消息，TURN 贡献）
```

新增的东西：一列 `memory_facts.title`、一个渲染器、两条提示词贡献、一组 CLI。没有新表，没有新调度步骤，没有新的模型调用路径（回填 CLI 是一次性的所有者操作）。

## 4. 标题（架构书 Q9）

### 4.1 存储【推荐】

`memory_facts` 新增一列 `title TEXT NULL`（迁移 `0163`）。只有 `kind=episode` 使用；其余 kind 恒为 NULL。

为什么是一列而不是新表：标题与正文一一对应，跟随同一行的生命周期。整人遗忘直接删行（S11），标题随行消失，不需要级联或同步；单条失效、被取代后渲染按状态过滤，和正文一样。新表要额外处理删除级联、Dream 输出与 Rebuild 的同步。

迁移 `migrations/versions/0163_memory_episode_title.py`：`upgrade` 加列，不回填；`downgrade` 删列（SQLite batch）。冻结迁移，不引用 ORM。`MemoryFactModel` 加 `title` 映射；`docs/architecture/README.md:34` 的 head 改为 `0163`。

### 4.2 生成【推荐】

由写这条经历的那次模型调用一并给出，不新增调用：

| 写入方 | 改法 | 覆盖 |
|---|---|---|
| 自省 | `SelfEpisodeProposal` 加必填字段 `title`；指令加一句"title 用一句不超过 20 字的话概括这件事，不写日期" | SELF 经历（83%） |
| 提取 | `MemoryClaim` 加可选字段 `title`；指令加一句"kind=episode 时给 title，规则同上；其他 kind 省略"；`EXTRACTION_SCHEMA_VERSION`、`BATCH_EXTRACTION_SCHEMA_VERSION` 各加一 | 人物、群经历；Rebuild 同路 |
| Dream recompose | 输出事实的 `title` 取该输出的 `focus`（S8），`DreamRecomposePlan` 带上 focus 传给 `mutate_dream`（`memory/mutation/service.py:132`、`:306`） | 不改 Dream 指令 |
| Dream synthesize | 输出事实沿用锚点的 `title` | 不改 Dream 指令 |
| Dream merge / keep | 锚点原样保留 | — |
| Main `save_memory(kind=episode)` | 不改（改参数会动固定工具清单）；标题为 NULL | 少量 |
| 存量 | 一次性 CLI 回填（§7.2） | 1142 条中除 recompose 已有 focus 的 95 条 |

标题为 NULL 的经历照常进入目录，标题位置渲染"（未命名经历）"。不因为没有标题就排除（缺标题不是准入条件）。

写入方的改动**不受** `memory.episode_index_enabled` 控制：标题只是多存一个字段，用户看不到；开关只管渲染。这样开启目录时，开关关闭期间写入的经历已经有标题（§9 P2-Q7）。

### 4.3 为什么不用其他来源

| 来源 | 结论 | 原因 |
|---|---|---|
| 截取正文开头 | 不选 | 880/944 条 SELF 经历以日期开头，首句中位数 53 字（§2） |
| 复用 `memory_key` | 不选 | SELF 的 key 是来源哈希，改语义会牵连 FTS、变更定位与 embedding 文档；非 SELF 的 key 是英文短语 |
| Dream 批次后新增"标题步骤" | 不选 | 多一个调度步骤和模型调用；当天写入的经历要等到次日才有标题，尾部无法渲染 |
| 只靠 CLI 回填 | 不选 | 新经历每天 10–61 条，需要所有者持续执行 |

## 5. 经历目录（静态贡献）

### 5.1 接口

新模块 `memory/episode_index.py`：

```python
@dataclass(frozen=True, slots=True)
class EpisodeIndexRender:
    index_text: str          # system 末尾的目录；空串表示没有
    recent_text: str         # 当前消息里的今日新经历；空串表示没有
    index_fact_ids: tuple[int, ...]
    recent_fact_ids: tuple[int, ...]
    through_fact_id: int     # 本次使用的水位；没有已收尾的 Dream 运行时为 0

class EpisodeIndex:
    async def render_conversation(
        self, conversation_id: str, *, through_fact_id: int | None = None
    ) -> EpisodeIndexRender: ...
```

`through_fact_id` 只给 CLI 离线核对用（§7.1）；运行时取 §5.2 的水位。会话身份的解析与 P1 一致（`memory/resident.py:131-147`）。一个只读会话，不调用模型，不写库。证据来源查询复用 `memory/resident.py:515-543` 的 `_origins`，私聊与群的判定复用 `:254-268`，抽成两个模块共用的函数，不复制第二份。

### 5.2 水位：目录每天只变一次【推荐】

水位 = 最近一次**已收尾**（`completed_at` 不为空，终态为 completed 或 partial_failed）的 Dream 运行的 `snapshot_max_fact_id`（S9）。不新增列或表。

- `fact_id ≤ 水位` 的可见经历进目录；`> 水位` 的进今日新经历（§6）。
- 一次 Dream 运行收尾时水位前进一次；P1 的核心集也在同一时刻变（S9），所以一个会话的缓存前缀每天最多因记忆失效一次。
- 运行中（05:00 到收尾之间）沿用上一次运行的水位。
- 当天 Dream 产出的新事实 ID 大于本次快照，会留在尾部到次日；被它们取代的旧经历当时就从目录消失。近 14 天 recompose 与 synthesize 合计 26 次操作（各种 kind 合计），影响很小。
- 从来没有已收尾的运行（Dream 关闭或尚未运行）时水位为 0：目录为空，经历全在尾部，受 §6 的上限约束。

目录字节在一天之内还会因为两类事实变化而变：列出的经历失效、被取代、被删除，或其人物停用、合并。这和 P1 常驻段相同，属于必须立即反映的变化。

### 5.3 可见范围（与 P1 任务书 §5.3 同一套证据规则）

共同条件：`kind='episode'`、`status='active'`、`conflict_state='clear'`、`review_state!='quarantined'`、`valid_until` 为空或未到；`authority` 不是 `third_party`；person / person_group 经历的主人人物（原人物与根）enabled。

| 会话 | 收哪些经历 | 证据条件 |
|---|---|---|
| 与 P 的私聊 | 主人是 P（按根）的 person / person_group 经历；SELF 经历中 `visibility_type='private'` 且可见人物根为 P 的 | 任一证据来自别人的私聊、或证据所在会话无法追溯，即排除；没有证据行的允许（同 P1 Q14） |
| 群 G | G 的群经历；SELF 经历中 `visibility_type='group'` 且可见群为 G 的；主题群为 G 的 person_group 经历 | 至少一条证据，每一条都是 `event_id` 不为空、所在会话 `space_id` 为 G 的直接聊天事件（"本群证据条件"） |

- 群里不收 person 范围的经历，即使证据全在本群（与架构书 Q16 选 b 一致；主群受影响 35 条）。见 §9 P2-Q2。
- 证据是工具回执、且回执的触发事件在本群的，仍不满足本群证据条件（与 P1 相同）。工具结果可能含其他会话的内容，评估集排除例 155400 就是从群聊查看他人私聊。代价是主群 143 条 SELF 经历与评估集 P1 案例的 fact 3157 不进群目录。见 §9 P2-Q3。
- 标题与正文出自同一条经历，可见范围相同，不单独判定。

### 5.4 格式与排序

```
经历目录（截至 11-21 的每日整理。每行一件可以想起的事，用 search_memory(fact_id=编号) 读全文；更早的只给每月条数，可用 search_memory 的 since/until 按时间查）
- 2026-09：共 31 条
- 2026-10：共 143 条
- 11-05 <标题>（fact:3210）
- 11-06 （未命名经历）（fact:3221）
…
```

- 经历日期取 `coalesce(valid_from, created_at)`，按部署时区（`memory_dream_timezone`）显示 `MM-DD`。33 条 active 经历没有 `valid_from`，用写入时间。
- 排序键 `(经历日期, fact_id)`，升序。取排序后最后 `MAX_EPISODE_INDEX_LINES` 条逐行列出，其余按 `YYYY-MM` 计数，月份行在前。
- 标题把连续空白折成一个空格，不截断、不改写（同 P1 任务书 §5.2）。
- 标题行"截至 MM-DD"取水位所属运行的 `completed_at` 的本地日期。
- 没有可见经历时 `index_text` 为空串，不输出标题行。
- 输出只取决于数据库内容与水位，与查询顺序、进程、时间无关。

### 5.5 预算【推荐】

| 项 | 上限 | 依据 |
|---|---|---|
| `MAX_EPISODE_INDEX_LINES` | 120 行逐条 | 主群从 fact 3210 到评估集 E1 的失败时刻之间有 104 条可见经历；120 行约覆盖主群两周 |
| `MAX_EPISODE_RECENT_LINES` | 20 行 | 主群每天新增 0–19 条可见经历 |

这些是提示词篇幅的预算，不是准入门槛：超出的经历以月计数出现，仍可按需读取。代码常量，同 P1 的 `MAX_RESIDENT_SET`。

**成本估算**（P1 研究报告附录 B.8 的公式与基线；标题按平均 16 字、每行约 35 字估，每字 1.0–1.5 token，缓存价按 10%）【假设】：

| | 所有者私聊 | 主群 |
|---|---|---|
| 目录（120 行，约 4200 字） | 每次请求输入 +4200–6300 token，缓存命中后等价 +420–630 | 同左 |
| 每轮等价未命中 token 增幅（目录） | 约 +5%–7% | 约 +6%–9% |
| 尾部（满 20 行，约 700 字） | 约 +1.5% | 约 +4%–5% |
| 每日失效一次 | 与 P1 常驻段同一时刻，整段历史重计费一次 | 同左 |

每次请求的原始输入 token 增幅约 10%–16%，超过 P1 用的"10%"阈值，所以 §11.4 改用等价未命中成本作为阈值。选 60 行可以减半，但 E1 的依据经历不在逐条范围内（§9 P2-Q4）。

## 6. 今日新经历（TURN 贡献）

- 收 §5.3 过滤后 `fact_id > 水位` 的经历，按 `(经历日期, fact_id)` 取最后 20 条，升序；超出时首行后加"（另有 N 条，可用 search_memory 查）"。
- 格式：

  ```
  今天新记下的经历（还没进入目录）
  - 11-22 <标题>（fact:4105）
  ```

- 在当前消息里，排在 `context.current` 之后（`priority=84`，`context.current` 是 85）。`prompting/serializer.py` 为 `memory.episodes_recent` 加一个原样输出的分支（#687 删掉的是 `memory.resident` 的同类分支，`prompting/serializer.py:21-23`）。
- 写回历史的是不带资料的原消息（S2），尾部不进会话历史，也不进 compact 检查点。

## 7. 维护与 CLI

### 7.1 `yuki memory episodes`（`cli.py:203-222` 一带，与 `resident` 平级）

| 命令 | 作用 |
|---|---|
| `render --conversation <id> [--through-fact-id N]` | 打印该会话此刻的目录与今日新经历全文、fact ID 列表、水位；不看开关；`--through-fact-id` 用于离线核对评估集 |
| `check` | 对全部会话做只读渲染，输出每个会话出现的 fact ID；复核查询放在验收脚本里，不在产品代码里放第二份过滤（P1 任务书 §15 第 28 条） |
| `backfill-titles [--dry-run] [--limit N]` | 对 `title IS NULL` 的 active 经历按 fact ID 升序成批生成标题（§7.2）；`--dry-run` 只打印 fact ID 与标题，不写库 |
| `set-title --fact <id> --text <标题>` | 所有者改写一条经历的标题 |
| `status` | 水位与其运行、有标题 / 无标题的 active 经历数、各会话目录与尾部的条数 |

`--dry-run` 与 `set-title` 的输出含正文派生内容，只在部署环境内查看，不写进仓库文档。

### 7.2 存量回填

- 在 CLI 进程内装配模型运行时（S12），用途 `ModelTask.MEMORY_DREAM`，结构化输出 `{items: [{ref, title}]}`，输入是一批经历的别名与正文，每批不超过 `memory_dream_max_input_characters`。
- 程序校验每个 ref 都在本批输入里，再用一个短写事务只更新 `title IS NULL` 的行；事务内不等待模型。
- recompose 产生、已有 focus 的 95 条，回填时直接取 focus，不调模型。
- 预计调用次数：约 1050 条、按平均 238 字计每批约 80 条，约 14 次【假设：按字数估算】。
- 回填只写 `title`，不碰 `updated_at` 与正文。Dream 的 `fact_signature` 含 `updated_at`（`memory/dream/repository.py:106-127`），改了它会把这些事实重新排进 Dream 待审队列。`title` 也不加入 `fact_signature` 和 embedding 文档。

### 7.3 记忆依据规则【推荐】

`memory/context.py` 的 `MEMORY_GROUNDING_RULE` 第一句（#687 后为"系统提示末尾的'常驻记忆'只带少量稳定条目……"）改为同时说明经历目录："系统提示末尾的'常驻记忆'与'经历目录'只带少量稳定条目与经历标题，可能为空；其余长期记忆不自动附带。"后面不变。

它在恢复哈希范围内（P1 任务书 S4），部署当次在途 Work 换链一次，与 P1 部署相同；上线前按 P1 任务书 §12.1 第 2 步确认没有执行持有未收尾的公共压缩回执。不改它的话，"其余长期记忆不自动附带"与目录并存，构成矛盾表述（§9 P2-Q5）。

## 8. 提示词位置与开关

### 8.1 开关

`MemoryRetrievalRuntimeConfig.episode_index_enabled: bool = False`（`admin/models.py:167-183`，与 `resident_enabled` 并列），对应 `config.py:224` 一带的静态默认 `memory_episode_index_enabled: bool = False`。

- 关闭：不渲染目录与尾部；写入方照常写标题；CLI 照常可用。
- 开启：`ContextAssembler` 在 `_with_resident`（`services/context_assembler.py:330-353`，可改名为 `_with_memory_segments`）里多调一次 `EpisodeIndex.render_conversation`，结果写进 `AssembledContext.episode_index_text` 与 `episode_recent_text`（`:62-84`）。
- 与 `resident_enabled` 互不依赖，可单独开、单独关。

### 8.2 位置

| 段 | 贡献 | 位置 |
|---|---|---|
| 常驻记忆（P1） | `memory.resident`，静态，priority 10 | system 消息倒数第二段 |
| 经历目录 | `memory.episode_index`，静态，priority 5，`PromptChannel.CONTEXT` | system 消息最后一段 |
| 今日新经历 | `memory.episodes_recent`，TURN，priority 84 | 当前消息里 `context.current` 之后 |

- 两者都不加入 `invariant_contributions()`，恢复哈希不含它们。
- 不新增缓存断点；system 消息仍是一条，`static_count` 不变。
- 渲染失败：与 P1 同一处（S3），目录与常驻段各自独立接住，这一轮只少出错的那一段，记 `memory_episode_index_render_failed` 日志。这是 P1 任务书 §15 第 29 条已说明的有意例外，不在渲染器内部兜底。
- 入口：与 P1 任务书 §6.5 相同。主轮、定时任务、SELF 主动轮、外部唤醒与 Work 续接按所在会话渲染；子 Agent 与插件轮不带。
- 在途 Work：同一激活内 system 前缀不变；续接是新激活，按续接时渲染（#687 的 F17 结论）。
- compact：压缩请求只把 system 前缀当上下文，被压缩的对话与检查点里没有目录或尾部（#687 的 F23 结论）。

## 12. 上线与回滚
