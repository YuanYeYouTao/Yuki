## 1. 速度结论：还有明显的本地优化空间

最新一笔自然 QQ 配图只有 **23,556B**，接纳到成功结算用了 **29.614秒**：

| 区间 | 时间 | 现在能说明什么 |
| --- | ---: | --- |
| 接纳 → 最后一段正文成功时间戳 | 5.314s | 三段正文，含原发送及段间节奏 |
| 最后一段正文 → 图片 Social 回执创建 | **21.882s** | 图片发送前的后台发现、来源核验、选图、快照读取和 Social 准备等；尚不能细分到单个函数 |
| 图片回执创建 → 图片成功结算 | 2.419s | 仍包含 claim、平台调用和 Yuki 账本提交，不能叫纯网络耗时 |
| 成功结算 → 配图意图关闭 | 0.074s | 本地派生收尾 |

这张图的不可变快照早在10月19日已经存在；本次没有首次收藏、首次发布或视觉描述。相同素材另一笔历史记录总共14.099秒，其中正文后准备6.642秒。文件大小与格式都没有规定它必须等二三十秒。

当前段间配置是1–2秒，三段正文只有两次段间等待，合计2–4秒；它解释不了最后正文之后的21.882秒。保留这个用户可配置节奏，提速不顺手关闭分段或改变人格表达。

本次又对同一素材做了无发送、无修索引的只读拆测：

| 当前受控组件 | 三次观测 |
| --- | --- |
| 环境内实际等价暖检索，含只读 cache/排名/当前JSON/原件查证 | 137.1 / 19.1 / 18.4ms |
| 含一次新 Python、helper import 与 Docker exec 的观测总耗时 | 1.758 / 0.690 / 0.518s |
| 环境内 Python noop | 0.238 / 0.303 / 0.456s |
| Bot 实际 immutable reader 读并校验这23KB快照 | 5.02 / 0.60 / 0.49ms |
| 原只读 environment_status socket 往返 | 103.5 / 7.0 / 5.0ms |

这些顺序探针会暖缓存，和旧慢消息不是同一负载窗口，不能相减成一次端到端加速倍数。它们说明：当前数据本身的必要检索和读取工作可以远小于21秒；helper启动有固定成本，几十秒空档仍需补阶段取点查清。

同一轮不查健康接口的一分钟主机样本：CPU空闲73.9%、I/O wait 4.15%，换入11.49MiB、换出22.27MiB；历史卡顿窗口曾有明显更高的换页和I/O等待。CPU没有算满，主机压力会放大读库、进程启动和文件读取的尾延迟。不能拿当前空闲样本替代旧慢消息的负载，也不能只根据swap存量认定泄漏。

可复用数据见[耗时证据JSON](../operations/emoji-latency-evidence-20261026.json)。最近自然样本仍停留在10月25日21:28 UTC，本轮没有制造新消息。

实际安装的 SnowLuma 2.1.1 会等待素材构建/必要上传、QQ原生发送响应和自身finalize收尾，然后才返回OneBot成功。已有上传快传和UID映射快路，不应在Yuki再建一套资源ID缓存。OneBot引用不证明对端已读；OneBot调用耗时也含网关本地工作。

## 5. P02：统一本地发表和通知媒体读取

**文件**：`gateway/social.py`、App/ACP adapter、`social/service.py`/原repository、`plugin_host/notification_delivery.py`/repository/db_models、原媒体reader、`client_api/views.py`/`files.py`和共享历史可见性查询。

### 5.1 必要的内部确认事实

在既有内部 `TransportReceipt` 中增加 `remote_confirmed: bool = True`；App/ACP无副作用adapter显式返回False。原远端适配器和第三方正常回执沿原True语义。

这个事实只表达已发生的远端确认，不是模型参数、任务模式或持久状态。不得根据 `reference is None` 或平台名字猜：QQ文件成功也可能无native引用，仍保None+True。所有真正消费receipt的地方传递同一事实，不保一份相互冲突的判断。

### 5.2 本地事件才是成功

App通知在原writer中完成事件append和outbox sent；普通Social也以本地event+receipt提交为成功点。adapter noop返回之后不能提前置confirmed，再把本地append失败记成成功。

本地去重使用原outbox/operation派生的明确内部ledger键，外部平台消息号保实际None；不编造native ID。commit确认丢失先查原outbox/ledger键，按真实提交结果恢复。同一writer已rollback时没有半条出站；真实远端已确认后本地持久化出错仍保原远端事实，不能被本地规则误伤。

还要处理不抛异常的未发表分支：当前 `content_sources_retained=False` 会跳过append，随后仍finish succeeded。App没有已发生远端效果，这时应按原来源撤销/未发表事实结算，不能得到成功而event_id=None；远端已确认的同一路径继续保原远端结果。实际forget/generation变化撞上这个检查也列入验收。

图片先在writer外由原媒体来源冻结稳定artifact，账本段保存当前已有的artifact/version引用，Client沿原授权读取。只删第一处None判断而保后续非空门槛不算完成。

补齐原outbox与实际发表事件的关系：在既有outbox增加可空 `event_id` 外键及必要索引，和本地append/sent在同一事务保存；这是真实交付关联，不是影子状态。event被合法删除后置空，原sent事实保留，不因空值重发。旧行迁移保NULL，不扫历史猜补。原attempt/CAS不成立时，事务中的本地append也必须回滚。

Client消费者一起收敛：`ClientViews.events`/ACP历史的现有 `history_delivery_predicates` 和 `ClientFiles._references` 文件列表目前只认成功Social回执。让共享的已发表查询同时识别原sent outbox关联的真实event，保原Person/Conversation、keeper、Work访问和artifact精确version条件；不伪建Social行，不删除所有可见性限制。验收必须通过实际messages/history、files list再下载，不能手填artifact ID只测下载接口。

### 5.3 冷恢复按原本地提交事实处理

`remote_confirmed` 是调用返回时的事实，不是重启凭证。由实际Provider在既有connection profile的capabilities声明本地ledger发表语义：发送adapter不产生外部消息效果，交付由本地事件提交完成。接纳时把原provider_id、Presence及该声明冻结进原prepared路由；恢复从原登记Provider/Presence核对这一语义，不能以None、今天默认入口或平台名字反推。缺声明的旧行不能推定可重放，调用后结果也不能倒填成调用前证明。复用原prepared资料，不增加恢复模式表或连接状态列。

同步处理 `SocialOperationRepository.recover_interrupted` 的executing→uncertain、outbox过期processing→uncertain及 `finish_outbox` uncertain→sent要求native ID的消费者：对明确的本地投递先查原outbox/内部ledger键/真实event关联，已提交返回原结果；未提交且来源仍合法时只恢复同一次本地原子发表。真实远端和无法证明来源的旧unknown保持原事实，不扩大成通用重放。部署不批量改写旧终态。

### 5.4 U01在本包收敛

通知worker复用原 `read_owned` 一次取得owned metadata和verified bytes，交给既有TransportMedia；删除transport中裸 `Path.read_bytes` 与重复resolve。先做一条本地损坏注入验证差异，再统一该读取路径，不新建checksum账本。原TTL/plugin/source批准及旧成功回执优先返回保持。

**验收**：App/ACP text/image、实际批准SDK、目标grant；实际messages/history、files list和下载都可见/可读且跨Person不可见。每次本地成功恰好一个事件与原outbox sent。覆盖正常source检查跳过append、rollback、commit确认丢失、取消、App noop前后/writer前后崩溃、租约恢复、handle到期、撤权和错误version。损坏/截断媒体在消息API调用前被原verified reader拒绝。QQ file None+True、native text/image缺真实回执、远端unknown不重放均保持。

## 10. P07：崩溃pending自动回收

**文件**：`workspace/store.py`、必要的小型OS锁原语和部署runbook。只保护私有artifact根的未发布临时文件。

采用根目录一个固定OS共享/独占锁：

1. 每次snapshot用独立FD先取得shared，再创建pending，覆盖复制/hash/fsync、短manifest提交和原finally；真正物理操作结束后释放。多个publisher持shared并行复制。
2. 原cleanup另一个物理阶段try-exclusive，忙就跳过本轮pending回收；成功说明遵守协议的活跃publisher为0，可分页清确证无主pending。GC不持SQLite writer等待OS锁，不等活跃copy。
3. 崩溃由OS释放锁，下一次取得exclusive的cleanup回收遗留。保留原blob引用GC；已rename但commit未知的blob不按pending清理。持续发布时可暂缓回收，不设伪回收时限。
4. 固定锁文件不存PID、年龄、版本或任务资料；不锁SQLite数据字节。它的文件身份保持稳定，正常运行不unlink/replace，acquire不写入/truncate，也不搬Application锁的NUL/PID写入。部署权限保证Bot真实UID和Manager都能访问，不扩大整个artifact根权限。

POSIX采用真正shared/exclusive flock，Windows采用真正shared/exclusive LockFileEx；CRT独占锁不能冒充shared。相关系统能力见 [Python flock](https://docs.python.org/3/library/fcntl.html#fcntl.flock) 和 [Microsoft LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)。只复用/提取已有OS底层，不复用写PID的Application业务互斥类。

**验收**：同进程双线程、双进程并行复制确实能同时进入读取区；同进程独立FD及第三进程GC都不删活跃文件；创建边界、正常异常、重复取消、kill、重启遗留都覆盖；已经rename/commit未知仍保原blob。Linux与Windows真实验证，不以mock或耗时门槛冒充并行。

两真实publisher必须同步切换锁协议。旧publisher不持锁时，新GC不能与它混跑；部署按原close收拢两owner再启用新代码，不重建持久环境。

## 11. P08：收藏保存流式，描述按需读取

**文件**：`emoji/library.py`、`emoji/media.py`、原共享复制/描述测试。

保lookup→copy→catalog→首次赢家描述次序。miss后流式取得命名所需真实格式，不再read_bytes/inspect_content驻留全部原件；也不走会全文hash的inspect_path或GIF全部n_frames枚举。原授权缓存SHA与Manager copy expected_version继续核实际复制字节。命名探针须覆盖原来支持的格式，不能把尚未适配的格式默默降为BIN。

无Vision或非JSON创建赢家不准备完整bytes。赢家需要描述时，后台再读取原本次原件并核原SHA；TGS取真实平台预览。不要为了lazy输入改走带20MiB上限/Base64往返的RPC，给原功能无声加新限制。延迟读取失败只结束这次可选描述，已收藏原件保留；像素准备保持原真实视觉预算。

**验收**：8MiB及更大原件在无Vision保存前不再多驻留整份B；重复收藏不读缓存；有Vision并发仅一位赢家尝试一次描述；真实换源由原expected_version拒绝；取消等待实际文件读取退出。描述自身有图像成本，不冒称全流程常数内存。

## 12. P09：TGS格式嗅探保持小而明确

**文件**：`emoji/media.py`，native_media/helper消费者与格式回归。

用小型流式顶层字段嗅探替换gzip后的整件json.load；不引第三方SAX，不写完整JSON验证器，不把gzip头直接认成TGS。

- gzip分块读取，根为object；只识别根级v/layers并取必要w/h，nested同名不算。键匹配处理分块、引号、反斜线与合法转义。
- 无关字符串/数组/对象用引号、转义和嵌套深度跳过，不构造值；只保存固定键匹配状态、必要尺寸及实际嵌套信息。不能把大字符串先join再discard，也不能宣称所有输入严格O(1)。
- 必要标志与尺寸取得后结束；缺可选尺寸时可到根结束并返回None尺寸。字段晚出现只增加扫描，不加经验前缀上限或重试。
- 这是格式嗅探，不再验证全文JSON或gzip尾CRC；可识别前缀但尾部损坏的原件仍可收藏，真实动画消费时报告解析失败。职责与普通PNG头嗅探一致，必须在合同和测试里明说这一删减。

原文件hash仍覆盖实际原始字节，native/历史无MIME的同字节TGS识别保持。无平台预览不冒充看过动画；WEBM/GIF/WEBP语义不变。

**验收**：键顺序/跨块/转义、nested伪标志、普通gzip、截断与坏尾、可选尺寸、真实TGS预览/legacy读取；8KiB gzip包裹约8MiB无关JSON时，不再形成16MiB级整件对象副本。完整动画解码留给实际消费，不靠新增文件大小门槛过关。

## 13. P10：提前准备，实际发图仍排在正文之后

**文件**：`emoji/delivery.py`、`social/emoji_intents.py`、`social/service.py`。依赖P00/P01及文件生命周期修正。

复用现有selected_json、`_deliveries`和`_wake`：

1. 原第一正文claim事务确认提交后即wake现有worker；选图不在writer内，也不等第一条正文API返回才准备。
2. pending先按已有活动集合跳过在途项，再读回执。未选择项可进入准备；已选择项仅在原正文派发结束或来源失效后继续。复用原reader，必要时对本页父/子回执批查询。
3. 同一个原task先选图、保存selected并publish。若正文未结束，返回并保持open/selected，不另建ready字段、队列或长寿命waiter。正文后恢复时跳过重选图，复用manifest和原publish请求。
4. 保留原 `_finished` 的wake：最后正文提交可能撞上准备task尚在活动集合的时刻，完成回调必须补唤醒；selected/not-ready筛选保证这次扫描会退出，不自旋。
5. 实际图片Social claim仍等原 `_text_dispatch_finished`。它认完整子回执及失败/unknown/停止派发事实，不能收紧成全段成功。来源、真实目标路由、取消代次和原回执在claim重核。

准备task返回前收拢实际线程、FD和P07 shared锁；等待正文期间仅保原selected/artifact/receipt事实，不在内存挂住整图或Base64，也不以selected有值冒充publish已成功。后续恢复仍读原manifest/request结果。

第一claim提交确认丢失、正文结束与task移出活动集合的竞态、重启初次wake都要覆盖。最小落点是在原writer上下文完成物理收尾后的finally，依据已有prepared_emoji发一次现有wake；wake只提示查询原ID，不裁决提交。成功或确认未知都不会丢提示，已rollback最多发生一次空查询，不靠新增commit标记/回调框架判断。不得在提交前发一次通知冒充可靠wake。普通Main/Work结束不取消已接纳图片。

图文第一claim和纯图admit都用这个实际writer收尾点。还要处理第一正文claim已持久EXECUTING、但异常发生在进入实际派发前的窗口：单段可能一直未结束，多段首段普通Exception也不同于已有CancelledError分支。联动P03按原operation和真实API未调用事实停止/结算原正文，再唤醒原图片；验收须看到图片最终收拢，不能只断言wake或selected、靠重启或删除正文顺序条件过关。实际已经派发或无法证明未派发时保原未知，不重发。

**行为变化**：选择和快照时刻前移，无候选也会较早结束；后来才改标签/换图不会暗改本次selected或已冻结artifact。只前移准备不提前发聊天，不改变原文字计划及段间随机节奏。

**收益口径**：如果准备耗时原样不变，这笔样本重叠正文最多只能遮约5.314秒，单靠重叠仍剩约24.30秒。因此P00定位和删除重复/冷I/O必须一起完成，不能把并行二字当作解决21秒空白的证明。

**验收**：纯图无text parent直接前进；准备先完成/正文先完成均一次派发；最后正文wake撞active task不丢；selected等待期间无忙轮询；正文失败/unknown/停止仍沿原事实；cancel/换代/撤权、普通完成、选中后publish中断、双owner和重启均保原回执。文字与图并行时同时测正文延迟与磁盘，不把文字拖慢换图片数字好看。
