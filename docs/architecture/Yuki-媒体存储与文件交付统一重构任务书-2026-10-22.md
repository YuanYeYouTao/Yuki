## 1. 用户已明确的方向

- 删除和重构优先，禁止防御性编程。不用新协调器、同步器、全局去重数据库、兼容开关或经验门槛替换旧链。
- 入站原件由 Bot 缓存 24 小时，沙盒直接读取同源只读挂载；不在沙盒里另建一份 24 小时缓存。
- 按需看图、显式保存、原生表情收藏和首次后台视觉描述继续工作。后台表情看图本身不是本次要删除的问题。
- 普通文件和图库文件在沙盒内长期保存、自由编辑。不可变 artifact 专门承担发布及交付版本保存。
- 对外发送保持一个入口。本次将模型工具统一为 `send`，不保留旧名可执行别名，统一发送文字、图片和文件；普通发文件的发布步骤收进程序内部，不新增 `send_file`，也不同时保留两个可执行工具名。
- 原内部事件、人物、执行、请求、已提交协议和真实投递回执保持原事实；不因文件到期、工具改名或升级而重发。

## 3. 重构后的存储职责

```text
Bot 入站原件缓存（24 小时，唯一 writer/清理 owner）
    ║ 同源只读挂载
    ╚══ /inputs/media-cache
           ├── 按需 inspect
           └── Manager 直接复制
                  ├── /workspace/普通文件
                  └── /workspace/stickers/<platform>/files + index
                                  ↓ 明确发布或实际发送
                           不可变交付 artifact
                                  ↓
                            原 Social 统一出口
```

同源缓存不要求把不同事件的同哈希原件改成全局共享对象；本次不改变每个真实来源的 24 小时寿命，也不增加全局内容寻址存储。

### 3.1 一条直接复制实现

后台收藏与显式保存共用同一个 Manager 私有文件操作：源共享缓存路径、所选内容哈希、目标路径、原 request ID。终端自行 `cp` 仍沿正常 Linux 文件语义，不强制经过该桥。

Collector 当前读取的 `PreparedAttachment.source()` 可能是 Bot 私有临时文件，不能直接把该路径交给 Manager。应复用现有 `ConversationMediaService` 的同次下载与缓存发表，取得真实 `/inputs/media-cache/v1/...` 路径；不得重新下载或把整份内容通过 JSON/Base64 再传一次。

Manager 复用 `FileWorkspace` 的源 FD、目标 parent FD 与已有文件 I/O owner，流式复制并在同一次读取计算哈希，核真实源版本后原子落目标。真实路径和原件核验保留；普通目标覆盖不加 CAS、额外容量门槛或自动备用文件名。

`FileWorkspace.write()` 当前存在“已有文件必须提供匹配 expected_version”和落盘前重复目标版本比较。重构普通复制时一并删除这两层目标 CAS、对应的目标 `expected_version` 参数、全部相关调用、说明和冻结旧规则的测试，不留下失效字段；源哈希核验与调用者显式选择的源版本不能误删成同一件事。

复用现有 `environment_mutations` 回执和 `file_request` 的执行收拢：先查询原 request，再接触源文件。成功复制不会因 24 小时原件到期而变成失败；用户随后编辑、移动或删除目标，不触发恢复时重拷。未知结果沿原事实核对，不盲目再复制。取消等待须收拢实际线程 I/O 后处理暂存文件，不能把仍在发生的写入当作已经取消。

### 3.2 保留普通文件与交付快照的独立版本

收藏、保存不创建 artifact；首次后台表情描述、JSON 编目和可重建检索索引继续消费原文件。相同表情按原内容哈希复用，不因这次存储重构重新购买描述。

真实发布时才冻结交付版本，之后普通文件的改写、改名或删除不改变原交付内容。继续复用现有表情发布身份和原执行发布回执；不引入全库去重扫描或第二张发布状态表。

不以硬链接把可编辑工作文件连接到临时缓存或不可变 blob。图库索引 `search.sqlite3` 仍可重建，原图、可编辑 JSON 和原交付快照不能据此当作缓存清空。

## 4. 统一发送合同与工具改名

### 4.1 Main 只选择发送动作

当前支持：

```json
{
  "path": "/workspace/report.pdf",
  "attachment_kind": "file",
  "text": "报告在这里"
}
```

该参数交给目标工具 `send`，内部沿原发布服务冻结所选文件，再走同一 Social/适配器出口。已有 `artifact_id` 继续作为已冻结文件的输入。存在附件时 `path` 与 `artifact_id` 二选一，纯文字和现有 emoji 发送沿原行为。

`path` 沿现有共享工作区或共享缓存文件范围，不解释为客户端本机路径、任意宿主路径或 URL。保留当前发布可选文件名及显式源版本的用途，不把它们变成必填门槛；绑定目标与人物身份仍认内部 ID。平台文件 API 和传输差异继续留在适配器，不增加平台专属模型 schema。

`workspace_publish` 退出 Main 完整执行清单、direct 声明、Code 直调和 Script API；内部发布服务及 Manager 发布操作保留。不得另起一个 `send_file`、保留可接新调用的旧别名，或只在 direct 隐藏而由 Code 继续执行旧工具。

插件原媒体 handle、SDK 与 Client 上传合同不因此获得 Host 路径读取能力；有真实共享环境授权的 Main/工作者等入口共用同一实现。Client 下载和已存在的 artifact 引用继续认原对象，不为精简模型工具删除内部交付能力。

### 4.2 冻结一次，按原回执交付

在原读取授权范围内，先查询既有发布/发送回执，再接触可变路径、文件存在性、源版本和当前目标可达性。没有可复用回执且需要产生新效果时，沿原执行核当前实际来源、授权、目标，再内部发布；今天文件已删除或目标不可达不能否定原成功事实。

用原执行/call ID 派生稳定发布子键，复用现有 Manager 发布回执和不可变 snapshot；不把路径或今天文件内容当作新的业务身份。内部发布沿现有安全 FD 流式 snapshot，不借视觉 `workspace_media_read` 的 Base64/20 MiB 读取桥，避免把模型看图预算变成普通文件发送门槛。

原发送参数、实际冻结的 artifact 和原 Social 操作各保真实来源。恢复先查原发布/投递回执，已冻结后不重新读今天的可变路径；已完成、已派发未知或部分成功的发送不因工具包装改变而重发。文件发布成功不代表平台送达，原快照尚在但文件已被用户删除也不能否定过去已经送达的事实。

`path` 调用的原模型参数没有 `artifact_id`。必须把实际冻结 ID 沿原可信回执交给 Work 交付汇总、Client/SSE、文件下载与效果证据；不能只改 schema 和 SocialMessage，让 `effect_outcomes` 等消费者继续只读原参数中的 artifact ID。原请求指纹不被内部解析出的参数覆写。

内部发布与发送只是同一请求的既有步骤，不新增任务、队列、全局成功门槛或自动失败切路。新工具合同在部署时冻结并开启合法新链，不修改已经提交的前缀、工具配对或已付请求。

### 4.3 文件、附言按实际步骤报告

新调用统一以原发送计划和逐步 `parts` 回执为事实。删除“第一步一定是文件”的新汇总猜测，以及由它生成的错误成功说明；文件结果由原计划中实际携带 artifact 的步骤确定，文字结果由实际文字步骤确定。

同步收敛 `AgentTools`、`effect_outcomes`、交付意图、原效果查询、客户端展示和相关测试，不让这些消费者继续依赖 `file/caption` 的位置别名。历史 `send_file_caption` 回执继续可读，不注册成新工具，不重写旧回执为新计划。

QQ 文件加附言、Telegram 原生 caption、Feishu/Lark 先文字后媒体或多段文字，均沿真实计划报告。上传已发生、平台确认未知或部分发送成功时保持原状态，不因汇总修复重传或重发。

### 4.4 `send_message` 改为 `send` 的范围

当前执行入口已经统一为 `send`。名称缩短本身不改变能力；结合路径发送和退出模型侧 `workspace_publish`，新说明统一写清“向当前会话或指定目标发送文字、图片、文件或表情”。不新增通用 action 分派参数，不扩大到任意网络或宿主操作。

当前内置清单没有另一个公开 `send`，Code Mode 的脚本名按既有投影规则由 `yuki_send_message` 改为 `yuki_send`。部署仍使用原目录的重名核验，不建立新别名注册器。静态扫描 `src/yuki` 有 22 个 Python 文件包含旧工具同名字面量，既有当前工具判断，也有必须保留的持久 action；不能把文本命中数当作可全文替换的清单。

| 层次 | 计划改动 | 不能混改的事实 |
| --- | --- | --- |
| 模型工具与目录 | `send_message` → `send`，canonical 工具 ID 随之为 `core.send`；用途/检索词补齐发文件、发图片 | 权限 namespace `social.send` 已表达领域权限，继续使用 |
| direct / Code | 完整执行清单、直调清单、目录、Script API 共用同一新 schema，投影 `yuki_send` | 旧 `send_message/yuki_send_message` 不保留新执行入口 |
| 调度与恢复特判 | 当前发送的串行屏障、补充输入边界、原未派发意图和结果捕获判断全部识别 `send` | 保现有发送行为，不因漏改而落入普通业务调用或并行读取分支 |
| Social 当前分发 | `SocialService.execute()` 和实际内部调用者改用 `send` | 不接受两个当前工具名来兼容漏改调用者 |
| 持久领域动作 | 继续使用现有 `send_message`、`send_message_sequence` 与历史 `send_file_caption` 存储值 | action 已参与 `payload_hash`、emoji 指纹、父子步骤和既有回执关联，不能按工具名改写 |
| 原执行和展示 | 新事实记录真实工具名 `send`；旧事实读取仍识别原 `send_message` 并保原名 | 不改旧 `tool_id`、call ID、参数、证据、已付协议、诊断或回执来凑新名称 |

需要逐项改的是下列当前调用者与判定，不能只改 `social/tools.py`：

- `capabilities/provider.py` 的常驻工具、能力元数据与检索词；`codemode/tool_visibility.py`、`services/main_agent_contract.py` 和自动 API 投影，更新 schema/合同修订。
- `capabilities/coordinator.py` 的发送串行屏障，`services/agent_runner.py` 的 Code 子调用分类，`services/main_agent_backend.py` 与 `services/invocation_service.py` 的补充消息、原发送意图恢复及回执捕获。
- `social/agent_adapter.py` 的插件后台来源判定，`social/service.py` 的当前工具分发；`emoji/delivery.py`、`plugin_host/facades.py`、`gateway/providers/app/ingress.py`、`memory/self_reflection/reporting.py` 的真实当前调用。
- `runtime/effect_outcomes.py`、交付汇总和工具结果中的当前名称。读取旧证据时识别旧名不等于允许执行旧工具。`participation_feedback.py` 读的是 Social action，保原领域动作集合，不能机械替换成工具名 `send`。
- `prompting/contracts.py`、`runtime/work_control.py`、`services/semantic_participation.py`，以及订阅监视插件的新通知指令、当前示例和现行文档。后台 Agent、SELF、子 Agent 与普通 Main 共享同一名称。
- `docs/emoji-system/AGENT.md` 等供模型实际阅读的指引同步。部署中现有 `/workspace/stickers/AGENT.md` 可由用户编辑，升级只显式纠正失效工具名、保其余正文，不整份覆盖；旧通知输入或 TaskSpec 原文不批量改指纹或重放。

Social 内部动作与模型工具名在当前入口明确分开。现有 `_effect()` 的 `startswith("send_")` 等判断认的是持久动作；漏分层会让新 `send` 绕过原交付记录。原 `sequence_prefix`、`social_call_key`、snapshot 子键、Social/emoji 指纹及 Work 归属保持不变，不新增“旧调用失败后换新名再发”的 fallback。

Plugin SDK 当前公开的是 `send_text/send_private/send_group/send_image`，并没有一个同名 `send_message` API；它们只需内部继续走统一出口，不因模型工具缩名而重命名整套 SDK。通知 `publish`、Client `/messages` 与 `prepare_message` 同样保持；F02 的 Client/SDK 工作只涉及实际 artifact 结果消费，不扩大公开发送 API 改名。现行自动化 TaskSpec 交共同 Main 执行；`chat-media-workspace.md` 的“静态提醒编译为 social.send_message DSL”已过时，须删除这段现行说明，不能机械改成不存在的 `social.send` 动作。适配器 `sendDocument`、OneBot `send_*` 和 HTTP/WebSocket 的 `send()` 保其真实协议名称，历史迁移和验收记录保当时事实。

新增 `path` 也须贯通现有媒体授权判定：`main_agent_backend.py` 当前依据 `artifact_id/emoji` 判断插件委托的媒体发送能力。新路径附件不能误判为纯文字而绕过现有媒体授权，也不能借此开放插件 Host 路径；只同步既有媒体输入消费者，不新增审批或权限层。

## 7. 行为验收

| 场景 | 必须证明的结果 |
| --- | --- |
| 普通入站、未保存 | Bot 单份 24 小时缓存；沙盒同源只读视图，无沙盒第二份 24 小时缓存；收藏/保存不生成永久中转快照，首次 Main 无自动像素输入 |

| 保存后用户改写/移动/删除 | 查询和恢复不重新覆盖或恢复用户文件 |
| 源被编辑、读取中变化、复制被取消 | 核对实际选中字节，收拢 I/O；错误/未知如实保留，不伪报成功或盲重跑 |
| path 发文件/图片 | 一个 `send` 调用完成内部冻结和统一发送，消息能力按真实平台执行 |

| 发布后进程中断、发送前恢复 | 使用原冻结版本和原请求，不能重新读取今天路径 |
| 已发文件、附言失败/未知 | 原文件送达事实保持，不重发文件，汇总不把文字成功当文件成功 |
| Feishu/Lark 先多段文字后文件 | 每一步状态认原计划；文件失败不报告 file_sent_caption_unconfirmed |
| Telegram/QQ/App/ACP | 原目标、引用/提及、原生 caption、Client 文件关联与下载按真实入口正确 |
| Work、SELF、子 Agent、插件调用 | 原身份与授权、实际 artifact 效果归属和回执保持，不从参数缺 ID漏记交付 |
| direct/Code/目录 | 同一固定合同，只有 `send/core.send/yuki_send` 对应当前发送入口，无可新执行的 workspace_publish/send_file/send_message/yuki_send_message 别名，说明与执行一致 |

性能只测可归因的量：未发布收藏的永久 blob 增量、复制字节数/耗时、峰值内存、原件读取/hash 次数，以及普通 path 发送的模型调用步骤。不把工具减少一项或本地复制提速宣称为 Provider 缓存命中率提高；真实 cache/usage 字段缺失时保持未知，不改公共历史前缀或旧已付请求求分数。工具改名与删除声明会形成新合同前缀，切换不能承诺沿用旧前缀命中；按合法新链和真实 usage 核验，不为保持表面命中而暗改旧请求。
