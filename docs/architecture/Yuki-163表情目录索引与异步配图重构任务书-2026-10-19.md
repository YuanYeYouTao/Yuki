## 1. 用户确认的方向

1. 删除旧自动偷图 worker 及其整条采集、分类采用、池容量和修复链。平台明确标记的表情继续自动收藏，直接复用本次已经下载的内容；普通图片也允许 Yuki 主动收藏。
2. 表情集中放到一个永久目录，提供能通过终端和 `rg` 阅读的索引。保存文件不等视觉识别、标签齐全或“是否适合表情”的模型裁决。
3. 日常配图沿 `send_message` 的既有意图入口触发：文字先发，后台选图，再通过同一 Social 出口发送。选图和识别不延迟普通文字，不要求 Main 再跑一轮。
4. 显式读图、保存附件、发布文件以及发送已经指定的图片/文件继续使用现有工具语义；本任务不把所有文件操作改成后台投递。
5. 允许清空旧表情库、旧表情文件并升级数据库，不维护旧采用状态兼容链。历史事件、已付请求、原发送计划和回执继续保留。
6. 禁止防御性编程优先。旧限制直接删，不改成另一套开关、配额、打分、审核或重复授权系统。

### 2.1 为什么可以直接从临时内容持久化

“自动存下媒体”和“成为永久表情库”只有寿命与可见位置的区别，不需要再做一次网络收集。来源可能是共享内存字节，也可能是共享临时原件；后台保存直接复制这份内容，经现有 Host/Manager 文件桥进入永久目录。不能移动或提前删除仍被 Main、缓存和其他消费者使用的原件。

QQ 的表情通常仍以 image 段进入，差别在 `sub_type`、`emoji_id`、`emoji_package_id` 等原生资料。它并不天然对应另一套文件格式。保存时同时保留实际字节格式和表情展示语义，发送时由 QQ 适配器恢复相应表现。普通图片可以手动收藏，不把原生标记变成收藏资格门槛。

QQ 内置 `face` 段只有表情编号及可读名称，不是已经下载的图片；它保留原消息语义，不能伪造一张原件或为了收藏再抓一套图片。具有原件的商城表情等才走文件持久化。原生字段说明见[消息段文档](https://doc.napneko.icu/onebot/segment)。

永久收藏直接使用 `PreparedAttachment`，不等待临时缓存发表成功。当前缓存有容量拒绝及 `_pending >= 32` 静默跳过；仅监听“缓存成功”会漏掉已经能取得的表情。新收藏入口不继承该准入条件；本任务不为此重建通用缓存队列。

## 3. 新链路及归属

```text
原入站事件与附件
  → 共用 PreparedAttachment 原件
  ├→ Main 原生媒体／通用临时缓存（现有职责）
  └→ 明确表情自动收藏，或显式收藏普通图片
       → /workspace/stickers/files/ 原件
       → 资产与来源记录 → 可重建 index.jsonl
       → 可选后台描述／标签补充

send_message(text, emoji 意图)
  ├→ 原 Social 文字效果 → 原文字回执立即返回
  └→ 已接纳配图意图 → 目录索引选图 → publish 不可变快照
       → 独立派生 Social 图片效果 → 原图片回执
```

| 资料 | 唯一事实与 owner | 生命周期 |
| --- | --- | --- |
| 原聊天附件 | 原内部事件、附件索引及媒体服务 | 原事件与实际媒体可用性 |
| 永久图库原件 | Manager 持久工作区中的真实文件 | 独立于临时缓存和 Work；普通终端可操作 |
| 资产与描述 | 表情领域的最小资产/来源记录；真实内容 hash 标识版本 | 文件、人工编辑与索引实际变化 |
| `index.jsonl` | 从目录和资产资料导出的终端检索视图 | 可删除重建，不成为第二个写入事实源 |
| 已发布图片 | 原 workspace artifact 不可变快照 | 独立于可编辑图库；沿既有引用回收 |
| 接纳的配图意图 | Social 下的待选输入、原执行身份与派生调用引用 | 接纳至选定并交给原 Social 效果，或真实取消/失败 |
| 发送结果 | 现有 Social operation/receipt 与内部事件 | 永久保持原事实；不复制另一套 sent 状态 |

## 4. 永久目录与最小索引

### 4.1 物理布局和现有桥

使用终端能访问的 `/workspace/stickers/`，默认原件为 `files/<sha256>.<真实扩展名>`，索引为 `index.jsonl`。这是 Manager 持久工作区内的普通目录，不是把 Bot 的 `data/emoji` 改个名字，也不是把 Bot 数据库或凭据挂进终端。部署路径沿现有持久环境映射，不写死宿主绝对路径。

新增内容复用共享下载结果及已有 hash。相同字节只保留一份图库原件，同时追加真实来源；URL、平台 file_id、文件名不作为内容去重键。首次导入与并发重复保存使用原导入身份与内容结果收敛，不增加 seen_count 采用规则。

复用现有媒体保存/checkout/publish 桥，分清相对目的路径与 artifact 显示名称，允许写入表情子目录。普通读写、移动、删除继续交给终端，不恢复已删除的 workspace CRUD 工具。首次收藏不必为目录另造一套 artifact 库；若现有桥经过快照，则复用该真实快照及引用，不重复发布同一导入。

图库文件可编辑，已发布快照不可变；不得通过可写软硬链接把二者绑在一起。复制、hash、解码、扫描、文件同步和导出放在线程或现有文件执行边界，SQLite writer 内不做这些操作。文件失败按真实结果处理，不新增磁盘余量、文件数量或像素经验门槛。

### 4.2 字段与终端修改

资产仅保留内部 asset ID、内容 SHA256、相对路径、真实 MIME/格式、大小及实际可得的尺寸/动画信息、图片描述、标签与 OCR。没有描述也可以收藏、按 ID/路径查看和显式发送；删除旧 `is_emoji`、confidence、adopted、scope、pin、retention score 等字段。

来源可多条，指向原内部事件 ID、附件索引和当时内容 hash，保留必要原 Person/Space/Conversation 引用。终端导入等无入站事件的内容，只在真实执行/导入来源可得时关联，不伪造 ChatEvent，不拿平台消息 ID 重建归属。用户直接放图、自由 cp/解包后才被目录扫描发现的文件，可以记录目录发现事实、原执行未知，照常入索引使用；不增加写入代理或强制登记，也不补当前 Person/事件当来源。文件内容相同不合并原事件或人物。

终端改名、移动、覆盖和删除是正常文件操作。索引重建读取目录真实内容：缺失项退出当前可选集合，改变字节形成新内容版本；不改写旧快照、旧来源或已提交配图。重建不复活已删除文件，不让旧路径名冒充原 hash。目录重扫不进入 Main 和发送热路，不新增为维持固定文件布局而强制修复的守护器。

`index.jsonl` 包含可检索的资产 ID、相对路径、格式、描述、标签等图库资料，不导出原私聊正文、账号凭据和个人聊天上下文。模型通过现有终端 `rg` 与媒体查看桥使用它；图库变化不增加工具、不改系统提示词前缀，也不把整库注入每次请求。

### 4.3 描述和标签的实际生产者

通用媒体缓存当前没有语义标签，不能把这份职责写成已经实现。新内容保存后，可用现有显式配置的视觉能力做一次后台描述，记录图片本身内容、文字与表达含义，例如大笑、反讽或幸灾乐祸的区别；不把原聊天人物和语境拼成图片事实。复用确有对应内容版本的已有观察，不能挪用聊天猜测。

这是一份可选索引补充，不保留旧“判断是不是表情→采用”的付费裁决。先保存，再补充；重复来源不重复调用模型。未配置视觉能力、调用失败或进程退出时，原件和已有资料继续可用，不阻塞收藏、Main 或发言。启动/重建只重建本地可得资料，不因空标签隐式重复付费；显式补充索引沿真实模型调用身份及原结果处理，未知不当作失败自动重跑。

不另造旧式持久分类 jobs、固定重试次数和轮询 worker。后台任务由现有应用生命周期拥有，正常 Work 结束不取消共享收藏；关闭时清理其所持临时资源。若某次保存尚未成功，记录真实失败，不宣称仅有 create_task 就已永久入库。

共享原件由媒体服务拥有，收藏消费者持有原引用，不自行 close、move 或删除。应用关闭先收拢收藏任务及尚在执行的复制线程，再关闭共享媒体和 Manager 桥；取消 async 等待不等于复制线程已经退出。沿现有生命周期安排顺序，不新增资源租约表，避免临时目录在复制途中被 owner 清掉。

### 4.4 平台差异和共享图库

适配器保留“平台明确的贴纸/表情”语义，领域按该通用事实选择自动收藏。各平台的判定留在各自规范化处，不在通用服务堆 QQ/TG 字段分支，不按昵称、文本关键词或扩展名判断。

格式与展示语义分开。QQ 动图、普通图片及 Telegram 静态/动画/视频贴纸保存各自原件，不能把所有 sticker 都假定成静态 IMAGE。适配器按真实能力发送；需要的转换或渲染另有实际产物，不能伪造 MIME、把缩略图冒充原件，或新增隐式付费转换。后续平台只实现规范化与传输，不复制收藏和发送业务。

当前 Telegram 只有 `sendPhoto/sendDocument`，并未实现原生 `sendSticker`，另一发送桥也漏传 emoji 标记。S01/S06 要补齐这些真实消费方，同时把 sticker 标记、`is_animated/is_video`、尺寸及可得的 emoji 描述写进原附件段，保证入账、重启和主动收藏仍能取得相同语义。平台 file ID 仅作适配器资料，不能当内部资产 ID；静态 WEBP、动画 TGS 和视频 WEBM 按实际格式处理，见[官方贴纸规范](https://core.telegram.org/api/stickers)与[Bot API](https://core.telegram.org/bots/api#sticker)。普通 GIF 不冒充原生 TGS/WEBM 贴纸。本任务补原生可发送格式，跨平台转换的未覆盖项如实列出，不为保存原件增加转换前置条件。

Telegram 当前回复规范化没有恢复回复附件。主动收藏“被回复的贴纸”要沿已有内部回复事件及其附件索引读取；确无内部事件时按现有原生引用取得真实来源，不用今日 file ID 或平台消息号反造业务所有权。

已收藏内容属于 Yuki 共享图库，Person 遗忘清除该人的来源关联、个人使用资料和额外拼入的私人语境。图片本身与像素描述可以保留，不要求仍有活跃聊天来源才准用。私人临时附件及原聊天读取仍按原事件授权；相同 hash 不开放原事件、私人缓存或个人资料，也不补造来源。

## 5. 后台配图与唯一发送出口

### 5.1 选择与主模型速度

保留 `send_message.emoji` 的现有目标/情绪输入，整理说明使其表达“我想配什么图”，以完整目标语义检索描述、OCR 和标签；情绪可以作为补充，不再只按粗情绪池选择。先用已有索引检索，删除同步拼图 Vision、发送时补 caption、置信度裁决和随机兜底。

文本发送不 await 选图、视觉请求、目录全扫描或图库修复。索引未齐或暂时无合适图片只是本次可选配图缺失，不能抛错撤销正文。已明确指定的图不再进行一次语义选图。若后续质量不足，基于真实误选样本调整索引，不在本任务中预设一套加权规则或第二个付费选择器。

工具返回实际文字结果和配图已接纳/未接纳事实，接纳不等于发送成功。只有配图、没有文字的请求也可返回已接纳，不伪造正文成功；若接纳或文字之一失败，如实保留另一部分结果。Main 不为等图新增轮次，后台配图不自动把详细结果塞进公共历史或唤醒 Main。

### 5.2 已接纳效果和恢复

在 Social 领域保存恢复真正需要的配图输入：原调用身份、原文字 operation 引用、原内部事件/执行与 actor、Conversation/generation、Presence/目标、选图意图；选定后固定资产内容版本、不可变 artifact 和派生 Social 调用引用。原 Social receipt 只有请求 hash，不能单独恢复未选择的输入，不能拿诊断日志代替持久接纳。

配图使用由原调用确定的独立效果键，经现有 `SocialService` 发送，继续使用原适配器、发送 CAS、账本和回执。不能追加进已经开始发送的正文分段计划，不能改变原工具参数 hash 或覆盖原回执。重放和并发接纳沿同一派生键收敛；发送后的 sent/failed/uncertain 只读现有 receipt，不复制另一套完成台账。

正常 Main/Work 结束不撤销已经接纳的配图，普通聊天不强制登记 Work。后台消费者从持久资料取得独立合法上下文，不持有已经结束的 ToolRuntime、Work lease、effect capture 或当前控制对象。真实取消、来源换代及隐私删除沿现行合同停止尚未发生的新效果，已确认的文字/图片继续保留原事实。

接纳资料还须保留原来源已有的取消事实引用/代次；存在 Work 时关联原 Work/子节点身份。不能只看 generation：现有同会话取消可仅改变 scope 的 `cancel_epoch`，指定子树取消也有自己的撤权事实。发送 claim 的同一短 writer 沿现有领域规则复核真实取消，不保存过期 owner/fence/lease，不要求 Work 仍活跃，不新建取消机制；`completed` 本身不阻止已接纳配图。

重启可继续未选/已选但未发送的接纳输入；发送已 claim 后中断按原 Social 恢复为未知，不盲发。选图期间取消或删除、选定后文件变化、publish 与接纳之间中断均按实际来源和已持久资料处理，不能选另一张重写已发生效果。这里需要的是原意图及快照，不复制一个通用后台任务框架。

不复用强制活动 Work 租约的 `runtime_delivery_intents`，也不把内建配图塞入插件通知 outbox。插件授权和另一套直接传输完成台账不成为新的内建发送路线。图库索引与配图发送独立装配：没有 Vision 仍可发送已有图片，不能沿旧“有视觉服务才启动 worker”的条件。

### 5.3 使用信息

删除旧冷却、次数限制、混合权重和独立 usage 完成判断。需要“最近用过什么”时，从现有 Social 成功回执及内部发送事件派生；失败、待选和未知不能记作成功使用。派生资料更新失败不推翻真实已发送结果，不把它变成下一条消息的门槛。

## 6. 整链删除清单与施工顺序

先按下表拆除旧调用及替代职责，反复搜索装配、消费者和文档，确认没有新调用仍依赖旧生命周期，再实现新目录与后台配图。删除旧链不等于删除其历史回执和真实升级 reader。
