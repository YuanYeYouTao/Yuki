## 3. 建立在现有实现上的删减方向

当前已经具备：

```text
automation_create / 管理入口
  → TaskSpec → AutomationCompiler → AutomationScript
  → 原 Validator / DelegatedAuthority → Repository / version / call key
  → AutomationWorker / claim / scheduled slot / run / step cursor
  → Executor → 静态 Social 或插件 Handler
             → 共享 MainAgentTurnService → 原 Agent loop / Durable Work
  → 原 Work 等待、派生、恢复、预算与效果回执
  → 原 step 结果 → run 结算 → 原计划下一时段
```

不新建自动化 Agent、队列、预算系统、结果存档器、恢复协调器或状态机。主 Agent 的原工具、上下文冻结、任务树和 settlement 已经存在；自动化负责原计划与原 run/step 游标，不再附加一套按长度、次数、字段名和旧状态猜测工作资格的逻辑。

代码索引以下文基线为准。`automation/...`、`services/...`等路径相对`src/qq_ai_bot/`，同行的短文件名沿该模块；`src/yuki_plugin_sdk/...`、`tests/...`、`docs/...`、`.env.example`、`.github/...`相对仓库根。实施后行号移动，保留符号核对，不靠旧行号机械删除。

### 5.1 收尾的删除顺序

### 7.1 原版本不是新的恢复框架

只改name也改变canonical_script_hash；原cursor/parent_execution_id与当前owner不同，Work报automation_task_source_changed，Executor fresh与cursor writer也继续阻断。handlers.resume_work还从最新owner取授权、context和hash；D41不能只删来源reader，恢复入口和writer都沿原cursor对应version/delegation。

已有automation_versions保原script/hash，但只保证 `(automation_id,version)` 唯一，hash不含授权；A→B→A或同script重新委托可出现同hash不同授权。**原Run/ready/Work source没有version唯一引用，version也没存原DelegatedAuthority**；更新覆盖唯一authority_snapshot，audit只有name/status/hash，不能重建原grant/schema/provenance。纯删hash比较并继承新权限会把旧目标装上新授权，按hash找最新version也不正确。

### 7.2 原执行消费与未来日期分开

基线pause会清claim，heartbeat中止直接Handler，既有Work又可能由自己的Scheduler继续；SELF发送的`social/service.py:138–139`另要求run.running / owner.active。D45 / D27 / D41要一起清这些plan状态/祖先终态连坐，已接纳run和合法活动后代沿原来源/原scope继续；真正本树取消仍撤新效果资格。本轮已实现并验收暂停只停未来调度（V19），没有新增paused_running等状态；本段保留基线删除理由。

pause/resume、run_now或update改了next_run_at后，旧S1即使完成也可能无人消费；D46补D25，让旧slot沿原事实收尾。也不能只改成永远读最早RUNNING：在原明示次数未耗尽的周期计划中，S1等待时合法新S2仍须实际接纳，之后S1信号到达再收尾，复用同Worker/claim，不新建并发器。

D47 是另一个接纳窗口：V1/S1 claim 提交后合法更新 V2/S2 或 cancel 清 claim，旧 Worker 仍可 create_run(S1)，甚至把当前 V2 hash 写进旧 ready，随后被原 owner CAS 拒绝而留下 RUNNING。heartbeat 创建后台 pulse 后直接让出，并不证明 create_run 前已有新握手。原短事务接回真正准备事实即可，不增加“完成前还要再验一次”的辅助门。D46 放宽旧 slot 消费必须与它一起核，不能让错误 V2 cursor 被当成 V1 原目标。

D17的问题不是普通分页：领取limit≥50（例如合法LLM concurrency64）、超过50个旧waiting run保留较早due、poll10秒越过5秒backoff时，头50每轮再次占满，尾部永远入选不了。默认LLM concurrency4实际头3就有同类风险，不能把默认每轮写成50。删N−1后留下无推进路径的50帽仍有饥饿；不要改成“waiting没资格调度”新封口。
