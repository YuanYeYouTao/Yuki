## 1. 结论

定位（用户已定，不再讨论）：

- Yuki 是长期存在的角色。她的"心"——主 Agent loop、记忆、会话、身份、凭据——留在沙箱外的 Bot 里（agent with sandbox）。
- 沙箱成为**她自己的电脑**：长期存在，由她改动，坏了能恢复。她用它过自己的生活（布置桌面、装东西、上网、做东西），也替本人做**轻量**工作。
- **重活交给本人自己的电脑**，走现有本机连接器（`use_coding_agent`），不在本稿范围；沙箱里不跑工作者 Agent。
- 保留现有运行时选择（安装器按 Docker 实际注册情况写入 `runsc` 或 `runc`），**不加内存**（生产 2 GiB 环境、4 GiB VM 不变；各档默认值不变）。
- **三档同等对待**：`lite`、`headless`、`desktop` 都是"她的电脑"。整机快照、回滚、从最新快照重建、环境级自启动在三档、两种运行时上都必须可用，包括最小的 `lite`。画面级自启动只在有画面的 `desktop`；闲置休眠在有浏览器的 `headless`、`desktop`，`lite` 没有。

本稿交付三件事：

1. **整机快照与回滚**：rootFS 与 HOME 卷作为一个一致的时间点一起保存、一起还原；保留 3 份滚动。
2. **自启动，桌面归她**：环境级和画面级两种自启动；系统只提供"显示器"（Xvnc）和 Yuki 的自动化 Chromium＋驱动，窗口管理器和桌面是她的。
3. **节律**：闲置 30 分钟自动休眠画面层，下次使用自动唤醒；Yuki 也能自己让画面休眠或唤醒。

## 3. 目标

- 她装的软件、她的桌面、她的文件和网站登录状态，能整体回到一个确定的时间点；容器丢了不再退回 11-11 的迁移检查点。
- 她能决定环境启动和画面启动时运行什么，不再需要守护脚本。
- 画面层不用时休眠，在 2 GiB／runsc 下降低整环境 OOM 的机会；需要时自己醒来。
- 三档、两种运行时行为一致，差别只来自"有没有画面／浏览器"这一真实事实。
- 不新增鉴权层，不改 Bot 的记忆、会话、Work 与回执事实。

## 4. 设计约束

- **整机，不是部分**：快照的单位是"这台电脑"。不提供只还原 HOME 或只还原 rootFS 的选项。
- **Bot 的事实不随电脑回滚**：记忆、会话、Bot 数据库、Manager 状态、运行与执行记录、只读媒体缓存、已交付 artifact（已冻结在 Bot）都不在快照内。网站侧的账号状态也不回滚。
- **快照不受环境内进程控制**：快照是电脑坏了或被污染后的恢复手段。环境里的 root 进程（包括网页诱导她跑的脚本）不能创建、删除或还原快照，否则 3 份滚动可以被连续新建冲掉。只有 Host 侧经核验的调用（Yuki 的工具调用、本人桌面端、Manager 自己的每日任务）能触发。
- **复用现有机制**：Supervisor 服务、`environment_mutations` 回执、`computer_revision` 通知、Client API 个人命令回执、`checkpoint_image` 重建路径。
- **配置是产品设置，不是完成门槛**：30 分钟、3 份、每日都写在 `.env`，可改；它们不进入任何接纳或成功判断。
- **闲置计时是短期信号**：按"刹车信号不重要，刹车的行为才重要"，只在 Manager 内存里，Manager 重启从零计，不持久化。

## 5. 设计

### 5.1 整机快照与回滚

**范围**

| 包含 | 不包含 |
| --- | --- |
| 容器 rootFS（`docker commit`，含 apt 装的软件、`/etc`、`/root`、`/workspace`／`/inputs` 符号链接） | Bot 记忆、会话、`data/` 与主库 |
| HOME 卷全部内容：`workspace/`、Chromium 资料（她的网页身份与登录）、收藏的表情、`.config`（含 `resolv.conf`、`~/.xsession`、Openbox 配置）、pip／npm 用户目录 | Manager 状态卷（`jobs.sqlite3`、快照记录本身、服务登记、回执） |
| | runtime 卷（运行记录、驱动请求、桌面状态文件） |
| | `/home/yuki/inputs/media-cache`（另一卷，只读） |
| | `sandbox-code` 卷（随 Bot 版本） |
| | 已交付 artifact（Bot `./workspace`） |

HOME 中的 `inputs/media-cache/` 在 Manager 视角只是空挂载点，仍显式排除。Chromium 资料中的 `Cache`／`Code Cache`／`GPUCache` 也排除（用户已定）：缓存会自行重建，与她的登录和网页身份无关，排除后每日增量明显变小。Cookie、Local Storage、保存的密码等其余资料照常保存。

**存储**

- rootFS：`docker commit --pause=false -c 'LABEL io.yuki.snapshot=<id>' yuki-environment yuki-environment-snapshot:<id>`。runc 与 runsc（`--overlay2=none`，`check_runtime()` 已强制）都把写入落在 Docker 可写层，commit 能拿到。同一容器的每次 commit 都是"自容器创建以来的完整差异"，与底层镜像共享层。
- HOME：新的 external 卷 `yuki-sandbox-snapshots`，**只挂给 Manager**（不挂环境、不挂 Bot）。每份快照一个目录 `<id>/`，用 `rsync -aHAX --numeric-ids --delete --link-dest=../<上一份>/` 从 Manager 的 HOME 挂载复制。未变化的文件与上一份硬链接，只占一次空间；rsync 先写临时文件再改名，旧快照里的 inode 不会被改写。
- 运行时镜像（Bot 与 Manager 同一镜像）`Dockerfile` 增加 `rsync`。环境镜像不需要。
- 快照记录在 Manager `jobs.sqlite3` 新表 `environment_snapshots`：`id`、`request_id`（唯一）、`source`（`daily`／`yuki`／`person`）、`actor`（person_id／device_id／label，或 Work ID 与工具调用键）、`note`、`state`（`creating`／`ready`／`failed`）、`image`、`point_at`（暂停时刻）、`container_id`（代际）、`sizes`、`pause_seconds`、`error`。记录属于 Manager 状态，不随回滚变化。

**创建（三种来源同一流程）**

1. 按 `request_id` 查已有记录：同键返回原结果；有另一份 `creating` 或一次未结束的还原时返回 `snapshot_in_progress`／`restore_in_progress` 及其原请求 ID，不排第二份。
2. 写 `creating` 记录（短事务）。
3. 取 `ComputerRuntime.lock`（截图与输入动作排队等待，不会与快照交错），并在 Manager worker 中串行执行，期间 worker 不派发新的终端执行（新 `run_command` 照常入队，状态 `queued`，快照结束后派发；不拒绝、不产生未知）。
4. `docker exec yuki-environment sync`，再 `docker pause`。
5. 暂停期间：commit rootFS；rsync HOME 到 `<id>.partial/`，完成后改名为 `<id>/`。
6. `docker unpause`（`finally`）。记录 `ready`、`pause_seconds`、各部分大小；`checkpoint_image` 指向这份镜像。
7. 轮换：`ready` 超过保留份数时删最旧的一份（先删记录对应的 HOME 目录，再 `docker image rm` 其标签）。**只在新快照 `ready` 之后才删旧的**；创建失败不删任何旧快照。

暂停期间画面冻结，已运行的终端进程冻结后继续；显式 `timeout_seconds` 按墙钟可能因暂停提前到期，如实记录。Manager 在暂停中崩溃：`recover()` 看到容器 `State.Paused` 先 unpause，未完成的 `creating` 记为 `failed`，删 `.partial` 目录与已打的标签。

**变化判断（每日快照用）**

"自上一份快照以来有变化"按事实判断，不按活动推测：

- HOME：Manager 在自己的挂载上找第一个 ctime 晚于上一份 `point_at` 的条目（排除 `inputs/media-cache` 与 Chromium 缓存）。
- rootFS：在环境内用一段 Python 遍历 `/`，跳过 `/proc/self/mountinfo` 列出的所有挂载点和其他文件系统，找到第一个即停。P0 实测：`find / -xdev` 仍会报告挂载点目录本身（HOME 变化让 `/home/yuki` 的 ctime 变化，`/tmp` 同理），所以不用 `-xdev`。
- 用 ctime：新建、修改、删除（父目录 ctime 变化）、改属性都会推进 ctime，`touch -d` 改不了它。runc 与 runsc 实测一致（第 19 节）。
- 没有任何快照时视为有变化。

**每日**

- worker 每轮检查：距最新一份 `ready` 快照（任意来源）已满 `YUKI_SANDBOX_SNAPSHOT_INTERVAL_HOURS`（默认 24），且距上次每日检查也满该间隔（`environment_state.snapshot_daily_checked_at`）。
- 满足时做变化判断：有变化就以 `source=daily` 创建；没变化只记检查时间，不占名额。
- 本人正持有控制权时推迟到交还后（不冻结本人正在操作的画面）；这是排程，不是门槛，交还后照常进行。

**回滚（还原）**

1. 按 `request_id` 查原记录：同键返回原结果或当前进度。另一次还原或快照未结束时返回其原请求 ID，**不开始第二次**。
2. 写 `environment_restores` 记录：`request_id`、`snapshot_id`、`actor`、`state`（`accepted`／`done`／`failed`）、开始与结束时间、新代际。写入即接纳；之后的步骤都向这一目标收敛。
3. 取 `ComputerRuntime.lock`，`ready=False`。
4. `docker stop`、`docker rm` 原容器。
5. `rsync -aHAX --numeric-ids --delete <id>/ → HOME`（排除 `inputs/media-cache/`）。
6. `checkpoint_image` 设为该快照镜像，调用现有 `recover()` 创建并启动新容器；`apply_programs()` 照常补齐当前档位缺的包。
7. 旧代际的活动执行由现有代际检查结束为 `failed`，`interrupted: true`，错误码 `environment_restored`（附 snapshot_id），不重放、不重派。完成回执照常经 outbox 送到原 Work。
8. 记录 `done`，`computer_revision` 加一并通知订阅者。

Manager 中途重启：`recover()` 发现未结束的还原记录，先完成第 4–6 步再创建环境。容器删除与 rsync 都是向同一快照收敛的操作，继续执行是完成原请求，不是重做；**绝不在 HOME 还原到一半时启动环境**。

不自动在还原前额外拍一份：那会悄悄挤掉一个名额，甚至挤掉要还原的那份。确认界面与工具说明告诉调用者"快照之后的改动会丢失，需要的话先手动拍一份"。

**还原的事实边界**

- 还原后 Bot 中引用了 HOME 文件、但文件在快照时还不存在的记录（例如之后收藏的表情），使用时按真实"文件不存在"报告，不重新下载、不改写原记录。
- 网站侧状态不回滚：在网站上已发生的发帖、改密码、退出登录都保留；本地 Chromium 回到快照时的 cookie，网站可能要求重新登录。
- Chromium 的 `SingletonLock`／`SingletonSocket` 随资料一起恢复，与今天 OOM 重启后的情形相同；在 E2E 中核对能正常启动（失败情况 S16）。实测：Chromium 正常启动并改写锁，cookie 与登录回到快照时；因为快照拍下的是运行中的资料，有头 Chromium 会像 OOM 重启后一样显示“Chromium 未正确关闭，恢复页面？”，页面由她或本人点“恢复”。

**容器丢失时从最新快照重建**

- `checkpoint_image` 始终指向最新 `ready` 快照的镜像，所以 `recover()` 遇到容器不存在时自然用它创建，不再回到迁移检查点。
- 只有 rootFS 丢了，HOME 卷还在：**只恢复丢失的部分**，HOME 保持当前内容。环境状态报告 `recreated_from: {snapshot_id, point_at}`，Yuki 能知道那之后装的软件需要重装。
- 快照镜像被手动删除而记录还在：创建失败按现有 `environment_create_failed` 报告，不静默回退到别的镜像（失败情况 S12）。

**镜像清理**

- 正在运行的容器所基于的快照镜像不能删标签（Docker 拒绝删除运行中容器使用的镜像）。轮换到它时只删记录和 HOME 目录，镜像留着；`recover()` 时清理所有带 `io.yuki.snapshot` 标签、既不在记录中也不被当前容器使用的镜像。它的层本来就被当前容器占用，不额外占盘。
- 迁移检查点 `yuki-environment:migrated-20261111131841` 在容器第一次从快照重建后由运维删除标签（第 9 节）。
- 每次从快照重建会在镜像层链上加一层；回滚很少，记录层数，不设上限（P0 记录）。

**runsc 与 runc**

| | runc | runsc（`--overlay2=none`） |
| --- | --- | --- |
| rootFS 写入位置 | Docker 可写层 | 同左（`check_runtime()` 已保证） |
| `docker pause` | cgroup freezer | P0 实测 `runsc pause` |
| 写入可见性 | 宿主页缓存 | directfs 下经宿主 FD 写入；`sync` 后 commit／rsync 可见性 P0 实测 |
| ctime | 原生 | P0 实测 |
| OOM | 只杀超限进程，快照不受影响 | 整个环境退出；若发生在快照暂停期间，按"Manager 崩溃中"同一路径处理 |

P0 中任一项在 runsc 下不成立，回到本稿决定，不在实现中临时放宽。

**三档**

快照、回滚、重建在三档完全相同；差别只是内容大小（第 10 节）。`lite` 环境里没有 Chromium 资料，HOME 一般最小。所有重活（commit、压缩、rsync）在 Manager 与 Docker 守护进程里做，**不占环境的内存限额**；环境内只跑一次 `sync` 和一次 `find -print -quit`，`lite` 的 512 MiB 与 PID 256 都够。

### 5.2 自启动：桌面归她

**环境级（三档）**

- 约定文件 `/etc/rc.local`（rootFS，属于她的电脑，随快照保存）。这是没有 systemd 时"开机自启"的通行约定，模型熟悉。
- Manager 每个环境代际提交一次 Supervisor 服务执行（与 `yuki-desktop` 同一 Supervisor 机制），请求键 `autostart:<代际>`（实施修订：不登记为 `environment_services` 中的 `restart=on-failure` 服务，因为以 0 结束的运行保持 `succeeded`，环境重启时只有进行中的执行被记为 `environment_stopped`，`restore_services()` 不会再跑它；按代际的请求键不改 `restore_services()` 语义，也不新增重启策略）：

  ```
  [ -e /etc/rc.local ] || exit 0
  /bin/sh /etc/rc.local > /var/log/rc.local.log 2>&1
  echo "exit $?" >> /var/log/rc.local.log
  exit 0
  ```

  同一代际的请求键返回原执行，所以同一代际内不重复运行；新代际（runsc OOM、还原、VM 重启）有新的请求键，恰好再跑一次。**不改 `restore_services()` 语义，不新增重启策略。**
- 输出重定向到日志文件，她用 `&` 起的后台进程不占 Supervisor 的输出管道，脚本退出后它们由 `docker-init` 收养继续运行。真实退出码写在日志末行。
- Manager 重启不触发（环境没有重启）。同一代际内想立即生效，她在终端直接运行即可。
- 现有 `sandbox-dns` 是运维登记的系统服务，保持不变，不算她的自启动。
- 不恢复 `environment_service` 模型工具。

**画面级（`desktop`）**

`desktop_service.py` 的子进程分三类：

| 类别 | 内容 | 归属 | 退出时 |
| --- | --- | --- | --- |
| 显示器 | Xvnc `:1` | 系统 | 整个服务结束，Supervisor 按 on-failure 重启 |
| 会话 | `~/.xsession`（存在时以 `/bin/sh ~/.xsession` 运行），否则 `openbox-session` | 她 | 不结束显示器，不自动重启；状态文件记 `session: exited`＋退出码 |
| 自动化浏览器 | Chromium＋驱动 | 系统 | 只重开这两者（现有行为） |

- 启动顺序不变：Xvnc 就绪 → 会话 → Chromium（让窗口管理器先在，Chromium 窗口被它管理）。
- 会话环境：`DISPLAY=:1`、`HOME=/home/yuki`、cwd `/home/yuki`；标准输出与错误写 `~/.xsession-errors`（X 的通行约定）。
- **没有 `~/.xsession` 时用 `openbox-session` 而不是 `openbox`**。理由：Openbox 已在有头镜像里（`environment_programs.py headed`），`openbox-session` 是它自带的会话入口，会执行 `/etc/xdg/openbox/autostart` 与 `~/.config/openbox/autostart`。她已经写好的自启文件不用任何迁移就生效；不预装完整桌面环境，换 xfwm、LXQt 之类由她自己装、自己写 `~/.xsession`。
- 会话退出不再结束服务：这改变 e61e9575 中"Openbox 退出即结束整个服务"。窗口管理器现在是她的，她换窗口管理器或注销都不应杀掉显示器和 Yuki 的浏览器。要重开整个画面就用 sleep＋wake。
- `desktop-status.json` 增加 `session`（`running`／`default`／`exited:<code>`），经 `display_status` 与 `get_environment` 返回。
- `headless` 没有 X，不运行会话；`lite` 没有桌面服务。

**退役 `desktop_guardian.sh`**

- 它在她的 HOME 里，本稿**不删除、不停止**它，也不改她的任何文件。
- 新版本上线后，下一次唤醒画面时她的 `~/.config/openbox/autostart` 会启动 `feh` 和 `tint2`。守护脚本仍在运行时可能多出一个 `tint2`（失败情况 A7）。
- 提示词与环境说明告诉她现在有自启动；由她自己停掉并删除守护脚本，必要时把 `/root/.config/tint2/tint2rc` 与 HOME 中的副本合并。

### 5.3 节律：闲置休眠与唤醒

**什么算"在用"**（Manager 内存中的 `last_activity`）

- Yuki 对自己环境的任一 `computer`／`browser` 调用（读或输入）结束时；
- 有任何一路 `display_stream` 打开（包括桌面端检查器的紧凑预览）期间，以及最后一路关闭时。桌面端窗口隐藏或最小化时断开它的画面流，重新显示时再连（用户已定），所以只有本人真的看得见画面才算"在看"；
- 本人持有控制权（`holder=human`）期间；
- 每次 wake。

终端命令不算：`run_command` 跑在环境层，休眠不影响它。用终端以 `DISPLAY=:1` 起的图形程序会随显示器一起结束（见下）。

**休眠**

- 画面在运行，且 `now - last_activity ≥ YUKI_SANDBOX_DISPLAY_IDLE_MINUTES`（默认 30，`0` 表示不自动休眠）时，worker 在 `ComputerRuntime.lock` 下执行与 `display_sleep` 相同的停止（`service stop yuki-desktop`），回执键 `idle:<当前 yuki-desktop run_id>`，写入 `environment_mutations`，`computer_revision` 加一。
- 停止的只有画面层：Xvnc、会话、Chromium＋驱动。X 客户端（`tint2`、`feh`、她的图形程序）在显示器消失时自行退出。环境、终端执行、后台进程、`rc.local` 起的守护进程、`sandbox-dns` 都继续运行。
- Manager 重启时 `last_activity` 取启动时刻，最多推迟一个闲置周期，不持久化。

**三档**

| | `desktop` | `headless` | `lite` |
| --- | --- | --- | --- |
| 休眠停止什么 | Xvnc、会话、Chromium、驱动 | 无头 Chromium、驱动 | 不存在（没有桌面服务） |
| "在用"信号 | 工具调用、画面流、本人控制 | 只有 `browser` 调用（没有画面流；本人控制在此档没有意义） | — |
| 唤醒 | 下次 `computer`／`browser` 或 wake；画面级自启恢复她的桌面 | 下次 `browser` 或 wake | — |
| `computer(sleep/wake)` | 有效 | 有效，作用于无头浏览器 | `browser_unavailable` |

**唤醒**

- 自动唤醒沿现有 `_ready()` → `display_wake`，不变。
- 新增 Yuki 显式 `computer(action="wake")`／`computer(action="sleep")`（第 6 节）。本人桌面端的唤醒／休眠保留。

**标签页、Work 与回执**

- 闲置休眠必定在没有动作进行中时发生（持有 `lock`，且已闲置 30 分钟），不会打断一次输入，不产生新的 `unknown`。
- Chromium 收到 SIGTERM 正常退出，以 `--restore-last-session` 在下次唤醒时恢复标签页：网址、cookie、登录保留，页内未提交的状态（表单输入、滚动、脚本状态）丢失，tab id 改变。
- 标签页→Work 归属只在驱动内存，恢复后为 `unknown`。未完成的 Work 下次用旧 tab id 时得到现有的 `tab_not_found`＋当前标签页清单，据此重新选择；不重放任何已确认或未知的输入。
- 闲置休眠与 Yuki 的 `sleep` 回执中附休眠时的 `tabs.json`（含 Work 归属），作为"当时开着哪些页"的原事实。
- 闲置休眠不因存在未完成 Work 的标签页而跳过：Manager 读不到 Work 状态，而一个等待数天的 Work 会让画面永远不休眠——那会把辅助状态变成门槛。本人桌面端休眠的 `confirm_sleep()` 确认流程保留不变。
- Yuki 的 `sleep` 不要求 `confirm_active_work_tabs`：是她自己在决定；本人正持有控制权时返回 `control_held`。

## 10. 资源与磁盘

**内存**：不改任何档位的限额。快照的 commit、压缩、rsync 在 Docker 守护进程与 Manager 中进行，计入 VM（本机 4 GiB 共用）而不计入环境限额；rsync 约数十 MB。环境内只有一次 `sync` 和一次 `find`。闲置休眠在 `desktop` 档释放画面层（本机醒着时环境共 652 MiB，其中 Xvnc 约 250 MB RSS、Chromium 多进程占大头），在 runsc 下直接降低整环境 OOM 的机会；`headless` 释放无头 Chromium。

**磁盘**（与 Bot 数据共用一块盘，`disk_status` 已标明共享）：

| 档位 | 每份 rootFS 成本 | HOME 成本 | 3 份估算 |
| --- | --- | --- | --- |
| 公式 | 自容器创建以来的可写层差异 × 约 1.5–2（containerd 存储同时保存压缩 blob 与解包快照） | 第一份＝HOME 全量；之后每份＝变化文件 | 3 × rootFS 差异 × 2 ＋ HOME ＋ 2 × 日变化 |

## 19. P0 实测结果与实施偏差（2026-11-14）

### P0 实测

在临时 Colima VM（aarch64，2 CPU、3 GiB，Docker 29.5.2，containerd 镜像存储，gVisor `release-20261109.0` 以 `--overlay2=none` 注册）上，用 `debian:bookworm-slim` 与本分支构建的 `yuki-environment`／`-desktop` 镜像实测；命令与输出留在本地暂存（未入库）。

| 项 | runc | runsc（`--overlay2=none`） |
| --- | --- | --- |
| 1. `docker pause`／`unpause`；暂停中 `docker commit --pause=false` | 可用；commit 成功 | 同左 |
| 2. 环境内写入后 `sync`，宿主 commit 与 Manager 一侧 rsync 是否看到最新内容 | 两者都看到 | 同左（directfs） |
| 3. ctime：新建、修改、删除、`touch -d`、`chmod` | 都推进 ctime（新建、删除体现在父目录）；Manager 一侧看 HOME 卷同样 | 同左 |
| 3 补充：`find / -xdev` | **仍报告挂载点目录本身**：HOME 里新建／删除文件让 `/home/yuki` 被报告，`/tmp` 同理 | 同左 |
| 5. 删除运行中容器所基于镜像的标签 | Docker 拒绝（`conflict … must be forced`），容器照常运行 | 同左 |
| 5. 层数 | 基础 1 层，连续两次从快照重建后 3 层（每次加一层） | 同左 |
| 6. Chromium 从运行中拷贝（带 `SingletonLock` → `yuki-environment-<pid>`）的资料在新容器同名主机上启动 | 正常启动并改写锁（Chrome 156） | 同左 |
| 7. `openbox-session` 在 Xvnc 下执行 `~/.config/openbox/autostart`；Xvnc 退出 | autostart 运行（标记文件与 `xmessage` 窗口）；Xvnc 退出后 openbox 与 xmessage 都退出 | 同左 |

第 4 项（暂停秒数、每份大小、快照卷占用）与第 8 项（GitHub runner）由 `sandbox-compose` 的 `snapshots-<档位>.json` 记录，见下文“E2E 与 CI”。

结论：P0 全部与设计假设相符，除 `find -xdev` 一项：rootFS 变化判断改为在环境内跳过 `/proc/self/mountinfo` 的全部挂载点（见 5.1“变化判断”），否则 HOME 或 `/tmp` 的变化会被当成 rootFS 变化（不影响“是否有变化”的并集结论，但 `/tmp`、代码卷与 runtime 卷的变化会让每天都“有变化”）。

### 实施偏差（均已就地修订正文）

1. **环境级自启动不登记为服务**：以 0 结束的 `restart=on-failure` 运行保持 `succeeded`，环境重启时只有进行中的执行被记为 `environment_stopped`，`restore_services()` 不会再运行它。改为每个代际提交一次服务执行，请求键 `autostart:<代际>`；不改 `restore_services()`，不新增重启策略，环境里也不常驻进程。
2. **快照与还原的回执就是它们自己的记录**：`environment_snapshots.request_id`、`environment_restores.request_id` 唯一，同键返回原记录或当前进度；不再在 `environment_mutations` 另写一份（`control_request_get` 同样查到它们）。`wake`／`sleep` 与闲置休眠照原设计写 `environment_mutations`。
3. **轮换保留记录**：被轮换的快照记为 `rotated`（HOME 目录与镜像标签已删），这样原请求键重试仍得到原记录而不是新建一份（S1）。新快照记录 `rotated` 列出被它挤掉的那份。
4. **`VOLUMES` 不加 `snapshots`**：`VOLUMES` 是挂进环境的卷名；快照卷只由 Compose 挂给 Manager（`/var/lib/yuki-sandbox-snapshots`），不进环境。
5. **桌面端的快照／还原请求写入即返回**：`POST /computer/snapshots` 返回 `state: creating`，`POST /computer/restore` 返回 `state: accepted`，进度经 `computer_revision` 与 `GET /computer`；Yuki 的工具调用则等到结束，返回 ready 记录与被轮换掉的那份。`GET /computer.snapshots` 每项另含 `state`（creating／ready／failed）与失败时的 `error`。
6. **`sleep` 与闲置休眠等到画面层真实停止**再写回执（上限与唤醒等待相同），回执中的 `display`／`browser` 是停止后的事实。
7. **镜像清理只在本次恢复新建了容器时做**：Manager 单独重启（环境未变）不调用任何 Docker 命令。
8. **`.env.example` 原把 `YUKI_SANDBOX_RUNTIME=runc` 写死**，安装器因此从不选 runsc（先于本稿的缺陷）；改为留空注释，安装器按 Docker 实际注册情况写入。
9. **提示词不写保留份数**：第 8 节要求数值留在工具说明与 `get_environment`，【我的电脑】写“只保留最近几份”。
10. **测试夹具中的默认值**：`PersistentManager` 构造参数里每日间隔与闲置分钟默认为 0（不自动），由 `manager.py` 按 `.env` 传入 24／30；测试显式打开，避免无关测试触发 Docker 命令。
11. **还原未能完成时的再试**：还原向同一快照收敛；一次尝试失败后，下一次跟随 worker 原有约 15 秒的恢复节奏，不在 0.5 秒循环里反复执行 rsync。
