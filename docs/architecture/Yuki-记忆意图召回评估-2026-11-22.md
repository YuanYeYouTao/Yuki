# 记忆意图召回：现状评估与两项改进（2026-11-22）

基线 `d1440c0a`（生产镜像 `db51c147`，schema `0165`）。所有者批准两项改进：画像下的“可查话题”与
`search_memory` 词法排序。现行合同写在[检索合同](memory-v2-retrieval.md#查询与排序)与
[人物画像](memory-v2.md#人物画像)；本文保留当时的证据、数字与取舍。

生产数据只读（`mode=ro`、`query_only`、逐行流式、只输出聚合数字），正文、人名、查询原文都没有离开容器；
下文只给统计与抽象类别。离线评估用真实查询向量（DashScope，471 次 query embedding），对全部 1585 条 active
事实检索，不按请求者授权收窄（新旧两边相同），所以命中数只用于新旧比较。

## 1. 现状评估

### 1.1 检索怎么切中文、怎么排序

- **词法**：`memory_facts_fts` 是 FTS5 `tokenize='trigram'`，列为 content / memory_key / category，
  bm25 权重 1 / 4 / 2。查询 NFKC + casefold 后按 `[^\W_]+` 切段：三字及以上的段拆成滑动三字组 OR 进 MATCH；
  不足三字的段走 `LIKE '%t%'`（content / key / category），**按 fact ID 升序取前 51 条**、分数一律 1000。
  经历标题、主人的名字都不可搜。
- **向量**：`qwen3.7-text-embedding`（1024 维 dense，带 query instruct），Vec1 在授权子查询内取前 50，
  不设相似度阈值。
- **融合**：代码在 RRF（k=60，权重 1:1）之前先按 `relevance_band = int(余弦 × 20)` 分档（key / content
  与查询全等为 21 档），RRF 只在同一档内排序。于是向量分数实际决定顺序：不在向量前 50 的词法候选
  分数为 0 档，永远排在 50 个向量候选之后；默认只返回 4 条。现行文档写的是“既有 RRF 合并排序”，
  这一档没有写进合同。
- **过滤**：SQL 授权、active、未隔离、未过期、严格时间范围；结果不另做去重。

对中文短查询的影响（1585 条 active，事实与查询都来自生产库，构造方式见 §3）：

| 查询 | 现行 hit@4 |
|---|---|
| 二字话题词（库内少见的二字词） | 39%（51/130） |
| 三字话题词 | 53%（68/129） |
| 人名 + 空格 + 二字词 | 30%（22/74） |
| 人名 + 的 + 二字词（连写） | 28%（21/74） |

原因：话题词本身在库里精确出现，但短查询的向量相似度低、分档靠后，被 50 个“语义相近”的候选挤出前 4；
人名查询还有第二个缺口：529 条人物事实里 240 条（45%）正文不含主人的名字，词法上搜不到；
连写的“人名的词”在旧切法下只剩跨词三字组，几乎不命中。“的”“我”这类单字走 LIKE，按 ID 升序截断，
单字查询会挤占二字词的候选窗口。

## 2. 改进一：画像下的“可查话题”

**做法**：人物画像的每个版本多存至多 4 个话题词（每个至多 8 字），各带依据 fact。私聊渲染对方两份画像的
话题，群里每位名单成员只渲染公共画像的话题，各占一行 `- 可查话题：A、B、C`，紧跟该画像条目。依据规则
加一句：话题与当前话题相关时可以 `search_memory`。

**为什么用模型而不是确定性聚合**：所有者优先确定性聚合，但生产数据不支持：

- `memory_key` 是英文蛇形标签且几乎一事一键（1584 条 active 有 1541 个不同的 key），拆词后最常见的是
  `preference`、`yuki`、`identity`、`for`、`with` 等无区分度的词；有区分度的部分是英文专名。
- `category` 只有 preference / interest / identity 之类的粗类，且中英文混用。
- 从正文聚合中文词需要分词（见 §3 的代价）；纯 n-gram 频次会得到跨词碎片。
- key 里有健康、亲密关系、作息一类的标签词，确定性聚合无法执行画像已有的“不写健康、性、财务类”规则。

所以话题由**画像维护的同一次调用**输出（`ProfileOutput.topics`），不新增调用：模型本来就看到该画像全部可用
事实，输出时引用 `f_N`，程序按画像条目的同一套规则校验与渲染复核。

**可见范围**：话题与条目同一套证据规则——公共画像的话题只能引用公共可用事实，私人画像的话题只能引用本人
私聊来源事实；渲染时每个话题的每个编号沿后继解析并复核，任一不过整条不显示。群里只出现公共画像的话题，
私聊来源的话题只进本人私聊。

**节奏与缓存**：话题存在画像版本快照里，只在 Dream 收尾（模型维护、程序清理）或所有者 CLI 写版本时变化；
渲染在 system 末尾常驻段，不进当前消息，不新增语句（与条目同一条版本查询、同一批复核）。已有版本没有话题
（`topics_json IS NULL`）的画像在下次 Dream 被维护名单覆盖时到期一次，补上话题；之后照旧按签名到期。

**篇幅**：上限为公共 4 个 + 私人 4 个话题。实测（`test-results/memory-recall/T6-length.json`，
四字话题、各画像填满 4 个）：所有者私聊（对方两份画像）增加 2 行 54 字；主群（名单 5 人）增加 5 行 135 字。
话题少或画像未生成时按比例减少；生产现有画像 10 份、群名单尚未生成，部署后的实际字数以
`yuki memory profile show` 与常驻段渲染为准。

**替换与删除**：没有新开小节、新开表或新开调用；版本快照加一列。群核心集与经历目录不加话题：群事实只有
27 条（核心集已常驻 10 条），经历已有标题目录；离开窗口的经历只在有离开者时才进比较调用，看不到全量归档，
硬加话题需要新调用，留作后续。

## 3. 中文 n-gram 切词的代价与取舍

参考实现（SuInk/Diana `cd37d828`）：查询侧切一/二/三字组（权重 0.18 / 1 / 1.25），候选池内统计文档频率
算 IDF，按字段加权（实体 1.55、主题 1.45、键 1.3、正文 1、证据 0.72），有成词时只命中单字的候选得 0 分，
提到的人 +0.12，Jaccard MMR 去重，命中回写时间配合软衰减；词典分词（gse）可选，源码注释写明常驻约 129 MB
（简体）/ 197 MB（全量），默认关闭。

本机基准（Apple Silicon，Python 3.12，合成 Zipf 中文文本，55% 35 字事实 + 45% 275 字经历，与生产比例相近；
脚本随 PR 附在 `scripts/memory_lexical_benchmark.py`）：

| 规模（active 事实） | 常驻 n-gram 倒排（Python） | 旧词法 SQL p50 / p95 | 新词法 SQL p50 / p95 | 候选池打分 p50 / p95 |
|---|---|---|---|---|
| 1.6k | 构建 0.35 s，常驻 111 MB | 0.03 / 0.35 ms | 1.1 / 4.3 ms | 0.2 / 0.8 ms |
| 5k | 1.4 s，337 MB | 0.05 / 1.1 ms | 3.5 / 13.5 ms | 0.2 / 0.9 ms |
| 20k | 5.8 s，1.2 GB | 0.08 / 4.3 ms | 15 / 55 ms | 0.3 / 1.0 ms |

生产只读重放 82 条真实查询（同一库、同一批查询）：词法 SQL 由 1.4 / 2.5 ms（p50 / p95）变为
2.4 / 4.4 ms；近 14 天 100 次带 query 的 `search_memory` 工具耗时 p50 587 ms、p90 1103 ms（主要是
query embedding 网络请求），新增约 1–2 ms。

**结论**：不做词典分词，不建常驻倒排（百 MB 起步，违背“常驻大内存”的否决条件）；只做查询侧切词：
三字组照旧走 trigram 索引，二字组（以及整句只有单字时的单字）走一条带权 LIKE 扫描，IDF 只在候选池里算。
每次 `search_memory` 多约 1–2 ms，无常驻内存。扫描随 active 事实线性增长（2 万条时 p95 约 55 ms），
到那个量级时应改为二字组 FTS 表。

## 4. 改进二：search_memory 排序

采纳：

1. **查询侧切词与字段加权**：同上；字段为主人名字（人物显示名、并入人物与别名，群事实为群名）1.55、
   经历标题 1.45、key 与 category 1.3、正文 1。不含证据摘录：证据可能来自本会话不可见的来源。
2. **有成词时忽略单字**：查询里有二字及以上的词时，只命中单字的候选不算词法候选（仍可经向量进入）。
3. **人名进候选**：查询里的词出现在某人的名字里时，那个人（同一人族）的事实也进扫描候选窗口。
4. **删除 `relevance_band`**：最终顺序回到合同写的 RRF；key / content 与查询全等仍排最前。

离线评估（hit@4 / MRR@10；A 为现行，D 为采纳方案）：

| 查询集 | A 现行 | B 只删分档 | C 只换词法 | D 采纳 |
|---|---|---|---|---|
| 二字话题词（130） | 39% / 0.30 | 100% / 0.89 | 39% / 0.30 | **100% / 0.88** |
| 三字话题词（129） | 53% / 0.46 | 100% / 0.90 | 53% / 0.45 | **99–100% / 0.88** |
| 人名 + 空格 + 词（74） | 30% / 0.25 | 20% / 0.13 | 46% / 0.36 | **55% / 0.47** |
| 人名的词（连写，74） | 28% / 0.24 | 18% / 0.14 | 38% / 0.33 | **55% / 0.49** |
| 生产查询银标（8） | 6/8 / 0.53 | 5/8 / 0.54 | 6/8 / 0.42 | 5/8 / 0.36 |

银标是“当时返回且被回复用上的事实”，只来自现行系统自己的前 4，样本仅 8 条，任何改动在这里只会持平或下降；
丢的一例是向量第 4、词法分低的事实被两条“词法第一、向量第 13/15”的候选挤到第 8。82 条真实查询的前 4 里，
只命中单字的词法候选为 0；近重复对（二字组 Jaccard ≥0.6）现行 2 对、新方案 0 对。
两次运行间 query 向量有微小浮动，个别名次相差 1。评估脚本 `scripts/memory_recall_offline_eval.py`（随 #703 附带，之后删除，见 git 历史）
在容器内只读运行、只打印聚合数字；查询集由生产库现场构造，复核需生产只读权限。

代码上删除：`relevance_band` 分档、旧切词 `build_safe_lexical_query` / `SafeLexicalQuery`、按 ID 升序的
LIKE 回退、`rank_lexical` / `rank_hybrid` 两段排序（合成一次 RRF）、无人读取的 `MemoryLexicalCandidate`、
`AuthorizedLexicalCandidate`、命中项的 `matched_terms` / `exact_match` 字段、按目标路径的原始 SQL 拼接与
`strict_time_sql`；按目标与全局两条路径共用同一套候选语句与打分。

不采纳：

- **MMR 去重**：上面的近重复几乎为零（Dream 已合并重复），去重只增加一个阈值。
- **按当前消息 @ 的人加权**：搜记忆的轮次只有 4/96 @ 了别的成员；查询里写了名字已由第 3 项覆盖，
  要限定某人时模型可传 `target`。
- **命中回写与软衰减**：`search_memory` 是纯读取，现行合同明确“被想起不等于更重要”。
- **每轮强制注入**：所有者约束。

## 5. 性能与部署

- 每轮渲染：话题与画像条目同一条版本查询、同一批复核，语句数不变（用例断言）。
- Dream 收尾：到期判定在原有一次画像查询里多取一列；程序清理对条目与话题一次批量复核。
- `search_memory`：多一条名字查询（persons / person_aliases / spaces，按 `IN` 批量）与一条扫描语句，
  语句数为常数；EXPLAIN 不 SCAN 大表（用例断言）。
- 迁移 `0166`：`memory_profile_versions` 加 `topics_json`（可空）；已有版本保持 NULL。
- 依据规则加一句，它在恢复合同哈希范围内：部署当次在途 Work 换链一次。
- 首个 Dream：被维护且没有话题的画像各到期一次（生产现有 10 份画像，受每次运行 24 个主人上限约束）。
