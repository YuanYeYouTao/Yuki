## 2. 已定决定【决定，用户】

1. 两层。确定性、只读的事实检查周期运行，不花模型费；只有发现**新**问题时才激活 Yuki。
2. 投递沿人物的主动消息路由（`person_active_routes`，Desktop「主动消息发送入口」设置，`client_api/routes.py`、`identity/routing.py`）。收件人是有超管资格的 Person。“Yuki 主动发起一次私聊”设计为可复用入口，看门狗是第一个来源；本轮范围只做看门狗需要的部分。
3. Yuki 在那个私聊里用自己的话告诉主人（一次 Main 激活，事实作为本轮运行资料），说明情况并建议处理方式。**只汇报**：恢复、取消、改配置等管理动作只在主人于普通轮次同意后、以主人自己的授权执行。看门狗来源本身不获得管理权。
4. 只报问题，没有每日摘要。同一问题只说一次；清除后再次出现才再说。其他时候安静。
5. Bot 宕机检测（Bot 不能报告自己的死亡）本轮不做。
6. 不做“轻路由”重构；Yuki 继续自己做真实工作。
7. 抖动合并：一个 issue_key 清除后在 `no_progress_seconds` 内重新出现，视为同一次出现，不再通知（§4.4）。
8. 每人通知最小间隔 `watchdog.notify_min_interval_seconds`（默认 1800）：期间的新问题累积，到时合并为一次通知；最坏每人每天 ≤48 次激活（§4.6）。

## 4. 设计

### 4.1 总体

```
WatchdogChecker（只读事实检查，周期运行，无模型费）
   │ 发现的问题集合（内存）
   ├─ 与 watchdog_issues 已开放行比对（reader）
   └─ 有变化才短写：新问题插行、已清除的问题删行
          │ 有未告知的新行
          ▼
ProactivePrivateTurns（可复用入口；来源 = watchdog）
   人物 → 主动路由 → 私聊会话 → 一次 Main（SELF 主体、只汇报）
   本轮资料 <runtime_context>.watchdog = 当时仍开放的问题事实
   Yuki 用 send 告诉主人
```

- 位置：检查器放 `application/`（应用运行时层，组合健康面与各领域只读查询）；入口放 `services/proactive_turns.py`；各领域的只读事实查询放在各自领域（例如委派事实在 `external_agents/delegation.py`，协议存储事实在 `runtime/protocol_store.py`），检查器不扫描其他领域内部表猜结论（`development-contract.md` §5）。
- 生命周期：在 `container.py` 装配，作为一个带健康钩子的 lifecycle 条目启动；关闭时取消循环与在途通知任务。
- 依赖方向不变：入口与检查器 → 领域服务 → 仓库。

### 4.2 第一层：事实检查器

- 每 `watchdog.check_interval_seconds`（步调参数，§4.9）跑一次。全部读取在 `read_session()` 中完成，每项有界、走既有索引；内存健康直接调用已有的 `health()`/`runtime_status()`，不重复查询。
- 产出：`{(person_id, issue_key): facts}`。`issue_key` 由持久内部 ID 或组件名构成，重启后稳定；`facts` 只含 ID、状态、原因、计数、时间（§4.6 隐私）。
- 每个问题有三态：**存在**、**健康**、**未定**。只有观察到“健康”才清除；“未定”（例如重启后内存健康尚未经过步调间隔、网关刚启动尚未连上）既不开新问题，也不清除旧问题。这避免“重启 → 误判清除 → 再次出现 → 重复通知”。
- 比对在 reader 里做完：读出 `watchdog_issues` 已开放行，和本次结果求差。没有差异就不取 writer（`development-contract.md` §6“无变化只读返回”）。有差异时一次短写：按主键插入新行（`on_conflict_do_nothing`）、按主键删除已清除行；写事务里不读历史、不扫描、不等任何外部工作。
- 检查器本身的读取失败按类别记在自己的健康里，不开问题、不通知（否则故障会自我放大）；下一 tick 照常再试。

### 4.4 “只说一次”的持久化

候选对比：

| 方案 | 结论 |
|---|---|
| 只在内存记住 | 重启（每次部署）后会把仍开放的问题再说一遍，违反决定 4 |
| 用 `runtime_work` + `runtime_work_inputs` 的唯一 `source_key`（T13 观察通知的做法） | 通知 Work 的第一个响应检查点要写协议存储；在 I1 那样的容量事故中，通知 Work 自己会以 `work_protocol_storage_capacity` 挂起，正好说不出它要报告的问题；而且 WorkScheduler／WorkResumer 只认固定来源（A10），还要再加一条恢复分支 |
| 从事实自身推版本号（例如 `work_id:revision`） | 挂起期间 revision 也会因其他更新变化，会重复通知；协议存储、组件健康没有天然版本 |
| `plugin_notification_outbox`、`autonomy_initiative_runs` | 外键绑插件或群（T14） |
| **新建两张小表（迁移 `0160`）** | 选用。一张记开放问题（谁已被告知哪一次出现），一张记每次主动私聊的回执（可复用入口自己的 run 记录，同 `automation_runs` 之于自动化） |

【决定，提议】迁移 `0160_watchdog_proactive_turns.py`：

```
proactive_turns
  id            TEXT PK（uuid）
  source_kind   TEXT NOT NULL            -- 本轮只有 'watchdog'
  person_id     TEXT NOT NULL FK persons -- 收件人（原 Person ID，不按今日账号重建）
  conversation_id TEXT NULL FK canonical_conversations
  presence_id   TEXT NULL
  state         TEXT NOT NULL CHECK IN ('pending','running','finished','failed','unknown')
  reason        TEXT NULL                -- route_none / route_paused / conversation_missing / 失败码
  result_json   TEXT NULL                -- llm_calls、tool_calls、messages_sent、failure code
  created_at, updated_at  FLOAT
  INDEX (state, person_id) WHERE state IN ('pending','running')

watchdog_issues
  person_id   TEXT NOT NULL FK persons
  issue_key   TEXT NOT NULL
  opened_at   FLOAT NOT NULL
  facts_json  TEXT NOT NULL      -- 打开时的有界事实，仅 ID／状态／原因／计数／时间
  turn_id     TEXT NULL FK proactive_turns  -- 由哪次主动私聊告知
  PRIMARY KEY (person_id, issue_key)
  INDEX (turn_id)
```

语义：

- 一行 = 某位超管对某个问题的一次“出现”。行存在即“这次出现已登记”。问题被观察到“健康”后，检查器在内存里记下开始清除的时间；连续清除满 `no_progress_seconds` 才删行（决定 7 的抖动合并），其间重现仍是同一次出现、不再说；删行后再出现插入新行，于是再说一次（决定 4）。不加 `cleared_at` 列：清除计时只在内存，重启丢失只会推迟删除，不会多说一次（重启后需要重新观察到健康并再满一个间隔）。告知过什么由 `proactive_turns`、Social 回执与出站账本证明。
- “已告知”= 行的 `turn_id` 指向 `state='finished'` 的回合。`turn_id` 为空，或指向 `failed` 回合且该回合没有成功的 Social 回执，视为“未告知”，随该人下一次批次一并说明（不自动重试，§4.6）。
- 新超管：下一次检查为他插入当前开放问题的行，他会被告知一次。失去资格：不再插入新行；已有行在问题清除时删除；激活前复核资格（§4.6），不再给他发。
- 规模：行数 = 开放问题数 × 超管数；`proactive_turns` 每次通知一行，保留作回执（与 `automation_runs` 同理），数量极少。
- 写入点只有三个：检查器的差量短写；入口把 pending 回合置 running（同一事务把该回合不再提及的行解除关联）／finished／failed，及 pending 原因变化时更新 `reason`；启动时结算上一进程遗留的 running。每个都是按主键或小索引的短事务。
- 实际表结构（`runtime/proactive_schema.py`、`0160_watchdog_proactive_turns.py`）：`proactive_turns` 增 `attempts`、`started`，时间列为 epoch 秒（同 `runtime_work`）；`watchdog_issues.opened`。

### 4.5 可复用入口：Yuki 主动发起一次私聊

`ProactivePrivateTurns`（新），接口只为看门狗所需：

```
enqueue(session, person_id, source_kind) -> turn_id      # 在调用方的短写事务里登记 pending 回合
run_pending()                                             # 由入口自己的任务调用
```

`run_pending` 对每个 pending 回合：

1. **复核收件人**（reader）：`person_is_superuser(person_id)`（T12）；不再是超管 → `finished`、`reason='recipient_not_superuser'`，不发。
2. **解析路由**：`PresenceRouter.resolve_send_for_person(person_id)`（R3）。`none`／`paused`／连接不可用 → 回合保持 `pending`，`reason` 记类别，什么都不发；下一次检查重新解析（纯读，无模型费）。健康里报告“有未能送达的通知”及人物 ID。已定只用已设置的路由（§9-3）：先读 `person_active_routes`，缺失或暂停时不调用 `resolve_send_for_person`，避免它的 `cas_takeover_person` 建立路由。
3. **定位会话**：`conversation_for_binding(binding_id, presence_id=…, thread_id=None)`（R4）。没有 → `pending`、`reason='conversation_missing'`（主动路由的设置本身要求已有该会话，R2，正常不会发生）。
4. **取得会话**：`turn_coordinator.background_turn(key, origin=PROACTIVE_PRIVATE)`；返回 None（会话正忙）就保持 `pending`，下一次检查再试，不排队等锁、不占检查器。取得后持 `concurrency.conversation(key)`，与普通 Main、WorkScheduler 恢复互斥（与 A3 相同）。
5. **置 running**（短写，CAS `pending → running`），然后才派发第一次模型请求。
6. **重读资料**：读出 `turn_id` 关联且仍开放的问题行；全部已清除 → 置 `finished`、`reason='cleared_before_start'`，不调模型（不报告已健康的状态）。
7. **调用 `generate_origin_turn`**：`identity = ConversationScope.private(...)`；`content` 为固定的简短指示（§4.6）；`source_runtime = ToolRuntime(origin=PROACTIVE_PRIVATE, actor_context=SELF 主体（proactive_turn_id=turn_id）, actor_is_superuser=False, activation_context=…, work_control=None)`；**不**取 Work 租约、不绑 `WorkControl`。
8. **结算**：正常返回 → `finished`，`result_json` 记模型请求数、工具数、`messages_sent` 与失败码；异常 → `failed`。

要改的闸门（G1–G5 对应）：

- `TurnOrigin` 增加 `PROACTIVE_PRIVATE = "proactive_private"`。不复用 `SYSTEM_TASK`：它已用于沙箱完成和 Work 恢复触发（`runtime/trigger.py:83,99`），含义是“继续原来源”，不是 Yuki 自己发起。
- `ToolActor`、`ToolRuntime.require_actor/validate_source` 增加 SELF 的第三个合法组合：origin `PROACTIVE_PRIVATE`、`proactive_turn_id` 必填、私聊会话（无 `group_id`）、`presence_id`、`conversation_id` 必填，仍不得带 user/person/event。
- `ConversationTurnSnapshot` 的锚点增加 `proactive_turn_id`（四选一）。
- Social：`invoke_social` 白名单加入 `PROACTIVE_PRIVATE`；`_validate_self_context` 增加分支，按 `proactive_turns` 行核对 `state='running'`、会话、Presence 与该会话的人物属于收件人人物族；省略 target 的 `send` 发到当前私聊会话。
- `proactive_message_label` 对 `origin='proactive_private'` 的出站消息给出 `[主动消息｜Yuki 主动发起]`，让后续轮次看得出这是 Yuki 主动说的。【实证】`chat_events.origin` 没有 CHECK 约束；E2E S1 的出站事件 `origin='proactive_private'` 正常写入。

不改：固定工具声明、系统提示、SOUL、WorkScheduler／WorkResumer 的来源白名单（本入口不建 Work）。

### 4.6 激活：来源、权限、资料、代价与失败

**来源与主体**【决定，提议】：主体是 SELF（`PrincipalRef(self, self)`），来源 `proactive_private`，锚点是 `proactive_turns.id`。理由：这是 Yuki 自己决定开口，不能借主人的身份（`development-contract.md` §1“不借最近真人或超管身份”），也不是插件事件（不需要伪造 `external_event`，A5）。

**只汇报**：

- Work 控制工具：不绑 `WorkControl`，`manage_task/start_subtask/message_task/wait/get_tasks` 全部按现有路径返回 `work_control_unavailable`、不执行（A8）。无需新增规则；这同时意味着本回合不会被接纳成 Work，不会写协议存储。
- 能力目录工具：在 `MainAgentBackend.execute_call` 增加一条来源规则：`origin is PROACTIVE_PRIVATE` 时，按实际参数得到的 `CapabilityRisk` 不是 `read` 的调用，除 `send` 外一律以 `report_only_source`、`executed=false` 拒绝（A9）。只读工具（记忆检索、网页查询、读结果等）照常；记忆写入本就不在 `_MEMORY_CHANGE_ORIGINS`（`services/agent_tools.py:93-100`）。这是用户决定 3 的直接实现，不改工具声明、不影响其他来源。
- 管理只发生在主人随后的普通轮里：主人回复“恢复吧”，那是 `user_message` 来源、主人的当前授权，现有执行处核验照常（超管可管理全部 Work 与安排）。

**资料如何进入**：`activation_context()` 返回

```json
{"origin": "proactive_private", "proactive_turn_id": "…",
 "watchdog": {"issues": [{"key": "protocol_storage_capacity", "kind": "protocol_storage_capacity",
   "opened_at": "2026-11-20T…+08:00", "facts": {"usage_bytes": …, "cap_bytes": 2147483648,
   "suspended_work_ids": ["…"], "suspended_count": 7}}, …],
```

由 `_finalize_initial_layout` 放进 `<runtime_context>`（A6）。它只属于这次激活：不进公共历史、FrozenFragments 或摘要；没有 Work，也不进任何 journal。`content`（当前消息）是固定指示，约两句：“看门狗发现了上面运行资料里的新问题。用你自己的话告诉对方发生了什么、影响什么、建议怎么处理，并写出处理需要的内部 ID；这次只汇报，不执行管理操作，对方同意后会在普通对话里处理。”它与自动化的 instruction 一样不建账本事件（A2）。【实证】E2E S1 断言 `chat_events` 中没有指示正文与 `watchdog` 资料，主人随后的普通轮请求也不含它。

**后续对话需要的事实**：本轮资料不保留，所以指示要求 Yuki 在消息里写出处理需要的 ID；主人下一轮的 Yuki 可以用 `get_tasks`、`get_schedules` 读当前状态。已定后续普通轮不附这些资料（§9-5）。

**隐私**：facts 只含内部 ID（Work、委派记录、操作、自动化、会话、人物）、状态、原因、类别、计数、时间与组件名。不含：Work goal、委派 brief、原生请求内容（命令、参数、`options`）、事件 payload、任何人的消息正文、群名或昵称。请求只给 `permission_id`、`kind` 与工具名。`facts_json` 写入时即按此投影，激活时只重读行。

**代价**：每人每批一次激活。批次 = 一次检查 tick 内该人所有未告知的行；若该人已有 pending 回合，新行挂到它上面（同 T13 的“尚未开始的通知吸收新事实”）；有 running 或等待重试的回合时新行等下一 tick。回合只在该人上一次激活开始（`started`，含重试）满 `notify_min_interval_seconds` 后才开始，期间的新问题都挂在同一个 pending 回合上，到时合并说一次；因此每人每天最多 86400/1800 = 48 次激活（决定 8）。模型请求数不设上限（Main 合同），正常为 1–2 次。没有问题时零模型调用。

**会话里已有活动 Work**：`background_turn` 返回 None 时回合保持 pending（`reason=conversation_busy`），下一 tick 再试（§4.5 第 4 步）；本回合运行中主人发来的消息按现有规则在锁后排队，不并入本回合（`stage_work_input` 只并入同一 actor 的 Work，`services/chat.py:569-631`）。主人自己的挂起 Work 不受影响。

**路由缺失／暂停／没有路由**：回合 pending、`reason` 记录、什么都不发，健康里列出；没有任何超管有可用路由时，健康显示“无人可告知”。不改用其他平台、不广播到群。

**失败与容量**：

- 本回合不建 Work、不写协议检查点，因此在 C5 的容量事故中仍能发出消息（I1 的普通私聊失败来自 Host 私聊接纳写检查点，A7 说明本来源不会被接纳）。【实证】E2E S1：容量已满（真实 Work 已以 `work_protocol_storage_capacity` 挂起）时通知送达，`runtime_protocol_objects` 行数与 `runtime_work` 行数不变（本场景未触发公共 compact，长历史下的 compact 未单独验证）。
- 模型或网关失败 → `failed`（若该回合已有成功的发送回执则算 `finished`）。隔一个检查周期自动重试一次（同样受每人最小间隔约束，见上）；第二次仍失败则 `attempts=2`，这些行视为未告知，等该人下一批新问题合并再说。每次出现最多两次付费尝试，不会每 tick 重试。
- 进程在 running 中丢失 → 启动时置 `unknown`，按回合 ID 查 Social 回执（`social_operation_receipts` 以 `(source_turn_id, tool_call_id)` 唯一，`social/db_models.py:22-60`；【实证】回执键为 `{conversation_id}:proactive:{turn_id}`（`turn_source_key`），E2E S1 用真实发送核对、S6 用三种回执核对结算）：已有成功发送 → 视为已告知；没有任何发送 claim → 视为未告知（同上并入下一批）；有 claim 但结果未知 → 保持未知，不重发（合同 §5“未知不重发”）。
- 本回合自己不会成为问题来源：它不建 Work，所以不会出现在 C1/C5 的挂起 Work 里，不会形成“通知挂起 → 报告通知挂起”的循环。检查器自身失败只进健康，不开问题。

### 4.7 健康暴露

lifecycle 条目 `watchdog` 的健康：`running`、`last_check_at`、`last_error_category`、`open_issues`、`pending_turns`（含 `reason` 计数，如 `route_none`）、`last_turn_state`。同时加进 `runtime_health(app)` 的行和 `/healthz` 的 workers（不影响 `status`）。

### 4.8 主人同意之后

不新增工具或命令。主人说“好／恢复／取消”时，Yuki 在普通私聊轮用现有工具（`manage_task`、`manage_schedule`、`message_task` 回答权限卡等）以主人的授权执行；配置变更仍走 `/ai` 管理命令或管理 API。看门狗随后在下一 tick 看到问题清除并删行。

### 4.9 步调参数（不是完成门槛）

按现有热配置惯例（`admin/config_specs_hot.py` 的 `_spec`，同 `memory.maintenance_interval_seconds` 的七处：`Settings` 字段、`settings_domains.py`、`.env.example`、spec、运行配置 dataclass、snapshot 映射、循环每轮读取），全局作用域：

| 键（环境变量） | 默认 | 含义 |
|---|---|---|
| `watchdog.check_interval_seconds`（`WATCHDOG_CHECK_INTERVAL_SECONDS`） | 300 | 检查节奏；同时就是批次窗口（一次 tick 内的新问题合成一批），不另设批次参数。`0` 关闭看门狗（与 `snapshot_interval_hours=0` 的惯例一致），关闭时每 60 秒重读该值；不设单独的总开关 |
| `watchdog.no_progress_seconds`（`WATCHDOG_NO_PROGRESS_SECONDS`） | 900 | C2、C3、C4、C6、C7、C9、C11 的“持续多久才算该说”的汇报节奏，也是抖动合并窗口（清除后在此间隔内重现算同一次） |
| `watchdog.notify_min_interval_seconds`（`WATCHDOG_NOTIFY_MIN_INTERVAL_SECONDS`） | 1800 | 同一人两次激活（含重试）开始之间至少相隔的秒数；期间的新问题合并 |
| `watchdog.protocol_storage_warn_ratio`（`WATCHDOG_PROTOCOL_STORAGE_WARN_RATIO`） | 0.8 | C5 预警比例；只是汇报，不改变准入 |

C5 已满不用步调参数（达到上限即是事实）；C8 循环停止立即报告。

9. 首次上线存量问题告知一次。
10. C7 在线无事件保留，按出现只说一次。
11. 默认：检查 300 秒、无进展 900 秒。
12. 抖动合并：清除后在 `no_progress_seconds` 内重现算同一次；用内存清除计时延迟删行，不加列（§4.4）。

### 10.3 生产故障：主动回合第一次工具调用即失败（2026-11-20 21:20 UTC）

现象：turn `9ba28996` 第一次模型请求正常完成，27 ms 后 `proactive_turn_failed category=ExceptionGroup`，没有发送。

根因【实证】：每个目录工具执行完后，`MainAgentBackend.execute_call` 在工具自身的 try 之外调用 `ChatService._record_tool_receipt` 写工具回执（Memory 证据）。`ToolReceiptRepository.record_receipt` 对 SELF 主体一律调用 `resolve_self_origin`，只认 SELF initiative 或 SELF 定时执行的来源；主动回合的执行 ID `proactive:<turn>` 两者都不是，于是抛出 `MemoryPartitionResolutionError("self_execution_source_missing")`。读工具在 `ToolInvocationCoordinator` 的 `asyncio.TaskGroup` 里并行执行，这个异常把整轮变成 `ExceptionGroup`；`send` 是串行执行，在消息已经送达之后同样抛出。E2E 没有发现，是因为测试场景没有装配工具回执记录器（容器里有）。前一轮审查记下的 B3（主动回合发表情失败）就是这个原因：发送本身成功，回执写入失败。为它加在通知指示里的“只用文字，不发表情”已删除（后台选图是否送达未单独验证）。

修复：工具回执是其原始来源的 Memory 证据，来源只有三种：触发事件、SELF initiative、SELF 定时执行。主动私聊三者都没有，因此与没有触发事件的人物轮次一样，不写回执（`chat._record_tool_receipt` 在 actor 带 `proactive_turn_id` 时返回）。没有新增限制，也没有绕开任何核验；工具本身按原合同执行。`proactive_turns` 的失败日志加了 `exc_info`。

验证：场景改为与容器一致，装配工具回执记录器、结果归档和网页工具（在修复前的代码上 8 个用例失败）。新增 S22：一批并行调用真实目录里全部 parallel-safe 工具（read_chat、search_memory、web_search、read_webpage、read_result、find_contacts、get_members、get_schedules、view_file、get_environment、read_command），并以带贴纸的 `send` 收尾。每个工具都返回结果，`send` 成功，回合 finished。断言目录里的 parallel-safe 集合被这批调用完整覆盖。

TaskGroup 的核对：工具自身的失败在 `execute_call` 的 try 内会转成该工具的失败结果；只有 try 之外的收尾（回执写入、结果来源围栏 `tool_result_source_changed`、结果渲染）抛出时才会中止整轮。普通私聊轮的回执以触发事件为来源，不会碰到本问题；后两者是有意的来源／隐私核验，中止是原合同的行为。但在并行批次里，这类异常会被包成 `ExceptionGroup`：`AgentRunner._run_with_receipts` 只拆开 `HistorySourceChangedError` 与 `WorkBudgetExceeded`，其他异常以 `ExceptionGroup` 类别结算，而串行时类别是原异常名。建议另开 issue：在协调器里只有一个子异常时抛出原异常（或在 runner 中拆开单元素组），不改变中止语义，只让日志与结算类别保持原异常。本次没有改。
