## 1. 要删什么，什么不能跟着删

以[开发约束](development-contract.md)为最高设计依据。先删无消费者的分支、重复业务模式、影子状态和经验门槛；不为它们另建开关、缓存协议、恢复队列或通用框架。局部模块已经提供的事实与执行 owner 应继续使用。

这里的“安全删除”指在明确范围内去掉代码后，真实调用、原有事实和当前外部合同仍成立。它不等于“搜索没有命中，因此任何外部使用者也不存在”。本次反查覆盖跟踪的源码、测试、脚本、配置、文档、包级导出、SDK 声明和冻结迁移；无法证明仓库外从未深层 import 某个实现。

| 类别 | 可执行含义 | 本次主要对象 |
| --- | --- | --- |
| 直接删除 | 仓内无业务消费者的私有方法、无用参数、无消费返回值，或重复的本地经验截断；同步清理专属导入和失效测试 | F05、F07、F09、F24–F28 的明确子集、F29 的未读字段/死构造、F33 的明确子集 |
| 完整退出旧模式 | 必须连同装配、调用点、提示/说明、测试一起退出，不能只删叶子 | F15；F16、F21、F22、F23 还涉及显式撤销 Python/CLI 接口 |
| 先解耦再删 | 保留原调用身份、当前授权、原子发布或存储升级后，才删旧路径和重复工作 | F01–F04、F08、F10–F14、F17–F20、F30–F32、F34 |
| 不在安全删除范围 | 现役恢复、权限、持久回执、事实原件、公开 opt-in 能力；或仍待确定产品语义的部分 | F06 的通用 ON_FAILURE 行为、Q01，以及下列必须保留项 |

“直接删除”不代表不需要编译和相关行为回归；“先解耦”也不要求一律新建抽象。删除目标的可观察行为若属于公开合同，必须作为明确的接口撤销记录，不能伪装成无痛内部整理。

必须保留：

- Person、Conversation、Binding/Presence 和原事件的既有职责。平台消息号不能重建内部事件或业务所有权。
- 原 Work、请求键、执行 ID、已付协议检查点、预算、来源资格、授权和真实效果回执。未知不改成失败，不授予重新执行或发送资格。
- Main 固定工具声明、统一 `send`、公共历史与 Work 私有输入边界。删除不改写已冻结消息、opaque、签名或旧工具配对。
- 主库现有 FIFO writer 与当前 session 的组合事务。独立 Workspace/Manager/Connector SQLite 各自的 owner 不能为了“统一”硬并进主库。
- Workspace 原件、不可变发布、真实引用核验与孤儿 GC；媒体缓存和 short_state 的独立寿命不受旧 Workspace expiry 退役影响。
- 原 server ACP 存量执行与终态/permission 回执 reader。新接纳已退役不等于历史恢复无人消费。
- SDK 的真实插件批准、执行 grants、schema 校验、插件 metadata、ON_FAILURE 显式选择和独立 Plugin session。
- 冻结迁移和历史审计材料。新增升级只管理自己的对象，不导入当前 ORM；不能靠改旧迁移让已有库“看起来正确”。
