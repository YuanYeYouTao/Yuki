## 4. 目标合同

### 4.1 五种资料各认自身事实

| 层次 | 唯一来源 | 使用方式 |
| --- | --- | --- |
| 不可变主体 | 既有角色/SELF、Person、Conversation、原执行与事件 ID | 不由名称、人设或平台昵称重建 |
| 当前角色名称 | 整合现有 `character_profile.display_name` | 桌面、管理入口和需要角色名称的消费者共用 |
| 人格 | 一份用户维护的 `SOUL.md` | 背景、性格、偏好、关系态度、表达方式及明确标注的虚构语气示例 |
| 程序规则 | 现有 `core_contract`、Memory grounding 和各模块职责提示词 | 工具、授权、交付、Work、Provider、提取与整理规则 |
| 当前事实 | 本轮运行资料、原 Conversation 历史、Memory、工具回执 | 保原来源、作用域和时间，不混成人格或新发言 |

`system` 是发给 Provider 的消息角色，不是人格文件的业务名称。SOUL 编译后仍可进入 system 消息；内部生成的完整 `system_prompt` 字段如确有协议消费者可以保留，但不得再作为第二个可编辑人格配置源。

用户可以自由写人格。后端不解析固定章节、不设姓名一致性检查、人格评分、最小长度或内容准入，不根据 SOUL 文字改变授权、Provider 路由、工具清单和任务生命周期。

实施时逐段拆分现有文字：可爱程度、口头禅、情绪表达、是否使用动作/旁白等角色审美归 SOUL；`send_message` 的统一出口、内部最终正文、原回执、任务进度反馈与自主触发含义归程序规则。现有防刷屏与共享发言节奏按真实产品约定处理，不把它们改成 SOUL 准入检查或任务完成门槛。角色语气示例仍明确是虚构示例，不当成经历写入 Memory。默认预设整理保留用户已选定的表达内容，不借文件改名重写一套未经讨论的人格。

### 4.2 单 SOUL 文件与简单变量

- 仓库默认角色模板统一为 `config/SOUL.md`；实际部署的可写原件统一为 `character/SOUL.md`。前者只用于明确的初始化，不是运行时回退来源。
- 路径配置统一为 `SOUL_FILE`，内部配置名为 `soul_file`。运行时只读实际选定的一个文件，不搜索多个旧文件，也不把 env 字符串再拼成另一份人格。
- 正文保持自由 Markdown，仅支持精确、非递归的 `{{name}}` 替换。变量取本次激活的当前角色名称；原件保存变量。其他花括号原样保留，不解析表达式，不进行模糊全文替换。
- 空 SOUL 合法，表示省略人格段，程序执行规则仍正常提供；不自动填回默认 Yuki，不因空正文拒绝工作。
- 显式文件读取失败如实报告 I/O/配置错误，不静默改读示例或旧路径。编辑失败不发布半份新内容；沿现有文件发布与生效回执反映真实状态，不增加全局运行门槛。
- 默认 Yuki 人格可以作为用户明确选择的预设，正文内自称及示例标签使用 `{{name}}`；用户自行写下的姓名、引用或设定原样保留，不自动纠正。

### 4.3 名称与平台资料分开

`character_profile.display_name` 是当前角色名称的唯一权威，不再由 `BOT_DISPLAY_NAME` 与数据库长期各存一份。新部署由现有向导/初始化流程将用户选择写入角色资料；既有实例沿明确升级步骤选择其实际名称，不从自由正文猜测姓名。

删除名称的 `cached_property` 和各服务构造时的永久副本。复用现有角色领域与激活准备，获取一次所需的当前名称、显式唤醒别名和已生效 SOUL，向本次消费者传递一致值；不另造身份注册表、人格总线、TTL 缓存或逐模块刷新队列。

需要识别自身的消费者在 SOUL 正文之外接收最小角色身份参考，明确当前名称；内部角色 ID 只在真实消费者需要时提供。空 SOUL 或不含 `{{name}}` 只影响人格正文，不使真实角色名称缺席。该身份段沿相同激活边界提供，不复制第二套可编辑人设，也不要求用户补占位符或通过姓名一致性检查。

唤醒别名仍是显式配置，当前角色名自动参与现有名字命中；删除对所有角色默认附带 `Yuki/yuki/由纪` 的隐式行为。除非用户显式配置，不因改名偷偷保留旧名为新别名。名称命中只是参与线索，自身身份继续按 Account/Presence 等内部事实判断。

平台账号昵称、群名片仍认 Account 与实际 SpaceBinding。改角色名不调用 QQ/TG 改昵称接口，不改变账号归属、Person、SELF 或 Conversation。

### 4.4 同源不等于所有模型都扮演角色

| 消费者 | 人格与规则边界 |
| --- | --- |
| 普通 Main、SELF 主动轮、自动化、Work 新激活、插件受控 Main | 共用现有 PromptComposer：同源 SOUL、共同技术合同、本轮来源资料 |
| 子 Agent | 沿 Main 静态人格与固定完整能力合同，加自己的真实任务 brief；不复制父私有工具尾部或拼接公共历史 |
| Self Reflection、SELF Dream | 专用任务提示词＋同源人格参考，用于理解自身视角；不塞入完整 Main 交互规则或伪造真人请求 |
| JEV | 独立评分规则＋当前角色名称/必要身份参考及原参与反馈；不代入角色发言，不以人格改变评分输出合同 |
| 普通人物/空间 Memory 提取和 Dream | 保持事实提取、整理职责；需要区分自身时用明确身份参考，不灌整份扮演指令 |
| Compact | 沿原请求的真实装配与原付费检查点处理；不另读文件给旧请求换人格 |
| 视觉、ASR、表情素材描述 | 保持观察或结构化处理职责，不引入人格扮演 |
| 配表情 | 继续消费 Main 给出的表达目标和真实素材，不新增人格模型 |
| 插件独立 AI 会话、外部 ACP Agent | 保各自既有隔离和任务合同；与“调用 Yuki Main”明确区分，不全局强塞 SOUL |

模块可以维护自己的职责提示词，但不自行读取旧人格文件、不复制角色正文、不各自保存另一份当前名字。需要扩展消费者时沿现有依赖注入及角色读取入口接入，不复制配置解析或新建 Prompt 框架。

- 向导、脚本、Compose、发布包和现行帮助中的旧配置示例、旧准备命令与双来源描述。

不留旧 endpoint、字段别名、参数兼容、双写阶段、兼容开关、旧文件自动查找或隐式降级。确有协议层意义的 `system_prompt` 内部变量不必为消除单词而乱改，必须同时确认它已不再是可配置角色源。

### 6.2 单文档编辑合同

复用桌面分支已有的角色授权、原请求回执、原子文件发布和激活流程，精简为单 SOUL。目标管理语义为 `character soul show/set/reload`；个人/管理 API 各自在原前缀下使用 `/character/soul` 读取/保存及 `/character/soul/reload` 显式重载，不保留旧双文档路由。

保存保留原 `request_id`、真实 owner/operator 授权和必要的原文 revision，防止两个编辑者互相覆盖；文件源 revision 与实际 active revision 可能不同，结果如实说明 written/active/unknown，不用新增人格状态机将普通模型工作封住。原请求重放查原结果，不把改名或重载变成新发送效果。

名称变更沿原角色资料 revision，SOUL 原件版本沿真实文件字节；二者在新激活中共同决定实际身份/人格内容，不另造联合版本账本，也不能以 SOUL 文件 hash 未变推断模型中的名字未变。进程内 SSE 更新计数只作通知，不冒充持久事实版本。

直接编辑磁盘后由原管理流程显式 reload；编辑器保存可沿原流程生效。不新增文件监视器、周期轮询、逐轮目录扫描或重复序列化；复用现有已生效正文与激活准备。

独立 Yuki Desktop 同步删除旧双页签、缺占位符提示和旧类型，显示 SOUL 编辑及真实生效状态。更新 SDK/OpenAPI、固定合同源提交/哈希、能力与 API revision；这是破坏性变化，按实际新合同发布新 revision，不继续声称 additive 兼容，也不猜测版本号。Main 工具说明本次清理按实际内容变更正常更新部署合同 revision；以后单纯改角色名不改变它。Plugin API 没有实际合同变化时不顺带升版。不提供旧客户端兼容入口，旧回执仍作为原事实查询。

Desktop 必须从最终固定后端提交导出真实 OpenAPI，同步 `contracts/client-api.openapi.json`、`contracts/source.json`、`src/shared/contract.gen.ts` 与 `src/shared/api.ts` 的 `REQUIRED_API_REVISION`，保留 `build-tools/check-contract.mjs` 的真实合同核对；IPC/preload、单测和实际后端 fixture 一并更新，不能靠手改 hash 让旧合同过检。本次调查的 Desktop `source.json` 固定后端 `34e0187fd3b560452edcdcdfce87db1cd76d0174`、API revision 5，与表中桌面后端分支 head 不同；不能用相近分支的通过结果冒充固定合同已对齐。

复用已有 CharacterProfile 与编辑基础，不再建立第二份 Bot 身份表；整合时只接入本任务需要的角色领域及其真实依赖。已部署桌面库若存在，须用其实际结构副本验证升级；不得因不兼容旧接口而删除现有角色、Person、Conversation、文件、Work 或回执。

### 6.4 Desktop 本地草稿和未决命令

独立 Desktop 的 `src/main/outbox/prompts.ts` 还把旧 key、正文、请求 UUID、版本和 submitted 状态保存在本地 SQLite 的 `prompt_drafts/prompt_commands`，不只是 UI 页签。升级时明确导出或由用户选择保留原草稿正文；不无脑删草稿，也不自动合成一份 SOUL。

原 submitted/unknown 命令只按原请求号经已有查询查看已发生事实；升级后不再向旧写端点补发，不把旧 UUID/payload 换成新 SOUL 写入。核对 `src/main/connections.ts` 重连时的自动重试，旧 pending 不再派发，也不能成为新 SOUL 编辑的全局门槛。无法确认的结果仍保持 unknown，不伪造成功。用户确认后的 SOUL 保存是新合同下的明确新意图。迁移在一次本地数据转换中处理旧形状，不为旧 key 保留常驻发送分支；原回执的只读展示与新命令分发分开。

删除 `outbox/prompts.ts` 使用 `normalizeMessageText` 拒绝空人格的门槛，贯通编辑器、IPC、outbox、API、加载与重启的空 SOUL 行为。`PromptCode.tsx` 的旧占位符高亮/导入提示和 PromptEditor 的缺占位符告警同步退出；不能只放开后端空正文，客户端仍阻止提交。

沿现有 owner/operator 合同读写 SOUL，不扩大普通设备权限；同实例不同 Person 的草稿、凭据与原请求 namespace 保原隔离，撤销 owner 不把旧私有草稿交给下一位用户。保留原编辑器换行、撤销与崩溃草稿恢复等真实可用行为，不为换格式重做编辑器。

## 7. 热更新、历史与缓存

1. 新激活在准备阶段取得一致的当前角色值。当前激活的模型/工具往返保持开始时的静态前缀；不在同一轮中途替换人设。
2. 改名、保存或 reload 后，后续合法新业务激活/新请求链使用新值；等待后接续原 Work 沿现有合同变化处理，保原 Work、预算、执行 ID 和效果对账，不重建任务。若等待的是已派发 Provider 请求或原协议检查点，先按原材料及回执恢复；不能仅因 wakeup/activation 名称就换前缀、强制 Compact 或重购。
3. 原已付请求、opaque/signature、工具调用配对、未决请求及自省/Dream/Compact 检查点按原件恢复。热更新不是重新购买或重放未知效果的理由。
4. 原账本、当时昵称与提及、公共 FrozenFragments、Compact 覆盖点不随当前名字重渲；删除派生历史对当前名的不必要依赖，不以统一名字为由刷新全部公共上下文。
5. 同一配置下，SOUL 展开、规则顺序与工具声明确定且字节稳定。当前说话人、权限、时间、进度、平台场景仍只进对应的当前资料，不塞入 SOUL 或稳定前缀。
6. 名称/人格改动会改变相应角色前缀，不能保证继续命中全部旧前缀缓存。固定工具描述不含当前名，使热改名不额外改变工具合同；不为缓存另造按人/平台的人格版本、历史分支或权限缓存。
7. 本地比较 payload/字节只能验证确定性。真实命中率以 Provider usage 为准，缺失字段保持未知，不把本地 hash、健康检查或一次新前缀命中当线上缓存验收。
