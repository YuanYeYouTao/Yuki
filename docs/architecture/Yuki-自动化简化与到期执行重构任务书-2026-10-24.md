## 1. 要解决的问题

自动化负责在约定时间启动一段完整任务。模型到点应当清楚知道：谁原来安排了什么、哪一次发生已经到期、现在该继续哪一部分、发消息时实际发给谁。

当前实现仍要求模型填写一些固定值和重复字段，把收件人、静默模式、执行场景混在 `delivery` 中，同时没有把本次到期事实交给模型。查询又不能完整取回原要求。模型面对这些输入，需要猜测的地方过多。

2026-10-24 的提醒是具体病例：任务 142 在 01:04 创建，02:04 正常触发；给模型的正文仍是“一个小时后在 QQ 私聊提醒……”，附带 `delivery=none`，没有本次到期身份。模型调用一次 `automation_manage(create)`，建立 03:04 的任务 143，原发生以 `succeeded` 结束，发送数为 0，实际没有调用 `send`。这些执行事实已经由真实请求、工具回执和 Social 记录核实；对模型为何选择重建的解释属于输入语义分析。

这次重构直接减少需要猜测的参数和分支，沿现有 Main、Work、Social 和 SQLite owner 完成。目标是让模型精确执行任务，同时让运行代码和存储更简单。

## 2. 设计边界

遵守[共同开发约束](development-contract.md)、[Main 运行合同](main-agent-runtime.md)、[Tool Kernel](tool-kernel.md)和[插件自动化合同](../plugin-development/automation.md)。以下是拟实施的目标设计；落地时同步修订现行合同，不用任务书替代已经运行的事实。

- 先删冲突模式、重复定义、无消费者字段及旧透传，不用新开关、策略层或解释器替代。
- 到期继续调用同一个 Main，使用部署时固定的完整工具合同，实际权限在执行处核验。
- 内部 final、Work 完成和自动化发生结束继续沿统一出口。是否需要发送来自完整任务要求，发送事实来自原 Social 回执。
- 不新增强制发送、必须调用指定工具才可完成、额外审核模型、纠正轮或失败重跑机制。到期后仍可合法安排独立后续事项，不禁止自动化调用创建工具。
- 原创建者、来源、真实执行与已发生效果保持原身份。未知结果先查原调用，不重置预算、换 ID 重发或把旧请求当新真人消息。
- 动态发生资料属于当前激活，不进入公共 FrozenFragments、公共 compact、长期记忆或固定系统前缀。
- 本任务书只覆盖自动化及其直接消费者。SELF 的日常 quiet、聊天参与状态和其他领域的调度含义各按现行合同处理。

## 3. 模型应看到的任务定义

### 3.1 新定义

新建任务只要求两个业务字段：`goal` 和 `trigger`。`name` 是可选显示标签，`max_runs` 是可选的真实有限次数要求。

```json
{
  "action": "create",
  "task": {
    "goal": "在已确认的 QQ 私聊入口提醒远野背单词。收件人的稳定人物身份和指定入口线索写在此处，使用正常 send 发送。",
    "trigger": {"type": "after", "seconds": 3600}
  }
}
```

该例说明业务结构，文字中的身份说明不是程序解析语法。实际创建时，已有可信身份线索可直接沿用；有实质歧义时按现有联系人和来源工具查清，把实际取得的稳定线索写入完整要求。后端不从正文中用关键词、正则或另一次模型调用反推收件人。

| 当前字段 | 新合同 |
| --- | --- |
| `goal` | 唯一完整任务要求，保存原文及必要收件人、渠道、内容、完成预期 |
| `constraints` | 删除独立输入通道；具体要求写进完整 goal，不丢失原要求 |
| `delivery.target` | 整体删除；没有 `auto/self_private/current_group/none` 模式，也不新增同义替代字段 |
| `version=1` | 从模型声明删除；历史格式识别留在必要 reader 中 |
| `name` | 可选显示名，不作为执行目标、收件人或等价判定；未提供时显示“自动化 #ID”等中性名称 |
| task 级 `timezone` | 删除，与 trigger 的实际时间语义收拢 |
| `max_runs` | 仅表示用户明确要求的累计发生次数上限，默认不限，不是经验预算 |

全局安全目录不能从私有 goal 摘取或生成默认标题。显示名仍沿既有目录可见性处理，完整要求按真实读取权限返回。

### 3.2 唯一的时间表达

保留现有五种真实安排，不合并为一份需要程序二次解释的自然语言时间。

| 类型 | 模型字段 | 保存和执行语义 |
| --- | --- | --- |
| `after` | `seconds` | 首次从创建接纳时刻计算一次绝对到期时刻；更新非时间字段和迁移不重新起算 |
| `interval` | `seconds` | 沿既有周期规则推进；没有第二份“重试间隔” |
| `once` | `local_datetime`，明确包含 UTC offset | 唯一绝对时刻，不再接受另一份覆盖时区 |
| `daily` | `hour/minute`，可选 `timezone` | 未指定时采用共同默认时区，创建后固化唯一有效值 |
| `weekly` | `weekdays/hour/minute`，可选 `timezone` | 同上，星期使用现有约定 |

`after/interval` 不要求无作用的时区。显示时间使用现有时间服务并带明确 offset；显示选择不改变实际到期时刻。旧 once 未带 offset 时按旧真实有效时区转换为同一个绝对时刻。

原文字中的“一小时后”可以完整保留为请求原文。实际调度只认结构化 trigger、本次 run 的 `scheduled_for` 和原接纳版本，不从正文再次计算时间。

用户明确修改 after/interval 的时间参数时，沿既有更新合同，以该次修改接纳时刻计算新的未来时间；不能从最早 created_at 起算。仅更新要求、名称或次数不构成重新倒计时。

### 3.3 管理与次数修改

继续使用固定 `automation_manage`，保留 `create/update/pause/resume/cancel/run_now`。一次部署冻结声明，不在每次调用或每个主体下更换 schema。

- `create` 提交完整 `goal/trigger`，可带 name；name 缺省或 null 表示未命名，`max_runs` 缺省或 null 表示不限。
- `update` 替换未来的完整 `goal/trigger`；name 缺省保留原值、明确 null 清除自定义标签。`max_runs` 缺省保留，正整数修改，明确 null 解除次数限制。字段是否出现必须真实传到服务层，不用 `.get()` 混淆缺省和 null。
- `max_runs` 认自创建以来的原累计发生和已接纳发生，不因更新、暂停、恢复或迁移清零。降低上限不取消在途执行；达到上限后不接纳新发生，按原生命周期收尾。失败、取消、未知等已经记录的发生不被改写成“没有发生”。
- `completed/cancelled` 不因修改辅助参数暗中复活。本次沿既有这两个终态的合同；用户要继续一项已完成安排时，显式创建新的未来安排，原发生和累计计数留在原 ID 下。`failed/blocked` 继续支持现有获准的修改和恢复，不能借“终态”笼统封死。
- pause/cancel 处理未来安排；已接纳 Work 继续按原 Work 控制合同处理。run_now 返回原入队事实，不声称已经执行或送达。

各 action 的声明只表达实际参数关系。删除不消费的参数槽及含糊文案，复用现有校验方式，不另建通用参数验证或 patch 框架。

`max_runs` 位于 manage 调用的安排层，不混入完整 goal。SDK/Host 的 `create_task/update_task` 同步提供这个可选参数，create 保留现有稳定 request_id；update 同样保留缺省/null/整数的区别。沿具体入口传递字段是否出现，不新建通用更新框架。

## 4. 到期激活应看到的事实

复用 `TurnExecution._finalize_initial_layout()` 和已有 `<runtime_context>`，在当前触发正文前合入本次发生资料。不是另建自动化消息通道。

最低需要表达：

| 事实 | 来源和用途 |
| --- | --- |
| `scheduled_automation` | 原发生来源，表明这次是已经到期的执行，不是新真人发言 |
| automation ID、run ID | 原安排和本次发生身份，用于查证及恢复 |
| 原创建者 Person 或 SELF | 正确解释“我”、身份与后续反馈；名称仅作展示，ID 来自真实原 owner |
| 原来源 Conversation/平台及必要场景 | 解释已有上下文，不冒充实际收件人 |
| 原任务创建时间 | 读取 automation 的真实 `created_at`；不使用更新时会变化的快照时间替代 |
| 本次 `scheduled_for` | 唯一到期事实；迟到执行仍认该时刻 |
| 本次可信时间快照 | 显示当前实际时间，首次合法请求准备时取得 |
| 完整原要求 | 作为已经安排的目标，不重新起算相对时间；只展示一份 |

说明要直接表达：“本次安排已经到期，继续完成这次发生尚未完成的工作；原话中的相对时间属于原安排。”不增加提醒关键词识别或禁止创建后续安排的策略。

首次到期的当前触发正文使用接纳版本的完整 goal，`instruction()` 直接输出这段完整要求，运行资料只放发生和来源事实，不再输出一份需要模型解释的自动化配置 JSON。不要把整份 goal 再复制进 runtime_context。原创建者完整资料和全自动化目录继续按需查询，不整包预取。

### 4.1 重试与原 Work 续跑

同一次激活首次合法新请求冻结资料；工具往返和 HTTP 重试保留已提交原件，不每次改写当前时间或追加目标。不同合法激活可以准备自己的当前时间，不回写先前请求。

`session.uses_recovery_transcript` 路径继续保留原初始化跳过语义。旧已付请求、工具配对、签名和 opaque continuation 不倒插新块；必要的新资料在既有合同允许的新链边界接入，不清 journal、不重购模型。

已有 Work 恢复的是原发生尚未完成部分，当前目标认当前 Work.goal。原自动化通过原 version/run 引用溯源，按需读取完整原件，不再把原 version.goal 作为一条新的当前任务正文插入。现有 runtime_state 已投影 Work.goal 时复用该投影，本次不再复制第二份目标。新授权输入、原工具配对与原回执保持既有位置；发送已确认的提醒不因恢复而重发。无 Work 丢进程继续按原发生 uncertain 等真实状态处理。

“目标只展示一份”约束本次 Host 新增的触发材料，不对整个 Provider payload 做同文次数判断。公共原历史和旧已付协议可以合法含有同一原句，不为满足次数断言删除或重写它们。

## 5. 收件人与发送

执行场景保持原来源 Conversation、Presence 和授权，不因为任务要求 QQ 私聊就把飞书来源伪装成 QQ 用户输入。

实际发送沿普通 `send` 的真实 target/binding。完整 goal 说明要提醒谁、哪个渠道及已取得的稳定线索；运行资料说明原创建者和来源。需要指定 QQ 入口时，模型显式使用该目标，不能把省略 target 的“当前会话发送”当作指定 QQ 私聊。

删除 delivery 的重复目标推导和静默提示；内部工作是否需要沟通由完整要求决定。明确要求静默的原正文继续保留，明确要求提醒的原正文也继续保留。最终正文仍只是内部结果，不增加自动兜底发送。

## 6. 查询合同

模型侧只保留 `list/get/history` 三种查询。删除 `match_task`、`diagnose` 及其多余消费者；`completed` 合入生命周期筛选，不另建一份终态目录。

| 查询 | 输入 | 结果 |
| --- | --- | --- |
| `list` | 可选 status、limit、cursor | 全局安全摘要：ID、名称、创建者、生命周期、下一到期时刻；不暴露私有正文 |
| `get` | automation_id | 当前完整定义和必要状态；按原创建者或当前超管权限读取完整私有要求 |
| `history` | automation_id，可选 limit、cursor | 原发生、原版本和实际执行结果；沿现有 owner/超管读取权限 |

list 默认 active，status 接受真实生命周期值及 all；查询已完成项用 status=completed，原 completed 的“仅当前主体”隐含语义退出模型合同。插件的 owner-scoped 列表仍沿实际主体过滤，不变成全局私有读取。

get 不再复用 list 的简表。读取完整私有要求和读取全局安全目录是不同数据范围，复用原领域授权，不增加批准流程或新权限系统。全局目录可见不授予修改或读取他人私有目标的权利。

分页在同一层定义实际 limit，数据库读取 `limit+1` 后生成下一游标。删除“上层接受任意数、底层截成 101 却说没有下一页”的两层口径。沿现有简单数字 offset cursor，使用 SQL 分页，避免全量读取后切片；本次不增加游标编码、分页快照、签名服务或游标状态表。目录变化仍按实时目录理解。

创建恢复以原调用键和领域回执为准，不靠结构等价查询决定是否已经创建。诊断需求使用现有执行过程和管理审计，不把一份额外审计视图塞回模型工具。

## 7. 存储只留一个完整定义来源

复用 `automation_versions` 保存完整不可变定义。`automations` 保存安排身份和调度状态，不再复制整份脚本与授权 JSON。

| 对象 | 负责保存的事实 |
| --- | --- |
| automations | 稳定 ID、创建者、原来源、创建调用键、生命周期、next/last run、累计次数、max_runs、租约、时间戳 |
| automation_versions | 原版本 ID/序号、完整要求/trigger/可选名称、原 hash、必要原来源事实；新版本不写无消费者常量 |
| automation_runs | 本次发生 ID、scheduled_for、接纳的 version_id、真实终态、模型/工具累计计量与原结果 |
| Work/领域回执 | 已接纳 Work、原调用、预算/预留、实际效果与投递事实，继续各认原 owner |

当前目录按现有 `(automation_id, version)` 索引取得最新定义，批量读取一页；不增加另一套 current definition 配置或完整 JSON 缓存。运行与历史始终取 run 自己的 version_id，不能取最新版本代替。

删除当前定义上的 `script_json/script_hash/schedule_json/authority_snapshot_json` 完整副本及无效同步。name/timezone 也不另存第二份业务定义；目录名称和显示时间从唯一当前定义及现有时间服务投影。

必要的原创建者、Conversation/Presence 等来源字段可以继续是可索引的真实关联。不要因“去重复”删除权限和恢复需要的身份；也不把显示名或平台消息 ID 用来重建它们。

来源字段的存储归属必须一起落地：

| 来源字段 | 唯一归属和读法 |
| --- | --- |
| creator_kind / canonical_creator_person_id | automations 保存永久创建者；实际执行资格仍查当前真实人物，不借快照永久提权 |
| 原 canonical_conversation_id | 在 automations 保存明确原关联；迁移只取已存真实快照，不能从今日活跃路由推导；旧未保存者保持缺失事实 |
| 原 canonical_presence_id | 保留当前原关联；已接纳版本保留原快照，不因今日 Presence/Binding 改变替换 |
| 原 source_event_id（如有） | 由创建调用真实 ToolActor 沿链保存；无事件的 SELF/内部调用不补造，旧平台消息号不反查重建事件 |
| canonical_target_person_id / canonical_target_space_id | 原版本里的真实旧目标保留供隐私和回执查询；context/SELF 的执行场景独立按原 Conversation 读取，不把旧投递选择继续当新收件人模式 |
| current_group_id、原平台账号标识 | 必要旧 reader 继续读原版本；新场景使用原 canonical 关联，实际仍需原平台标识的 consumer 保留原值，不改用今日路由或正文解析 |
| conversation_generation | 既有新发生与已接纳发生分别沿现行 generation 合同；不以旧投递枚举或原显示名取代 |

修改任务的操作者可以来自另一个会话，但不能让这次操作的会话覆盖原安排来源。SELF 来源、Conversation reset 和执行恢复迁到明确原场景；隐私清退继续按永久 owner 及原版本里保存的真实 target，沿原合同查询和清理。来源与收件目标不能互相替代，也不从 goal 解析补造目标。所有消费者随字段归属一起修改，不能只删 ORM 字段。

owner 上的旧 canonical_target 两列在各读者迁到正确来源后退出 ORM 和当前表；删除前先保证原值已在精确原版本中保留。版本表里的旧 target 列保持历史原值，新版本不借它们建立第二份收件人模式。旧“创建者 A 在群 G 安排向 B 私聊”的记录，即使当前定义已经简化，也仍须按原 B 目标处理既有隐私清退，不能只凭 A/G 查询而漏掉 B。

| runtime_automation_cursors | 保留原 run→Work 的必要旧 reader 和原件；不再让新运行依赖该表 |
| automation.gateway 的插件通知调用 | 按真实消费者归位或改名；不以文件名判断死代码而删掉仍用的插件能力 |
| poll/lease 的管理端经验上限 | 与现有实际数值合同收拢，保真实正值/类型，不新加节流或准入门槛 |

旧 `updated_by` 保留在历史版本中供查证；新版本实际操作者沿同事务已有管理审计记录，不新增第二套操作者事实。历史列退出新写入时明确空值/默认约定，不由旧账号字段假冒当前操作者。

## 8. 一次性迁移与原执行保留

升级通过新的冻结迁移执行，迁移自身使用冻结结构，不导入未来 ORM。不在每次启动或查询时自动搬迁，也不新建归档表或多套兼容配置。

### 8.1 先保留原件，再发布未来定义

1. 核对每个将删除的 owner 完整副本是否已有精确原版本。若确实缺失，只追加一份原样当前快照，不伪造旧 run 授权或改挂旧发生。
2. 原 version.script_json/hash/authority/targets、run.version_id、Work source/checkpoint、原工具调用和 Social 回执逐字保留。旧 JSON 供历史查询及必要恢复，不强制套新 TaskSpec 验证。
3. 对仍有未来安排用途且能确定转换的现行 TaskSpec 追加简洁版本，原 lifecycle、next_run_at、run_count/max_runs、租约及创建身份不变。blocked/paused 不因转换变 active；completed/cancelled 不额外发布未来运行。
4. 旧步骤、模板或插件程序继续保留原件及既有非活动状态，不复活解释器。后续真实用户提交完整新要求时，沿正常新定义操作处理。
5. 确认引用和新旧读者均正确后删除重复 owner 列及死投影；没有必要再复制一份 archive JSON。

精确原版本核对包括原 script JSON/hash、authority 原件、canonical target 和 presence。版本缺失处理只发生在这次迁移中：删除 `create_run()` 遇到 NULL authority 就从当前 owner 复制新版本的运行时补迁移分支。历史 NULL 原件继续表示原资料未知，不能填入最新授权或回挂新版本。

`get_for_run()` 从该 run 的原 version 直接建结果，只从 owner 读取稳定创建者和当前调度状态；不得先解析最新 owner 的新结构再覆盖旧字段，造成旧发生依赖新 TaskSpec。

调查时线上有 134 个定义、179 次发生：69 个旧步骤定义无 active 项；259 条 step 原件、150 条旧预算和 153 条旧 cursor 仍在。这里只是 2026-10-24 的样本，迁移前必须重新读取真实现场，不能把这些数字写成程序判断。

### 8.2 文本与时间转换

- 完整保留旧 goal；每条 constraints 按原顺序和完整边界追加到 goal，不截断、不重写里面的 JSON 或自然语言。
- 旧明确的 self_private/current_group 目标，沿已有稳定 Person/Space 和原入口线索写入完整任务要求，不换人物、不拿今日昵称反推原目标。原来源场景继续保留。
- 删除 `none` 模式，不根据这个辅助字段生成“禁止发送”，也不让它覆盖正文中的明确提醒要求；原正文中明确静默的要求原样保留。原字段仍可在原版本中查证，不再作为新模式执行。
- 墙上时间按旧有效优先级 `trigger.timezone or task.timezone` 归一；once 保同一绝对时刻，带 offset 原件不重算；after/interval 保现有已排定时刻，不从升级时间重新倒计时。
- 转换不得调用 `initial_run_at(now)` 批量重排旧任务，不把原历史输出交给模型重新解释。

### 8.3 在途、未知与合同变化

已经接纳的发生继续取自己的原版本/hash/来源；新定义只服务未来发生。更新或迁移不能改写旧 Work 的累计预算、原 goal、工具配对和已付协议材料。

已提交的创建、发送和控制调用先查原持久调用/领域回执，再校验是否需要进入新的 TaskSpec/hash 路径。已确认原调用直接复用原结果，不拿新 schema 验证它的旧参数；新结构 hash 不得覆盖旧 creation key 的原参数，不能因为旧参数缺少新字段就把已执行调用判成未执行。

这不意味着同 creation key 的真实不同参数可以冒充回放：原调用/参数指纹仍须一致；同一事件下不同合法调用键仍分别生效。原调用身份、相同原参数恢复和新的修改请求三者不能混在一起。

尚未派发且与新声明不兼容的调用，沿现有合同切换进入合法新链组织参数，不增加旧参数自动翻译/重派循环。已派发未知保持原未知，沿原 ID 查证；已确认效果不重做。

升级前已付响应含旧 schema 的未派发 create/send 尾部时，先按原调用键配齐真实未执行回执，再沿既有合法新链让模型使用现行合同决定下一步；不能自动翻译旧参数，不能借新 ID 重派原未知效果。

下一周期仍由原接纳版本、本次 scheduled_for 与真实完成时间按原规则计算。迟到旧发生的结束不能覆盖后来编辑产生的新 next_run_at；运行资料中的当前时间快照不能参与改写这一结算规则。

## 9. 生命周期和投递各认原事实

run 的 succeeded 表示这次模型/Work 正常结束，不改为“用户目标已被程序证明”。查询明确给出原生命周期、错误、内部结果和真实投递情况。

无 Work 路径当前统计成功 Social 分片；有 Work 路径当前复制投递预留计数，必须消除把它们都解释成送达数的口径。沿已有 Social 操作/分片回执解释 succeeded、failed、unknown；预留和待派发沿原 Work 预算事实展示。确定没有调用 send、也没有投递意图时可以报告已知零发送；已有预留/派发但缺确认时保持未知，不能将其记成零发送或补造成功。

不修改原 Work 预算或预留数来美化统计，不增加每轮全库聚合或第二份投递账本。需要查询时按原 run/执行身份和既有索引关联；无直接关联的旧记录标明旧口径，不能按内容/平台消息号猜归属。

普通内部整理可以零发送正常结束；提醒任务的行为验证要看到真实 send 及其目标回执。两者都不通过“发送次数必须大于零”这种通用运行门槛来裁决。
