## 1. 现象与原因

### 1.1 现象【issue】

`github-monitor` 从 2026-10-22 04:05 起没有成功轮询过 GitHub，状态却一直显示“运行中”。手动执行 `sync ... baseline` 清掉 `github_cursor_missing_from_overlap` 后，每次请求都报 `PluginPermissionError`。

部署环境：

- Mac 上的 Clash Verge，开了 TUN 和 `enhanced-mode: fake-ip`（`198.18.0.1/16`）；

- httpx 在 `trust_env=False` 时，只用 `certifi.where()`；
- `trust_env` 会一路传到 transport 的 `create_ssl_context`；
- 依据：httpx `_config.py:34-40`、`_transports/default.py:153`、`_client.py:685-705`。

结论：F2 的检查本身没错，错在**解析来源**。

### 1.3 威胁模型【实证】

由 F7，这道地址检查防不了恶意插件。它防的是**可信插件替人取了不该取的地址**（SSRF）。

`subscription-monitor` 的实际情况：

- `monitor` 命令仅限超管（`plugins/subscription-monitor/subscription_monitor/plugin.py:45-56`、`plugin_host/command_adapter.py:202`）；
- 唯一的出站请求是 `GET subscription.url`（`polling.py:236`）；
- feed 条目里的链接只出现在摘要里，不会被请求（`polling.py:66-70`）。

因此 SSRF 的输入来源是：

- 超管配置的 URL；
- feed 服务器返回的重定向；
- feed 域名的 DNS。

allowlisted 插件只能影响路径和查询串。主机能否越出白名单，取决于两件事：

- 重定向：每跳都查白名单；
- 被批准域名自身的 DNS。

D1 防的正是后一种情况。

### 1.4 同类路径【实证 + 假设】

`services/media_resolver.py:439-461` 和网页读取（`web/page_extractor.py:54`）也是“本地解析 → 校验全部地址”。由此推断，它们在 fake-ip 环境下同样会被拒，但**未经生产复核**。本 PR 不处理，见 Q7。

## 2. 方案：显式配置的可信 DoH【决定 D1】

### 2.1 每一跳的行为

对第一个 URL 和每次重定向的目标，依次执行：

1. **URL 检查**：URL 解析、scheme、凭据、IDNA、白名单，沿用现有逻辑。
2. **IP 字面量**：不做 DNS 查询，地址必须通过 §3.4 的“公网单播”检查。
3. **域名**：
   - 向配置的 DoH **并发**查询 A 和 AAAA，等两个查询都结束或截止时间到（§3.3）；
   - 按 §3.3 判定本跳的地址集合；
   - 集合中**每个**地址都必须通过 §3.4；
   - 任何一步失败就拒绝本次请求。被拒时目标零连接，也不尝试任何其他解析来源。
4. **连接**：
   - 只连接已检查集合中的地址（§3.6）；
   - Host 头、SNI 和证书主机名都用逻辑域名；
   - 整次请求共用同一个截止时间（§3.7）。

配置了 DoH 时，这条路径上系统解析器**零调用**。

### 2.2 配置【推荐，Q1】

```dotenv
PLUGIN_HTTP_DOH_URL=https://dns.example/dns-query
PLUGIN_HTTP_DOH_BOOTSTRAP=203.0.113.53,2001:db8::53
```

两个变量的取值组合**只有以下三种合法**，其余全部视为配置错误：

| # | `PLUGIN_HTTP_DOH_URL` | `PLUGIN_HTTP_DOH_BOOTSTRAP` | 含义 | DoH 端点（拨号地址） | DoH 连接的 TLS 身份 |
|---|---|---|---|---|---|
| K1 | 未设置 | 未设置 | DoH 关闭，行为与基线相同 | — | — |
| K2 | `https://<IP 字面量>[:port]/path` | 未设置 | 使用 IP 形式的 URL | URL 中的 IP（只有这一个端点） | 证书必须含该 IP 的 IP SAN。按 RFC 6066 不发 SNI【假设：以 E2E 记录为准】 |
| K3 | `https://<主机名>[:port]/path` | 一个或多个 IP 字面量 | 主机名加 bootstrap | bootstrap 中的各个 IP，按配置顺序 | 证书必须匹配该主机名；SNI 和 `Host` 都用该主机名（带非默认端口时，`Host` 含端口） |

除 K1–K3 以外的组合都是配置错误，处理方式见 §2.4。例如：

- 只设了 bootstrap；
- 主机名 URL 没有配 bootstrap；
- IP URL 又配了 bootstrap；
- URL 不是 `https://`；
- bootstrap 中有一项不是 IP 字面量。

**端点规则**：K2 的 URL IP 与 K3 的每个 bootstrap 适用同一规则，都必须是**单播** IP 字面量。组播、未指定地址（`0.0.0.0`、`::`）和广播都属于配置错误。

**端点可以不是公网地址**：端点是所有者显式提供的出口配置，不是插件输入，因此可以指向局域网里自建的 DoH。这与目标地址必须公网的规则（§3.4）是两套规则，见 §3.5 I2。

**不提供的功能**：不内置默认 DoH 服务商，不自动探测 fake-ip。

**IP SAN 实测**【实证，2026-11-21，开发机，非生产容器】：`1.1.1.1`、`8.8.8.8`、`9.9.9.9`、`223.5.5.5`、`1.12.12.12` 在 443 端口上的证书都含对应的 IP SAN，证书链校验通过。生产容器能否连通这些地址**未核**（§3.9）。

### 2.4 启动结果与 CA 不可用【推荐，Q10】

**总原则**：DoH 模块不新增任何启动失败，只有“显式配置写错”一种情况例外。整机启动结果一律与**相同环境、相同配置的基线**对照，不作绝对承诺。原因是基线中别的模块可能已经会因同一个 CA 文件而启动失败：网页读取在装配 `DirectPageExtractor` 时就会构造读取 `SSL_CERT_FILE` 的 SSL 上下文（`application/modules/web.py:296,310`、`web/http_transport.py:189-197`），而这一装配本身受网页配置控制【实证】。

| 情形 | 整机启动 | DoH 模块自身 | 运行时 |
|---|---|---|---|
| K1（DoH 关闭），无论 CA 状态如何 | **与相同配置的基线相同** | 不构造任何对象，不读文件 | 与基线相同 |
| 不属于 K1–K3 的配置错误 | 失败。这是 DoH 模块唯一新增的启动失败，与 `Settings`（`config.py:59`，pydantic `BaseSettings`）对其他非法设置的处理一致 | — | — |
| K2/K3，且 `SSL_CERT_FILE` 不存在或不可读 | **与相同配置的基线相同**：网页模块被装配就失败，未装配就成功 | 启动阶段不构造 DoH 的 SSL 上下文，不读该文件 | 见下方“运行时归类” |
| K2/K3，且 `SSL_CERT_DIR` 不可用 | 与相同配置的基线相同 | 同上 | 见下方“运行时归类” |

**运行时归类**

“需要 DoH 的请求”指：DoH 开启、插件只有 allowlisted 权限、目标主机是域名。目标是 IP 字面量，或插件有 unrestricted 权限时，都**不会**向 DoH 发查询，所以不受 CA 状态影响（E24、E23）。

需要 DoH 的请求在建立 DoH 连接时，按能判明的事实分两类：

| 能判明的事实 | 返回 | 日志类别 |
|---|---|---|
| 构造 DoH 的 SSL 上下文时，读取 `SSL_CERT_FILE` 抛出 `FileNotFoundError` 或 `PermissionError`（本地 CA 不可用） | `http.dns_failed` | `doh_ca_unavailable` |
| 构造 DoH 的 SSL 上下文时，`SSL_CERT_FILE` 能读但内容无效（空文件、不是证书、PEM 损坏），抛出 `ssl.SSLError` | `http.dns_failed` | `doh_ca_invalid` |
| TLS 握手时证书校验失败。`SSL_CERT_DIR` 不可用时会表现为找不到签发者，在协议层与“证书不受信”无法区分，也归入这一类 | `http.dns_failed` | `doh_tls` |

以上三类都**不回退**到 certifi 或系统 DNS，目标零拨号。

本机实测（Python 3.12.16，OpenSSL 3.5.9）【实证】：空文件、纯文本文件、Base64 损坏的 PEM，在 `create_default_context(cafile=...)` 构造时都抛 `ssl.SSLError`；前两者的 reason 为 `NO_CERTIFICATE_OR_CRL_FOUND`。生产容器中的 OpenSSL 版本与实际行为【假设】，以 E25⑤ 记录为准。

本机实测【实证，Python 3.12.16】：

- `ssl.create_default_context(cafile=不存在)` 在构造时抛出 `FileNotFoundError`；
- `capath=不存在` 构造时不报错。

所以只能判明 FILE 类的“不可用”，DIR 类只能归入 TLS 错误。DoH 的 SSL 上下文在首次需要时构造；构造失败不缓存，下一次需要 DoH 的请求会重新构造。

## 3. 安全审查

### 3.1 Bootstrap

- 不用系统 DNS 解析 DoH 主机名，原因有二：fake-ip 环境下会自我依赖；DoH 的目的地也不应由本地 DNS 决定。
- 多个 bootstrap 地址时，**只有 TCP 连接失败**才按配置顺序换下一个。TLS、HTTP 或报文出错，**下一个 bootstrap 零拨号**，直接拒绝（E3b）。
- 所有尝试共用 §3.7 的截止时间。

### 3.2 认证与 CA

**服务端认证（必须）**：

- 严格校验证书链，以及主机名或 IP SAN；
- 不提供 `verify=False`；
- 不回退到明文 `http://`、DoT 或 53 端口。

**CA 来源**：基线插件客户端设了 `trust_env=False`，所以只用 certifi（httpx `_config.py:34-40`、`_transports/default.py:153`）。

| 选项 | DoH 连接 | 目标连接 |
|---|---|---|
| C1【推荐，Q9】 | 独立的 `httpx.create_ssl_context(trust_env=True)`：读 `SSL_CERT_FILE`/`SSL_CERT_DIR`，否则用 certifi。客户端仍是 `trust_env=False`，不读代理 | **保持只用 certifi** |
| C2 | 同 C1 | 也读 `SSL_CERT_FILE/DIR` |
| C3 | 只用 certifi | 只用 certifi |

C1 中两类 CA 的隔离见 §3.5 I1。

**信任边界（写入文档）**：

- Host 信任 DoH 运营者，以及 DoH 连接所用的 CA 集合；
- 不做 DNSSEC 校验，也不以 AD 位作为条件；
- DoH 运营者能看到所有插件查询的主机名。

**客户端凭据**：第一阶段不支持（Q2）。

**DoH 请求本身**：

- 只发协议必需的头：`Accept`/`Content-Type: application/dns-message` 和 `Host`。
- 不带插件传入的任何 Header、Authorization、Cookie 或 Proxy-Authorization。
- 不跟随重定向。
- 响应体超过 65535 字节（DNS 报文的协议上限）即拒绝。
- 查询报文设置 RD=1。

### 3.3 DNS 判定：A/AAAA、CNAME、DNSSEC、终结否定、截止

**协议与查询方式**

- 使用 RFC 8484 `application/dns-message`，报文用 `dnspython` 解析（Q3）。
- 查询设 RD=1，**不设** DO 位。
- Host 不做 DNSSEC 校验，也不把 AD 位当作判断条件。

**查询状态**

每个查询在截止时间到来时，处于下面两种状态之一：

| 状态 | 含义 |
|---|---|
| **已完成** | 截止前收到完整的 HTTP 响应。随后按第一步到第三步分类 |
| **未完成** | 截止时还没收到完整响应，可能停在拨号、TLS、发送请求、等待响应头或读响应体任一阶段。**不参与报文分类**，只参与优先级判断 |

**第一步：报文合法性**

已完成的应答若违反下列任一项，归为“错误”：

- HTTP 状态码为 200；
- Content-Type 正确；
- 能解析为 DNS 报文；
- QR=1，opcode=QUERY；
- question 与请求一致；
- TC=0；
- RA=1；
- RCODE 为 NOERROR 或 NXDOMAIN；
- 响应体不超过 65535 字节。

DoH 连接本身的失败（TCP 被拒且没有剩余 bootstrap、TLS 失败、CA 不可用、3xx）在截止前发生时，也算“已完成”，归为“错误”。

**第二步：CNAME 链（A 与 AAAA 各自独立建链）**

- 从 qname 出发，沿 answer 节里 owner 等于当前名的 CNAME 逐步跟随，走到没有 CNAME 的名为止，这个名就是**链尾**。
- 两族的链**各自**建立、各自验证，可以不同（例如 CDN 轮换）。一族的链出错，只让这一族归为“错误”。
- **原始逐条记录**【推荐】：所有“数量”和“冲突”类检查，都基于报文中**逐条可区分**的原始记录（answer 和 authority 两节），不基于解析库合并后的 RRset。涉及的检查有：同一 owner 有多个 CNAME、CNAME 与其他数据共存、SOA 条数、owner 与链的关系。
  - 理由【来源：Codex 引用的 dnspython 文档与源码，本机未安装 dnspython，**未复核**】：`dns.message.from_wire` 默认会把记录归并成 RRset，而 `Rdataset.add` 对 CNAME 这类 singleton 类型会先清掉已有值。若在归并之后才检查，冲突的 CNAME 或多条 SOA 可能只剩最后一条，被掩盖掉。
  - 实施时具体用 dnspython 的哪种解析方式（例如是否能保留逐条记录），在写 E7 时确定；做不到逐条区分时，必须自行按 RFC 1035 的报文格式遍历资源记录。
- **同一 owner 有多个 CNAME 且目标不同** → 错误。目标完全相同的重复记录按一条处理。
- **链成环** → 错误。
- **同一 owner 上 CNAME 与冲突的数据记录并存**（如 A、AAAA 或其他非 DNSSEC 类型）→ 错误。
- **CNAME 与 DNSSEC 元数据并存**（`RRSIG`、`NSEC`、`NSEC3`）**不算冲突**（RFC 4035 §2.5）。这些记录一律忽略：不验证、不采信，也不据此判断。
- owner 不在链上的记录一律忽略，既不检查也不连接。
- 链长不设经验上限，由 65535 字节的报文上限和成环检测兜底。
- CNAME 目标不按白名单检查。白名单约束的是逻辑主机；最终地址另由 §3.4 检查。

**第三步：归类**（均以本族链尾为准）

| 归类 | 条件 |
|---|---|
| **地址** | NOERROR，且链尾有本 qtype 的记录 |
| **NODATA** | NOERROR；链尾没有本 qtype 的记录；authority 节**恰有一条** SOA，且其 owner 是链尾本身或链尾的祖先域 |
| **NXDOMAIN** | RCODE=NXDOMAIN（RFC 6604：指链尾不存在，前面可以有 CNAME），且 authority 节有满足同样条件的 SOA |
| 转介 → **错误** | NOERROR，没有本 qtype 记录，authority 节有 NS 而没有 SOA |
| 未完成别名 → **错误** | NOERROR，answer 节有 CNAME，但链尾既没有本 qtype 记录，也没有满足条件的 SOA。不另外发查询去追链尾 |
| 无证据的否定 → **错误** | 没有本 qtype 记录，也没有 SOA 或 NS |

**接纳策略声明**：RFC 2308 允许不带 SOA 的否定应答（例如其中的“NODATA type 3”）。本项目**有意更严格**：没有 SOA 作证据的否定，一律当作错误，失败关闭。主流递归 DoH 的否定应答会不会带 SOA，尚未核实【假设】。实施前须对所选 DoH 的真实应答做一次只读核对。如果所选服务不带 SOA，只有单族地址的域名会被拒绝，届时由所有者决定换服务还是改规则（Q14）。

**第四步：两族合并**（只在两族**都已完成**时适用）

| A ＼ AAAA | 地址 | NODATA | NXDOMAIN | 错误 |
|---|---|---|---|---|
| **地址** | 两族地址全部检查 | 只用 A | 拒绝（两族矛盾） | 拒绝 |
| **NODATA** | 只用 AAAA | 拒绝（无地址） | 拒绝 | 拒绝 |
| **NXDOMAIN** | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| **错误** | 拒绝 | 拒绝 | 拒绝 | 拒绝 |

**优先级**（结论唯一）【推荐，Q6】

A 与 AAAA 并发发起。两族都等到“已完成”或截止，**不因其中一族先失败而取消另一族**。

| 优先级 | 条件 | 插件看到的结果 |
|---|---|---|
| 1 | 某族**已完成**且归为“地址”，其中有地址未通过 §3.4 | `PluginPermissionError` |
| 2 | 不满足 1；且某族**已完成**并归为“错误”，或两族都已完成、按第四步合并后为拒绝 | `PluginResult(ok=False, error_code="http.dns_failed")` |
| 3 | 不满足 1、2；且有一族**未完成** | `http.request_failed` |

推论：

- 已完成且归为“错误”的报文里，即使带有私网地址，也只算优先级 2，因为这些地址未被采信。
- 一族“地址全部通过”、另一族“未完成”时，归优先级 3。不能拿半边结果去连接，因为 D1 要求检查**全部**地址。

现有系统解析路径对空结果返回的是 `PluginPermissionError`（F2），与 DoH 路径不同。这一差异写入文档；按 D3，系统解析路径不改。

**三种计数**

E2E 要区分以下三种计数，不再笼统地说“各恰好一次”：

| 计数 | 含义 | 期望 |
|---|---|---|
| **发起** | 客户端开始的 DoH 查询数，按 qtype 统计 | 目标为域名时，每跳 A、AAAA **各 1**；IP 字面量或跳到白名单外时为 0 |
| **拨号** | 网络层对 DoH 端点的 `connect_tcp` 次数 | **不作统一承诺**。CA 预先失败（§2.4）时拨号为 0；DoH 客户端复用已认证的连接时，也可能没有新拨号（I4 只对目标客户端禁用 keepalive）。只有明确要求新建连接的子例（E3b、E4、E21）才断言拨号次数。**所有**实际发生的 DoH 拨号都必须属于配置的端点集合 |
| **收到** | DoH 服务端收到的 HTTP 请求数 | 只有 TLS 成功且在截止前发出请求时才计入；TLS 失败时为 0 |

**TTL 缓存**：第一阶段不缓存，每跳都重新查询（Q4）。

### 3.4 地址检查：公网单播、site-local 与 NAT64

**DoH 分支对目标地址的条件**（新代码只在 DoH 分支使用）：

1. IPv4：`is_global` 为真，且 `is_multicast` 为假。
2. IPv6：`is_global` 为真，`is_multicast` 为假，且 **`is_site_local` 为假**（D6）。
3. 地址落在 `64:ff9b::/96`（NAT64 知名前缀）时，把内嵌的 IPv4 取出来，再按第 1 条检查。

**本机 Python 3.12.16 实测【实证】**

| 地址 | `is_global` | 其他属性 | DoH 分支结论 |
|---|---|---|---|
| `224.0.0.1`、`233.252.0.1`、`239.255.255.250`、`ff02::1`、`ff05::2`、`ff0e::1` | **True** | 组播 | 拒绝 |
| `fec0::1`、`feff::1` | **True** | `is_site_local=True` | 拒绝（D6） |
| `64:ff9b::7f00:1`（内嵌 `127.0.0.1`） | **True** | — | 拒绝（内嵌地址不是公网） |
| `::7f00:1`、`::a00:1`（已弃用的 IPv4 兼容地址 `::/96`，内嵌 `127.0.0.1`、`10.0.0.1`） | **True** | — | 现稿规则下**会通过**，见 Q12 |
| `5f00::1`（`5f00::/16`） | **True** | — | 现稿规则下**会通过**，见 Q12 |
| `64:ff9b:1::a00:1`、`::ffff:10.0.0.1`、`2002:7f00:1::1`、`fc00::1`、`fe80::1`、`::1`、`::`、`0.0.0.0`、`255.255.255.255`、`100.64.0.1`、`198.18.0.1`、`2001:db8::1`、`2001::1`、`3fff::1`、`100::1` | False | — | 拒绝 |
| `2606:4700:4700::1111`、`2001:4860:4860::8888`、`192.88.99.1`、`64:ff9b::808:808` | True | — | 通过 |

**结论**：标准库的 `is_global` 不等于“可作为单播目的地的公网地址”，单靠逐条排除很难列全。

**Q12【推荐】**：DoH 分支的 IPv6 地址再加一条正向条件——必须属于 `2000::/3`（RFC 4291 的全球单播分配范围）。效果如下：

- **一并排除** `fec0::/10`、`::/96`、`5f00::/16`、`64:ff9b::/96`，第 2 条中的 site-local 判断和第 3 条的 NAT64 处理因此变成冗余，但为了明示仍保留在规则表里；
- **代价**：NAT64 知名前缀下的公网内嵌地址（如 `64:ff9b::808:808`）也会被拒。
  - **更正第五版**：第五版写“公共 DoH 不做 DNS64 合成”，**这是错的**。Google Public DNS64 就是公开提供、支持 DoH 的 DNS64 服务【来源：Codex 引用的 Google 官方文档，本会话未复核】。
  - **取舍**：如果所有者选了做 DNS64 的 DoH 并采用 `2000::/3`，那么对只有 IPv4 的公网域名，应答是“公网 A + 合成的 `64:ff9b::/96` AAAA”。按 D1“任一地址不通过即拒绝”，**整跳都会被拒**，即便 A 本身可用。不采用 `2000::/3` 时，同样的应答因内嵌 IPv4 是公网而能通过。
  - **推荐**：仍采用 `2000::/3`，同时在运维文档中写明“不要选择做 DNS64 合成的 DoH”。Q14 核对所选解析器时，一并记录它是否做 DNS64 合成。
  - `2000::/3` 范围内的网络专用 NAT64 前缀（N1）仍要靠出口侧约束。

**不采纳 Q12 时**，须至少补两条显式排除：`::/96` 和 `5f00::/16`。

上表是 3.12.16 的分类结果，其他补丁版本可能不同。E8 会把实际值写进产物。

**系统解析路径不改**（D3）：unrestricted 和 DoH 关闭时的 allowlisted 都**不加**上述任何检查。组播、site-local、`::/96`、`5f00::/16`、`64:ff9b::7f00:1` 在这些路径上仍会通过，作为已记录的现状缺口 N3、N4。

### 3.5 隔离：CA、端点、Host/SNI、连接池

| # | 要求 | 违反的后果 |
|---|---|---|
| I1 | **CA 隔离**：DoH 的 `SSLContext` 只用于 DoH 连接；DoH 分支的目标连接只用 certifi（C1）。两个上下文是不同对象 | 为 DoH 配置的私有 CA 会被用来信任目标 |
| I2 | **端点隔离**：DoH 端点（K2 的 URL IP 或 K3 的 bootstrap）只用于 DoH 连接，不进入目标地址集合，也不因为和目标同 IP 就跳过 §3.4 的检查；DoH 应答里的地址也从不用来连接 DoH 端点 | 两套信任来源混在一起 |
| I3 | **Host/SNI 隔离**：DoH 连接的 `Host` 是 DoH URL 的 authority，SNI 是 DoH 主机名（K2 不发 SNI）；目标连接的 SNI、证书主机名和 `Host` 都是该跳的逻辑域名，插件传入的 `Host` 被丢弃（`http_client.py:22,115`） | 域前置；拿一个名字的证书去服务另一个名字 |
| I4 | **连接池隔离**：DoH 分支使用**专用的** DoH 客户端和**专用的**目标客户端，目标客户端 keepalive=0，所以同 IP、同端口也会重新握手。基线共享的 `SafeHttpClient`（`application/modules/plugins.py:107-110`）**不改配置**，unrestricted 和 DoH 关闭的路径继续使用它 | 连接池按 `(scheme, IP, port)` 复用时，为某个名字验证过的 TLS 连接会被拿去承载另一个名字的请求 |

I4 只适用于 DoH 分支。基线共享客户端的复用行为本 PR 不改（D3）。

### 3.6 固定 IP、多地址与目标请求次数【推荐，Q6】

**拨号顺序**：先 A 后 AAAA，各自按应答中的顺序。

**换地址规则**：

- **只有 TCP 连接失败**才换同一已检查集合中的下一个地址。换地址时不重新解析，也不换解析来源。
- TCP 建立之后，TLS 握手、证书校验、读写或超时中任一失败，都直接返回结果：下一个候选地址**零拨号**（E14），也不重发请求，避免重放非幂等请求。

**每跳目标请求次数**：

- 目标服务端至多收到 1 次 HTTP 请求；
- TLS 失败时为 0 次；
- 跳到白名单外或私网 IP 字面量时，目标零拨号。

### 3.7 统一截止时间【推荐，Q5】

**基线（F9）**：每个操作各自计时，重定向时重新计时，读响应体也没有总时限。

**DoH 路径的规则**：

- `SafeHttpClient.request()` 取得并发许可后，确定一个截止时间：`deadline = 当时 + plugin_http_timeout_seconds`（`config.py:304`，默认 15.0）。
- 以下所有步骤都只能用剩余时间，剩余时间 ≤ 0 即失败：
  - 所有跳的 DoH 查询，包括 bootstrap 续试；
  - 目标的 TCP 连接、TLS 握手、发送请求、接收响应头；
  - 读完整个响应体；
  - 所有重定向。

未启用 DoH 的 allowlisted 和 unrestricted 都不变（D3）。

### 3.8 重定向：正文与凭据

**每跳流程**：每一跳都重新执行 §2.1 全流程，并扣减同一个截止时间。

**提前拒绝**：

- 跳到白名单之外的主机：在**发出 DoH 查询之前**拒绝（E10）。
- 跳到 IP 字面量：不查 DoH，直接按 §3.4 检查。

**`Location` 解析**：相对 `Location` 以**逻辑 URL** 为基准解析，不以 IP URL 为基准（`http_client.py:144`）【实证】。

**正文与凭据的去留**。基线规则【实证，`http_client.py:107-114,126,145-147`】：是否“同源”以**第一跳**的逻辑 `(scheme, host, port)` 为准；一旦出现不同源的一跳，此后**所有**跳都不再携带调用方数据（Header、Authorization、Body），即使之后又跳回原来的源也一样。

| 重定向 | 同源 | 跨源（或此前已出现跨源） |
|---|---|---|
| 301、302、307、308 | 保留方法、正文、调用方 Header 和 Authorization | **保留方法**；正文、调用方 Header、Authorization 全部丢弃 |
| 303 | 改为 GET，丢弃正文；Header 和 Authorization 保留 | 改为 GET；全部丢弃 |

**基线的一个副作用**：跨源的 307/308 会以原方法（例如 POST）发出一个**没有正文**的请求。DoH 路径是否保留这一行为见 Q11。推荐保留基线语义：不新增拒绝规则，在文档中说明；E2E 记录目标实际收到的方法和正文长度（E12）。

**重定向响应的正文**：不读取，也不返回给插件。连接在 `finally` 中关闭（`http_client.py:189-191`），也不计入响应体大小上限。

### 3.9 DoH 可达性

- DoH 连接不读代理变量，直接连 bootstrap IP 或 URL 中的 IP。
  - 在 TUN 环境下，这类连接**预期**由 TUN 接管并按规则转发；TLS 保证内容完整和服务器身份。
  - **本部署的 DoH 可达性未验证**【假设】：唯一的现场证据是 GitHub 加入 filter 后恢复（§1.1），说明不了 DoH 端点能否连通。Q13 的只读报告也没有涉及可达性。
- **只能经显式代理出网**的部署里，DoH 不可达，所有 allowlisted 请求都会失败关闭（L1）。
- 不做启动探测，也不设健康门槛；启动只校验配置格式（§2.4）。
- 运维文档给出一次性人工核对方法：在 Bot 容器内向 bootstrap IP 发一次 DoH 查询。
- 看门狗目前看不到这类失败（与 Q8 同源）。

### 3.10 分阶段保证与边界：透明代理、NAT64

**DoH 分支在 Bot 进程内能保证的事**，按阶段分开写：

| 阶段 | 保证 | 不保证 |
|---|---|---|
| **G1 DoH 端点拨号** | 只连 K2 的 URL IP 或 K3 的 bootstrap，不连其他地址。端点可以是内网地址（所有者配置）。之后的 TLS 用 DoH 专用上下文验证 DoH 身份 | 端点本身可不可信、DoH 给的应答是否真实，都交给所有者对 DoH 运营者的信任（§3.2） |
| **G2 目标拨号** | 只连通过 §3.4 检查的地址。目标是域名时，地址来自本跳 DoH 应答且两族全部检查过；目标是 IP 字面量时，就是该字面量本身 | **TCP 先于证书校验建立**：即使之后证书不符，SYN 和握手报文也已经发到了这个已检查的地址 |
| **G3 HTTPS 请求发出** | 只在目标证书经 certifi 验证、且与逻辑域名匹配之后，才发出请求行、Header、凭据和正文 | **`http://` 目标没有这一阶段**：只有 G2 的地址保证，没有身份保证，请求内容是明文 |

**超出进程 socket 的部分 Host 一概不保证**。下面这些情况都在 G1–G3 之外：

| # | 情况 | 说明 | 状态 |
|---|---|---|---|
| L1 | 只能经显式代理出网 | 不支持，失败关闭 | 【issue】仅能证明：GitHub 加入 filter 后已恢复（§1.1） |
| T1 | 透明代理改写目的地 | 例如 Clash/Mihomo 开了 `sniffer` 的 `override-destination`，会让 G2 失效；Host 检测不到。部署必须为 Bot 流量关闭这一改写 | 【假设】生产配置未核 |
| T2 | 透明 TLS 解密 | DoH 分支的目标连接只信 certifi，被解密的连接会失败。若所有者把解密代理的 CA 放进 `SSL_CERT_FILE`，G1 的信任会扩展到该代理 | 【推论】 |

| T4 | `dns-hijack` | 只作用于 53 端口 | 【推论】 |
| N1 | 网络专用 NAT64 前缀（NSP） | 从地址上无法识别。在 `2000::/3` 范围内的 NSP 地址会通过 | 【推论】 |
| N2 | DNS64 | 同时查询的 A 记录若含私网地址，整跳会被拒 | 【推论】 |
| N3 | 系统解析路径的 NAT64、`::/96`、site-local 缺口 | D3，不修 | 【实证】 |

## 4. 备选方案与不选理由

- **P. 按域名经代理**（第一版的推荐）【不选，D2】：
  - 由代理解析域名，Host 看不到最终地址；
  - 被批准域名指向内网，或代理规则 `DIRECT` 到局域网时，会连进内网，代理 `192.168.5.2` 本身就在局域网里；
  - 防护效果取决于部署者的代理规则，无法由代码或 E2E 证明；
  - `0177.0.0.1`、`2130706433` 这类写法会被 `ipaddress` 当作主机名（实测），交给代理后怎么解释无法控制。
- **B. 放行 `198.18.0.0/15`**【不选，D4】：
  - fake-ip 环境下所有主机名都拿到这一段的地址，检查对**所有**名字失效；
  - 等于把代理软件的可配约定写死在代码里；
  - 会误放真实网络中的 `198.18.x`；
  - 与 `sandbox/network_guard.py:24` 把该段列为私网相矛盾。
- **C'. DoH 加经 HTTP 代理 CONNECT 已校验的 IP**【本阶段不做】：
  - 能覆盖 L1“只能经代理出网”的部署；
  - 目前唯一的现场证据是 GitHub 加入 filter 后恢复（§1.1）。“本部署经 TUN 直连 DoH 端点可行”**未经实测**；如果实测不可行，C' 的优先级需要重新评估；
  - 会引入代理选择和隧道清理，且代理侧仍有 T1 风险；
  - 前提是 DoH 端点另有可达路径，例如 DoH 也经代理，或者能直连。
- **S. SOCKS**【不纳入，D5】。
- **D. 逐个域名加 `fake-ip-filter`**【现状临时处理】：保留为未配置 DoH 时的做法，也是 unrestricted 在 fake-ip 环境下唯一的办法。

## 7. E2E：先写的失败情况与记录项（实施阶段第一步，现在未写）

### 7.1 测试环境

不访问外网，不连生产。

- **DoH 服务**
  - 进程内 loopback TLS DoH，可按情况返回预设报文。
  - 带**屏障**模式：A、AAAA 两问都到达之后才开始回复，并记录“首个回复发出前两问是否都已到达”。
  - 证书有两类：主机名证书，和含 `127.0.0.1` IP SAN 的证书，均由 **DoH 专用 CA** 签发。
- **目标服务**
  - loopback TLS 目标，支持虚拟主机，按 SNI 选择证书，按 `Host` 返回不同正文。
  - 证书由**目标专用 CA** 签发；E18 另用一张由 DoH 专用 CA 签发的证书。
  - E16 需要一个能同时扮演 DoH 和目标的**同端口**服务：按 SNI 区分角色，并记录每次 TLS 握手的 SNI。
- **注入点（只有三处）**
  1. 测试用的 httpcore 网络后端：记录每次 `connect_tcp(ip, port)`，把预设的“公网”测试 IP 和端口转发到对应的 loopback 服务。
  2. 包在 DoH 客户端 transport 外面的计数器：记录“发起”的查询数和 qtype，然后原样转交给真实 transport。
  3. 包在目标客户端 transport 外面的观测器：只记录响应正文流的消费情况（见 §7.2“消费端”），不修改数据。
  - 除这三处外，解析、检查、TLS 和重定向都走真实代码。
- **系统解析器**：可计数。默认返回 `198.18.0.x`，模拟 fake-ip。E15 和 E23①② 返回公网测试 IP。E23③ 把字面量**原样返回**，并记录返回值。
- **记录型代理**：设为 `HTTPS_PROXY`，用来证明插件请求从未经过代理。
- **CA 注入**
  - DoH 专用 CA 通过 `SSL_CERT_FILE` 注入（C1）。
  - 目标专用 CA 通过现有的 `SafeHttpClient(client=...)` 注入，DoH 分支专用的目标客户端按实施时提供的同类构造参数注入。
  - 另加一条装配断言：生产装配里共享客户端的配置不变，DoH 分支的目标客户端只用 certifi 且 keepalive=0，DoH 客户端使用独立的上下文。
- **入口**：全部经真实的 `BoundHttpFacade`。
- **合成凭据与正文**
  - `auth_secret` 指向测试 Secret，值为固定的合成串；
  - 伪造的 `Authorization` 用另一个合成串；
  - 正文是固定的合成字节串。
  - 产物里只写“是否相等”的布尔值，**不写任何值**。
- **基线**：用同一套测试代码跑一遍。DoH 相关的环境变量照样设置，基线会忽略它们。
