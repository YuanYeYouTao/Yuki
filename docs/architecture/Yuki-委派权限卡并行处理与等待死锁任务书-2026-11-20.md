## 2. 代码事实【实证】

| # | 事实 | 依据 |
|---|---|---|
| K1 | `wait` 不看被等待的委派是否正在等本 Work 回答，直接登记并返回 `waiting` | `runtime/work_control.py` 1130–1196 |
| K2 | 登记时只对**未消费**的唤醒类输入重新发信号；已消费但请求仍未答的卡不在考虑之内 | `runtime/work_wait.py` 298–324 |
| K3 | `owned_run` 只在子任务终态（completed/failed/cancelled/detached/uncertain/unknown）时匹配；子委派处于 `waiting_user`（等父 Work 回答）永不匹配 | `runtime/work_wait.py` 998–1014 |
| K4 | 委派仍待回答的请求可由事实计算（事件 + 回答操作），不依赖输入是否已消费 | `external_agents/delegation.py` `pending_requests`、`_unowned_waits` |
| K5 | `get_tasks(id, cursor)` 把同一个 cursor 先交给 Work 进度查询（要求 `[时间戳, 键]` JSON），对委派记录的时间线游标（事件 ID）必然报 `invalid_work_progress_cursor`，到不了 `delegations.timeline` | `runtime/work_control.py` 951–972；`runtime/work_queries.py` 171–177 |
| K6 | `message_task` 回答后只返回 `{id, answered, status}`，不告诉模型该委派还剩哪些未答请求 | `external_agents/subtasks.py` `message_external` |
| K7 | 刚登记、回执未到的回答不计入 `pending_requests` 的"已答"集合（只认有结果且无 error 的 respond） | `delegation.py` `pending_requests` 中 `answered` |

## 3. 设计（待审查）

原则：按事实在执行处核验；不改工具声明与系统提示（前缀缓存不变，变化只出现在工具结果里）；不加经验阈值。

1. **等待前先核对"子任务是否在等你"**（修 K1–K3）
   - `wait` 中每个 `owned_run` 目标若是委派记录，且按 K4 有本 Work 可回答的请求（`answer_at` 为 `yuki_or_user` 或 `deny_only`；观察记录的 `native_terminal` 不算），就**拒绝登记**。
   - 返回错误 `run_waiting_for_you`，逐条列出未答请求（`permission_id`、类型、工具、收到时间）：先回答，再等待。
   - 与 `mode`（any/all）、其他条件无关：只要等待目标在等本 Work，就先答。
   - 核验读的是事实，不依赖卡片输入是否已消费，覆盖本次情况。
   - 核验与登记之间新到的卡仍是未消费输入，被 K2 的重发信号覆盖（现有行为，需测试锁定）。
2. **逐卡处理的反馈**（修 K6、K7）
   - `message_task` 回答结果附 `remaining`：该委派其余未答请求，同样逐条列出。
   - 计算时把本次刚登记的回答（按原生请求 ID）视为已答，避免把刚答的那张又列为未答。
   - 每张卡、每次回答仍一一对应（一个 `reply_to` 只答一个请求），不提供批量回答。
3. **时间线游标**（修 K5）
   - 对有卡片的委派记录，`cursor` 只用于时间线，不传给 Work 进度查询（委派记录没有 Yuki 循环，进度为空）。
   - 不改工具 schema。
4. **不做**：
   - 不改卡片投递或输入消费机制（证据显示投递正确）；
   - 不对子任务的 `waiting_user` 自动匹配 wait（会在模型不答时反复立即返回，形成空转；拒绝登记并列出请求更直接）；
   - Yuki 自己的子 Work（非委派）的 `waiting_user` 是否同样处理【决定】，本书只覆盖委派记录。

## 4. 失败情况与测试（先写失败测试）

| # | 失败情况 | 测试 |
|---|---|---|
| W1 | 两张并行卡、只答一张后 `wait(run)` 被登记并挂起（本次事故） | 集成：设备连发两个权限事件 → 父 Work 答后一张 → `wait(run)` 返回 `run_waiting_for_you`，含前一张的 `permission_id`；`runtime_work_waits` 无新 active 行 |
| W2 | 两张都答后 `wait` 仍被拒 | 同上，全部答完 → `wait` 正常登记；委派完成时唤醒 |
| W3 | 卡片已消费但请求未答，`wait` 仍登记 | 卡片输入置为 consumed 后调 `wait` → 拒绝（核验不依赖消费状态） |
| W4 | 核验通过后、登记前到达的新卡丢失 | 在核验与登记之间注入新权限事件 → 登记后立即被唤醒（K2 路径） |
| W5 | 登记后到达的新卡不唤醒 | 回归：等待中到达新卡 → 唤醒（现有行为） |
| W6 | 无主 deny-only 等待被忽略 | 委派上有 `deny_only` 等待 → `wait` 拒绝并列出 |
| W7 | 观察记录的等待阻止父 Work 等待 | 观察记录的 `native_terminal` 请求 → 不拒绝 |
| W8 | 回答结果不列剩余请求，或把刚答的列为未答 | 连发三张，答第一张 → `remaining` 恰为另外两张；答完 → `remaining` 为空 |
| W9 | 时间线游标报 `invalid_work_progress_cursor` | `get_tasks(id=委派, cursor=时间线 next_cursor)` → 返回下一页时间线 |
| W10 | 真连接器下并行请求逐一处理 | E2E：CLI 线路一条助手消息发两个 `can_use_tool` → 父 Work 答一个后 `wait` 被拒 → 答另一个 → 线路收到两个应答，回合结束 |
