# Yuki 开发架构约束

这是当前开发的共同约束。功能任务书、历史验收报告、旧版本发布说明不覆盖本文。
新增功能和临时补丁都要遵守；发现代码与约束冲突时，应标明缺口并修正依赖方向，
不能把现有残留实现当成新功能的模板。

本文描述应保持的边界，不等于所有存量代码已经完成解耦或所有修改已上线。
当前实现、待验证修改和生产状态必须分别说明。

## 1. 永久主体不依附平台账号

一个数据库对应一个长期存在的 Yuki。Person、Space、Conversation、Presence、
Binding、GatewayConnection 分别表示人、空间、会话、自身平台账号、外部绑定和连接。

- 人物记忆、关系和偏好属于 Person；群空间状态属于 Space；SELF 属于 Yuki。
- QQ 号、群号、Provider 名称和连接句柄不是业务所有者。
- 换账号、切网关、连接重建不改变 Conversation generation，不复制记忆或人物。
- 模糊名称、多个 Binding 或多个候选必须明确消歧；不能取第一项冒充唯一结果。

详见 [canonical runtime](canonical-runtime.md)。

## 2. 事件 ID 沿处理链向下传递

需要区分三种标识，不能因名称相近互相替换：

| 标识 | 用途 |
| --- | --- |
| `chat_events.id`、`trigger_event_id`、`source_event_id` | 内部账本事件主键；运行时快照、工具回执、因果关系按此定位 |
| `canonical_event_id` | canonical 事件关联标识；不等同于账本整数主键 |
| `platform_message_id`、OneBot `message_id` | 平台消息凭据；用于接入去重、引用、撤回和平台投递关联 |

接入层解析平台事件并写账本；此后主 Agent、工作调度、子 Agent、工具审计和 Memory
应携带可信内部事件 ID。事件已经存在时，禁止再用 QQ 消息 ID 或消息正文扫描账本、
猜测“最新一条消息”或重建来源。按主键读取后仍须核验 Conversation 和来源边界。

平台消息凭据只在确实需要与网关交互的位置使用。保留凭据用于来源展示或投递关联，
不意味着它可以决定内部身份、所有权或任务恢复。
没有对应事件的定时或系统工作，应使用自己的可信工作/运行身份；不能伪造用户入站事件。
内部 ID 缺失时不得静默回退到平台 ID 查找；明确处理无事件场景或拒绝不完整上下文。

接入写账本后，Host 在 `InboundMessage.source_event_id` 中盖入内部主键；主动群聊、
插件、管理命令和 Memory 必须继续传递它。无用户事件的工作使用 Host 提供的
`source_execution_id`，不能借用 `message_id` 作为执行身份。
任务接纳及改向输入使用 `event:<conversation_id>:<event_id>` 去重；联网来源按
`trigger_event_id` 或真实 `execution_id` 查询、授权和清理。历史当前消息替换按内部 ID。

0058 迁移转换已有任务的接纳键，保留任务 ID、预算、检查点、模型历史和执行回执。
旧联网来源只在迁移时按会话唯一匹配一次；无法确认来源的有界搜索缓存清理掉，
不删除聊天账本和工作区。运行时不保留同类平台回查兜底。
平台凭据仍可保存于接入去重、引用解析、撤回和投递回执中；纯审计展示字段不是授权依据。

## 3. 适配层只转换协议，不重新决策业务

依赖方向为：传输适配 → 应用入口/运行时 → 领域服务与工具执行器 → 仓库或外部适配器。
QQ、未来 WebUI、CLI 的入口转换可信来源，不能各自复制人物、权限、任务或记忆规则。
插件通过 SDK Facade 使用应用能力，不直接访问 ORM、数据库或私有 Host 对象。

显式部署配置决定可用后端；模型决定在已声明工具中调用什么，后端执行授权检查。
禁止在搜索适配器中重新加入按日期、关键词、话题、域名或模型回答内容选择 Provider 的路由器。
配置 DeepSeek 搜索优先时，带日期要求的新闻搜索也必须先请求 DeepSeek。
只有真实请求失败、协议响应无效或无真实来源时才可调用已经配置的兜底。
兜底结果不得成为后续调用持续绕过首选后端的缓存策略。

协议不支持某项严格保证时，明确能力限制和证据状态；不能将限制伪装成成功，
也不能偷偷改用其他服务。合理的输入校验、权限拒绝和网络地址校验不是 Provider 分流。

## 4. 主 Agent 入口与工具合同固定

所有代表 Yuki 生成或发言的普通聊天、主动触发、自动化、插件生成与续跑，
复用主入口、Runner、提示词编译和工具实现。不能为某个入口建立简化人格、
独立短提示词或第二套恢复循环。独立插件计算会话不是 Yuki 主发言链。

- 部署时冻结主 Agent 工具的名称、说明、参数结构、顺序及原生工具合同。
- `request_tools` 查询目录与用法，不在主循环中添加、删除或重排工具声明。
- 声明可见不等于允许执行；每次执行仍检查真实来源、委托、能力、预算与效果围栏。
- 不能因图片、网页、工具错误、当前人物或某个任务阶段临时修改已冻结声明。
- 自动化与创建者在目标会话的普通聊天使用相同工具和当前权限，不设独立工具白名单；插件安装批准边界仍单独核验。
- 原生工具由 Provider 执行，不存在虚构的本地逐次授权拦截。

工作者使用独立固定提示词和工作工具子集，工具实现共用；不得借工作者身份增加
工作区文件审批，也不得获得主 Yuki 才能执行的消息发送、长期记忆写入或自动化权限。
主、子 Agent 的前缀无需完全相同，各自链内必须稳定。参见 [持久工作者](persistent-subagents.md)。

## 5. 历史、工作与执行证据分开保存

原始账本是事实来源；Rollup 是可重建投影；Memory 是有来源和权限的长期知识；
short_state 是小型全局短期记录；工作区是持久文件；工作日志和执行回执是任务状态。
不能把这些数据互相当作替代品，也不能自动将目录和完整任务日志塞进提示词。

请求链提交后，普通续跑只追加事件、工具结果和改向信息。不得重写前部的时间、
short_state、资料包或历史摘要。压缩、权限收窄、generation 变化、合同或 Provider 变化
必须走显式链边界，保留必要目标、证据、预算及执行 ID。

缓存验收比较实际 `messages/input`、完整 `tools/native_tools` 和固定请求设置；
哈希只能辅助定位，不能独立证明正确。缓存命中和持久化是两件事，不承诺永久命中，
不靠无意义调用保温，不为好看的命中率增加无关上下文。

## 6. 工作可以等待，副作用不能猜测

任务、一次激活、模型请求和终端执行是不同层次。任务等待外部结果时保存状态并释放
执行名额；新输入在安全边界追加，不撕裂正在提交的工具结果。
主 Yuki 可以报告进度后继续工作，口头承诺不是启动、完成或发送的证据。

工具成功、失败或结果未知，都按原 call_id 把真实回执追加回原 Agent 循环。
正常业务结果不能强制收尾、替写正文或触发额外总结模型；工具成功不等于整个目标完成。
记忆一次写入授权、管理委托、预算与未知效果围栏在执行层保留；显式命令和模型不可用的
运维状态属于独立接口。不完整 Provider 响应中的调用不执行，补齐未执行回执后有界恢复。

- 启动前登记执行意图，返回稳定工作/执行 ID。
- 超时和断连后的结果未知，先按原 ID 查询，不能默认失败再执行一次。
- 重启、分段和恢复不重置总预算；父子任务共用根预算并保留主任务收尾额度。
- 每个完成事件有唯一消费者，迟到结果、重复回执不能导致重复发送。
- 当前工作接纳新输入中的独立任务后，在同一事务登记新任务和交接标记，立即让出本轮；
  原工作不得代做或代发新任务。按内部事件选择已登记的工作，不按文件名或内容哈希跨任务去重。
- 文件与附言分别核对回执。文件已送达、附言失败不要求重传文件；当所选产物及附言已在
  当前会话确认送达，完成工具直接结束本轮，不再生成重复收尾句。向别处发送仍保留当前会话回复。
- 取消或 generation 失效保留已完成文件和回执，禁止旧链继续产生外部效果。
- 撤回绑定原发送 Presence；主动路由不是成员可达性的证明。

## 7. SQLite 写事务必须短

事务中不等待模型、网络、网关、终端或其他外部工作。仅仅把 HTTP 移出事务还不够：
`session.add()` 后的 SELECT 可能触发 autoflush，提前占住写锁。

先解析和核验内部事件、会话与记忆归属，再把新记录加入会话并提交。
需要原子比较的租约、revision 和授权变更在短事务里复核；不能为了缩短事务删除围栏。
不得持写锁扫描历史消息；不要通过增大 busy timeout 掩盖慢查或扩大事务范围。

日志区分“等待别人释放锁”和“自己持有锁”的时间，记录操作类别而非正文或凭据。
单实例 SQLite 部署不得临时启动第二个主动 Bot 写同一数据库。

## 8. 持久环境与宿主权限边界

工作区是 Yuki 全局共用的持久环境，不按人或群分区。结构化写入使用内容版本检查，
终端任意写入不宣称具有自动冲突保护。交付文件先发布不可变 artifact。
Manager 管理环境生命周期；终端不能通过宿主 Docker 控制、Bot 数据库或 QQ 凭据绕过边界。
Bot 重启不等同于环境重建，任务记录清理不等同于删除产物。

## 9. 修改、验证与交付纪律

以当前代码和用户明确决定为依据，历史任务书是背景而非现行实施指令。
新增兼容分支必须说明真实调用者和退出条件，不能因不确定而擅自恢复已删除的旧路径。
技术执行合同放在代码或开发文档里，不写进用户的 `system_prompt.md`。

主 Agent 的代码执行合同要求较大操作在登记后、执行前用 `report_progress` 简短交代，
随后继续调用工具；已有工作恢复时核对持久回执，避免重复开工说明。明确要求工作者的任务
使用子 Agent 委派。陌生或不确定的公开事实先联网查证；私人经历与工作区状态分别查
获准历史和执行证据。模型选择工具，适配器不按关键词强制分流。
这些行为指引复用现有发送权限、回执和续跑机制，不是语义正确性的硬保证，也不新增定时汇报器。
真实新输入才可支持新目标，模型生成的假设、群聊续写和执行完成通知不能充当用户请求。

按实际风险安排必要验证：小改动采用定向检查；通过且未变化的检查不重复执行。
需要扩大验证时说明新增风险，不把机械重复全量测试当作可靠性证明。
用户明确要求先改代码时，保留未验证状态，不擅自跑测试、上传或部署。

本地修改、测试通过、提交、推送、PR 合并、主工作树同步、生产部署是不同状态，
报告时逐项说清。代码回退不得覆盖上线后产生的新文件、消息和执行回执。
恢复旧数据库是数据恢复操作，不能作为所有代码回退的默认步骤。
