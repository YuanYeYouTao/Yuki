# Yuki 开发架构约束

**发现现有代码复杂，不代表应继续增加保护层；优先检查是否可以删除状态、缩短生命周期或收回不必要的抽象。**

这是当前开发的共同约束。功能任务书、历史验收报告、旧版本发布说明不覆盖本文。
新增功能和临时补丁都要遵守；发现代码与约束冲突时，应标明缺口并修正依赖方向，
不能把现有残留实现当成新功能的模板。

本文描述应保持的边界，不等于所有存量代码已经完成解耦或所有修改已上线。
当前实现、待验证修改和生产状态必须分别说明。

## 1. 永久主体不依附平台账号

一个数据库对应一个长期存在的 Yuki。Person、Space、Conversation、Presence、
Binding、GatewayConnection 分别表示人、空间、会话、自身平台账号、外部绑定和连接。

- 人物记忆、关系和偏好属于 Person；群空间状态属于 Space；SELF 属于 Yuki。
- QQ 号、群号、Provider 名称和连接句柄不是业务所有者。
- 换账号、切网关、连接重建不改变 Conversation generation，不复制记忆或人物。
- 模糊名称、多个 Binding 或多个候选必须明确消歧；不能取第一项冒充唯一结果。

详见 [canonical runtime](canonical-runtime.md)。

## 2. 事件 ID 沿处理链向下传递

需要区分三种标识，不能因名称相近互相替换：

| 标识 | 用途 |
| --- | --- |
| `chat_events.id`、`trigger_event_id`、`source_event_id` | 内部账本事件主键；运行时快照、工具回执、因果关系按此定位 |
| `canonical_event_id` | canonical 事件关联标识；不等同于账本整数主键 |
| `platform_message_id`、OneBot `message_id` | 平台消息凭据；用于接入去重、引用、撤回和平台投递关联 |

已入账事件的内部身份以 `chat_events.id` 为准；平台 `message_id` 仅用于接入去重、引用、撤回和外部投递关联，不得重新承担内部事件身份或因果定位。

接入层解析平台事件并写账本；此后主 Agent、工作调度、子 Agent、工具审计和 Memory
应携带可信内部事件 ID。事件已经存在时，禁止再用 QQ 消息 ID 或消息正文扫描账本、
猜测“最新一条消息”或重建来源。按主键读取后仍须核验 Conversation 和来源边界。

平台消息凭据只在确实需要与网关交互的位置使用。保留凭据用于来源展示或投递关联，
不意味着它可以决定内部身份、所有权或任务恢复。
没有对应事件的定时或系统工作，应使用自己的可信工作/运行身份；不能伪造用户入站事件。
内部 ID 缺失时不得静默回退到平台 ID 查找；明确处理无事件场景或拒绝不完整上下文。

接入写账本后，Host 在 `InboundMessage.source_event_id` 中盖入内部主键；主动群聊、
插件、管理命令和 Memory 必须继续传递它。无用户事件的工作使用 Host 提供的
`source_execution_id`，不能借用 `message_id` 作为执行身份。
任务接纳及改向输入使用 `event:<conversation_id>:<event_id>` 去重；联网来源按
`trigger_event_id` 或真实 `execution_id` 查询、授权和清理。历史当前消息替换按内部 ID。

0058 迁移转换已有任务的接纳键，保留任务 ID、预算、检查点、模型历史和执行回执。
旧联网来源只在迁移时按会话唯一匹配一次；无法确认来源的有界搜索缓存清理掉，
不删除聊天账本和工作区。运行时不保留同类平台回查兜底。
平台凭据仍可保存于接入去重、引用解析、撤回和投递回执中；纯审计展示字段不是授权依据。

## 3. 适配层只转换协议，不重新决策业务

依赖方向为：传输适配 → 应用入口/运行时 → 领域服务与工具执行器 → 仓库或外部适配器。
QQ、未来 WebUI、CLI 的入口转换可信来源，不能各自复制人物、权限、任务或记忆规则。
插件通过 SDK Facade 使用应用能力，不直接访问 ORM、数据库或私有 Host 对象。

显式部署配置决定可用后端；模型决定在已声明工具中调用什么，后端执行授权检查。
禁止在搜索适配器中重新加入按日期、关键词、话题、域名或模型回答内容选择 Provider 的路由器。
配置 DeepSeek 搜索优先时，带日期要求的新闻搜索也必须先请求 DeepSeek。
只有真实请求失败、协议响应无效或无真实来源时才可调用已经配置的兜底。
兜底结果不得成为后续调用持续绕过首选后端的缓存策略。

协议不支持某项严格保证时，明确能力限制和证据状态；不能将限制伪装成成功，
也不能偷偷改用其他服务。合理的输入校验、权限拒绝和网络地址校验不是 Provider 分流。

## 4. 主 Agent 入口与工具合同固定

所有代表 Yuki 生成或发言的普通聊天、主动触发、自动化、插件生成与续跑，
复用主入口、Runner、提示词编译和工具实现。不能为某个入口建立简化人格、
独立短提示词或第二套恢复循环。独立插件计算会话不是 Yuki 主发言链。

- 部署时冻结主 Agent 工具的名称、说明、参数结构、顺序及原生工具合同。
- `request_tools` 查询目录与用法，不在主循环中添加、删除或重排工具声明。
- 声明可见不等于允许执行；每次执行仍检查真实来源、委托、能力、预算与效果围栏。
- 不能因图片、网页、工具错误、当前人物或某个任务阶段临时修改已冻结声明。
- Person 自动化与创建者在目标会话的普通聊天使用相同工具和当前权限；SELF 自动化使用稳定 SELF 主体和原群场景，不能继承最近真人或超管权限。插件安装批准边界仍单独核验。
- 原生工具由 Provider 执行，不存在虚构的本地逐次授权拦截。

工作者使用独立固定提示词和工作工具子集，工具实现共用；不得借工作者身份增加
工作区文件审批，也不得获得主 Yuki 才能执行的消息发送、长期记忆写入或自动化权限。
主、子 Agent 的前缀无需完全相同，各自链内必须稳定。参见 [持久工作者](persistent-subagents.md)。

## 5. 历史、工作与执行证据分开保存

原始账本是事实来源；Rollup 是可重建投影；Memory 是有来源和权限的长期知识；
short_state 是小型全局短期记录；工作区是持久文件；工作日志和执行回执是任务状态。
不能把这些数据互相当作替代品，也不能自动将目录和完整任务日志塞进提示词。

请求链提交后，普通续跑只追加事件、工具结果和改向信息。不得重写前部的时间、
short_state、资料包或历史摘要。压缩、权限收窄、generation 变化、合同或 Provider 变化
必须走显式链边界，保留必要目标、证据、预算及执行 ID。

缓存验收比较实际 `messages/input`、完整 `tools/native_tools` 和固定请求设置；
哈希只能辅助定位，不能独立证明正确。缓存命中和持久化是两件事，不承诺永久命中，
不靠无意义调用保温，不为好看的命中率增加无关上下文。

## 6. 工作可以等待，副作用不能猜测

任务、一次激活、模型请求和终端执行是不同层次。任务等待外部结果时保存状态并释放
执行名额；新输入在安全边界追加，不撕裂正在提交的工具结果。
时间、当前会话消息和获准插件事件可以持久绑定原 Work；交付只追加输入并续原 ID、journal
与预算。新任务与原 Work 等信号是不同操作，插件或 QQ 文本都不能自行指定恢复所有者。
主 Yuki 可以报告进度后继续工作，口头承诺不是启动、完成或发送的证据。

工具成功、失败或结果未知，都按原 call_id 把真实回执追加回原 Agent 循环。
正常业务结果不能强制收尾、替写正文或触发额外总结模型；工具成功不等于整个目标完成。
记忆一次写入授权、管理委托、预算与未知效果围栏在执行层保留；显式命令和模型不可用的
运维状态属于独立接口。不完整 Provider 响应中的调用不执行，补齐未执行回执后有界恢复。

- 启动前登记执行意图，返回稳定工作/执行 ID。
- 超时和断连后的结果未知，先按原 ID 查询，不能默认失败再执行一次。
- 重启、分段和恢复不重置总预算；父子任务共用根预算并保留主任务收尾额度。
- 每个完成事件有唯一消费者，迟到结果、重复回执不能导致重复发送。
- 当前工作接纳新输入中的独立任务后，在同一事务登记新任务和交接标记，立即让出本轮；
  原工作不得代做或代发新任务。按内部事件选择已登记的工作，不按文件名或内容哈希跨任务去重。
- 文件与附言分别核对回执。文件已送达、附言失败不要求重传文件；当所选产物及附言已在
  当前会话确认送达，完成工具直接结束本轮，不再生成重复收尾句。向别处发送仍保留当前会话回复。
- 取消或 generation 失效保留已完成文件和回执，禁止旧链继续产生外部效果。
- 撤回绑定原发送 Presence；主动路由不是成员可达性的证明。

## 7. SQLite 写事务必须短

事务中不等待模型、网络、网关、终端或其他外部工作。仅仅把 HTTP 移出事务还不够：
`session.add()` 后的 SELECT 可能触发 autoflush，提前占住写锁。

先解析和核验内部事件、会话与记忆归属，再把新记录加入会话并提交。
需要原子比较的租约、revision 和授权变更在短事务里复核；不能为了缩短事务删除围栏。
不得持写锁扫描历史消息；不要通过增大 busy timeout 掩盖慢查或扩大事务范围。

日志区分“等待别人释放锁”和“自己持有锁”的时间，记录操作类别而非正文或凭据。
单实例 SQLite 部署不得临时启动第二个主动 Bot 写同一数据库。

## 8. 持久环境与宿主权限边界

工作区是 Yuki 全局共用的持久环境，不按人或群分区。结构化写入使用内容版本检查，
终端任意写入不宣称具有自动冲突保护。交付文件先发布不可变 artifact。
Manager 管理环境生命周期；终端不能通过宿主 Docker 控制、Bot 数据库或 QQ 凭据绕过边界。
Bot 重启不等同于环境重建，任务记录清理不等同于删除产物。

## 9. 复杂度预算与最小充分架构

Yuki 的目标不是最大化抽象层数、状态数量、可恢复路径或形式化围栏，而是在保持身份、权限、事实、因果和外部副作用正确的前提下，选择**复杂度最低的充分设计**。

新增功能和修复缺陷时，应优先判断现有状态、对象和边界是否可以简化、删除或复用，再考虑增加新的持久状态、控制层或恢复协议。不得仅因为某种情况“未来可能出现”而提前建立完整对象模型、并行运行路径或永久兼容层。

### 9.1 先区分 Invariant、Policy 与 Heuristic

所有重要规则应明确属于以下三类之一，不得将当前策略或经验参数自动提升为永久架构约束。

#### Invariant

Invariant 表示违反后会导致身份、权限、事实归属、因果关系或外部副作用错误的系统不变量。

例如：

- Person 不等于平台账号或当前发送者 ID。
- Presence、GatewayConnection 和模型实例不代表永久 Yuki 主体。
- 未授权主体不能产生外部副作用。
- 已知内部事件存在时，不得使用平台 ID、正文或“最近一条消息”重新猜测来源。
- 外部效果未知时，不得默认失败后重复执行。
- Memory、Relationship、Work 等长期状态必须归属于真实 canonical owner。
- 已确认发送、工具效果和任务完成必须依据真实回执或持久事实，而不是模型声明。

Invariant 可以形成数据库约束、事务围栏、执行前复核和失败关闭行为。

#### Policy

Policy 表示当前产品或运行策略，可以根据实际使用、部署模式和后续设计调整。

例如：

- SELF 自动化当前允许作用的社交范围。
- 主动参与是否启用。
- Memory 默认注入数量。
- 当前 Relationship 阶段划分。
- 某类能力是否默认关闭。
- 某项操作需要何种确认或审核流程。

Policy 不应被编码成难以迁移的数据模型不变量，也不应为了当前策略额外复制一套执行链。

#### Heuristic

Heuristic 表示用于排序、预测、召回、参与、节奏和模型行为的经验规则。

例如：

- decay 参数。
- 主动参与权重。
- recall boost。
- 社交节奏估计。
- 阈值、窗口、冷却时间。
- prompt wording。
- 模型选择和观察规则。

Heuristic 应尽量保持可替换、可实验和可回放。除非它产生了需要长期保存的真实结果，否则其内部中间状态默认不进入 canonical 数据模型。

当无法确定一个新规则属于哪一类时，默认按较弱层级处理，而不是直接提升为 Invariant。

### 9.2 新增状态前先尝试删除状态

遇到边缘情况、恢复缺口或并发问题时，不得默认通过增加新的状态字段、epoch、generation、revision、watermark、receipt 或 enum 解决。

实施前至少回答：

1. 这个问题是否由现有状态重复、职责重叠或生命周期不清造成？
2. 能否删除中间状态，让已有事实源直接决定结果？
3. 能否通过缩短状态生命周期解决，而不是增加新的永久状态？
4. 能否由已有 canonical owner、event、Work、effect 或 receipt 表达？
5. 如果新增状态，它的唯一事实来源是什么，谁负责修改，何时删除或失效？

若无法明确回答新增状态的所有权、生命周期和退出条件，不应将其加入长期模型。

复杂系统中的缺陷既可能来自“缺少状态”，也可能来自“状态过多”。两种可能必须同时检查。

### 9.3 区分 Durable State、Derived State 与 Ephemeral State

新增数据前应明确其持久性等级。

#### Durable State

重启后丢失会改变真实长期事实、权限、承诺或已经发生的外部效果。

典型包括：

- Person、Space、SELF 等长期主体状态。
- Memory fact 及其 evidence。
- Relationship 中经过确认的长期状态。
- 已接纳 Work、Automation 和长期任务。
- 已产生或可能已经产生的外部副作用及其 receipt。
- 用户明确创建、修改或删除的持久对象。

Durable State 应持久化并具有明确 owner、来源和变更规则。

#### Derived State

可由 Durable State 或可信事件重新计算。

典型包括：

- 检索索引。
- 某些 ranking score。
- embedding。
- 某些统计聚合。
- 可重建的缓存和投影。
- 可由事件历史重新计算的参与或节奏统计。

Derived State 可以持久化以提高性能，但不得成为新的事实来源。损坏时优先重建，而不是要求其他模块迁就其旧状态。

#### Ephemeral State

仅服务于一次观察、推理、排序或候选选择。

典型包括：

- 一次模型调用中的候选。
- 尚未接纳的主动参与 proposal 的临时排序结果。
- 单轮启发值。
- LLM 内部建议。
- 临时候选集合。
- 一次性风险评分。
- 未形成承诺的内部“想法”。

Ephemeral State 默认允许在重启时丢失。不得仅为了“完整恢复所有思考过程”将其升级为 Durable State。

判断标准：

> 重启后丢掉这个状态，是否会改变已经发生的事实、已授予权限、已形成承诺或可能重复真实副作用？

若答案是否定的，应优先保持 ephemeral 或可重建。

### 9.4 只恢复承诺，不恢复所有思考过程

Yuki 需要可靠恢复已经形成的承诺和可能产生副作用的执行，但不要求恢复每一个内部认知阶段。

必须优先恢复：

- 已接纳 Work。
- 已登记 Automation。
- 已启动但结果未知的外部副作用。
- 已创建的长时间代码、文件或环境任务。
- 用户可感知且有重复风险的发送或交付。
- 已形成持久等待条件的工作。

通常不需要恢复：

- 尚未接纳的主动参与候选。
- 一次闲聊中的模型内部判断阶段。
- 未执行的临时排序。
- 未形成 Work 的短期兴趣判断。
- 可以根据最新现实重新观察得到的瞬时状态。

系统重启后，重新观察现实通常优于恢复过期的内部判断。

### 9.5 事故修复不得自动升级为架构规则

单次 Provider、Gateway、模型、平台或实现缺陷，不得未经分类就形成永久系统不变量。

修复前应区分：

- 真实领域问题。
- 当前 Provider 限制。
- 某平台协议限制。
- 实现 Bug。
- 临时兼容需求。
- 观测不足导致的保守策略。

仅真实领域问题适合进入长期架构合同。

Provider 或平台特例应尽量停留在对应适配层，并写明退出条件。不得因为一次事故在整个 Runtime 增加永久状态或控制层。

新增兼容分支必须说明：

- 当前真实调用者。
- 解决的具体限制。
- 何时可以删除。
- 为什么不能由现有适配层处理。

“为了安全起见”本身不足以证明需要新增永久架构。

### 9.6 大型功能先设计概念边界，再实现最小充分集合

对于 Relationship、Workspace、SELF、Social、Memory 等大型能力，可以先完整分析未来可能涉及的概念，但第一阶段实现只加入已有真实需求证明必要的部分。

应遵循：

```text
概念完整分析
    ↓
识别当前真实需求
    ↓
最小充分数据模型
    ↓
真实运行与观测
    ↓
发现缺口
    ↓
再扩展模型
```

这与“阉割功能”不同。

最小充分实现要求当前已确认的核心能力完整可用，不要求为尚未验证的未来需求提前建立所有状态、表、worker 和协议。

例如，一个未来可能包含 familiarity、reception、reciprocity、trajectory、rhythm 和 confidence 的 Relationship 模型，不意味着第一版必须同时引入全部维度。只有在当前模型无法表达真实使用中已出现的问题时，才增加新的独立状态。

### 9.7 优先复用已有语义，不复制平行控制链

当多个入口需要相同能力时，优先让它们复用同一领域语义和执行链，而不是分别建立：

- 专用发送器。
- 专用 Agent loop。
- 专用 Memory 规则。
- 专用恢复器。
- 专用权限模型。
- 专用状态机。

“统一”指统一语义和事实来源，不要求所有代码集中在同一个模块。

若两个入口确实需要不同策略，应优先让差异停留在 Policy 层，而不是复制底层执行机制。

### 9.8 不以持久化数量或恢复覆盖率作为架构成熟度指标

更多数据库表、迁移、状态字段、恢复点或事务围栏不等于更成熟。

设计质量优先考虑：

1. 是否只有一个明确事实源。
2. 是否容易解释状态属于谁。
3. 是否可以从真实证据还原行为原因。
4. 是否避免重复副作用。
5. 是否允许替换 heuristic 和 policy。
6. 是否能由单个维护者和代码 Agent 正确理解。
7. 是否存在更简单且同样正确的方案。

在满足正确性的多个设计中，应优先选择状态更少、所有权更清楚、恢复链更短的方案。

### 9.9 控制单文件与单模块认知负担

架构边界应逐步反映到代码组织中。

当一个模块同时承担多类领域职责，或修改某一能力必须理解大量无关代码时，应优先拆分职责，而不是继续向大型文件追加新的条件分支和 guard。

拆分的目标不是追求固定行数，而是保证：

- 一个文件的主要职责可以用一句话说明。
- 修改一个领域行为时，不需要理解大量无关能力。
- Agent 不需要通过复制附近代码来猜测正确模式。
- 领域服务、持久化、适配和策略层保持可区分。
- 公共 helper 只有在确有共同语义时才抽取。

不得仅为了减小文件长度制造大量无语义的包装层。

### 9.10 新抽象必须证明其净收益

新增长期抽象前，应说明：

- 它消除了哪些已有重复或错误。
- 它取代什么，而不只是增加什么。
- 哪些真实调用者需要它。
- 它增加了哪些状态和失败模式。
- 如果不增加它，会出现什么具体问题。

如果一个抽象只让设计图更完整，而没有减少重复、错误或真实维护成本，应暂缓加入。

新层级原则上应满足至少一个条件：

- 删除现有平行实现。
- 消除真实语义错误。
- 明确长期所有权。
- 隔离真实外部副作用。
- 显著降低多个调用者的重复复杂度。

### 9.11 开发任务先给出最小充分方案

大型任务开始实施前，设计说明应优先回答：

1. 当前真实问题是什么？
2. 哪些现有事实和模块已经足够？
3. 最少需要新增什么状态或接口？
4. 哪些想法只是未来扩展，不在本次实现？
5. 哪些状态可以重建或直接丢失？
6. 是否正在把 Policy 或 Heuristic 错误提升为 Invariant？
7. 本次新增复杂度是否删除了等量或更多旧复杂度？

Codex 或其他代码 Agent 不应默认选择“最完整”“最保险”或“未来最灵活”的架构。除非用户明确要求，否则应优先提交最小充分方案，并单独列出可选扩展，不自动实施。

### 9.12 正确性与可理解性同为工程约束

Yuki 是长期单人维护项目。一个理论上正确但需要跨越大量状态机、owner、generation、revision 和恢复协议才能解释的设计，本身具有维护风险。

因此设计时必须同时考虑：

```text
正确性
+ 可解释性
+ 可维护性
+ 可替换性
+ 单人认知成本
```

架构目标不是追求最大形式化程度，而是：

> 在不会破坏身份、权限、事实、承诺和真实副作用的前提下，用最少必要机制表达系统行为。

发现两个方案都满足现有 Invariant 时，默认选择更容易阅读、测试、恢复和删除的方案。

## 10. 修改、验证与交付纪律

以当前代码和用户明确决定为依据，历史任务书是背景而非现行实施指令。
新增兼容分支必须说明真实调用者和退出条件，不能因不确定而擅自恢复已删除的旧路径。
技术执行合同放在代码或开发文档里，不写进用户的 `system_prompt.md`。

主 Agent 的代码执行合同建议较大操作在登记后、执行前通过 `send_message` 简短交代，
随后继续调用工具；已有工作恢复时核对持久回执，避免重复开工说明。明确要求工作者的任务
使用子 Agent 委派。陌生或不确定的公开事实先联网查证；私人经历与工作区状态分别查
获准历史和执行证据。模型选择工具，适配器不按关键词强制分流。
这些行为指引复用现有发送权限、回执和续跑机制，不是语义正确性的硬保证，也不新增定时汇报器。
真实新输入才可支持新目标，模型生成的假设、群聊续写和执行完成通知不能充当用户请求。

按实际风险安排必要验证：小改动采用定向检查；通过且未变化的检查不重复执行。
需要扩大验证时说明新增风险，不把机械重复全量测试当作可靠性证明。
用户明确要求先改代码时，保留未验证状态，不擅自跑测试、上传或部署。

本地修改、测试通过、提交、推送、PR 合并、主工作树同步、生产部署是不同状态，
报告时逐项说清。代码回退不得覆盖上线后产生的新文件、消息和执行回执。
恢复旧数据库是数据恢复操作，不能作为所有代码回退的默认步骤。
