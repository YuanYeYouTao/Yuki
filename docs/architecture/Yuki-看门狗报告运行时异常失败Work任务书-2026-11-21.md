## 1. 现象与原假设

### 1.1 现象【issue】

#674 的协调 Work `fdf3c50f` 在 2026-11-21 08:45 UTC 以 `RemoteProtocolError`（stage `activation`，`retryable=false`）进入 failed，之后停了两小时，直到所有者自己发现。同日 `c376c90f`（09:25，`RemoteProtocolError`）同样无人告知。生产当前有 68 个 failed Work，`runtime_work_recovery` 都有 `exit_reason='failed'` 和 `failure_json`：stage `journal` 53（`work_response_not_persisted`，重启打断在途模型请求）、`activation` 10、`provider` 5。

### 1.2 看门狗任务书的排除理由不成立【实证】

看门狗任务书 §4.3“不纳入”写：“`failed` 的 Work：模型已作出结束决定，按原合同由 Yuki 交付；无决定退出的会落成 suspended，已在 C1。”（`Yuki-看门狗与主动私聊任务书-2026-11-20.md:167`）。源码事实是：

| R2 | 失败那一轮的回复被抑制：`AgentRunResult(text="", suppress_delivery=True, ...)`，不会有任何交付 | `services/agent_runner.py:364-378` |

## 3. 判据分析（待决 Q1 的依据）

用 §2 的路径逐个检验候选判据。“报”指会被看门狗当作运行时异常失败报告。

| 候选 | P1 | P2（首次） | P2（之前有过失败） | P3 | P4 | 结论 |
|---|---|---|---|---|---|---|
| a. issue 方向：`exit_reason='failed'` 且 `failure_json` 非空 | 报 | 不报 | **误报** | **误报** | 视上次退出而定 | 不可靠 |
| b. 按 `stage` | 报 | **误报**（settle 也写 `stage='activation'`） | 误报 | 误报 | — | 不可用 |
| c. `exit_reason='failed'` 且 `runtime_work.reason = failure_json.code` | 报 | 不报（reason=`"failed"`，S2） | 不报 | 不报（reason 为空） | 不报（见下） | **推荐** |
| d. 改代码：settle 写 `failed/cancelled` 时也重置 `failure_json`，再用 a | 报 | 不报 | 不报（只对新数据） | 误报 | — | 改热路径、改 `attempts` 语义，存量旧行仍脏 |
| e. 新增 `exit_reason` 值（如 `runtime_failed`） | 报 | 不报 | 不报 | 不报 | — | 新增状态值；存量 68 行没有新值，仍需 c 兜底 |

**a 的误报场景（真实可发生）**：
- F-a1：`fdf3c50f` 这类 Work 先以 `RemoteProtocolError` 进入 failed（P1），所有者让 Yuki 继续（resume 不重置 recovery，S1），后来模型判断目标不可行而 `manage_task(fail)`（P2）。recovery 仍是 `exit_reason='failed'` + 旧的 `RemoteProtocolError`，a 会把模型的决定当成运行时异常再报一次。
- F-a2：某次请求超时（`LLMTimeoutError`，可重试 → `queued`，recovery 写入失败），重试成功后模型主动 fail：同样残留旧 `failure_json`。
- F-a3：P3，模型已经决定 fail，之后的辅助请求断开：`failure_json` 有值。

**c 的依据**：P1 的 `reason=failure.code` 与 `failure_json` 由同一次 `commit_state` 在同一事务写入（`work_supervisor.py:148-169`）；其他路径要么把 reason 写成 `"failed"`（P2），要么写空（P3），要么不碰 recovery（P4、P5）。P4 理论上的巧合：一个 P1 failed 的 Work 被 resume 后、在下一次激活写 recovery 之前，被人以与旧失败码**逐字相同**的 `text` 执行 `fail`。这需要模型或人把失败码当作原因原样写入，概率可忽略；即使发生，报告的仍是一个真实停住、无人交付的 Work。c 只用现有列，不改代码、不迁移，存量 68 行同样适用。

## 5. 设计草案（按 §4 推荐；用户改选时相应调整）

### 5.1 只读事实

`runtime/work_repository.py` 新增 `runtime_failed_works(reader, *, page=256)`，与 `suspended_works`（`:2864-2886`）并列、同样按 `(state, updated)` 分页：

```sql
SELECT w.id, w.revision, w.conversation_id, w.updated, w.model_requests,
       json_extract(w.source_json,'$.origin')  AS origin,
       json_extract(w.source_json,'$.owner')   AS owner,
       r.stage, json_extract(r.failure_json,'$.code') AS code
FROM runtime_work w
JOIN runtime_work_recovery r ON r.work_id = w.id          -- 主键
WHERE w.state = 'failed'                                  -- ix_runtime_work_state_updated
  AND w.parent_work_id IS NULL                            -- Q5
  AND r.exit_reason = 'failed'
  AND w.reason = json_extract(r.failure_json,'$.code')    -- Q1 判据 c
ORDER BY w.updated, w.id
```

代价随 failed 总数线性增长（failed 不会自动消失），每个检查周期一次，在 reader 里完成；不需要迁移或新索引。`resume_blocker` 在同一 reader 里按行调用。

### 5.2 检查器

`application/watchdog.py` 的 `_check_works`：

- `observe()` 中 works 检查的前缀加入 `"work_failed:"`，读取失败时整组标为未定，不开不清（沿 `watchdog.py:411-436`）。
- 每行开 `work_failed:{work_id}:{revision}`，facts 按 Q7。
- 清除：该键不再出现（Work 被 resume、被 cancel、被删除，或 revision 变化）且观察确定为健康，按现有内存清除计时删行。
- 看门狗本身不取消、不恢复；处理沿 #666/#674：所有者在普通轮同意后，由 Yuki 以所有者授权执行（自己的 Work 可 resume；范围外的只能放弃）。

### 5.3 不改

`work_supervisor`、`commit_state`、recovery 写入、工具声明与系统提示、`CONTENT`、迁移、主动入口、存储持有者报告。

**文件**：`tests/integration/test_watchdog_failed_work_e2e.py`。沿用 `test_watchdog_capacity_incident_e2e.py` 的场景装配：真实 SQLite（alembic 到 head）、真实 `WorkScheduler`/`WorkResumer`/Main/Social/`PresenceRouter`，只有模型是脚本化 fake provider。

- **S1 主场景**：私聊 Work 进行中，fake provider 在第 N 次请求时抛 `httpx.RemoteProtocolError`（真实异常，经 R3 分类为 `activation`、不可重试）→ Work failed；tick → `work_failed:{id}:{rev}` 开放、一次主动私聊送达、facts 符合 Q7；再 tick、重启 → 不重复。另一条路径用真实重启打断在途请求得到 `work_response_not_persisted`（R4）。
- **S2 模型主动结束**：P2 首次、F-a1、F-a2、P3、P4 各一条，均不开键。
- **S3 排除**：工作者 P1 失败（父 Work 收到结果）、委派记录 `_end_unstarted`、观察记录、可重试失败、容量挂起。

- **S6** 注入一次查询异常。**S7** 存储达到告警线时同一 failed Work 同时出现在 `failed_holders` 与 `work_failed`，放弃后两者各按自己的条件清除。

**生产只读核对**（实施前由所有者或在授权下只读执行，验证 #675 的“68 个都不是模型主动结束”；本阶段没有执行）：

```sql
-- 按判据 c 统计 failed Work
SELECT r.stage,
       w.parent_work_id IS NULL                      AS is_root,
       r.exit_reason,
       w.reason = json_extract(r.failure_json,'$.code') AS runtime_exit,
       count(*)
FROM runtime_work w
LEFT JOIN runtime_work_recovery r ON r.work_id = w.id
WHERE w.state = 'failed'
GROUP BY 1, 2, 3, 4;

-- 判据 a 命中而 c 不命中的行（即 a 的误报候选）
SELECT w.id, w.reason, r.exit_reason, r.stage, json_extract(r.failure_json,'$.code')
FROM runtime_work w JOIN runtime_work_recovery r ON r.work_id = w.id
WHERE w.state = 'failed' AND r.exit_reason = 'failed' AND r.failure_json <> '{}'
  AND w.reason IS NOT json_extract(r.failure_json,'$.code');
```
