# 分段结果交接修复与长任务复验

2026-10-05，分支 `codex/pi-codemode-experiment`，起点 `b50093c1`。

## 已查明并修复的原因

1. **程序缺陷**：`finish_tool_turn` 在刚好用完段配额时保存 paired 后停跑。
   `WorkSession.restore` 随后把配对误当成结果已被模型观察，退出整个执行尾部。
   工具确实执行了，回执也在原账本，但下一次模型请求看不到详细结果或脚本错误。
   新激活现在从原 journal 提取最后尚未观察的一轮，保留调用 ID、effect key、参数及
   详细回执，作为 `work_unobserved_tool_round` 工作证据与当前获准聊天一起呈现。
   不复制创建时群史、签名、reasoning 或旧 opaque；原效果 ID、预算及回执不变。
   原生 Responses 不接受普通聊天的旧工具调用格式，所以统一用新的工作证据消息，
   不放宽 Provider serializer 的协议检查。任务压缩 anchor 仍只包含当前公开输入。
2. **程序说明缺陷**：说明推荐 asyncio.gather 却没要求显式导入，并错误暗示不能导入
   模块。原生 worker 支持 asyncio、math 等内置模块；宿主 Python 包不可用。固定
   声明已明确导入与字典回执访问 `r['ok']`/`r['data']`。模型写 `r.ok` 是生成代码错误，
   Host 隐去该错误回执是另一项程序缺陷，二者分别验证。context_note 说明明确累计
   发现与中间值需要接续，不把持久日志当作模型已记住的状态。
3. **测试装配缺陷**：旧 Code 组以前只挂当前 helper，旧主迭代没有调用 VM 恢复，也
   没有处理 yielded 标记。现在在隔离加载的旧迭代中加两个明确的测试兼容钩子；旧
   direct 迭代源码保持不变。记录原源码和适配后 hash。这个组仍是实验组合，不能
   当作旧生产应用完整部署的能力证据。
4. **测试覆盖缺陷**：原真实入口测 36 次调用，跨段时 VM 仍 pending，避开了刚好
   32 次时结果已经配对的缺陷。新增真实入口 Code/直接调用 32 次、5/6 配额边界、
   段末 AttributeError 纠正、连续三段、19 种 Provider/协议的实际请求体检查。
   无模型看到原结果就不能 complete；累计预算及一次写入断言保留。
   旧 Code 装配增加真实原程序跨段完成，完成响应必须先看到原代码结果。
5. **程序交接缺陷**：只补最后一轮回执仍不足以保留更早的累计发现。现在段配额耗尽
   后保留当前工作上下文，允许一次受原模型预算约束的模型请求：目标已核验则 complete，
   否则保存有来源引用的累计 context_note。业务调用的剩余额度仍为零，不能继续写入。
   模型不遵守提示也只能得到这一次请求；模型预算不足时由第 1 项回执交接兜底。
   定向回归分别覆盖累计五份结果进入便签、下一段读取便签完成，以及无视提示时
   不执行额外业务调用。真实入口也覆盖第 32 次调用后直接收尾。
6. **测试记录器缺陷**：记录器对模型参数直接 json.loads，遇到无效 JSON 会先抛
   JSONDecodeError，阻止程序正常的参数拒绝与模型纠正流程。记录器现在保留原参数，
   标记 arguments_valid_json=false，将原响应交给 Host 处理；新增无效参数后纠正并
   完成任务的回归。没有替模型修参数，也没有把错误生成当成正确调用。
7. **测试任务表述缺陷**：验收器一直要求成功回读最终报告，原任务只写“验证文件/
   报告”。五次额度下一个模型依据写入回执及文件大小宣布验证完成，没有发起
   workspace_read。这不是 Host 丢调用或测试漏计；是任务表述与验收器不一致，
   文件大小也不能证明文件内容。任务现在明确要求 workspace_read 读回报告的实际
   文本后才能 complete，四组同时适用；输入、答案及通过标准保持。新增四组反例：
   文件全正确且 Work completed，但没有回读时仍失败。相关 39 项通过，17.47 秒。
