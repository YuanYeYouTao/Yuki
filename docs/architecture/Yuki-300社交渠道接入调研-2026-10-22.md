# #300 社交渠道接入调研

调研日期：2026-10-22。调研源码基线：`62bbacec0426eb904868ea102b52c4d18f30a94e`，即调研时的远端 main。关联 [#300](https://github.com/YuanYeYouTao/Yuki/issues/300)。本文保留候选渠道、原 QQ/TG 差异及选择依据；后续飞书实现见文末和[当前接入说明](../operations/feishu.zh-CN.md)。

用户已确认：**飞书接入继续，飞书端不做自动偷表情包。** 普通图片收发、从已有图库发送表情、用户明确要求的收藏继续使用公共媒体链路；不把收到的普通图片自动当作表情收集。这项范围不改变 QQ/TG 现有行为。

## 建议先接什么

先做飞书企业自建应用机器人，适配代码同时留出 Lark 域名配置；下一步按使用场景选择 Discord 或企业微信。个人微信也有官方接入路径，适合作为个人入口另做。钉钉可以接，但标准机器人收不到群里的普通聊天，和 Yuki 的自然参与场景有明显差距。

决定优先级的关键是能看到什么消息。只收得到 @ 的渠道可以正常做问答、任务和结果交付；要让 Yuki 理解群里的日常讨论并自行决定是否接话，就需要相应的群消息可见性。不能把“成功收到一条 @”写成完整群聊支持。

| 候选渠道 | 合适的接入方式 | 对 Yuki 的价值 | 主要限制 | 工程判断 |
| --- | --- | --- | --- | --- |
| 飞书 | 企业自建应用机器人，SDK 长连接收事件，OpenAPI 发消息 | 国内渠道首选；单聊、群聊、附件和话题比较完整 | 群全量消息需单独申请权限；贴纸、卡片和账号 ID 有平台语义 | 中等，接入层为主 |
| Lark | 与飞书共用适配实现，显式选择平台域名与对应凭据 | 飞书完成后可一并覆盖国际版 | 不共用飞书租户、凭据和账号命名空间 | 飞书完成后增量较小 |
| Discord | Gateway WebSocket + REST | 更适合社区、兴趣群与自然社交 | Message Content、成员及频道权限；频道和 thread 要分别处理 | 中等 |
| 企业微信 | 智能机器人 API 长连接 | 国内团队使用方便，现已有官方 SDK | 先按单聊和群 @ 场景评估；回复窗口与主动发送是不同协议路径 | 中等 |
| 个人微信 ClawBot | 参考腾讯官方插件实现 iLink 长轮询、扫码及媒体 | 日常个人入口价值高 | 当前官方插件只声明 direct，不能据此承诺微信群支持；会话 token、媒体加解密需适配 | 中等，建议独立一轮 |
| 钉钉 | 应用机器人 Stream 收消息，OpenAPI 发消息 | 团队问答、任务通知 | 标准群消息仅 @；临时 session webhook 不能作为长期 Work 的唯一投递通道 | 中等 |
| Slack | Socket Mode + Web API | 工作团队使用合适 | scopes、线程和应用分发方式；Socket Mode 不能进入公开 Marketplace | 中等，按实际需求排期 |
| Matrix | Bot 账号 `/sync` + Client-Server API | 开源、自建环境友好 | 加密房间还要维护设备和加密状态 | 普通房间中等，加密范围较大 |

以上工作量是源码与协议对照后的判断，没有做按天估时，也没有将平台账号申请和权限审批算成已经完成。

官方依据：

- 飞书/Lark：[长连接 SDK](https://github.com/larksuite/node-sdk#subscribing-to-events-using-long-connection-mode)、[消息与权限](https://github.com/larksuite/node-sdk/blob/main/docs/channel.md)、[Python SDK 的域名配置](https://github.com/larksuite/channel-sdk-python/blob/main/docs/quickstart.md)。长连接建议从企业自建应用开始，不将其支持范围扩大到所有应用分发类型。
- Discord：[Gateway 与 Message Content](https://docs.discord.com/developers/events/gateway#message-content-intent)、[消息接口](https://docs.discord.com/developers/resources/message)。没有内容权限时，收到事件也未必能取得普通群消息正文和附件；私聊、@ Bot 等有例外。
- 企业微信：[官方 Node SDK](https://github.com/WecomTeam/aibot-node-sdk)、[官方 Python SDK](https://github.com/WecomTeam/wecom-aibot-python-sdk)、[腾讯的长连接接入说明](https://intl.cloud.tencent.com/zh/document/product/1316/84454)。Node SDK 已支持媒体上传和主动发送媒体，不能根据较旧的 Python README 推断平台只支持文字。
- 个人微信：[腾讯官方插件](https://github.com/Tencent/openclaw-weixin/blob/main/README.zh_CN.md)、[实际 channel 能力声明](https://github.com/Tencent/openclaw-weixin/blob/main/src/channel.ts)、[协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)。它是微信中的 Bot 入口，不等于接管普通个人账号的全部好友和群聊。接 Yuki 可以参考协议边界，无需让 Yuki 改跑 OpenClaw。
- 钉钉：[应用机器人和群 webhook 的区别](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/overview/)、[收消息](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/appbot/receive/)、[回复与主动发送](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/appbot/reply/)。Stream 是接收通道，发信仍走对应消息 API。
- Slack：[Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)、[历史与限频](https://docs.slack.dev/reference/methods/conversations.history/)。内部自建应用与商业分发、非 Marketplace 应用的限频规则不同。
- Matrix：[Client-Server 规范](https://spec.matrix.org/latest/client-server-api/)。

## QQ 和 Telegram 的工具差多少

**主 Agent 工具数量差为 0。** 两端都用 `platform` 合同，内置 direct 工具完整装配时为 30 项，不含插件。联网、记忆变更、自动化、artifact 等有装配条件，具体部署数量看实际冻结清单。Code 模式共同增加 `execute_code` 和 `lookup_tools`，再按固定直调政策投影。只有 App/ACP 个人入口另加 `read_personal_entry`。

源码见 [MainAgentContract](../../src/yuki/services/main_agent_contract.py)。其中 `version: 25` 是合同修订号，不是工具数量；旧平台文档里的 direct 29 也不能作为当前统计依据。

两端都能使用这五个社交工具：

| 工具 | QQ | Telegram | 共同语义 |
| --- | --- | --- | --- |
| `find_contacts` | 支持 | 支持 | 内部人物和空间目录 |
| `read_conversation_history` | 支持 | 支持 | 已入账、获准读取的会话历史 |
| `send_message` | 支持 | 支持 | 文字、图片、文件、真实提及、内部事件引用、后台配图 |
| `get_group_members` | 支持 | 支持 | 已观察的逐账号目录，`coverage=observed` |
| `recall_own_message` | 支持 | 支持 | 由原发送账号撤回原出站消息，平台失败如实返回 |

此外，`query_chat_history`、记忆、终端、工作区、搜索、Work、子 Agent 与自动化共用现行领域实现。历史工具在 QQ 也不会默认补查远端完整历史，成员工具在 QQ 也不是完整群名单。[社交声明](../../src/yuki/social/tools.py)、[Main 工具装配](../../src/yuki/services/agent_tools.py)、[Social 执行](../../src/yuki/social/service.py)。

工具名相同，原生行为仍有这些区别：

| 能力 | QQ 当前实现 | Telegram 当前实现 |
| --- | --- | --- |
| 提及具体账号 | OneBot `at` | 原生用户链接或 `@username` |
| 提及全体 | 适配器识别 `@全体成员` / `@all`；能否发送仍由平台决定 | 没有对应的真实全体提及 |
| 正在输入 | 仅私聊，支持开始/停止 | 私聊、群、topic；定期刷新，到期消失 |
| topic/thread | QQ 当前无对应布局 | 入站、发送和引用保留原 topic |
| 文件和附言 | 文件上传与文字分别派发、分别确认 | 短附言可随文件发送，超长附言拆分 |
| 文件传输 | Bot 与网关需要共享传输挂载 | HTTP multipart，无需共享目录 |
| 文件撤回 | 返回真实 message ID 才可沿消息撤回；只有 `file:` 回执时不可 | document 返回消息 ID，可走撤回工具，仍受平台条件约束 |
| 表情/贴纸发送 | QQ image 的 `sub_type=1` | WEBP/TGS/WebM 可走 `sendSticker`；GIF 配图走动画 |
| 平台长度处理 | 此适配器没有额外的协议长度拆分；公共分条仍在 | 正文 4096、媒体 caption 1024 字符，适配器安排拆分 |
| 入站编辑 | QQ 当前入口没有对应的 TG 编辑流程 | 更新原事件，不重新启动 Main；没有开放消息编辑工具 |
| 禁言、踢人、置顶、消息反应 | 没有内置 Main 工具 | 没有内置 Main 工具 |

依据：[QQ 原生发送](../../src/yuki/adapters/onebot/social.py)、[TG 原生发送](../../src/yuki/gateway/providers/telegram_social.py)、[输入状态与平台合同](platform-adapters.md)、[撤回执行](../../src/yuki/social/service.py)。不能把平台 OpenAPI 理论上有的能力算成 Yuki 已经开放的工具。

连接声明也有一点差异：QQ、TG 各有 6 个 capability，共享 `send_private/send_group/group_member_probe/media_fetch/typing_private` 五项；QQ 多 `message_history`，TG 多 `typing_group`。这是底层连接能力，不代表 QQ 的 Main 历史查询就能读取完整服务器历史。[SnowLuma profile](../../src/yuki/gateway/providers/snowluma.py)、[TG profile](../../src/yuki/gateway/providers/telegram.py)。

### 插件 SDK 的差异更大

QQ 的 `onebot` facade 另有六个接口：`send_music_card`、`send_custom_music_card`、`send_private`、`send_group`、`call_read_action`、`call_mutating_action`。只读 action 目录当前有 29 项，包含 QQ 原始历史、转发、好友和完整群成员查询等。它们仍需独立批准并由网关实际支持，TG 不适用；`call_mutating_action` 也不是所有管理操作必然成功的保证。[SDK 源码](../../src/yuki/plugin_host/facades.py)。

这些接口不自动进入 Main。只有获批插件将其包装为工具，才可能出现“两端冻结声明相同，TG 调用时报告平台不适用”的情况。音乐卡片、任意 OneBot action 不能当成跨平台通用工具；合并转发发送在当前 SDK 里也明确拒绝。

## 飞书接入时怎么处理工具

继续用原来的公共工具和领域服务，让飞书适配器负责原生消息格式。飞书文档、日历、表格属于业务集成，可另做插件；它们不是接通飞书聊天的前置条件。

首轮需要明确几件事：

1. **群消息权限。** `im:message.group_at_msg:readonly` 只能收到 @；自然参与需要申请 `im:message.group_msg` 并经管理员批准。官方高层 Channel 自带 `requireMention` 策略，不能拿到全量权限后又过滤普通消息。Yuki 已有参与逻辑，优先使用底层事件与 Client，或明确关闭重复策略。[官方说明](https://github.com/larksuite/node-sdk/blob/main/docs/channel.md#common-issues)
2. **身份命名空间。** `user_id` 在租户内使用，`open_id` 与应用相关，`union_id` 用于同一应用提供方下的关联，不能直接视作全局自然人 ID。接入编码要区分飞书/Lark、应用和租户，人物仍通过已有 AccountAssignment 显式关联。[身份规则](https://open.larksuite.com/document/home/user-identity-introduction)
3. **引用与话题。** 保存平台 root/thread/reply 关系，映射到现有 `thread_id` 与内部事件引用；不把同群不同话题混成一段公共上下文。[原生消息模型](https://github.com/larksuite/node-sdk/blob/main/docs/channel.md#normalizedmessage-fields)
4. **媒体与表情。** 图片、文件等按原连接取真实字节，再进入已有共享缓存与工作区。飞书端不做自动偷表情包，不依据普通图片的外观猜测并自动收藏；已有图库发图与用户明确要求收藏可复用公共链路。飞书消息资源下载接口明确排除原生 sticker；原生贴纸可以按平台 `file_key` 发送复用，但不能照搬 QQ/TG 的原文件收藏流程。平台 file key 不跨平台复用；要跨端发送，仍需真正取得可用文件字节。[官方资源接口参数](https://github.com/larksuite/oapi-sdk-go/blob/v3_main/service/im/v1/model.go#L14875)、[贴纸发送示例](https://github.com/larksuite/node-sdk/blob/main/docs/channel.md#sending-messages)
5. **实际发送与撤回。** 文本、图片、文件、提及及引用继续由 `send_message` 表达，协议布局在 `plan_send`。每次真正的消息派发保留自己的回执；没有原生撤回、真实消息 ID 或权限时，就返回该项实际不可用，不虚构成功。

`get_my_capabilities` 当前只查询主体权限和配置能力，不能证明 Bot 有平台管理员、全体提及或完整成员权限。确有必要提前告诉 Agent 原生限制时，优先补现有能力查询的返回资料，复用连接事实；不做一套动态工具清单、第二个能力管理器或每平台一套 Agent。[能力查询实现](../../src/yuki/services/agent_tools.py)。

## 实际需要改到哪里

现有 `GatewayProvider`、Catalog/Registry、`PlatformSocialOperations`、Media 和 Activity 足够承载飞书；内置 App/ACP 已经走同一体系，测试也有名为 `extra` 的额外模拟平台接入案例。不需要借接飞书重写 Main、Memory、Work 或身份模型。[Provider 合同](../../src/yuki/gateway/provider.py)、[注册点](../../src/yuki/gateway/providers/__init__.py)、[额外平台测试](../../tests/integration/test_telegram_runtime.py)。

但完整接入不止增加一个文件：

| 修改面 | 内容 |
| --- | --- |
| 飞书原生客户端与 ingress | 登录身份、长连接、事件投影、原生提及/引用/附件、去重与编辑；确认和业务完成分开处理 |
| Social/Media 适配 | 消息布局、发送、撤回、真实成员探针与媒体字节；没有输入状态接口可直接不实现 Activity |
| 配置、装配、启停与健康 | 应用凭据、平台域名、Provider 注册、container 生命周期，沿现有配置方式接入 |
| 对应验证 | 单聊、群与话题、提及、图片文件、重复事件、编辑、部分成功、未知回执及断连恢复 |

群接入和主动路由发现有真实成员探针调用，飞书不能把 `is_member` 硬填为成功。已有确定当前路由的正常发送继续沿现行规则，不额外加每条消息的成员预查。[路由实现](../../src/yuki/identity/routing.py)、[当前平台合同](platform-adapters.md)。

首轮可交付范围是完整的飞书聊天入口：收消息、参与、发消息、引用、提及、附件、原发送撤回和对应回执。卡片交互、文档、日历、表格、群管理按明确需求继续增加，不把这些全部捆在第一次接入里。

## 后续实现

飞书和 Lark 已按本报告选择的接入边界实现：原生异步长连接、应用范围账号、消息投影、公共 Processor/Main/Social、图片与文件、提及、引用和 root 消息路由。平台 ACK 等入账或明确忽略，重投不重新触发 Main；原发送回执继续负责撤回和未知结果。没有新增平台专属 Main 工具，也没有自动偷表情包。

配置、实际权限、未接入的消息编辑推送与原生贴纸资源限制统一在[飞书与 Lark 接入](../operations/feishu.zh-CN.md)维护。测试覆盖本地真实 WebSocket、HTTP 协议替身与 SQLite/工具完整路径；它们不代表已经用真实飞书应用完成收发。本次交付为源码和 PR，不含生产部署。
