## 1. 要解决什么，不解决什么

### 1.1 现象【实证】

- 自动提取的人物、群事实（非经历）2026-W45 新增 55 条，W46（11-16 起）新增 272 条。所有者 11-14 起新增的 158 条 active 非经历事实里，37 条正文含 PR / issue 编号、分支、任务书等当次任务指向（按 §11.3 的正则口径）。
- 所有者范围按 `search_memory` 省略 query 时的顺序（重要度降序、更新时间降序，`memory/repository.py:587`）取前 50 条，22 条是这类当次任务条目，50 条的 importance 全是 4–5。
- 架构书 §1.2 列出的一次性指令（fact 3916、3949、3951、3963）与同义规则（3944、3946–3948、3954、3959–3961、3965、3969、3970，和明确事实 3975 同义）都仍 active。
- active 非经历事实 1386 条，有 425 个不同的 `category`，其中 257 个只用过一次；SELF 事实只有 6 个。

### 1.2 原因【实证】

| # | 原因 | 依据 |
|---|---|---|
| C1 | 提取指令要求"精选长期事实与共同经历"，但没有说当次任务指令不算长期 | `memory/event_extractor.py:29-36` |
| C2 | 写入时不去重：每条通过校验的 claim 都按 `independent_claim` 新建，候选集恒为空 | `memory/claim_processor.py:110-168`、`:182`；`memory/service.py:305-375` |

### 1.3 P3 做

1. **提取合同**：提取指令写明当次任务指令不提取、同一批同义只出一条；提取不再输出 `category`，由 kind 生成（§4）。受新开关 `memory.extraction_tightened_enabled` 控制，默认 false。
2. **同义合并**：不新增合并机制。把 Dream 每次运行的簇上限提到与调用预算相同，让积压的同义条目轮得到现有的 merge / synthesize（§5）。删除写入侧从未被调用的冲突候选查询。
3. **存量清理**：所有者用 CLI 对存量自动事实按 §4 的同一条规则做一次分类，审阅计划文件后，按签名校验批量失效；可撤销；不按时间（§6）。

### 1.4 P3 不做

- 不在写入时按相似度拦截或合并（不新增相似度门槛）；不给提取模型喂已有事实。
- 不改 SELF 自省（SELF 类别已收敛；自省指令另有边界，`docs/architecture/self-reflection.md:19`）。
- 不改 Dream 的指令、聚类算法、相似度阈值、簇大小、分区与 6 种操作；不改调度时间。
- 不改存量事实的 `category`、`memory_key`、正文。
- 不按时间、重要度或使用次数做任何失效或准入。
- 不改 `search_memory`、`save_memory`、`edit_memory` 的声明。
- 不改 P1 的常驻段与挑选步骤，不改 P2 的经历目录。

## 4. 提取合同（开关 `memory.extraction_tightened_enabled`）

### 4.1 指令【推荐】

`_VALUE_INSTRUCTION`（`memory/event_extractor.py:29-36`）在开关开启时用 v8 文本：原有句子保留，加两句：

> 只为当前这件事给出的要求、决定或安排——指向某个 PR、issue、分支、文件、任务书、当次交付物或当次会话——是当次任务指令，不提取；它们留在会话历史与任务记录里。对方表明以后都适用、或描述的是一般做事方式的，才作为长期偏好提取。同一批里同一个意思只输出一条 claim。

- 单事件与批量两份指令都用这段（S1），Rebuild 同样受开关控制。
- 这是让模型按内容性质判断，不是程序门槛，和 S3"不设最低价值门槛"一致：没有分数线，也没有按字段丢弃 claim 的后端逻辑。
- 不用 `temporal_mode=temporary` 表示当次指令：它要求 `valid_until`（S2），等于按时间过期。

### 4.2 类别由 kind 生成【推荐】

- 开关开启时，提取的结构化输出用不含 `category` 的 claim 模型；`MemoryClaimValidator` 把 `category` 设为 `kind` 的值（fact / preference / episode），与 `save_memory` 的现行做法相同（C6）。
- `memory_key` 仍由模型给出（变更定位与 FTS 在用）。
- 存量事实的 `category` 不改：改了会让这些事实全部重新进入 Dream 待审队列并重新生成 embedding（S5），而 `category` 只在检索排序里作一项精确匹配加权（`memory/ranking.py:98-119`），收益不抵成本。

### 4.3 版本与开关

- 开关开启：`EXTRACTION_PROMPT_VERSION = "memory-v2-extraction-v8"`、`EXTRACTION_SCHEMA_VERSION = "7"`、`BATCH_EXTRACTION_PROMPT_VERSION = "memory-v2-batch-extraction-v7"`、`BATCH_EXTRACTION_SCHEMA_VERSION = "6"`；关闭：现有 v7 / 6 / v6 / 5 原样。P2 若先合并（它给 claim 加 `title`），这里的版本号顺延。
- `MemoryRetrievalRuntimeConfig.extraction_tightened_enabled: bool = False`（`admin/models.py:167-183`）。提取 worker 与 Rebuild 需要接上运行时配置（S11），每个批次开始时读一次快照；同一批次内不切换。
- 开关只影响提取请求与写入的 `category`。主 Agent 提示词、恢复哈希、工具清单都不变。
- 验收通过后，另开一个 PR 删除 v7 指令、旧 claim 模型与这个开关（删除优先；两个变体不长期并存）。

## 5. 同义合并

### 5.1 提高 Dream 吞吐【推荐】

`memory_dream_max_clusters_per_run` 的默认值从 12 改为 24，与 `memory_dream_max_model_calls_per_run`（24）相同（`config.py:213-214`）。每簇至少一次调用，调用预算本来就是 24；现在实际只用到 12（C3）。

- 每日 Dream 调用从约 12 次增至至多 24 次；P1 的挑选步骤另计，至多 12 次（P1 任务书 §15 第 32 条）。
- 按近 14 天每簇平均 2.7 条估算，每天可审约 65 条，高于开关开启后的预计新增量；786 条积压按差额逐日消化【假设：新增量下降幅度要开启后实测】。
- 需要更快消化积压时，所有者可在部署环境临时调高这个配置几天再改回；不新增机制。
- 同义规则合并到明确事实：Dream 已有规则（C4）。P1 上线第 3 步所有者把工作规则写成明确事实后，这组自动同义条目在轮到时 merge 到明确锚点。P1 的常驻渲染会沿取代链找到后继（`memory/resident.py:448-512`），常驻段不受影响。
- 不改排序（C5）：簇上限提高后积压逐日消化，排序只影响先后，不影响最终是否被审。

### 5.2 删除未被调用的代码

删除 `MemoryFactRepository.list_conflict_candidates`（S4）。它按 key、正文、同类别同 kind 找冲突候选，但写入侧从不调用（C2），留着会让人误以为写入时有去重。

### 5.3 不做的方向

| 方向 | 结论 | 原因 |
|---|---|---|
| 写入时按 embedding 相似度合并 | 不选 | 新增相似度门槛，且与"按实际 fact ID 执行"的变更合同冲突 |
| 把主人已有的明确事实喂给提取模型 | 不选 | 增加每次提取的输入；与 Dream 的显式锚点合并重复，成两条去重路径 |
| 让 Dream 跨 fact / preference 分区合并 | 不选 | 这组同义规则全是 preference，与分区无关；改分区要动簇校验（`memory/dream/planning.py:71`） |
| 不把单条簇送给模型 | 不选 | 单条簇仍可 recompose 拆分混合记忆；吞吐问题由 §5.1 解决 |

## 6. 存量清理

### 6.1 为什么不按时间

当次任务指令与长期偏好的区别在内容，不在新旧：所有者那 38 条当次任务条目里 37 条写于 11-14 之后，按"超过 N 天"清理一条也清不掉；反过来，8 月的长期偏好（称呼、身份、边界）正是常驻层要用的。按容量或时间清理的旧机制已经删除（S12），本书不恢复。

### 6.2 流程【推荐】

新增 `yuki memory hygiene task-scoped` 子命令组（与现有 `hygiene scan/apply` 平级，S9）：

| 命令 | 作用 |
|---|---|
| `scan --output <plan.json> [--limit N]` | 候选：active、`source_type='automatic'`、非经历、scope 为 person / person_group / group、`authority` 不是 explicit 的事实。按 fact ID 升序成批交给模型，用 §4.1 的同一条规则判断"当次任务指令 / 长期内容"（`ModelTask.MEMORY_DREAM`，结构化输出只引用别名）。计划文件只写被判为当次任务指令的 fact ID、各自的 `fact_signature` 与扫描时间，不写正文 |
| `show --plan <plan.json> [--content]` | 列出计划里的 fact ID、主人、kind；`--content` 打印正文，只在部署环境内使用 |
| `apply --plan <plan.json>` | 逐条重读事实并重算签名，任一条签名不一致或已不 active，整批拒绝（"重新 scan"）；全部一致时逐条经 `MemoryService.invalidate_fact` 失效，原因 `administrator_invalidated`（S8），每条一个短写事务，事务内不等待模型 |
| `revert --plan <plan.json>` | 对计划里仍处于失效、且原因是 `administrator_invalidated` 的事实执行恢复；其他原因失效的不动 |

- 分类在读取会话之外完成，写入阶段不调用模型、不扫描历史（AGENTS.md）。
- 所有者可以直接编辑计划文件删掉不想失效的 ID，再 `apply`；`apply` 只认文件里的 ID。
- 明确事实、SELF 事实、经历不在候选内；所有者在 P1 中写下的工作规则因此不会被清理。
- 预计调用次数：候选约 1170 条，按每批 40 条约 30 次【假设：按字数估算】。
- 失效而不是删除：保留证据链与状态事件，可恢复；P1 渲染与 Dream 候选都按状态过滤，不需要同步。

### 6.3 与 P1 的关系

- P1 挑选步骤的指令已排除一次性任务指令（`memory/resident_selection.py:48-67`）；清理减少的是候选池里的噪声，不改挑选逻辑。
- 被清理的事实若在某个核心集里，下一轮渲染自然消失（P1 任务书 §5.3），下一次挑选按"列表条目失效"把该主人排为到期。

## 11. 验收

### 11.1 E2E

§8 的 16 个用例全部通过，两次运行产物逐字节相同。

### 11.2 离线重放（调用生产提取模型，不写库）

用生产只读数据取固定的源事件集合，分别用 v7 与 v8 指令、生产 `memory_extraction` 模型各跑一次，只生成 claim 不写库。结果文件只存事件 ID、claim 条数与 kind，正文只在部署环境内人工判定。

| 集合 | 来源 | 期望 |
|---|---|---|
| A：当次任务指令 | 架构书附录 A.4 列为"当次指令"的事实（3916、3949、3951–3953、3963–3966）的证据事件 | v8 对这些事件不产生对应的长期 claim（人工判定）；v7 作对照 |
| B：长期规则 | 架构书附录 A.1 来源中自动提取的事实（如 3944、3970、3924、3686、3712）的证据事件 | v8 仍各产生至少一条对应的长期 claim（人工判定） |
| C：近期样本 | 所有者私聊 11-14 至 11-21 产生事实的全部源事件 | 记录 v7 / v8 的 claim 总数与 §11.3 正则口径的占比，只记录 |

阈值：A 中 v8 产生长期 claim 的事件不超过 1 个；B 中 v8 漏掉的不超过 1 个。不达标就改指令措辞再重放，不加后端机制。

## 12. 上线与回滚

### 12.1 上线

7. 验收通过后另开 PR 删除 v7 变体与开关。

## 13. 假设与未核实之处

- 生产提取模型对 v8 指令的遵从程度未测，由 §11.2 验证。
- "开启后新增量下降、积压可消化"是推断，由 §11.3 实测。
- 清理分类用的是 Dream 模型，质量未测；所有者审阅计划文件是最后一道判断。
- 正则口径只用于统计，会漏掉不带编号与关键词的当次指令，也可能把长期规则里提到的 PR 计入；它不进入任何产品判断。
- 提取 worker 接运行时配置的方式参照 P1 给 Dream worker 的接线，细节实施时定。
- 每簇平均 2.7 条、清理约 30 次调用都是按近 14 天数据估算。
- 自动同义条目只有和明确锚点同一主人、同一 kind 才会进同一簇（`memory/dream/repository.py:81-96`）。这组同义条目与 fact 3975 都是 preference；所有者按 P1 写入工作规则时若存成 fact，Dream 不会把它们合并，需要所有者在写入时指定 kind，或在 Dream 审过后人工失效。
