## 1. 用户要的行为

在 QQ 群里问“TG 某群上周怎么讨论雷达站的”，Yuki 能先找到那个群的真实入口，再查询它的已入账历史，最后在原 QQ 群回答。已知内部 ID 时直接查询，不重复找群。整个查询读本地账本，不请求 Telegram 补历史、不切换主会话、不拼接不同 Conversation 的公共上下文。

- 保留两个现有工具：`find_contacts` 发现目标，`query_chat_history(recent/search/around)` 读取记录。
- 平台、群聊/私聊、具体目标、作者、日期、附件条件按需填写；已知目标不要求重复指定平台或类型。
- 来源条件与目标条件取交集。分级用于理解资料，不要求“选平台→选群私聊→选群→选话题”逐级调用工具。
- 默认搜索 Yuki 实际参与、已入账、当前来源获准读取的全部 Conversation，包含所有作者。作者过滤仅由显式作者条件决定。
- `/ai new` 只清理自动聊天上下文，不能影响显式永久历史。人物合并、账号换绑、原消息和发送回执继续认各自真实身份。

### 2.1 已取得的证据及其边界

- 线上 SQLite `3.46.1` 的只读 `EXPLAIN QUERY PLAN`：名称包含查询扫描 Space 目录；`WHERE canonical_conversations.space_id=?` 扫描会话目录；`WHERE id=?` 使用主键定位。前两者不是聊天正文全扫。目前25个 Conversation，不能拿当前小目录证明扩展后没有成本。
- 离线8事件、真实 `query_history`：关键词加宽日期4次 SELECT、0次 MATCH；两个命中各取前后1条，共7次 SELECT，即1次主查询加每命中3次邻文查询。
- 与线上同版本的 SQLite `3.46.1` 会把 FTS rowid 上下界下推：`192:M1>` / `192:M1><`，主键回表，无临时排序。Windows `3.53.1` 的同一小样出现不同驱动顺序和临时排序，不能当成线上现状，也不能声称当前每批必定从头扫描全部 posting。
- [既有完整实验](experiments/chat-history-448-2026-10-22/README.md)：稀有词约5.18ms，叠全范围日期约252.92ms、精核1875行；但每页重做 FTS IN 在2万条全假阳性样本中又由约95ms恶化到约6703ms。不能只删开关后机械套用反复物化的 IN。
- 上次线上0.3263秒只验证一次真实查询；独立进程首次调用包含连接和 OpenCC 冷初始化，不能视为常驻 Bot 稳态延迟或最快证明。

## 3. 最小的公共接口调整

### 3.1 来源过滤保持可选

`query_chat_history` 新增一个可选 `source`：

| 字段 | 语义 |
| --- | --- |
| `source.platform` | 平台的真实标识，开放字符串，按已保存 Binding/Account 事实筛选；不枚举 QQ/TG 分支。 |
| `source.scope` | `private` 或 `group`；group 对应现有 Space 共享会话，不另建平台群类型系统。省略则不限。 |

`target` 继续是一个互斥内部 selector：Conversation、Person、Space、Binding 或原 operation。recent/search 的 source、target、原作者、日期、媒体条件全部取交集；around 的定位条件是实际event/receipt、target、source和event_kind。source不塞进target的oneOf，不静默忽略较窄的来源条件。平台/type不匹配、未知平台或其他适用过滤后无交集时返回真实空结果，不回退到当前会话、最近入口或全局。缺失原件仍沿现有unavailable/missing语义。

目标含义保持明确：`space_id` 选择该 Space 的真实会话集合；`binding_id` 选择一个原平台入口的所有 thread；`conversation_id` 精确选一个会话/话题。话题精确定位直接用 Conversation ID，不新增平台 thread ID 业务主键、名称转身份或多套同义定位字段。`target.person_id` 选私聊入口，顶层 `person_id` 筛原作者。

| 调用 | 选择范围 |
| --- | --- |
| recent，无 target、未提供 source 字段条件 | 当前 Conversation。 |
| recent，无 target、有来源条件 | 当前获准集合与 source 的交集，可直接浏览某个平台的近期记录。 |
| search，无 target | 全部当前获准已入账 Conversation，再应用 source；不限制作者。 |
| recent/search，有 target | target 的真实范围与 source、委托取交集。 |
| around | 先按原内部事件/原回执定位实际 Conversation，再与 target/source/当前读取授权取交集；不扩大邻文到其他入口。 |

空 `source` 等于省略；已指定目标时不要求重复填写平台或scope。recent/search保留现有all/any/phrase、exclude、作者、日期、附件及ID续页语义。around按已知中心读取邻文，搜索用keyword/person/date/has不参与该view，也不为这些无关字段新增拒绝门槛；工具说明明确需要先筛选消息时使用search及其context_before/context_after，不凭空增加中心筛选语义。

### 3.2 目录平铺，不建目录树

`find_contacts` 的 `view=subjects|entries` 默认 subjects。entries 的单位是**真实 Conversation**，解决“找一个话题或历史入口”的需求，不是另建查询系统或权限层。

- subjects 沿现有 `kind=person|space` 与 `target_id/display_name/subject_ref` 主体定位语义，kind 仅是主体视图的类型要求；不能继续把它设成整个工具的全局必填字段。
- entries 使用同一 `HistoryTarget` 类型的可选 `target`，以及 `source/display_name/limit/cursor`；不接受主体视图专用 kind/target_id/subject_ref，不靠 UUID 猜目标种类、不静默忽略交叉字段。复用历史内部范围与原回执归属语义，不增加第二个解析器。
- source 在两个视图中都于SQL分页之前取交集。subjects 的 kind 与 source.scope 冲突时为空；所附 Binding 列表仅给匹配来源的条目，不能先取20个主体再在Python里滤平台。当前发送联系人事实与历史 entries 分别使用自身查询，不把 current active-only 条件搬进 entries。
- entries 按名称、目标与来源直接平铺查询。不把所有 Binding、全部 thread 嵌套塞在一个主体下面，不做子游标树。两个视图的完整 schema 随部署一次冻结，不按 view 动态改变工具声明。
- 每项给出主体 ID、原 Binding ID、原 entry_presence_id、Conversation ID、平台、scope、可读名称与 thread_id；私聊Assignment的active/disabled/ended、群SpaceBinding的active/disabled及Presence阶段分别标注，不压成一个含义混杂的status。显示资料不覆盖原事件作者或用今日Presence替代原来源。
- 保留/legacy Conversation 没有完整Binding时使用外连接，不裁掉记录；平台只认能证实的原Binding/Presence/Account事实，缺失则标未知，不从原生ID形状、当前路由或默认QQ猜测。有platform条件才按已知真实平台取交集。不为目录逐会话COUNT或补查历史来证明非空。
- 主体页按原主体 ID、entries 页按 Conversation ID稳定升序seek；页大小可显式请求，N+1 证明 has_more，next_cursor 为最后一项 ID。删除固定20项帽，不新增反向排序、深 OFFSET、总数预算、签名、epoch 或服务端分页任务。
- entries 从保留的 canonical Conversation 发现历史，含停用、解绑和 ended 的旧阶段；不要求来源 owner 现在 enabled、有账号、曾发特定类型消息或入口现在能发送。现行主体发送资格不得搬进这个 view。
- 同名返回可读候选及真实平台/入口，不靠猜测最近活跃群消歧。只给名称不制造身份；已知 ID 就跳过名称查询。
- 目录执行沿与历史读取一致的真实来源、read_scope 和插件批准。复用现有查询/小型私有函数，不新增 ScopeResolver、权限缓存、服务注册器或“万能查询服务”。

已实现的调用示例：

```json
{"view":"entries","source":{"platform":"telegram","scope":"group"},"display_name":"某某群","limit":30}
```

取目录返回的内部 Conversation ID 后，一次读取该话题：

```json
{"view":"search","target":{"conversation_id":"目录返回的内部UUID"},"keyword":"雷达站","start_at":"2026-10-15T00:00:00+08:00","end_at":"2026-10-22T00:00:00+08:00"}
```

## 4. 查询执行：一次候选语句，同一只读快照

1. 按真实 target/source/委托取得最小范围资料。平台从原 Conversation 对应的 Assignment/SpaceBinding 读取，不从今日主动路由或当前账号归属反推旧来源。
2. 一次准备字面 query 和原作者同人族。保持现有唯一 FTS 与精确 matcher，元数据和真实来源谓词在共同候选 SQL 内参与筛选。
3. 候选SQL执行一次，以同一个游标显式分块取原文，在现有CPU线程中精核。先只使用已加载行的content/audio_transcript，真命中才解析附件/外部JSON及构建完整EventRecord，不增加二次hydrate SQL。累计limit+1个真实命中或EOF停止。需要Python精核时不能用SQL页大小截断假阳性候选；没有keyword/exclude时SQL行已经是真实命中，应保留SQL N+1以减少排序和装载，不能机械删除这个正确限制。
4. 关闭候选游标后再查邻文与原回执补充。保持同一 AsyncSession/只读快照，不边持活跃流边另开连接查询或重新建立快照。
5. 对 matches、context、另行展示的 receipt_anchor 的实际 Conversation 批量装配 sources。候选阶段仍正确应用 ACP 出站成功回执谓词，不能为延迟展示资料而把真实事实过滤延迟到结果以后。

实现必须显式设置 ORM 流式分块，例如 `yield_per` 或明确大小的 fetchmany/partitions；不能只把 scalars 改名 stream_scalars 后默认迭代。SQLAlchemy 默认 `yield_per=None` 路径可能一次取完 ORM 候选。不得使用 `.all()`/`fetchall()` 把整个候选集合装进内存。物理块大小只影响传输，不构成业务上限，不新增可配置预算或固定块大小断言。

流式仅限制应用层取回和装配，不保证SQLite首行立即可得。若ORDER BY使用临时B-tree，引擎仍可能在首次fetch前扫描、排序大量甚至全部候选。必须对生产同版本SQLite的最不利组合检查EQP、完整调用、读取量和内存，不能仅以“一条SQL”或“使用stream”判为优化完成，也不强制INDEXED BY冻结某一小样计划。

取消覆盖 SQL 启动和每次流式 fetch：对同一 SQLite driver interrupt，等待实际操作退出，finally 关闭游标，再传播取消。达到 N+1、EOF、错误或取消都及时清理。自有session由本次读取退出结束事务；调用者提供session时只关闭本次游标，不commit/rollback调用者事务，其原读快照由事务所有者结束。matcher 的线程退出信号继续保留，不能声称取消 asyncio 等待就硬终止 OpenCC。

长只读快照会推迟 WAL checkpoint，但不因此获得 writer 锁；关闭游标不等于释放调用者快照，writer能提交也不等于reader已退出。不为此增加经验超时、扫描帽、分批提交读事务或盲重试。仅 exclude、全部 gram 假阳性等情况仍可能穷尽合法候选；真实没找到和被中断不能互相冒充。

单次参数验证优先删除Main上游重复解析，保留一个实际边界；不要为了传typed对象扩展所有Social工具的通用签名或增加dict/model双形态兼容。现有settings的limit/before/after缺省值继续生效，显式参数仍覆盖缺省值，不能退成硬编码20或丢失around默认条数。Client/Plugin自身外部边界验证仍各自存在。

媒体条件按真实候选SQL形状处理：有全文候选时按事件ID相关EXISTS，不先物化全部媒体；无全文候选则保留媒体IN集合，避免极稀疏媒体逐条探测聊天。隔离2万行对照证明一律EXISTS会把纯稀疏媒体由约2ms退化到约38ms；此处按是否有全文候选分支，不加统计预查、选择性阈值或新planner。

## 5. 邻文：删除确定冗余，保持有界读取

- 普通 search 的 context_before/context_after 默认0，继续按需读取；不自动为每条命中展开邻文。
- 对已通过当前范围与谓词核验的命中，直接使用该 EventRecord 查邻文，不再 SELECT 中心。
- 执行入口继续沿真实授权/原回执确定范围；仓库 `history_around` 按传入Conversation、事件和真实谓词核中心、keeper及事件类型，再复用小型私有邻文读取函数。不把Social actor/operation解析搬进仓库，不增加公开skip_validation/trusted_anchor开关或认证token。
- before/after 只需指定数量的行，不需要侧页 has_more，删除为复用普通分页而多读的 N+1 和无用 page/matched_fields 装配。
- 每个锚点按原 Conversation 前后 seek，邻文不继承关键词、作者、日期、附件筛选。正常命中按主键唯一，返回结果继续去重；不为假想重复锚点另建状态。不能按全页最小/最大ID扫远隔区间，也不能为“必须一次SQL”引入全会话窗口扫描。
- 删除中心重查可把双侧 H 个命中的读取由约 `1+3H` 降为 `1+2H`，侧页也不再多读N+1。不同锚点的邻文仍可能有重复I/O；本轮不强制彻底消除它。只在复用现有已读资料能减少代码且有实际计划/读取行数证据时采用进一步复用，不作为完成门槛，不新建区间缓存管理器或覆盖推断算法。
- 返回 matches/context 按原事件 ID 去重，source_event_ids 覆盖实际返回证据，不把探测行、未命中目录或中间无关原文混入来源追踪。

## 6. 索引、复杂度和升级

- 精确 Conversation ID 使用现有主键。Space/Binding 的实际筛选 SQL 与索引同时核对，特别是 OR 和 partial index 条件，不能仅看模型里“已经有索引”。补能加速真实定位的普通索引；测试至少包含已绑定入口和多 thread，不能只测 legacy Space。
- 名称包含匹配本身仍可能扫描目录，普通 B-tree 不能保证 `%词%` seek。先在 SQL 内应用平台/类型/目标过滤、索引连接、ID 页；不得声称添加 name 索引就解决包含匹配。不为小目录直接新增一套名称 FTS 或词典服务。
- 复用既有一张会话前缀 FTS，不重写原文字面语义，不把平台/权限/generation 复制成另一套词元或索引身份。不为此次读侧改造重建全部正文索引。
- 索引变更通过新的冻结迁移建立，不修改已经执行的0147及以前迁移；实施时读取最新 head 后分配版本，不预写未来编号。测试库建表与正式迁移索引一致。
- 单次已选来源表达式仍有约 `O(C·G)` 构建成本，C为 Conversation 数、G为准备后的词元表达式规模；不能把延迟展示资料写成不再需要确定来源集合。
- 结果至少要付出返回文字的读取/转换成本；精核粗略为 `O(K·Q·L)`，K为候选数、Q为词项数、L为字段长度，另有倒排、SQLite 计划/排序成本。最坏可扫描全部合法候选，不承诺所有组合 O(log N) 或固定毫秒。
- 规模实验覆盖大量来源，核实际 SQLite 参数/表达式能力。若遇真实引擎限制，改查询形状，不靠经验平台/会话数量帽拒绝正常范围，不回退扩大范围。

## 7. 防御性编程审查结论

### 本轮应删

目录隐藏20项上限；发现查询字符串128字符帽；历史 entries 误用当前发送资格；元数据强制停用 FTS；重复候选 SQL 和内部 boundary；假候选提前解析完整事件；已知中心重查；邻文无用的 N+1；全目录展示资料装配；外部参数解析后再转JSON重解析；around 内恒真的 view 条件。

连同只服务这些旧行为的代码、注释、文档、配置和测试断言一起删，不给它们换开关。不增加替代候选缓存、扫描预算、自动降级、阈值 planner、索引 ready/repair 服务或后台协调器。

### 按事实保留

- 内部 UUID、整数事件/游标、非负条数、明确枚举、未知字段核验和 target 单一 selector；这些表达真实输入合同，不是经验大小帽。
- 原 actor 当前资格、read_target/read_scope、插件批准和 plugin_background 实际委托；目录不能比相应历史读取暴露更多来源。
- ACP 原出站成功回执、operation 的原来源 Conversation/原事件、keeper 和隐私；失败发送不能当作已发生聊天，原件删除不能找一条新消息代替。
- Person 当前同人族用于选择范围，原作者/Account/Presence/Assignment/Conversation/已付请求及回执保原事实；账号转移不携带旧历史所有权。
- no_autoflush、只读快照、取消及连接清理；N+1 **真实命中**证明 has_more；source_event_ids、隐私代次和发布边界。
- Client 个人 API 自己的本人会话范围，Plugin messages 自己的 invocation 会话批准。优化共同仓库不等于把这些接口改成 Main 的全局查询。
