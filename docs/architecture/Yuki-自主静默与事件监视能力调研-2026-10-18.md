# 自主静默工作与事件监视能力调研

日期：2026-10-18，UTC+8。源码基线：`a12f9dd1e6299fc8753f48e8416cbef8152cb1d3`。
本轮在独立工作树 `quiet-self-initiative/Yuki-QQbot`、分支 `codex/quiet-self-initiative` 调查并修正提示词。
本文记录当前证据、此次修改和后续方向；后续方向尚未实现，不替代现行运行合同。

## 1. 结论与本轮范围

当前执行底座已经允许 SELF 静默做事：使用 Main 的完整工具、管理 Work、委派子代理、保存资料、
等待时间或事件后恢复。实际问题有两层：

1. 系统合同和每轮注入都明确鼓励开启话题，且把 `NO_REPLY` 写成找不到切入点后的选择。
2. Work 的持续执行能力较完整，但聊天等待是接管后续输入，尚不能充当可靠的旁路事件监视器。

本轮已改系统约束、SELF 每轮注入、quiet 的工具说明和现行文档；删除人设示例中重复的通用进度汇报要求。
新指引优先静默推进已有事项、关注重要人物已表达的关切及事件进展、整理工作区与资料、研究或创作。
持续事项暂无变化时保存必要进展并等待，没有需要继续的工作才安静结束；
已有任务需要反馈、约定提醒到期或重要变化需要对方知道或决定时，才按需发送。

本轮没有修改参与机会函数、增加发送拦截器、添加工作量或汇报门槛，也没有实现新监视订阅。
未连接生产数据库、修改生产配置或发送真实聊天消息。

## 3. Work 能力矩阵

| 需求 | 当前能力与限制 |
| --- | --- |
| 静默整理工作区、资料、记忆 | 支持，沿实际工具与原授权执行，内部结果不会自动发到群聊 |
| 长工作、后台子代理、暂停后继续 | 支持持久 Work、独立 child lease、journal、原回执与累计预算 |
| 时间到后继续原工作 | `time_due` 支持绝对时间或秒数；等待释放执行名额 |
| 等自己所属执行或子任务 | `owned_run` 核验真实归属，交付原 run 的结束状态；详细结果沿原查询工具读取 |
| 等当前会话后续消息 | 支持一次性 `conversation` 等待，但接管普通聊天输入 |
| 某 Person 发言才唤醒 | 无原生 Person 筛选条件 |
| 某 Person 提到某主题才唤醒 | 无人物、主题、关键词或语义谓词条件 |
| 跨会话持续关注某人 | 当前等待绑定原 Conversation，不能直接跨会话订阅 |
| 外部事情变化后继续 | 支持获准插件的 `plugin_event`，筛选 plugin/type/source；变化识别由事件生产方完成 |
| 定期查网页、文件或其他状态 | 可以编排 `time_due` 或自动化后调用工具比较结果；没有通用变化检测器 |

[`normalize_conditions`](../../src/yuki/runtime/work_wait.py) 当前只接受 `time_due`、`conversation`、
`plugin_event`、`owned_run`。`conversation` 只接受 `{kind}`，额外人物或主题字段会被拒绝。
此表描述核心 Work/wait 条件，不代表仓库没有业务订阅：已有 `subscription-monitor` 支持 feed 订阅和自然语言通知条件，
`github-monitor` 支持仓库事件订阅。两者的实际范围及与 Agent 持续关注的区别见 §10。
源码默认 `runtime_work_enabled=False`、`subagents_enabled=False`；实际部署开关本轮没有读取，不能据默认值判断线上是否启用。

### 聊天监视的四个具体缺口

**会接管正常聊天输入。** `work_wait.py` 为匹配的 Work 保存输入，
[`OrdinaryAdmission.publisher`](../../src/yuki/conversation/ordinary_admission.py) 将真人事件登记为 `route=work`。
[`processor.py`](../../src/yuki/services/processor.py) 看到该接纳后返回 `work_input_queued`，不会另开普通 Main。
若监视子代理判断消息无关并静默结束，普通聊天入口也不会自动再答这条消息。
现有 `test_open_floor_input_reaches_original_wait_without_waiting_window` 已实际验证这一行为。

**一次性订阅有重新登记空窗。** 第一条匹配后 wait 变为 delivered；子代理排队和推理期间不再订阅。
重新登记以当时 `max(ChatEvent.id)` 建新水位，中间消息不会自动补成信号。
读取历史可以辅助补查，但现有 `read_conversation_history` 只有最近有界条目或单个内部 event 查询，没有连续增量 cursor。

**人物需要再次按原事件查询。** Work 信号当前提供内部 `event_id` 和正文，没有直接带 `author_person_id`。
[`social/history.py`](../../src/yuki/social/history.py) 可按原内部事件返回 `person_id`；昵称或平台账号不能代替人物身份。

**多个子代理能收到同一条首次信号，但不能据此承诺持续广播。** `work_wait.py` 遍历当前会话所有 active waits 并分别投递，
最后只用一个 delivered input 发布普通接纳。多 child 广播结论来自源码，未新增相应整链验收；上述接管和空窗仍然存在。

因此，不应将“给子代理一个盯人目标，再循环 conversation wait”宣传为已经可靠的静默监视能力。
现有等待适合原任务接续；长期观察需要明确与普通回复并存的语义。

## 5. 后续实现方向，尚未实施

建议复用 Work、子代理、事件账本和现有调度，先补以下实际语义：

外部 feed/GitHub 采集、增量状态和已存在的条件判断应先复用现有业务插件，不再新建相同采集器。
新增需求应围绕 Agent 关注目标、聊天人物、原 Work 接续和旁路观察，不能把插件已有的语义通知误列为从零开发项。

1. **旁路观察。** 原任务等回复保留现行接管语义；监视订阅接收有来源的观察输入，同时保留正常聊天的独立接纳。
2. **人物及来源筛选。** 用稳定 Person ID、原 Conversation 和真实事件类型筛选候选；主题相关性可交原子代理判断，不为每条全群消息新建工作。
3. **持久水位。** 在原订阅保存已处理内部事件位置，排队、运行与重启后能按授权增量追赶，不在重新等待时直接跳到最新消息。
4. **实际事件源与间隔检查。** 外部系统有事件就沿插件来源投递；只有读取能力时按时间等待再查，并保存比较所需的原资料。
5. **发现与外发分开。** 相关发现先留在原 Work 或工作区；按原目标、提醒约定和真实可行动变化决定反馈。无需结果时保持静默，不增加汇报完成门槛。

典型目标可以是“关注 Person P 关于论文提交的后续消息，更新资料，有期限变化或需要我决定时告知”。
子代理负责理解新证据和推进目标，持久订阅负责等待和追赶；原 Person、内部事件、Work、授权及回执贯穿全链。
验收需覆盖旁路观察与直接 @ 并存、无关消息、推理期间的多条消息、重启、撤回或修订、跨来源授权及重复回执。

## 7. 第二轮调研：持续关注与唤醒的分工

用户进一步明确：监控与订阅继续查资料，暂不修改其运行机制；自主轮提示词需要先改。
本轮重新核对两处实际提示词，原有“主动开启话题”“确实没有自然切入点时才 NO_REPLY”均已移除。
本节及后续对照只扩充调研，不引入监视运行代码或新依赖。

### 7.1 三种不同的持续行为

| 行为 | 应保留的事实 | 唤醒来源 | 不应混同 |
| --- | --- | --- | --- |
| 自主巡查 | 自己的既有目标、资料与未完成事项 | 合法的自主机会 | 醒来不代表要与人聊天，也不保证按时履行每个既有任务 |
| 事件订阅 | 原目标、关注来源及人物、每个订阅的读取位置 | 新事件或资料修订 | 观察一条消息不代表接管它的普通回复，也不自动证明值得通知 |
| 持续任务 | 原 Work、已有证据、回执及下一步 | 时间、事件、执行完成或真实补充输入 | 等待不需要让模型或子代理一直空转 |

Yuki 当前 `intrinsic` 仍是社交机会函数。实际锁定的参与库 `961155ca3f7c29ea75fe08077e13f4cd1e6881f3`
中，`dynamics.intrinsic_rate()` 乘入真人活动及沉默衰减，`Controller.intrinsic_opportunity()` 传入原群状态；
与[现行参与模型](autonomous-participation-model.md)一致。群聊长期安静时新自主机会减少，缺少活动证据时为零。

因此，修改提示词能改变“醒来后做什么”，不能独立保证“已有关注事项何时继续”。
已有目标应沿原 Work 的确定时间、事件或执行信号恢复；`WorkScheduler` 的时间等待循环独立于新社交机会。
此处是源码调查和设计判断，本轮没有改变概率模型、开启额外周期任务或读取生产频率。

### 7.2 事件等待不等于持续日志订阅

[Inngest 的 waitForEvent](https://www.inngest.com/docs/durable-execution/primitives/step-waitforevent)
明确允许一条事件恢复多个匹配的等待，并可同时触发其他函数；等待期间不保留函数进程，按稳定实体 ID 或表达式关联。
但它也明确只接收开始监听之后的事件，早到的匹配事件不会自动恢复该 wait。
这个限制与 Yuki 的重新等待空窗直接相关：增加字段过滤还不足以补齐长期订阅，仍需独立保存和追赶证据。

[Temporal 的消息机制](https://docs.temporal.io/encyclopedia/workflow-message-passing)
区分异步 Signal 与有处理结果的 Update；接纳信号不是业务操作完成。
[Workflow Streams](https://docs.temporal.io/workflow-streams) 则采用每个订阅者独立 offset，可断线后继续读取。
它目前仍是 Public Preview，日志截断、发布进程尚未刷出的缓冲和消费者处理后未保存位置都存在实际边界，
不能从“持久流”推导端到端不丢、不重或通知恰好一次。

[LangGraph interrupt](https://docs.langchain.com/oss/python/langgraph/interrupts)
可保存当前执行并等待外部恢复；持久 checkpointer 支持恢复原 thread。
但 `thread_id` 不是上游聊天事件的消费水位，checkpoint 也不自动提供事件广播、漏消息追赶或外部通知回执。
恢复会重入包含 interrupt 的节点，已有副作用需按原回执处理。

这些机制只作为设计参考。本轮不建议把 Yuki 的 SQLite Work 整体迁移到另一套工作流框架。

### 7.3 外部源的投递保证需要逐项核对

[Slack Events API](https://docs.slack.dev/apis/events-api/) 要求及时确认接收，再把处理交给队列；
失败可重复投递，文档明确事件系统为 best effort，不能把回调当作无遗漏的永久日志。
[GitHub Webhook](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks)
默认不自动重投失败投递，需要由应用或操作者处理重投。

因此，外部连接已建立、事件到达、已写入内部账本、已交给原 Work、模型已处理及通知已送达必须分开记录。
平台投递 ID 留在接入去重边界，业务订阅和恢复仍沿 Yuki 内部事件、原 Person 与 Work 身份。

### 7.4 对后续设计的收敛

原任务等待用户回复时，现行输入接管有其业务用途，应继续保留；旁路观察应明确表达自己的非消费语义。
一个监视目标收到消息，不应使正常聊天入口或其他监视目标失去该消息。

持续订阅在子代理运行期间仍保留关注及接收位置。先将有来源的新增证据持久交给原 Work，再推进该订阅的读取位置；
副作用是否发生继续认原执行回执。事件修订和撤回也要进入追赶，不能只比较新增 event_id 的大小。
人物、会话、事件类型等事实可以先筛选，开放主题的相关性由原 Work 或子代理结合目标判断，不把自然语言主题硬编码成固定标签。

例如，“持续关注 P 的升学进展，有申请时间变化时告诉我”可以先静默收录新证据、更新资料、继续调查，
直到真的出现相关变化再反馈。模型判断相关、任务需要继续和是否向人发送仍是不同决定。
这是一条待设计和验证的运行路径，本轮没有将它宣传为已支持能力。

## 8. 第二轮调研：开源代理的实际接入路径

### 8.1 Memoh：接收 Hook、定时工作和后台执行各有边界

第二轮固定提交 `67fae5e7c15bfbf29e1d2d9c4fc231ed3f3b1fd1`。
[UserMessageReceived 的实际调用](https://github.com/felinics/Memoh/blob/67fae5e7c15bfbf29e1d2d9c4fc231ed3f3b1fd1/internal/agent/application/hooks.go)
存在，可把 query 等交脚本处理；但它位于接收路径上，不能直接等同于独立持久观察者。
[匹配代码](https://github.com/felinics/Memoh/blob/67fae5e7c15bfbf29e1d2d9c4fc231ed3f3b1fd1/internal/hooks/types.go)
没有执行预留的 conditions，regex matcher 目标也不是正文与稳定 Person。自定义脚本能判断内容，不能据此承诺原生语义订阅。

[Schedule 服务](https://github.com/felinics/Memoh/blob/67fae5e7c15bfbf29e1d2d9c4fc231ed3f3b1fd1/internal/schedule/service.go)
会从数据库恢复已启用日程，但 session 忙碌时本次触发会被丢弃、不重试。
[Background Manager](https://github.com/felinics/Memoh/blob/67fae5e7c15bfbf29e1d2d9c4fc231ed3f3b1fd1/internal/agent/background/manager.go)
的任务注册表是内存 map；输出日志落盘不能证明所有注册任务可以跨服务重启恢复。
可直接参考其静默任务合同，不应照搬忙碌丢弃与内存任务表作为 Yuki 的持久监视方案。

### 8.2 Letta 与 LettaBot：后台记忆、执行恢复和输入订阅需要分别核对

[Letta Memory & dreaming](https://docs.letta.com/configuration/memory)
说明后台记忆整理按完成步骤或 compact 触发；它不是人物或事件监听服务。
[Long-running executions](https://docs.letta.com/guides/agents/long-running)
处理请求断线后继续执行及输出恢复，也不能单独证明存在外部订阅。

LettaBot 核验提交 `99c3b5dd73550fe0a4eac2ee31b1c3229ca9e550`。
[实际 heartbeat/feed 提示词](https://github.com/letta-ai/lettabot/blob/99c3b5dd73550fe0a4eac2ee31b1c3229ca9e550/src/core/prompts.ts)
把默认静默写入触发上下文：优先待办，可推进项目、研究、整理记忆或接续已有工作；无事结束，有必要才显式联系别人。
这是本次自主轮指引最贴近的额外样本，但其普通聊天自动发送模式不替代 Yuki 的统一显式出口。

它也确实有按人物账号订阅的具体接入：

- [Bluesky 说明](https://github.com/letta-ai/lettabot/blob/99c3b5dd73550fe0a4eac2ee31b1c3229ca9e550/docs/bluesky-setup.md)
  与[适配器](https://github.com/letta-ai/lettabot/blob/99c3b5dd73550fe0a4eac2ee31b1c3229ca9e550/src/channels/bluesky/adapter.ts)：
  Jetstream 长连接按 DID/list 和事件集合筛选，默认 listen，消息再交 Agent；保存 cursor 后可断线重连。
  这是平台账号过滤加语义处理，不是通用 Person/主题条件服务。
- cursor 在模型处理前推进，部分 seen 去重只保存在内存；重连回退窗口没有与模型处理成功或通知回执形成持久原子交接，不能承诺不漏、不重。
- [Gmail polling](https://github.com/letta-ai/lettabot/blob/99c3b5dd73550fe0a4eac2ee31b1c3229ca9e550/src/polling/service.ts)
  保存已见 ID，新邮件进入 silent feed；但先保存 seen 再调用 Agent，下游失败并没有可靠的原事件重试回执。

对 Yuki 更合适的借鉴是“新证据触发静默处理”；人物仍使用自己的稳定 Person 身份，交接与通知使用已有持久 Work 和回执。

### 8.3 OpenClaw：最接近需求的几条路径，不能混为一个功能

固定核验提交 `28f97f236f882af739aac9f0e6e77d83b2da2a7c`。以下是 main 快照，不代表已经运行验收的正式 Release。

| 路径 | 实际机制 | 边界 |
| --- | --- | --- |
| Standing intents | SQLite 保存未来要留意的指令，关键词及 sender/channel 范围匹配后注入上下文 | 只在 eligible user turn 前匹配，不独立启动静默后台执行 |
| Message received / ambient room event | 异步观察独立于 reply dispatch；ambient 的最终文本保持私有，显式消息工具才外发 | 内存 Hook 本身不是持久订阅；ambient 也不是通用人物或主题条件服务 |
| MCP Events | 订阅、持久接收、排队，交 isolated automation 执行，可配置不投递结果 | opt-in 实验 profile；上游 replay、乱序、缺失和去重保留范围仍有边界 |
| Condition watcher | 无模型脚本返回 fire/state，未变化只存检查状态，变化后才调用 Agent | 时间源仍是轮询，stream 源逐批次检查；处理失败后的再次触发仍需核原效果回执 |

[Standing intents 文档](https://docs.openclaw.ai/concepts/standing-intents)
及[匹配入口](https://github.com/openclaw/openclaw/blob/28f97f236f882af739aac9f0e6e77d83b2da2a7c/extensions/memory-core/src/standing-intents-model.ts#L277-L290)
明确限定 user turn；sender identifier 也不是 Yuki 的稳定 Person ID。
其 cooldown、次数与 expiry 默认是产品策略，不作为 Yuki 的设计硬条件。

[消息观察源码](https://github.com/openclaw/openclaw/blob/28f97f236f882af739aac9f0e6e77d83b2da2a7c/src/auto-reply/reply/message-received-hooks.ts#L14-L62)
明确独立于正常 reply dispatch，适合参考“观察不消费普通聊天”的边界。
[Ambient room events](https://docs.openclaw.ai/channels/ambient-room-events)
说明未 @ 群消息的静默执行语义；这与“收到群消息就必须回复”分开，但不证明具备端到端无漏的监听日志。

[MCP Events 生命周期](https://docs.openclaw.ai/automation/mcp-events)
及[接收源码](https://github.com/openclaw/openclaw/blob/28f97f236f882af739aac9f0e6e77d83b2da2a7c/extensions/mcp-events/src/http.ts#L140-L187)
先持久接收再确认，订阅 lease、cursor 和来源可跨重启保存。
[Ingress claim 与 receipt](https://github.com/openclaw/openclaw/blob/28f97f236f882af739aac9f0e6e77d83b2da2a7c/src/cron/store/event-ingress.ts#L46-L76)
共同提交，提供接收交给执行的明确边界；提交后由原 run 负责完成或保留中断事实，不能靠重跑掩盖未知副作用。
上游 null cursor 不提供 replay，truncated 表示历史不完整，不能将本地持久接收等同于端到端恰好一次。

[Condition/stream schedules](https://docs.openclaw.ai/automation/cron-jobs/schedules)
提供“先查变化、再叫醒模型”的样本；stream 有有界合并与丢弃语义，不能照搬来保存每一条聊天事件。
对 Yuki 最有价值的是输入交接和静默处理的语义，不是新增同名框架或复制上游经验阈值。

### 8.4 nanobot：持久收件箱与通知判断分开，但不需照搬额外模型门槛

固定核验提交 `a377a8e0d358d6c072abc125cfcda2dd35be8836`。
[Heartbeat 实现](https://github.com/HKUDS/nanobot/blob/a377a8e0d358d6c072abc125cfcda2dd35be8836/nanobot/cli/gateway_runtime.py#L653-L725)
执行工作时抑制直接消息，再由额外模型评估是否有新发现、产物、错误或指定提醒需要通知。
无 active tasks 跳过是其产品选择；不应把它变成 Yuki 只有已有待办才能研究或创作的新门槛，
也不需为了采用静默语义再加一次 evaluator 调用。

[Local trigger store](https://github.com/HKUDS/nanobot/blob/a377a8e0d358d6c072abc125cfcda2dd35be8836/nanobot/triggers/local_store.py)
保存 inbox/processing，重启可以恢复中断投递；它采用至少一次投递语义。
事件交给 Agent 后的执行失败会记录 error 并完成该 delivery，不保证成功处理，也不无限重试。
这支持“先持久接收、再处理”的参考，但不是原生 Person/主题语义订阅，子代理也不能据此宣称都能跨重启自动续跑。

## 10. 补查现有插件：业务订阅、Hook 与 Agent 关注目标

用户指出插件已有订阅能力后，补查了仓库真实实现。前两轮主要盘点核心 Work/wait 与 Host 外部事件接入，
遗漏了现成的 `subscription-monitor` 和 `github-monitor`；因此有关“尚无语义条件”的结论必须限定在核心聊天等待条件，
不能泛化到所有插件或整个项目。

| 能力 | 已有实现 | 与本次 Agent 持续关注的区别 |
| --- | --- | --- |
| 外部业务订阅 | Subscription Monitor 轮询 RSS/Atom/JSON Feed，GitHub Monitor 轮询仓库事件 | 管理员配置具体数据源、目标和通知策略，插件维护各自增量状态 |
| 插件 Hook 订阅 | `event.subscribe` 注册消息/回合/回复等事件观察者 | 开发者注册的进程内通知，部分事件只有元数据，不是持久人物/主题任务 |
| Host 外部事件 | `notifications.publish` 将插件事件入账，可 ask_agent 或 resume_waiting_work | 是来源接入与唤醒机制，不自动定义长期目标或决定关注何时结束 |
| Agent 持续关注 | 希望由 Main/子代理围绕人物或事件目标持续收集证据、推进工作 | 复用已有来源，另外需要原 Work 目标、旁路观察与持续追赶；这部分不能由一次通知等同证明 |

### 10.1 Subscription Monitor 已有自然语言条件

[`prepare_request`](../../plugins/subscription-monitor/subscription_monitor/polling.py) 先按 include/exclude 规则筛选，
再将 `judge_prompt` 或模板作为 `agent_intent`，与新条目证据一起交给统一主 Agent。
它明确要求命中才用 `send_message` 通知、未命中安静结束；插件请求本身 `text=""`，不直接发送动态正文。
所以现有插件已经能做“这个来源出现符合某自然语言条件的新动态时通知”。

[`FeedPoller`](../../plugins/subscription-monitor/subscription_monitor/polling.py) 保存基线、已见标记和 pending 请求，
先持久化待提交请求再标记已见；重试复用相同 event_key 与原参数，并使用 Host 原回执。
它仍只读取源提供的有限快照，同 ID 的编辑不作为新动态，不能据此承诺补齐离线期间已消失的所有历史。

[`plugin.py`](../../plugins/subscription-monitor/subscription_monitor/plugin.py) 当前注册 SUPERUSER 管理命令和后台服务，
没有向模型注册创建/管理订阅的专用工具。它不是 Agent 根据自己的长期目标自由建立的通用人物或主题订阅。
该插件设置 `ask_agent=True`，`resume_waiting_work` 保留默认 false；默认是新外部事件后台任务，
不是自动接续某项既有 Work。Host 已有显式 `resume_waiting_work` 能力，但接入方必须真实选择和配置它。

### 10.2 GitHub Monitor 的通知策略独立存在

[`GitHub Monitor`](../../plugins/github-monitor/README.md) 已保存仓库游标、pending/inflight 和目标策略，
支持事件类型、分支、忽略作者等筛选；目标分别控制文本、卡片和 ask_agent。
[`polling.py`](../../plugins/github-monitor/github_monitor/polling.py) 原 Agent intent 要求每次给出自然反应；
扩展提示审查中已改为按原工作静默处理，需要补充重要信息、履行反馈约定或请用户决定时再发言。
订阅配置、ask_agent 开关及文本/卡片投递保持原行为，未将订阅通知改造成 SELF 自主机会。

### 10.3 Hook 不是业务订阅的持久收件箱

[`EventBus`](../../src/yuki/plugin_host/event_bus.py) 按 EventName 订阅，通知经进程内有界 FIFO 分发；
队满、取消订阅与关闭时允许丢弃，重启不会恢复该队列。
[`MESSAGE_NORMALIZED` 发布点](../../src/yuki/services/processor.py) 只携带是否有正文、附件数量、是否提及 Bot 等元数据，
没有正文和稳定人物身份，不能只靠这个 Hook 实现“某人提到了某主题”的持久监听。
业务插件自己的持久去重与 pending 队列不应与该通知总线混同。

后续若实现 Agent 关注目标，应让现有插件继续负责相应外部来源，Work/子代理负责理解、跟进与产物，
并按原授权和通知约定决定外发；不复制已有来源采集、队列和语义通知链。

## 11. 最终收敛：只改提示词，教会使用现有 Work

按用户最新要求，本轮只调整提示词、工具说明和相应文档，不添加 Goal、长期事项目录、监视器、数据表或运行时控制。
前面的能力调查用于说明真实接口，不作为要求增加架构的任务书。

### 可直接使用的持续工作方式

Work 已能保存具体持续目标、来源、进展、子任务和等待状态；一次唤醒不是一项新工作。
以“持续留意某人的申请，日期或材料要求变化时告知”为例：

1. 原 Work 的 goal 说明目标与反馈约定；已有当前工作直接继续，不反复 accept。
2. 读取获准历史或材料，查证变化，必要时委派具体调查。
3. 按需在 context_note 保存有来源的发现、未决问题与下一步，详细资料留工作区或 artifact。
4. 无新变化但仍需跟进时，用 time_due 或实际可用的事件登记 wait；等待释放执行名额。
5. 新信号到来沿原 ID、来源、预算和回执接续，有应当反馈的变化再发送，整个目标结束才 complete。

注意：无其他结束决定的最终正文，包括空正文与 NO_REPLY，会提交完成决定。因此“没有变化直接 NO_REPLY”
不适用于仍须持续的目标。这次在共享系统约束、SELF 动态指令和业务续跑提示中同步教清楚等待。
当前激活的工作不必 resume；恢复另一项获准原工作时，resume 将它交回原链，不代表当前工作被替换。

conversation 等待没有人物或主题筛选；定期读取历史或资料再由模型判断，是当前接口可做的方式。
不把提示词描述成已实现无遗漏的事件监听，也不为此预先增加新机制。
日常 Main、SELF、自动化和子代理共用基础 Work 指引；自主工作的静默优先指引按 SELF 场景适用，
本轮没有再给日常对话注入长期事项或监视目录。

### 系统提示审查与删改

静态审查能确认重复、过细限制和使用说明缺失，不能证明每句提示对模型有效或无效。

本地自动化测试可确认装配、静默执行和 Work 生命周期接口，不能证明真实模型会稳定选择正确行为。
