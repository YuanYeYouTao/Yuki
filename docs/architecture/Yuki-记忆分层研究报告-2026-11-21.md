# Yuki 记忆分层研究报告（2026-11-21）

本报告是[记忆分层架构书](Yuki-记忆分层架构书-2026-11-21.md)研究阶段（R1–R6）的完整结果、方法与原始数据，从架构书第三版中拆出。架构书只保留结论；结论的依据、查询、候选集与重放明细都在这里。生产数据为 2026-11-21 只读查询。

## 1. 研究结果

研究只做了只读查询和读源码，没有改代码、没有写库、没有调用生产模型。原始材料在附录 B–E。

### 1.1 取样范围与共同限制

- **主人**：所有者（person `0d842ebc`）、active 事实最多的另外 9 个人物（附录 C.1 列出 person_id 前缀）、主群 space `0ae63bce`、SELF 的 global 事实。有群事实的群只有 3 个，另两个各只有 6 条和 1 条非经历事实，所以群只跑了主群。
- **候选池**：active、非经历、`conflict_state=clear`；人物事实限 `authority` 为 explicit 或 self_report。人物分"私聊视图"（全部候选）和"群视图"（证据全部来自主群）两个池。
- **时间窗**：重放用 2026-11-07 至 11-21 的 14 个每日 05:00 快照。
- **策略 A 的模拟方式**：由 Claude（`claude-fable-5-2`）扮演挑选操作，读完每个池的全部候选后按同一份指令挑选，独立做了两次（A1、A2）。**不是生产的 Dream 模型（`deepseek-flash`）**，生产模型的挑选质量未测【假设】。
- **所有者抽查没有做**：第二版要求所有者抽查自己和两三个熟人的候选集。候选集的 ID 在附录 C.3，等所有者过目。
- **没有查部署前备份**；所有数字来自运行中的生产库。
- **重放的近似**：事实在某天是否有效，按创建时间和第一条非 active 状态事件判断；520 条非 active 事实没有状态事件，用 `updated_at` 代替。权威与证据按今天的值算。

### 1.2 R1：核心集用什么方式维护

**做法**。三种策略在同样的候选池上各产出最多 10 条：
- A：模型判断（两次独立运行）。
- B：确定性规则。第二版设想的规则信号在数据里几乎不存在：有证据的 person 非经历事实 594 条里，证据跨两天以上的只有 12 条；`last_confirmed_at` 晚于创建时间的只有 26/991。能用的排序键只剩 importance。B1 = importance 降序、ID 升序（偏稳定）；B2 = importance 降序、ID 降序（偏新）。
- C：明确事实在前，B1 补足到 10 条。

**结果**【实证】（完整表见附录 C.2，候选集 ID 见附录 C.3）

| 指标 | 数值 |
|---|---|
| A 两次运行的重合度（Jaccard），23 个视图 | 0.56–1.00，中位数 0.80；候选池大于 30 条的 13 个视图里为 0.56–0.89；候选池很小或为空的视图重合度为 1，不说明问题 |
| A1 与 B1 的重合度（不计空池） | 0–0.36；所有者私聊 0.11，所有者群视图 0.06 |
| A1 与 B2 的重合度 | 0–0.45 |
| A1 与 C 的重合度 | 0–0.36；所有者私聊 0.05 |
| 所有者私聊 B1 的 10 条 | 2 条同义的身份事实、1 条敏感类事实、7 条工作规则（其中 5 条互相重复） |
| 所有者私聊 B2 的 10 条 | 全部是 11-21 当天的工作规则，多数互相重复 |
| 所有者群视图 B1 / B2 | 含 fact 3513（敏感类，证据来自群聊） |
| 所有者私聊 C 的 10 条 | 全部是明确事实，含过时的 140、141 与重复的 35 |
| A 两次都给出空集的视图 | 人物 9 的私聊视图；人物 4、8、9 的群视图 |

**评估集覆盖**【实证】。PR #683 的 21 例里，事前依据是一条记忆且按 §4.4 可以在失败会话里常驻的有 8 例：

|---|---|---|---|---|---|---|
| R1–R5 | fact 2486（群事实，space `ea413ebf`，证据在本群） | 该群 | 否 | 是（该群只有 1 条候选） | 是 | 是【假设：该群未单独模拟 A，唯一候选是一条群规，按入选计】 |
| R6 | fact 3803（人物 `2ce0ffa0`，证据在本人私聊） | 本人私聊 | 否 | 否 | 否 | 是（A1、A2 都选） |

其余 13 例 P1 不覆盖：D3（fact 3327）的证据来自私聊而失败会话是群，按【决定】不常驻；P2（fact 423）没有证据行，失败会话是群；P1（fact 3157）是经历；P3–P5、E1–E5、D1、D2 的依据在聊天账本里，不是记忆。

**结论**
1. 规则挑选不可用：能用的信号只有 importance，而 importance 不区分重复、时效与敏感程度。这一条的依据是对 B1、B2、C 选出内容的检查（可用附录 C.3 的 ID 复核），不是重合度：重合度拿模拟结果当参照，只说明两者选得不一样。评估集上的实际差别是两条事实：C 与"明确事实 + A"只差 fact 3803 和 1597；两条都来自非生产模型的模拟，其中 3803 被模拟者自己标为是否适合常驻需人工判断。R1–R5 五例共用 fact 2486，是同一条规则的五次违反，按事实算只是一条。
2. 模型挑选的质量明显更好，但每次从头选不稳定；需要"以现有核心集为基础、只看新候选"的增量方式。增量方式的稳定性本轮**没有模拟**【假设】，列为 P1 的观测指标。
3. 明确事实应直接常驻，不经挑选：D5 的依据就是一条明确事实；但明确事实需要先清掉过时的几条。
4. A 如何越过 Dream 的分区与上限：挑选步骤不用簇，一个主人一次调用。所有者的候选池最大（337 条，平均每条 45 字），一次调用约 1.9 万字，在现有 `memory_dream_max_input_characters=24000` 之内。

### 1.3 R2：变动有多频繁

**做法**。在 14 个每日快照上重算 B1、B2、C；A 无法重放 14 次，用"A1 选中的条目中有几条创建于窗口内、分布在几天"作为下界。

**结果**【实证】（完整表见附录 C.4）

| 指标 | 数值 |
|---|---|
| 22 个视图 × 14 天 = 308 个"主人·日"中发生变动的 | B1 30、B2 67、C 31、A（下界）27 |
| 所有者私聊 14 天内变动的天数 | B1 2、B2 8、C 3、A（下界）3 |
| 人物 3、4、8、9 | 14 天内没有新候选，任何策略都不变 |
| 每天有新候选的主人数（全部人物与群） | 1–9 个，中位数 4 |
| 单个主人单日新候选最多 | 38 条（所有者，11-16） |
| 所有者窗口内新增的明确事实 | 6 条，分布在 6 天，每天至多 1 条 |
| 窗口内失效或被取代的非经历事实 | 32 条（person 20、self 12） |
| A1 选中的 95 条的年龄 | 0 到 101 天，中位数 35 天 |

**结论**
1. 每日一批时，任何策略都满足"每个主人每天最多变一次"。按当前消息放置时，变动也不影响缓存前缀。
2. 真正的变动来源是所有者的明确事实（窗口内每天至多 1 条）和已选条目被取代或失效（两周 32 条，分散在全部主人）。
3. 每天需要挑选的主人不超过 9 个，现有模型调用预算的空余（12 次）够用，不需要改 Dream 的预算或调度。

### 1.5 R4：放在哪里

**结果**【实证】
1. **恢复哈希**。`work_contract` 在主 Agent 上把传入的 system 消息换成 `invariant_messages()`（E17）。只要常驻层不加进 `invariant_contributions()`，无论放在 system 还是当前消息，哈希都不变。哈希变了也不是失败（E18）。
2. **compact**。公共压缩范围不含当前消息；`static_count` 按 system 消息条数算（E19）。常驻层放在当前消息时与压缩无关；放进 system 时仍是一条 system 消息，计数不变。只有"在 system 与历史之间插入一条独立消息"这种放法会让计数失配，本书不采用。Work 内的两种压缩都原样保留当前消息：公共压缩保留 `messages[public_count:]`（`services/context_compaction.py:405`），执行压缩的边界不早于初始消息之后（`:584`）。所以长 Work 压缩之后，常驻段仍然逐字在场。
3. **断点**。Claude 方言已用 3 个断点（E6）。Anthropic 接口单请求最多 4 个断点，这一条来自接口文档，**没有实测**（研究不允许调用生产模型）。P1 不新增断点，所以不依赖这个上限。
4. **Gemini 与 Chat Completions**。两个方言都不发缓存控制，只读命中数（E6）；命中靠 Provider 的隐式前缀缓存。生产 11-17 起主对话全部走 OpenAI（E24），生产用的是哪个 OpenAI 方言、是否开了显式断点没有核对。
5. **入口**。所有主 Agent 入口共用 `ContextAssembler.assemble`（E21），在这一处按会话身份解析常驻层即可覆盖主轮、定时任务、SELF 主动轮、外部事件与 Work 续接。子 Agent 用 `static_messages()` 加简报，不经过这里；插件轮走另一条装配路径，本轮只读到入口，没有追到底。
6. **在途 Work**。当前消息连同资料段在首次请求时进入 Work 的 transcript，合同未变的续接沿用日志里的原 transcript（`runtime/work_session.py:141-158`），所以常驻层在一个 Work 内不变。【假设：续接时 transcript 的还原没有逐行追到底，由任务书用例 17 确认】

**结论**：放进稳定前缀是安全的，但 P1 不需要。P1 放在当前消息，新增断点数为 0，不新增稳定档（Q6）。各入口带哪一份见 Q13。

### 1.6 R5：经历目录多大

**结果**【实证】（附录 B.6）

- key 可读的 193 条（17%），全部是非 SELF 经历；SELF 经历 919 条的 key 都是哈希。

**结论**：目录的长度可以接受，但 83% 的条目没有标题来源。目录推迟到 P2，先决定标题存在哪里、由谁生成（Q9）。P1 不做目录。

### 1.7 R6：常驻层的 token 成本

**做法**。按附录 A 与 A1 的候选集计算渲染字数。token 没有用分词器实测，按每个汉字 1.0–1.5 token 估【假设】。缓存命中的输入按未命中价格的 10% 计【假设，未核对生产模型的实际计价】。

**结果**（附录 B.8、C.5）

| 会话 | 常驻段内容 | 字数 | 估计 token |
|---|---|---|---|
| 所有者私聊 | 明确事实约 22 行（附录 A.1、A.2 加保留的现有明确事实）+ 核心集 10 行 + SELF 原则 3 行 | 约 2300 | 2300–3500 |
| 其他人私聊（人物 1、2、3、6） | 核心集 7–10 行 + SELF 原则 2 行 | 550–930 | 550–1400 |
| 主群 | 群核心 6 行 + SELF 原则 2 行 + 发言人至多 5 行 | 约 950 | 950–1400 |

| 基线（11-14 至 11-21） | 所有者私聊 | 主群（11-17 起） |
|---|---|---|
| 请求数 / 轮次数 | 6729 / 270，每轮 24.9 次请求 | 1365 / 388，每轮 3.5 次请求 |
| 平均每次请求输入 token | 约 48000 | 约 42000 |
| 缓存命中 | 按天 80%–94% | 按天 90%–94.5% |

| 估算（按 3000 / 1400 token） | 所有者私聊 | 主群 |
|---|---|---|
| 每轮新增的等价未命中 token，放在当前消息 | 约 10200（+4.7%） | 约 1750（+7.5%） |
| 同上，放进 system | 约 7500（+3.5%），另加每次变动约 43000 | 约 490（+2.1%），发言人部分仍在尾部 |
| 每次请求输入 token 增幅 | +6% | +3% |
| 缓存命中率变化，放在当前消息 | 约 +0.3 个百分点（后续请求都命中） | 约 −0.7 个百分点 |

**结论**：成本在个位数百分比，两种放法差 1–5 个百分点，按会话不同（所有者私聊约 1 个，主群约 5 个）。它不构成把常驻层放进稳定前缀的理由。

### B.4 候选池定义（R1–R3 共用）

- 共同条件：`status='active' and kind!='episode' and conflict_state='clear'`。
- 人物私聊视图：`scope_type in ('person','person_group') and canonical_subject_person_id=:p and authority in ('explicit','self_report')`，且来源集合里没有别人的私聊。
- 人物主群视图：私聊视图中，来源集合非空且全部是 `('group', 0ae63bce…)`；person_group 事实还要求 `canonical_subject_space_id` 是主群。
- 主群群事实：`scope_type='group' and canonical_subject_space_id=:g`，来源集合非空且全部是本群。
- SELF：`scope_type='self' and visibility_type='global'`；"群可用"再去掉来源含私聊、没有证据行或证据事件全为空的。

### B.5 策略定义与重放（R1、R2）

- B1：`order by importance desc, id asc limit 10`。B2：`order by importance desc, id desc limit 10`。

## 附录 E：策略 A 的模拟指令

两次独立运行使用同一份指令，各自读完全部 12 个候选池（10 个人物、SELF、主群）后给出 fact ID。指令要点如下，原样用于模拟：

> 对每个主人，从候选里挑出"面对这个主人时，每一轮对话都值得放在眼前"的稳定核心事实，最多 10 条，宁缺毋滥，可以少于 10 条甚至 0 条。
> - 选：身份与关系、称呼、长期稳定的喜恶与边界、长期目标或长期状况、长期有效的互动方式要求。
> - 不选：一次性任务指令或某个 PR/issue 的当次要求、当次事件、时效性强的状态、琐碎细节、玩笑梗、对某个模型或产品的随口评价。
> - 同义重复只留一条。
> - 所有者的开发流程、委派、汇报与生产边界类规则另有一节，不选进人物核心。
> - 每个人物给两份：私聊视图从全部候选里挑，敏感隐私是否入选按"对与本人相处是否必要"判断；群视图只从证据全在本群的候选里挑，不得选健康、性、财务。
> - SELF 只挑稳定的行为原则，不挑口味、人格设定、能力描述与单次教训。
> - 群只挑群规、长期约定与稳定的称呼约定。

两次运行都报告完整读完所有候选池。它们各自标注的不确定处（只含 ID）：所有者私聊都选了敏感类的 fact 2474；fact 1520 与 2188 可能互相矛盾；人物 6 的 fact 3735 可能已被 3737 更新；人物 6 的 fact 3803、3845 是否适合常驻需人工判断。

这份指令与 §4.6 推荐的生产步骤有三处不同：生产步骤是增量的（以现有核心集为基础，只看新候选）；每个主人只有一份列表（群聊里按 §4.4 过滤，不另选群视图）；模拟指令明确排除了所有者的开发流程、委派、汇报与生产边界类规则，而任务书 §7.2 的生产指令只靠"与已常驻的明确事实同义的不选"，自动保存的规则类事实（如 fact 3944）仍是候选，是否补进生产指令列在任务书 §15。按单份列表过滤后群里还剩多少，见 §7.4。
