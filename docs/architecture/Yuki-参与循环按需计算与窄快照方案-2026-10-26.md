# Yuki 参与循环：按需准备，窄进度保存

日期：2026-10-26。本文为方案与本机实验记录，后续实现、复审与交付见[实施记录](../operations/algorithm-performance-implementation-20261026.md)。本方案替换 [10-25 总任务书](Yuki-算法与资源开销优化任务书-2026-10-25.md)的 D02、A01–A04；其他算法工作包继续沿用总任务书。

主仓库基线 `75e21a5c824876485d75e7fcd58e8111bdddeb4d`，参与库固定 `79d266918dc6ce19b7d81568565deaed450301d5`。库源码按固定 Git 对象读取，本机 venv 中的另一个版本未作为证据。约束见[开发合同](development-contract.md)、[参与接入](semantic-participation.md)和[数学合同](autonomous-participation-model.md)。

## 1. 这次怎么改

现在每两秒，不管一个会话有没有新情况，基本都重新准备历史、回执、身份和配置，最后把整个参与状态保存一遍。时间计算确实有用，但它拖着一大堆没变的材料一起跑。

改为三件事：

1. **必要计算照常推进。** 原连续衰减、来源到期、两秒抽样和随机序号都保留。
2. **重准备认真实变化。** 历史正文、来源投影、身份归一和回执分组没变，就复用准备结果。Jev 还在退避时，不为新请求准备整套材料；清理到期项、quiet 复核、既有反馈和 intrinsic 仍继续。
3. **进度和正文分开放。** 每次抽样仍保存真实数值进度；冷材料有变化才重新编码、写入。两者仍是一份快照，共用一个 Store、一个 revision、一次原子提交。

不另起调度循环、数据库 runtime、后台队列或新服务。不增加用户配置、经验冷却或“满足某指标才算完成”的条件。删掉的是重复工作。

## 2. 为什么撤回上一版的时间锚与随机键改动

上一版为了少保存，建议改成按时刻生成随机键，并让无新贡献的 baseline 长期不重锚。现在有三个本地反例：

| 问题 | 原程序 | 少存或合并后 |
| --- | --- | --- |
| 十次两秒衰减与一次大步衰减 | activity `0.21495939317213694` | `0.21495939317213697`，差 1 ULP |
| 运行时 tau=60、恢复时 tau=30 | activity `0.014936120510359197` | 旧锚恢复为 `0.010702198004175741` |
| 五次未提议的抽样之后重启 | sequence=5，下一 arrival 为 `0.4518963454237354` | 未保存则回到 sequence=0，下一 arrival 为 `0.854291853456234` |

因此不改随机键、不跳原数值重锚、不改冷恢复解释。旧 `sample_sequence` 的哈希材料、arrival/selection 两流、浮点顺序、候选次序与原保存点保留。非空 scores 分支即使 `dt=0` 或 total=0，也按旧代码增加 sequence，不能另加捷径。

保留原崩溃恢复，就不能普遍做到“空闲零写盘”。这一版的目标是**必要的小进度继续保存，大材料不再跟着重写**。精确反证和浮点值见[等价研究](research/participation-20261026-equivalence.md)。

## 3. 一轮怎么走

保留现有 `sleep(2)`、session 生命周期、并发二、约十秒新 scope 发现及原执行顺序。已有确定入口和普通聊天不排进新的参与任务队列。

```text
原 tick
  → 读取本 scope 当前窄事实，比较原准备依赖
  → 只重做变化或到期的 Social / 历史 / 身份 / 配置准备
  → observer 本地清理与 ready 判断
  → 真正有新 Jev 请求时才准备并发出；await 后继续核当前来源
  → 原 pending 查询/重试接纳，保持其早于 advance 的位置
  → 按原分支 advance：衰减、资格、原随机流
  → 冻结本次进度；冷材料变化时一起冻结
  → 原 Store 单 CAS 提交；确认真实 revision
  → 若有新 proposal：原 admit → 再 save
  → 原末尾 reconcile
```

保留 Social 效果应用、hydrate、第二次绑定、观测、post-await 核验、pending 查询、advance/save 的先后关系。不能把原本下一轮才应用的回执提前进本轮 rate。提示只令准备过时，不额外触发一次抽样。

### 3.1 凭什么知道材料没变

不能只看 `_dirty`、最后消息 ID、行数或最大更新时间。撤回、补全、人物合并、配置删除和迟到回执都可以没有新消息。

| 原领域 | 每轮需要的当前事实 | 不变时省掉什么 |
| --- | --- | --- |
| Event ledger | 既有 Conversation generation/floor/prompt_source_revision；保留源的实际有效性 | 64 条正文重读、重复事件投影 |
| scene / routing | 原 Presence、binding、route、space.enabled 等窄字段 | 同轮重复场景装配 |
| 参与配置 / owner | 全局与本群实际参与 key、删除与 override、autonomy binding | 每 scope 完整 RuntimeConfigSnapshot 装配 |
| Person | 本轮实际 actor/target 的当前归属，原执行处权限 | 重复 ID 收集和同阶段身份归一 |
| Social | 近窗原标量 proof、live FK、caption 的 parent 依赖闭包 | 大字段搬运、未变页的分组和纯绑定准备 |
| admission / Work / Memory | 原 owner 的已提交 admission、run/receipt/source 行 | 未变事实的解析与投影；缺少完整窄合同的部分仍读取 |
| 本地 queue / Controller | 实际成员、来源变化与原精确期限 | 未到期且依赖未变的离散结构准备 |

优先批读原 owner 的窄数据，不建立全库 revision 服务或持久 dirty 表。`commit_hints` 只是可丢的全局 bool，诊断提交也会触发，不能当完整失效依据。没有完整证明的领域保留原读取，先减少解析和装配；不靠“每 N 轮重建一次”补漏洞。

所有复用放在原 `_Session(conversation,generation)` 生命周期内，退休时自然释放。身份根和当前行只是准备材料，不能作为跨 await 的永久授权。等待 semaphore 或 Jev 后，沿原场景、generation、来源及接纳 CAS 核验当前事实。窗口外仍被 unit、boundary 或 caption 引用的源同样覆盖。

### 3.2 Jev 不可用时做多少

把 `ObservationSession` 中便宜的 readiness 判断提前，真正消费 queue 的 `take` 仍在原请求入口。期限来自原规则，不新增等待：

```text
debounce_due = min(last_dirty + 3, first_dirty + 20)
request_due  = max(debounce_due, last_call + 12, retry_after)
expires_at   = event.at + 75
```

先处理原到期/撤销；有 in-flight 不开第二个请求。首次 last_call=-inf 不额外等十二秒。request_due 不早于 expiry 的项没有新的合法观测机会，但仍保留 expiry 清理。最终选择仍走原 priority/顺序，不把“最早 due”替换为被选者。

Jev 退避或无凭据时，省掉的是只为新请求服务的上下文、身份与冻结工作。quiet 复核所需事实变化时仍处理；真实 feedback、SELF/intrinsic、主聊天和已接纳任务照常运行，不把 provider 健康变成 host_available 或接纳门槛。

### 3.3 同一次计算只准备一份

- feedback 内逐条 `any(effects)`，改成同次 prune 的 recent run 集：`O(F×E) → O(F+E)`；原 cutoff 和保留次序不变。
- 同次同步 evaluation 共享 eligible groups、pressure、排序后的来源和一次解析的 participation checkpoint。中途真实写入后按依赖重新准备，不跨 await 复用资格。
- 保留每条原 decay/observe 的浮点步骤，只复用完全相同输入的准备或已计算值，不合并求和、换排序或跳数值 fold。
- 到期准备从原状态求最早边界；先线性 min，不加 heap。新增、替换、撤回、晚到结果、配置变化和删除最早项都重新导出。跨过多条期限只清理当前事实，不补发历史观察。

原 typed Record 只是浅冻结，内嵌 dict 仍可变。默认不把 raw checkpoint 和 typed 图各常驻一份；同一调用显式传准备值，未知 namespace 与原单 unit reader 的读取语义保留。

## 4. 一份快照，两种物理材料

### 4.1 字段怎么放

固定库的 State 共 38 个字段，已做全集分类，详见[字段与存储研究](research/participation-20261026-state-storage.md)。本轮不借存储优化删除仍属原快照的计数或状态。

| 数学进度：普通 tick 更新 | 冷材料：真实结构或内容变化时更新 |
| --- | --- |
| now、last_sample_at、sample_sequence、skipped_seconds、replay_after、baseline 计数 | 原 scope/epoch、事件、观察、候选、提议、pending、运行与效果 |
| belief 的 at/value/last_action，原 trace、attention 数值、可选 reception baseline | belief key/thread/target，attention key/顺序、来源与 boundary |
| 保留旧浮点值与每个更新步骤 | observer/host checkpoint、自报、熟悉度、work pulse、发送锚、reception 等真实事实 |

身份长字符串只存一份冷布局。热数值按同一原字典位置对应；身份、成员或顺序变化时，布局和数值同时提交，不重排原求和顺序。last_action 也可能在时间边界跨过仍保留的 effect 时改变，不能当冷身份。它引起原 belief 字典换序时，直接做一次 full save，不加 slot 排列表或第二索引。位置是编码细节，不是新的业务 ID。冷材料不只随聊天变：600 秒来源退休、两天 reception 归档、quiet/health 或 pending 到期都可能要求 full save。

热区大小记为 H，冷体为 C；普通保存编码成本从 `O(H+C)` 变成 `O(H)`。H 不是常数：本地修正后的 64 个 belief、七个数值/项的热 JSON 为 8,568 B，长身份留冷体，attention 和整数位数仍会影响 H。原 Python 整数不改成 uint64，不新增 header 上限。

### 4.2 选定窄 head 与冷 body 两表

同一 Store、同一数据库、同一连接 owner：

```text
snapshot_head(scope, generation, revision, progress, logical_bytes)
snapshot_body(scope, generation, body, logical_size_delta)

主键均为原 (scope,generation)
revision 只在 head，body 没有独立 revision
load：原 key 驱动的单个一致性 LEFT JOIN → 重组原 State → 一次模型校验与 scope 核验
```

名称是示意；确定的是竖向隔离、单 revision 和原子性。head 的变化不触碰冷 body 的 overflow 页。full save 在原 BEGIN IMMEDIATE 事务里核 CAS、更新 head/body 并提交；hot save 只更新 head。读取用单个 key 驱动的 LEFT JOIN 区分两侧均无记录与仅缺一侧；后者报真实错误，不能用 INNER JOIN 的空结果悄悄新建 Controller。布局不匹配同样不猜测、不填空、不从旧副本回退。

不选“同一 row 新增 hot 列”。本地 SQLite 3.46.1、4 KiB 页、WAL/FULL，十二次更新结果：

| 合成冷体 / 热体 | 整份 payload | 同行两列 | 窄 head + 冷 body |
| --- | ---: | ---: | ---: |
| 约 64 KiB / 约 460 B | 312 帧 | 312 帧 | 12 帧 |
| 约 512 KiB / 约 460 B | 2,328 帧 | 2,328 帧 | 12 帧 |
| 约 512 KiB / 约 16.6 KiB | 2,400 帧 | 2,400 帧 | 93 帧 |

同行 row 在 revision 127→128 或 hot 增一字节时可能重排整个 record。少绑定一个大 BLOB 并不等于少写磁盘。以上是本机合成布局实验，未包含原容量查询，不是生产延迟或总写盘倍数；可移植摘要见[实验数据](research/participation-20261026-evidence.json)。

### 4.3 编码、容量与保存竞态

producer 先取得原 `_save_lock`，再在提交前的同一无 await 片段中物化本次确实变化的 checkpoint、捕获 dirty、冻结 scope/generation、当前 expected_revision、热 bytes 及必要冷 bytes/布局。不能在等锁之前冻结 revision；pins 只防退休，不是修改锁。worker 只处理不可变交付，不再 State→JSON→State→JSON；冷加载重组后只解析一次。不把实验中全量 dump 再 split 的原型移入热路。

保原 1 MiB/scope、16 MiB 总逻辑容量语义。物理热冷 JSON 长度之和不等于旧完整 State JSON 长度，使用确定公式：冷准备时，原 Pydantic 完整编码长度为 L，精确 typed 热编码长度为 H，保存有符号差额 `logical_size_delta=L-H`；后续热保存计算 `logical_bytes=logical_size_delta+len(new_hot_bytes)`。两种表示的包装差异、原 key、身份和未知扩展都折在该差额内。冷热布局、成员顺序、存在性或容器形状改变就重算，不把结构变化误判成纯数值变化。

热编码必须保留原字段的序列化类型，例如 float 默认值虽是 Python int 0，原字段仍应编码为 0.0。采用明确类型的数值向量/元组及同一 Pydantic 配置；所有动态叶在两种表示中必须具有相同的标量 token。不以泛型 Any 或 stdlib JSON 估计，不逐叶另建长度账本。长身份、转义、负零、非有限值、任意长整数与未知扩展分别对照原完整编码。

冷/full save 接受一次原完整编码计量和一次新 body 编码的成本；不再声称冷体只编码一次，也不为此造 JSON 拆片器。hot save 不编码、hash 或读取冷正文。总量沿 head 长度元数据查询，覆盖全部原 scope/generation，不新增增减维护的全局字节账本。差额只是随该冷体原子保存、可重建的编码元数据。迁移初始 logical_bytes 保留旧 payload 的实际字节长度，避免仅因格式归一化改变其他 scope 占用；第一次原语义 save 后才按上述新 State 的原编码长度更新。

删除 `_Session.saved` 整份 JSON 比较之前，库与 Host 的真实变更入口必须能报告“仅热 / 冷也变”。`observe_committed_event(False)` 仍可能补 source_order，`evaluate_due(False)` 仍可能改 queue/health；原 bool、对象地址和返回 None 都不能替代变更事实。checkpoint 只在 queue/health 真实转换时物化，不每 tick 重建再比较全图。

保存沿原锁顺序：取得锁后，捕获并取走本批 dirty 与冻结必须在同一同步片段；await 期间的新变更重新留下 dirty。成功只确认本批 revision/已提交 codec 元数据，不清后来的标记，也不把旧 batch 的 State 或布局写回当前 Controller。冻结、编码、任务提交前异常及已确认回滚都只把本批 flags 并入当前 flags，不恢复旧 State。

取消等待原 operation 完成，确认提交先更新 item.revision，再传播取消。只有实际 future 成功才推进 revision；异常不能假装已确认回滚，不自动重放冻结 payload，也不编造一个现有代码并不存在的“未知提交恢复器”。未确认的错误沿原异常/CAS 事实暴露。不新增第二队列、持久变更日志或影子版本。

不延后原保存点，不等多个 scope 集齐，不新加 fsync 合并窗口。先把写的东西变小，避免让快 scope 等慢 Jev 或让前台增加排队。

### 4.4 迁移与恢复

停止旧 writer 后做一次原子格式迁移：事务外读取旧 payload，按固定旧 schema 准备配对数据；格式拆分不调用 restore/advance/prune，不提前重锚或重置时钟。然后在一个迁移写事务内只核对原 key/revision 集合、创建/填充配对新表并删除旧 snapshots 表；不在写事务中解析或扫描历史正文。

每个 scope 保留原 revision、generation、epoch、原 proposal/run/receipt。SQLite 的表切换与数据一起提交：提交前中断回滚后仍是旧表示，可重新执行同一格式升级；提交后只有新表示。以实际表结构识别格式，不新增版本计数或迁移标记。新数据库一次建齐两表；已有库的半对或新旧混合布局报真实格式错误，不补成空状态。正常运行没有双 reader/writer，也不新增逐 scope 迁移进度或恢复器。迁移准备的峰值内存单列测量，不加新容量门槛；原容量政策和旧 payload 长度继续处理。

另一本地 SQLite 3.53.1 小实验验证了 DDL 提交前另一连接仍见旧表、rollback 保留旧表/值、commit 仅发布新表并保留 revision；结果已收进实验摘要。这不是最终 Store 迁移实现的验收。

加载时用单 JOIN/同一读取快照取两部分，重建原顺序和数值，再交原 `Controller.restore`。原 restore 的 now/last_sample_at 重置、停机不补抽、当前配置 prune 与旧序号继续方式都不改。旧未知扩展保留原 reader 语义；损坏不伪装成空状态。删除 scope、close、过期 session、容量统计和未完成原 run 的 reader 一起迁移。

## 6. 验收看什么

正确性按固定外部返回与相同 tick 时刻逐步配对；真实运行耗时减少会改变实际墙钟，不能把两次自由运行当成同一随机实验。

| 组 | 必须覆盖 |
| --- | --- |
| 原数学 | 全部 State 浮点逐 `float.hex()`、负零、字典次序、sequence、arrival/selection、同一 UUID 来源；dt/total=0、无 scores、明确邀请、pending/capacity、epoch |
| 时间/输入 | 600/3600/两天边界前等后、同时间来源、晚到/撤回/补全、原 proof 退休、参数热更；每个原保存点后 crash，以相同恢复时刻与旧/新 tau 对照 |
| Host 依赖 | 提示丢失、配置删除/rollback、Person 合并、route/Presence、无消息新增 scope、窗口外父 caption/SourceRef、终态 run 的晚到回执、await 后撤权 |
| observer | 空队列、fresh backoff、过期、in-flight、失败/晚到结果、quiet 纠正；不提前 take、不增加请求或改原退避 |
| Store | 全 38 字段热冷覆盖、布局增删换序、CAS 冲突、提交前后读配对、head-only/body-only 损坏、rollback、取消/close/确认未知、保存期间新冷变更、原子迁移中断重开、纯拆分不提前 restore、真实 scope 校验 |
| 容量 | logical_bytes 与旧完整编码逐字节等长；scope/总量阈值前等后、超长身份/整数、未知扩展、非规范旧 payload、退休 generation 总量，不静默忽略冷体；迁移初值单独对照原 payload 长度 |
| 性能 | 1/8/32 scope 的空闲/候选/突发/Jev 退避与慢请求；不同 H/C、revision 跨编码宽度，实际 JSON/SQL/绑定字节、WAL、CPU、峰值内存与 loop/前台延迟 |

成功表现：仅热变化的编码和绑定量随 H 增长，不随 C 增长；冷体未变不重写；重复准备次数下降；相同输入时刻下原行为精确一致。仍有当前窄读与每 scope 数值推进，所以不宣称总成本 O(1)，也不宣称本地 WAL 帧下降就是整机同倍提速。

不靠削历史、改概率、延长保存周期或加缓存额度获得数字。若最后 fsync 仍占主导，单列测量结果再决定下一步，本方案不预埋批量协调器。文档、实现、CI、PR、合并与生产效果分别记录。
