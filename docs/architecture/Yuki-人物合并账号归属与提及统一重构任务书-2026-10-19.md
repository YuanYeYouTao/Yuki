## 2. 统一模型：两个对象、一种归属关系

### 2.1 先纠正抽象，再决定表和接口

用户提出的“平台账号、Person、后端权限”抓住了主要边界。进一步收敛：**Account 和 Person 是身份对象；账号归属是它们之间的关系；权限是后端消费真实关系作出的决定。** 后端不再持有另一种人物，也不建立一套通用权限主体或 RBAC 框架。

设 A 为已知稳定平台账号的集合，P 为现存 Person 记录的集合，Y 为本库唯一的 Yuki：

```text
Account 的原生唯一键 = (platform, stable_native_account_id)
r : P → P                         当前人物代表，r(r(p)) = r(p)
u : A ⇀ (P ⊔ {Y})                 当前归属，允许没有归属
human_owner(a) = r(u(a))           仅 u(a) 是 Person 时有意义
```

`⇀` 表示部分函数：一个账号最多有一个当前归属，可以尚未关联；多账号可归同一个人，人物可以没有账号。因此不要求满射，也不要求每个原生账号都创建 Person。第三方 Bot、只有地址但没有稳定 ID 的 TG username，不为补齐函数伪造人物。`Y` 是现有唯一 SELF 身份，不新增一行 Person、Principal 或 owner 注册表。

同平台相同稳定原生号是一个 Account；同数字跨平台是两个 Account。名称、username 和群名片可变且可重名，均不进入唯一身份键。App/ACP 的真实本地地址可继续使用原内部入口标识；设备凭据直接证明原 Person，不为图形整齐再套平台账号或从新 root 制造新入口。

### 2.2 只保存一份账号归属关系

采用 **Account＋AccountAssignment**，真正替换现有 `identity_bindings`／`presences` 两份持久归属。Binding 和 Presence 保留为类型明确的领域投影：

| 概念／资料 | 唯一事实源 | 职责 |
| --- | --- | --- |
| Account | 稳定内部 UUID、原生唯一键、当前账号昵称 | 跨归属阶段的账号资料；无 Person 的原生提及目标 |
| 账号群资料 | Account＋SpaceBinding | 当前账号在这个具体平台群的名片；Person＋Space 只保人物语义关系 |
| Person | 原 UUID、现有单层 root、人物资料与人物资格 | 统一同一个人的当前资料和权限归属；原编号不复用给别人 |
| AccountAssignment | 原阶段 UUID、Account、kind、原 Person、status、真实阶段时间 | 唯一带历史的归属关系；`kind=person` 是 Binding，`kind=yuki` 是 Presence |
| Conversation／设备／执行／回执 | 各自现有原记录 | 分别证明上下文、认证来源、执行来源与已发生效果，不纳入账号 owner |

Assignment 的 person 类型必须带原 Person，yuki 类型不带 Person。一个部分唯一索引直接保证每个 Account 最多一条 `status != ended` 的记录；不再跨两表反查互斥。一个 Account 可以没有当前阶段。旧 Binding／Presence UUID 原样成为相应 Assignment ID；改变外键目标，不重编号，不改原调用 JSON／hash。

只保一份 `status=active|disabled|ended`：可用、暂停、已结束。暂停仍有归属；结束才释放归属。保三种真实情况足够，无状态机框架、另一份 enabled、当前角色指针或同步层。`ended_at` 只记录有证据的结束时间，旧已结束但时间未知可为空；当前性按 status，不能用空时间误判仍有效。新阶段的已知时间采用 `[start,end)`。

Presence 的既有 ingest 选择政策仍属于平台接入，连接仍属于 Registry 的真实句柄；二者不复制到 Account，也不混进人物权限。

### 2.3 人物合并是等价关系，账号转让是关系替换

`p ~ q` 当且仅当 `r(p)=r(q)`。同人关系满足自反、对称、传递；root 是存储代表，不是另一种人。在同一真实调用者及授权范围下，当前资料必须满足 `p ~ q ⇒ data(p)=data(q)`，不能旧 A 引用报错、新 B 引用才读到。沿现有扁平 root 实现，A→B→C 后 A/B 直接指 C；重复合并同一当前人物只读返回。不加同人组表、递归 resolver、身份缓存或资料搬迁 worker。

| 操作 | 数学上的改变 | 原事件、原执行与回执 |
| --- | --- | --- |
| 改账号昵称／群名片 | 只改账号资料 | 不变 |
| 改人物名字 | 只改人物资料，旧名保别名 | 不变 |
| A、B 是同一个人，合并 | 合并 Person 等价类；原 Assignment.person_id 不改 | 原 actor 仍为原编号，当前资料按同人关系完整可用 |
| 账号从 A 真正转给 B | 结束原 Assignment，建立 B 的新 Assignment；不改变 A、B 同人关系 | A 的旧历史、设备、资格与任务不转给 B |
| 解绑 | 结束原 Assignment，不建立新归属 | 不删除原 Person 或冒改旧作者 |
| 暂停账号阶段 | 只改这个 Assignment 的使用状态 | 不抹归属，不等于解绑 |
| 停用人物 | 暂停当前人物的正常使用 | 不删除资料或改历史；真实旧撤权仍有效 |
| 重读成功回执 | 读取原结果，不做身份变换 | 不用今天的账号状态重新执行原操作 |

“增删改查”可以描述外部操作，但实现必须区分删除资料、解除关系和结束阶段。人物遗忘沿现有完整同人族隐私删除清退资料及必要记录；仍保留的无正文回执只保原 ID，不据此重建人物或正文。账号解绑不隐式触发人物遗忘，账号转让不替新人领取旧资料。

同人关系的合并在数学上与代表选择无关；主名、路由、配置的冲突选择有明确方向，不能把“目标优先”冒称为可交换的集合并集。合并关系本身可重复归一，真实原 request_id 始终读原回执。

### 2.4 一次回答一个身份问题

| 问题 | 使用什么 | 不附加什么 |
| --- | --- | --- |
| 这些资料属于哪个当前人物 | `current_person_id`／同人族查询 | 资料原 owner 的启用、在线或账号数量 |
| 这件事当时是谁做的 | 原事件／设备／Work／grant 接纳时的 source Person | 今日账号 owner 或最新 grant 的创建者 |
| 现在能否做这项操作 | 真实 actor、动作、资源与该入口已有授权 | 被读取资料或被群内提及对象的启用门槛 |
| 现在从哪个账号发到哪里 | 原 Conversation／明确 route、实际 Assignment 和连接 | 任意全局人物名字猜测 |
| 这次实际发生了什么 | 原执行 ID、请求与回执 | 今日 root、昵称或新的 schema 重新解释 |

原来源有效性复用 `person_enabled_condition(raw_source)`：原来源启用且当前 root 启用；人物资格只取当前 root。这个谓词只在真实执行授权边界使用，不返回另一个 actor，不用于资料 owner 或被提及者。它保留现行已撤权事实；若删掉它，就必须把旧人物停用广播到设备、Binding、grant、Work 再设计恢复，反而制造更多耦合。本任务不增加这种广播、来源控制面或 source-policy 对象。

代码落实为“原 ID 贯穿，按问题查询”：

- `ToolActor`／`source_person_id` 始终保原编号，不把局部变量改成 root 后继续传作 actor。人物资料仓库直接按 family 过滤，权限函数只返回实际授权结论。
- 当前资格沿现有 `identity/authority.py:10–28` 的 source→root 单次 JOIN 读取所需字段；单对象资料直接 JOIN 取需要的列。删除 `current_person_id→get(root)→require_live_person` 反复组合和去 Presence／Space 表试错类型的查询，不新增身份上下文大对象、策略参数或缓存。
- 一页目录需要当前人物投影时，在页查询 JOIN 或复用既有 `current_person_ids` 批读；不在每行里 await 一次 root。真实 claim 仍复核实际来源与当前资格，准备结果不代替执行授权。

## 3. 操作内核与当前资料

### 3.1 三个关系原语，入口复用同一实现

普通人物／账号资料的查询和修改沿各自仓库。改变身份关系只保下面三个内部原语，名称可按现有模块习惯调整：

| 原语 | 唯一职责 | 消费入口 |
| --- | --- | --- |
| `merge_persons(source, target)` | 合并当前同人关系和必要当前资料，保原身份来源 | 已认证同人 link、明确管理合并 |
| `replace_assignment(account, expected_assignment, new_owner)` | 同事务结束原阶段，按需创建 Person／Yuki 的新阶段；无当前阶段可明确登记 | attach、真解绑、transfer、Yuki 登记与角色转换 |
| `set_assignment_usage(assignment, enabled)` | 改未结束阶段的 active／disabled，不改归属或阶段边界 | 账号暂停与恢复 |

`expected_assignment` 是实际操作的原内部阶段 ID，空表示原本无归属；不是新的账号版本或许可 token。`new_owner` 是已有 Person／唯一 Yuki／无归属的类型参数，不建 owner 表。调用者保具体动作及其真实授权，原请求回执与关系修改同一事务。新请求遇实际阶段已变化时返回当前事实；有权读取的原成功回执命中只读返回，不为查询先占 writer。真正变更仍在原提交事务复核回执及其原 hash；首次需要登记接纳的命令保原子回执，不以只读优化省掉事实。

同人重复 attach／transfer 返回原未结束阶段且不顺手启用；真正换人或人↔Yuki 才换阶段。attach 遇另一 owner 如实给出现归属，调用者须明确选择 transfer 或经认证的同人合并；不隐式抢绑。管理员可维护停用人物，资料调整不自动启用它。普通重连只登记真实连接，不创建新归属或复活暂停／结束阶段。Bot 自动首次登记只接纳尚无归属阶段的账号；有已结束阶段的账号重新作为 Yuki 使用，沿明确重新登记创建新阶段，不从 current=None 猜首次。无归属账号的正常入站沿既有接纳规则建立新归属，不从最后一条历史阶段偷挂回原 Person。

ended 是原归属已经结束的事实，不能 set enabled 复活。A→B→A、解绑后回 A 均创建新阶段；原 A 的发码证明、旧私聊执行和路由不能借“又是 A”重新有效。不同平台不各写一遍创建、转让、互斥和恢复规则。实现不新增 `force`、`allow_disabled`、`skip_owner_check` 等绕行参数。

### 3.2 当前人物资料是真正完整的资料

合法 B 入口可按权限读、修改和管理同人原 A 的资料，按旧 A 内部编号查询也定位同一当前人物。原来源 A 停用不让它作为资料 subject 消失。

| 数据 | 当前查改规则 | 保留的原事实 |
| --- | --- | --- |
| 人物名称、别名、关系、共同 Space | 主名保目标非空值，来源名保别名；完整同人族联合读写，按实际事实／关系去重 | 当时名称、原观察与事件；账号群名片另归实际账号 |
| Memory、证据、private SELF | subject 与 visibility 各自按同人族处理；无账号／原成员停用不使资料消失 | fact/evidence ID、原 owner、来源、已付输入和指纹 |
| Runtime 用户配置 | 独立 scalar key 目标优先，来源独有行实迁；冲突输家归档后从当前表删除，unset 无隐藏回退 | 原行 ID、版本和实际移动审计 |
| Plugin 用户配置 | 按插件完整配置对象选择：目标已有显式配置则保整个目标对象，否则继承来源对象 | 原对象、行 ID／版本归合并审计；输家不留当前表，不逐 key 拼坏对象，不因插件离线／配置未填完阻止合并 |
| Plugin 人物状态／KV | 沿既有 namespace、key、version 和 typed canonical owner 查改，支持完整同人资料；原 owner 停用不使 get/list 失败 | 原行、原 owner、CAS 版本和插件值；不猜 namespace／任意 JSON 的人物字符串 |
| Binding、设备与历史入口 | 同人按原权限管理、发现原入口；入口分别读取 | 原 Binding、设备来源／撤销、Conversation 与请求 namespace |
| Work、自动化、grant、publication/job | 当前同人可管理；实际新执行保 raw actor/source，另核当前人物与实际授权 | 原创建者、预算、版本、工具配对、效果与回执；旧 job 不借今日 grant 换人 |
| 超管资格、主动路由 | 资格仅两个当前 root 未撤销值取 OR；目标已有合法路由优先，来源只继承真实可用候选 | 原来源停用；旧成员 true 不复活被撤销资格；物理发送证明不变 |
| 自省／JEV／扫描进度 | 人物语义认同人；各原执行流分别扫描、恢复 | 原 unit、checkpoint 与覆盖位置，不用 max 游标代替完整处理 |
| 遗忘 | 按完整同人族及原账号阶段清退，包含无 Binding 来源；不误删已转给其他人的新阶段 | 必需的无正文效果事实；不重建正文、不重发 |

配置冲突在各自配置领域一次处理：Runtime 独立 scalar key 保目标值；Plugin 按完整插件配置对象选择，目标已显式配置就保整个对象，否则继承来源对象。不对任意 JSON 递归合并，不在身份内核加载插件或运行 validator，不因插件离线、配置尚未填完阻止人物合并。当前表只留赢家及迁入行，冲突输家的原对象、owner、行 ID／version 写入既有合并审计后删除；审计沿既有敏感字段和整族遗忘规则处理，不另建配置历史表。unset 不扫描旧成员找回值；显式历史恢复复用现有配置写入：修改现存行须原行 ID＋version 一致；当前确实为空时用 expected absence 创建新行，保新的写入审计。旧审计和原行 ID 仍是历史，不凭同 key／同版本接管另一条行。

人物当前查询、资料存在性和实际执行授权各自有清楚参数；不再提供同时判类型、查启用、归一成 root 又供写入 source 的万能 `require_live_person`。实际 actor 原样沿调用链传递；当前 owner 按需派生，不覆写原字段。

### 3.3 启停和权限不另造身份

原 A 的 enabled=True 不表示合并后有第二个人，False 也不表示 A 的资料不存在。合并不为归档把 A 设 False，也不借 B 复活 A 的真实旧撤权。Person disable 管当前 root；现有 enable 按明确原来源及必要 root 恢复，不批量恢复别的成员、设备、Assignment、grant 或 Work。资料与管理页面清楚展示来源和当前人物，源事实不在消费者里另造一套控制状态。

超级管理员只读当前 Person 的资格；转让账号不携带资格，解绑最后账号不删除资格。合并只对两个当前 root 未撤销资格取 OR，旧成员 true 不作 fallback。operator Bearer、个人设备与插件批准保持原入口用途，不做新的通用权限系统。

同人合并、账号转让不取消原人的全部内部计算。原私聊 Assignment 已结束时，平台效果不能切到新主人的入口；原成功／unknown 回执仍是事实，不按今日可用性改判失败或允许重发。

### 3.4 人物资料、配置与扫描的具体改法

本轮继续沿实际仓库查证，以下以现有资料类型为单位实施，不在身份内核增加 JSON 搬运器：

| 资料／现行入口 | 实施要求 | 真实冲突与恢复 |
| --- | --- | --- |
| `person_state.py`、`people_repository.py` | 主名与真正人物别名认 current Person；昵称／群名片观察移归 Account。人物共同 Space 按 family 去重，账号名片按 Account＋SpaceBinding 独立读取 | 同人多账号不选“最新一张名片”代替每个账号；旧无账号证据的别名保原观察，不批量指派 |
| Memory fact／evidence／private SELF | subject 与 visibility 分别按 family 取全；原 fact、evidence、event、owner 和付费输入不批改，实际调用者权限独立判断；key 是标签，同 key 独立事实全保留，仍按 fact ID 修正／撤回 | 合法合并只改变当前所属，不使已准备原证据失效；原证据／隐私确实变化仍按原事实处理 |

| Plugin KV | 现有唯一键实际是 `(plugin, namespace, key)`，不是 Person＋key。保原键、值、行 ID 和 CAS；typed owner 只作人物资料归属，get／list 的当前 subject 投影一致 | 不把 namespace 或任意 JSON 中的 Person 字符串改写，不编造插件业务值的合并算法；真正插件业务键转换由该插件的现行数据合同负责 |

| SELF／Dream／JEV／事件扫描 | 保原 owner 流、原 run、原 cursor；每条事件按自己的 Conversation／generation 处理，同人读取取资料全集 | 删除把一个 owner 的任意一个 Conversation 边界推进整个 owner 游标的捷径；不能因重置一个入口跳过同人的其他入口，也不取各成员 cursor 的 max |
| 隐私遗忘 | 从完整 family 与原 Assignment 查清实际敏感资料及在途效果；先准备外部文件／peer 清理，短写提交领域删除和原回执 | 准备后 family 实际增加成员须重备完整清退，不删这项真实依赖复核；不清已转给别人的当前 Account 资料；ACK 晚到仍结算无正文原效果，不恢复被删人物／正文，不重发 |

Plugin KV 的 typed owner 合并不等于替插件改名所有业务键。Host 保证数据保留、当前归属及授权语义一致；插件自定义 opaque 字段不能被任务书冒称为已完成业务迁移。现行 SDK ctx.storage 写入全部是 plugin-global，没有 Person-owned 的运行时写入消费者，不为假想业务新增人物扫描／迁移 SDK。SDK／示例相应说明按内部 Person 引用资料，禁止把平台号或昵称当人物键；不新增泛化 KV 迁移协议。纯名称目录先按最终输出的 alias 字符串去重再 limit；不能先按 (alias,scope) 截一页再去重字符串。带 scope 的原观察按各自真实键保留；共同 Space 的现有 COUNT DISTINCT 已正确，不物理合并旧关系去撞原 PK。Preference 列表展示原 fact ID，接现有 memory correct／invalidate 命令，不因同 key 多事实阻止人物合并。

### 3.5 合并一次事务真正改变哪些行

1. 沿实际 actor 与原请求 namespace 查原命令回执；有权读取的原成功请求返回原结果。
2. 一致读视图解析两个当前 root、原成员、当前配置对象、人物名称及真实可用路由候选；不扫描聊天正文、插件任意状态或外部历史。
3. 短 writer 复核真正依赖：同人关系、实际调用授权，以及本次要选择／移动的配置行身份和版本。反向并发合并重新解析已提交关系，重复同人只读返回，不形成指针环。
4. 同事务按已准备范围集合更新来源族，使成员直接指向目标，保各原 enabled/source、按实际行推进 revision；配置按原行 ID＋version 集合迁入／删输家，人物元资料、实际路由、原审计与控制回执一起提交。完整审计 JSON 在首条 DML 前准备，不逐成员重新查 root 或 flush。原 Assignment.person_id、事件作者、设备 source、Work source、grant 原接纳来源和 paid 请求均不改。
5. 各资料查询立刻按既有 root／family SQL 认同一个人，不设置“搬迁中”、后台进度或另一个合并完成条件。无关改名／观察 revision 不等于原证据失效；真实行被换掉的 CAS 也不因同人关系而放行。

查询按真实问题分三类，复用同一仓库的类型化查询，不加控制开关：

- **认当前身份／显示**：取未 ended 阶段及其 kind，允许 disabled；暂停的 Yuki 账号仍归 Yuki，不因不可用就被看成真人或第三方 Bot。
- **做新接入／发送**：在上述身份事实之外，按实际 actor、active 使用状态、接入政策与真实连接执行。源撤权、路由和原 proof 各认真实用途。
- **读历史／回执**：按保存的原 Assignment ID／kind 读取，即使 ended；不从今天原生号匹配另一条记录。

这三类贯穿 `event_author.py`、ingress 的 yuki_account_ids、真实 AT Yuki 识别、Registry、route、目录、App/ACP 和原付费资料的只读投影。现行“只把 enabled Presence 认作当前身份”的查询不能机械改字段名后继续使用。

迁移在原 schema 基线上保原 ID 搬入 Assignment，重建受影响 FK／类型约束及现有触发器，完成数据对应和 `foreign_key_check` 后去掉双表事实源。正式升级是 schema 一次切换；不保双写表、永久兼容视图或后台同步。旧格式只由冻结迁移转换为共同只读资料，原始字节保作证据；新运行时不留逐版本消息／调用解释器。

### 4.5 迟到原消息、原生时间与无证明作者

本轮真实隔离链已复现 P10：A 时段发出的另一条消息，在真实 transfer 到 B 后才首次入账，即使带转让前时间仍写作者 B。已入账消息重投保原事件／A 是正确行为，应继续保留。QQ normalizer 未保原 event.time；TG 虽把 date 放进 received_at，作者解析仍只查当前角色。

按下面边界细化，既不把今日 B 当旧作者，也不为过去的消息建立新授权：

1. **先读原接入回执／内部事件。** 已入账的重投、编辑、原 reply、旧请求都沿原 ID 和原作者；不为升级再按时间或今日账号重判。收件去重不能只拿今日 Presence 阶段 ID；原接收 Account 与适配器完整原生接入 namespace 定位已保存 receipt，再沿其中的原 Presence／canonical event 读取。该定位仅作传输去重，不用平台消息号重建业务 owner。原receipt ID／hash保留，新唯一性依据真实稳定接入namespace，不是Assignment今天的阶段。
2. **发生与观察分开。** QQ event.time／TG date 投影为可空的原生发生时间，Host 接收为观察时间。既有事件 occurred_at／observed_at 各保其用途；来源时间缺失在现有事件来源 JSON（`segments_json` 内 `yuki_context` 等实际载体）明示为空。没有原生时间时，事件排序用观察时刻，但它不能成为“已证明原发生时间”的依据。不按相差几秒／几小时的经验阈值猜迟到。
3. **首次事实有可证时段。** 原生发生时间落入唯一有证据的 Assignment `[start,end)` 时，作者与私聊入口认该原阶段；群仍认实际 SpaceBinding／topic。同步改 `ingress._author_for`、`_ensure_person_id` 和 `canonical_uow`：识别到原阶段后不能又被“找不到当前人物则 ensure”改成今日 B。
4. **确有历史但无法证明 owner。** 原生时间明确早于当前阶段、旧边界又无法证明时，保存稳定 Account 事实，不猜 Person、Presence 或 system。新增窄 `AuthorKind.ACCOUNT`／`author_account_id`，表达“账号已知、原人物／Yuki 阶段未知”；这是现有 Account 的事实引用，不是新主体表或授权。
5. **未知私聊不冒建入口。** 群里该 account 事实仍可归原群 Conversation；无法证明原私聊阶段时，在现有 chat_events＋原接入回执一次保存，允许该类 account 事实无 canonical Conversation。只放宽这一真实资料形状，普通／已证事件仍保原 Conversation 合同；不建临时 Conversation、隔离表、补认 worker 或等待队列。原事实与接入 receipt 同事务提交成功后才确认 Telegram update；成功后重投直接返回原 receipt，无 Conversation 也不二次入账或反复 ensure，不把它灌入 B 的私聊或生成其个人授权／记忆。
6. **时间完全缺失的协议。** 无从保证任意旧消息的原作者；普通实时接纳继续沿当前 Assignment，不能把所有无时间消息都去人物化。QQ/TG 本轮先完整保留实际原生时间；不把此有限保证写成万能历史还原。

实际修改覆盖 `domain/identity.py` AuthorKind、EventAuthorProjection／IngressPreAdmit、ChatEvent 作者形状约束及 Conversation 可空范围、append／原生回执事务、EventRecord／serializer／receipt_compat、reply 作者判定和提示渲染。新增 account 类型不被当 Yuki，也不沿今日 Account owner 形成 Person；Memory／SELF／控制权限继续在真正有 Person／Yuki 证据的地方使用原类型。缺 Conversation 的原事实不是任意会话上下文，原 scope 检查不全局放宽。

这项是 P10 修复及 Assignment 历史语义的实际落点，须实现后验证 schema 和平台确认链，不能只加一个 enum 就称支持。历史时点决定作者事实，实际当前授权决定新效果；账号转让不取消原人的全部内部工作，旧私聊路由也不借新阶段恢复。

### 4.6 面向后续平台，复用现有 Provider 边界

第三、第四个平台按现有 `GatewayProvider`／Catalog 接入，不新建 MentionProvider、名称服务、平台策略注册表或能力协商框架。稳定原生账号键在公共层是平台命名空间内的不透明字符串，不假定都是数字，也不把 username 当稳定主键。`stable_native_account_id` 由适配器按协议真实身份作用域规范化；原生号仅在租户／服务器内唯一时包含该稳定命名空间，不混入可变 Profile、连接或网关实例 ID。原生发送由适配器在实际入口转换完整键，不丢掉作用域后只比末端原生号；不另加通用 tenant 表。

| 边界 | 唯一职责 | 公共层不承担的事 |
| --- | --- | --- |
| Provider 入站投影 | 原生账号键、真实发生时间、账号／群资料及原生实体投影成共同事实；未知原生地址保其类型 | QQ segment、TG UTF-16、未来平台的实体编码和服务端自动识别规则 |

| media／activity 等已有能力 | 实现平台实际支持的下载、媒体与活动提示 | 为不支持的能力造空效果或阻塞主模型等待补齐 |

名称的共同语义是账号显示名与具体群内显示名；平台原生 username、地址类型和特有资料留适配器的来源资料，不为每个未来平台预置列。`@all` 的拼法、支持范围与原生行为也由适配器表达，不在公共层按 QQ/TG 名称分支。群成员补查只保现有群恢复等真实消费者，不成为新平台提及能力的必备前置接口。

删除 `PlatformSocialOperations.file_caption_separate` 及 Social 依赖它拒绝文件＋回复的 `file_quote_unavailable` 分支；布局已有 `plan_send`，无需第二份平台布尔政策。文件＋附言时，原引用放在实际可引用的 caption／文字 part；只有文件且协议不能引用时保真实发送能力事实，不造空文字。删除 Social 回执恢复中按 `platform == "qq"` 转旧 `_file_result` 的分支，统一按原 prepared parts 和回执投影结果。

同一能力的新平台只增加适配器及现有注册，不改身份内核或模型工具 schema。确有新能力时再扩展对应现有传输合同，不提前搭建未来能力矩阵。验收增加一个非 QQ/TG 的测试 Provider：非数字账号键、不同原生跨度编码、独立文件布局、不支持全员提及且不需远端成员查询；它证明公共层不依赖两端枚举，不是本次新增真实平台功能。

## 6. 提及与原事件引用的目标合同

### 6.0 统一展示与还原：看到什么，就能怎样提及

按用户最新要求重写整条提及链：原生事实→共同可读展示→模型沿同样写法发送→Host 解析→各平台原生编码→账本与回执反馈。模型看到一个已明确指向 Ice 的 `@Ice`，发送时照写可沿该账号有来源的名称观察还原；名字后来被另一账号使用或原人物阶段结束时，返回真实歧义／归属变化，不静默换人。只依赖当前昵称无法保证任意时刻的旧名字唯一还原，任务书不作这种承诺。

名字不唯一时，展示／目录直接附可复制的内部 Account 引用；人物、Yuki、第三方 Bot 和无归属账号使用同一种引用。普通情况不填结构数组、事件索引或第二份提及参数。Main、JEV、历史和发送反馈共用这些原生关系，不让各自再猜一次。

“防假艾特”指已知明确目标能生成真正原生提及，并且记录中分清真实提及与普通文字；一个未知名字前加 `@` 不产生身份。已知目标确有冲突时保正常正文和称呼、返回具体候选，不让该片段退回 TG username 另选一个人；该片段只输出称呼，不输出会触发原生地址识别的 `@`。消息照常派发，回执不冒称已成功提醒。入站普通文字不反造原生事实；完全未知的 TG 原生地址仍单独按平台事实处理。

### 6.1 删除重复的已见门槛，不改变原授权人

删除 Social 回复引用的 `event_id in context.visible_event_ids` 门槛，以及只为此传递的 SocialContext 字段。原事件已经有实际 Conversation、消息类型、原平台 namespace、目标路由和现有授权核验；不再为发送另建“模型看过这条消息”的白名单、同步状态或刷新机制。参数类型由工具合同处理，原事件存在和真实发送权限仍按事实核验。

授权历史查询返回的事件、Code Mode 同一程序里先查询再引用的事件，以及真实发送回执返回的新事件，都能沿原来源直接引用，不要求再购买一次模型请求。不得因已见门槛删除就允许任意跨 Conversation 事件；跨入口操作仍沿实际原入口与既有明确读授权，不拿事件编号替代授权。

TurnState 的 observed 集合用于观察去重，并不等于模型实际采用，更不是权限。ToolRuntime 的事件资料仍有上下文、媒体和证据等真实消费者，不能全局一删了之。原有 dispatch／checkpoint 事实照实保留，专用的重复发送白名单退出。普通轮、Work、Code Mode、恢复和旧已付请求均不依赖它才能引用原事件。

`current_speaker` 始终绑定原 ToolActor，本身并未跟 steer 换人。删除新调用中这种含糊快捷选择，改用明确内部来源；人物管理权限和本轮新增聊天资料是两件事。

### 6.2 模型写自然文本，Host 只解析本次真实提及

日常调用保留现有 `send_message.text`，不改成模型必须填写的 parts 数组：

```json
{"text":"@查查 收到了，@Ice 你也看看"}
```

Host 对实际目标 SpaceBinding 中的本地当前账号资料及有来源的名称观察做一次批量读取，将可唯一确定的名字转成带位置的真实提及。名字是本次查找文字，解析后仍用内部 Binding／Account 和原生来源发送、入账。群名片、账号昵称与明确的本群别名有来源；不做全局人物名字反查、模糊猜人、最近发言人猜人或逐 AT 远端查询。

没有可解析提及的普通文字不为提及新增账号／姓名读取。只有精确 Account 引用时，对去重后的内部 ID 集合批读账号及原阶段，不加载整群姓名目录；重复出现仍保每个 span。只有自然名字待匹配时才批读实际目标群资料，不新增常驻名称缓存或后台刷新；耗时在实现后测量，不把“无远端请求”冒称速度验收。

遇到同名或同人双账号，保留每个真实账号候选；不按 Person root 压成一个。已知名字无法唯一绑定时沿 §6.0 只发称呼及正常正文，回执说明 Host 未选择具体账号及内部候选，不冒称已成功提醒某人，也不把冲突当成未知退回平台地址。无须强制再跑一轮模型；确实需要提醒时，模型可只补发明确提及，不重复原正文。

精确选择只保一种文字形式，复制目录给出的完整内部 Account 引用：

```json
{"text":"@{account:目录返回的UUID} 你看看"}
```

人物账号、Yuki、第三方 Bot 与无归属账号都用它。它明确指这个物理账号；账号转让后不能冒称仍指旧 Person。需要找某个人时先查当前人物的实际账号，不自动把此引用换成该人的其他账号。

原 Assignment 由 Host 从真实名称观察、准备和 claim 保存，不交模型另填。删除 binding／presence 两种提及文字语法和相应解析器，不为旧写法保别名；不给模型加 event_id／mention_index 或第二份 mentions 参数。无效明确引用如实返回未解析事实，不猜另一对象。

匹配已知完整名字，支持名字中真实存在的空格和标点；不用 `@\S+` 截词或通用 `\b` 排除中文相邻句。多个完整名字前缀冲突也不猜目标、不吞正常正文。未知名字保持文字，不为报告未知名再造分词器；回执报告实际已解析目标和有具体候选的歧义即可。email／URL 中的地址不当作群昵称，不引入完整 Markdown 语义分析器；`\@` 仅退出 Host 姓名解析。

**入站与出站严格区分职责。** 入站 QQ 仍只从真实 `at` segment、TG 从原生 entity 读取事实，原句里的普通 `@文字` 不被 Host 补造成历史原生提及。姓名解析仅作用于新出站工具文本，不扫描或重渲染旧事件、frozen 历史与已付请求。实施时同步改写现行文档的“普通 @ 不反造提及”适用范围，删掉被替代的规则。

平台各自负责原生语义与编码：QQ 输出原位置的 `at` segment；TG 用原生用户名或按真实用户身份生成 mention／链接，entity 定位沿 UTF-16。姓名查找共用一次本地准备，不给每个平台复制人物规则。Host 已明确展示的名字与真实目标对应关系优先还原，不能仅因字符串像 TG username 就跳过已知目标、改发同形全局地址。若本地资料中确有同形原生地址与另一昵称指向不同目标，展示明确候选／内部引用，不静默选人。没有已知映射的 TG 原生 `@username` 保其地址语义，不等远端查证是否存在，不据此虚构 Person。这些原生语义由适配器识别，不在公共业务里按平台名堆分支。

TG 还会在服务端自动识别原生 `@username`，见[官方实体说明](https://core.telegram.org/api/entities#autogenerated-entities)。所以“Host 未选定内部账号／保留原文”不等于“平台绝未产生提及”，`\@` 也不承诺禁止平台识别。只有 username 而没有稳定数字身份时保地址事实，不伪造 Account／Person，不增加 username 查证链、隐藏字符或实体抓取 worker。消息送达不独立证明对方实际收到提醒。

普通文本、提及位置和身份在 Host 准备后同源，供协议布局、账本与回执使用；不要再把所有 AT 放在正文前或只放第一条。先解析再分条，提及不可从中间切断；不在每段重新查名字。纯 AT 的可读出站内容必须含真实展示，不再作为空消息从 Main/JEV 消失。

新入站及出站沿现有 JSON 保存已知 Account／Binding／Presence、原位置、名称与 native provenance；原计划和回执恢复读原件，不按今日 root、昵称或路由重算。未知真人、外部 Bot 和 Yuki 的原生账号保真实来源，不为提及造 Person。`@all` 沿平台原生能力，不伪装普通人或遍历全群逐人发送。

发送前在现有 claim 短事务复核已准备 Binding 的真实归属／平台，不因改名或合法同人合并就判失效，也不新增缓存、身份审核、第二个模型或新的状态表。提及目标不是执行授权来源，不借用私聊联系人准入要求它先发言；执行者和真实发送路由仍沿原授权核验。

### 6.3 共同消费与发送

- Main、JEV、历史查询和工具回执消费同一份提及显示与关系资料；保原句位置、每个实际账号、重复次数、未知对象、作者与提及对象的区别，以及 reply 中的独立关系。显示不依赖被提及者启用状态；JEV 不新增按 AT 才准入的门禁，参与单元的 target 也不改作收件人。若接口受影响，同时更新独立参与库、Host schema 与实际 pinned 版本，不把 Host 数据库依赖塞进参与库。
- QQ `at` 与 TG entity／UTF-16 偏移只在适配器内转换。文字、mention、caption、引用和换行分条保持顺序，纯 mention 允许发送。
- 前台文字／提及先发且只发一次，表情后台只追加选中的图片。现行有正文时后台本就不重发 AT，不以未证实的重复发送为重构理由。无正文的 mention＋emoji 目前会等后台选图，按真实前台内容修判断即可。有前台内容时保现有首次 claim 与意图的原子接纳、实际父 Social 操作和原目标；纯 emoji 允许空 text，沿原 intent／调用身份直接接纳，不造空文字父回执，也不等待 Work。重启、partial 或 unknown 沿原回执，不重发已确认文字和 AT。
- 有前台的配图只等待原派发序列结束事实，不要求所有 parts 成功；后段预检退出、取消或硬停恢复留下的未派发 prepared 由原父回执收束，不堵死配图或重发正文。
- Plugin SDK 普通发送、App/ACP Sender 和自主／自动化／Work／子 Agent 复用 Social 内容合同；通知原 outbox 路径也接同一内容准备与协议布局，保自己的真实 claim／回执，不叠第二份效果。独立批准的原生 QQ SDK 仍保原生参数语义。具体边界见 §6.7。
- 原发送计划逐项有真实回执，文件／附言各自确认。原成功、部分成功、unknown 与未派发事实分别处理，不重发已确认文字或附件。
- 升级时按 §8 一次处理旧激活、旧发送与旧 intent；新运行时只校验新 schema。旧 paid call 不在当前工具执行器复活，原 call/payload/hash 和效果回执以统一只读形状查证，旧普通 @ 不增加新效果。

### 6.4 共同快照与真实姓名观察

`domain/messages.py:MessageMention` 已有原句跨度，现缺 Account／原阶段引用；`snapshot_mention_segments` 已有 native source，沿现有 JSON 扩充以下事实：实际 kind、Account、原 Assignment／Person／Presence（已知才有）、当时 display_name、`[text_start,text_end)` 和原生 source／地址类型。普通文字没有原生 span，不能从它补造入站事实。

TG `text_mention` 有稳定数字目标；普通原生 `@username` 常只有地址。`telegram_ingress.py:41–89,220–247` 当前又丢掉 sender.username；应在真实 user／getMe 观察时保存 Account 的可变 native username，与昵称、稳定数字 ID 分开。未知地址保原实体种类和原文本，不发远端补查，不按显示名猜数字身份。

账号当前资料与名称观察共同归 Account：新真实昵称／名片观察保实际 Account、SpaceBinding 和当时 Assignment，旧名可继续作为有证据的别名。它是实际资料，不是“模型已见”许可、运行时名称缓存或后台刷新的状态。旧 PersonAlias 只有能证明账号来源的行才归入账号观察；剩余资料保原人物观察，不能广播到同人的全部账号，也不为迁移扫全库正文猜来源。

名字候选按真实账号／阶段保留：改名后旧名仍能定位原账号；同名被另一账号使用则返回候选；原人物阶段 ended 的旧名不能直接跳到新主人。disabled 仅暂停使用，不抹名字或禁止被群内提及。`account:UUID` 明确指物理账号，不冒称它永远属于某个 Person；因此不会沿旧人物别名假记新主人的身份。

已有 `canonical_uow.py:415–440` 的重投 reader 会还原 native source，`ingress.py:420–430` 从原内部 reply 读取原快照，`event_repository.py:733–744` 认可现代明确空提及集。这些 reader 保原语义：一次迁移把实际旧原生 AT 投影为共同快照；原 source／冻结字节不改，不按今日名字重解，不扫描普通旧 @ 猜目标。上线后只读共同形状，删在线 legacy 投影器。

### 6.5 可实现的姓名查找与语法边界

1. 先定实际发送目标和 ResolvedSend；群名来自**最终目标 SpaceBinding**。当前入口目录沿原 Conversation.space_binding_id；跨入口沿明确内部 Conversation／SpaceBinding，若只有一个 Space 但有多个实际入口就返回入口候选，不混多平台名字。目录读资料不要求网关在线或发送路由 active。
2. 先分出精确 Account 引用和自然姓名。普通无可解析 @ 不因提及解析增加账号／姓名查询；仅精确引用按去重 ID 批读，不加载群名录。有自然名字时以少量集合查询取得实际目标群账号、可证别名及内部引用，不强求一条会让多账号×多别名相乘的大 JOIN；同一准备只读一份，不逐 AT 扫全群或补查平台。目录按账号保项，不按 Person group_by，不过滤人物启用，不要求对象先作为作者发言；原生被提及的已知账号也有资料。继续 `coverage=observed`，不冒充完整远端名册。
3. 复用同一显示规范化，按完整已知名字建立本次调用局部的前缀查找结构，终点直接保存去重后的 Account／原阶段候选；扫描 @ 后的实际前缀，不用自拼巨大正则或对每个 @ 遍历全部名字。设名字总长度 S、文本长度 T，建表 O(S)，查找成本按实际前缀比较字符计，不冒称无条件 O(T)。无需引入分词、Aho-Corasick、通用解析框架或常驻索引；局部前缀查找已经处理本任务的姓名边界和歧义。对象按 Account／原阶段去重，重复出现的 span 不去重。
4. 命中一个实际目标时记录匹配区间；同一目标多个别名前缀取最长完整匹配并保原文字。若匹配不同目标的完整名前缀，不用最长者猜人：该 @ 退出真实提及，保剩余原句文字并返回候选。此处只处理已知候选，不另造未知姓名分词器。
5. 唯一 `@{account:UUID}` 先按完整引用解析，内部 ID 不来自模型自填的原生号。email、URL 的地址文本不作群名解析；`\@` 去掉一个 Host 转义斜线后保普通 @，不承诺抑制平台自己的原生 username 识别。只解析新发送正文参数，不解析 Code Mode 程序源码、文件名或文件内容。
6. 私聊只使用其实际入口参与者资料，不转去全局人物库找同名人；正文提及不改变私聊收件人或扩大 DM 授权。平台原生地址／实体及不支持的实际形式由适配器表达，不给姓名解析复制联系人门禁。

`find_contacts` 是人物／群候选查询，`get_group_members` 是具体群的逐账号观察目录；名称查询返回候选，发送目标用内部 ID 或默认当前入口。`social/tools.py` 目前共用 selector，删除新 send 的快捷目标时同时清掉 target 侧 display_name／subject_ref，不能只删 mentions 数组而保隐式全局选人。目录只给候选，历史查询只读迁移后的共同事实形状。`get_group_members` 从 Account＋SpaceBinding 的真实观察资料取唯一账号，按内部 Account ID 游标先在 SQL 分页，再批量附名；不扫描聊天历史、不按 Person 压缩、不取全量到 Python 再切页。发送姓名解析读取本次作用域完整候选，不能把目录第一页冒充完整姓名集；多别名不重复账号或挤掉下一页。

### 6.6 内部跨度、分条与平台编码

当前 `gateway/social.py:17–19` 的 TransportMention 没有位置；Social `service.py:634` 将全部 AT 放首条，QQ `onebot/social.py:88` 与 TG `telegram_social.py:69–73` 又统一前置。新合同必须同时替换这三处，不能只改 schema。

- Host 解析后的文本和内部 mention span 是同一份内容。模型仍只写 text；内部跨度使用 Python code-point 半开区间，保持原位、重复目标及原名字。
- 扩展现有 TransportMessage／TransportMention 或其同域值结构即可，不叠加第二套解析框架。现有 Splitter 返回带源区间的切片／跨度投影，保现有分条节奏和结构规则；不能将处理后的字符串再用 find 猜回原位置。strip、换行分组、代码块重包等已有转换须同步转换跨度。
- 每个实际 part 只带落在该 part 的 mention，偏移平移为本段坐标；切点不落提及内部。有序跨度与有序 part 用前移游标分配，不能让每个 part 重扫全部 mention。原生限长与 caption 布局同样消费这些原子区间，不对每段重新查名字、不把所有 AT 重挂首条。
- QQ 以 text／at／text 的真实顺序输出 segment；TG 沿实际区间转义文字并原位插入 link／entity，UTF-16 换算只在适配器做。QQ 入站一次拼装／规范化并同步投影边界，不逐 AT join＋sanitize 累计正文，也不以列表查重兼作关系存储；TG 将实际需要的 entity 边界排序后一次扫描换算，普通无 mention 不建无用映射。入出站均不逐提及重扫全文前缀；控制字符、CRLF、首尾清理、非 BMP 字符与重复 span 必须对齐。
- TG `plan_send:26–55` 会再次截 text／caption，QQ 文件拆上传＋附言，TG sticker 拆正文＋贴纸；这些纯布局也要保护跨度。账本按实际 part 保存 Account／原 Assignment、当时名称、位置和 native provenance，不能按“该段有 AT”复制整份旧 ledger。
- 原 reply 定位留在真实包含引用的 part，不随正文提及选人。纯 AT 的 content 保可读 @显示名，Main／JEV／历史都能看见；纯 emoji 仍无空文字父发送，正文／AT 与后台配图按原效果回执各自收束。

### 6.8 prepare、claim、ACK 的身份责任

准备阶段冻结实际文本、跨度、Account／原 Assignment 和目标路由，这里复核提及指向和实际收发入口，不借账号转让取消原人的全部内部任务。短 claim 只核实际依赖，不在 writer 中查目录、重新分词、读历史或请求网络。人物合并／改名不使同一原阶段失效；真实 transfer、角色变更或阶段结束不能仍以旧人物身份派发。

明确 `account:UUID` 的请求只断言物理账号，账本不虚构某个旧 Person；自然姓名解析的原阶段仅由 Host 保持真实来源，不另提供模型可选的阶段语法。claim 之后平台已实际收下的消息，即使换绑或隐私删除后才收到 ACK，也按原已执行效果结算：保实际原快照，不能用今日新 owner 改账，也不能因为旧阶段现在 ended 就重发。

## 8. 不可逆迁移、旧执行收束与性能

### 8.1 原效果按事实结算，Work 沿原身份继续

停止旧进程接纳新请求、工具派发与调度，正常关闭时接收已经返回的 ACK。按原执行域、原请求／part／外部 run 读取事实，不能以“升级了”批量标成功、失败或取消。

| 原执行事实 | 一次切换的处理 | 新运行时行为 |
| --- | --- | --- |
| 已确认成功／partial | 保原效果及每个物理 part 的结果；未确认项分别处理 | 查询原结果，不重发成功项，不重新解析原调用 |
| 已派发或可能已派发，结果尚不明 | 有原 ACK 则结算；否则保现有 unknown 和真实外部 run ID | 不自动重跑、不杀独立外部运行；未知不阻止无关任务继续 |
| 旧工具调用已付费，但能证明未派发 | 沿已有回执记 `never_dispatched`／`executed=false` 等该领域实际未执行事实，保存原 call／payload／hash | 不交新参数解析器，不自动执行旧调用或重新购买同一请求 |
| 已接纳、尚未实际发送的通知／emoji 业务意图 | 冻结迁移据原来源转成共同 prepared 内容，保原请求／part ID 和回执；旧普通 @ 无 span，实际原生提及仅据原证明。若原内容／目标无法证明，就沿原域收束为未执行，不猜今日 owner | 沿原意图与新共同准备形状继续，不恢复旧参数执行器，不生成第二次接纳 |
| 使用本次退役工具合同的私有续跑链／旧 Code Mode pending | 保原 paid response、call/hash、协议对象与效果记录；旧链结束派发，未完成调用按上述事实处理 | 不恢复旧 wrapper、旧工具 manifest 或任意版本执行分流 |
| 原 Work／父子任务仍未完成 | 保原 work_id、source、累计预算、目标、成果、父子关系与外部 run；沿现有业务恢复边界建立新 chain，用当前 manifest 接续业务 | 不新建替代 Work、不归零预算、不取消整树、不重复启动子任务或外部 run |

父序列 prepared、WorkEffect prepared、emoji intent closed 都不单独证明未派发；须看原子项、调用接纳与实际派发事实。不能用父状态覆盖真实子项 ACK／unknown，也不要求所有 Work 结束或所有 unknown 查明才能升级。

`WorkSession.rebase_business` 已有以业务目标／成果／回执重建合法新链的路径，但当前排除了真实 `work_id`；本任务调整这个现有边界，让真实 Work 也能按原身份接续。新链只承接可读目标、资料、结果与原回执，不把旧 call 伪装成新 schema 成功执行。保原 journal 和协议对象引用，不直接清 checkpoint 丢证据，不建 carryover 表、迁移 worker 或新的取消状态。实际当前授权仍在现有激活／执行边界核验。未受本次工具合同变化影响的已付资料结果沿原提交边界处理，不把人物合并或升级本身当成重买理由。

### 8.2 一次切换的迁移顺序

1. **停旧执行，清楚记录在途事实。** 停旧 admission／dispatch／scheduler，按 §8.1 结算原回执和封存旧私有链。保留独立外部 run，不以整个任务成功或所有 unknown 消失为迁移条件。
2. **更换身份事实源。** Account 按有证据的 `(platform, stable_native_account_id)` 规范化；无稳定 ID 不造账号，同数字跨平台不合并。原 UUID 搬入 Assignment，原 FK 改指同一 ID 的新行，准备新唯一索引、角色类型约束、触发器及 fresh-schema／schema_guard；旧表在原资料抽取和新结构核对完成后删除。原 Person、Conversation、设备、事件、执行、请求 ID 不重编号。
3. **只迁真实身份与资料。** active／disabled／ended 据原控制事实转换；未知结束时间保未知。真实当前归属冲突须按原回执查明后才能安装该唯一约束，给出具体账号及冲突记录，不做全库身份健康门禁。群名片只按可证 Account＋SpaceBinding 回填；Person 别名无账号证据仍是人物资料，不广播给账号。配置赢家进当前表、输家进既有合并审计后删除，unset 无隐式复活。
4. **归一旧只读资料与已接纳意图。** 冻结迁移在原 schema 下将旧消息快照、结果、通知原发布与待执行业务意图投影成统一资料。原 paid/wire、来源、payload/hash 原件保留，不改原签名输入，不按今日名字猜旧提及。通知原全文／媒体身份／manifest 固化到原 source event 的 Host 来源资料，物理 part 及原 ACK 分开保存。先在原 schema 抽取本次所需事实，再写共同形状、安装约束并核对原引用，最后删除旧双表；不在删旧表后回头猜原资料。旧原件不再需要在线版本解释器。
5. **只启动新合同。** 当前工具、Code Mode、SDK、CLI／HTTP／聊天命令与新 schema 同步切换。原回执查询沿原 namespace／ID 与实际读授权；重复操作仍核原 payload/hash，同 ID 另传内容仍报真实冲突。查询旧结果不要求重新提交旧命令；旧格式输入返回当前合同的明确错误，不因 ID 已存在就免校验、转发旧端点或自动补参数。Work 按 §8.1 原身份建立新链；原已接受业务意图沿共同 prepared 内容恢复。
6. **删除旧运行代码并验证新边界。** 冻结迁移脚本自带旧 schema 定义，不导入可变 ORM；旧解析代码不挂回产品执行路径。新建库与真实 0140 升级安装相同新约束，核 `foreign_key_check`、原 ID 对应、回执及 §9 矩阵。不提供降级脚本、旧库恢复模式或运行时兼容开关；后续修正沿新 schema 前进。

### 8.3 本次必须删除的运行链

- `identity_bindings`／`presences` 两份持久事实源、跨表互斥／恢复、兼容 view、双写和旧 owner 镜像；Binding／Presence 只留内部有类型投影。
- binding／presence 两种精确提及语法、旧 mentions 数组、含糊 subject／display_name 发送目标、SDK 去重提及字段与旧字段投影。Account 引用是唯一精确语法，名称是本次本地查找文字。
- 依据 manifest revision 选择旧执行器、旧工具参数在线转换、旧 Code Mode wrapper、旧 emoji intent 翻译，以及 Social 多版本 sequence hash 试探；证据字段不再控制执行版本。
- 通知从旧 text／媒体行反拼原发布的 `_load_stored_manifest` 及 `legacy_media_part_key` 等运行时旧布局推断；新通知只读已经保存的原 manifest 和共同 prepared parts。
- `file_caption_separate`、公共文件＋引用拒绝和 QQ 旧 `_file_result` 回放分支；共同发送结果从原物理 parts／回执产生。
- 已被新合同取代的 SDK 输入别名、命令转发器、旧消息／调用版本解释器及其只验证兼容行为的测试；保冻结迁移测试与真实新行为回归。

清理按实际消费者完成，不能只把旧函数改名或挪到新 facade。原件只读查询、冻结迁移和产品执行在用途上分清；不为保留原事实留下“先试新路径，失败再试旧路径”的接口。真实旧撤权、必要隐私清退和原效果回执继续有效。

### 8.4 查询形状与最少索引

优化先删除重复解析、逐行查询、历史扫描和重复写入。复用当前仓库与 SQLAlchemy 表达式，不建人物查询引擎、root 缓存或新的批处理服务。具体落实：

| 查询／写入用途 | 目标形状与索引依据 |
| --- | --- |
| 固定 Person 的资料／Memory subject／private SELF visibility | 以 `owner IN family(输入人物)` 让 owner 索引先缩候选；family 用现有 Person PK＋`merged_into_person_id` 索引。不能对每个资料行调用 root 标量子查询再比较；真正双列同人比较仍按实际用途保留，不全局机械替换 |
| 账号与当前阶段 | Account 原生唯一键定位；以与部分唯一索引一致的 `status <> 'ended'` 谓词取得当前 Assignment，再按用途核 active。不能指望只写 active 就自动利用另一谓词的部分索引。原 ID 查询／claim 用主键，不额外查今日默认阶段 |
| 人物的账号／账号历史阶段 | 分别按原 Person 与 Account＋真实阶段时间的实际条件建查询路径，历史作者读取只查该账号的阶段，不扫描整库事件。旧时间无法证明仍按 §4.5 保存原事实 |
| 群账号／名称观察 | 群目录需 SpaceBinding 在前的读取路径，账号＋群资料有真实唯一约束；全局账号名按 Account、群内名按实际 scope 批读。同一名字观察按实际 Account／阶段／scope／名字更新，不每条消息无变化追加候选 |
| 分页与别名 | 目录接口的一页先选唯一 Account，再批读姓名和必要当前 Person 投影；自然姓名发送仍取目标入口完整的可匹配候选，不能只读目录首页；纯人物 alias 按最终输出字符串去重后分页。cursor 用实际稳定内部键，排序附确定性 ID，不能全量拉取再切片或把多个别名 JOIN 成重复账号 |

只保真实唯一性和实际查询需要的索引。Account 原生唯一键、Assignment 当前部分唯一索引、Person 主键／root 索引是明确用途；其余按最终 SQL 的筛选、连接和排序验证，不能给每个字段／enabled／status 机械建索引。旧表索引不整套搬迁；对被复合索引左前缀覆盖且无独立用途的索引，核相关查询计划后删除，减少写放大。绑定参数的实际 SQL、新建库及迁移库都用 `EXPLAIN QUERY PLAN` 验证；不把 SQL 写法看起来像集合查询当成已经命中索引。

### 8.5 writer 只覆盖必须原子的提交

- **能只读就只读。** 有权读取且原 hash 一致的成功回执、无需新接纳的同人无变化结果，不先 `BEGIN IMMEDIATE`。有真实新修改／接纳时，领域修改、授权依赖和原回执仍在同一短事务复核、提交，不拆成多次 commit。
- **纯数据库合并保一致快照。** 沿现有 `apply_snapshot_write` 在同一 WAL 读视图准备人物族、配置、名称与真实路由，准备完整后才进入 DML；只在原纯 DB 单元整体回滚确认后换 session 重备同一 ID。不把网络、模型、文件或提交确认未知放进这个重备边界，不另建重试框架。
- **准备不提前弄脏 ORM。** 默认 autoflush、普通 SELECT 和 `begin_nested` 都可能提前触发 DML；先准备局部值和实际依赖，再修改挂载对象。确需时仅在本地准备段使用 `no_autoflush`；它不阻止 `begin_nested` 建 SAVEPOINT 前的强制 flush，不能靠包住嵌套事务保证准备期不写。不全局修改 Session 语义。配置／审计 JSON、名称解析、hash、历史扫描和文件工作均在首条 DML／`BEGIN IMMEDIATE` 前完成。
- **账号替换是一笔关系变更。** 按 expected 原 Assignment ID／真实状态条件结束旧阶段，插入新阶段，再写原命令回执；唯一索引裁决当前归属，中间不 commit，不加 Account 锁表、owner 镜像或版本 token。
- **发送不跨网络持读事务。** 结束准备读 session 后才等待平台／文件／模型；claim 的新短 writer 只核实际 actor、阶段、当前资格、路由、连接及原效果状态，网络在提交后执行。ACK 结算沿原 part。不能把纯 DB 一致快照误用成跨网络持有读连接，也不能把批量准备误用成取消每个真实物理效果的必要核验。
- **入站和批量写不反复准备。** 当前 `canonical_uow` 的原事件／receipt／水位原子性保持；媒体索引的 owned_upload／原资料和 primary alias 提前批读，writer 只绑定实际 event ID、应用已备观察和写账本。合并配置、通知子项和遗忘按领域集合操作，保 FK／触发器的真实顺序；SQL 参数量确需分批时只分执行批次，不拆原子提交，不新增业务条数上限。

原数据量导致的必要原子工作按真实受影响行计，不承诺零锁或把整族原子变更伪装成分页提交。延长 busy timeout、增加全局 mutex／写队列或一律先取 writer 不能代替缩短持锁工作。

### 8.6 复杂度、等待与缓存的验证

实现时对照本基线，分别增加同人族 F、目标群账号 A、名称总长 S、文本 T、提及 M、物理 part P 和无关历史 H：固定入口查询不随 H 线性扫历史；目录只处理实际候选与页；身份列表不每行查 root；解析不逐 AT 遍历全部 S；跨度转换不做 M 次全文扫描；子项计划不做 P² 查找。合并触及 F 和实际配置行是必要工作，不把真实数据规模当失败条件。

- 先核实际绑定 SQL 的计划、结果等价、页完整性及批量查询形状，再做多规模隔离计时，记录查询次数增长、处理行数、准备时间、SQL／提交时间及可观测等待。不要用固定 SQL 条数、EXPLAIN 文本快照或机器相关毫秒阈值冻结实现。
- 并发屏障核实：准备阶段没有提前 DML；原回执纯读不等其他 writer；纯 DB 竞争完整回滚后只提交一次；fake 网络暂停时准备读 session 已关闭，其他合法读写仍可推进。WAL 下另一个 writer 能提交不独立证明旧读事务已结束，还须核连接／事务实际退出。
- 复用既有 SQLite 诊断及测试内采样，不新增生产诊断写入、常驻探针或性能门禁。`held_lower_bound` 只能报可观测持锁下界；pool／driver／SQLite 等待无法拆分时记未知，不用总耗时冒称精确锁等待，不承诺单机 SQLite 并发零等待。
- 表情前台／后台按原意图和实际 parts／回执处理，身份重构不插新等待。工具清单按合法新合同固定，不按人物／平台动态变化；不重渲染 frozen 历史、不清 generation／compact。Provider 实际 cache usage 独立测量，查询提速、局部字节／hash 相同不冒充命中率。

迁移收口也保持最小：旧解码和必要全量扫描只属于冻结离线迁移，产品不导入迁移模块，不探测旧表后在线补迁；不加常驻“迁移完成”状态或巡检 worker。真实 0140 升级与 fresh 库的一致性、原事实保留、产品路径只认新形状，分别验收。

## 10. 复审与交付记录

实施前后至少做以下四轮，发现缺口回到对应任务再复审，不以一次清单勾选代替贯穿：

1. 身份与持久资料：Person／Account／Assignment、名称、配置、Memory、授权与遗忘。
2. 最广消费者扫描：现有全部平台／入口、Main/Work/子 Agent/自动化、插件/通知、Code Mode、目录、历史、提示、测试与 CI；用第三平台测试发现 QQ/TG 假设。
3. 最深竞态与恢复：准备→writer、队列→派发、合并／转移／重授、已付→新链、ACK→入账、隐私清退与部分发送。
