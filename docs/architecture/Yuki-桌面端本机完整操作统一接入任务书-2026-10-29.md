## 1. 目标与交付

让运行在服务器的 Yuki 经桌面端管理的同一 Connector，直接使用本人电脑的命令、文件、程序和既有浏览器。这里的程序指能够由命令或脚本调用的程序；任意原生 GUI 的全屏识别和跨应用键鼠不在本期。任务判断继续由云端 Main 负责，本机只执行获准操作并返回真实结果。

本期有两条必做交付线，共用既有连接、执行与回执，不建立两套实现：

| 交付线 | 本期内容 |
| --- | --- |
| 本人电脑接入 | 桌面统一管理连接和完整访问；本机 Shell、统一文件桥、已安装程序的直接调用、Agent 可选委托及结果查看 |
| 现有链路修复 | T13 修复 [#514](https://github.com/YuanYeYouTao/Yuki/issues/514) 剩余的持续监督差错；T14 修复主动进度查询失准。二者可与本机接入并行，均须本期完成 |

本机终端直接运行该电脑上的现有程序，包括 OpenCLI 等浏览器工具。本期不自研、内置或默认安装浏览器 CLI，不管理其扩展、调试协议、浏览器会话和子动作回执。工具安装和浏览器授权沿各工具自身方式处理，文件与截图共用本期文件桥。给 Yuki 自己的环境安装浏览器、扩容沙箱或改造 VNC 均不是本期交付或前置条件。

### 1.1 完成后怎样使用

用户安装或更新桌面端，由原流程安装/更新配套 Connector；连接当前 Yuki，为这台电脑开启一次完整访问。之后可从 App、QQ 等已有获准入口交代任务，Yuki 明确选择本机目标后直接执行，并返回原执行的进展、结果和需要交付的文件。用户无需手工复制命令或为每个项目单独授权。Yuki 的连接桥只有原 Connector；OpenCLI 等外部工具的安装与授权认其自身要求，不另写 Yuki 浏览器桥。

需要操作浏览器时，从本机终端调用已安装的 OpenCLI 等工具，按该工具核可用浏览器与实际授权。缺少外部工具不阻止电脑连接、Shell 或文件功能；没有 Codex/Claude 只影响对应可选委托。

关闭桌面窗口后是否继续可用，认现有 Connector 后台服务的真实状态。电脑离线时保留原操作及结果，不将同一操作转到服务器或另一台设备重做。

| 能力 | 本期应交付的行为 |
| --- | --- |
| Shell、文件与程序 | 以 Connector 所在 OS 账号执行命令和脚本，访问该账号可用的文件与目录，使用本机程序；可读取增量输出、真实退出结果并定向取消本次执行 |
| 浏览器 | 由本机终端调用 OpenCLI 等现有工具操作；Yuki 只接原命令、真实输出和统一文件管线，不另做浏览器适配器或安装浏览器 |
| Codex / Claude / ACP | 沿已有原生 Agent 接入完成可选委托，保留原实例、会话、登录和执行回执 |
| 持续监督 | 修复 #514 在当前实现中仍存在的等待、激活、完成及进展反馈问题，沿原 Work/监督关系接续；不以静默或单轮结束代替持续目标完成 |
| 主动进度查询 | 用户追问时，区分 Yuki 自身 Work 与原生 Agent 会话，按原目标查询最新相关事实、执行结果和未决事项；不把旧调研、生命周期或在线状态当作当前进度 |
| 观察与交付 | 原文件默认留在本机；需要给 Yuki 查看或发送时传输选定的实际字节，复用现有私有媒体、成果存储和 send |

### 1.2 完整访问的含义

完整访问描述 Yuki 自身在这台电脑上的操作范围。工作目录只是执行位置，可以随任务切换；该 OS 账号可访问的其他目录不再受项目白名单限制。普通操作沿已开启的设备授权执行，Yuki 不增加逐条确认或服务器管理员资格要求。操作系统、浏览器和原生 Agent 的实际权限、登录和原生许可仍按各自事实处理。

Shell、文件和浏览器能力独立于 Codex / Claude 的安装。原生 Agent 是可选委托对象，本任务不统一改写其 sandbox、profile 或会话权限配置。

普通聊天中的本机终端、图片观察和文件发送沿原工具调用执行，不增加接纳 Work 的前置条件。任务已经属于 Work 时，才接入原 Work 的等待和接续；原生 Agent 委托继续遵守 external_agent 的现行合同。

### 1.3 怎样算交付完成

本次交付以下五条真实链路。本机能力在 Windows、macOS、Linux 的现有发行目标上核验相同的调用与结果语义，持续监督与进度查询修复按共同 Main/Work 合同验证：

1. 未安装编程 Agent、未选择项目的电脑，能由 Yuki 执行本机命令、跨目录处理文件，查到原进程的输出和退出结果。
2. 本机终端能够直接调用外部 CLI；截图与下载产物沿同一文件桥观察或发送，不为浏览器新增工具、动作协议或维护一套自动化实现。
3. 已安装的编程 Agent 能从同一设备入口接收委托，原会话、问题、取消与执行结果仍可查询。
4. 持续监督沿原 Work、原操作和累计预算跟进；有效等待与真实新输入按合同接续，静默期间仍需跟进的目标保持可恢复，目标真正结束后正常完成。进展反馈按用户要求及真实事件时间处理。
5. 用户主动询问当前或指定行动会话的进度时，Yuki 能定位原目标，按实际需要读取最近相关步骤、原回执和结果；查询不到当前事实时说明已知时间和未知部分，不将旧记录描述成最新进展。追问本身不重启原执行或结束持续监督。

本机新增链路 1–3 从桌面连接、Connector 执行到结果查看贯通。监督与查询链路 4–5 沿原 Main/Work、原事件、回执和 send 验收，涉及本机原生会话时才核 Connector；Yuki 自身 Work 查询不以桌面在线为前提。服务启动、socket 在线或某个接口返回成功均不能单独代表目标完成。具体证据见第 10 节。

本期范围为命令、文件、程序和浏览器页面操作。完整访问不表示已经具备任意原生 GUI 的全屏识别、跨应用鼠标键盘、多屏和系统弹窗控制；这些能力单列于第 12 节。

### 1.4 组件各自做什么

| 组件 | 本期职责与安装位置 |
| --- | --- |
| 云端 Yuki / Main | 理解任务、选择真实设备、发原调用、解释回执和反馈；不在云端另跑一套本机执行器 |
| Yuki Desktop | 本人电脑上的管理入口：连接、开关、能力/任务查看及 Connector 安装升级 |
| 本机 Connector runtime | 桌面端配套发行并管理的本机用户服务，包含 Python、通用 Shell 执行器与文件传输；独立进程不等于要求用户另装产品 |
| 本人已安装浏览器 | 由用户所用 OpenCLI 等外部工具处理页面、会话与浏览器自身许可；不是 Connector 的一套新执行器 |

| Yuki 自己的持久 Linux 环境 | 保留已有终端和实际文件系统；省略 device_id 仍指向它，源码有浏览器扩展不证明当前已安装或可用 |

Connector 随桌面端交付通用 Shell 与文件桥。第三方 CLI 是本机程序，不属于本期新增打包责任；不得再以浏览器功能名义增加专属 RPC、journal 字段、daemon 或运行时。

### 2.2 本期关联问题：#514

[#514](https://github.com/YuanYeYouTao/Yuki/issues/514) 记录了旧版本持续监督两个本机 Codex 会话时的三组问题：关键进展迟报并被说成刚发生；首次等待登记成功后再次激活，继而反复等待冲突；quiet 最终响应经普通 final 路径结束了仍需跟进的监督 Work。

这些是历史现场证据，不代表当前 main 已复现。T13 先对照当前实现、原输入顺序和已有修复，再定位仍存在的差错。当前仍有 active-wait 冲突和普通 final 完成入口，单凭入口存在、Issue 仍 open 或测试文件存在，均不能判定已经复现或修好。

本期将它列为明确 Runtime 修复范围，T05 的接续和 T09 的原生 Agent 回归与其共同核对，最终由 T12 汇总验收。若当前已包含某项修复，需提供对应实现和针对原场景的回归证据；只保持原委托能运行，不能代替 #514 专项验收。

### 2.3 本期关联问题：主动询问进度时回答失准

本轮按用户要求只读查阅其与 Yuki 的私聊记录，已找到历史回答失准的实例。2026-10-25 10:55，用户询问最后在做什么（内部事件 `117585`），答复 `117586` 却将 10-20、10-23 的旧调研作为最新进展。2026-10-25 11:17，答复 `117604` 再次声称提供最新情况，用户随后指出“依旧全错”（`117605`）。本次实例发生在 Codex 会话；T14 同时核查 Yuki 自身 Work 及其他原生会话的查询，不以此个案限定范围或预设共同根因。

原工具记录同时确认了读取路径的问题：`322471/322472` 读取历史原文，完整结果为 2,600,416 字符，转存 Artifact 后向模型返回短结果；`322491/322492` 对 92 条倒序历史使用 `offset=90, limit=2` 读取末尾，之后 `322506/322507`、`322511/322512` 仍从 29 条结果的尾部取到旧资料。历史答复失准、超大结果转存及倒序尾部读取已有证据；转存不等于原历史丢失。当前 main 下的完整重现、各环节的影响及唯一根因仍需验证，不能据此直接认定是单一分页错误。

源码还需分别核对两个信息入口：`task_control get/list` 主要提供目标、生命周期、等待与计数，不直接返回最近步骤、context_note 或执行回执；原 Work 业务接续已有私有工作材料和执行证据。T14 沿原来源、授权和实际模型观察核查这组差异，按第 6.5 节修复；证据见[专项笔记](research/local-device-20261029/progress-query.md)。T14 与 T13 分开定位、联合验证，不以自动监督反馈正常代替主动查询准确。

## 4. 复用边界与接入方案

确定的边界是：一个设备安装与 Connector 服务、原设备和 Person 身份、原调用与执行回执、既有 Main/Work 及媒体交付。下图描述这些职责关系。具体字段布局、通用终端与文件传输及版本扩展方式属于接线方案，先以 T01 的真实调用者和最短验证确定，再更新对应合同。

~~~mermaid
flowchart LR
    U[本人通过 App / QQ 等原入口提出任务] --> M[云端 Main / Work]
    M --> T[原 terminal 工具与来源核验]
    M --> A[原 external_agent]
    T --> S[原 Linux Manager]
    T --> W[同一设备 WSS / 原调用 ID]
    A --> W
    W --> C[已有 Connector 用户服务]
    C --> P[本机 Shell / 文件 / 已装程序]
    C --> N[原 Codex / Claude / ACP driver]
    P --> B[本机现有程序：OpenCLI 等]
    P --> F[按需选定的文件流]
    B --> F
    F --> O[私有工具媒体 / inspect]
    F --> I[不可变成果 / send]
~~~

Electron 保持薄入口，负责本机设置、配对、状态、任务查看和服务管理。真正执行者仍是独立 Connector 用户服务。不能把云端任意命令暴露成聊天 renderer 的通用 Node IPC；现有 contextIsolation、sandbox 与 sender 身份核验没有限制 OS 文件范围，保留即可。

传输共享，领域回执各认其事实。AgentOperation 必须归真实 Agent instance，session、run 和 native execution 按具体操作事实可以缺省；不能为了 Shell 放宽 instance 硬关联，也不能登记虚假 ACP/Shell Agent 绕过它。终端继续使用 SandboxTaskRun 的原 request/source/run 和既有 completion/continuation。文件只补实际跨设备字节桥，不恢复旧 local_device 的文件权限、执行队列或活 API。

不把服务器环境搬到本机，不把两边文件系统合成虚假共享目录；本机离线不自动改到服务器或另一台电脑执行原命令。

### 4.1 固定工具怎样选择电脑

以下为拟议合同，尚未实现：

| 工具/入口 | 本期扩展 |
| --- | --- |
| external_agent(action=list) | 沿既有设备目录读取 devices/instances，补设备通用能力；设备无 Agent 实例也能列出 |
| terminal_exec | 增加可选 device_id；省略保持原服务器环境。显式设备时在该电脑运行 command/cwd |
| terminal_read / terminal_control | 只按原 run_id 查执行目标，不再允许换 device_id；原执行在谁那里就向谁读取/控制 |
| environment_status | 可选 device_id 查询该设备实际 OS、Shell 与完整访问状态；省略保原服务器状态 |
| workspace_inspect(path) | 增加可选 device_id，选择真实本机文件并经文件桥取回；artifact_id 仍认原已发布版本 |
| send(path) | 增加文件来源 device_id，服务内先冻结/导入原文件，再走原发送；这不是消息目的设备 |
| save_conversation_attachment_to_workspace | 允许显式设备目标，把已获准附件保存到本机真实 destination；省略保原服务器语义 |
| external_agent 其他操作 | 原声明、原 Work 委托与原生资源语义继续；无需新增 local_codex/local_claude 工具 |

设备目录不是动作审批。Main 的工具声明仍在部署时冻结；设备上线、下线、安装程序或打开浏览器只改变查询结果，不在每次模型请求中动态删改工具清单。

Host 在首次派发前确定真实执行目标，随原调用持久保存，并参与原请求一致性核验；后续读取、取消、恢复都使用这份事实。目标不从“现在选中的电脑”、路径、名称或最近在线设备重建。

SandboxTaskRun 也承载原生 Agent 的 Work 回执，不能把缺少新目标字段的旧行一律认成 Manager。先沿原工具/回执种类和已保存的资源关联区分 native、旧 ACP/Manager 与终端；只有原事实表明来自 Manager 的旧终端才保持该目标。原 native 继续回 external_agent，目标未知则保原 ID/unknown，不靠缺字段或一次网络失败选择另一个执行器。

优先复用现有 task、source 与回执保存目标。使用既有 JSON 还是增加字段，由实际派发、恢复和查询需要决定，不在任务书里预定 terminal_target 的字段名和存储位置。必要索引用实际查询与 EXPLAIN 证明；不为同一执行另建任务表、影子账本或全库 revision。

现有 agent_tools 只向启动工具传 source，读取/控制常传 None。本机分派必须补齐所有实际调用者的可信来源，包括 Main、子 Agent、Work 恢复和取消清理；不能让一个 run_id 变成无来源的本机控制凭据。服务器原共享环境的语义不因此被改成每人独立沙箱。

### 4.2 真实授权放在哪里

完整访问启用事实由 Connector 自己的私有配置持有，Desktop 通过现有管理 CLI 修改并读取它。云端目录展示该服务当前公布的真实能力，不再保存一份可以独立开启的完整访问布尔值。云端命令不能把本机授权从关闭改成开启。

旧安装缺少此字段时仍按原 Agent-only 能力运行；升级不替用户开启整机访问。用户在原设备上明确开启后扩展同一安装，保 device、实例、journal、未决操作与服务停止/运行状态。

本人设备资格沿原 Person、connector 凭据与当前撤销状态处理。不同群成员、平台超管、operator 或没有本人设备来源的 SELF，不因看见工具就获得另一人的电脑；子任务沿真实获准委托执行。无需为每个目录和项目再授权，也不把服务器管理员角色加回来。

关闭完整访问阻止此后新派发的通用 Shell、文件传输和交互输入，保留已发生事实和原回执。已启动脚本可能继续操作文件或程序，开关不能追溯撤销它的 OS 权限；需要停止时按原 run 定向取消并核实际退出。原先单独授予的 Agent-only 连接继续按原授权运行；要断开整台设备，复用停止 Connector 或撤销设备。

关闭状态拒绝新的通用操作与尚未发送的 stdin，保原查询和定向取消。已运行的脚本、外部 CLI 或其后台程序按原系统事实处理，开关不会追入外部程序逐动作撤权；需要停止时显式取消原 run。不新增浏览器动作队列，不关闭用户已运行的浏览器或 Agent daemon。

## 5. 本机 Shell 的执行合同

首版支持普通命令、长命令、stdin、增量输出、真实退出码、定向取消和后台服务持续连接。用异步进程读写与事件等待，不用高频遍历进程表、空转轮询或等待命令退出后一次性收集全部输出。

按真实 OS 选择并报告 Shell：Windows 使用本机可用的 PowerShell（用户可明确选择），macOS/Linux 使用实际选择的 Shell；不把 Bash 命令、POSIX 引号或 /workspace 写死到所有系统。程序路径、参数数组与 command 脚本分开，路径有空格/中文仍按原字节语义执行。初始 cwd 默认用户主目录，用户可指定任意该账号可用目录；目录不存在就返回实际错误，不偷换到另一个项目。

Python 3.12 已有异步 subprocess，可复用随附运行时。Windows 的进程组、管道、取消和 POSIX 不同；普通 PIPE 不等于真正 TTY。原 Linux Supervisor 顶层依赖 pty、termios、fork 和 /proc，不能整份拷进 Windows Connector。[Python 官方说明](https://docs.python.org/3.12/library/asyncio-subprocess.html)

本期不把普通 stdin 宣称为 PTY。tty=false 的跨平台 Shell 是必做；tty=true 在本机首版若未实现，明确返回该设备不支持，不静默退成管道。真正 TTY 作为后续可独立交付项，复用 POSIX PTY 和 Windows ConPTY；无需为基础电脑操作先写完整终端模拟器。[ConPTY 官方说明](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session)

取消必须作用于本次执行实际持有的进程/子进程范围。POSIX 进程组、Windows Job Object/进程组各用薄适配；不要按程序名杀进程，不向跨重启复用的 PID 发送取消，也不只杀外层 Shell 就宣称子任务结束。无法确认终止时保原 run 与 unknown。Windows Job Object 可管理所属进程组，是需核对的现成 OS 原语，不另造跨平台进程管理服务。[Microsoft 官方说明](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

默认不加命令总运行时间上限，调用等待时间只影响本轮何时交还 run。显式 timeout 才按其原意执行。输出沿原游标读取，转存本机日志，截断/轮转时如实报告；不把每个字节作为需要服务器持久化的进度事件。真正终态、执行意图与未知结果仍保留。

普通执行由同一 Connector 服务持有；短暂断网不停止进程。服务正常停止时收拢自己直接持有的执行，无法确认的结果不伪称取消。强杀、掉电、OS 重启后恢复 journal，不自动重跑旧命令；首版不增加独立 Shell 守护进程来承诺任意进程跨服务崩溃存活。

## 6. 原回执、恢复与文件交付

### 6.1 终端回执与原执行接续

普通本机工具执行使用原事件或原执行来源与原工具回执，不强制新建 Work；已有 Work 时才关联其等待与 continuation。原生 Agent 现有的接纳要求不扩散到 Shell、看图或发送文件。

1. Host 使用原 invocation/execution 身份生成 request ID，核本人设备与当前来源，在短事务里登记原 task/target；提交后才写 WSS。
2. Connector 在启动进程前 journal.begin 原命令；相同 ID 返回原结果，参数冲突保原事实，不启动第二个进程。
3. 进程接纳后返回原 run。输出由原 owner 提供，终态先落本机原 journal，再发服务器。
4. 服务器以已认证 WSS 的 device 核原 task 目标、request/run 与真实来源，在提交边界复核关联，写入原 terminal completion 及适用的接续事实后 ACK。
5. ACK 丢失只重传原事件。terminal_read、Work 等待/恢复及取消清理统一查原 run，不重调模型或重发命令。

SandboxTaskRepository.receive 目前信任 Manager，不是电脑身份核验器。新 WSS handler 不能仅拿客户端自报 request_id 就调用它，更不能让一台电脑结算另一台电脑的任务。身份准备在 writer 外完成，原子写入处复核必要依赖；持锁不等待网络、进程或文件。

保留 Agent 与终端各自的已确认状态映射。当前 terminal 取消会阻止自动 continuation，不能复制 Agent 的完成投影导致所有取消都触发续跑。Work 结束、detach、原生完成和平台 send 仍分别结算；本机 Shell 不另跑 Main。

除启动外，input、interrupt、cancel 与文件写入也保留各自原调用和结果。terminal_control(input) 继续按现行合同发送原样 text，输入交付只证明字节已交给进程，不能被解释为页面动作完成。

外部 CLI 通过普通终端调用；Host 只持有该次原 exec/control/run 身份及其真实输出。终端输入接纳不证明页面动作完成，网页业务结果由外部工具输出与实际状态核对；没有页面结果时保未知，不自动重提原命令。

普通 terminal_control 保持原样 stdin，terminal_read 返回原输出；不解析任意 stdout 来建立浏览器业务状态。OpenCLI 等工具自身的调用结果、会话与子动作恢复由其原实现负责，Yuki 不额外建动作数据库、子协议或恢复循环。

### 6.2 本机文件必须有真实字节

普通文件查找、读写、移动和程序调用直接走 Shell。只有文件需要给云端模型观察、平台发送，或把已有云端附件放到本机时，使用共同文件桥；不新增一套远程文件管理产品。

字节传输共用一条路径，传到服务器后按实际消费者处理：

~~~text
本机选定文件版本
  → 沿原设备身份传输实际字节
  → 服务器私有临时文件 / FD
  → 仅供模型观察：原私有工具媒体 / tool_handle
  → 需要发送或保留成果：WorkspaceStore.snapshot / artifact_id
~~~

原 device、request/transfer ID、文件名、版本/hash、字节数与原调用来源相连。传输和 hash 在 SQLite writer 外完成。仅观察使用第 6.3 节的原私有媒体通道；需要交付时复用现有 snapshot 和 Social 发布身份。确认丢失查原 transfer/handle/artifact，不重新生成交付身份或重新发送。文件中途变化按真实版本冲突返回，不将混合字节发表成成功；已经采用的观察像素与已发表快照不随本机原文件改变。

反向保存附件同样传真实字节。原内部 event/附件索引先按现有来源授权，目标为本机实际 destination；完成回执说明该电脑上的实际保存结果。不能假称本机与服务器共用 /workspace，不能用客户端上传接口伪造新的用户聊天事件，也不靠把大文件 Base64 塞进 stdout 完成传输。

文件传输共用原 Connector、设备身份和原操作回执。字节可沿现有流式 HTTP 模式或设备通道接线，T01 依据实际调用和复用成本选定，统一入口不等于所有流量必须挤进一个 WebSocket。电脑继续主动连出，不为传文件另设设备身份或本机入站服务；传输使用背压，控制和重要回执不能被大文件长期堵住。

分片进度是可丢临时状态，不逐片落主库。原文件版本、已采用的观察来源、最终发布/写入和未知结果才需要持久回执；不建设第二套 artifact 数据库或文件传输调度器。

本机完整访问意味着该账号可访问的资料可能被任务读取。程序不自动同步整盘、浏览器 profile 或原生登录文件；页面、选取文件和输出会按实际任务进入云端。不能把“认证资料默认留在本机”宣传成完整访问下 Shell 无法读到这些文件的保证。

### 6.3 文件和截图具体放哪里

默认不把本机资料放进 Yuki 的 Linux 沙箱。原电脑与服务器有独立文件系统，云端需要的观察/交付字节按需传输。

| 材料 | 默认位置 | 生命周期 |
| --- | --- | --- |
| 用户原文件、任务项目文件 | 本机原目录或任务明确选择的目录 | 正常文件语义；缓存清理不删除用户文件 |
| 浏览器下载 | 本机实际下载目录或本次明确选择的位置 | 归用户文件；不因 Work 结束清掉 |
| 外部工具生成的截图 | 原工具输出目录或本次 Shell 指定路径 | 按用户文件保留；Connector 不另建截图缓存或清理外部工具目录 |
| 给 Yuki 看一次的图片/页面资料 | 服务器已有的私有工具媒体存储 | 沿现有保留配置和真实 Work/artifact_refs 保护，到期且无保护引用时回收；已付请求的原像素副本按原 journal/checkpoint owner 保留，不默认发布永久成果 |
| 明确发送、收藏为成果的文件 | 现有 WorkspaceStore 不可变成果存储 | 沿原发布/隐私/回收合同；不是自动到期的截图缓存 |
| 确实要在服务器继续处理的副本 | 显式保存到 Yuki 沙箱实际目标目录 | 原件仍在本机；副本按该任务和普通环境文件语义处理 |

源码事实需要分清：WorkspaceStore 已移除 expires_at，cleanup 只清损坏记录、无 manifest 引用 blob 和遗留 pending，不会按时间删除有效 snapshot。因此不能把每张观察截图都 snapshot 后声称会自动过期，也不能把会话入站缓存的 24 小时规则套到它上面。[现有存储](../../src/yuki/workspace/store.py#L51)

仅供观察的本机图片可复用 WorkspaceInspector 的 file_metadata/data 字节入口、NativeMediaPreparer 和现有 ToolArtifactRepository.write_media_artifact，形成原来源下的私有 tool_handle；保留模型实际采用的像素与原版本，不依赖本机原文件仍存在。该存储已有配置保留期、原来源核验、Work/祖先和已登记 artifact_refs 保护及清理。默认保留配置为 86400 秒，实际仍认配置与保护引用，不是固定一天后一律删除。[字节入口](../../src/yuki/workspace/inspect.py#L39)、[私有工具媒体](../../src/yuki/tool_results/artifacts.py#L349)、[真实保护范围](../../src/yuki/tool_results/artifacts.py#L66)、[现有清理](../../src/yuki/tool_results/artifacts.py#L660)

已付请求/检查点不能被误写成所有 tool_handle 的自动永久 owner。WorkJournal 已对原工具图保存私有对象副本，沿原已提交输入、来源与对象引用回收；这份副本与观察缓存各认自己的 owner。恢复使用原字节，不重新读取本机当前文件，不为截图另建数据库或保全所有历史原件。[现有原图副本](../../src/yuki/runtime/work_journal.py#L766)

这里有真实接线工作：当前能力结果对 provider_id=core 不会自动走上述媒体归档分支。实施须在选定本机媒体入口明确复用私有归档、source/access 和 image 验证路径，将已冻结图绑定 source=tool 与原 tool_handle；不能把本机路径留成服务器 workspace_path，让后续校验再去 Manager 查不存在的文件，也不能重写所有 core 图片的生命周期。原 device、transfer/request、path 与 hash 保留在原 inspect 结果和回执里，不因有了 handle 就丢来源。[当前分支](../../src/yuki/capabilities/results.py#L156)

本机 captures 缓存的保留时间属于配置与文件生命周期，不是任务成功门槛。复用同一 Connector owner 的按需/低频清理入口，保留真实在用资料，清理自己的未引用临时文件；服务重启不删除未确认操作或用户目录。云端已确认冻结所选像素/成果且没有本机活动引用后，本机临时截图可按缓存策略释放；历史回执记过路径不等于永久占有这份临时文件。云端接收临时文件在观察资料归档或成果发布确认后释放，失败/未知沿原引用和回执查证，不保留永久中转副本。

观察或归档失败不推翻原操作成功：分别报告“页面动作/截图已发生”和“图片尚未取得”，保原操作/传输回执；不能为取得画面再做一次点击、表单提交或下载。

### 6.4 持续监督的等待、接续与收尾

#514 的处理复用既有 Main/Work、外部执行回执和 send。T13 可与本机能力开发并行，不依赖 Shell、文件桥或浏览器全部完成；涉及同一接续/结算入口时与 T05 一起修改和验证，保留唯一 owner。

1. **先定位当前差错。** 依据原 Work、wait、operation/run、输入顺序、模型实际观察及发送回执，核对事件发生、入账、激活、模型观察和送达的关系。原现场首次 wait 已成功，不能把后续冲突改写成“从未等成功”，也不预设 Connector 丢事件或某类信号必为原因。缺失证据如实记录，不为补时序另建长期账本。
2. **等待按真实来源接续。** 有效等待保持其原身份和条件；提前激活须认现行合同允许的真实输入、匹配信号、执行事实或显式恢复。已有等待冲突应收敛到原有效等待或明确当前状态，消除反复购入模型申请同一等待、空写 context_note 的路径。合法新输入仍能接续，不把 Work 锁死到计时结束。
3. **静默与目标完成分开。** quiet 继续表示闲聊参与意愿，不单独证明持续目标完成。仍需监督时使用原等待/接续；原单轮完成、detach 和监督目标完成分别认真实含义。目标真正结束时，显式结束与现行合法 final 均能正常结算，不增加“所有会话已关闭”“必须发过汇报”或“必须显式 complete”条件，也不推翻已接纳的真实结束决定。
4. **反馈认用户要求与原事实。** Main 根据原目标及用户追加的“重大进展”“降低检查频率”等要求决定何时反馈，统一 send。晚观察的旧事件不描述成刚发生，缺少发生时间时不编造；重传同一事件不重复生成输入或自动汇报。用户新的询问仍按新输入正常回答。核实际发送回执，不以消息条数替代送达与内容证据。
5. **修原链，保原事实。** 排查入口包括 [work_wait.py](../../src/yuki/runtime/work_wait.py)、[work_supervisor.py](../../src/yuki/runtime/work_supervisor.py)、[turn_execution.py](../../src/yuki/services/turn_execution.py)、[work_repository.py](../../src/yuki/runtime/work_repository.py)、[提示合同](../../src/yuki/prompting/contracts.py)及原生事件接入。按证据删除冲突/重复规则，必要时同步现行合同和相关测试；不另建监督循环、reporting 模式、固定汇报频率、里程碑白名单或重试阈值，不改人格。

监督修复保原 Work、原事件/操作、监督范围、预算和已付请求；不清空旧任务、重派历史效果或重买旧请求。专项回归按原问题顺序贯通，同时保留正常等待唤醒、用户结束监督、普通 final 完成等反例，见 V21–V27。

### 6.5 主动进度查询：定位原目标，读取相关事实

T14 处理用户主动询问进度时的准确性，与 T13 的持续监督接续、结束及自动反馈分别定位。先对照第 2.3 节的真实私聊与原工具记录，核清目标选择、查询结果、截断、模型实际观察和最终回答，再在原链路修改；不把当前缺口预先归为某个原生 Agent 或某一条提示。

1. **先认目标与状态含义。** 问题可能指 Yuki 自身 Work，也可能指被委托或监督的原生 session。沿原上下文及内部 ID 定位，已有明确目标不反复询问；多个真实候选无法区分时再消歧。Work 生命周期、原生 session、单轮 turn、operation/run 与送达分别认事实；本轮 no_active_work、设备在线、无活跃 turn 或 completed 均不能单独回答业务做到哪一步。
2. **按需取最新相关事实。** 已有足够的真实结果时直接使用；需要查询时，优先读取原目标下的必要最近步骤、结果和未决事项，原操作确认仍按原 operation/run 查询。原生会话的当前活跃轮、最近已结束轮和明确指定的旧 execution 分别查询，不能用最新轮替换指定旧轮。最新相关 turn 的真实 ID、时间、状态与必要行动内容应有直接读取入口；历史方向、最新端和续读方式在短结果或 Artifact 清单中仍可见。保持原数组 offset 语义，按需分页，不把倒序尾部当最新，也不默认扫描整份历史后靠模型猜进度。缺少当前证据时说明原观察时间与未知部分，不把摘要或旧调研补写成新事实。
3. **复用已有事实入口。** Work 目录只承担其实际提供的信息；如不足以解释进展，按当前真实读取授权复用原 context_note、工具效果与原回执、结果及子任务关系。原生 Agent 沿既有 session/turn/operation 查询和增量资料读取，不另存进度数据库、自动全史摘要或第二套状态机。私有工作材料不因可查询目录元数据而成为全局可读，也不将整个 checkpoint 原样返回。
4. **查询不授权重做效果。** get/list 和进度读取不作为恢复、重派或取消原业务效果的许可，不为获得最新回答重跑效果、重买原已付请求或重置预算；现有查询中的原回执查证及观察恢复仍保留。合法追问按现行输入合同处理，持续监督仍沿原 Work 与等待接续；回答进度不等于结束监督，也不把仍有 active session/turn 作为所有 Work 不可完成的条件。
5. **回答与结算各认原合同。** 回答区分已发生、正在执行、等待、失败和未知，必要时给出事实时间与来源，发言沿统一 send。查询次数、报告条数、是否查遍历史及是否发过汇报都不是完成门槛；普通目标真实完成时仍能按原合法结束决定结算。
6. **按实际能力说明读取范围。** 当前工具的目录第一页、旧标题和 cwd 不能代替原目标；保必要的原生时间、来源及分叉线索。Claude 的最早页不能用于回答最近行动，ACP 的状态读取不能冒充历史读取；驱动投影后的 full 不能冒充完整原件。按原 ID 取所问行动的必要输入、输出/错误或明确缺失，不恢复私有推理和无关原文；不为补齐缺失历史另行加载或接管未附着会话、启动业务执行，原 operation 查证中的既有观察恢复继续保留。指定 execution 不因同时带监督 operation 被静默换成最新轮，也不因结果缺少 execution 被默认为原执行已确认。

分页之外的续审见[Q01–Q08](research/local-device-20261029/progress-query-edge-audit.md)。T14 同时核目录范围、实际 driver 能力、原内容投影与时间语义；刷新当前、续读旧页和指定旧执行分别处理，游标的原资源、方向及对应参数在短结果中仍明确。多次读取不承诺同一瞬时快照，原生发生时间、入账时间和查询观察时间不混用；保既有 sequence/恢复查证，不为一致性新增全局锁、快照数据库或后台轮询。Claude SDK 的有界响应仍可能先解析完整文件，性能按实际读取路径验证。

公开实现对照进一步确认：优先删除进度查询路径内自动耗尽全部历史页的组装，让原生历史按需返回一页和真实续读游标，实际消费传入的 native cursor。查询当前/最近行动直接读取相关 turn 的必要内容，大单轮也按实际能力选择详略或条目分页；原参数含义、类型与真实消费者一并更新。原执行查证和观察恢复中为定位指定旧 ID 所需的扫描继续保留；不机械删除共用迭代器，不在通用 Artifact 翻转数组，也不因新版文档有接口就宣称所有 owner/store 已支持。见[公开源码对照与最小修订](research/local-device-20261029/progress-query-comparison.md)。

实现优先核 [Work 查询](../../src/yuki/runtime/work_queries.py)、[本轮状态投影](../../src/yuki/runtime/work_control.py)、[原工作材料与执行证据](../../src/yuki/runtime/work_session.py)、[聊天记录读取](chat-history.md)、[原生 Agent 服务](../../src/yuki/external_agents/service.py)和[客户端原步骤投影](../../src/yuki/client_api/works.py)，按证据修最小接线并同步现行说明。V28–V32 覆盖真实失准场景的受控回归和正常反例，不要求每次询问固定调用同一组工具。

## 7. 外部程序和浏览器工具：直接使用本机终端

本期不自研或内置浏览器 CLI。已有本机终端后，Yuki 可以直接调用这台电脑上的 OpenCLI 等现有程序；没有理由再维护一套浏览器连接、按键、上传下载和会话实现。第三方 CLI 的安装、运行依赖、扩展和浏览器许可沿其自身方式处理；不能将它是否已安装写成连接电脑或使用 Shell 的前置。

Connector 只执行原 Shell 命令、接收原 stdin、返回原输出与进程回执；普通命令不被自动识别为浏览器协议，不新增 browser RPC、专属 journal、后台服务或网页工具 schema。OpenCLI 是示例，不写成唯一可用程序，不自动安装它或重启用户浏览器。

截图和下载仍是本机文件。用 workspace_inspect(path,device_id) 观察实际像素，send(path,device_id) 冻结并发送成果；云端附件用同一文件管线保存到本机，再由外部工具上传。输入已接纳、CLI 进程已退出与网页业务完成分别认实际事实，未确认不自动重派点击或提交。原 Linux 终端与 CDP 源码保持原实现，不因本次新增抽取或打包。

## 8. 桌面交互与生命周期

入口改为“这台电脑”，至少清楚呈现：当前连接的 Yuki/本人/设备、完整访问是否开启、后台服务与云端是否连接、实际 Shell、可选 Agent、当前及历史操作。只保留已有设置页和工作区结构，不新建控制台。

首次连接可以直接开启本机能力。项目选择、原生 Agent 安装和登录仅影响对应可选能力；本期沿已有入口发现、配置和使用已安装 Agent，保原登录方式，不新增安装器或登录系统。关联已有 Connector、更新随附运行时继续沿原目录和原配置，不创建重复设备，不为了新功能清空旧 journal。

### 9.1 API、协议与迁移

交付明确匹配的 Bot、Connector 和 Desktop 版本，沿现行版本核验与配套升级流程处理协议变化。T01 根据真实线格式及消费者决定是否属于兼容扩展；确有不兼容变化时升级对应版本，不预定必须保住协议 3，也不预定必须升到 4。

必要的设备能力资料复用原目录；为保留某个版本数字再建立双向协商、按版本暂存事件或长期混合运行机制，不属于本任务的默认施工范围。只有实际发布计划和消费者确有需要时才增加最小兼容，说明真实调用者与退出条件。

升级保留原设备、命令、journal、未 ACK 事件及已确认回执，版本不符时不派新操作，按现有方式提示更新较旧端。原回执恢复和 ACK 丢失重传按原 ID 核验，不把更新变成重做命令。回退时保留已经发生的事实与未决原件，不能用删数据、改原请求或重放效果制造“兼容”。未验证的混合版本、降级组合不声明支持。

本期优先保留原 NativeOperation/operations API 的 Agent 结构与 instance_id 硬语义，沿同一 /agents/v1 服务增加终端目录、原 run 和控制回执投影；Desktop 同页展示不同类型。无需为统一界面将原 NativeOperation 扩成大量 nullable 字段或先建“万能操作表”。终端控制沿现有个人命令请求/回执机制扩展，保独立原操作键；不把取消仅包装成一条未经确认的聊天自然语言。

若实际选择改变原 HTTP 返回结构，才按真实破坏性升级 Client API revision；只增加端点/字段不能独立证明必须升级。无论 revision 是否改变，都从实际路由导出 OpenAPI、更新 hash/生成类型与精确 pin；包版本、协议、API revision、能力和现场运行状态分别记录。

主库优先复用已有执行记录。新增字段、索引或迁移以实际保存/查询/恢复需要为依据；若确有必要，只管理本次新增事实，不顺手迁移消息、人物或 Memory。Connector 升级保原 namespace 和原操作/回执；缺少新授权配置继续保持原能力范围。迁移编号按施工时实际 head 分配，不改冻结迁移。

发布沿原五目标构建：Windows x64、macOS arm64/x64、Linux x64/arm64。Windows ARM 没有当前产品验收依据；Rosetta 也不替代 Intel 实机。本机 Shell/文件桥及必要依赖进入原 Connector runtime；不捆绑 OpenCLI 或另一套浏览器 CLI，不修改原 Linux CDP 实现，不把 Bot 的 ORM/Manager 拖入本机包。

## 11. 收益、代价与理论代码量

预期收益：Yuki 可以直接使用用户本机环境，简单文件/命令不必再经过一次 Coding Agent 模型调用；复杂编程继续委托现有 Agent；浏览器复用真实账号和现场状态。服务器无需为这些本机任务再起一套 Chromium/Xvnc，相关执行 CPU/RAM 转移到本机；网络延迟、文件流和模型所需页面内容仍有成本。本轮没有实测，不填节省 MB、百分比或响应 SLA。

可维护性的改善来自一个设备 owner、一套配对/运行时/升级、一个传输/原操作链、原终端与原 Agent 各自清楚的结果职责，以及同一份 CDP 动作。不是把所有东西硬塞进一张表或一个文件。最大风险是把共享传输误作共享 Agent 会话、把路径字符串当文件交付，或重连重做已经发生的效果。
