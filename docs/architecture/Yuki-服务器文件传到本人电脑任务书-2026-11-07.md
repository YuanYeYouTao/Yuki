## 1. 基线与问题

源码 main `5af28501`；生产镜像 `yuki:local-75e33e92`。事故时 `CODE_MODE_ENABLED=true`，20:42 UTC 已关闭，现为 direct 模式。Connector 0.4.3 / 协议 4。

2026-11-07 用户要求把 Yuki 持久环境中的两份报告（12396 / 15062 字节）放到本人 Mac `~/Documents`。模型没有传输工具，把文件 base64 读进上下文再逐字抄进 Mac 上的 `python3 -c`：单次生成 65–92 s，多次被插话作废；第一份写入后 sha256 不符（含乱码与错字），第二份留下 0 字节文件；之后定时自动化 162 又在 Mac 上 `rm -f` 了人工恢复的一份。两份最终由人工从环境容器原件恢复，sha256 一致。

第一份报告 11-05 曾作为 QQ 文件发给用户（#133496）。该事件是出站事件，`conversation_media_items` 无记录，附件查询只认入站（`conversation/media_service.py:513-524`），附件保存会返回 `attachment_not_found`。其 segment 带 artifact_id `70925bea…`（12396 B，sha256 `1a6b…`，`source_key` 为 `send:…`），Bot artifact 库中 blob 仍在。**以 artifact 为来源即可一次完成**。

## 3. 目标

模型用一次工具调用把 Yuki 环境中的文件或 artifact 原样写到所选本人电脑的指定路径；字节不进入模型文本；未确认的写入保持未知，不重传已完成写入；不新增永久中转 artifact（`chat-media-workspace.md:100`）。

## 4. 方案

### 4.1 工具 `copy_file`

由 `save_conversation_attachment_to_workspace` 改名并泛化，遵守工具面任务书 §6.7 的共同约定：

- 来源三选一：`path`（可带 `device`，表示源所在电脑；本期只能省略）| `artifact_id` | `event_id` + `attachment`。执行处单点检查，错误码 `choose_one_source`。
- `destination`（必填）；`to_device?`：目标电脑，省略为 Yuki 环境。
- `device` 在 `view_file`、`send` 与 `copy_file` 中一律表示**源**所在电脑，目标另用 `to_device`，避免同名反义；第二期做反向时只放开实现，不改 schema。
- 成功返回 `{destination, size, sha256}`；未确认返回 `{ok: false, error, status: "unknown", message}`，message 带源 sha256，并说明目标目录可能残留 `.yuki-transfer-*.part`、可在本机终端核对 sha256。
- 本工具直接按最终名称与参数落地，或并入工具面任务书 §6.10 的一次切换；不先以旧参数上线再改一次。

### 4.2 字节来源

`LocalDevices.upload` 改为接收 `(stream, size, sha256)`，删除其内部预哈希与 fstat 校验；三种来源在上传前都已知 size 与 sha256，Connector 末片仍核整文件。

- **path → 本人电脑**：Manager `files_read`（`sandbox/client.py:40`、`sandbox/persistent.py:204`、`computer_transport.py:54-97`）的头部给出 size 与 sha256，Bot 直接把流交给 upload，不落临时文件。
- **artifact → 本人电脑**：打开 blob 的文件描述符，沿用 `send(artifact_id)` 现有的 immutable 条件（`social/service.py:1154`；生产仍有 30 个 2026-09 遗留的可变 artifact）。授权与 `send(artifact_id)`、`workspace_inspect(artifact_id)` 相同：凭 ID 读取（`social/service.py:1150-1155`、`inspect.py:45-50`），不新增可见范围门；复制到操作者本人设备不超出 send 已有的能力。
- **附件 → 本人电脑 / Yuki 环境**：保持现有分支；附件按事件与序号全局共享（`media_service.py:513-524`）。
- **path → Yuki 环境**：复用 Manager `workspace_copy`（`persistent.py:804-807,926-990`），`source_key` 为 `path:<path>`，零新增机制，本期开放。
- **artifact → Yuki 环境、本人电脑 → Yuki 环境**：需要 Manager 新方法，第二期；本期返回明确错误 `source_not_supported_for_destination`。
- path 来源的权限与终端、`send(path)` 相同；Client API 的超管门（`client_api/computer.py:68-70`）属于那个入口，不随复用迁移。

### 4.3 恢复语义

- 不新派生 ID：`transfer_id = request_id = invocation_key`（`services/agent_tools.py:905`，来自 `main_agent_backend.py:263` 的 operation_id）。
- 先调 `upload_result`：succeeded 原样返回、不读源；not_found 才读源并上传；其余一律为 unknown。确定失败（`file_bytes_mismatch`、中途关闭完整访问等）在恢复时也读作 unknown，因为 Connector 不记录 failed。本期接受这一事实，不另建续传或失败记录。
- Bot 在读源阶段重启：恢复时 not_found，重读源再传，正确。在分片阶段重启：结果为 unknown，可能残留 `.part`，由模型核对后以新调用重传。

### 4.4 Connector 现状与可选小改

0.4.3 无大小限制；目标已存在时静默覆盖；目标是已存在目录时 `os.replace` 失败（`files.py:211`），报 unknown 并残留 `.part`；父目录不存在或无权限时 staging 在 `x+b` 打开处即失败（`files.py:187-190`），不残留文件，但 OSError 未转成 DriverError，被 `connector.py:530` 归为 unknown；相对路径按 Connector 进程 cwd 解析，在 Desktop 下不可预期。

可选独立小改（Connector 0.4.4，Desktop 重新打包即可；`app.ts:410` 最低 0.4.3 不变）：目标为已存在目录时写入“目录/源文件名”（模型最常写 `~/Documents` 这类目录）；offset 0 时 `mkdir(parents=True)`；replace 前的 OSError 转 DriverError。主功能不依赖此项，但第一项强烈建议同期完成。

## 6. 风险

- **吞吐**：每 64 KiB 一次网络往返、Connector 一次 fsync、三次 `synchronous=FULL` 提交（片 begin、片 complete、传输级 annotate，`files.py:132`），以及 Bot 每片一次授权查库（`local_device.py:456`）。推测 RTT 50 ms 时约 1.3 MB/s。
- **无超时**：设备请求没有超时（`external_agents/transport.py:35`），设备挂起时工具一直阻塞当前轮。
- **首次调用离线**：`upload_result` 也返回 unknown（`local_device.py:466`），传输回执只记 path 与 pending、不含 sha256。
- **`files_read` 限制**：只接受 `/workspace` 下路径（`workspace/files.py:40-52`），`/inputs/media-cache` 会被拒（`view_file` 接受）；拒绝任一级符号链接与硬链接（nlink≠1，`:58-85`）；文件不存在、ELOOP、读取期间变化都统一为 `invalid_request`（`persistent.py:213-214`）；`WorkspaceError` 为 RuntimeError（`store.py:21`），未被捕获，Bot 读到 EOF 后在 `client.py:51` 报 JSON 解析错误。Manager 先把整个文件复制到宿主临时文件再发头部（`computer_transport.py:54-78`），首字节要等整份读完、宿主盘多占一份；中途出错没有错误帧，Bot 必须按头部 size 与 sha256 核对（现有消费者 `client_api/computer.py:239-262` 不核）。

## 8. 验证

E2E：复用 `tests/integration/test_local_device_transport.py` 的 bridge 与 actual_connector（隔离 SQLite + 真实 Connector 包），加 `PersistentManager(testing=True)` 的 Unix socket（参照 `test_workspace_copy_receipts.py:33`），工具从 direct 声明调用。

1. 固定种子生成 12 KB 中文 Markdown、1 MiB+1 二进制、0 字节、恰好 128 KiB；分别经 path、artifact、附件三种来源写入设备，以及 path → Yuki 环境，比对 sha256。
2. 首次成功后删除源，以同一 request_id 直接调用服务模拟恢复：返回原回执，不读源，目标 inode 不变。
3. 末片之前断开 WebSocket：结果 unknown；以同一 request_id 模拟恢复，仍为原回执、不重写。另测“末片在途时断线，恢复读到 succeeded”。
4. 关闭完整访问：新写入被拒、目标不存在，get 仍可用。
5. 传输进行中改写源：目标为读取开始时的快照，或报错，不出现混合内容。
6. 目标已存在被覆盖；目标为已存在目录（0.4.3 报 unknown，0.4.4 写入同名文件）；父目录缺失。
7. 首次调用设备离线；符号链接或硬链接源；可变 artifact 被拒；同目标并发复制。
8. 64 MiB 文件吞吐，记录耗时。
9. 旧名历史回执经统一映射仍投影为“保存档案”。

产物：`artifacts/e2e/file-copy-<commit>.json`，记录每个用例的源与目标路径、sha256/size、transfer_id、回执状态、耗时、Connector 版本与协议、commit。
