# Yuki 文件膨胀、函数爆炸与工具面删减任务书

日期：2026-11-07（同日补充工具面，并经独立复审修订）

状态：**调查与任务书，产品尚未实施。** 只新增本文；实现、测试、PR、合并另行记录。作者要求把交给模型的工具名、参数、schema、描述与结果格式一并纳入，并决定一次性重做工具面，见 §6。

## 1. 来源与立场

- Yuki 于 2026-11-05 生成的《代码整洁之道视角下的 Yuki 架构深度审查与演进建议报告》（Deep Dive）提出了参数爆炸、局部 import、上帝类、异常与 ORM 边界等问题。本文逐条复测：**膨胀和函数爆炸属实，但多数诊断与建议不适用本项目。**
- Clean Code 的处方面向 Java 式分层；本项目按 [开发约束](development-contract.md) §0、§8 处理：删除重复状态、死参数、重复检查与无用分支；**不新增 DTO 层、Facade、Command Bus、事件总线、领域异常树或经验阈值门禁**，不为文件行数制造包装层。
- 基线：main `5af28501`。测量用 Python `ast` 静态统计（函数长度按 `end_lineno-lineno+1`，嵌套把 `elif` 计为同层，参数不计 self/cls），行数按 `wc -l`。下文“推测”指未逐行实施验证的估算。

## 6. 工具面：名字、参数、schema、描述与结果

### 6.1 方法与规模（已核实）

数据来自生产库只读：direct 模式下实际发给模型的完整工具列表（trace 411675，11-07 18:18）；2026-10-24 起 14 天的 provider 请求与响应中的 tool_calls 和 role=tool 结果（去重 6560 条）。`task_control`、`subagent_*` 不写 `tool_start/tool_end`，因此统一从 provider 请求与响应统计。**口径限制（复审指出）**：该统计只解析了 Chat Completions 的 `choices`，漏掉 Responses 格式约 1,027 条响应（约 1,002 次 function_call，其中 task_control 505、send 173）与 Gemini 格式 319 条；14 天内跨了不同版本的 schema；下文调用数因此偏低，但“0 或接近 0”的结论不受影响。实施前用三种格式重新统计。

- 29 个工具、176 个参数，工具 JSON 约 35k 字符（UTF-8 45.8 KB）；主描述 7427 字、参数描述 2682 字。**工具声明是 system 提示（7175 字）的 4.9 倍。**
- 体积最大的三个工具占 32%：`memory_change`（21 参数 / 5.2 KB / 描述 882 字，14 天仅调用 4 次）、`query_chat_history`（20 参数 / 4.7 KB / 19 处 anyOf，458 次）、`task_control`（14 参数 / 4.7 KB / 描述 1295 字，1254 次）。
- 14 天调用为 0 或接近 0：`environment_service` 0、`read_memory` 1、`recall_own_message` 1、`get_my_capabilities` 5、`subagent_start` 5。
- 只做机械清理（去掉 pydantic 生成的 `title`、`anyOf[…, null]`、`default: null`）约省 4.8 KB。

### 6.2 命名

- 动词与词序混用：`get_/find_/read_/query_/lookup_/inspect_` 并存；`search_memory` 与 `web_search`、`inspect_conversation_attachment` 与 `workspace_inspect` 词序相反；`time_get_current` 名词在前；`*_control / *_manage / *_query` 混用。
- 分派参数名有五种：`action`（task_control、subagent_control、external_agent、terminal_control、automation_manage、environment_service）、`view`（query_chat_history、automation_query、read_memory）、`operation`（memory_change、read_tool_artifact）、`mode`（get_my_capabilities）、`kind`（find_contacts）。
- 同一概念不同名：目标对象有四套结构（send 的 `{kind,target_id,conversation_id,binding_id}`、query_chat_history 的 `{conversation_id|person_id|space_id|binding_id|operation_id}`、search_memory 的 `{scope,subject_ref,display_name,person_id,space_id,space_name}`、memory_change 的 `{subject_ref,scope_type,subject_name,candidate_ref}`）；cursor 有 integer、string、uuid、数字字符串四种类型，另有工具用 offset；`task_control(wait)` 把 child_id 填进 `run_id`。
- 同义工具：子任务派生有 `subagent_start` 与 `task_control(derive)`（14 天 0 次）两条路；`subagent_control` 的 list/status/result 与 `task_control` 的 get/list 重叠；查看媒体分成两个 inspect；联系人与成员分在 `find_contacts`、`find_conversations`、`get_group_members` 三个工具。

### 6.3 参数与生产出错证据

- 万能工具的 action 多数没人用（14 天）：`task_control` 只用了 complete 351、list 337、wait 322、update 124、get 97、accept 16、resume 3、cancel 1，derive、wait_status、cancel_wait、need_input、fail 为 0；`memory_change` 只用过 create 与 invalidate；`external_agent` 的 prompt、steer、queue、respond 为 0。
- 声明但从未使用的参数：`external_agent` 9 个（含描述写着“兼容别名”的 `request_id`、enum 只有一个值的 `outcome`）、`memory_change` 8 个、`task_control` 6 个、`subagent_control` 6 个。
- 互斥与相近参数只靠文字说明，生产持续出错：
  - `query_chat_history` 同一工具里有三对前后参数（around 的 before/after、recent/search 的 context_before/context_after），模型 35 次传入不存在的 `around`（占 around 视图 117 次的 30%，11-06 仍在发生）；`target.person_id`（选私聊入口）与顶层 `person_id`（筛作者）同名不同义。
  - `search_memory` 出错 24 次：顶层误传 `scope`、`subject_ref/display_name/person_id` 三选一冲突（`services/agent_tools.py:1372`）、scope=group 未给群，返回的提示“请检查枚举及带时区日期区间”与真实原因无关（`agent_tools.py:1058-1061`）。
  - `external_agent` get 只传 instance_id 导致 `external_agent_resource_required` 22 次。
  - `task_control.conditions` 是 `items: {additionalProperties: true}`，条件种类只写在文字里；模型写过 `seconds`、`after_event_id`、`child_id`；内部字段 `context_note.version` 被模型填了 113 次。
- 错误信息模型看不懂：校验器原样输出 `target: anyOf; declared alternatives…`（`capabilities/validation.py:143-186`）；兜底分支把 `type(exc).__name__` 当错误码配“工具执行失败”（`agent_tools.py:1063,1069`、`main_agent_backend.py:325,449`），14 天内 `TurnSupersededError` 67 次（实为被新输入抢占，见连续性任务书）、`ClientError` 32 次；work-control 错误只有裸码。

### 6.4 描述

- 超长：task_control 1295 字、external_agent 897 字、memory_change 882 字；按 Diana `docs/tool-descriptions.md` 的尺度（主描述目标 150 字、上限 300；参数描述上限 120），8 个工具超限。
- 写入内部合同术语：“原执行链”“原回执”“canonical”“Binding/Presence 阶段”“generation”“history_order”“冻结”“Monty”等。
- 与 system 提示重复：send 的规则在描述、【发送】、【媒体与提及】出现三遍，“conversation_id 优先”写了 4 遍；task_control 描述与【持续工作】约 800 字大段重叠。

### 6.5 结果格式

- 通用信封 `ToolExecutionResult.model_payload`（`capabilities/results.py:69-85`）每条结果都带 `retryable`、`mutation_committed`、`provider_id`、`tool_name`，按情况还有 `request_postcondition_satisfied`、`finalize_after_commit`、`evidence_state`、`memory_grounding_policy`、`executed`、`process`；前四项平均约 90 字，占全部结果的 3.6%；`tool_name` 可由 call_id 配对，`provider_id` 是内部信息。另有 work-control（ok/works/next_cursor）与 execute_code（operations/usage/stdout）两套信封，以及 `evidence_note`、`provider_summary_instruction`、`do_not_copy_verbatim_to_user` 等固定说明句。
- `query_chat_history` 结果总量最大：平均每条 10.7k 字，每个事件约 1050 字，正文 `content` 只占 9.4%；`event_view`（`persistence/event_view.py:13-28`）有成对别名 id/event_id、source/origin、person_id/author_person_id、presence_id/author_presence_id，每个事件重复 conversation_id，null 字段照样输出。
- `send` 平均 1700 字：每个分条重复 target、presence_id、original_conversation_id、original_event_id，并回传 `delivered_text` 原文（约 11.6%）；模型需要的只有 status 和各条 event_id。
- `terminal_exec/read`：output 占 69%；`process`（`results.py:493-526`）与 `completion` 再抄 run_id/status/pending/exit_code，另有 64 位 hex 的 `request_id`、`state_sequence`、`admitted`，以及 cursor、next_cursor、output_offset 三个位置字段。
- `task_control list` 返回平台账号号码 `creator_user_id`、generation、浮点 epoch 时间戳。

### 6.6 为什么一次性重做

作者决定按激进方案重做工具面，不分批修补。依据 [开发约束](development-contract.md) §0：旧代码、旧测试和“以前为了安全”不能独立证明现有设计必要；测试不冻结布局；陈旧说明直接删改，不叠加矛盾补丁。分批改名会让工具合同连续变化三次、旧名别名散落各处，正是叠加补丁。“固定工具合同”指每次部署冻结完整清单、执行处核验、目录查询不改已提交声明，不指工具设计不可改。

硬约束是 §1、§5：原事件、执行与回执保持原事实。已落盘回执按旧工具名存储，因此保留一张**只读**的“旧名 → 新名/类别”映射供历史投影与恢复读取；旧名不再出现在模型面前。真实来源核验（证据事件、SELF 引文）不因参数简化而放宽；选择器带来的事实上的限制随选择器删除，不改写成新的授权门槛。

### 6.7 共同约定

| 项 | 约定 |
| --- | --- |
| 命名 | `动词_对象`；只读工具用 read / get / find / search 开头，其余为有效果的动作。唯一例外是 `send`：它能发文字、文件、图片与表情，作者曾有意从 `send_message` 改为 `send`，保留原名 |
| 目标 | 对象参数 `target`，恰含一个键：`person_id` / `space_id` / `conversation_id` / `binding_id` / `operation_id`，沿用现有 `HistoryTarget`（`services/history_query.py:10-27`，已在 find_conversations 与 query_chat_history 中使用，schema 自带类型）；省略为当前会话；记忆另允许 `{"self": true}`。删除 send 的 `kind/target_id`、记忆的 `subject_ref/scope_type/named_member/candidate_ref` 等变体。不做“单字符串 ID 自动判断类型”：没有现成解析器，Binding 与 Presence 同表，需要新增探测机制 |
| 分页 | 请求 `limit` + `cursor`（不透明字符串）；结果 `next_cursor`，没有更多时省略。删除 offset、native_cursor 与多种 cursor 类型 |
| 时间 | `since` / `until`，带时区 ISO-8601，until 不含；严格过滤 |
| 分派 | 只有动作共享同一组参数时才用 `action`；参数不同的动作拆成独立工具。不再出现 `view`、`operation`、`mode`、`kind` 等分派名 |
| 设备 | `device` 一律表示**源**所在电脑；写到另一台电脑用 `to_device` |
| 互斥 | 能用 schema 表达的用 schema；多来源统一写成“来源三选一”，执行处单点检查，错误码 `choose_one_source` |
| 描述 | 第一句动宾句说明做什么；只写不说就会出错的约束；跨工具流程只放 system 提示；不写内部合同术语（原回执、generation、canonical、冻结、Binding/Presence 阶段等）；篇幅以主描述约 200 字、参数描述约 60 字为写作指引，不作测试门槛 |
| 成功结果 | 直接返回业务数据，不包固定信封；不输出 null、内部 ID 别名、平台账号号码、提供者名与工具名 |
| 失败结果 | `{"ok": false, "error": "<snake_case 码>", "message": "<一句说明哪个参数、期望什么>"}`；可能已产生效果时加 `"status": "unknown"` 并说明如何查证。保留 `ok: false`，避免与业务数据中本身含 `error` 字段的成功结果混淆 |
| 异步 | 尚未完成的动作返回 `{"status": "running", "id": …}`，由对应的 read/get 工具查询；不在结果里重复抄状态 |

**结果改投影前须先迁移的内部读取**：以下位置解析模型可见的结果文本，须先改为读取 typed outcome，再改投影；并同步 `tool-results.md`（其 Artifact 路径根节点为信封 `data`、预算按 `model_payload` 计量）。
