## 1. 要做成什么

**原调用已经完成，就读取原结果；当前对象后来变了，不再反过来否定原成功。**

本次处理三处实际缺口：

| 缺口 | 当前行为 | 完成后的行为 |
| --- | --- | --- |
| F1 插件 Memory 连续修正后重入 | 原成功结果被当前 active 列表过滤，误报 `memory.not_found` | 按原 mutation 返回原结果 ID，后来的 superseded/invalidated 不推翻原提交 |
| F2 Memory 已提交、Work T3 未保存 | 已有 `memory:<mutation_id>`，恢复却返回 generic unknown | 读取原 Memory 回执，返回实际变更结果，不再次写 Memory |
| F3 原生 Agent 控制回执恢复 | steer 等无 run 操作已有领域回执，Work 恢复仍未知且缺原操作 ID | 按原请求键读取原控制回执，保留 action、operation ID 与实际状态，不再派发 |

内部 `ToolInvocationContext.call_id` 的名字同时澄清为 Host 调用键，避免误接 Provider 裸 ID。该整理服务于上述链路，不扩成全仓改名工程。

本次沿现有 Invocation、Work effect、Memory receipt 和原生 operation 完成修复。领域 ID 各认自己的实体，原事件、预算、来源和已发生效果不变。

## 2. 删除优先的做法

先删重复裁决，再补真正缺失的读取；新增代码落在已有职责内。

- 删掉 F1 的两层 active 列表成功判定，连同仅服务这两层判定的 helper、局部变量和陈旧断言一起清理。
- F2/F3 复用既有领域回执和结果投影。Work 负责把原调用接到所属领域，不扫描其他领域内部状态猜成功。
- 在 `RuntimeEffectQueries` 与 `WorkJournal.effect_result()` 的现有路径接入结果，替换不完整分派和重复包装；不把同一结论在多个分支重新计算。
- 实际有共同代码时才提取小函数。两行 hash 不为统一形式单独建抽象，纯转发包装也不因“可扩展性”保留。
- 没有来源或回执的调用如实保持未知。它只影响原调用，不成为新独立调用或 Work 结束的额外门槛。

本次不增加全局操作表、注册中心、协调器、重试器、后台对账循环、影子状态、全库 revision 或 SDK 结果快照；不新增开关、经验阈值、必须登记 Work 的入口限制。已有必要授权仍在原执行/读取边界核验，不逐层复制同一套条件。

## 4. 实施任务

### D01 删除插件 Memory 对原成功的两次重判

**修改对象**：`MemoryAdmin.correct_fact()`、`_visible_person_correction()`、Facade Memory update、`_visible_person_projection_fact()`。

1. `correct_fact()` 继续沿原 mutation 和真实调用键执行/重入。保留 `not mutation.ok or mutation.new_fact_id is None` 的实际结果判断，随后直接 `get_fact(mutation.new_fact_id)`；不再要求这个结果仍出现在当前 `list_person()`。
2. 删除 `_visible_person_correction()` 的 active 投影。核清真实调用者后删除该 helper，不能换个名字在其他层重新查列表。
3. Facade 使用上述原结果 ID，删除 `_visible_person_projection_fact()` 和对应重复读取/正文比较装配，连同仅被该 helper 使用的 `normalize_memory_text` import 一起删除；调用前的实际 owner、插件批准、当前人物资格继续由原入口负责。
4. 清理“找不到 active 结果即不属于当前用户”的错误解释。真实不存在、当前不可读与原操作未成功各按其现有事实返回，不拿其中一个替代另一个。

**结果边界**：已知原提交与当前正文展示分开。普通 superseded/invalidated 不是原调用失败；隐私删除后不能恢复正文。无需保存一份冻结 SDK JSON，也不强制 add 返回过去的 active 状态。

这里保留现有 `get_fact` 已足够，不要求另改 `_mutation_fact()`。后者既会 fallback 到 `old_fact_id`，默认缺对象又会报“记忆变更未提交”；无条件复用可能把拒绝当成功，或否定后来清退的原提交。

`correct_fact()` 的另一个真实消费者是 `services/commands/memory.py` 中的 `/ai memory correct`。删除 helper 中的 Person-only、当前列表和正文二次判断，不在入口补回同样门槛；管理员原本获准的 Group/SELF 修正也应返回真实结果。SDK 自己的 `person_owns_fact` 范围保持原样。此处非 Person 误报由源码确认，尚未进行新的动态复现，实施时用获准命令场景验证。

**验收**：同可信 callback 的 `add -> update1 -> update2` 按原顺序重入，分别认回原结果 ID，无新事实版本；`add -> delete` 维持原效果。旧结果被后续修改、失效不会变成 `not_found`；真正删除/撤权不泄露正文或获得新写入权限。

### D02 复用原 Memory receipt，补齐 Work 的结果读取

**修改对象**：Memory 原回执 repository/结果投影、`RuntimeEffectQueries`、`WorkJournal.effect_result()`。

1. 从原 effect 中取已持久绑定的 `memory:<mutation_id>`。领域读取使用原调用身份与既有 receipt 寻址；优先复用 `find()` 和原幂等编码，核取回的 mutation 与绑定引用一致。
2. 如果沿已保存 mutation ID 读取能减少准备与参数转换，就在原 receipt repository 内增加这一查询能力；不为它增加表、索引迁移、owner 对象或多套并行查找顺序。最终保留一种直接的读取路径。
3. 使用 `MemoryMutationResult.from_receipt(receipt, deduplicated=False)` 保原 outcome。这里读取原提交，不把全部已知结果改成 `DEDUPLICATED`；不改变现有 mutation 重入自己的去重语义。不重新解析原模型输出、重建完整变更请求或重新核一遍事实当前 active 状态来猜结果。
4. 在现有 Work 领域查询处接入结果。沿原 Work/effect/ref 关系和既有来源读取规则返回允许披露的事实；匹配关系在实际消费边界核对，不把同一验证散布到每层。
5. 恢复读取只开 reader。没有 receipt、processing 或真实归属不匹配，沿原未确认/拒绝语义处理，不补写成功，不重新调用 `mutate()`。

**结果边界**：`committed`、`committed_as_contested`、`no_change`、`rejected` 等由原领域结果解释。已知拒绝不是未知；无变化也不是“重新执行一次试试”。领域结果和 `executed / mutation_committed / uncertain` 必须一致，不能把所有已找到的行都设为成功。

工具侧已有 `agent_tools._memory_change_result`。需要共享其中的纯字段投影时，将该段移到所属领域并让原工具也使用它，删除原副本；不在 Runtime 手抄第二份结果结构，不为一次读取装配完整 Main 工具后端。

**验收**：实际 T1/T2、领域 commit 完成而 Work T3 尚未保存的持久状态，经原恢复入口返回原 mutation、结果 ID 和实际状态；原事实/变更不重复新增，原调用不重复扣预算，原已付请求不重买。配对、检查点保存与后续合法请求沿原合同继续。来源/引用不匹配与缺回执不串账。当前 fact 被后续修正不影响原效果判定。

### D03 复用原生操作查询，补齐无 run 控制回执

**修改对象**：原生 operation 本地查询/结果投影、`RuntimeEffectQueries`、`WorkJournal.effect_result()`。

1. 对原 `external_agent` effect，沿既有 `sha256(effect_key)` 请求键读取所属 operation；历史编码原样保留。不因没有 SandboxTaskRun 就认为没有领域回执。
2. 公开 `AgentRepository.operation()` 保留原鉴权和 id/run_id 查询用途。历史恢复在同一 repository 精确读原 operation ID，按原 Work/action/持久 actor/source 认归属，不把 `authorize -> require_person` 的今日有效人物条件变成否定原效果的门槛。
3. 将 `_view` 已有本地投影移到原领域可共用的位置，公开服务与恢复都调用这一份，删除纯投影旧副本。#502 新增的当前连接在线判断仍由公开服务的薄包装负责，历史 reader 不调用连接对象；保留持续监督的当前 execution 投影和已提交拒绝结果。复用实际 repository/session，不为这份投影构造含连接器等依赖的完整 ExternalAgentService，也不复制公开 `_get/execute` 链。
4. 恢复读取不联网，不查询设备当前执行来覆盖原控制结果，不为 steer/respond/cancel/detach 伪造 SandboxTaskRun。读取已有回执不要求新租约、当前设备在线或再次批准执行。
5. 原 Work、actor、action 与领域来源按实际保存关系核对，不取当前活跃用户或反查今日账号来补来源；归属不明就不借其他操作证明本次成功。向调用方披露内容仍遵守实际读取/隐私规则，新效果继续核当前授权；设备离线、人物后来停用、执行结束不改写已确认事实。
6. 返回实际 operation/request ID、action、状态和已有 session/execution/run 关系。记录存在但未确认时保留未知与原定位信息；记录不存在时不凭可计算的 ID 伪造已接纳操作。

**结果边界**：steer 被接纳不代表原生任务完成；cancel 成功不代表原任务成功；detach 解除关系不代表执行停止。模型可见结果与 Work 的效果事实同时保留这种区别。

本次使用现存确定性关联即可读取历史操作，不增加新的 `original_domain_ref` 写入协议作为先决条件，也不批量回填旧数据。后续出现现有关系无法表达的真实需求，再按该事实讨论。

**验收**：steer/respond/cancel/detach 分别以符合动作合同的回执验证；原领域已确认、Work T3 前中断时能读原结果。pending、unknown、缺失和真实归属冲突分别保持实际状态。读原回执不重新派发、不重复扣预算或新增 run；原任务随后仍可按真实授权继续独立新操作。原 prompt/queue/watch 的 run 恢复保持原行为。

### D04 在原恢复链收口，删除重复的结果解释

**修改对象**：`RuntimeEffectQueries`、`WorkJournal.effect_result()`、已有 `recorded_result/historical_evidence` 消费点。

1. D02/D03 共用现有查询对象与 runtime 依赖。分派只需表达当前真实领域，保留 Social/Sandbox 原行为；不做 provider 式注册、动态插件查找或通用生命周期框架。
2. 已 accepted 且保存完整结果的 Work effect 继续返回原件；补领域读取用于实际缺结果的恢复窗口，不覆盖已保存正文、媒体配对或 Provider 协议。
3. Work 的 `prepared` 在 T2 后仍可能同时带 `dispatch_started=true`。恢复必须认原派发事实和领域回执，不因 state 字面值把已派发当未派发。
4. 从原领域结果投影到既有恢复事实。替换当前仅按 Social 的 `status in {succeeded, accepted}` 包装结果的假设；Memory 认原 outcome，Native 认原控制结果，Social 保原分步事实。核模型收到的结果以及 `current_result_capture` / `historical_evidence` 消费，删除被这条路径替代的重复状态推断或包装，不另建通用成功状态机。
5. reader 本身不改原 effect、领域回执或根预算，也不续租、接纳新 Work、调模型、恢复 VM 或重新发送。读回结果后，原 Runner/Code/worker 按既有授权继续正常工作；不把纯查询边界变成停止原任务的限制。跨表必要读取沿已有 reader/session 传递，不为读回结果抢 writer。

**验收**：至少在真实 Main/Work 恢复消费处验证 D02/D03，不只测查询 helper。direct 与 Code child 使用各自原调用键，worker 保原 child Work 和根预算；只读结果投影不能丢来源/隐私信息或把控制成功当目标完成。

### D05 小范围澄清 Host 调用键

将内部 `ToolInvocationContext.call_id` 改为 `invocation_key`，同步唯一生产构造及真实访问点；局部变量名称随用途调整。它表示 `InvocationIdentity.operation_id`，不表示 Provider 裸 call ID。

基线范围为 `capabilities/invocation.py`、`services/main_agent_backend.py`、`services/agent_tools.py`、`automation/creation_key.py`、`workspace/service.py`、`social/agent_adapter.py`、`plugin_host/facades.py`，以及实际构造该内部对象的测试。

不新增旧名 property、双字段、兼容 DTO 或转换状态。Provider `call_id`、Social/SDK 字段、持久 `invocation.operation_id`、Code 的父子 metadata 和公开响应保持原合同。新增名字不影响任何 key 的字节编码。

特别保留 `_fingerprint({"operation_id": key})` 的 JSON 字面字段名；它参与旧幂等 hash。内部改名不能改变此字面量或原 hash 参数顺序/编码。

**验收**：静态检查真实消费者和构造点完整；同一输入生成原 key/指纹，旧回执仍可读。此项无需复制一套业务测试或以全仓 grep 零 `call_id` 为完成条件。

### D06 同步文档与测试，移除旧规则断言

实现时同步 Main/Tool Kernel、Memory 变更、插件 Facade 和原生 Agent 对应合同。说明原回执与当前展示的区别、Host 键与领域 ID 的区别，以及恢复读原记录的真实路径。技术说明留在模块文档，不加入人格或模型提示词，不改工具声明。

研究探针按真实行为并入现有测试模块，复用 fixture；原生探针现在通过是因为它断言“存在 unknown 缺口”，实施后必须换成正确结果断言。删除固定 active 过滤、重复投影或旧错误返回的断言，不靠新增兼容分支维持旧测试。

研究附件保留固定基线证据，不改成一份假装修复前就通过的记录。实施记录引用实际代码提交、测试命令和结果，不将旧调研的通过数重复计入新版本验收。

## 5. 保留的事实与职责

| 保留项 | 原因 |
| --- | --- |
| 原 Person/Conversation/event、执行与 Work ID | 真实主体、来源和承诺，不由当前账号/平台号重建 |
| `InvocationIdentity`、原 chain/sequence/provider call | Main/Code 已统一，恢复仍需原协议配对 |
| Social 父子回执、文件/附言/配图状态 | 一个调用可以产生多项真实效果，不能合成一个总成功 |
| Memory mutation/fact/Dream operation | 请求、变更、事实版本与后台整理是不同实体 |
| Native operation/session/execution/run | 控制请求、资源和 Work 等待/监督关系不同 |
| #500 前旧事件级 Memory 回执 reader | 真实历史消费者仍在；不能猜它属于哪个逐调用或补跑 |
| 原授权、隐私清退及同 ID 参数冲突 | 核真实来源和效果，不能因删重复状态判断一起删掉 |
| T1/T2/T3 与累计预算 | 未派发、已派发、未知及确认必须按原事实解释 |

不改直接/子调用 ID 算法，不删除 WorkSession 的确定性原键编码，不让 Code lifecycle 再走一次准入；首次 accept 建立 owner 的既有事务不重做。

后台自省的 run/result index、自动提取的同源 claim 指纹、Dream 的 run/preview/operation 保留。自动提取去重不等于 Main 两次同正文调用去重，不把不同职责机械统一。
