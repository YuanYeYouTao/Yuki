## 2. 已确认修复项

### F01 / P1：原生协议保留尾被统一压缩计划拒绝

**首次引入：#423；#427 最终版本仍存在。**

位置：`src/qq_ai_bot/services/context_compaction.py` 的 `execution_compact_plan`，最终基线 371–381 行；#423 head 对应 327–337 行。

函数寻找实际 Main 的已配对前缀，但只允许保留尾包含 `ChatMessage`。尾部含 `ProviderContinuation` 或 `FunctionCallOutput` 时，整个候选被跳过。普通 Chat 的等价回合可以生成压缩计划；Gemini 的真实工具回合却直接报 `WorkCapacityError("model_request_capacity")`。请求已经有 continuation 时，公共 P 的 eligibility 也不成立，无法靠公共压缩补回此缺口。

**实际复现：** 使用现有 `GeminiProvider` 和离线 HTTP transport 完成两个工具响应，保留其实际生成的 continuation、签名和调用 ID，再追加真实形态工具结果。没有调用外部模型。

| 项目 | 本地统一估算 / 结果 |
| --- | --- |
| 输入预算 | 10,476 |
| 当前完整 Gemini 请求 | 14,861 |
| 已配对旧前缀加 compact 指令 | 8,976，可容纳 |

这里的数字是同一 Host 估算器的受控样本，不是 Provider usage 或生产命中率。

**最小修复方向：** 在统一 compact 入口处理合法原生协议切面，复用已有业务恢复中对未观察回执的处理。新窗口保留必要的真实结果、调用 ID、效果键、原 owner 和来源；原 opaque、签名、已付请求及回执仍保存在不可变 journal/ProtocolStore 中。

不得仅按 Gemini 名称增加特判；当前类型判断也服务其他带 continuation 的协议。不得仅删除类型判断后把旧 opaque 直接搬到新链，不补造 function response，不重新执行旧调用，不把私有结果发布到公共检查点。

**验证：** 实际 Gemini、Responses 与现有其他 continuation 适配器的离线序列化；旧前缀可容纳、最新未观察结果可容纳而合计超容量的工具链；原调用配对、签名原件、恢复、预算累计与效果键；等价 Chat 回归。分别报告已验证协议，不能由一条 Gemini 用例推断其他协议已经通过。

### F02 / P2：缓存删行同时删除公共 compact 检查点

**首次引入：#424 将唯一检查点所有者迁至投影表；#427 最终版本仍存在。**

位置：`src/qq_ai_bot/conversation/scope_repository.py:128–140`；与既有 `src/qq_ai_bot/conversation/projections.py:337–385` 的缓存回收组合触发。

公共检查点只从 `prompt_projections.selected_summary_*` 读取。现有缓存先清空原文并标记 `capacity`，随后仍会按预算或缓存标记数量删除整行。Rollup 退役后，删掉这一行也删掉唯一公共检查点，读取回到 `starts_after_event_id`，已覆盖群史重新成为原文输入。

**实际复现：** 原会话保存检查点、coverage=1；依次发布其他会话的投影。缩小缓存配置和默认 `maximum_views=128` 均复现。默认配置发布第 257 个会话后，原检查点为空、coverage=0，事件 1 重新进入 raw input。来源未变、generation 未变、没有隐私删除。

这会使有效输入前缀退回旧原文；旧群史超真实容量时将再次触发付费压缩。不是原件丢失，但违反已采用公共窗口的持续接续与缓存要求。

**最小修复方向：** 每个 Conversation 保留当前检查点及其来源信息，缓存淘汰只清理可重建原文 payload。删除会连带有效检查点整行清退的二次回收路径，继续使用既有列和 owner，不另建缓存服务、摘要表或恢复协调器。

**关联复现 F02-b：只保留行还不够。** `PromptProjectionRepository.read` 的 104 行仍用 `invalidated_reason IS NULL` 过滤缓存。`current_public_compact`（`context_compaction.py:169–181`）通过这一接口寻找较新检查点。原文缓存被标记 `capacity`、检查点仍合法且仍在行内时，reader 返回 None，旧已付响应因此覆盖较新的检查点。受控复现中 coverage 从 2 回到 1，`Later adopted checkpoint` 被替换成 `Older paid checkpoint`，恢复生成的 items 为空，事件 2 随后重新成为 raw。来源和 generation 均未变化。

修复须同时区分**原文缓存是否可用**与**持久检查点是否有效**。恢复应读取经原 generation/source/privacy 验证的当前检查点，较旧已付响应不能因 payload 淘汰而回退它。复用现有列及有效来源读取，不通过保留失效正文绕过隐私或来源核验。

后续组合复核补充确认：两份付费结果覆盖点相同、较新一份已经采用时，旧结果也不能替换已采用正文。回归分别覆盖“覆盖点更大”和“覆盖点相同而正文不同”；读恢复沿已采用结果，writer 按同一来源与实际已采用内容核对，不依赖时间阈值或额外版本表。

重置、来源修改和真实隐私删除仍沿原合同使检查点失效；不能让已失效正文重新参与请求。固定系统/工具与 checkpoint 之后的原文追加保持原顺序。

**验证：** 默认与受控小缓存的淘汰、标记清理、字节预算路径；冷启动、跨 actor/入口回访、原文缓存淘汰后的较旧付费 response/paired 恢复；有效 checkpoint/coverage 不丢、不回退，已覆盖原文不回流，不重新购买相同范围的摘要；隐私/reset/source revision 回归。缓存资源断言只约束可重建 payload，不把当前检查点生命周期冻结为缓存行数量。

### F03 / P1：不能回收的保留尾驱动重复 compact

**首次引入：#423；#427 最终版本仍存在。**

位置：`turn_execution.py:979–997,1210–1215` 与 `execution_compact_plan` 的保留尾选择。后置容量失败只覆盖“没有 retained 且不是公共 P”的情况；有 retained 时，外层循环继续压缩。

**实际复现：** 已配对 Chat 工具结果的原样保留尾自身超过 4096 输入预算；较早的小段执行记录可以总结。FakeProvider 每次返回相同的短检查点，真实工具结果始终保留。当前实现连续派发 3 次逻辑 compact，最后返回 `<stop>`，退出原因仅是样本配置的 3 次分段预算。未派发正常 Main 请求，没有任何真实外部模型消费。

这不是要求摘要必须缩短某个比例，而是所选保留部分已经不可能进入真实容量。不断总结它前面的小检查点不能解决容量问题；真实模型路线会为这些无益调用付费。原预算仍是有效预算，不得删掉预算来掩盖该循环。

**最小修复方向：** 选择实际可替换范围时，一并核对固定部分与原样保留尾能否进入本次真实预算。无法形成合法可容纳窗口时，调整可替换范围或准确返回容量原因；不要再次购买相同无效切面的摘要。保留原工具结果、引用和回执，不能通过截断原件或伪造已观察来通过容量检查。

不新增“最多 compact N 次”“摘要至少缩短 X%”“连续两次无进展即失败”或新的软水位。需要退出的是已证明不可容纳的实际输入，不是正常部分成果或暂未完成的任务。

**验证：** 不可容纳单条回执、固定初始资料过大、可容纳原文尾、正常多批公共压缩、私有有效换窗；原显式预算计量不重置，不重复购买无效整理，不增加压缩率门槛。

### F05 / P2：公共压缩切点搜索同步反复处理长前缀，工作量呈平方级

**首次引入：#423；#427 最终版本仍存在。**

位置：`context_compaction.py:252–267` 的 `public_compact_plan`。每次从末尾退一个片段，都重新 `FrozenFragments.load`、构造完整 messages 并序列化估算此前所有片段。

**实际测量：** 使用 2048 的受控输入预算和等长合法冻结片段，最终覆盖点都为 20。

| 原片段数 | 容量估算次数 | 累计参与序列化的消息数 | 本机耗时 |
| ---: | ---: | ---: | ---: |
| 256 | 237 | 33,180 | 0.524 s |
| 512 | 493 | 132,124 | 2.170 s |

来源翻倍，重复处理量接近四倍。耗时只说明本机受控样本；算法结构和序列化工作量证明其平方级增长。此同步路径在 async Main 中运行，会占用事件循环，削弱“其他会话继续工作”的目标。

**最小修复方向：** 复用同一真实容量估算器，在公共纯消息前缀具有单调性的切点上用单调搜索或一次累计准备选取最后可容纳的完整片段。避免逐个候选重复深拷贝和全前缀序列化。不要加固定历史条数上限、切掉来源、缓存保温或另一套摘要预算；原生 E 的 opaque 切面不能在未证明单调性时直接照搬 P 的算法。

**验证：** 相同最后合法切点、整条事件不拆分、当前触发和私有资料不入 P；不同来源规模的准备工作量与事件循环让出。报告复杂度及实际耗时，不用本机固定秒数或某个调用总数作为业务完成门槛。

### F08 / P2：原 journal 的来源重核仍有“一次”经验上限（现行遗留）

**不是本批新增；当前 main 和组合版本均存在。** 位置：`work_session.py:963,1011–1025` 的 `source_rechecked`。

原纯数据库发布因 `work_journal_source_changed` 回滚后，源码允许重新验证一次；第二次来源 revision 竞争即直接拒绝，不再核验原选择是否仍合法。

### F09 / P3：系统执行约束统一使用 Compact 检查点术语（本地已修）
