## 2. 现状要点【实证】

### 2.1 代理的配置与创建

- Manager 读 `YUKI_SANDBOX_PROXY`（`manager.py:98`），`PersistentManager` 保存为 `self.proxy`（`persistent.py:118`），只在 `docker create` 时写四个变量 `HTTP_PROXY/HTTPS_PROXY/http_proxy/https_proxy`，值相同（`persistent.py:745-749`）。未设置时写空值，用于覆盖旧检查点镜像里残留的 Squid 代理变量。
- `ALL_PROXY`/`NO_PROXY` 不由 Manager 写，`NO_PROXY` 来自环境镜像（`Dockerfile.environment:33-34`）。
- 已有容器不随 `.env` 改变；`environment_status.recreate_required` 只比较环境文件挂载、`/tmp`、`/dev/shm`（`persistent.py:635-643`）。重建环境的现有入口：整机快照后还原（任何来源）、升级时缺环境文件挂载的自动快照重建（`environment_snapshots.py:714-760`）、容器丢失后从检查点重建。三者都按当前设置创建新容器，都保留 HOME、已装软件（rootFS 来自快照）与原执行回执，已派发的执行记 `environment_restored` 或 `environment_recreated`，不重放。

### 2.2 防火墙

- 环境在 `yuki-egress0` bridge 上。`network_guard.apply` 在 Docker 实际使用的 iptables 后端中：`INPUT -i yuki-egress0 -j DROP`，只在它上面放行 execd 的回应（`network_guard.py:51-60`）；`DOCKER-USER -i yuki-egress0 -j YUKI-EGRESS`，该链丢弃 `PRIVATE` 中全部非公网段，包括 fake-ip 段 `198.18.0.0/15`（`network_guard.py:15-30, 61-67`）。
- 因此代理只要在宿主上（经 bridge 网关或宿主任一地址，走 INPUT）、在局域网或 Colima、Docker Desktop 的宿主网关地址（走 FORWARD），都被丢弃。只有公网地址上的代理今天能用。
- `apply` 在每次 `recover()` 里执行（`persistent.py:499-518`），即每次 Manager 启动和每次重建。

### 2.3 生产形态（2026-11-23 只读）

- Mac 上 Colima `yuki` VM：Compose 项目 `yuki-local`，`manager`、`bot`、`snowluma` 与 Manager 创建的 `yuki-environment`。
- Manager：档位 `desktop`，运行时 `runsc`，`YUKI_SANDBOX_RESOLV_CONF` 已设置，**`YUKI_SANDBOX_PROXY` 未设置**；环境容器的四个代理变量均为空，网络只有 `yuki-sandbox-egress`。
- Bot 容器的 `HTTP(S)_PROXY` 指向 Colima 的宿主网关地址（私网段）。该地址在环境防火墙的丢弃范围内，即使把同一地址写进 `YUKI_SANDBOX_PROXY` 今天也连不上。
- 【推断】生产环境出网走 Mac 上的透明代理（TUN）：环境用 HOME 内的 resolv.conf 指向自己的 DNS 服务以避开 fake-ip（见 #678 与 `persistent-environment.zh-CN.md:83`）。本次未进入环境实测出网。

## 3. #509 方案

### 3.1 原则【决定】

- 配置入口不变：`.env` 的 `YUKI_SANDBOX_PROXY`，改后 `docker compose up -d`，与档位、资源、快照设置同一处。空值即停用。不加 Admin API、Desktop 页面或数据库配置（Q4）。
- 不另建代理服务、节点池、自动切换、健康轮询或后台循环；不自动复用 Bot 的 `HTTP_PROXY`（Q3）。
- 代理凭据可以写在 URL 里，环境内的程序本来就需要它；Manager 的状态、日志和检测结果只给出去掉凭据后的 `scheme://host:port`。

### 3.2 放行配置的代理端点（实施 PR）

- Manager 启动时解析 `YUKI_SANDBOX_PROXY` 的主机与端口（缺端口时 http 为 80、https 为 443），在 Manager 所在的宿主网络里解析为 IPv4 地址。
- `network_guard` 增加一条 `YUKI-PROXY` 链，每次 `apply` 清空重填：配置了代理时只有 `-d <地址>/32 -p tcp --dport <端口> -j ACCEPT`；未配置时为空。`INPUT` 与 `DOCKER-USER` 各在第 1 位跳转一次（`-i yuki-egress0 -j YUKI-PROXY`），位于原 DROP 和 `YUKI-EGRESS` 之前。原有规则、顺序和"公网不按端口限制"不变。
- 这一个端点之外，宿主、私网和 fake-ip 段仍全部丢弃；停用后链为空，回到今天的隔离。代理只需监听宿主上环境可达的接口（bridge 网关地址或局域网地址），不需要向公网开放。
- 名字解析失败不阻止 Manager 启动：状态报告 `proxy.firewall_error=proxy_unresolved`，检测按真实结果失败。

### 3.3 保存值与实际值

- `environment_status.proxy`：`configured`（`.env` 值，去凭据）、`environment`（当前容器实际变量，去凭据）、`allowed`（放行的 `地址:端口`）、`firewall_error`、`check`（最近一次检测，见 §3.4）。
- 两者不同时 `recreate_required` 列出 `proxy`，与 `/tmp`、`/dev/shm` 一致。
- 应用方式沿现有重建：拍一份整机快照并还原它，新容器按当前设置创建；HOME、已装软件和原回执保留，在途执行按 `environment_restored` 结束、不重放。是否改为像环境文件那样在 Manager 启动时自动快照重建，见 Q1。
- 已在运行的进程不换变量。重建即重启整个环境，所以重建后终端、服务、`rc.local` 和浏览器都是新进程；交互 TTY 会话与后台服务属于被中断的执行，按原回执处理。

### 3.4 从沙箱内检测（实施 PR）

- Manager RPC `environment_network_check`（参数可选 `url`，默认 `https://deb.debian.org/`）：Manager 用 `docker exec` 在环境里运行 `curl -s -o /dev/null -m 20 -w '%{json}' <url>`，使用环境的实际变量，不另传代理。结果写入 Manager 状态库（`environment_state`），`environment_status.proxy.check` 返回最近一次。
- 运维入口：`docker compose exec --user 10001:10001 bot yuki setup environment-check --network [--url URL]`。不进入安装器默认流程（无外网的环境不应因此安装失败）。Yuki 自己在终端里用 `curl` 即可，不新增模型工具（Q5）。
- 分段（由 curl 的退出码、`http_connect`、`http_code` 判定）：

  | `stage` | 含义 | curl 事实 |
  | --- | --- | --- |
  | `ok` | 拿到目标的 HTTP 响应（附 `http_code`） | 退出码 0 |
  | `proxy_unresolved` | 代理名字在环境里解析不了 | 有代理，退出码 5 |
  | `proxy_unreachable` | 连不上代理（拒绝、被防火墙丢、超时） | 有代理，`http_connect=0`，退出码 7 或 28 |
  | `proxy_refused` | 代理拒绝 CONNECT（如 407、403） | `http_connect` 为 4xx 等非 200、非 5xx |
  | `proxy_upstream_failed` | 代理连不上目标或其上游节点 | `http_connect` 为 5xx |
  | `remote_failed` | 隧道已建立，TLS 或目标失败 | `http_connect=200`，退出码非 0 |
  | `dns_failed` | 未用代理，目标名字解析失败 | 无代理，退出码 6 |
  | `direct_failed` | 未用代理，连接或目标失败 | 无代理，其他非 0 |
  | `proxy_failed` | 有代理但不属于上面任一情况 | 其余 |

  结果同时附原始 `exit_code`、`error`（curl 原文）、`http_connect`、`http_code`、`remote`（实际连到的地址）和 `proxy`（去凭据），不把分段当成事实本身。
- 只有 https 目标能区分代理与目标两段；http 目标经代理时由代理直接转发，`http_connect` 恒为 0。

### 3.5 覆盖范围（写入文档）

- 读标准变量的程序走代理：curl、wget、apt（http/https 源）、pip、npm、git（https）、Python `urllib`/`requests`/`httpx`、Chromium（无桌面环境配置时按变量）。
- 不走：直接开 TCP/UDP 的程序（ssh、数据库客户端、DNS、ping）、忽略变量的程序；`ALL_PROXY`/SOCKS 不由 Manager 设置。HTTP 代理变量不等于全部流量走代理，这些连接仍按防火墙规则直连公网。
- 目标在 `NO_PROXY` 内（localhost、127.0.0.1、::1）时直连。

## 6. E2E 验收与产物

扩展现有 `scripts/sandbox_compose_e2e.py`（CI `sandbox-compose`，runc 与 runsc 两路），在已经装好浏览器的最后阶段加 `proxy` 阶段：

1. 在 CI 宿主的 bridge 网关地址上起一个最小 HTTP CONNECT 代理（脚本内置，记录每次 CONNECT 的目标与结果；目标连不上回 502）。
2. P1：未配置时经该端口检测，`proxy_unreachable`/超时；同一宿主其他端口超时。
3. 写 `YUKI_SANDBOX_PROXY` 并 `up -d manager`：P5 状态。
4. 快照并还原：P6 状态与文件保留。
5. 检测 `ok`，代理日志出现 `deb.debian.org:443`；终端 `curl`、`pip download` 一个小包、一次后台服务的 `curl`、浏览器打开 `https://example.com`，代理日志分别出现对应目标（终端、包管理、后台服务、浏览器分别记录）。
6. P2：宿主其他端口（22）仍超时。P11：检测 `https://127.0.0.1:9/` 得 `proxy_upstream_failed`。P8：停掉代理后检测得 `proxy_unreachable`。
7. P13：清空设置后 `YUKI-PROXY` 为空，代理端口重新被丢弃，`recreate_required` 含 `proxy`。
8. P14：全部状态与检测结果中不含测试凭据字符串（测试代理 URL 带一个假的 userinfo）。

产物：`test-results/sandbox-compose/proxy.json`（每步的状态、检测结果、代理日志）与代理自身日志 `proxy-log.txt`；CI 上传为 `sandbox-compose-<runtime>`。可在任何带 Docker 的 Linux 宿主按脚本文档串复现。

单元层只补防火墙规则顺序与清理（`tests/unit/test_terminal_environment.py` 的 `Firewall` 假后端）和分段判定，先写失败用例再写代码。

## 7. 不做什么

- 不做 Admin API、Desktop 代理页面、数据库中的代理配置。
- 不做代理节点池、自动切换、健康轮询、定时检测或失败后改直连。
- 不让 Bot 的 `HTTP_PROXY` 隐式传给环境。
- 不设置 `ALL_PROXY`、SOCKS 或透明代理，不改 DNS。
- 不为代理单独改变已有的宿主/私网隔离范围，不开放整个宿主或整个私网段。
- 不在运行中的进程里热换变量。
- #524：不新增命名预装组合、不按 digest 固定镜像、不新建并行环境调度。
