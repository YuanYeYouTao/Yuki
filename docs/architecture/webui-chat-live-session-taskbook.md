# WebUI 聊天时间线与当前执行视图任务书

本文记录 2026-09-28 的新增反馈；用户已确认下述交互方向并授权开发、PR、合并与上线。每项只有在实现、针对性测试和页面核对完成后才标为“已完成”；PR、合并和生产验收分别记录。旧的 WebUI 可用性清单 U01/U02 对一般信息列表仍成立，聊天时间线以本文的专门要求为准。

## 已核对的现状

- `Chat` 固定请求最近 40 条，而不是把整段聊天正文一次传到浏览器；但它使用编号页，且把 40 条按时间倒序渲染。会话消息多时，编号页的 SQL 查询还会计算同一筛选范围的总条数。卡顿是否由 COUNT、媒体/头像请求、React 渲染或其他因素造成，实施前需测量，不能把“全量传输”直接当成已证实原因。
- `list_chat_events` 已有绑定会话及筛选条件的游标能力。可从末端取最近一段，按内部 `chat_events.id` 向过去查询，再在时间线中正序呈现，无需新建第二套聊天账本。
- 聊天气泡头像的 CSS 将图片设为 `object-fit: contain` 并加 `padding: 7px`，造成方图缩在圆形框内；统一头像基础样式已使用 `cover`，这里有局部覆盖。
- “现在的 Yuki”目前是版本、会话数、入口数、待重启配置数；“运行状态”是全局组件健康表。这些不能回答所选会话此刻在执行什么。现有执行轨迹有 `conversation_id`、`turn_id`、`operation_id`、`work_id`、`execution_id`、`source_event_id` 和投递关联；前端仅在手动刷新或换查询时读取，没有实时订阅。
- 聊天气泡的“查看本轮”目前只把入站 `source_event_id` 或出站 `delivered_event_id` 交给执行轨迹列表，随后显示步骤行，并非直接打开确定的完整轮次。没有轨迹、一个事件关联多个轮次、跨会话发送、诊断过期等情况需要明确呈现，不可把空列表称作“本轮”。

## 已确认的交互方向

### 聊天与活动

选择会话后只取最近一小段消息，画面落在底部；画面顺序是旧消息在上、新消息在下。向上滚动接近顶部时按游标取更早的一段，插入顶部并保持原可见消息的位置。聊天不显示页码、总页数或跳页框。切换会话、筛选或定位事件时，重建该会话的有界时间线；历史浏览中出现新消息时提示有新消息，回到底部后继续跟随。时间筛选和按内部事件 ID 定位保留，但应作为“跳到指定位置”的入口，而不是倒序搜索结果页。

时间线顺序以稳定的 `chat_events.id` 账本入账顺序为准；`occurred_at` 显示原事件时间，不重排迟到事件。这样游标翻阅与已入账事件身份一致，不会因原事件时间回跳而重复或漏读。

请求和 DOM 都须有界：服务端使用游标和 `limit`，不为聊天执行编号页 COUNT；客户端对长时间上滑采用列表虚拟化或等效窗口化；图片、头像和执行详情按需加载。测试应覆盖连续上滑、消息到达时的滚动位置、筛选/会话切换、长文本/图片造成的高度变化以及窄屏。

### “现在的 Yuki”

建议把概览里同名的全局指标改为“所选会话的 Yuki 执行现场”，并在聊天页提供同一会话的入口：显示此刻是否有实际运行，运行来源和开始时间，当前模型请求/工具调用/等待外部结果等可证实步骤，以及该轮已完成步骤和结果摘要。无运行时显示“当前没有执行”，并可折叠查看最近一次完成的轮次；不拿版本号或组件健康冒充会话状态。原系统健康信息可保留在独立的系统/运维区域。

当前诊断轨迹能供事后回看，但不保证每一步在进行中都有可查询记录，也不能仅凭一条未配对的开始轨迹断言进程仍在运行。实施前应逐点核查原 Runner、Work、模型和工具回执的记录时机；以原执行 ID 和持久回执为准补足只读现场投影。对失联、取消、诊断过期或无法判定的执行明确显示证据不足。不要新建并行执行状态机，也不从诊断记录恢复或重放工作。刷新机制可采用有节制的轮询/增量查询，是否需要推送以端到端延迟和现有服务结构决定。

### “查看本轮”

按钮只在有可信关联时叫“查看本轮”，打开确定的 `turn_id`，按实际执行顺序呈现模型请求、工具调用与结果、投递回执；可从某步展开原诊断详情。入站事件可关联零个或多个轮次，出站事件先经已核验的 `delivered_event_id` 找到实际轮次；跨会话投递显示原执行会话。多个轮次要列出选择，零个轮次要解释“未触发执行 / 记录已过期 / 关联缺失 / 查询中”，无法区分时不要编造原因。若只有单条事件信息，则按钮改为“查看事件”，不得继续宣称可查看本轮。内部身份始终是 `chat_events.id`，不按 QQ `message_id`、正文或时间猜测。

## 追加核查：路由代数（独立于 WebUI）

用户询问群主动发送、群接入与人物路由的“代数”为何不同，明确要求先解释、不修改。现行架构为 Person 主动发送、SpaceBinding 接入、Space 主动发送分别保存 `route_generation`：各条路由创建时为 1，只有该路由的目标、Presence 或暂停状态变化时增加；`revision` 也随该行变化。前者用于运行时旧路由失效围栏，后者用于管理编辑的版本比较；两者目前通常数字相同。它们不是 `/ai new` 推进的 Conversation generation，其他群/人物的数字不要求相同。截图里的数字差异本身不是异常。

## 已确认范围

“现在的 Yuki”始终跟随页面当前选择的会话；有执行时优先显示正在进行的轮次，无执行时显示空闲和折叠的最近一次轮次。工具参数、结果和当轮提示词在展开后可查看，首屏只放步骤摘要；Provider 未返回的思考不推测或补造。
