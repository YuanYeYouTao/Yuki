## 0. 约束（所有者 2026-11-23，不在本书重新讨论）

- 不恢复每条消息的相似度检索注入；细节记忆仍用 `search_memory` 按需取。
- 记忆层只放在 system 消息尾部的稳定前缀。当前消息最多带极小的增量，例如当天新记下的经历。
- 只给少数选定的人物放常驻内容；群里的人物记忆按群稳定选定，不按发言人逐条注入。
- 常驻层按易变程度分层：规则 → 人物核心 → 经历索引，层间放缓存断点。每层最多每天随一次 Dream 批处理变化，所有者明确要求时立即变化。目标是一段连续对话里不变。
- 常驻层是现有事实的核心集合视图：在少数事实上做 core 标记，由确定性渲染器绘制。Dream 不写散文文档，只负责合并重复与维护标记。
- 私聊来源的事实永远不进常驻层。是否私聊来源由证据判断：`memory_evidence` → `chat_events.scope_type`。
- 数据库：每轮渲染的语句数为常数；后台走索引范围扫描，不全表扫描 `chat_events` 或 `memory_facts`；写事务只做短的主键或索引写；新查询都跑 `EXPLAIN QUERY PLAN`；数据层改动合并前在接近生产规模上做规模测试。
- 聊天事件是事实源，记忆事实是可丢弃的派生物；可以积极清理事实，不碰 `chat_events`。

## 2. 共同定义

**非私聊来源**（谓词 `group_sourced(evidence)`，放在 `memory/resident.py`，和 `space_evidence_visible` 并列）：
事实至少有一条证据，并且每条证据都能解析到一条 `chat_events`（直接 `event_id`，或回执的 `trigger_event_id`），该事件的
`scope_type='group'`。下面三种都不算非私聊来源：有任何一条证据在私聊、有证据无法追溯、没有证据行。最后一种也按私聊处理，
沿用现行“证据缺失按私聊处理”的原则。现有的 `evidence_origins_where` 一条语句就能取到需要的列。目前它按会话 kind 取值，
这里要改为取 `chat_events.scope_type`。

**标记**：沿用 `memory_resident_sets` 存标记，一行一个主人，内容是有序的 fact ID 列表。一个 fact ID 出现在某行，就是它的
core 标记；标记的维度（所有者、人物、群、SELF、工作规则）就是行的 `owner_kind`。表里不存正文，可以删除重建。不另建标记表，
也不在 `memory_facts` 上加列：后继迁移、修订号、锁与 CLI 都已经在这张表上。

## 3. P1：规则与所有者核心（只在所有者私聊）

### 3.1 范围

- 所有者私聊：常驻层由三部分组成——工作规则行、SELF 原则行、所有者人物行，全部只取非私聊来源的事实。这个会话不再渲染
  `[对方明确要求记住的]` 与所有者的两份画像。
- SELF 原则行在所有会话里都加上非私聊来源条件（G1 的 SELF 部分）。
- 全部会话：system 消息按层切成几段，层间放断点（G4）；列表里的事实被取代后，渲染不再当场换成后继（G3）。
- 其他会话的人物、群内容（明确事实小节、画像、群核心、群成员）留到 P2，本阶段不动。

### 3.2 数据模型与迁移 `0167_memory_resident_rules`

`memory_resident_sets` 放宽两条 CHECK。SQLite 要用 `batch_alter_table` 重建表；表里只有 4 行，迁移冻结，不引用 ORM：

- `ck_memory_resident_sets_owner` 增加两种主人：
  `owner_kind='rules' AND owner_person_id IS NULL AND owner_space_id IS NULL`（单例）；
  `owner_kind='person' AND owner_person_id IS NOT NULL AND owner_space_id IS NULL`。
- `ck_memory_resident_sets_source`：`owner_kind IN ('self','rules','person')` 时 `source='owner'`。P2 的 0168 再为 person 放开 `dream`。
- 唯一索引 `uq_memory_resident_sets_owner` 不变。不迁移数据。downgrade 删除 `rules` 与 `person` 行，再恢复原 CHECK。

写入校验在 reader 里做，再用一个短写事务提交，沿用 `ResidentMemory.write_set`：

| 行 | 可写的事实 | 条数上限 |
|---|---|---|
| `rules` | person 范围、主体人物根是超级管理员的 fact 或 preference | 20（附录 A.1 原有 12 类规则） |
| `person`（P1 只允许超级管理员的人物根） | 该人物根的 person 事实，kind 为 fact 或 preference | 10 |
| `self` | 现行条件不变 | 10 |

三种行在写入时都要满足共同条件（active、`conflict_state=clear`、未隔离、`valid_until IS NULL`、主人 enabled）和
`group_sourced`。不满足时整次拒绝，返回错误码（`private_source`、`no_evidence`、`wrong_owner`、`wrong_kind`、`inactive`、
`too_many`），行不变。

### 3.3 渲染器

**入口**：`ResidentMemory.render_conversation(conversation_id)` 返回值改为
`ResidentRender(rules_text: str, audience_text: str, fact_ids: tuple[int, ...])`，原来的单个 `text` 拆成两段。
`ContextAssembler` 把两段分别填进 `AssembledContext.resident_rules_text` 与 `resident_text`。

**受众**：`canonical_conversations` 的 kind 为 private，并且对方人物根的 `is_superuser=1`，就是所有者私聊。不按入口类型区分，
定时任务、续接和 SELF 轮按所在会话渲染；子 Agent 与插件轮不带。这些都和现行一致。

**输出格式**（行格式沿用 `- 正文（fact:ID）`，正文的连续空白折成一个空格；小节内按列表顺序排）：

```
[工作规则]            ← 只在所有者私聊；rules 行
- …（fact:ID）
[我自己的原则]        ← 所有会话；self 行，按现行可见规则再加 group_sourced
- …（fact:ID）
--- 分段 ---
[关于你]              ← 只在所有者私聊；所有者的 person 行
- …（fact:ID）
```

前两个小节组成 `rules_text`（第 1 层），`[关于你]` 是 `audience_text`（第 2 层）。在其他会话里，第 2 层仍是现行的人物、群小节，
直到 P2。没有条目的小节不输出；一层为空就不出这一段。

**每轮过滤**：
- 列表里的 ID 只要 `status IN ('active','superseded')`、`conflict_state='clear'`、未隔离、主人 enabled、`group_sourced`，
  就按**原 ID** 渲染。被取代的条目当天照旧显示原版本，由下一次 Dream 维护换成后继（G3）。
- 失效（撤回、隐私删除、管理员失效、过期）、争议、隔离、主人停用、新增私聊证据的条目，下一次激活起立即不显示。
  这些都是事实变化，而且很少发生。
- 删除渲染时的 `resolve_listed` 后继解析，该函数改由 Dream 维护调用。

**语句数**（常数，与历史长度、事实数、条目数都无关）：受众 1 条（会话按主键，并连人物根）；本会话需要的全部行 1 条
（`owner_kind IN (...)` 走唯一索引）；被列出的事实按主键 1 条（同时取主人 enabled 与根）；证据来源 1 条
（`ix_memory_evidence_fact`，连回执、`chat_events`、会话都按主键）。读的行数等于列出的 ID 数与它们的证据数。

### 3.4 Dream 维护（不调用模型）

在 `ResidentSelection.run` 开头、群挑选之前加一步 `maintain_listed`，对所有行都做：
1. 一条语句取所有行；一条语句按主键取全部列出 ID 的状态；对非 active 的 ID 调 `successor_steps`
   （`ix_memory_facts_supersedes_id` 与已提交 Dream 操作的输出），走到 active 的后继。
2. 后继要满足该行的写入条件，包括 `group_sourced`：满足就原位替换，不满足或没有后继就删掉该 ID。
   失效、争议的 ID 也在这里删掉。
3. 每个有变化的行一个短写事务：比对读到的 `revision`，所有者在维护期间改过这一行就放弃；按主键 UPDATE 列表并把 `revision` 加 1。
   `source` 与 `locked` 不变。维护属于“维护标记”，不改所有者的选择。

P1 里 `rules`、`person`、`self` 三种行都只由所有者写，Dream 不往里面加新 ID。

### 3.5 稳定前缀里的位置与缓存断点

| 段 | 内容 | 变化频率 | 断点 |
|---|---|---|---|

实现要点：
