## 2. 现行语义与威胁模型

下列几点在现在就成立，本轮不改变：

1. **前缀授予的是“这个程序带任意参数”**。`pytest` 等于允许 `pytest -p 任意插件`，`git` 等于允许 `git -c core.pager=…`，`python` 等于允许 `python -c …`。`env`、`xargs`、`time`、`nohup`、`timeout`、`exec`、`sh`／`bash`、`sudo` 这类包装命令写成前缀，就相当于全部命令。
2. **命中前缀和 `write_paths` 的关系按驱动不同**（D6）：
   - Claude：命中前缀的 Bash 被自动批准后由 Claude CLI 以本人身份运行，连接器不加沙箱（F6）。
   - Codex：沙箱内的命令本来不发审批；发来的审批通常是要沙箱外权限或联网。自动批准只是同意这一次请求，之后如何运行、是否成功由 Codex 决定（F7）。
   - ACP：Agent 的 `execute` 权限请求范围内且 Agent 给出 `allow_once` 时选它，没有 `allow_once` 时仍上报；命令由 Agent 自己执行，有没有沙箱看 Agent。连接器代开的 `terminal/create` 与 `fs/write_text_file` 范围外直接拒绝、不出卡片，范围内由连接器以本人身份直接执行（F2）。
   - 命令前缀判断只看命令文本，不检查命令会写哪些路径；三种情况下，`write_paths` 都约束不了已批准的命令。
3. **所有者允许写的目录里，Agent 本来就能放代码**（conftest.py、`.git/config`、Makefile），之后任何会执行项目代码的前缀都会跑这些代码。
4. **cwd 不是范围的一个维度**：`runs` 不看 cwd。相对路径的程序前缀（`./run.sh`、`.venv/bin/python`）在 cwd 变化后指向别的文件。

所以范围是“所有者同意哪些事不必再问”的约定，用来防一个诚实但粗心的 Agent，**不能**把存心逃逸的原生 Agent 关在里面。

**Codex `writeStdin` 的位置**：它审批的不是新命令，而是往已在运行的终端写入的输入（F8）。审批参数里没有输入内容字段（F15），连接器只能拿 `command` 去比前缀。被写入的进程若是 `python`、`bash`、`node` 或调试器这类交互程序，输入就是任意代码。按命令前缀批准它，等于把“程序带任意参数”扩大成“程序加任意交互输入”，超出了前缀原本的意思，所以 D5 收紧。D5 只处理 Codex **实际发来的** `writeStdin` 审批；Codex 是否为每次写入都发审批，不在连接器控制之内，本稿不作这样的假设。

## 5. 未来方案：D1 组合命令（未批准，安全验证未完成，本轮不实施）

### 5.1 范围

只研究一种放宽：`&&`、`||`、`;`、换行（`\n`）连起来的命令，每一段都命中所有者写的前缀才算范围内。管道、重定向（含 `2>&1`）、隐式 `cd`、后台 `&` 一律不放行。

### 5.2 判定草案（仅供评审）

1. 文本：字符串照旧；列表照旧 `shlex.join`。**只去掉首尾的 ASCII 空格、`\t` 和 `\n`**（不用 `str.strip()`）。为空 → 判外。
2. `commands` 含 `*` → 判内（不变）。
3. 文本里出现下列任一字符 → 判外，不论是否在引号内：`` ` ``、`$`、`(`、`)`、`{`、`}`、`<`、`>`、`\r`，以及空格、`\t`、`\n` 之外的任何空白或控制字符（Unicode 类别 `Zs`、`Zl`、`Zp`、`Cc`，含 NBSP、U+3000、U+2028、U+0085、`\x1c`–`\x1f`）。
4. 从左到右，在每一处 `&&`、`||`、`;`、`\n` 切开（先认两字符运算符），不认引号和反斜杠；只认字面 `\n`，不用 `str.splitlines()`。
5. 任一段里还有 `|` 或 `&` → 判外。
6. 每段去掉首尾 ASCII 空白：空段 → 判外；只有连续换行之间的空行可以忽略。
7. 每段必须满足 `段 == p` 或 `段.startswith(p + " ")`。没有 `cd` 形式。
8. 所有段都满足 → 判内。

**论证（未经验证）**：第 3 步排除了展开、替换、子 shell、分组、脚本块和重定向字符；剩下的引号、反斜杠、`#` 只会去掉某处分隔符的含义，不会造出分隔符，所以 shell 真正的命令边界应是切分点的子集。关键字只在命令位置被识别，而命令位置只出现在段首。这是推理，不是证明：它没有覆盖用户 shell 里的别名、函数、`chpwd` 等钩子，也没有覆盖 PowerShell、cmd.exe 的全部语法，必须由 §5.4 的验证补齐。

## 10. 风险与回滚

**风险**

- **D5 多出卡片**：非通配范围里，Codex 每发来一次 `writeStdin` 审批，就多一张卡片，委派可能停下等回答。Codex 何时发这种审批未知（F15）。F13 不完整的观察里没有看到非通配范围的使用，但这不能证明没人用；这是有意的收紧。
- **卡片可能看不到输入内容**（F15）：回答者可能在不知道写什么的情况下批准。运维文档要求看不到内容时拒绝或问用户；之后若实测发现 `command` 或 `reason` 里带有输入内容，再更新文档。
- **显式 `kind: null`**：如果某个 Codex 版本给普通命令审批发 null，非通配范围的所有命令审批都会变成卡片。方向安全，卡片上可以直接看出来，到时按真实 payload 调整。
- **`humanCommand` 在通配范围仍自动批准**：今天收不到（F9）；将来声明 `requiredHumanApproval` 时须重新决定。
- **回答路径不校验响应结构**（F10）：现有行为，D5 不扩大也不缩小。
- **#648 说明变长**：工具清单缓存失效一次，每次请求多几十个 token；说明与代码不一致的风险靠 W4 逐句对照。
- **`uv lock` 意外改动依赖**：只接受连接器自身版本一行的 diff，其他变动单独处理。
- **D1 未做**：收窄范围下的组合命令继续逐条变成卡片（#647 原问题仍在）。这是按远野条件和 F13 作出的取舍；§5 的验证没有做，不能当作“将来可直接放宽”的依据。

**回滚**

- **#648**：回退 `subagent_tools.py` 一处字符串即可，与连接器无关。
- **D5**：回退到连接器 0.9.3 会**放宽**而不是收紧：非通配范围的 `writeStdin` 重新按命令前缀自动批准。回退不是安全方向，优先修正向前；只有卡片过多确实影响使用、并经所有者同意时才回退，并在运维文档里写明。因为本 PR 不发布，合并后、发布前发现问题时，回退源码即可，不涉及已安装的连接器。
- 两边互不依赖，任何版本组合都能工作：Bot 新、连接器旧时，说明照样准确（描述的是 0.9.1 起的判定），只是 D5 尚未生效。
- 不碰 Bot 存储、协议、迁移，没有数据回滚。
