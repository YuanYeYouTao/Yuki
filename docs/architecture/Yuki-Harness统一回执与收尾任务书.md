# Yuki Harness：回执回归 Agent 循环任务书

状态：2026-09-13 已按下述决定实施；本地定向验收通过，PR 与部署结果以交付记录为准。
基线：`5955923`。依据真实事故与直接调用链核对；不采纳第三方静态审查报告。

## 1. 核心决定

**工具不论成功、失败、部分成功还是结果未知，都把真实回执交回原 Agent 循环。
Agent 自己决定继续调用工具、查询、等待、解释结果、提问或结束。**

不为每项操作规定一句固定回复，不强制报告成功或失败，不增加专用收尾轮次、回复 Agent、
文案审核模型或“只能回答不能行动”的新阶段。工具成功并不意味着用户的整个目标已经完成；
工具失败也不意味着必须立即结束，Agent 可以根据回执选择合法替代方法。

Harness 负责真实输入、授权、效果持久化、预算、取消、恢复与发送去重。
它不能替 Agent 撰写正常对话、强制播报、覆盖模型正文，或因一个工具结果提前截断循环。

保持现有主入口、人格、固定工具声明、Provider 配置和根预算；不修改用户 `system_prompt.md`。
本任务优先复用既有工具结果结构，不为了统一文案另建 `OperationOutcome` 框架或数据库表。

## 2. 已确认的问题

### 2.1 记忆变更绕过 Agent 自然表达

17:30 的 `memory_change` 成功后，`terminal_memory_reply()` 直接让 Runner 返回固定文字：
“这条记忆已撤回并失效；审计记录仍保留，但不会再作为有效记忆使用。”
业务执行成功，但回执未按普通工具结果继续交由 Agent 决定下一步，后台模板成了 Yuki 的回答。
同轮还曾先调用变更工具、收到 `accept_work_before_execution`，随后补登记并执行成功。

### 2.2 作文事故不能靠强制收尾解决

清理 SVG 后，模型在空响应恢复中虚构了不存在的群聊要求，尝试登记作文被拒，
再通过 `task_control.answer` 发出作文。真实输入登记检查已经部分起效，不能说完全没有围栏。
这说明模型可能幻觉，不等于应在每次成功后新增禁用业务工具的收尾状态机。
保留真实输入/新工作归属校验和模型不虚构输入的合同；不能声称这些机制能判断全部正文语义。
本任务不引入关键词拦截、作文检测、强制只读收尾或成功后禁止继续工作的补丁。

清理实际由主 Agent 执行，没有派出工作者；PNG 后续确实删除，但生成脚本还在。
准确回执应让 Agent 能看到这些区别，不能把“命令成功”缩写成“全部目标完成”。

## 3. 需要移除或改接的路径

| 路径 | 当前问题 | 改动 |
| --- | --- | --- |
| `memory/runtime/finalizer.py:finalize_mutation_text` | 为创建、纠正、失效、恢复、合并、归属、元数据更新输出固定成功文案 | 自然语言 Agent 路径不再调用该文本渲染器；已有结构化结果回到循环 |
| 同模块的无变化、争议、候选歧义、未找到、失败、未知 outcome | 特殊结果也由模板决定最终措辞，未知结果可能落入笼统成功句 | 保留实际状态、原因、候选与操作是否提交，由 Agent 判断下一步；不统一假报成功 |
| `chat.py:terminal_memory_reply` → `agent_runner.py` | 记忆专用钩子直接结束 Runner | 删除 Agent 路径专用终结控制；按普通工具完成流程追加结果并继续循环 |
| `chat.py:finalize/exhausted/_memory_mutation_final_text` | 后端固定记忆文案覆盖正常回复或预算处理 | 撤掉这种覆盖；预算仍按统一持久恢复处理，不借机重做业务操作 |
| `memory/runtime/command_plane.py`、`turn_session.py:finalize_text` | 将领域结果转换为 Agent 最终正文 | Agent 调用方读取结构化回执；显式管理命令如仍需要确定性文本，限定在命令界面使用 |
| `_recover_committed_mutation` / `post_commit_recovery_text` 及包装层 | 用已提交结果的模板替代后续模型回答 | 审计实际调用者，去掉固定业务文案旁路；已提交结果保留给原链恢复，不再次执行 |
| 管理工具失败、自动化创建未持久化等正文覆盖 | 自然语言路径有后端替写结果的逻辑 | 作为工具/执行反馈返给 Agent；真实权限和 persisted 检查留在后端，不用模板冒充 Agent 回答 |
| 暂停、额度耗尽与工具错误 | 某些路径可能直接发系统句或把单工具失败当整轮结束 | 区分工具失败与 Agent 本身不可运行；可继续运行时交回执，不能机械中止 |
| `answer`、进度、文件附言、自然正文 | 可能多处表达同一次结果；这些多数不是固定模板 | 保留 Agent 自主表达，明确发送回执，阻止同一投递重放；不按相似句或关键词硬去重 |

工具 JSON、CLI 状态、插件 SDK 返回值是机器接口，保持机器语义。
显式 `/ai` 管理命令可以保留操作反馈，但不能通过它们给自然语言 Agent 套固定结尾。
未证明可达的残留先核查再删除，不把同一渲染器的多个调用点误算为多个独立发送器。

### 3.1 补充核查：确有强制行为，需要改接

以下按 `5955923` 的符号和路径核对；代码分支存在不等于全部在线触发过。
这里的“收口”是返回真实结果并恢复普通循环，不是新增统一强制收尾器。

| 路径 | 核对结果 | 决定 |
| --- | --- | --- |
| `agent_runner.py:finalizing_commit_in_batch` → `force_finalization` | 已提交结果含 `finalize_after_commit=true` 即设置强制最终回复；随后 `finalization_only` 拒绝模型继续调用工具 | 移除“提交即终结”对普通 Agent 的控制权。结果标记仍可作为事实，不可驱动强制只说一句 |
| `mcp/models.py`、`descriptors.py`、`binding.py`、`capabilities/results.py` | `finalizeAfterCommit` 可从 MCP 配置/结果经描述符和序列化进入 Runner，并非只属于记忆 | 一并审计生产配置及 SDK 调用者。废止该标志支配 Agent 循环的语义；必要的旧配置读取只作弃用兼容，不保留隐性终结能力。不直接全量改工具 schema |
| `chat.py:execute` 的社交失败分支 | send/poke/recall 任一失败就 `_tools_closed=True`，虽然结果返回模型，后续业务执行被整轮关闭 | 明确失败回到 Agent；只限制未知结果的同一效果重放，保留查询和合法其它操作。真实授权失效仍拒绝，不能将所有失败视为未知 |
| `chat.py:execute` 的一般 mutation 错误与 `_admin_retry_constraint` | 部分失败记录 `_admin_terminal_failure` 并关闭工具；重试被限为同工具同操作，违约也关整轮 | 普通工作区等业务错误移除通用“管理命令式收尾”。区分原操作重试、独立查询与合法替代；确属后端委托限制的范围保留，不能以恢复自由为由扩大管理权限 |
| `chat.py` 的 exclusive memory write / `_mutation_committed` | 记忆隔离写成功可同时关业务工具并触发专用终结 | 将一次写入授权、去重和表达分离。已消费的写授权不复用，回执仍能进入原 Agent；不因本次变更给它新增管理能力，也不自动替写回复 |
| `agent_runner.py` 无工具响应分支的后台状态文案 | 工作未明确结束时先纠正，之后可能把模型正文换成“后台任务仍在进行”等固定文字 | 保留未完成工作，返回后台真实状态给原循环或按真实等待释放本次激活；去掉普通流程的正文替换。不把没调用 complete 当作必须强制说某句话 |
| `agent_runner.py` 的 `[提及` 恢复 | 先反馈未产生真实 @；不能恢复时直接覆盖为固定句 | 保留真实 mentions 发送约束和未执行事实，移除正常可恢复阶段的强制改写。不要取消 @ 校验，更不要原样发送伪造提醒 |
| `agent_runner.py:agent_empty_final_retry` | 即使没有新业务需求，也可能要求再生成正文；提示还断言“已经完成所需工具调用” | 按已知结果判断：已交付且 Agent 明确结束可静默结束；未完成就继续普通循环或有界恢复。不把空字符串一律当完成，也不把沉默一律当需要追加总结 |
| `agent_runner.py:agent_incomplete_response_recovery` | Provider 不完整响应后追加“只根据已有结果给出最终答复”，收窄 Agent 行为 | 保留不完整标记、已提交调用和有界恢复；按协议配对完整结果后续跑，不强制最终答复。未完整的调用参数绝不执行 |
| `agent_runner.py:finalization_only` 拒绝工具后调用 `tools.exhausted` | 可将“被强制收尾规则拒绝”误报为“工具调用次数过多” | 删除提交标志造成的强制路径；确实到预算/无进展时保留真实退出类别，不借其它异常冒充额度耗尽 |

### 3.2 有停止或返回，但不应当一律删除

| 路径 | 为什么保留 | 本任务的处理边界 |
| --- | --- | --- |
| Agent 无工具调用、正常生成正文后返回 | 模型自己结束本次响应，是普通 Agent 行为 | 保留，不强迫它继续调用；移除返回前不必要的固定文案覆盖 |
| `task_control.answer` → `chat_answer` 返回 | 模型显式选择回答，不是后端替它写答案 | 保留模型的选择；不另加一次总结，不把任何 answer 都视为违规 |
| `completion_delivered` 且 Agent 提出 completed | 用户交付已有真实回执，再生成会增加重复回复 | 保留有证据的结束；只有单个工具成功而未满足目标时不得套用 |
| `handoff_work_id` 返回 | 真正交接到另一个持久工作，旧工作不应代做代发 | 保留来源与交接；未完成目标仍有接管者，不伪报已完成 |
| 工作者 waiting_user/waiting_external 返回 | 释放执行名额，等父消息或执行结果后续跑 | 保留；状态与回执持久化，不能改成无限空轮询 |
| `decline_reply` / `declined_reply` | 在获准场景由模型显式选择不插话 | 保留已有来源/尚无副作用门槛，不追加“我不回复了” |
| 分段到限 queued、取消、generation/租约失效 | 执行资源与授权边界，继续运行会越界 | 保留暂停/续跑语义；这些不是普通业务失败，不要求在已失效权限下继续请求或发送 |
| 无进展检测、根预算耗尽 | 防止循环浪费或无限失败 | 保留硬边界。已登记工作走现有结构化暂停；无 Runtime 的有限调用者须确认实际用途，不能直接删掉其次数上限 |
| `has_visible_effects` 与语音需正文的区别 | 已有媒体和只准备好语音模式不同，不能把尚未生成语音当作已交付 | 保留证据区分；空响应处理不能破坏媒体交付或强制已完成媒体再附一句 |
| 显式管理命令、接纳前 Provider 不可用的系统状态 | 不属于“正常工具结果交回仍能运行的 Agent” | 保留独立接口；不能假设没有可用模型时模型仍能自然报告 |

### 3.3 包装层与动态上下文的结论

`plugin_host/agent_backend.py` 和 `automation/handlers.py` 的 `finalize` 当前直接返回原文，
`post_commit_recovery_text` 返回 None；不能把接口名字当作存在成功模板的证据。
它们的 `exhausted` 是固定额度终止文本，需要核对调用者究竟是持久主工作还是独立有限调用。
前者交给现有预算/恢复状态，后者保留限额与机器错误语义，不擅自移除执行上限。
`services/main_agent_contract.py` 中状态工具后端也有同类恒等 finalize/空 recovery，应按真实装配核对。

Runner 的 `fixed_definitions` 会覆盖中间的工具投影；
不论怎样移除强制收尾，都必须比较最终请求，而不是根据 `_tools_closed` 名字就声称 schema 已变。
执行权限收窄与对外固定声明是两层，不应一起删除。

## 4. 正常循环和失败恢复

### 4.1 回执必须完整返回

沿用现有 `ok/data/error/retryable/mutation_committed` 等字段和领域结果。
必要时只补缺失的事实，不重建全工具结果合同：

- 实际操作、受影响对象与数量，成功/部分成功/无变化/争议/未执行/失败/未知的区别。
- 原执行 ID、稳定效果键与产物引用；结果是否已提交、是否已发送。
- 可恢复错误与不能重试的边界；“记忆失效”不等于物理删除，“进程退出 0”不等于目标已验收。
- 需要 Agent 选择的候选或下一步查询线索；不把 SQL、凭据或完整内部数据库行塞进模型上下文。

无论结果如何，按对应 call_id 追加至原请求历史，再进入现有下一步循环。
这一步是普通工具循环的一部分，不是每次成功都附加一个强制总结请求。
Agent 可以继续干活、自然回复或在完成交付后结束，不要求每项回执都播报。

### 4.2 单工具失败与模型不可用分开

- 工具返回明确失败：交给 Agent；允许它根据目标改参数、查证、换合法方法、询问或停止。
- 工具结果未知：回执说明未知并给原执行 ID；Harness 继续禁止盲目重放副作用，允许查原状态。
- 结果已提交后模型超时/空响应/400：保留工具历史与效果，按现有有界恢复继续原链，不能重执行。
- 单段到限：保存检查点、按现有预算续跑；不由某个领域模块输出“已完成”来掩盖到限。
- Provider 持续不可用或根预算耗尽：Agent 此时无法自行报告，不能假设它还能生成一句话。
  复用现有系统状态/健康诊断和持久暂停机制，不新增成功或失败的聊天模板。
  如既有运维通知需要保留，明确它是系统故障状态，不属于业务回执，也不扩展成正常回复路径。
- 恢复、取消、generation 变化和迟到回执沿原围栏处理，保留实际效果，不重新生成已接受的投递。

### 4.3 不追加不必要的限制

不新增强制收尾阶段、不在 complete 后一刀切禁止继续业务、不把 answer 变成必须经过文案审查的接口。
保留现有工作生命周期语义，若发现某处为了固定文案而强制 close tools/结束循环，只移除该特殊行为。
真实授权、任务来源、取消、未知效果、额度等原有执行限制不因此放宽。
新输入按现有安全点接入，主 Agent 在子任务执行期间仍能聊天。

模型可能胡说与程序重复执行是不同问题：前者不能靠封死循环解决，后者必须由稳定 ID 和回执去重保证。
不声称仅凭内部事件 ID、来源存在性或固定工具声明就能消除模型幻觉。

## 5. 开工与查证保持行为规则

已约定的大任务开工说明、按用户要求委派、陌生公开事实先查证继续保留在统一代码合同中。
Agent 使用现有 `report_progress` 后继续工作，依据真实回执说话，不每个工具都汇报。

删除上一稿提出的强制开工状态、接纳与发消息绑定、新增 accept 参数、发出开工消息后才允许执行等设计。
不为了确保一句话出现而加数据库字段、投递依赖或后台定时播报器。
若执行顺序反复不顺畅，依据实际请求单独修正工具说明或原有登记链，不在本任务扩建审批/状态机。

查证仍由 Agent 在固定工具集中自主选择：公开知识联网、私人经历查获准历史、工作区状态查实际环境。
保留执行证据，但不强制每轮搜索，不按关键词选 Provider，不因联网撤销用户已授权的正常工作能力。

## 7. 实施与验收

按两个完整工作包执行：

1. 清理自然语言 Agent 中的固定回执、回复覆盖和专用终结钩子，使记忆及相关工具结果回到普通循环。
2. 按第 3.1–3.3 节逐项处理结果标志、关工具、正文替换与包装层；验证普通成功、失败、恢复与各入口一致性，只修复直接相关的结果丢失、提前终止或重复交付。

定向验证：

- 记忆各操作及无变化/争议/歧义/失败的原始结果确实进入下一次 Provider 请求，没有后端模板覆盖。
- 使用可控模型返回自定义正文、继续查询、修正参数或结束，确认 Harness 不另发成功/失败句，也不强制总结。
- 工具失败后仍可选择合法下一步；已提交但生成失败时恢复原链，未知结果禁止盲重试。
- 已发文件及附言的回执可见，Agent 可以结束；相同执行/投递重放不会再发一次。
- 主聊天、主动入口、子任务回传、自动化、插件原调用方复用相同处理；工作者仍无 QQ 发送权。
- 显式管理命令和 CLI 保持约定接口，不把自然语言 Agent 的文案改动扩散到机器调用方。
- 两种 Provider 对照真实 messages/input、完整 tools/native_tools：仅追加结果，固定声明不漂移。
- 相关生成请求仍计入既有预算，分段/重启不重置；不给每次成功附加额外“总结+审核”调用。
- MCP/核心工具返回 finalize_after_commit 后模型提出合法后续查询或执行，不再被强制最终回复拒绝；旧参数兼容不保留暗门。
- 明确社交失败可继续查询/其它合法操作，未知发送仍不能盲重试；管理委托和记忆单次写授权不因改动被扩大。
