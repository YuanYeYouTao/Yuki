## 1. 会快多少

ANN减少的是本地距离比较；分批读取减少的是同时持有的行和向量。这两项不能混为一个收益。query embedding 的远程请求、FTS与事实读取仍有各自耗时。

本次线上只读快照于服务器 `2026-10-25T17:07:50Z` 获得：

| 项目 | 数量 |
| --- | ---: |
| profile | 1 个，1024 维 |
| 全部已存向量 | 2,373 |
| 原 float32 BLOB 总长度 | 9,719,808 B |
| active、非隔离、未过期事实对应的向量 | 1,511 |
| 当前各类有效事实合计 | 1,511 |

这是全库数量；每次查询还按真实人物、群、SELF可见性和日期过滤，合法候选可能更少。五万只是旧扫描上限，不能当作当前规模。当前最先比较原生精确扫描与IVF ANN，不承诺ANN必胜或整次请求快十倍。

测量分为query embedding、授权SQL、索引召回、候选hash/解码/精排、事实回读/RRF，以及整次查询。旧Python实现保留为离线结果oracle；原生NN也不保证与原binary64/fsum逐位相同。

## 2. 首选验证 SQLite 官方 Vec1

优先验证 **Vec1 v0.8**。它是SQLite官方的可加载C扩展，提供原生NN与IVFADC/OPQ ANN，数据/模型/索引在同一数据库内，适合继续使用原Database、连接池及FIFO writer。

这能省掉外挂索引的独立发布、回调补偿、文件版本和恢复协调。第一版不引入独立向量服务。仅采用一套正式检索后端；NN/IVF在实验中比较，选定本次部署模式，不增加按事实数量自动切换的应用调度器。

固定研究源码为SQLite官方mirror `4012bdca5f1599d5dd3d6671112f170bfd48a26f`，宏版本0.8。源码头放弃版权；正式集成仍需固定构建来源、许可证说明与平台产物。SQLite 3.38是所用API的下界，本次只验证了3.46.1，不声称已覆盖所有版本。

| 其他候选 | 本轮未优先采用的原因 |
| --- | --- |
| hnswlib | Python过滤可用，但索引与SQLite另行同步；载入RAM、查询/修改互斥和删除标记需另管 |
| USearch Python | 当前Python接口无predicate filter；mmap view不可动态增删，不能把Rust示例当Python能力 |
| vectorlite | 固定发行版不支持事务，新增一致性维护反而更复杂 |
| sqlite-vec | 稳定版与ANN预发行能力不同，DiskANN需要单独验证 |
| Faiss IVF/PQ | 可作性能/召回对照；第一版优先减少跨存储维护工作 |

资料：[Vec1说明](https://www.sqlite.org/vec1.html)、[手册](https://www.sqlite.org/vec1doc.html)、[参考](https://www.sqlite.org/vec1ref.html)、[固定源码](https://github.com/sqlite/sqlite/blob/4012bdca5f1599d5dd3d6671112f170bfd48a26f/ext/vec1/vec1.c)、[USearch接口矩阵](https://github.com/unum-cloud/USearch#functionality)、[hnswlib接口](https://github.com/nmslib/hnswlib#api-description)。

## 3. 数据怎样放

`memory_facts`继续是事实源；原profile、embedding job、claim与事实ID都保留。`memory_embeddings`继续保存原id、fact/profile外键、内容hash与时间，不另建业务ID映射。

建议按不可变profile创建对应的Vec1表，避免混合不同维度、模型和训练分布。表名只由原内部profile整数ID生成。其rowid使用原 `memory_embeddings.id`，一个必要的整数metadata列保存原fact_id，供授权IN下推。

正式迁移目标是把原始向量正文收到Vec1的同库存储，普通表移除 `vector_blob`；检索精排与Dream都经原Repository读回原始float32值。应用不在普通表和虚表各长期保一份原始向量。Vec1内部原值、打包表示与PQ索引占用另行实测，不能把压缩码大小当总磁盘量。

转换在停旧writer的受控迁移中进行，保全部原embedding id、fact/profile、hash、job与原已付请求；不重新调用Embedding API。先验证原始BLOB在NN与PQ配置下逐字节读回，再迁移消费者，最后删除旧列；不留下正常运行的双存储链。

消费者枚举还包括 `memory/quality/audit.py` 中直接引用旧列的SQL及普通表原 `length(vector_blob)` CHECK，不能只迁移ORM读取；审计改走原Repository/profile向量存储，保留原维度/来源检查。

`quality/audit.py` 的orphan/missing-vector与 `quality/hygiene.py` 的“metadata存在即有向量”判断也须接到对应Vec1原值行，避免元数据已迁、真实向量缺失仍算完整。普通表DELETE trigger按已创建profile生成具体表名与WHEN条件，不用OLD.profile_id动态拼SQL标识符。

## 4. 查询怎样走

```text
原query embedding（含已有合法query缓存）
  → 原SQL解析当前授权范围、profile/kind/日期/有效性
  → 同读取快照内生成合法fact ID子查询
  → Vec1 metadata IN过滤参与原生候选选择，召回R项
  → 只读这批候选的当前事实、原始向量与hash
  → 用原codec计算分数，按原fact ID处理同分，取k项
  → 原FTS/向量RRF及最终当前授权回读
```

R是供精排的候选数，k是原语义候选数。用实验比较R与nprobe的质量/延迟，最终固定合理设置，不把ANN内部旋钮放进主Agent工具schema。

复杂人物与群关系不复制到索引，不维护永久许可缓存。复用 `authorized_fact_condition` 和原target条件，SQL子查询只给出当前合法ID。拟采用的关键形状是：

```sql
-- 形状示意：实际授权子查询仍由原Repository装配。
SELECT ann.rowid
FROM profile_vectors(:query_blob, :search_parameters) AS ann
WHERE ann.fact_id IN (SELECT fact_id FROM authorized_fact_ids);
```

这里 `fact_id` 是Vec1 metadata列，不能改成rowid IN并假定同样下推。显式给K；JOIN/ORDER BY之后的LIMIT不能直接当ANN内部K。没有固定全局top-N后再丢掉无权限结果的问题。

固定源码与本机原型证实metadata IN可进入原生计划。成立条件是直接metadata列、BINARY collation、可用约束；实际Yuki SQL还需EXPLAIN与结果验证。IN成员比较可能随授权集合增长，PQ实现还可能先算整块距离再mask。因此这里只承诺过滤参与top-k资格，不承诺所有未授权向量都不会产生内部距离计算。空、小、大授权集合分别测。

保持原hash核验、归一化、fsum、同分排序与最终当前事实回读；ANN距离不直接替代Yuki输出分数。精排能保已召回候选的分数，漏召回由召回率实验衡量，不冒称恢复了全局精确top-k。

原生NN对它自己的度量执行精确扫描，但C距离与原binary64/fsum可能给不同边缘顺序；仅取R项再精排，仍不能保证旧top-k没有落在R之外。R未覆盖全部合法向量时，不因名字叫NN就标成Yuki旧分数下全局穷尽。

## 5. 写入、删除和恢复怎样保持简单

在 `jobs._complete_page` 原claim/事实CAS成功后的同一writer中，更新普通embedding元数据与Vec1值；HTTP、原向量编码、hash和训练都在writer外准备。对虚表使用其实际INSERT/UPDATE/DELETE能力，不假定支持UPSERT或虚表外键。

普通元数据表保留真实fact/profile FK。由其DELETE触发器清理对应profile虚表，覆盖fact删除、Person遗忘和purge-old的级联路径；更新/新增由同一Repository原事务完成。原型已验证普通表触发器可更新Vec1，以及FK级联删除可随外层事务和savepoint回滚。

purge-old在同一原管理事务内先删除profile，让FK级联与DELETE trigger完成；再删引用该虚表的trigger，最后DROP对应虚表及其模型。不能遗留指向已删表的普通表trigger，即使其WHEN分支当前为false。新profile从原合法向量建立自己的表，表/trigger成对创建；少量数据也可通过统一接口查询，训练不是启用Memory的门槛。

这样没有“数据库提交成功、外挂ANN回调漏了”的第二套恢复状态。训练模型、索引及原向量由SQLite同库持久化；重开走SQLite已有恢复。索引仍可从合法原资料重建，不作为已发生事实或执行回执的替代来源。

Vec1删除可能留下内部tombstone。验收沿现行遗忘合同核查询、原始向量访问、索引重建、备份与清退，不把不可查询宣传为磁盘安全擦除。本轮未新增更强的安全擦除产品承诺。

训练在离线/受控维护阶段完成，不在普通search中训练，不每次启动自动全库训练。训练与重建成本、索引增量写入对writer持有时间的影响单列测量；不能用查询变快掩盖消息写入变慢。

## 6. 现有接口怎样改

- `MemorySemanticIndex.search_authorized/search`统一走新Repository的候选接口，删每次加载全部BLOB/正文再评分的路径。旧精确实现只作验证oracle，是否保正式精确模式按最终选型确定，不无条件常驻两套业务管线。
- `MemoryEmbeddingRuntime.start`装配检索后端；扩展由Database在每个物理连接建立后、迁移和任何相关表访问前加载，不等Memory服务start。Embedding关闭也可能执行既有FK/trigger，所以迁移工具及测试连接同样沿原owner初始化。继续使用原stdlib/aiosqlite；正式发布覆盖Linux/Windows和实际架构，不靠生产现场安装编译器。
- 连接审查覆盖 `migrations/env.py` 的独立engine、`persistence/schema_guard.py` 及 `scripts/verify_work_backup.py`；按实际Vec1读写需要装载，不假定它们都经过Database。普通元数据查询未必需要扩展，且裸SQLite的integrity_check成功不代表已验证Vec1检索语义；备份验收另做加载扩展后的重开/向量访问。
- 固定Vec1内循环未见主动interrupt检查，取消不保证及时中止C计算。取消、close与pool释放沿原Database/SQLiteConnection等真实driver操作或physical_exit完成，再释放连接/writer，不新建native查询协调器。查询、重建与关闭期间取消分别验证。
- 原向量/元数据写入、profile创建、删除触发器、Dream读取和迁移一起改，不能只改search入口。
- 正常ANN属于近似检索，不等于索引故障。复用现有exhaustive/原因表达近似性；索引缺失、陈旧、Provider降级仍按实际事实报告。核 `Retriever` 与工具出口的 `partial_failure`，避免把所有正常ANN都报成故障，也不把候选精排成功说成全库穷尽。
- 不以ANN访问数代替原score_count、coverage或全库事实总数。覆盖率/新鲜度的定义及现消费者必须随接入一并修订，不为继续填旧bool在每次查询全库hash正文。
