## 1. 结论与基线

Yuki 已有完整的持久 Work 主干，也有投入使用的持久子 Agent。任务树已有一层执行关系、结果通知和管理能力；缺少的是所有 Work 共用的多层关系，而不是从零缺少调度器、子任务或管理页面。

**用户关于上下文主链的判断得到源码和定向测试支持：现有公共投影冻结、每 Work 私有 journal、未决协议恢复与配对后的业务续跑已分开实现。** 本轮不重建它们。Pi durable 最直接的参考是 runtime/context/commit，任务树是另一个扩展点，不能反过来成为上下文重构的理由。详细证据及外围删除项见 §§16–17。

上一版任务书对现状的认识不完整，现纠正如下：

- 子 Agent 已实现且线上开启，不是未来才从零接入。未来要扩展的是它的派生、委托和多层协作能力。
- 当前仅允许主 Work 派生 worker；这描述当前限制，不能成为任务树只能一层的设计约束。
- 指定任务树取消、子工作详情和预算显示已有实现。需要扩展关系范围、复用入口，不能重新造一套。
- `completed` 当前是 Work 业务终态。activation 退出、模型响应结束、终端 run 结束均不等于 Work 完成。
- 当前没有后台模型再次验收业务目标的机制；确实存在的是代码对未决效果、未结束子任务、产物及状态变化证据的完成门槛。

## 3. 身份与关系：已经存在的几种结构

| 名称 | 当前职责 | 不能混同的东西 |
| --- | --- | --- |
| Work ID | 持久目标、状态、输入、效果和检查点的身份 | 不是一次模型轮 |
| activation ID / lease owner | 一次取得执行权的激活；同 Work 可激活多次 | 退出不代表业务完成 |
| model request / chain | 原协议链中的一次实际调用及响应 | 不自动成为子 Work |
| source owner | 原来源的调度与授权所有者，如 automation、plugin_background | 不是父 Work |
| worker root_id | 当前一层关系中同时表示直接父与预算根 | 不能原样推广到多层树 |
| initiative / automation / sandbox run | 各领域执行记录，有各自状态 | 不是统一一种 Work 状态 |

目前真实 Work 关系如下：

```text
runtime_work（主 Work）
  └─ runtime_subagents(root_id=主 Work.id, work_id=worker Work.id)
       ├─ 独立 lease / fence / cancel_epoch
       ├─ 原 Work 输入、效果、journal、wait
       └─ result / notified_revision → 直接父的持久邮箱
```

还存在以下关联，但不能拼成推测出来的 Work 树：

- Automation → run → step → Work：游标、script hash 与 run budget。`automation/executor.py:259、522`；`execution_sources.py:161`。
- SDK 调用 → Work：`source.parent_execution_id` 是调用方 execution ID，不是 parent Work。`services/durable_invocations.py:137–144`。
- 插件后台 Job → Work：实际绑定同一个 Work，由 Job owner 恢复，迁移 `0100`。
- Work → Sandbox request/run：终端执行归属及 continuation。`sandbox/continuation_worker.py:40`。名为 `completed_children` 的查询也可能指终端回执，不能仅看名称认定为子 Work。
- Code composition → wrapper effect：同一个 Work 内的父子调用，`parent_effect_key/child_ordinal`。`codemode/driver.py:3、600、1079`。
- execution trace 的 parent_operation_id：诊断调用层次，不取得执行权或预算所有权。

## 4. 全部入口与恢复所有者

Chat、SELF、自动化和 SDK 主调用共享 `YukiRuntime → MainAgentTurnService → AgentRunner → TurnExecution → run_agent_loop`。入口共享不代表来源 owner 相同，也不意味着所有来源都由 WorkScheduler 接管。

| 入口 | 当前能力 | 原任务由谁恢复 | 关键索引 |
| --- | --- | --- | --- |
| 真人聊天 | 普通聊天可无 Work；模型 accept 后持久登记；支持 steer、独立新任务 handoff | WorkScheduler → WorkResumer → 原 Chat | `services/chat.py:711、983、1045`；`runtime/work_control.py:883、1092` |
| SELF 主动醒来 | initiative 原子登记 queued Work，无需伪造真人事件；不依赖普通聊天 admission 开关 | WorkScheduler → `_resume_self`，重建原 initiative | `services/semantic_participation.py:1170、1291`；`services/work_resume.py:71` |
| Person / SELF 自动化 | agent 步骤走共享主运行时；静态提醒可直接 Social | AutomationWorker 保留原 run/step/script hash/cursor；通用 scheduler 排除 | `automation/worker.py:68、146`；`automation/handlers.py:136、265` |
| SDK 主生成 | 原 invocation boundary 对应同一 Work，结果返回 caller | 当前 Host 协程；后续由 WorkScheduler 交原插件 Host | `plugin_host/main_turn.py:45、159、353、394`；`services/durable_invocations.py:29` |
| 插件外部事件背景轮 | durable Job 首次接纳时绑定 Work；waiting/suspended 时 park | PluginBackgroundTurnWorker，通用 scheduler 排除 | `plugin_host/background_turns.py:111、236、370` |
| 子 Agent | child 是独立 Work，独立租约，共用根预算、共享 Runner | SubagentScheduler → SubagentExecution | `runtime/subagent_scheduler.py:89`；`services/subagent_execution.py:174` |
| 终端完成 | 写入原 Work 的完成通知或唤醒信号 | SandboxContinuationWorker 只路由；原来源 owner 继续执行 | `sandbox/continuation_worker.py:40、62` |

`container.py:353–388` 已装配 Work 与 subagent 两个调度器、仓库和执行服务。`services/main_agent_contract.py:75–78` 已纳入 Work/子 Agent 工具声明；工具存在与实际接纳开关分开。

WorkScheduler 每 2 秒维护/选取最多 8 个根会话 scope；不同 scope 并发，同 scope 顺序。等待有独立 poll loop，模型慢不堵时间信号。SubagentScheduler 每 1 秒按实际容量选 child；关闭 admission 不等于丢弃已有 child。参见 `runtime/work_scheduler.py:206`、`runtime/subagent_scheduler.py:30–125`。这些是现行调度实现，不是新增任务树应继承的固定层数或子数限制。

| 重启/失租 | 原 journal 与效果恢复；失去 owner 的执行不可继续提交，shutdown 退出不等于业务取消 | `services/yuki_runtime.py:66`；`runtime/work_activation.py:132`；`runtime/lease_heartbeat.py:75` |

当前 Work 状态共八种：queued、running、waiting_external、waiting_user、suspended、completed、failed、cancelled。不能把 waiting/suspended 当仍占模型执行名额，也不能仅凭状态名推断外部 run 已停止。

当前完成规则没有统一语义评分器：`answer` 不要求发送或非空结果；`artifact` 校验已知产物及要求交付时的回执；`state_change` 校验状态改变证据。未结束 child、未决 effect 又构成共同门槛。问题在于这些事实被赋予了多少完成否决权，而不是缺少更严格的目标验收器。

## 13. Pi 功能与限制：需要纠正的具体理解

### 13.1 Task 树、Conversation 树与业务拆解不同

Pi Task 所有者可以是同会话 Task，也可以是 Conversation；Task 还可拥有另一个 Conversation，该会话里的任务继续进入归属遍历。Conversation 的 history parent 与 owner 又是不同的边。泛型 Task 确实能承载支付等业务流程，但默认图混合 generation、tool、compaction、自定义 Task 与 owned transcript，不能称为现成的业务待办树。

Pi 的 `taskGraph()` 只投影 live Task，不持久化第二套树状态；terminal 节点从图中移除。`src/harness/task-graph.ts:18–55、144、181`；`test/harness-task-graph.test.ts:84、168`。Yuki 可以借鉴派生查询，但长期 Work、工具调用与终端 run 保持各自身份，不创造假 canonical Conversation 来安置子 Agent。

Pi `busy` 看当前 live.run，`idle` 才考虑普通所属执行。自定义 Task、手动 compaction 影响 idle，不必然阻止新输入开始 generation；不能把“树里有活节点”扩展成“整个群都不能接新工作”。

Pi README 的前台/后台 subagent 是扩展示例：前台工具拥有子 Conversation；后台示例用 background anchor 和 reporter Task 把回答作为 follow-up 送回。它说明内核可以承载这些模式，不是 Yuki 应新增一套固定 subagent/reporter 框架。Yuki 已有独立 child lease、持久邮箱和结果通知，先复用这些能力。参见 `test/examples/22-subagent-foreground.ts`、`23-subagent-background.ts`。

### 13.2 held outcome 不等于 Yuki 当前 accepted_control

Pi TaskState 为 pending/running/waiting/completing/terminal；TaskOutcome 另分 completed/failed/aborted/orphaned/faulted。进入 completing 后已有 outcome，不再执行父 phase，等待普通 owned descendants；失败或取消先触发后代取消。Yuki 当前 accepted_control 仍是会被撤销的候选，writer 可因 pending 输入/unknown/child 改 queued、waiting 或 suspended，随后消费候选。这正是要删重复裁决的地方，不是已经具备 Pi held 语义。

Pi 没有与 Yuki waiting_user/suspended 等价的“暂停子 Task”状态。缺任务定义的 pending child 仍可让父 completing 等待；background 是显式执行边界，不是换个暂停名字。让 Yuki 已停止执行的暂停 child 不否决父业务完成，是拟议的 Yuki 适配，不能写成 Pi 默认行为。

Pi terminal Task 不重开、不保留执行 checkpoint；但其曾拥有的 Conversation 后续仍可接受新输入，产生新 Task。Yuki 某些尚未归档 completed Work 可原 ID 明确重开，child 又受父生命周期限制。两者的继续方式不同。参见 `test/harness-ownership.test.ts:265–283`；Yuki `runtime/subagent_repository.py:33–81、161–180`。

### 13.3 unknown、失败与完成的准确关系

`test/harness-tools-recovery.test.ts:109` 的实际样本是：unsafe 工具 intent 已保存，重启后保留部分输出、返回 interrupted error，不重复执行；模型随后回答，Submission 为 done。它证明工具错误不必阻断对输入作答，不证明外部效果已经成功，也不替 Yuki 判断业务目标。

因此 Yuki 应按用户设计删除 unknown 对整体完成的否决，保留未知事实，由 Agent 决定目标是否完成；同一个原 effect 不取得重放资格。仍有真实活动 owned run 时沿原 run 等待或收拢，不能把网络失联变成假成功，也不能把历史 unknown 当永远活动的 run。

Pi 终止工具轮要求所有工具结果都请求 terminate，generation 默认收齐 allSettled。Yuki 的“按原顺序 send→complete，接受结束后不再执行后面的新业务调用”是本项目适配，不是 Pi 原样算法。不能将 `send_message` 成功当 terminate，也不能把 model final 自动发到 QQ。

### 13.4 Pi 不是没有限制，也不更宽松于所有环节

- Pi 底层一个进程拥有 storage，无跨进程锁；Session mutation line 序列化提交。Yuki 保留其现有 SQLite 事务、来源 owner 与租约，不能因 Pi 不使用 lease 就删除原 owner 条件。
- Pi storage 错误或内部提交后状态无法采用，会结束整个 Session；普通外部监听器错误只报告。`src/session/session.ts:508–592`；`test/harness-storage-failure.test.ts:86`。不把这个全局故障策略搬成 Yuki 任意辅助错误暂停全局。
- Pi safe 工具恢复要求存储和当前策略都 safe，缺定义与 orphan 有具体处理；不能只摘一句“自动恢复”就重跑外部工作。`test/harness-tools-recovery.test.ts:136`。
- Pi 重复 requestId 按原 Conversation/type 返回已有 Submission，并不再次比较正文；Yuki 原内部事件和调用内容合同不能据此降为“相同任意字符串就算同一授权”。`src/harness/submissions.ts:148`；`test/harness-submissions.test.ts:82`。
- Pi phase 不改变 checkpoint 的 fault 检查针对其状态机，不能移植为 Yuki 重复读资料/结果相同就算无进展；其压缩示例也不能替代 Yuki 原隐私代次与来源复核。`src/harness/scheduler.ts:1013`；`test/harness-compaction.test.ts:1784`。
- Pi 工具/扩展选择、structured output、ownership 和 join 都有真实校验；本项目学习职责与数据流，不照抄每个 guard，也不把每个 guard 都误称纯防御。
- Pi 自动压缩、Provider retry 和 Registry reload 都有自身政策；本轮不引进更多阈值、重购模型策略或热注册框架。

## 14. 内核改造应如何对应，而非再建一套

```text
Yuki 业务层：Work（目标、来源、结果）── Work 子目标
                    │                    │
执行层：原 activation / request / effect / Sandbox run
                    │
持久事实：原输入、journal、领域回执、预算

Pi 参考：Task / owned Conversation / Task 执行归属
         借鉴输入边界、阶段提交、决定后收拢、取消顺序
         不把以上两层压成同一个新 Task 引擎
```

本轮优先改四处：完成候选不再反复业务审批；输入在实际选取边界结算；所有权能沿真实关系收拢；工具失败和发送结果只陈述事实。Work 父子关系只是业务任务树的地基，执行收拢仍复用现有 effect/run/lease，预算根与直接父分开。不要为“通用”新增一个混装 Work、消息、工具、终端的节点注册表。

允许先完善任务树内核与模型可用入口，后续接递归子 Agent。无需同时造计划器、依赖 DAG、树深度配额、第二种调度器或实时 WebUI。纯计划笔记沿 goal/context_note 表达；真正接受执行的子目标才登记 Work。停止某个子树不取得取消兄弟 Work 或更大 canonical 会话的权力。

前轮文档重写保留已有删除索引 D01–D21；本轮在 §17 追加外围门槛与局部减重复项，不把推测“升级”为既定实现。尤其是 paused child、failed 原 ID 继续、批次 terminate、存储保存重备，均标明 Yuki 目标语义和真实修改位置。

## 16. 重点复核：runtime 与多个 Work 的上下文冻结

### 16.1 Pi runtime 实际提供什么

此前对 Task/Work 概念的讨论过多，遗漏了更直接的执行机制对应。Pi `TaskScheduler.#runtime()`（`src/harness/scheduler.ts:1193`）按 phase 提供 agent、持久 memo、context、commit、等待等能力；Yuki 对应的是现有 `YukiRuntime → Runner/TurnExecution → WorkSession → WorkJournal/SQL writer`，无需新增同名适配层。
