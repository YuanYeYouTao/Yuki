## 0. 结论摘要

- **“dots”查实存在**：OpenAI 2026-09-29 发布的常驻 Agent（always-on agents），在 ChatGPT 中使用。
  与本文相关的是它的“主动研究”（proactive research）：用户不在用它时，它在后台回顾对用户的了解、对话历史和
  已授权的资料，**只用只读工具**，可以给自己记私人笔记，结果作为更新出现在它与用户的**唯一主对话**里。
  官方没有公开触发频率；推送方式也未写明（§1）。
- **#541**：所有者的判断成立。Work 是“要收尾的事”，长期在意的是“会一直放在心上的事”；
  Yuki 现在有执行底座（SELF、Work、定时、记忆），缺的是**一份很短、长期稳定的“在意的事”清单**，以及一个
  **按固定节奏、只读地看一看这些事**的入口。推荐方案（§4.3）不新建体系：清单是 SELF 记忆事实，
  渲染进现有常驻段；节奏复用定时任务；看完的结果写笔记，要不要告诉人另由已有的主动私聊决定。
- **#289**：Yuki 现在已经能跨会话读（`read_chat` 不给 target 时检索所有获准会话，近 30 天 270 次有结果的调用里
  228 次读到了别的会话），也能跨会话发（`send` 带 target）。缺的是**不读就不知道别处发生过什么**，以及
  **转达出去的消息在目标会话里没有来源标记**。推荐方案（§5.3）是两件小事：给转达加来源标签，
  在私聊里给一行“对方刚在哪个群和你说过话”的指针（不带正文）；**私聊内容永不自动进入群**。
- 调研中确认了一条现有的隐私敞口：主 Agent 的 `read_chat` 在普通用户轮里**不按提问者收窄范围**，
  群里任何人都能让 Yuki 检索任何一段她参与过的私聊。生产近 30 天有 8 次**群里触发**的 `read_chat`
  返回了**提问者以外的人的私聊**事件（4 次提问者不是超管；涉及的多数是 Yuki 自己在那些私聊里发出的消息）。
  这与现行文档“检索所有获准的聊天”一致，不是代码偏离合同，而是一个没有被单独拍板的取舍。
  做任何跨会话增强之前，应先决定是否收紧（§6、§8 Q5）。

### 1.2 主动研究：三件关键事实

1. **触发方式与频率**：用户“没有在和它一起工作”或“没人给它任务”时进行；TechCrunch 访谈描述为
   “按某个节奏（on a cadence），想一想它对你知道些什么”，再看对话历史和能访问的资源，寻找可帮忙之处。
   **官方没有公开具体频率或调度算法**。定时与周期检查（“每天早上看日历”）是另一项功能，由用户设定频率，
   在 Scheduled 页面管理（暂停、编辑、查看运行）。
2. **结果怎么呈现**：帮助中心原文是“定时运行和主动更新出现在对话里”；dot 会带着进度、问题或需要决定的事
   回来找你；桌面端可在 Activity View 跟踪后台工作。**是否推送系统通知，官方页面未写明**。
   访谈里提到时机问题：一次日程冲突提醒在事件前三分钟才到。
3. **权限边界**：主动研究期间**只用只读工具**，不能给别人发消息、不能改应用内容、不能操控浏览器或电脑；
   Custom Rules 不能关掉这条限制，dot 自己也不能（第三方报道称这一限制在代码里强制，而不只写在指令里）。
   它可以读已授权来源、给自己记私人笔记；之后的任何行动另走常规的动作规则与安全检查。
   OpenAI 称不直接用主动研究和“dot 给自己的笔记”训练模型。

可借鉴的不是某个算法，而是**三段分离**：发现（只读、记笔记）→ 执行（另走权限）→ 告知（回到唯一主对话）。
本仓库 [10-18 自主静默调研](Yuki-自主静默与事件监视能力调研-2026-10-18.md) §4 已有同样结论，本文沿用。

## 2. Yuki 现状：已经能做什么

### 2.1 能力盘点

| 能力 | 现行实现 | 边界 |
| --- | --- | --- |
| SELF 自主行动 | 语义参与库的连续机会率给每个**获准群**产生 proposal，接纳为 `AcceptedInitiative` + SELF Work，经共同 `MainAgentTurnService` 执行（[语义参与](semantic-participation.md#self-主体与同一执行链)、[自主参与模型](autonomous-participation-model.md)） | 只在群里；无来源机会率随该群真人活动衰减，群安静就为零。它回答的是“这个群现在适不适合我主动做点什么”，不是“我在意的事该看看了” |
| 主动私聊 | `proactive_turns`，`TurnOrigin.PROACTIVE_PRIVATE`，唯一来源是只读看门狗；只对超管、只走已设置的主动路由、只汇报不执行（[主 Agent 合同](main-agent-runtime.md#yuki-主动发起的私聊看门狗)） | 不调模型就发现问题，发现后才花一次 SELF 私聊；没有“为某件在意的事去私聊”的来源 |
| 自省 | `memory_self_reflection`：按批次处理新事件与工具回执，写 SELF 事实与经历（[自省](self-reflection.md)） | 只回顾已发生的事，不主动查新信息 |
| 定时任务 | `manage_schedule` / `get_schedules`；到期激活共同 Main，沿原创建会话执行；SELF 也能给自己建（`creator_kind='self'`，但要求在群场景里） | 固定节奏、固定指令；Yuki 不在运行时“记得”自己有哪些长期关注 |
| Work | 持久任务：`time_due`、`conversation`、`plugin_event`、`owned_run` 四种等待；预算、journal、子任务、原回执恢复（[主 Agent 合同](main-agent-runtime.md)） | 目标与终态收敛；长等待的续接成本问题见 #646；属于一个 Conversation |

| 跨会话发 | `send` 带 `target` 走共同路由与授权 | 目标会话的历史里，这条消息看起来和普通回复一样，没有“受谁委托”的来源 |
| 当前场景 | 运行资料只给简短的群聊/私聊说明与 `current_time`（[主 Agent 合同](main-agent-runtime.md)） | 不含任何别的会话的动态 |

### 2.3 差距

**#541 长期在意**
1. 没有“在意的事”这个对象。人物画像回答“这个人是什么样的”，SELF 原则回答“我怎么做事”，
   Work 回答“这件事做到哪了”；“我持续关心 P 的考试 / 我想跟进某个技术方向”没有落点。
2. 唯一的自主唤醒是群社交机会，跟群热度绑定，**现在还整体关着**。私聊和无会话场景没有自主唤醒。
3. 醒来之后 SELF 指令只有“简短意图和来源编号”，不知道自己在意什么；结果是 349 次行动 17 次发言，
   其余大多是“看了看，没事”。成本主要花在“找事做”，而不是“推进在意的事”。
4. Work 可以“等时间再看”，但它要求目标与终态；把长期关注塞进 Work 会碰到累计预算、续接重组、换代失效与
   Conversation 归属（#646、#673 的问题都与此相关）。

**#289 跨会话感知**
1. Yuki 在一个会话里不知道别的会话刚发生过什么，除非它恰好想到去 `read_chat`。私聊里这类调用已经很常见
   （213 次），说明需求真实存在，但完全依赖模型自己想到。
2. 跨会话发出的消息在目标会话没有来源，群里有人追问“这是谁让你说的”时，Yuki 只能去翻别的会话。
3. 没有成文的“自动出现”规则：现行 Memory 常驻层已规定“私聊来源的事实不进别人的会话或群聊的常驻层”，
   聊天内容的自动出现还没有对应规则。

## 3. 设计约束（本文推荐方案必须满足）

- 删除优先、复用 Work / SELF / 定时 / 记忆，不另起“Goal 引擎”“全局黑板”这类平行体系。
- 长期关注点遵守记忆分层原则：**极少变动、放在稳定前缀、不往当前消息塞大量内容**
  （[记忆分层架构书](Yuki-记忆分层架构书-2026-11-21.md)、[常驻记忆段](memory-v2.md#常驻记忆段)）。
- 成本可控：不加隐式付费调用。任何新的模型激活都有显式开关、固定节奏，默认关闭；不按内容自动增加调用。
- 隐私：**私聊内容不能流进群**；也不能流进与另一人的私聊。可见范围沿用现有证据来源规则，不新增可见性字段。
- 身份：关注点归 SELF 或原 Person；转达沿原内部事件 ID，不用平台消息 ID 重建来源。
- 告知与执行分离：只读研究不发消息；需要告诉人时，走已有的主动私聊或原会话的普通发送。

## 4. #541 长期在意：候选方案

### 4.1 方案 A：长期关注 = 不收尾的 Work

每件在意的事是一个 Work，目标写“持续关注 X”，用 `time_due` 等待定期醒来，醒来查一查、写进 journal，再等待。

- 优点：零新表，等待、预算、恢复全部现成。
- 缺点：违背 Work 的终态收敛语义（所有者 11-23 已指出两者不同）；累计预算与 transcript 会无限增长，
  长等待续接重组（#646）每次都付；Work 绑定一个 Conversation 与 generation，`/ai new` 或换代会让它失效（#673 类问题）；
  Yuki 在其他会话里看不到“我在意这件事”，除非去查 `get_tasks`。
- 结论：不推荐作为载体，但**具体要推进的子事**（比如“下周一前帮 P 查报名截止”）仍然用 Work。

### 4.2 方案 B：长期关注 = SELF 自建的定时任务

每件在意的事是一个 `creator_kind='self'` 的定时任务，指令写“看看 X 有没有新进展，有需要再告诉相关的人”。

- 优点：调度、去重、预算、回执全部现成；节奏显式、成本可预测。
- 缺点：定时指令是死的，Yuki 平时不知道自己有哪些关注；每件事一个任务，关注多了调用线性增长；
  SELF 自建定时目前要求群场景，私聊关注无法创建；关注之间无法合并处理（一次看完几件事）。
- 结论：调度部分可复用，但“在意什么”不能只存在定时指令里。

### 4.3 方案 C（推荐）：关注清单进常驻层 + 一个只读的“看一看”定时入口

把“在意什么”和“什么时候去看”分开，各自落到已有机制上。

**① 清单：SELF 记忆里的“在意的事”**
- 一条关注就是一条 SELF 事实，`kind=fact`、固定 `category='concern'`。`memory_facts.kind` 现有 CHECK 只允许
  `fact / preference / episode`，新增 kind 要重建这张大表，不划算；`category` 没有约束，现成可用（Q2）。
  正文一句话，可附关联 Person / Space（现有 `canonical_visibility_person_id / space_id`）。
- 可见范围沿用 SELF 的 global / private（某人）/ group（某群）三种，并套用常驻段的证据规则：
  从与 P 的私聊来的关注只在与 P 的私聊和研究入口里出现，**不进任何群**。
- 渲染：常驻段新增一小节 `[我在意的事]`，排在 `[我自己的原则]` 之前，**最多 5 条、只列一句话 + `fact:ID`**；
  不放进展、不放笔记。它随常驻段进入 system 末尾的稳定前缀，与现有常驻内容一样“每天最多变一次”。
- 谁来写：
  - 所有者或本人明确说“帮我盯着……”时，Main 用现有 `save_memory` 写入（明确事实，下一轮常驻段即出现）；
  - Yuki 自己判断值得长期关注的，也用 `save_memory` 写成同类事实，但**不进常驻段**，只在研究入口里被查到；
    要升为常驻，由所有者用 `yuki memory resident`（与 SELF 原则同一入口）确认。这样常驻内容只在明确要求或所有者确认时变动，
    不新增 Dream 挑选范围；
  - 结束一件关注：`edit_memory` 失效该事实；不设到期门槛。
- 这一步只改常驻段渲染，不加模型调用。

**② 节奏：一个 SELF 的只读“看一看”入口，复用定时任务**
- 部署级一个 SELF 定时（默认关闭，所有者用开关打开），节奏显式配置，比如每天 1–2 次；
  一次激活**合并看完所有 global 与自己有权看的关注**，不是每件事一个任务。
- 这一轮的来源是现有 `scheduled_automation` 的 SELF 变体，主体 SELF，不借任何人的身份；
  需要放宽“SELF 定时必须在群场景”这条限制（`automation/service.py` 的 `self_automation_scene_required`），
  改为可以没有会话（与 `proactive_private` 一样只经 `activation_context` 给资料，不建账本事件）。
  实施前要核对 `automations` 的会话与 Presence 列在 SELF 行上能否为空、到期执行对无会话来源的处理；
  如果改动面超出“删一条限制”，退回用所有者私聊作为这条定时的原会话。
- 工具：与 dots 一样**只读加记笔记**——联网搜索、网页读取、`read_chat`、`search_memory`、工作区读写、
  `save_memory`/`edit_memory`（写 SELF 笔记，可见范围不宽于关注本身）。`send`、管理、委派、终端写操作
  在执行处返回 `report_only_source`（直接复用看门狗主动私聊已有的风险判断）。
- 笔记：进展写成 SELF 事实或经历，按需层，**不进常驻**；下次醒来用 `search_memory(fact_id=…)` 读。

**③ 告知：复用主动私聊**
- 研究里认为“这件事需要对方知道或决定”时，只留下一条“建议告知”记录（复用 `proactive_turns`，
  新 `source_kind`，收件人是关注关联的 Person），由现有 `ProactivePrivateTurns` 在对方私聊里另开一轮去说。
  路由、最小间隔、同一问题只说一次、回执结算都沿看门狗现行规则。
- 群相关的关注（global 或某群）不主动进群发言：等群 SELF 重新打开后，群 SELF 在常驻段里能看到这条关注，
  自己决定要不要提；或者在有人提起时自然接上。这样研究入口永远不直接写群。
- 第一阶段只允许告知所有者（与看门狗一致），见 Q3。

**为什么推荐 C**
- 新东西只有：一个固定 category、常驻段一小节、一个 `proactive_turns.source_kind`、放宽一条 SELF 定时限制。
  没有新表，没有新调度器，没有新执行链。
- 每轮主 Agent 只多几十个字，且在稳定前缀里；研究入口是唯一新增的付费调用，显式、固定节奏、默认关。
- 关注本身是记忆事实，跟人物遗忘、合并、证据规则自动对齐；Work 只承担具体要做完的事。

| 原文设想 | 本方案 |
| --- | --- |
| 用户建模与关系演进 | 已由人物画像（#227，P4）承担，不重复建设 |

## 5. #289 跨会话感知：候选方案

所有者的描述是“Yuki 知道自己现在在哪个群，刚刚私聊那边有没有给我这里传了消息”。拆开是三件事：
知道自己在哪（已有），知道别处刚发生过与这里有关的事（缺），知道这里的某条消息是从别处转达来的（缺）。

### 5.1 方案 A：只靠按需读取，补提示

不改运行时，只在 `read_chat` 的工具说明和系统规则里写清楚“对方提到别处的事时先查”。

- 优点：零成本、零风险；现有授权不变。
- 缺点：仍然完全依赖模型想到；“转达来源”问题不解决。
- 结论：作为基线，单独不够。

### 5.2 方案 B：把时间相近的别处短聊天冻结进本会话历史（issue 评论里的想法）

某人刚在 A 会话和 Yuki 说过话，来到 B 会话时，把 A 的最近几条消息作为一个冻结片段放进 B 的历史。

- 优点：感知最强，模型直接看到上下文。
- 缺点：
  - 隐私：A 是私聊、B 是群时直接违反“私聊不进群”；A 是群、B 是另一人的私聊时，把群内容带给了不一定在群里的人。
  - 能安全成立的只有一个方向：**同一个人，从群到他自己的私聊**（他本来就在群里看得到）。
  - 冻结片段进入公共历史，会改变缓存前缀、compact 范围与“每个 Conversation 一份公共历史”的合同；
    与“不往当前消息塞大量内容”的原则也冲突。
- 结论：不推荐作为默认机制；如所有者坚持，只考虑“群 → 同一人的私聊”且只放指针（见 C②）。

### 5.3 方案 C（推荐）：转达有来源 + 私聊里一行“刚在哪见过”的指针

**① 转达有来源（跨会话发送的出站事件带因果）**
- 一次 `send` 的目标会话与触发会话不同时，出站事件写上现有的 `caused_by_event_id = 触发事件 ID`，不新增列。
  这一列现在只给插件主动消息用（`plugin_background`，历史标签“由外部事件 #N 触发”），Social 对 SELF 定时与
  主动私聊上下文明确拒绝它；扩展到跨会话转达要放宽这条核验，并在 `event_prompt.py` 的标签函数里加一个分支。
- 目标会话的历史渲染只多一个标签，不带来源正文：
  - 私聊 → 群：`转达｜受 <请求者显示名> 私下委托`（请求者自己要求转达，名字可出现；内容不出现）；
  - 群 → 私聊：`转达｜来自群 <群名>`；
  - 私聊 → 另一人私聊：`转达｜受 <请求者显示名> 委托`。
- 被追问时，Yuki 可以按需用 `read_chat` 的 around（按内部事件 ID 定位）回查原委托；回查仍按现行读取授权，
  群里不因此获得读私聊的权限。
- 代价：只写一个已有字段和一处渲染；没有新模型调用。近 30 天这类发送约 170 次。

**② 私聊里的“刚在哪见过”指针（可选，Q4）**
- 只在**与 P 的私聊**里，运行资料（当前消息的 `<runtime_context>`）加一行：
  “P 最近 30 分钟在群 G 和你有过对话（事件 #a–#b）”。只给群名和事件范围，不给正文；需要时模型自己 `read_chat`。
- 只指向**群**，且只列 P 本人在其中发过言或被 Yuki 回复过的群；**群里永远不出现指向私聊的指针**。
- 每轮一条按 `(author_person_id, occurred_at)` 走索引的常数查询，不调模型；没有命中就不输出。
- 放在当前消息而不是稳定前缀，是因为它每轮都可能变；内容只有一行，符合“不塞大量内容”。

**为什么推荐 C**
- 两件都是在已有字段和已有资料块上加最小的东西；隐私方向单一可审计（私聊永不进群，群只以“群名 + 事件号”指向本人私聊）。
- 不做“全局黑板”或跨会话公共历史，避免改动 compact、缓存与 Conversation 合同。

## 6. 风险

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| 私聊内容进群 | 关注清单、研究笔记、转达标签、指针都可能成为通道 | 关注与笔记沿证据来源规则；群里只渲染本群来源；转达标签不带正文；指针只在私聊出现、只指向群 |
| 现有 `read_chat` 跨私聊读取 | 普通用户轮不按提问者收窄，近 30 天 8 次群触发的读取返回了别人的私聊事件（4 次非超管触发） | 先由所有者决定是否收紧（Q5），再做本文任何跨会话增强；收紧本身是删减授权范围，不新增机制 |
| 研究入口花费失控 | 只读研究可能每次都多轮搜索 | 一次激活合并看完全部关注；沿现有 Work 预算与每日调用上限；默认关闭、节奏显式 |
| 打扰 | dots 的教训：提醒时机不对、问得太多 | 研究本身不发消息；告知走主动私聊的最小间隔与“同一问题只说一次”；第一阶段只告知所有者 |
| 关注清单膨胀 | Yuki 自己不停加关注 | 常驻最多 5 条；Yuki 自判的关注只进候选，由 Dream 挑选“无理由不变”；所有者可锁定 |
| 关注过期 | 事情结束了还在常驻里 | 研究入口发现已结束时用 `edit_memory` 失效；所有者可直接失效 |
| prompt 注入 | 研究读网页和别人的聊天 | 只读工具在执行处强制；告知另开一轮、只发给收件人本人 |
| 缓存 | 常驻段变动会让该会话历史重计费一次 | 关注清单与现有常驻段同频（每天最多一次），不额外加变动 |

由 Yuki 用现有终端与文件工具自己维护；格式不强制、程序不解析、不做条数校验、不加新工具、不做迁移。不进常驻段、不按轮渲染、不进稳定前缀。
只在定时 SELF 唤醒的触发正文里提醒一次清单路径，普通聊天轮不提醒。理由：在意的事的生命周期不同于记忆事实（不随提取、Dream、遗忘与证据规则变化），
放在记忆里会被记忆流水线合并或清理；文件方案最简。提醒只给路径、不带内容：Bot 进程读不到沙盒 HOME 卷，带内容要新增读取链路，而 Yuki 醒来后自己读即可。
原 `category='concern'`、常驻段 `[我在意的事]`、`save_memory(kind=concern)` 与部分索引的实现已整体撤回，不留兼容（#731 的 revert 提交）。

**看一看改定（2026-11-23）**：不新建单独的研究入口、不限只读工具、不加新 `proactive_turns.source_kind`；复用现有群 SELF 自主唤醒的执行链
（`self_initiative` Work 来源、同一套工具与权限、同一条投递与回执），只多一种定时唤醒触发，节奏显式配置、默认关闭，能放宽现有条件就不加新机制。
先前写好的只读入口、模型请求上限与新来源已撤回。现有 SELF 的事实（2026-11-23 核对）：
- 场景：`self_initiative` 只在群里运行（`autonomy_initiative_runs.space_id` 非空，SELF 记忆来源 `memory/self_origin.py` 也只认群）；SELF 定时同样要求群场景。
  定时唤醒不属于某个群时，最自然的现有场景仍是一个获准群；具体取哪个群（或在每个获准群各醒一次）待实施时在 PR 写明。
- 能对谁发言：SELF 的 `send` 走共同目标选择、资料授权与发送回执，可带 target 发往别处，不限当前群或所有者。
- 预算：SELF Work 没有按次上限（根预算默认无限）；近 30 天 349 个 SELF Work 平均 13.7 次模型请求、3.7 次工具调用。按决定不为这次单独加上限，由所有者再定。
- 开关：生产自 11-03 起全局覆盖 `conversation.auto_reply_enabled=false` 与 `conversation.semantic_participation_enabled=false`。
  `auto_reply_enabled` 只控制“会话来源候选”，`proactive_wakeup_enabled` 控制无来源 intrinsic，`semantic_participation_enabled=false` 时整个控制器不推进。
  定时唤醒若作为语义参与控制器之外的独立触发，按这些开关的真实语义都不会被挡住；若挂进控制器，会被 `semantic_participation_enabled=false` 挡住。
