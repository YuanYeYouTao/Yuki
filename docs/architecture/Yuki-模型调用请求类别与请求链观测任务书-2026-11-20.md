## 2. 设计

只加观测字段，发给模型的内容一个字节都不改。

1. **新增两列**，都可空：
   - `request_kind String(32)`：值为 `main`、`execution_compact`、`public_compact`；
   - `request_chain_id String(64)`。

   不加 CHECK 约束，以后加新类别不需要迁移。历史行保持 NULL，表示未知，不回填，因为无法从旧行反推出来。默认不加索引（见 §6 Q3）。
2. **类别不放进 `ChatRequest`**，原因是 F11：放进去会改变 compact 回执内容和输入摘要。做法是在 `TaskModelExecutor.execute` 加一个关键字参数 `request_kind: ModelRequestKind | None = None`，经 `_execute` 交给两处 `_record_invocation`，同时写进 `model_phases` 的 metadata。`ModelRequestKind` 是 `model_runtime/models.py` 里新增的 StrEnum。
3. **请求链 ID 不加参数**，执行器直接读已有的 `request.request_chain_id`。空串记 NULL，不编造值。
4. **调用方只改两处，类别都按已有事实决定：**
   - F7 的两个 `partial` 传 `MAIN`。Work 恢复、Claude pause 续发都走这里，都算 Main。
   - F8 的 `execute()` 按 `plan.public is not None` 传 `PUBLIC_COMPACT` 或 `EXECUTION_COMPACT`，与 `:1286` 收尾时的判断一致。

   记忆、SELF、Dream、搜索桥不传，类别为 NULL，因为 `task` 已经能说明它们是什么（见 §6 Q2）。
5. **仓库层**：`record` 增加两个参数，`ModelInvocationRecord` 增加同名两个字段。`_prepare_write` 照旧把整行冻结成 `INSERT … SELECT`，只是多两个字面量，不增加条件也不读历史。没有 writer 的旧路径同样只多两个列值。
6. **不改的东西**：
   - 管理端用量 API 和四维聚合（§6 Q4）；
   - `provider_session_id` 和其他请求头；
   - compact 回执、摘要、`_REQUEST_METADATA`；
   - 隐私删除；
   - 执行诊断的保留规则。
7. **文档**：
   - `model-providers.md` 用量一节写明两列的含义：一行是一次逻辑调用；compact 请求带压缩前的链，之后的 Main 带新链；可以经 `runtime_work_journal` 的 chain 关联到 Work。
   - `README.md` 更新迁移 head。
   - `conversation-compact.md` 补一句观测口径。

为什么这样不影响前缀缓存：请求正文、工具声明、`instructions`、continuation 和 `x-session-id` 都不变（F5）。新增的两个值只在请求返回之后才写进数据库。

为什么写事务不扫描历史：写入仍是 F4 那条单行 `INSERT … SELECT`。迁移只做 SQLite 的 `ADD COLUMN`（可空、无默认值），只改表结构元数据，不重写表，也不扫描数据。

## 4. E2E 计划

文件：`tests/integration/test_model_invocation_request_kind_e2e.py`。

模型在 HTTP 边界由脚本替代，其余部分都是真的：真实 `TaskModelExecutor`、`ModelInvocationRepository(writer=DiagnosticWriter)`（writer 已启动）、真实协议适配器、`httpx.MockTransport`（抓取每次请求的 body 和 headers）、真实 SQLite（迁移到 head）、真实 `TurnExecution`／Work journal。

装配有两种候选：

- 复用 `tests/support/client_reference_server.py` 一类的正式应用装配，该装配启动了 `app.model_invocations.writer`；
- 或者在 `tests/support/work_compaction_capacity_helpers.py` 的 `_session`／`_runtime` 上，把 `InjectedModelExecutor` 换成真实执行器。

二选一，以改动最少为准，在第二阶段的失败用例里确定。

- **S1 执行级 compact（生产形态）**：Responses 协议加 `prompt_cache_breakpoints`，私聊 Work，`compact_trigger_tokens` 调低。脚本顺序：工具调用 → 工具结果 → 下一次准备时触发执行级 compact → 摘要 → compact 后的 Main。断言：
  - 三行依次是 `main(X)`、`execution_compact(X)`、`main(Y)`，且 Y≠X；
  - journal 的 `chain_links` 里有 `X→Y compact`；
  - `model_phases` 有类别。

  变体：硬容量下连续 compact（K6）。
- **S2 公共 compact**：Chat Completions，非 Work 的普通群聊。两种情况：
  - 公共前缀超过软阈值，触发自动公共 compact；
  - 超管发 `/compact 重点`。

  断言类别为 `public_compact`，链与紧随其后的 Main 衔接正确。同一场景附带一次结构化任务（例如记忆提取），断言它的类别和链都是 NULL（K10）。
- **S3 失败**：上游返回 5xx 或无法解析，断言失败那一行也有类别和链，原异常类型不变（K7）。
- **不改请求内容的证据（K8、K9）**：
  - 每次请求的 body（去掉缓存标记，做法同 `test_external_agent_prompt_prefix_e2e.py` 的 `content()`）和 headers 都存下来，并断言类别值、链 ID 不出现在任何 wire 字节里；
  - 先在基线提交上运行同一场景（预期因缺列而失败，但 wire 部分照样写出），再在改动后运行，比对两次的 wire 摘要；
  - 如果场景里有不可避免的随机内容（时间、uuid），只比对归一化之后的摘要，并在产物里写明归一化了哪些字段。
- **产物**：写到 `test-results/model-invocation-request-kind/<nodeid-sha256>/`，按 `tests/support/compact_delivery_evidence.py` 的格式保存 `evidence.json`，内容包括：
  - 源码 HEAD、`git diff` 补丁的 sha256、测试源码快照；
  - 每次 wire 请求的摘要和字节数；
  - 各行 `model_invocations`（不含正文）；

## 6. 需要用户决定的问题

- **Q1 字段名。** 推荐 `request_kind`，备选 `purpose`。管理端已经把 `task` 叫作“用途”（F16），再叫 `purpose` 会混。
- **Q2 非 Main 链的类别。** 推荐：记忆、SELF、Dream、搜索桥都留 NULL，由 `task` 区分。备选：给它们也定值，例如 `structured`／`structured_retry`／`web_search`。
- **Q3 是否给 `request_chain_id` 建索引。** 推荐不建：查询都在会话或时间窗口之内，已有索引够用。建索引会在迁移时扫一次全表，以后每次写入也多一份开销。
- **Q4 是否进入管理端用量 API**（按类别筛选或分组、单独统计 compact 的成本与命中）。推荐本 issue 不做，只加列和 `ModelInvocationRecord` 字段，需要时直接查 SQL；需要的话另开 issue。
- **Q5 是否同时加 `work_id`。** 推荐不加：可以经 `runtime_work_journal.chain_id`／`chain_links` 以及 `runtime_turn_id` 关联（F15）。#649 只要求类别和链。
- **Q6 迁移 `down_revision` 与合入顺序。** 推荐按 §5：开 PR 时用 main 当时的 head；如果看门狗之后才合入，由后合入的一方改成线性顺序，`0161` 的编号不变。
- **Q7 E2E 覆盖范围。** 推荐：Responses（执行级 compact，生产形态）加 Chat Completions（公共 compact，自动与手动），不跑 Claude Messages。插件 Agent 会话的 compact（K11）只做一个隔离用例，不做完整 E2E。
