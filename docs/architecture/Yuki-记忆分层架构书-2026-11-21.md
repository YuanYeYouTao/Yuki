## 3. 目标与非目标

**目标**
1. **工作记忆**：Yuki 每一轮都带着所有者的工作规则和她自己稳定的原则，不再依赖临场想起去查。
2. **人物记忆**：面对一个人时，眼前就有这个人最稳定、最重要的少量信息，而不是几百条碎片。
3. **事件回忆**：知道有哪些事可以想起，并能按 ID 精确读到那段经历和原话。
4. **更常检索**：给出线索，让检索在该发生的时候发生。
5. **极少变动**【决定】：一段连续对话期间常驻内容不变，最大程度复用缓存前缀。

**非目标**
- 不恢复按相似度逐条注入碎片。
- 不另立第二份事实来源，不让模型写常驻散文。
- **不把私聊来源的事实放进常驻层**【决定】。
- 不改变身份、证据、生命周期、隐私删除与重建的现行合同；按需读取的权限（E13）不在本书范围内改变。
- 不把 SELF 原则写成第二份人格。
- 在评估证明必要之前，不新增核心标记表、Dream 操作或新的缓存档。

## 4. 架构

### 4.1 三层

| 层 | 内容 | 用法 | 变动 |
|---|---|---|---|
| **常驻层** | 工作规则；当前会话相关人物的少量稳定事实；经历目录 | 每轮都在提示词里 | 最多每天一批，所有者明确要求时例外；连续对话期间不变 |
| **按需层** | 其余事实、偏好、经历片段 | `search_memory`：按 `fact_id` 精确读取，或模糊搜索（E7） | 中 |
| **原始账本** | 不可变的聊天与事件记录（现有） | 需要原话时读取 | 只追加 |

常驻层的每一行都是一条现有事实，确定性渲染，附 `fact:ID`；模型不临场写散文。视图是派生的，事实被纠正、失效或隐私删除后自然一致。

### 4.2 常驻内容从哪来

分两步，第二步是否需要由 P1 的评估结果决定：

1. **工作规则：整理后的明确事实**【决定】。只用现有明确事实不够：所有者的明确事实只有寥寥几条，而且有过时内容。例如 fact 140（明确保存，2026-08-02）要求"以猫娘香草的角色交流、每句话结尾带喵"，早已不适用。工作规则按附录 A 整理，由所有者确认后以明确事实写入（证据为所有者原话或原事实）。明确事实是 Dream 的不可变锚点（E11），天然稳定，Dream 也不能改写。
2. **人物、群与 SELF：核心集**。为每个主人选出一小组稳定事实。这需要**新增**能力：一个核心标记（Q1）和一个维护它的方式（Q3）。Dream 现有操作里没有这一项（E10），第一版说"复用 Dream 现有操作"不成立。维护方式由研究阶段（§7）用数据比较后决定。

### 4.3 读路径：按变化频率分层

```
[SOUL + 核心合同 + 记忆依据规则]            部署时才变；所有会话共享
[工作规则]                                 所有者明确要求时变
  ── 断点 ──
[人物稳定事实：私聊为对方一人；群聊为本群]    最多每天一批（P1 起）
  ── 断点 ──
[经历目录：截至上次整合的部分]               每天一批（P2 起）
  ── 断点 ──
[compact 检查点 + 会话历史]                 现有
[当前消息 + 动态资料 + 当天新经历 + 发言人/被提及者] 每轮变，不缓存
```

**变动频率的依据**：Provider 的提示词缓存只保留几分钟到一小时（E6），所以要做到的是"一段连续对话期间常驻层不变"，不需要几周不变。【实证】所有者私聊一天有数百轮；常驻层最多每天变一批，同一天内这些轮次都能复用同一前缀。所有者明确加规则很少（11-21 约三到四次），每次只让缓存失效一次。

**P1 的放法**【推荐】：P1 的工作规则先作为每轮动态资料的一段，不放进 system 消息、不新增缓存档。明确规则只有十几条，即使不缓存，成本也很低。这样 P1 不碰编译器的稳定档（E5），也不触及 Work 对已提交提示词的恢复合同【假设：Work 恢复依赖原 system 内容，须在 P2 移入稳定区前核实】。P1 有效之后，再决定是否移入稳定前缀。

### 4.4 可见范围【决定】

**私聊来源的事实不进常驻层。** 理由：按需读取（E13）是 Yuki 为了回答问题主动去查，而常驻会让这些内容在每一轮都出现在上下文里，容易在群聊中被说出来，造成隐私泄露。

判定方法：现有人物事实没有可见性字段（E12），按证据来源判断（E14）。

| 会话 | 常驻层允许的事实 |
|---|---|
| 与 P 的私聊 | P 本人的事实（包括 P 在本私聊中说的）、所有者工作规则（仅所有者私聊）；**不含**其他人私聊来源的事实 |
| 群 G | 只用**证据全部来自群聊**的事实；任何一条证据来自私聊即排除（保守）。是否进一步限定为只来自本群 G，见 Q8 |
| 被提及者（尾部） | 同上，按当前会话类型过滤 |

按需读取的权限不变：Yuki 仍可在需要时用 `search_memory` 查到现行合同允许的内容。本书只约束"自动常驻"。

### 4.5 经历目录与精确读取（P2 起）

- 目录是经历片段的视图：每条一行，`日期 · 标题 · ep:ID`。最近若干天逐条列出，更早的按月折叠。
- 标题：person 经历可以从 `memory_key` 派生；SELF 经历的 key 是哈希（E3），需要一个短标题（Q9）。
- 读取：沿用 `search_memory(fact_id=…)`（E7），不新增工具。
- 可见范围同 §4.4：私聊来源的经历不进群聊目录。
- 预期效果：目录就是线索，看到条目会顺着 ID 去读。【假设】由评估集验证。

### 4.6 写路径：三条车道

| 车道 | 时机 | 做什么 | 是否改常驻层 |
|---|---|---|---|
| 快车道 | 每段对话后 | 提取写入证据层；按 #682 收紧：一次性任务指令留在 Work 上下文，不进长期记忆 | **不改**稳定区。新事实能被搜到；当天新经历出现在尾部 |
| 慢车道 | Dream 定期（现为每天 5 点） | 合并同义碎片；P1 起维护核心集（需新增能力，方式按研究 R1 结论） | 只在常驻内容实质变化时改，且批量改 |
| 直通车 | 所有者明确要求 | "记住……""以后……""把那条删了"，以明确事实写入 | 立即改，很少发生 |

### 4.7 三种需求的落地

- **工作记忆**：任务内部靠 Work 的执行日志与检查点（现有）；跨任务靠常驻的工作规则。自省写下的原则如何提升进常驻层，留到 P2 决定（Q4）。所有者的规则是明确事实，Dream 本来就不能改写（E11）。
- **人物记忆**：P1 起，常驻少量稳定事实回答"他是谁"，P2 的目录回答"我们之间发生过什么"，细节按需读取。同一人跨入口沿用现有 Person 归并。
- **事件回忆**：先看目录标题，再按 ID 读经历，需要原话时读账本。

## 6. 考虑过的方案
