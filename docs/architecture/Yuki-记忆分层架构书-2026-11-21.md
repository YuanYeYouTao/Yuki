## 3. 目标与非目标

**目标**
1. **工作记忆**：Yuki 在所有者的会话里每一轮都带着所有者的工作规则和她自己稳定的原则。
2. **人物记忆**：面对一个人时，眼前就有这个人最稳定、最重要的少量信息。
3. **事件回忆**（P2）：知道有哪些事可以想起，并能按 ID 精确读到。
4. **更常检索**：常驻条目带 `fact:ID`，给出线索。
5. **极少变动**【决定】：一段连续对话期间常驻内容不变；常驻层不打断现有缓存前缀。

**非目标**
- 不恢复按相似度逐条注入碎片。
- 不另立第二份事实来源，不让模型写常驻散文。
- **不把私聊来源的事实放进别人的会话或群聊的常驻层**【决定】。
- 不改变身份、证据、生命周期、隐私删除与重建的现行合同；按需读取的权限（E13）不变。
- 不把 SELF 原则写成第二份人格。
- 不改 Dream 的聚类算法、分区、簇上限与调度时间。
- P1 不新增缓存断点或稳定档，不做经历目录，不改提取。

## 4. 架构

### 4.1 三层

| 层 | 内容 | 用法 | 变动 |
|---|---|---|---|
| **常驻层** | 本人的明确事实（含所有者工作规则）；Dream 挑选的少量稳定事实；所有者确认的 SELF 原则 | 每轮都在当前消息的资料段里 | 挑选部分每个主人每天最多变一次；明确事实在所有者或本人要求时立即变 |
| **按需层** | 其余事实、偏好、经历片段 | `search_memory`：按 `fact_id` 精确读取，或模糊搜索（E7） | 中 |
| **原始账本** | 不可变的聊天与事件记录（现有） | 需要原话时读取 | 只追加 |

常驻层的每一行都是一条现有 active 事实的正文，确定性渲染，附 `fact:ID`；模型不临场写散文。视图是派生的：事实失效、被取代、被隐私删除后，下一次渲染就不再出现。

### 4.2 常驻内容从哪来

| 来源 | 判定 | 谁维护 | 是否需要存储 |
|---|---|---|---|
| **明确事实** | 主人本人的 person / person_group 事实，`source_type=explicit` 或 `authority=explicit`（E22） | 本人对 Yuki 说"记住……"；现有 `save_memory` / `edit_memory` | 不需要，直接查事实表 |
| **挑选的核心集** | 每个人物、每个群一份有序列表，最多 10 条 | Dream 每日批次之后的挑选步骤（§4.6） | 新表一行 |
| **SELF 原则** | 一份有序列表 | 所有者确认（Q4），用管理 CLI 写入 | 新表一行 |

所有者的工作规则不需要单独的机制：附录 A.1 的 12 条整理后由所有者以明确事实写入，它们就是所有者本人的明确事实，只出现在所有者的私聊里。明确事实是 Dream 的不可变锚点（E11），Dream 不能改写。

按 E22，明确事实不等于"本人说过记住"：主 Agent 自发为发言人保存的本人记忆同样是明确事实，会不经挑选直接常驻；某人在群里形成的明确事实，会在他每次于该群发言时出现在发言人一节。是否接受见 Q17。

现有 16 条明确事实里有过时内容（fact 140、141）和重复（fact 35 与 33）。写入附录 A 之前由所有者失效这几条（Q2）。

### 4.3 读路径与放置位置

```
[SOUL + 核心合同 + 记忆依据规则]      一条 system 消息；部署时才变            现有，不动
[compact 检查点 + 会话历史]            现有                                  现有，不动
[当前消息]
   ├─ 常驻记忆段  memory.resident      本轮渲染；内容稳定但不在缓存前缀里      P1 新增
   ├─ 当前场景等动态资料               现有
   └─ 消息正文                         现有
```

常驻段是一个新的 TURN 贡献，排在 `context.current` 之前，和它一样拼在当前消息正文前面（E4）。

**为什么不放进 system 消息**【推荐，Q6】。研究 R4 的结论是两种放法都安全，差别在成本与牵连面：

| | 放在当前消息（P1 推荐） | 放进 system 消息末尾 |
|---|---|---|
| 恢复哈希 | 不涉及 | 不涉及（E17：哈希只含核心合同与记忆依据规则） |
| compact 切片 | 不涉及（E19：当前消息不在公共压缩范围内） | system 仍是一条，`static_count` 不变 |
| 在途 Work | 首次请求时的内容留在 Work 的 transcript 里，Work 期间不变 | 同左 |
| 缓存前缀 | 现有前缀完全不变；常驻段每轮首次请求不命中缓存 | 常驻段进入缓存；内容一变，该会话的全部历史重新计费一次 |
| Claude | 不新增断点 | system 断点变成按会话；要保住跨会话共享需第 4 个断点 |
| 群聊 | 群核心、发言人、被 @ 的人在同一处 | 群核心在 system，发言人只能在尾部，两处渲染 |
| 渲染字节不稳定的代价 | 只多付常驻段本身 | 每轮全部历史失去缓存 |
| 成本（R6，所有者私聊） | 每轮约 +4.7% | 每轮约 +3.5%，另加每次变动的整段历史重计费 |

**与"极少变动"的关系**：常驻内容仍然极少变动（§4.6），变动也不会影响任何缓存前缀。它与 #681 验收里"出现在稳定前缀里"的字面要求不同，所以放置位置标为需所有者决定（Q6）。

### 4.4 可见范围【决定】

**私聊来源的事实不进别人的会话或群聊的常驻层。** 判定按证据来源（E14），不新增可见性字段。

| 会话 | 常驻层允许的事实 |
|---|---|
| 与 P 的私聊 | 主人是 P 的 person / person_group 事实，`authority` 为 explicit 或 self_report，且没有任何证据来自别人的私聊。没有证据行的旧事实在 P 本人的私聊里允许（Q14） |
| 群 G | 证据**全部**来自群 G 的会话，且至少有一条证据。证据缺失、证据事件为空、任一条证据来自私聊或其他群，都排除 |
| 群 G 里的发言人与被原生 @ 的人 | 该人物的明确事实与核心集中，满足"群 G"一行条件的部分 |
| SELF 原则 | 先按现有 SELF 可见性（global；private 只在对应人物的私聊；group 只在对应群），群聊里再套用"群 G"一行的证据条件 |

所有会话共同的条件：事实为 active、`conflict_state=clear`、未隔离、未过期；`third_party` 权威的人物事实不进常驻层（F19）；群事实（`group_report`）只在本群。

按需读取的权限不变：Yuki 仍可在需要时用 `search_memory` 查到现行合同允许的内容。本书只约束"自动常驻"。

### 4.5 经历目录与精确读取（P2，P1 不做）

R5 的结论：1112 条经历里 919 条是 SELF 经历，key 是哈希，没有可用标题；主群最近 7 天就有 67 条经历。目录要可用必须先解决标题来源与存储（Q9），那需要新的列或表，超出 P1 的上限。P1 只保证常驻条目的 `fact:ID` 都能用 `search_memory(fact_id=…)` 读到（F13）。

### 4.6 写路径：三条车道

| 车道 | 时机 | 做什么 | 是否改常驻层 |
|---|---|---|---|
| 快车道 | 每段对话后 | 现有提取，不改 | **不改**。新的自动事实只进按需层 |
| 慢车道 | Dream 每天 5 点的批次（不改时间） | 现有簇处理不变；全部簇处理完之后，新增**挑选步骤**：对有新候选的主人各做一次模型调用，更新该主人的核心集 | 每个主人每天最多一次 |
| 直通车 | 本人明确要求 | 现有 `save_memory` / `edit_memory` 写入或失效明确事实 | 下一轮渲染立即反映 |

**挑选步骤**【推荐，Q3】
- 工作单元是一个主人（人物或群），不是相似度簇，所以不经过 Dream 的分区、簇大小与簇数上限，也不产生 Dream 操作行（操作行绑定簇，回滚语义针对事实变更，而挑选只写核心集这一行）。聚类算法、调度时间与现有 6 种操作都不动。
- 输入是该主人**当前的核心集**加上**上次挑选之后新出现的候选**，要求"没有明确理由就保持不变"。输出是从这些条目里选出的有序列表，最多 10 条。程序校验每一条都在输入里、仍然符合 §4.4 的共同条件，再在一个短写事务里更新。
- 候选不含明确事实（已常驻）、经历、`third_party` 权威与有争议的事实。
- 每次运行处理的主人数有上限（默认 12），与现有 12 簇合计不超过现有的 24 次模型调用预算（E25：近 14 次运行每次都只用了 12 次；R2：每天有新候选的主人最多 9 个）。没轮到的主人留到次日，按上次挑选的先后排队。
- 所有者可以用管理 CLI 查看、改写或锁定任何一个主人的核心集；锁定后挑选步骤跳过它。

### 4.7 三种需求的落地

- **工作记忆**：任务内部靠 Work 的执行日志与检查点（现有）；跨任务靠所有者私聊里常驻的明确规则。
- **人物记忆**：私聊里常驻对方的明确事实与核心集；群聊里常驻本群核心，发言人与被 @ 的人只带可在本群出现的部分。同一人跨入口沿用现有 Person 归并，核心集按人物根 ID 存一份。
- **事件回忆**：P2。

4. "只用本群证据"（Q8 选 A）与"任何群聊证据"差别很小：所有者 91 对 104，人物 2 为 38 对 53，其余相同。

### 7.5 R4：放在哪里

**结果**【实证】
1. **恢复哈希**。`work_contract` 在主 Agent 上把传入的 system 消息换成 `invariant_messages()`（E17）。只要常驻层不加进 `invariant_contributions()`，无论放在 system 还是当前消息，哈希都不变。哈希变了也不是失败（E18）。
2. **compact**。公共压缩范围不含当前消息；`static_count` 按 system 消息条数算（E19）。常驻层放在当前消息时与压缩无关；放进 system 时仍是一条 system 消息，计数不变。只有"在 system 与历史之间插入一条独立消息"这种放法会让计数失配，本书不采用。Work 内的两种压缩都原样保留当前消息：公共压缩保留 `messages[public_count:]`（`services/context_compaction.py:405`），执行压缩的边界不早于初始消息之后（`:584`）。所以长 Work 压缩之后，常驻段仍然逐字在场。
3. **断点**。Claude 方言已用 3 个断点（E6）。Anthropic 接口单请求最多 4 个断点，这一条来自接口文档，**没有实测**（研究不允许调用生产模型）。P1 不新增断点，所以不依赖这个上限。
4. **Gemini 与 Chat Completions**。两个方言都不发缓存控制，只读命中数（E6）；命中靠 Provider 的隐式前缀缓存。生产 11-17 起主对话全部走 OpenAI（E24），生产用的是哪个 OpenAI 方言、是否开了显式断点没有核对。
5. **入口**。所有主 Agent 入口共用 `ContextAssembler.assemble`（E21），在这一处按会话身份解析常驻层即可覆盖主轮、定时任务、SELF 主动轮、外部事件与 Work 续接。子 Agent 用 `static_messages()` 加简报，不经过这里；插件轮走另一条装配路径，本轮只读到入口，没有追到底。
6. **在途 Work**。当前消息连同资料段在首次请求时进入 Work 的 transcript，合同未变的续接沿用日志里的原 transcript（`runtime/work_session.py:141-158`），所以常驻层在一个 Work 内不变。【假设：续接时 transcript 的还原没有逐行追到底，由任务书用例 17 确认】

**结论**：放进稳定前缀是安全的，但 P1 不需要。P1 放在当前消息，新增断点数为 0，不新增稳定档（Q6）。各入口带哪一份见 Q13。

### 7.6 R5：经历目录多大

**结果**【实证】（附录 B.6）
- 经历 1112 条：self 919（group 可见 702、private 可见 217）、person 115、group 51、person_group 27。
- key 可读的 193 条（17%），全部是非 SELF 经历；SELF 经历 919 条的 key 都是哈希。

**结论**：目录的长度可以接受，但 83% 的条目没有标题来源。目录推迟到 P2，先决定标题存在哪里、由谁生成（Q9）。P1 不做目录。

### 7.7 R6：常驻层的 token 成本

**做法**。按附录 A 与 A1 的候选集计算渲染字数。token 没有用分词器实测，按每个汉字 1.0–1.5 token 估【假设】。缓存命中的输入按未命中价格的 10% 计【假设，未核对生产模型的实际计价】。

**结果**（附录 B.8、C.5）

| 会话 | 常驻段内容 | 字数 | 估计 token |

|---|---|---|

| 平均每次请求输入 token | 约 48000 | 约 42000 |
| 缓存命中 | 按天 80%–94% | 按天 90%–94.5% |

| 估算（按 3000 / 1400 token） | 所有者私聊 | 主群 |
|---|---|---|

## 附录 E：策略 A 的模拟指令

两次独立运行使用同一份指令，各自读完全部 12 个候选池（10 个人物、SELF、主群）后给出 fact ID。指令要点如下，原样用于模拟：

> 对每个主人，从候选里挑出"面对这个主人时，每一轮对话都值得放在眼前"的稳定核心事实，最多 10 条，宁缺毋滥，可以少于 10 条甚至 0 条。
> - 选：身份与关系、称呼、长期稳定的喜恶与边界、长期目标或长期状况、长期有效的互动方式要求。
> - 不选：一次性任务指令或某个 PR/issue 的当次要求、当次事件、时效性强的状态、琐碎细节、玩笑梗、对某个模型或产品的随口评价。
> - 同义重复只留一条。
> - 所有者的开发流程、委派、汇报与生产边界类规则另有一节，不选进人物核心。
> - 每个人物给两份：私聊视图从全部候选里挑，敏感隐私是否入选按"对与本人相处是否必要"判断；群视图只从证据全在本群的候选里挑，不得选健康、性、财务。
> - SELF 只挑稳定的行为原则，不挑口味、人格设定、能力描述与单次教训。
> - 群只挑群规、长期约定与稳定的称呼约定。

两次运行都报告完整读完所有候选池。它们各自标注的不确定处（只含 ID）：所有者私聊都选了敏感类的 fact 2474；fact 1520 与 2188 可能互相矛盾；人物 6 的 fact 3735 可能已被 3737 更新；人物 6 的 fact 3803、3845 是否适合常驻需人工判断。

这份指令与 §4.6 推荐的生产步骤有三处不同：生产步骤是增量的（以现有核心集为基础，只看新候选）；每个主人只有一份列表（群聊里按 §4.4 过滤，不另选群视图）；模拟指令明确排除了所有者的开发流程、委派、汇报与生产边界类规则，而任务书 §7.2 的生产指令只靠"与已常驻的明确事实同义的不选"，自动保存的规则类事实（如 fact 3944）仍是候选，是否补进生产指令列在任务书 §15。按单份列表过滤后群里还剩多少，见 §7.4。
