# 私聊自动登记 Work 标记任务书

日期：2026-11-12

状态：用户在桌面端提出「私聊时若调用发送以外的工具不是会强制开一个work吗，我觉得那个work不需要在聊天主界面上显示，单独把那一类work排除一下」。本任务书为后端部分的执行依据；桌面端据此在聊天主界面隐藏这类卡片，「工作」列表照常显示。

## 1. 调研结论

- 私聊（`origin=user_message`、无群）首个包含 send 以外工具的批次，由 `TurnExecution.admit_private_execution`（`services/turn_execution.py`）调用 `WorkControl.admit_execution`（`runtime/work_control.py`）在写事务内接纳 Work，目标为占位文字「完成本人私聊请求 event:N」。
- 与 `manage_task(action=start)` 接纳的 Work 使用同一 `source_key`、同一 `source_json`、同一行形状；`runtime_work` 没有记录接纳方式的列。目标文字会被模型 `update` 改写，不能作为依据；`source_json` 有一致性校验，不能写入标记。
- 客户端 `Work` 投影（`client_api/works.py`）与 `responses.Work` 都没有可区分的字段。

## 2. 施工项

1. `WorkRepository.accept_in_session` 接受接纳时的检查点事实；`WorkControl.admit_execution` 写入 `{"admission": "host_execution"}`。之后的检查点更新只按路径 `json_set`/`json_remove`，改写目标不会抹去该事实。
2. 客户端 `Work` 投影增加 `admission`（仅取该事实，其余为 `null`），`responses.Work` 声明 `admission: str | None = None`。
3. 文档 `client-api.md` 写明字段含义。既有行没有该事实，照旧为 `null`，不回填、不推断。

## 3. 失败情形（先写，再写代码）

1. 私聊无 Work 时首个非 send 工具批次接纳的 Work，检查点没有 `admission: host_execution`。
2. 该 Work 之后被 `manage_task(action=update)` 改写目标，`admission` 丢失。
3. `manage_task(action=start)` 接纳的 Work 带有 `admission`。
4. 客户端 `GET /works/{id}` 与列表对上述两种 Work 没有分别返回 `host_execution` 与 `null`。
5. 接纳失败时（同 source 冲突）留下带标记的半成品行。
