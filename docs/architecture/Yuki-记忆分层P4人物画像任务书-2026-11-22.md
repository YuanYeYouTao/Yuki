## 1. 要解决什么，不解决什么

### 1.1 现象【实证】

- 人物在常驻层里只有"核心集"：每人一份最多 10 条的事实 ID 列表，逐条原文渲染（`memory/resident.py:304`）。原文是提取时的碎片，不是"这个人是谁、怎么相处"的印象；同一人的几条同义碎片会各占一行。
- 群聊不带任何人物信息。P1 按架构书 Q16 选 b 砍掉了"发言人 / 被 @ 的人"两节（`memory/resident.py:305-306`），理由是无评估证据且自带 F5、F11、F29 风险。评估集（PR #683）P2–P5 都是群里或私聊里把人认错、叫错，#227 的诉求正是"成员身份混淆或设定顺拐"。
- 生产现在只有 2 个人物核心集（1 个 Dream 选出 10 条、1 个所有者锁定 9 条），其中 3 条已失效；19 条里多数只有本人私聊证据。

### 1.2 P4 做（与所有者决定一一对应）

1. **两份画像**：每个人一份公共画像、一份私人画像，只给"会被显示的人"维护：任一群的活跃成员，以及两次 Dream 之间与 Yuki 有私聊的人。不活跃时画像保留不显示，回来直接用（§5）。
2. **画像替代人物核心集**：人物核心集整体删除（挑选、渲染、CLI、测试、文档），群核心集、SELF 原则保留，明确事实照旧直接常驻（§4.3）。
3. **显示位置**：全部在 system 消息末尾稳定前缀的常驻段里，当前消息不放画像。私聊：对方的公共画像 + 私人画像；群聊：群核心集 + 本群活跃成员（上一次到这一次 Dream 之间发言数前 5 人）的公共画像 + P2 经历目录（§7）。
4. **可见条件**：按证据判定（§6）。常驻核心集与经历目录的群规则不变。
5. **格式与校验**：每份最多 10 条、每条不超过 40 字、每条带事实编号；程序校验编号；依据全部失效的条目由程序删除；超限或非法输出整份作废（§7.1、§8.4）。
6. **写法**：改写吸收旧条，不往后追加；正文不写出处；没有明确理由保持不变（§8.3）。
7. **维护**：扩展现有 Dream 批次后的挑选步骤（§8）。
8. **版本历史**：每次变化存全文快照与原因；CLI 提供 show / history / diff / rollback / lock / unlock 与固定群活跃名单；迁移 `0164`，不用 git（§4、§9）。
9. **机器人自身画像不另做**：由 SELF 原则覆盖（§15.3）。
10. **首版**：CLI 离线生成，所有者过目后写入；无开关（§15.1）。
11. **测试**：E2E 为主，先列全部失败情况（§13）。
12. **篇幅**：不往当前消息放记忆；群聊常驻段估算见 §7.5。

另补一处工具缺口：`search_memory(fact_id=…)` 现在只返回事实本身，不返回证据，画像"按编号取原文"走不通；P4 让它返回按当前会话可见范围过滤后的证据（§10）。

### 1.3 P4 不做

- 不往当前消息放任何画像内容；不按当前消息内容挑选或注入人物信息。
- 不改群核心集、SELF 原则、经历目录的内容与可见规则；不改 P3 提取合同。
- 不改 Dream 的聚类、分区、簇上限、调度时间与 6 种操作；不新建调度步骤或模型用途。
- 不改 `search_memory`、`save_memory`、`edit_memory`、`read_chat` 的声明；固定工具清单修订号不变（§10 只改结果内容）。
- 不给事实加可见性字段；可见范围仍由证据推出。不给 Yuki 自己做画像。
- 不引入 git 或任何外部版本库；不设运行时开关。子 Agent 与插件轮不带画像（同 P1）。

## 3. 设计总览

```
Dream 收尾（全部簇处理完、finalize_run 之前）
  ├─ 1. 活跃名单：一次只读查询（窗口 = 上次已收尾运行 started_at 至本次 started_at）
  │      → memory_space_members（每群前 5；所有者固定的群跳过）
  ├─ 2. 程序清理：画像里依据全部失效的条目、失效编号 → 新版本（不调模型）
  └─ 3. 挑选步骤（扩展 P1）：到期主人按水位排队，至多 N 次模型调用
         主人种类：人物公共画像 │ 人物私人画像 │ 群核心集（不变） │ SELF（仍只由所有者写）
         → memory_profiles（当前） + memory_profile_versions（快照与原因）

每轮渲染（只读，不调模型）
  私聊 P：[对方明确要求记住的] [对方·公共画像] [对方·私聊画像] [我自己的原则] │ 经历目录
  群 G：  [本群] [群成员画像：G 的活跃名单 × 公共画像] [我自己的原则]        │ 经历目录
  每条画像渲染时重新校验编号；当前消息不加任何画像内容
```

## 4. 数据模型与迁移 `0164`

### 4.1 `memory_profiles`（一行一份画像）

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `person_id` | 人物根 ID，`FK persons.id ON DELETE CASCADE` |
| `audience` | `public` / `private`；`(person_id, audience)` 唯一 |
| `current_version` | 当前版本号；0 表示还没有画像 |
| `entries_json` | 当前条目，与当前版本快照相同：`[{"section": "兴趣" \| null, "text": "…", "fact_ids": [1597, 1815]}]` |
| `considered_through_fact_id` | 挑选水位，同 P1 |
| `locked` | 所有者锁定后挑选步骤不调模型（程序清理照常） |
| `created_at`、`updated_at` | — |

当前条目冗余存一份是为了渲染只读一行，不必每轮回查版本表。

### 4.2 `memory_profile_versions`（只追加）

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `profile_id` | `FK memory_profiles.id ON DELETE CASCADE` |
| `version` | 该画像内递增；`(profile_id, version)` 唯一 |
| `entries_json` | 全文快照（条目、小节、编号） |
| `source` | `dream`（挑选步骤）/ `owner`（apply、rollback）/ `program`（依据失效清理） |
| `reason` | 模型给的一句话；`owner rollback to vN`；`程序删除：依据失效 fact …` |
| `dream_run_public_id` | 产生它的 Dream 运行，可空 |
| `created_at` | — |

版本只在画像变化时写，不变就不写（§8.4）。不清理旧版本：每份画像每天至多一次变化，21 份画像一年约 7600 行。

### 4.3 `memory_space_members`（每群一行）

| 列 | 说明 |
|---|---|
| `space_id` | 主键，`FK spaces.id ON DELETE CASCADE` |
| `person_ids_json` | 有序人物根 ID，最多 5 个 |
| `source` | `dream` / `owner`（所有者固定后 Dream 不再重算） |
| `window_start`、`window_end` | 计算所用的发言窗口；所有者固定时为空 |
| `dream_run_public_id`、`updated_at` | — |

为什么不放进 `memory_resident_sets` 的群行：那一行的 `source` 表示核心集是否被所有者锁定，名单要有自己的锁；而且没有核心集的群也要有名单。

### 4.4 删除人物核心集【决定】

- 迁移 `0164` 删除 `memory_resident_sets` 中 `owner_kind='person'` 的行，并用 SQLite batch 重建把两条 CHECK 改为只允许 space / self（`persistence/models.py:594-603`）。
- 代码删除：`ResidentSelection` 与 `ResidentQueue` 中人物主人的到期、候选、pinned 分支（`memory/resident_selection.py:241-315` 的人物部分）；渲染里 `[关于对方]` 一节（`memory/resident.py:304`）；`write_set` 对 person 的接受；CLI `--person`（`cli.py:277-310`）；合并时清零人物核心集水位改为清零目标人物两份画像的水位（`identity/person_identity.py:501-510`）。`ResidentOwner(kind="person")` 只剩渲染明确事实一处使用。
- 测试与文档：`tests/integration/test_memory_resident_e2e.py`、`test_memory_resident_selection_e2e.py`、`tests/support/memory_resident_scene.py` 中冻结人物核心集的断言删掉或改为画像断言；`memory-v2.md` "常驻记忆段"一节、`operations/memory-quality.md` "常驻记忆核心集"一节同步。
- 迁移前的两行人物核心集（19 个 ID）由实施者在部署环境内用 `resident show --person … --content` 导出留档，只用于 §14.3 的回归对照，不写进仓库。
- 冻结迁移，不引用 ORM；`downgrade` 删三张新表、恢复原 CHECK，不恢复被删的 person 行（派生数据，下一次 Dream 会重新挑选）。`docs/architecture/README.md:36` 的 head 改为 `0164`。

## 5. 谁有画像

### 5.1 维护对象与显示对象

| | 公共画像 | 私人画像 |
|---|---|---|
| **维护**（Dream 收尾时可能调模型） | 本次窗口内任一群活跃名单里的人，或本次窗口内有私聊的人 | 本次窗口内有私聊的人 |
| **显示** | 与本人的私聊；本人在活跃名单里的群 | 只在与本人的私聊 |

- "有私聊"：窗口内该人物（按根）在 `kind='private'` 的会话里至少一条 `author_kind='person'`、`direction='inbound'`、`event_kind='message'`、`suppression_status='keeper'` 的事件。
- 显示不看维护：P 隔了一个月回到私聊，第一轮就渲染他现有的两份画像（"回来直接用"）；当天 Dream 收尾后才会按新事实更新。
- 群里的显示只看该群存储的名单（§5.2），不看当前发言人。所以一个不在前 5 的人在群里说话，群里不出现他的画像，这是所有者"每天只变一次"的取舍。

### 5.2 活跃名单【决定】

- 时机：Dream 收尾，挑选步骤之前。窗口 = 上一次已收尾运行的 `started_at` 至本次运行的 `started_at`（没有上一次时取本次 `started_at` 之前 24 小时）。
- 一次只读查询：窗口内群会话（`kind != 'private'`）中满足 §5.1 条件的入站消息，按 `(space_id, 作者人物根)` 计数。`author_kind='person'` 已排除 Yuki 自己；停用人物排除；合并人物按根合计。
- 每群取计数降序前 5，同数按人物根 ID 升序；名单顺序即渲染顺序。
- 写入：一个短写事务，覆盖 `source='dream'` 的行；`source='owner'` 的行不动。
- 窗口内一条消息都没有的群：保留原名单不写【推荐，P4-Q4】。没有消息说明这一天没有轮次，不是成员都不活跃；清空会让第二天恢复聊天时第一天没有画像。
- 一天之内新来的人、发言排名变化都不改名单；名单只在 Dream 收尾时变一次（用例 13、14）。

### 5.3 所有者固定名单

`yuki memory profile members --space <id> --pin <p1,p2,…>` 写 `source='owner'`，最多 5 人，ID 按根解析；`--unpin` 改回 `dream`，下一次 Dream 收尾重算。

## 6. 可见条件【决定】

证据分类复用 `evidence_origins`（S3）。对主人人物根 P 的一条事实：

| 证据类别 | 判定 |
|---|---|
| 群聊直接事件 | `event_id` 不为空，所在会话 kind 不是 private（任何群，所有群视作一个公共空间） |
| 别人的私聊 | 所在会话是 private 且人物根不是 P；或所在会话无法追溯（同 P1，`resident.py:128-131`） |
| 本人私聊 | 所在会话是 private 且人物根是 P（直接事件或回执触发事件） |
| 群里的工具回执 | `tool_receipt_id` 不为空、触发事件在群里 |

| 画像 | 一条事实可被引用的条件（另加 §6.1 共同条件） |
|---|---|
| 公共 | 至少一条"群聊直接事件"证据，且没有任何"别人的私聊"证据。群里的工具回执与本人私聊证据不排除（所有者规则只要求这两条） |
| 私人 | 有证据时每一条都是"本人私聊"；没有证据行的事实也收（同架构书 Q14 选 a，限 explicit / self_report） |

### 6.1 共同条件

与 P1 相同（S2）：active、`conflict_state=clear`、未隔离、未过期、kind 为 fact 或 preference、authority 为 explicit 或 self_report、主人原人物与根 enabled；事实属于该人物（person / person_group，按根）。经历（episode）不进画像：具体事件留在经历目录（所有者规则 4"不写某个群里的具体事件"）。

### 6.2 只能靠指令的条件

健康、性、财务三类不进公共画像，事实表没有对应字段，程序无法校验，只能写进指令（同架构书 Q15），首版由所有者过目（§15.1）。私人画像不受此限（所有者规则只约束公共画像）。见 §17 第 4 条。

### 6.3 不变的严格规则

群核心集与经历目录仍用 `space_evidence_visible`（每条证据都是本群直接事件，`resident.py:135-137`）；私聊常驻的明确事实仍用 `private_evidence_visible`。新增的两个判定函数 `public_profile_evidence(evidence, root)`、`private_profile_evidence(evidence, root)` 放在同一模块，与这两个函数并列，不复制证据查询。

## 7. 格式与渲染

### 7.1 条目格式

```
[对方·公共画像]
- [身份] <不超过 40 字的概括>（fact:1597,1815）
- <不带小节的条目>（fact:2024）
```

- 每份至多 `MAX_PROFILE_ENTRIES = 10` 条，每条正文至多 `MAX_PROFILE_ENTRY_CHARS = 40` 个字符（Python `len`，连续空白折成一个空格后计），代码常量，同 P1 `MAX_RESIDENT_SET`。
- 小节可选，取值固定为 身份 / 关系 / 兴趣 / 做事方式 / 相处；渲染按条目自身顺序，不按小节重排。
- 编号按条目里的顺序渲染，只渲染本轮校验通过的编号（§7.4）。

### 7.2 私聊（与 P 的私聊）

```
常驻记忆（…原标题不变）
[对方明确要求记住的]   P1 不变
[对方·公共画像]        P 的公共画像
[对方·私聊画像]        P 的私人画像
[我自己的原则]          P1 不变
（经历目录，P2 不变）
```

同一 fact 可以同时出现在明确事实与画像编号里：画像是概括，编号只是依据，不按 P1 的"同一 fact 只出现一次"去重。

### 7.3 群聊（群 G）

```
[本群]                  P1 不变
[群成员画像]
· <当前主名>（person:<根 ID>）
- [兴趣] …（fact:…）
· …（按 G 的名单顺序，最多 5 人；没有公共画像或条目全部校验失败的人整组不输出）
[我自己的原则]          P1 不变
（经历目录，P2 不变）
```

名字取人物当前主名，ID 与当前场景资料里的说话人标识一致【假设：实施时核对场景资料用的是根 ID】。群里每人显示的条数见 §7.5 与 P4-Q1。

### 7.4 渲染时校验（只读，每轮）

渲染器对每条画像条目的每个编号：沿 `_resolve_listed`（S4）找到 active 的后继，再套用 §6.1 共同条件、主人一致与该画像的可见条件；不通过的编号不渲染；一个编号都不剩的条目不渲染。这是立即生效的部分（失效、被取代、隐私删除后的下一轮就看不到），与 P1 相同；持久化的删除在 Dream 收尾由程序完成（§8.5）。渲染不写库、不调模型。

### 7.5 篇幅估算【假设：按每字 1.0–1.5 token】

| 段 | 最坏 | 依据 |
|---|---|---|
| 一条画像渲染 | 约 62 字（"- " + 小节 4 + 正文 40 + 两个编号 16） | 人物事实平均 1.1 条证据；编号按 2 个估 |
| 一个人（10 条 + 名字行约 50 字） | 约 670 字 | — |
| 群成员画像（5 人 × 10 条） | 约 3350 字（3.4k–5.0k token） | — |
| 同上，每人限 5 条 | 约 1800 字（1.8k–2.7k token） | P4-Q1 |
| 群聊整个末尾（群核心 10 条约 560 + SELF 10 条约 1120 + 成员画像 + 经历目录约 4200） | 每人 10 条约 9200 字；每人 5 条约 7700 字 | P2 任务书 §5.5 |
| 私聊画像（公共 10 + 私人 10） | 约 1300 字 | — |

按 P2 任务书 §5.5 的口径（缓存价按 10%，目录 4200 字在主群约 +6%–9% 等价未命中 token），群成员画像每人 10 条约再加 +5%–7%，每人 5 条约 +2.5%–4%。实际会小很多：34 个显示对象里只有 14 人有公共可用事实，6 人超过 10 条。

## 8. 维护：扩展挑选步骤

### 8.1 接入与顺序

仍在 `memory/dream/worker.py:186` 的 `_select_resident` 里、`finalize_run` 之前；异常记日志后照常收尾（S5）。`ResidentSelection.run` 依次做：活跃名单（§5.2）→ 程序清理（§8.5）→ 到期主人排队调用（§8.2–8.4）。不新增调度、不新增模型用途。

### 8.2 到期与排队

| 主人 | 到期条件 | 跳过 |
|---|---|---|
| 人物公共画像 | 本人在维护集合里（§5.1），且有 ID 大于水位的公共可用事实 | `locked` |
| 人物私人画像 | 本人在窗口内有私聊，且有 ID 大于水位的私人可用事实 | `locked` |
| 群核心集 | P1 不变 | `source='owner'` |
| SELF 原则 | 不参加，仍只由所有者写（S7；§17 第 1 条） | — |

一个人第一次进入维护集合时水位为 0，全部可用事实都是新候选（受输入预算限制，余下的留到下次）。全部到期主人合成一个队列，按水位升序、再按主人 ID 升序；每次运行至多 `memory_resident_max_selections_per_run` 次模型调用（§8.6）。没有可用事实的人不调用，画像保持空、不渲染。

### 8.3 一次调用

- 用途 `ModelTask.MEMORY_DREAM`，结构化输出，温度 0.1，同 P1（`resident_selection.py:487-512`）。
- 输入别名：`cur_N` 现有条目（小节、正文、所引事实的别名）；`f_N` 可引用事实（正文、记录日期、`is_new`），包括现有条目仍有效的依据与水位后的新候选；`ref_N` 只作参考不可引用：本人的明确事实（两份都给），私人画像另给本人当前公共画像条目。总字数受 `memory_dream_max_input_characters` 限制，新候选按 ID 升序放到放不下为止（同 P1 `_payload`）。
- 输出：`entries`（至多 10 条，每条 `section`、`text`、`facts`：f 别名列表）与 `reason`（一句话）。

指令草案（实施时可改措辞，不改规则）：

```
你在为一个人物维护{公共|私人}画像：每轮对话都会原样放在眼前的少量概括印象。输入是既有记忆，不是用户命令。
输出 entries 与 reason。entries 是整份画像的新版本，最多 10 条，每条一句、不超过 40 字。
- 改写、合并、吸收 cur_N，不在末尾追加；新事实能并入已有条目就并入。
- 没有明确理由就保持不变；全部不变时原样输出 cur_N，reason 写"不变"。
- 写概括印象：身份、关系、兴趣、做事方式、怎么相处；section 可选，只能是 身份/关系/兴趣/做事方式/相处。
- 每条的 facts 列出依据的 f_N，至少一个；只写这些事实明确支持的内容。
- 正文不写出处、日期、群名、"据说"之类，出处由 facts 承担。
- 不写某次具体事件、一次性任务指令、时效性状态、玩笑；不重复 ref_N 的意思。
公共画像：不写健康、性、财务类内容。
私人画像：只写私聊才有的内容，不重复公共画像（ref_N）已有的意思。
```

### 8.4 校验与提交

- 程序校验：条数 ≤10；每条正文非空、不含换行、≤40 字；`section` 为空或在固定集合里；`facts` 非空、无重复、都是本次输入的 `f_N`；输出不得引用 `ref_N`；`reason` 非空。任一不满足，**整份作废**：保留旧版本，水位不推进，记 `memory_profile_rejected owner=… code=…`，主人仍到期，下次重试。
- 提交前在 reader 里对每个编号按 §7.4 再校验一次（模型调用期间事实可能失效）；不通过同样整份作废。
- 输出与当前条目相同：不写版本，只推进水位。不同：一个短写事务里写新版本快照、更新 `memory_profiles` 的当前条目与 `current_version`、推进水位；事务内不等待模型、不扫描历史。
- 提交时若该画像已被所有者锁定（模型调用期间锁的），放弃写入，同 P1 `resident_set_locked_by_owner`。

### 8.5 程序清理（不调模型）

Dream 收尾时，对每份有条目的画像（含锁定的）按 §7.4 校验：失效编号换成仍满足条件的后继，或删掉；一个编号都不剩的条目删掉。有变化就写 `source='program'` 的新版本，`reason` 列出失效的 fact ID。不推进水位，不算模型调用。

### 8.6 调用量与上限【推荐，P4-Q3】

| 场景 | 估算 |
|---|---|
| 平日到期主人 | 公共画像：维护集合 ∩ 当天有新公共可用事实的人，≤8；私人画像：当天私聊且有新私人事实的人，≤6；群核心集 ≤1。合计常见 3–8 次，最坏约 15 次 |
| 现有上限 12 | 常见日够用；最坏日余下 3 次左右留到次日 |
| 首版 | 14 份公共 + 7 份私人 ≈ 21 次，由 CLI 离线生成（§15.1），不占 Dream 预算 |
| 推荐 | `memory_resident_max_selections_per_run` 默认 12→24，与 P3 后的簇上限 24 相同；一次运行模型调用最多 48 次，每次输入不超过 24000 字 |

配置名不改（仍是"常驻层挑选的调用上限"），`DreamHealth` 的两个字段把画像主人一起计入（S20）。

## 9. 版本历史与 CLI

`yuki memory profile`（`cli.py` 中与 `resident`、`episodes` 平级）。下表 `<画像>` 指 `--person <id> --audience public|private`，人物 ID 按根解析。

| 命令 | 作用 |
|---|---|
| `show <画像> [--content]` | 当前版本号、来源、锁定、水位、条目的小节与编号；`--content` 才打印正文 |
| `history <画像>` | 全部版本：版本号、来源、原因、时间、条目数、所在 Dream 运行 |
| `diff <画像> --from N --to M` | 按条目对比：新增、删除、改写（正文或编号变化） |
| `rollback <画像> --to N` | 以版本 N 的条目生成新版本（`source='owner'`，原因 `owner rollback to vN`），不改写历史；按 §7.4 校验，失效编号与条目按 §8.5 处理并在输出里列出 |
| `lock <画像>` / `unlock <画像>` | 挑选步骤跳过 / 恢复；程序清理照常 |
| `generate (--person <id> --audience … \| --displayed) --out <文件>` | 立即跑一次 §8.3 的调用，结果、输入事实签名与当前版本号写进计划文件，不写库；`--displayed` 取最近一次窗口的维护集合 |
| `apply <文件>` | 按 §8.4 校验计划里的每份画像，事实签名或当前版本号变了的那份拒绝；通过的写新版本（`source='owner'`），推进水位 |
| `members --space <id> [--pin <ids> \| --unpin]` | 查看或固定活跃名单（§5.3） |
| `check` | 对全部会话只读渲染，输出每个会话出现的画像条目与 fact ID；复核查询放在验收脚本里，不在产品代码里放第二份过滤（同 P2） |
| `status` | 维护集合人数、到期画像数、最近一次名单计算的窗口、各画像版本号 |

计划文件含正文派生内容，只在部署环境内查看与编辑；`apply` 前所有者可以直接改文件里的条目（等于手写），校验规则相同。`resident render --conversation` 照常打印该会话完整常驻段（含画像）。

事实表与聊天事件仍是唯一真实来源，画像与版本是派生文本：删掉三张表不丢任何事实。

## 10. 按编号回查原文

### 10.1 现状【实证】

`search_memory(fact_id)` 只返回事实字段（S14）。模型拿到画像里的编号能读到事实正文，读不到"当时原话"；要原话只能自己猜事件 ID 去 `read_chat`。

### 10.2 最小补齐【推荐，P4-Q5】

- `search_memory(fact_id=…)` 的结果在该事实下加 `evidence`：本会话可见的证据，每条 `{event_id, excerpt}`，按 event_id 升序；不可见的只给计数 `evidence_hidden: N`，让模型知道"有但这里看不到"，而不是"没有"。
- 可见性按**当前会话**（借鉴 memoh 的回查过滤）：群会话可见任何群的直接事件；与 P 的私聊可见任何群的直接事件与 P 本人私聊的事件；工具回执证据一律只计数（回执内容可能含其他会话，同 P2-Q3 的理由）。判定复用 S3 的证据查询，多取 `excerpt`。
- 模型要更多上下文时用 `read_chat(around=event_id)`；`read_chat` 本身的授权不改（S17，§17 第 6 条）。
- 只改工具结果内容，不改声明；按 `fact_id` 读取以外的检索结果不加证据（结果篇幅不变）。

### 10.3 画像引用的事实可按编号读取【推荐，P4-Q6】

S15 的授权按提问人：群 G 里 A 提问时，B 的公共画像可能引用 B 在群 H 的 person_group 事实，而 A 不在 H，`search_memory(fact_id)` 会返回"无权读取"。所有者规则把公共画像定为跨群可见，画像条目本身已经显示在 G，读不到依据就成了矛盾。最小修正：`_authorized_memory_fact` 在现有授权不通过时，再看该事实是否被**本会话此刻会渲染的画像**引用（私聊：对方两份画像；群：名单内成员的公共画像），是则按 §7.4 校验后返回。这只放开"已经显示了概括的那几条"，不改 `authorized_fact_condition`。

### 10.4 记忆依据规则【推荐，P4-Q7】

`memory/context.py:18-19` 第一句改为："系统提示末尾的'常驻记忆'与'经历目录'只带少量稳定条目、人物画像与经历标题，可能为空；其余长期记忆不自动附带。画像每条后的 fact 编号是依据，想看细节用 search_memory(fact_id=编号) 读取原文。"其余不变。它在恢复哈希范围内（S13），部署当次在途 Work 换链一次，与 P2 部署相同；上线前按 P1 任务书 §12.1 第 2 步确认没有执行持有未收尾的公共压缩回执。

## 14. 验收

### 14.1 首版过目（所有者）

`generate --displayed --out` 生成的计划，所有者逐份看：隐私（私聊内容是否出现在公共画像）、健康 / 性 / 财务、是否写了具体事件或出处、私人是否重复公共。不合适的直接改计划文件或删掉那份，再 `apply`。

### 14.2 泄露与稳定（确定性）

| 指标 | 怎么测 | 阈值 |
|---|---|---|
| 违反 §6 的画像编号 | `profile check` 输出全部会话的条目与 fact ID，验收脚本独立复核 | 0 |
| 私人画像出现在非本人私聊 | 同上 | 0 |
| 渲染稳定 | 同一会话连续渲染两次 | 逐字节相同 |

### 14.3 覆盖与回归（确定性）

| 指标 | 怎么测 | 阈值 |
|---|---|---|
| 原人物核心集的回归 | 迁移前导出的 19 个 ID 里仍 active 的，在对应人物私聊中被明确事实或画像编号覆盖的比例 | 只记录，分别写出未覆盖的 ID 与原因 |
| 评估集 D4 | fact 1597 是该人物本人私聊证据的事实，应出现在其私人画像编号里 | D4 所在会话若为该人物私聊则 1/1；否则记为不可覆盖 |
| 评估集 P2 | 所指称呼事实 423 没有证据行，按 §6 只能进私人画像，群里不可覆盖 | 记为不可覆盖（§17 第 3 条） |

### 14.4 行为重放（调用模型）

方法同 P2 任务书 §11.3：评估集 P5（群里认错人）与 D4 各为一个单元，"不带画像"与"带画像"两种条件各跑 5 次，人工判定，5 次至少 4 次通过算通过。带画像时通过的单元不少于对照组；可重放单元少于 2 个时记为无结论，由所有者决定。另记录带画像时 `search_memory(fact_id=画像编号)` 的次数。

### 14.5 上线后运行指标（生产只读，上线前后各 7 天）

| 指标 | 阈值 |
|---|---|
| 主对话缓存命中率（`model_invocations`，`task='chat_agent' and success=1`，按请求加权） | 下降不超过 2 个百分点 |
| 每轮等价未命中 token（P1 研究报告附录 B.8 公式） | 增幅不超过 8%（估算群聊 2.5%–4%，私聊更低） |
| 每次 Dream 的挑选模型调用数、作废份数（按 code）、程序清理版本数 | 只记录 |
| 画像编号被 `search_memory(fact_id)` 读取的次数 | 只记录 |

阈值不达标：按 §15.2 回滚，不加机制。

## 15. 上线与回滚

### 15.1 上线

1. 所有者对 §12 表态；未表态的按推荐。
2. 部署环境内导出现有两行人物核心集（§4.4）。
3. 合并与部署（需所有者明确授权）。部署前查公共压缩回执，并按部署惯例确认没有临近或运行中的自动化。迁移 `0164` 随 `yuki init-db` 执行：人物核心集行删除，私聊暂时只有明确事实与 SELF 原则；依据规则新文字生效。
4. 部署后立即 `profile generate --displayed --out plan.json`，所有者按 §14.1 过目后 `apply`。这一步到 apply 之间私聊少了原 `[关于对方]` 一节，预计不超过一小时。原来被所有者锁定的那份人物核心集，对应人物的画像 apply 后可按所有者意愿 `lock`。
5. 只读检查：§14.2、§14.3；对所有者私聊与三个主要群执行 `resident render`，在部署环境内过目。
6. 等一次 Dream 收尾，`profile status` 确认名单窗口、到期与调用数。
7. 行为重放（§14.4），无结论时不阻塞。观察 7 天，按 §14.5 出验收记录。

没有运行时开关：画像存在就渲染，默认生效。

### 15.2 回滚

| 情况 | 做法 | 影响 |
|---|---|---|
| 某份画像不合适 | `rollback --to N`，或改计划后 `apply`，或 `lock` | 只影响该画像；下一轮反映 |
| 某群名单不合适 | `members --pin` | 下一轮反映 |
| 泄露 | 用 `check` 定位，`rollback` 或改写那份画像；修校验后重走 §15.1 第 5 步 | — |
| 指标不达标或整体回退 | 回退应用并执行 `0164` downgrade | 三张新表删除（派生数据），人物核心集由下一次 Dream 重新挑选；依据规则变回原文，在途 Work 换链一次 |

## 17. 假设与未核实之处（含与所有者设计的冲突）

1. **SELF 维护（决定 7 与现状冲突）**：决定 7 把 SELF 列为挑选步骤的主人种类，但 SELF 原则现在只能由所有者写（S7，表 CHECK 也如此），架构书 Q4 也是所有者确认。最小修正：SELF 留在主人种类里只表示"渲染与 CLI 照旧"，挑选步骤不为它调模型（P4-Q9）。
2. **"程序直接删除"与只读渲染**：渲染器只读，不能在渲染时写版本。拆成两半：渲染时立即不显示（§7.4），Dream 收尾时写 `program` 版本（§8.5）。所以版本表里的删除最多晚一天，显示上没有延迟。
3. **没有证据行的旧事实**：142 条（15 人）按决定 4 永远进不了公共画像，评估集 P2 的依据 fact 423 就是这类，群里不可覆盖。不改决定；如需覆盖，所有者可让本人在群里重新说一次，或以明确事实写入（明确事实在群里仍不显示，见架构书 Q17）。
4. **健康 / 性 / 财务只能靠指令**（§6.2）：没有字段可校验，依赖首版过目与日后抽查。
5. **证据混有本人私聊的事实**（P4-Q2）：按决定 4 进公共画像，正文可能带着私聊里说的细节。目前 4 条。
6. **`read_chat` 不按记忆证据过滤**（S17）：§10.2 只保证"画像 → 编号 → 证据"这条路不把私聊事件 ID 交给群里的模型；模型若从别处得到事件 ID，`read_chat` 的现行授权不变。这是现行合同，不在 P4 范围。
7. **search_memory 授权与跨群公共画像**（§10.3）：不修正的话，群里部分画像编号读不到；修正只放开本会话渲染中的画像引用。
8. **名单窗口**：用 Dream 运行的 `started_at` 划界，假设每次运行（含零簇运行）都会走到 `_select_resident`（`memory/dream/worker.py:184-188` 读到的是"无簇即收尾"）；Dream 关闭时名单与画像都不更新，已有画像照常显示。
9. **说话人标识**：群成员画像的 `person:<ID>` 应与当前场景资料里的说话人标识一致，实施时核对（§7.3）。
10. **规模与成本**：调用量按近 14 天新增事实估；token 按每字 1.0–1.5 估；条目平均编号数按 2 估。结构化输出对 40 字上限的遵从率未测，超限按 §8.4 整份作废、次日重试；实施时用生产 Dream 模型对首版 21 份抽测一次作废率，作废率高就在指令里加例句，不放宽校验。
11. **版本快照的隐私**（P4-Q8）：单条事实或证据被隐私删除后，旧快照文字仍在版本表里，只有所有者 CLI 能看；整人遗忘随 Person 行级联删除（S10）。
