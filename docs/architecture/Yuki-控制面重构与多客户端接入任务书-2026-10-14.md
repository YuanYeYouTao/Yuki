## 0. 先读这一节

**结论：新控制面不是“换一个更好的 WebUI”，而是两条分开的入口——管理控制面和个人客户端入口——都接到同一套 Person、Conversation、Work、Social 回执和 Workspace 上。** 旧 WebUI、`webui/`、`control_plane/` 的 WebUI 查询命令层和约 1 万行 `persistence/control_*` 读模型整体退役；`/ai` 管理命令仍在用的授权对象与命令回执留下并迁出。

五个直接影响实施的判断：

1. **个人客户端按“第一方网关”接入，而不是另造会话系统。** 现有 GatewayProvider／Registry 本来就是可替换网关的扩展点。新增一个 `app` Provider 和一个 Yuki `app` Presence，个人端消息走现有入账、身份、Main、Work 和 Social 路径；发给个人端的回复仍由 Social 在同一短事务里写出站事件与成功回执；没有外部网络效果，但事务提交确认丢失时同样按原 operation ID 查证，不当作“不会未知”。
2. **跨端接续靠已有的持久事实就够，第一版不需要 CRDT 或新事件日志。** `chat_events.id` 是持久单调游标，Work 有 `revision`。订阅登记完成后先发当前状态 `sync`，覆盖快照与订阅之间的窗口；丢提示时结束订阅，让客户端自动重连后再次 `sync` 并补读。SSE 不承载事实。
3. **私聊跨端延续同一个 Conversation。** canonical 合同规定私聊按 Person 唯一，QQ 私聊和 App 对话本来就是同一个 Conversation；手机能看到电脑上开始的任务与结果，不需要合并历史。群聊第一版不进入个人客户端。
4. **ACP 两个方向都不进入本次交付。** ACP 稳定版 1.11.0 只有 stdio；远程 HTTP/WebSocket 传输仍是 Active RFD，v2 仍为 draft。服务器常驻的 Yuki 若要被 Lody 等客户端接入，需要一个本地 stdio 适配进程，再走本次的个人客户端 API。推荐在个人 API 稳定后先做方向 A，方向 B 等 S8 再定。
5. **第一个完整体验在 #299 内做到“契约级可验证”，真机体验属于 S4/S5。** 本次交付两个独立设备凭据、参考 Python 客户端和故障注入测试，证明“电脑交办 → 关闭 → 手机接回 → 补充 → 取结果”在服务端成立；Android UI 与真机验收按路线图另做。

需要你决定的事项集中在 [§9.3](#93-需要你决定的实质问题)，共 5 项，其余实现选择本文已给出推荐。

### 1.2 目标

1. 删除旧 WebUI 与旧控制面实现，不留第二套控制面、改名包装或永久兼容层。
2. 建立两个入口：**管理控制面**（operator 配置、插件、诊断、管理操作）和**个人客户端入口**（Person 自己的对话、任务、结果和文件）。两者共用领域服务，身份与授权分开。
3. 让第一个完整体验在服务端成立：电脑交办长任务，关闭电脑端，手机看到同一任务、补充要求，最后取得原任务结果与文件。
4. 留出 ACP、设备执行器、语音与角色呈现的接入边界，但不预造接口。

### 1.3 不在本次范围

Android/桌面正式 UI（S4/S5）、推送通知、语音输入输出、角色渲染、设备执行器（S6/S8）、ACP 适配（§4）、群聊进入个人客户端、新的浏览器管理 UI。#300 的其他社交渠道可以复用本次的第一方网关经验，但不在本次实现。

## 3. 外部项目：证据、采用理由与不采用部分

### 3.1 Lody（`8971b66e`）

**它是什么。** 以 Loro CRDT 文档为事实载体的团队编码 Agent 工作台：每台机器跑一个 CLI daemon，daemon 作为 **ACP 客户端**启动 Claude Code、Codex 等 Agent；会话、历史、权限请求写入 Loro 文档，由托管 “Streams” 同步给桌面、Web、手机和 CLI。公开仓库只包含 `apps/{cli,electron}` 与共享包，托管后端、Web 与手机源码不公开（[AGENTS.md#L56](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/AGENTS.md#L56)）。因此下文凡涉及服务端授权与手机端行为，只能依据公开协议和文档，不能视为源码已证实。

| 关注点 | 源码／文档事实 | 对 Yuki |
| --- | --- | --- |
| 分工 | daemon 拥有 Agent 进程与会话执行；桌面 renderer 通过本地 socket 同步 Loro 文档，“Two planes”：本地数据面与云房间状态分开，不轮询、无请求/响应 HTTP（[cli-lib-local-loro-data-plane.md#L93](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/.agents/docs/cli-lib-local-loro-data-plane.md#L93)） | Lody 的执行在用户机器上，所以需要多端可写的同步文档。Yuki 执行在服务器，事实已在 SQLite，不需要 CRDT |
| 机器在线 ≠ 有权限 | presence 心跳与访问校验是两件事；访问服务不可用时重试有界，之后返回可重试错误且不创建工作，不把“不可用”当允许（[session-access-verification.md](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/session-access-verification.md)） | **采用**：设备在线、设备已配对、本次操作已授权三者分开 |
| presence 预算 | 心跳 TTL 90 秒，积压会让“已送达的心跳”仍被判离线；presence 只能由计时器或生命周期触发（[cli-lib-loro-presence.md#L28](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/.agents/docs/cli-lib-loro-presence.md#L28)） | **参考**（S6）：设备在线状态不能由进度流驱动 |
| 身份 | 桌面关闭后 CLI 可继续；个人身份与机器身份分开，后台工作不得取得个人管理密钥；密钥只插入不替换，不确定写入要对账（[host-identity-keys.md](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/host-identity-keys.md)，状态 draft，多数平台未实现） | **采用原则**：个人客户端凭据、管理 operator、设备执行器凭据三种主体分开 |
| ACP 接入 | `initialize` 声明 fs、terminal、elicitation、`_meta.lody` 扩展；按 `loadSession`／`sessionCapabilities.resume` 能力选择 load/resume/fork（[agent-client.ts#L1935-L2070](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/apps/cli/src/agent/agent-client.ts#L1935-L2070)）；自定义 Agent 只需 `command`＋`args`（[ai.ts#L123-L131](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/packages/shared/src/ai.ts#L123-L131)） | 方向 A 的接入面：Yuki 只要提供 stdio ACP 进程就能被 Lody 选作 custom Agent |
| 权限请求投影 | `requestPermission` 交给 session manager 的处理器，结果写入持久权限历史，各端在同一位置回答；服务端 20 分钟超时会撤回请求（[agent-client.ts#L785](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/apps/cli/src/agent/agent-client.ts#L785)；[permission-requests.md#L67](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/permission-requests.md#L67)） | **参考**：Yuki 已有 Work waiting_user 等待，等价物是“等待用户回答”的持久等待，回答走原 Work |
| 编排与恢复 | Operation 冻结派发配置；提交后不确定即“永久未知提交，不重放”；Stop 先持久化暂停再取消；本地 OSS 与云共用同一状态机（[session-orchestration.md#L115-L210](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/session-orchestration.md#L115)） | 与 Yuki “未知不重发、原回执优先”一致，**确认现有合同方向**，不需要照搬 Inbox 机制 |
| 重启／升级 | 已接受的重启即使 ACK 送不出也要执行；客户端超时只表示未确认（[machine-lifecycle-ack.md](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/machine-lifecycle-ack.md)） | **采用**：客户端超时一律按“未知，查原请求”处理 |

**不采用：** Loro CRDT 同步与托管 Streams（Yuki 的事实只有服务器一个写者，CRDT 只增加冲突面）；团队工作区与机器共享；会话级 worktree／PR 工作流；Lody 的 MCP 编排工具集。

**它解决的实际需求：** 多台用户机器各自执行、各自离线写入，还要合并到同一会话。Yuki 第一版只有服务器执行者，客户端只提交命令、阅读投影，所以不需要同等复杂度。等到 S6/S8 设备执行器出现，也只是“服务器派发、设备回执”，仍是单一事实源。

### 3.2 Memoh（`f6a46747`）

**它是什么。** Go 服务端＋Vue Web＋Electron 外壳的常驻 Bot 平台：服务端持有 Agent 执行，Web “local” 渠道与 Telegram/QQ 等 IM 渠道并列，ACP 用于在 Bot 容器内托管自定义 Agent。

| 关注点 | 源码事实 | 对 Yuki |
| --- | --- | --- |
| 持久接纳 | `Manager.Admit` 按 session＋invocation 写 ledger，计算 payload 指纹；同 ID 不同内容返回冲突；已有 owner 或已结束只返回原状态；无 owner 的原接纳由重试自己认领（[admit.go#L190-L257](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/session/admit.go#L190-L257)） | **采用语义**：客户端 `request_id`＋内容比较；Yuki 用 `canonical_event_receipts` 与命令回执实现，不另建 ledger |
| 原执行查询 | `GET .../invocations/{id}` 与读会话同一授权，只返回 found/run/turn/state，不泄露输入与 fence（[session_invocation.go#L59-L106](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/handlers/session_invocation.go#L59-L106)） | **采用**：`GET /client/v1/requests/{request_id}` |
| 订阅与恢复 | 订阅先授权，同会话旧订阅原子替换；**故意不按 cursor 补播**，因为实时投影没有持久事件日志，只回当前快照＋后续增量（[runtime_ws.go#L278-L340](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/handlers/runtime_ws.go#L278-L340)） | **采用“快照＋提示”**；Yuki 的账本 ID 是持久的，所以消息部分可以精确按游标补读，比 Memoh 更简单 |
| 补充要求的保留期 | live queue 每会话最多 64 个待处理项，终态只保留 64 个用于去重（[live_queue.go#L44-L48](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/session/live_queue.go#L44-L48)） | **不采用**有限保留：Yuki 的去重键在持久表里，保留期与账本一致 |
| 身份与管理权分开 | IM 渠道身份与 Web 用户通过一次性 LinkCode 绑定（Web 生成、在 IM 发 `/link <code>`）；每个 Bot 的 Manage 能力单独计算（[channelaccess/types.go#L5-L7](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/channelaccess/types.go#L5-L7)） | **采用，方向相反**：Yuki 的可信身份已在 QQ，故由 QQ 私聊签发绑定码，客户端输入码完成配对 |
| ACP（Memoh 作宿主） | 只用 `NewSession`，每个 ACP 会话从新开始；会话连续性以 Memoh 自己的上下文为准，每轮在同一事务发布 publication head，提示前比对，不一致则重启进程（[acp/AGENTS.md#L30](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/AGENTS.md#L30)；[session.go#L412](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/client/session.go#L412)；[session_pool.go#L1054](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/session_pool.go#L1054)） | 方向 B 的**关键参考**：外部 Agent 的会话状态不是事实源，宿主的 Work 与回执才是 |
| ACP 权限 | `RequestPermission` 限定在当前 prompt；越出工作区根直接拒绝；“同意形态”的请求必须给用户看，不能被策略自动放行（[client.go#L610-L700](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/client/client.go#L610)） | 方向 B 参考：权限请求转成原 Work 的用户等待 |
| 设备 Runtime | 设备主动建 WSS，服务器在通道上做 gRPC；mount 默认 read/write/exec 全部 allow（[remote.go#L426-L436](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/workspace/remote.go#L426-L436)）；设备按 key 激活连接（[userruntime/service.go#L170](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/userruntime/service.go#L170)） | 连接方向**采用**（S6/S8）；默认全放行**不采用**，Android 能力按项授权 |
| 恢复类型 | 优雅关机可带 `resume:旧run` 建关联新 run；崩溃收敛为 lost 等多种语义（[agent-runtime.md#L183](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/docs/agent-runtime.md#L183)） | 只作对照；Yuki 继续按原 Work ID 与持久回执恢复，不改成新 run |

**不采用：** PostgreSQL／Redis 分布式 lease 与 fencing（Yuki 单进程单 SQLite 写者，已有 instance lock）；Bot／团队多租户；容器内桌面与 WebRTC；把 IM 渠道和 Web 都做成 Turn 直连的“channel”抽象层（Yuki 已有 Gateway 抽象，不再加一层）。

### 3.3 ACP 与 MCP 的实际支持程度

| 事项 | 规范现状（`183f308d`） | 结论 |

## 5. 推荐架构

### 5.1 依赖方向

```text
QQ/OneBot ──► Gateway(onebot)──┐
个人客户端 ─► Client API ─► Gateway(app) ─┤
                                    ├─► MessageProcessor / Main / Work / Social / Memory / Workspace
operator CLI ─► Admin API ─────────┘        （领域服务与仓库，唯一事实源）
(后续) yuki acp ─► Client API
(后续) 设备执行器 ◄─ Device channel ◄─ Work 工具执行处
```

- **Client API**（`src/qq_ai_bot/client_api/`）：只做传输——认证设备、解析请求、调用应用服务、投影 DTO。它把消息交给 `app` Gateway 的入站路径，不直接写 `chat_events`。
- **`app` Gateway Provider**（`src/qq_ai_bot/gateway/providers/app/`）：进程内第一方网关。入站：构造 `InboundMessage`，`bot_user_id`＝`app` Presence 的外部 ID，`sender.user_id`＝Person 的 `app` Binding 外部 ID。出站：Provider **不写账本**，Social 按已核验路由的平台区分投递：QQ 继续调用网关并经 `parse_onebot_send_receipt` 严格校验；App 是本地投递，不调用 OneBot 发送或解析，不伪造外部消息 ID，`reference` 留空，沿现有 `social-operation:<operation_id>` 生成内部账本消息号。出站事件与成功回执仍由 `_dispatch_claimed` 在同一短事务提交，提交后再通知 SSE。当前代码在生成内部消息号前会先解析 OneBot 回执，必须在 P3 明确分开这两条路径，不能仅让 Provider 返回空 ID。没有外部网络效果；事务提交确认丢失时仍按原 operation ID 查回执与账本，不重发。
- **Admin API**（`src/qq_ai_bot/admin_api/`）：operator 认证与有限方法表，调用原领域服务与命令回执。
- **复用领域层**：Person、Conversation、Work 与回执仍是原事实源。Social 去掉仅限 QQ 的硬拒绝，按 Provider 声明能力，并明确区分 App 本地投递与 QQ 回执解析；Processor 的 App 普通消息去重先于轮次通知（§5.3），不新增任务系统或协调器。

### 5.2 四类主体分开

| 主体 | 凭据 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| operator（管理） | 服务器 TOML 声明＋环境变量 token（沿用现有格式） | 声明的管理能力 | 不因此成为某个 Person 发言；不读个人内容，除非显式具备内容能力 |
| 个人设备（客户端） | 绑定码配对后签发的设备 token，绑定一个 Person | 该 Person 私聊 Conversation、该 Person 拥有的 Work、相关文件 | 任何管理能力；其他 Person；群聊 |
| ACP 适配器（后续） | 就是一个个人设备凭据 | 同个人设备 | 同上 |
| 设备执行器（S6） | 独立配对的执行器凭据，按能力项授权 | 接受服务器派发的已授权操作并回执 | 发言、读对话、自行发起操作 |

同一个人的手机可以同时装个人客户端和执行器，但两个凭据各自撤销；关闭“允许操作手机”不影响聊天。

### 5.3 关键数据流

**交办任务（电脑端）**

1. 客户端生成 `request_id`，在本地记录后发送 `POST /client/v1/messages`。
2. Client API 认证设备 → Person，先查 `(app Presence, message, request_id)` 是否已有入账：**已有**先核对原事件的作者是该 Person、属于其私聊 Conversation 且当前可读，再比较本次请求与原事件的规范化正文和附件；无权返回 `not_found`，不得返回原事件或会话 ID；有权且内容相同才返回重放，不同返回 `request_conflict`，不构造新的 `InboundMessage`。**没有**才构造 `InboundMessage`，`received_at` 取服务器本次接纳时刻，segments 由服务器规范化。提前返回仍保留原入站的身份与会话校验，不能只凭同一消息号和正文判断。
3. 交给 `app` Gateway 入站，沿原 canonical 入账写 `canonical_event_receipts`。App 普通消息在现有 Processor 中**先完成 canonical 入账，仅首次创建事件时再调用 `notify_message` 并进入 Main**；重复请求不推进轮次、不取消原执行，也不再次进入 Main。当前 Processor 在入账前通知轮次，P3 必须调整 App 普通消息的这项顺序，不能只在 API 捕获异常后返回重放。若两个并发请求都通过第 2 步，后到者在原入账处因时间不同收到 `receipt_conflict`，此时重新执行第 2 步的全部授权与内容核对；只有确认是有权读取的同一请求才返回重放，身份或内容冲突不转成成功。复用原入账与轮次协调器，不新增去重队列；QQ 与 `/ai new` 的原合同另行回归核对。
4. 原 `MessageProcessor` → Main。Main 自行决定是否 `task_control.accept` 建立 Work，是否 `send_message` 回复。回复由 Social 按 `app` 路由进行本地投递与出站账本结算。
5. 响应返回 `{event_id, conversation_id, replay}`；Work 是否建立由后续状态投影体现，不在提交响应里猜。

**关闭电脑端**：什么都不发生。SSE 断开；Work 继续；后续回复照常写入账本。

**手机接回**

1. 手机用自己的设备凭据 `GET /client/v1/home` 得到私聊 Conversation 的 `latest_event_id`、该 Person 的进行中与最近 Work（`id`、`state`、`revision`、等待类型）。
2. `GET /client/v1/conversations/{id}/events?after=<cursor>` 补读消息；打开 `GET /client/v1/stream` 接收提示。
3. 补充要求：`POST /client/v1/works/{work_id}/inputs {request_id, text}`，或直接在对话里发消息（等待中的问题会按 Person 匹配到原 Work）。
4. 完成：Main 用 `send_message` 发结果与 artifact；手机通过账本看到出站事件，用 `GET /client/v1/artifacts/{artifact_id}?version=` 取原文件。若 Main 当时选择投递到 QQ，结果同样在这个 Conversation 账本里，手机一样可见。

### 5.4 Conversation 与共享边界

| 情况 | 推荐 |
| --- | --- |
| Person 与 Yuki 私聊（QQ 或 App） | 同一个 canonical Conversation（现行合同）。`/ai new` 推进 generation 时两端一起生效 |
| QQ 群里交办的 Work | 个人端显示为该 Person 拥有的 Work 卡片（状态、结果附件）；**不显示群聊天记录**；补充输入第一版只接受“取消”，文字补充请回到群里（待你确认，§9.3 Q2） |
| Memory | 按 Person／SELF 作用域天然共享，不随入口复制，也不因 App 登录合并群历史 |
| 主动消息投递 | 沿 Person 主动路由（现有三类路由之一）。新增 `app` 作为可选路由目标；默认保持 QQ，用户可改（§9.3 Q3） |

### 6.2 个人客户端 API（`/client/v1`）

认证分两类：`POST /pair` 只凭一次性绑定码授权（不带、也不接受设备 token），成功后签发设备 token；**其余所有个人接口**必须带 `Authorization: Bearer <device token>`。任何接口都不接受客户端提交 Person、权限或平台号。

| 方法 | 说明 | 复用 |
| --- | --- | --- |
| `POST /pair` `{code, device_label}` → `{device_id, token}`（**无需设备 token**） | 一次性绑定码授权；同一短事务内标记码已用、创建设备、必要时创建 `app` Binding。响应丢失时码已作废，用户重新签发绑定码；旧的未领取设备无 token 可用，可在设备列表撤销 | 新表；canonical 身份仓库 |
| `GET /me` | Person 展示名、私聊 Conversation ID | identity readers |
| `GET /home` | 快照：`conversation{id, generation, latest_event_id}`、Work 列表、`snapshot_at` | Work 查询（新写，按 `actor_person_id` 或私聊 Conversation 过滤） |

| `POST /messages` `{request_id, text, attachments[]}` | 提交；返回 `{event_id, replay}`。重试复用原入账（§5.3 第 2–3 步），不以新时间重建输入 | `app` Gateway 入站 → `MessageProcessor` |
| `GET /requests/{request_id}` | 查原请求：`found`、`event_id` 或命令回执状态；先核归属与可读范围，跨设备查询不重新派发 | `canonical_event_receipts`、`control_command_receipts` |
| `GET /works/{id}` | 公开投影：state、revision、goal 摘要、等待类型、子 Work 数、预算已用／上限、结果事件与 artifact 引用 | Work 仓库 |

| `POST /works/{id}/cancel` `{request_id, expected_revision}` | 取消 | `manage_work` ＋命令回执 |
| `POST /uploads` `{request_id, sha256, size}`＋文件 | 上传附件，返回媒体引用供 `messages` 使用；文件 I/O 与数据库登记分开处理，见 §6.5 | `ConversationMediaService` |
| `GET /artifacts/{artifact_id}?version=` | 下载原版本 | `WorkspaceStore` |
| `GET /activity` | 当前会话是否有执行、来源、开始时间、步骤类别（不含提示词与工具参数） | 从 `read_conversation_execution` 提炼公开投影 |
| `GET /stream`（SSE，`Last-Event-ID`） | 提示：`conversation{latest_event_id}`、`work{id, revision}`、`activity{conversation_id}` | 进程内提示中心 |
| `DELETE /devices/{id}` | 撤销本 Person 的设备 | 新表 |

**授权规则（在执行处核验）：** Conversation 必须是该 Person 的私聊；Work 必须 `source.actor_person_id == Person` 或属于该 Person 私聊；artifact 必须被该 Person 可读的出站事件或其 Work 结果引用。不满足一律返回 `not_found`，不透露存在与否。

原请求查询与重放也遵守同一授权：消息核原事件的 Person、私聊 Conversation 与当前可读性；命令回执核其 `principal_id` 对应的设备属于该 Person。另一台已授权设备可以读同一 Person 的原结果，但设备切换不产生新的派发资格。无权请求不比较私人正文、不返回事件或回执信息。

### 6.4 状态投影与重连收敛

- **先订阅，再核对**：客户端打开 `/stream` 后，服务器先把该连接登记到提示中心，**登记完成后**再读一次当前 `latest_event_id` 与该 Person 的 Work `revision`，作为第一条 `sync` 消息发出。客户端拿它和手里的快照比较，落后就按游标或 revision 补读。这样“快照之后、订阅之前”提交的结果必然被这条 `sync` 覆盖；之后的提交都会发出提示。SSE 只说“X 变了”，不承载事实。客户端也可以先开流再取 `/home`，两种顺序都以 `sync` 为准。
- **消息不会漏**：`chat_events.id` 持久且单调，`after=<cursor>` 可以完整补读；出站事件在提交后才发提示。
- **Work 不会错**：比较 `revision`；看到更大的 revision 就重读 `/works/{id}`。
- **丢提示就重连核对**：某订阅的提示无法投递或因慢消费者被丢弃时，结束该 SSE 连接，不保留表面在线但已缺更新的订阅。客户端自动重连，重新登记后接收首条 `sync`，按游标与 revision 补读；即使丢掉的是最后一条提示、之后没有新事件，也能收敛。进程重启同样走重连；回到前台再做快照比对。提示失败不撤销已提交事实，也不阻塞模型结果或 Work 完成；不新增持久事件日志。
- **不做的事**：不补造中间状态，不缓存流式 token（Yuki 的可见输出本来就是离散的 `send_message`），不把“正在执行”的诊断记录当事实——活动投影只说“有证据显示在执行”或“证据不足”。

### 6.5 错误与未知结果

| 码 | 含义 | 客户端应做 |
| --- | --- | --- |
| `unauthenticated` | 凭据无效或已撤销 | 重新配对 |
| `not_found` | 不存在或无权访问（两者不区分） | 停止重试 |
| `request_conflict` | 同一 `request_id` 内容不同 | 换新 `request_id` 前先让用户确认 |
| `version_conflict` | `expected_revision` 过期 | 重读后再决定 |
| `precondition_failed` | Work 已终结等 | 展示原终态 |
| `unavailable` | 服务器明确未写入任何东西（例如数据库 BUSY 后已回滚） | 可用**同一** `request_id` 重试 |
| 传输中断／超时（客户端侧） | **未知**，不是失败 | 用 `GET /requests/{request_id}` 查原请求，不换 ID 重发 |

服务器侧分两类处理：

- **数据库命令**（消息入账、补充入队、取消、配对、撤销）：数据库写入与对应回执在短事务内完成；消息的模型、媒体准备与其他外部执行留在事务外。被拒绝时不写入；数据库 BUSY 且确认回滚后才返回 `unavailable`；提交确认丢失时服务器自己也不确定，沿现有合同保留原 ID，下次按原 ID 查回。
- **文件上传**：文件 I/O 不进入写事务。顺序为：① 流式写入按 `(device_id, request_id)` 命名的暂存文件，边写边算 SHA-256 与长度；② 与客户端声明的 `sha256`／`size` 比较，不符即删暂存并返回校验错误；③ 原子改名到内容寻址路径（同内容已存在则直接复用）；④ 短事务登记媒体记录与命令回执。失败语义：①②失败没有任何登记，客户端用同一 `request_id` 重传；③后④前崩溃只留下未被引用的文件，不影响事实，由现有“删除前核实际引用”的维护清理；④提交确认丢失时客户端查 `GET /requests/{request_id}`，已登记就直接取原引用，未登记就重传（③会复用已有内容）。上传成功不代表消息已发送，消息仍走 `POST /messages`。

### 6.6 三种“离线”分别意味着什么

| 情况 | 意味着 | 不意味着 |
| --- | --- | --- |
| 客户端关闭／断网 | 视图暂停；未发出的草稿留在客户端；已发请求结果未知 | 任务取消、Work 所有权变化 |
| 服务器重启 | SSE 断开；Work 由原调度器按持久状态恢复；`app` 投递若停在 Social 已认领、尚未结算，沿原 operation ID 处理，账本与回执同事务，有事件就有成功回执 | 重跑模型、重发 QQ 消息、重置预算 |
| 执行设备离线（S6） | 依赖该设备的步骤以原操作 ID 等待；已派发未回执的操作为未知 | 换设备或换后端再执行一次 |
