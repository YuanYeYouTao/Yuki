## 0. 先读这一节

**结论：新控制面是两条分开的入口——管理控制面和个人客户端入口——接到同一套 Person、Work、Social 回执和 Workspace 上。QQ、Telegram 与 Yuki 自己的 App 主会话是同一层级的入口：身份按 Person 对应，会话、历史与模型 session 按入口分开。** 旧 WebUI、`webui/`、`control_plane/` 的 WebUI 查询命令层和约 1 万行 `persistence/control_*` 读模型整体退役；`/ai` 管理命令仍在用的授权对象与命令回执留下并迁出。

八个直接影响实施的判断：

1. **身份由后端鉴权确定，会话按入口分开。** Person、平台账号绑定、Conversation、模型 session 与 Work 是五个不同对象（§5.2）。当前私聊沿真实 Binding、Presence 与子会话解析；各入口保存自己的 Conversation、generation、公共历史和模型 session，不自动拼接历史。Person 归并只统一当前人物归属，保留原入口。入站、出站与读取端使用同一 canonical 解析，已有 turn 直接使用其中的 Conversation ID；旧 transport alias 只作历史定位（G9、§6.1）。
2. **每个原 App 入口由电脑与手机共用，人物归并不合并入口。** 设备只是凭据，同一入口在电脑和手机之间延续原工作；一个当前 Person 可拥有多个原 App Binding、Conversation 和请求 namespace。主会话另有显式的跨入口能力：按后端授权读取本人其他入口的会话账本（保留平台、绑定、会话与事件来源，内容作为不可信资料），以及向明确指定的平台账号与会话发送。工具声明按入口类型冻结，平台入口一套、主会话一套，同一 session 内从不切换（§5.6）。
3. **可信同人证明归并 Person，账号真正换主人由 operator 明确转移。** 新账号普通首次入站创建 Person；兑换有效绑定码时，新账号直接挂到码所指的人物，已有账号则证明两份身份属于同一人，沿 #453／0129 归并到码所指的当前 Person。归并保留原 Person ID、Binding、App、Conversation、设备、请求 namespace、历史、Work、预算与已付回执，不把原账号标为 `transferred`。只有 operator 明确执行 `binding transfer` 才表示账号交给另一个人：旧绑定标为 `transferred`，新主人取得新绑定，旧资料仍归原人（§5.3、§6.1）。CLI、ACP、App 都凭设备 token 得到 Person，QQ 不是必经入口。
4. **个人客户端按第一方网关接入。** `app` 与 `acp` 使用 GatewayProvider／Registry，消息沿原入账、身份、Main、Work 和 Social 路径；QQ、Telegram 是同层已实现的平台适配器。个人端回复由 Social 在原短事务写出站事件与成功回执，提交确认丢失仍按原 operation ID 查证。本轮复用这些执行底座，不另造会话或发送系统。
5. **跨入口补充 Work 沿原 Work ID，不搬 session，也能通过原来源核验。** Work 属于建立它的 Conversation 与 generation（私聊或群聊）。其他入口可以查看它、显式补充或回答（`POST /works/{id}/inputs`）、按原规则取消和取结果。补充事件留在所选 App／ACP 会话，同一短事务写入原 Work mailbox 并登记来源会话；`WorkSourceGuard` 只对本 Work mailbox 已接纳的那一条跨入口事件放行，原 generation、来源、隐私与效果回执合同仍适用（§5.4）。群 Work 用同一接口，补充不自动发成群消息，也不另起一次任务。跨端接续靠已有持久事实：`chat_events.id` 游标、Work `revision` 与订阅后的 `sync`，SSE 不承载事实。
6. **ACP 先 A 后 B，两者方向与事实源分开。** 方向 A 使用稳定 wire `protocolVersion=1`、本地 stdio 与 Python SDK `0.12.1`；schema 发布号、Rust crate 版本不当作 wire 版本。本地适配器持个人设备凭据，`acp` 原 Binding 内每个 session 是独立 Conversation，复用既有 `thread_id`；new 不推进、不取消其他会话，generation 只表示同一会话内重建。方向 B 现进入 #456 本轮范围：外部 Agent 是原 Work 的执行资源，运行于已有持久环境，沿原身份、授权、调用和回执；不因接入 ACP 恢复 MCP 动态工具或另建任务系统，细项见 §11。
7. **第一个完整体验在 #299 内做到“契约级可验证”，真机体验属于 S4/S5。** 本次交付两个独立设备凭据、参考 Python 客户端和故障注入测试，证明“电脑交办 → 关闭 → 手机接回 → 补充 → 取结果”在服务端成立；Android UI 与真机验收按路线图另做。
8. **手机有两个角色：个人客户端与设备执行器。** 个人客户端负责登录、聊天、任务接续、结果与文件，本次交付其服务端；设备执行器接受 Yuki 已授权的操作，用手机实际具备的能力执行并回传可查证的结果，属于 S6。两者可以在同一个 App 里，但凭据与授权分开：登录聊天不授予手机操作权，撤销操作能力也不撤销聊天登录。理解要求、选工具、接续工作仍由现有 Main、Work 与效果回执负责，手机不另跑一套规划循环（§5.7）。本次不预造设备协议或空工具，只保证个人凭据不被写死成“唯一的设备身份”。

产品决定已全部确认，记录在 [§9.3](#93-已确认的产品决定)；本文目前没有待决事项。

### 1.2 目标

1. 删除旧 WebUI 与旧控制面实现，不留第二套控制面、改名包装或永久兼容层。
2. 建立两个入口：**管理控制面**（operator 配置、插件、身份绑定、诊断、管理操作）和**个人客户端入口**（Person 自己的主会话、任务、结果和文件）。两者共用领域服务，身份与授权分开。
3. QQ、Telegram 与 App 主会话按同一层级的入口设计：身份可以对应到同一 Person，会话、历史与模型 session 各自独立；跨入口只做显式读取、显式发送与对指定 Work 的显式补充。
4. 让第一个完整体验在服务端成立：电脑交办长任务，关闭电脑端，手机看到同一任务、补充要求，最后取得原任务结果与文件。
5. 留出 ACP、手机设备执行器（S6，例如设定闹钟、操作其他 App）、语音与角色呈现的接入边界，但不预造接口。

## 3. 外部项目：证据、采用理由与不采用部分

### 3.1 Lody（`8971b66e`）

**它是什么。** 以 Loro CRDT 文档为事实载体的团队编码 Agent 工作台：每台机器跑一个 CLI daemon，daemon 作为 **ACP 客户端**启动 Claude Code、Codex 等 Agent；会话、历史、权限请求写入 Loro 文档，由托管 “Streams” 同步给桌面、Web、手机和 CLI。公开仓库只包含 `apps/{cli,electron}` 与共享包，托管后端、Web 与手机源码不公开（[AGENTS.md#L56](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/AGENTS.md#L56)）。因此下文凡涉及服务端授权与手机端行为，只能依据公开协议和文档，不能视为源码已证实。

| 关注点 | 源码／文档事实 | 对 Yuki |
| --- | --- | --- |
| 分工 | daemon 拥有 Agent 进程与会话执行；桌面 renderer 通过本地 socket 同步 Loro 文档，“Two planes”：本地数据面与云房间状态分开，不轮询、无请求/响应 HTTP（[cli-lib-local-loro-data-plane.md#L93](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/.agents/docs/cli-lib-local-loro-data-plane.md#L93)） | Lody 的执行在用户机器上，所以需要多端可写的同步文档。Yuki 执行在服务器，事实已在 SQLite，不需要 CRDT |
| 机器在线 ≠ 有权限 | presence 心跳与访问校验是两件事；访问服务不可用时重试有界，之后返回可重试错误且不创建工作，不把“不可用”当允许（[session-access-verification.md](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/session-access-verification.md)） | **采用**：设备在线、设备已配对、本次操作已授权三者分开 |
| presence 预算 | 心跳 TTL 90 秒，积压会让“已送达的心跳”仍被判离线；presence 只能由计时器或生命周期触发（[cli-lib-loro-presence.md#L28](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/.agents/docs/cli-lib-loro-presence.md#L28)） | **参考**（S6）：设备在线状态不能由进度流驱动 |
| 身份 | 桌面关闭后 CLI 可继续；个人身份与机器身份分开，后台工作不得取得个人管理密钥；密钥只插入不替换，不确定写入要对账（[host-identity-keys.md](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/host-identity-keys.md)，状态 draft，多数平台未实现） | **采用原则**：个人客户端凭据、管理 operator、设备执行器凭据三种主体分开 |
| ACP 接入 | `initialize` 声明 fs、terminal、elicitation、`_meta.lody` 扩展；按 `loadSession`／`sessionCapabilities.resume` 能力选择 load/resume/fork（[agent-client.ts#L1935-L2070](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/apps/cli/src/agent/agent-client.ts#L1935-L2070)）；自定义 Agent 只需 `command`＋`args`（[ai.ts#L123-L131](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/packages/shared/src/ai.ts#L123-L131)） | 方向 A 的接入面：Yuki 只要提供 stdio ACP 进程就能被 Lody 选作 custom Agent |
| 权限请求投影 | `requestPermission` 交给 session manager 的处理器，结果写入持久权限历史，各端在同一位置回答；服务端 20 分钟超时会撤回请求（[agent-client.ts#L785](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/apps/cli/src/agent/agent-client.ts#L785)；[permission-requests.md#L67](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/permission-requests.md#L67)） | **参考**：Yuki 已有 Work waiting_user 等待，等价物是“等待用户回答”的持久等待，回答走原 Work |
| 编排与恢复 | Operation 冻结派发配置；提交后不确定即“永久未知提交，不重放”；Stop 先持久化暂停再取消；本地 OSS 与云共用同一状态机（[session-orchestration.md#L115-L210](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/session-orchestration.md#L115)） | 与 Yuki “未知不重发、原回执优先”一致，**确认现有合同方向**，不需要照搬 Inbox 机制 |
| 重启／升级 | 已接受的重启即使 ACK 送不出也要执行；客户端超时只表示未确认（[machine-lifecycle-ack.md](https://github.com/LodyAI/Lody/blob/8971b66e3f79da21e6e106bf6959f3d487d5d32e/specs/machine-lifecycle-ack.md)） | **采用**：客户端超时一律按“未知，查原请求”处理 |

**不采用：** Loro CRDT 同步与托管 Streams（Yuki 的事实只有服务器一个写者，CRDT 只增加冲突面）；团队工作区与机器共享；会话级 worktree／PR 工作流；Lody 的 MCP 编排工具集。

**它解决的实际需求：** 多台用户机器各自执行、各自离线写入，还要合并到同一会话。Yuki 第一版只有服务器执行者，客户端只提交命令、阅读投影，所以不需要同等复杂度。等到 S6/S8 设备执行器出现，也只是“服务器派发、设备回执”，仍是单一事实源。

### 3.2 Memoh（`f6a46747`）

**它是什么。** Go 服务端＋Vue Web＋Electron 外壳的常驻 Bot 平台：服务端持有 Agent 执行，Web “local” 渠道与 Telegram/QQ 等 IM 渠道并列，ACP 用于在 Bot 容器内托管自定义 Agent。

| 关注点 | 源码事实 | 对 Yuki |
| --- | --- | --- |
| 持久接纳 | `Manager.Admit` 按 session＋invocation 写 ledger，计算 payload 指纹；同 ID 不同内容返回冲突；已有 owner 或已结束只返回原状态；无 owner 的原接纳由重试自己认领（[admit.go#L190-L257](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/session/admit.go#L190-L257)） | **采用语义**：客户端 `request_id`＋内容比较；Yuki 用 `canonical_event_receipts` 与命令回执实现，不另建 ledger |
| 原执行查询 | `GET .../invocations/{id}` 与读会话同一授权，只返回 found/run/turn/state，不泄露输入与 fence（[session_invocation.go#L59-L106](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/handlers/session_invocation.go#L59-L106)） | **采用**：`GET /client/v1/requests/{request_id}` |
| 订阅与恢复 | 订阅先授权，同会话旧订阅原子替换；**故意不按 cursor 补播**，因为实时投影没有持久事件日志，只回当前快照＋后续增量（[runtime_ws.go#L278-L340](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/handlers/runtime_ws.go#L278-L340)） | **采用“快照＋提示”**；Yuki 的账本 ID 是持久的，所以消息部分可以精确按游标补读，比 Memoh 更简单 |
| 补充要求的保留期 | live queue 每会话最多 64 个待处理项，终态只保留 64 个用于去重（[live_queue.go#L44-L48](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/session/live_queue.go#L44-L48)） | **不采用**有限保留：Yuki 的去重键在持久表里，保留期与账本一致 |
| 身份与管理权分开 | IM 渠道身份与 Web 用户通过一次性 LinkCode 绑定（Web 生成、在 IM 发 `/link <code>`）；每个 Bot 的 Manage 能力单独计算（[channelaccess/types.go#L5-L7](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/channelaccess/types.go#L5-L7)） | **采用**：绑定码由任一已鉴权的一端签发（QQ 私聊、已配对设备或 operator CLI），由新设备或平台账号兑换；QQ 不是必经入口。Memoh 把 Web 渠道与 Telegram/QQ 等 IM 渠道并列，也印证各平台同层。Yuki 已有账号兑换可信绑定码时沿 #453／0129 归并同一人的 Person，保原入口与来源；operator 明确转移账号给另一人另走 §5.3 的 transfer，不混用两种语义 |
| ACP（Memoh 作宿主） | 只用 `NewSession`，每个 ACP 会话从新开始；会话连续性以 Memoh 自己的上下文为准，每轮在同一事务发布 publication head，提示前比对，不一致则重启进程（[acp/AGENTS.md#L30](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/AGENTS.md#L30)；[session.go#L412](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/client/session.go#L412)；[session_pool.go#L1054](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/session_pool.go#L1054)） | 采用“Work 与回执是事实源”。不照搬不一致即重开：Yuki 的原 prompt 未决时保未知，只有确认允许的新链才可建立新 session，不借重建重派原效果 |
| ACP 权限 | `RequestPermission` 限定在当前 prompt；越出工作区根直接拒绝；“同意形态”的请求必须给用户看，不能被策略自动放行（[client.go#L610-L700](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/agent/runtime/acp/client/client.go#L610)） | 只参考请求与原 prompt 的对应关系。Yuki 沿实际来源与已有授权处理；确需用户决定的请求进入原 Work 等待，不为环境内已获准操作增加一律人工审批或另一套工作区权限层 |
| 设备 Runtime | 设备主动建 WSS，服务器在通道上做 gRPC；mount 默认 read/write/exec 全部 allow（[remote.go#L426-L436](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/workspace/remote.go#L426-L436)）；设备按 key 激活连接（[userruntime/service.go#L170](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/internal/userruntime/service.go#L170)） | 连接方向**采用**（S6/S8）；默认全放行**不采用**，Android 能力按项授权 |
| 恢复类型 | 优雅关机可带 `resume:旧run` 建关联新 run；崩溃收敛为 lost 等多种语义（[agent-runtime.md#L183](https://github.com/felinics/Memoh/blob/f6a4674739b40495fef9da928bb19092e144ff51/docs/agent-runtime.md#L183)） | 只作对照；Yuki 继续按原 Work ID 与持久回执恢复，不改成新 run |

**不采用：** PostgreSQL／Redis 分布式 lease 与 fencing（Yuki 单进程单 SQLite 写者，已有 instance lock）；Bot／团队多租户；容器内桌面与 WebRTC；把 IM 渠道和 Web 都做成 Turn 直连的“channel”抽象层（Yuki 已有 Gateway 抽象，不再加一层）。

### 3.3 ACP 与 MCP 的实际支持程度

| 事项 | 规范现状（`183f308d`） | 结论 |
| --- | --- | --- |
| 传输 | v1 只定义 stdio；Streamable HTTP 写着“draft proposal in progress”（[v1 transports.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/183f308d8324319d2e200dbd3724299ed5a937f0/docs/protocol/v1/transports.mdx)）；HTTP＋SSE／WebSocket 远程传输 RFD 处于 **Active**（[RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/183f308d8324319d2e200dbd3724299ed5a937f0/docs/rfds/streamable-http-websocket-transport.mdx)） | 现在没有可依赖的标准远程 ACP。服务器常驻 Yuki 只能经本地 stdio 适配进程被接入 |
| 会话恢复 | [当前稳定会话合同](https://agentclientprotocol.com/protocol/v1/session-setup)要求 `session/load` 回放完整可见会话，用户与 Agent 均经 `session/update` 返回；`session/resume` 不回放，另有能力声明 | 方向 A 已实现 load，分页读该 ACP Conversation 的原账本直至读完，回放用户与已确认出站；不将 Main 的摘要窗口当完整历史，不声明未实现的 resume/close 能力。方向 B 按所选 Agent 的真实能力恢复，不由支持 load 推导 prompt 可重发 |
| 提交去重 | v2 prompt RFD：响应在消息“插入”后返回 agent 生成的 `messageId`，**明确不增加客户端 promptId**（[v2/prompt.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/183f308d8324319d2e200dbd3724299ed5a937f0/docs/rfds/v2/prompt.mdx)）；v2 整体仍为 draft（[migration.mdx#L18-L21](https://github.com/agentclientprotocol/agent-client-protocol/blob/183f308d8324319d2e200dbd3724299ed5a937f0/docs/protocol/v2/migration.mdx#L18-L21)） | ACP 不提供“响应丢失后按原请求查回”。Yuki 自己的客户端 API 必须有 `request_id`；ACP 适配器只能在它这一侧补 |
| MCP | [当前会话规范](https://agentclientprotocol.com/protocol/v1/session-setup)要求 Agent 支持 stdio MCP；空 `mcpCapabilities` 只表示未声明 HTTP/SSE | Yuki 已退出 MCP；本轮仅接受空 `mcpServers`，非空显式报告不支持。此为已知互操作限制，不声称完整覆盖 ACP 所有 MUST，不新增动态工具或第二执行器 |

## 5. 推荐架构

### 5.1 依赖方向

```text
QQ/OneBot ─────► Gateway(onebot) ──────┐   每个平台账号绑定 → 自己的私聊 Conversation
(#300) Telegram ─► Gateway(telegram) ───┤
个人客户端 ─► Client API ─► Gateway(app) ┤   App 主会话：Person 的 app 绑定 → 一个 Conversation，多设备共用
(后续) yuki acp ─► Client API ──────────┤   acp 入口：Person 的 acp 绑定；每个 ACP session → 一个 Conversation
                                        ├─► MessageProcessor / Main / Work / Social / Memory / Workspace
operator CLI ─► Admin API ──────────────┘        （领域服务与仓库，唯一事实源）
(后续) 设备执行器 ◄─ Device channel ◄─ Work 工具执行处
```

- **Client API**（`src/yuki/client_api/`）：只做传输——认证设备、解析请求、调用应用服务、投影 DTO。普通消息交给 `app` Gateway 的入站路径，不直接写 `chat_events`；对指定 Work 的补充由 Work 输入服务经原 canonical 账本写入器写事件，与 mailbox、回执同事务提交，事件 `origin` 标为 `work_input` 并带 Work ID，在主会话历史中按来源标签呈现，不触发新的 Main 轮次（§5.4）。
- **`app` Gateway Provider**（`src/yuki/gateway/providers/app/`）：进程内第一方网关。入站：构造 `InboundMessage`，平台为 `app`，`bot_user_id`＝`app` Presence 的外部 ID，`sender.user_id`＝设备所属 Person 的 `app` Binding 外部 ID（由设备 token 查得，不取自请求）。出站：Provider **不写账本**，Social 按已核验路由的平台区分投递：QQ 继续调用网关并经 `parse_onebot_send_receipt` 严格校验；App 是本地投递，不调用 OneBot 发送或解析，不伪造外部消息 ID，`reference` 留空，沿现有 `social-operation:<operation_id>` 生成内部账本消息号。出站事件与成功回执仍由 `_dispatch_claimed` 在同一短事务提交，提交后再通知 SSE。当前代码在生成内部消息号前会先解析 OneBot 回执，必须在 P6 明确分开这两条路径，不能仅让 Provider 返回空 ID。没有外部网络效果；事务提交确认丢失时仍按原 operation ID 查回执与账本，不重发。
- **Admin API**（`src/yuki/admin_api/`）：operator 认证与有限方法表，调用原领域服务与命令回执。
- **复用领域层**：Person、Binding、Conversation、Work 与回执仍是原事实源。私聊 Conversation 的唯一键从 Person 改为绑定（P4）；Social 去掉仅限 QQ 的硬拒绝，按 Provider 声明能力，并明确区分 App 本地投递与 QQ 回执解析；Processor 的 App 普通消息去重先于轮次通知（§5.4），不新增任务系统、会话系统或协调器。

### 5.2 身份、入口与会话：五个对象分开

| 对象 | 是什么 | 由什么确定 | 不能由什么确定 |
| --- | --- | --- | --- |
| Person | 同一个人的永久身份；Memory、偏好、Work 所有权都挂在它上面 | 后端鉴权：平台入站经网关认证的账号查到的 Binding；个人客户端的设备 token；operator 显式命令 | 昵称、展示名、消息内容、客户端提交的 person ID、会话或 session 参数 |
| 平台账号绑定（IdentityBinding） | 原 Person 与“平台＋平台账号”的关系；当前人物按归并集合读取，可拥有多个原 App 入口，也允许没有账号 | 首次入站创建，或经可信绑定码／operator 挂接；已有账号兑换绑定码归并同一人的 Person 并保留原 Binding；operator 明确换主人时才创建新绑定、保留旧 `transferred` 行（§5.3） | 名称相同、内容相似不能证明同人；归并不改原 Binding 的 `person_id`，转移也不把旧行改成新主人 |
| Conversation（入口会话） | 某个绑定上的私聊对话；或某个 Space 的群聊。各有 generation、公共历史、compact 检查点 | 私聊取真实 Binding、Presence 与子会话；ACP 复用已有 `thread_id`，一个 session 一个 Conversation；群聊取真实 Space/Binding/thread | 不按 Person 合并；不按设备拆分；不经 transport alias 反查 |
| 模型／执行 session | 某 Conversation 当前 generation 的上下文与协议状态：公共窗口、私有执行尾部、Provider 续跑状态、`x-session-id`（[model-providers.md#L239](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/docs/architecture/model-providers.md#L239)）以及该入口类型的冻结工具声明 | Conversation＋generation（＋Work 分支） | 不在入口之间搬运或切换；不决定身份和权限 |
| Work | 可跨设备、跨入口查看、补充与取结果的原工作 | 建立它的 Conversation、generation 与 `actor_person_id` | 换入口查看不产生新 Work、不重置预算、不改原会话 |

会话可以记录所有者和来源，但登录身份与权限永远先由后端鉴权得到，再用来核对请求里的会话或 Work 是否属于这个 Person；顺序不能反过来。

四类主体分开：

| 主体 | 凭据 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| operator（管理） | 服务器 TOML 声明＋环境变量 token（沿用现有格式） | 声明的管理能力，含 Person 停用、绑定挂接与停用、为某 Person 签发绑定码 | 不因此成为某个 Person 发言；不读个人内容，除非显式具备内容能力 |
| 个人设备（App、`yuki client`） | 绑定码配对后签发的设备 token，属于一个 Person | 在该 Person 的 App 主会话发言；只读该 Person 其他入口的会话；该 Person 拥有的 Work 与相关文件；签发新绑定码；撤销本人设备 | 任何管理能力；其他 Person；群聊；向其他入口的会话直接写入 |
| ACP 适配器（#455） | 现有个人设备凭据，认证当前 Person 并保原设备与入口来源 | 在本人真实 ACP Conversation 发言、load 历史、查原请求与取消原 prompt | 不按客户端自报 Person/cwd 取得身份或服务器执行权限；`session/new` 不重建或取消其他 session |
| 设备执行器（S6） | 独立配对的执行器凭据，属于一个 Person，按能力项授权（如闹钟、某 App 的界面操作） | 接受服务器在原工具调用／Work 下派发的已授权操作，执行并回传可查证结果 | 发言、读对话、自行规划或发起操作；凭个人设备 token 取得操作权 |

同一个人的手机可以在同一个 App 里同时是个人客户端和执行器，但两个凭据各自配对、各自撤销：登录聊天不授予操作权，关闭“允许操作手机”不影响聊天，撤销聊天设备也不连带改动执行器授权以外的东西（§5.7）。

### 5.3 绑定、转移、解除绑定与身份获取

**现状与本次补充：**

| 能力 | 现状（`0aea047d`） | 本次 |
| --- | --- | --- |
| 新账号首次出现 | 自动新建 Person＋Binding（G10） | 保留；唯一例外是兑换绑定码的 `/ai link <code>`（见下） |
| 把账号挂到既有 Person | 只有 WebUI operator 命令，且只接受从未出现过的账号 | P2 迁到 `yuki admin binding attach`，语义不变；P5 增加用户自助的绑定码兑换 |
| 同一 Person 多个 QQ 账号 | 数据模型能表示；原基线只能经 WebUI 挂未出现的账号 | 可信绑定码可归并同人的已有身份；各原 Binding 与 Conversation 保留，不拼接上下文 |
| 不同平台账号 | 模型能表示；入站、Social、任务来源核验写死 `qq`（G11） | `app` 路径在 P5/P6 改为取入口平台；Telegram 余下部分随 #300 |
| 解除绑定 | 无写入路径 | P2 `yuki admin binding disable`：`status='disabled'`，该账号后续入站按现有 `canonical_owner_disabled` 失败关闭；历史、会话、Work、回执与 Memory 归属不变 |
| 账号已属另一个 Person | 原基线只能拒绝（`BINDING_AMBIGUOUS`） | 有效绑定码证明同人时归并 Person；真正换主人仅由 operator 明确 transfer |
| 合并两个既有 Person | 原基线无 | #453／0129 已交付可信绑定归并与 `yuki admin person merge`；保原来源和全部入口 |
| 停用 Person | WebUI 命令 | P2 迁到 `yuki admin person disable` |
| 个人设备凭据与撤销 | 无 | P5：`POST /pair`、`DELETE /devices/{id}`、`yuki admin client revoke` |
| CLI 身份 | 只有 operator（插件管理） | 管理 CLI 继续是 operator；个人 CLI（`yuki client`）是 App 入口的一台设备 |
| ACP 身份 | 无 | 方向 A 时适配器持设备凭据 |

**签发绑定码**（一次性、10 分钟过期、只存哈希）只能来自已经由后端确认身份的一端：

1. QQ 私聊 `/ai link`：作者 Binding 所属的 Person。
2. 已配对设备 `POST /client/v1/link-codes`：设备所属的 Person。
3. operator `yuki admin client pair --person <id>`；全新用户可先 `yuki admin person create`。这样第一台设备不需要经过 QQ。

**兑换绑定码：**

- **新设备**：`POST /client/v1/pair {code}`，得到属于码所指原 Person 的设备 token，并沿码的原 App 来源进入会话；缺少该入口时才在同一短事务创建。每个原 Person 有自己的 App Binding；归并后的当前 Person 可拥有多个原 App 入口，不合并 Conversation，不切换原设备的默认入口或请求 namespace。
- **新平台账号**：该账号在自己的平台上私聊 Yuki 发送 `/ai link <code>`。入站在“首次出现即建 Person”之前识别这条命令，做法与群超管 `/ai on` 的确定性控制入口相同：在写事务前核验网关连接与码，短事务内重验码未用、账号仍无 Binding，再创建挂到目标 Person 的 Binding、标记码已用、写命令回执。不新建 Person，不写聊天账本，不进入 Main 或 Memory，码文本不落库。
- 账号已绑定**同一归并集合**：复用原 Binding，返回当前 Person，码作废，不再归并或转移。
- 账号已属于**另一份 Person 身份**：账号持有人在该平台发送有效码，证明账号身份与码所指身份属于同一人。归并到码所指的当前 Person，复用原 Binding；回执为 `merged=true`、`transferred=false`，码作废。归并不写聊天账本、不触发 Main，也不重建历史或执行。

**同人归并沿 #453／0129。** 只建立原 Person 到当前 Person 的关系；原 Binding、App、Conversation、设备所属、消息作者、Work 来源、请求 namespace、指纹、媒体 UUID、预算与已付回执都保留。当前人物资料、权限、Work 与文件授权按归并集合读取，原入口的上下文、generation 和模型 session 仍独立。来源 Person 的显式禁用或设备撤销不会因归并而复活；遗忘按当前人物的归并集合清退。operator 也可显式执行 `yuki admin person merge <source-person-id> --to-person <target-person-id>`。

**operator 明确转移平台账号给另一人：** 账号今后归目标 Person；旧历史、Memory、Work、回执与文件授权留在原 Person，目标 Person 不因此取得旧资料。此操作不归并人物、不改写历史作者与既有执行归属，不转移原 Person 的设备凭据；`app`、`acp` 绑定不可转移。以下转移步骤与隔离规则只适用于真正换主人，不用于可信同人绑定。

真正换主人只由有权 operator 显式执行 `yuki admin binding transfer <binding_id> --to-person <id>`；绑定码兑换不调用 transfer，不接受自报账号代替真实授权。

最小数据调整（P5，迁移 0121，§6.1）：`identity_bindings.status` 增加 `transferred`；`(platform, external_account_id)` 的唯一约束改为只约束 `status <> 'transferred'` 的行。转移在一个短事务里完成：

1. 核 operator 授权与原命令回执，重验目标 Person 启用、旧绑定仍为 `active`；
2. 旧绑定行改为 `transferred`（`revision+1`），**不改它的 `person_id`**——旧会话、旧事件、旧 Work 来源都继续指向这一行，归属保持原 Person；
3. 为目标 Person 插入同一平台账号的新绑定行；
4. 原 Person 的主动路由若指向旧绑定，在同一事务暂停（`paused=1`、`route_generation+1`），原 Person 的主动消息失败关闭，直到原 Person 自己改路由；目标 Person 的路由不变；
5. 写原 operator 转移命令回执；不消费绑定码。

operator 转移给另一人后各处的结果（同人归并不套用此表）：

| 对象 | 处理 |
| --- | --- |
| 新会话解析 | 按“账号 → 非 `transferred` 的绑定”查到新行，再按 P4 的解析找到（首次则新建）新行自己的会话，primary alias 用 `binding:<新绑定 ID>`；旧 transport alias 不参与解析，不会导回旧会话 |
| 旧会话 | 归属不变（`person_id` 仍是原 Person，所属绑定是旧行），只有原 Person 的入口能读；目标 Person 的跨入口读取与 `/home` 不列出它 |
| 历史读取 | 原 Person 可照常读取旧会话；目标 Person 只看到转移之后新会话里的内容 |
| 主动路由 | 原 Person 指向旧绑定的路由暂停；目标 Person 需要时自行把路由指向新绑定 |
| 既有 Work | 不转移。来源恢复按“原 Person＋该账号＋有效绑定”核对执行身份（[execution_sources.py#L523-L532](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/services/execution_sources.py#L523-L532)），旧行已是 `transferred`，所以**依赖该账号的 Work**（该账号私聊里建立的，或该账号在群里发起的）在下一次来源核验时走现有来源失效路径，不会改用目标 Person 的权限继续产生效果；原 Person 经其他账号或 App 建立的 Work 不受影响。已派发的发送沿原回执，`uncertain` 不重发 |
| Memory、文件授权 | 留在原 Person；之后按该账号写入的新 Memory 归目标 Person |
| 设备凭据 | 原 Person 的 App 设备不动；转移只涉及平台账号 |
| 隐私删除 | 按 canonical 归属删除，不再把“这个账号的全部数据”当成“这个 Person 的数据”（见下） |
| 平台历史工具 | 只返回当前所有者拥有该账号期间的平台记录（见下） |

**拥有区间记在绑定行自己身上。** P5 在 `identity_bindings` 增加唯一一列 `history_starts_at`。**0121 之后新建的每一个绑定行都写入它，值就是本行的创建时刻**，此后不改。建立绑定的路径全部适用：普通入站自动建 Person 时的 `create_person_binding`（[canonical_repository.py#L251-L294](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/identity/canonical_repository.py#L251-L294)，`ensure_person` 也经它）、operator 挂接（现为 [control_command.py#L1605-L1645](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/persistence/control_command.py#L1605-L1645)，P2 迁入管理 CLI）、绑定码兑换、绑定转移与配对时创建 `app` 绑定。依据只有本行自己的创建时刻，不读取任何旧行、旧 Person 或转移记录，所以“遗忘当前持有人 → 账号再次入站重建绑定”后，新行照样有起点。0121 之前已存在的行保持为空（不设下限）。旧行转为 `transferred` 后不再被查找命中、不再更新，它的 `updated_at` 就是转移时刻。某 Person 对某账号的拥有区间是：起点＝该 Person 这一行的 `history_starts_at`（为空即不设下限），终点＝该行若已 `transferred` 则为其 `updated_at`（否则不设上限）。

每个所有者的边界只看**自己那一行**，不依赖原 Person 或旧行是否还在：前任被遗忘、其行随之删除后，现任行的 `history_starts_at` 仍在，过滤照常生效。这一列只是现任所有者自己的时间戳，不保存前任的任何资料，也不形成墓碑或转移记录。下面两条规则按每行的区间执行；只有 0121 之前的存量行两端都不设界，行为与现状相同。不再用“是否存在 `transferred` 行”或“是否经转移创建”分流。

对首次接入的影响：新账号的平台历史读取不返回绑定建立之前的平台记录（这些记录当时不属于任何 Person，按“无法确认归属”处理并计入 `withheld_unattributed`）；隐私删除时，正文中号码的脱敏只覆盖绑定建立之后的事件，因为在此之前这个号码在 Yuki 的事实里不属于该 Person。该 Person 自己的事件本来就从绑定建立开始，按 canonical 归属照常删除，不受影响。

**隐私删除按 canonical 归属与当前 Person 的归并集合执行。** 原基线 `delete_person` 收集平台账号后跨时期选取记录的做法不再适用；0121 保账号拥有区间，0129 保同人归并集合，两者同时生效。operator 把账号转给另一人不使两个人成为同一归并集合；可信同人归并后的旧 Person 也不能被当作无关前任单独遗漏。当前规则：

- 删除入口按内部 Person ID 解析当前归并集合。`/ai forgetme` 从真实发送者得到当前人物；没有可用账号时，由 operator 执行 `yuki admin person forget <person_id>`，复用同一实现。删除集合内全部原 Person 的绑定（含 `transferred` 行）、设备与全部所属私聊，不改用今日平台账号反查所有权。
- 事件、会话与 Work：按集合内原 `author_person_id` 与原私聊 Conversation 选取事件；受影响会话取这些私聊，加上含该集合作者事件的群会话，再执行原有 Work 清退与群会话 generation 推进。不重写原作者，也不因原 Person 已归并而漏删其数据。
- 外部账号条件：拥有区间不设界的账号（只有 0121 之前的存量行）保留现有全部条件。区间有界的账号不再用 `sender_user_id`、`private_peer_user_id`、会话 key 哈希、审计与表情使用记录里的账号等字符串条件跨时期选取或删除；这些行改按 canonical 列（`author_person_id`、`canonical_person_id`、私聊会话 ID）判定。正文、转写与 segments 里出现号码时的脱敏，只作用于 `created_at` 落在该 Person 拥有区间内的事件。
- Memory：按归并集合内的原 Person ID 与真实来源清退。Memory 重建不按运行创建时间、整批账号字符串或今日目标人物猜归属；条目与提案沿原 `event_id`、canonical 作者和绑定拥有区间处理。被遗忘集合的来源条目删除，无关人物的条目保留，原重建选择集不改写；区间不设界的历史绑定仍沿既有规则。
- 删除原 Person 时，它的 `transferred` 行在删除前给出区间终点，用来限定按账号的脱敏与提案删除，不会把新 Person 的数据纳入；随后这些行与原 Person 一起删除，不为隔离而保留原 Person 的资料。删除新 Person 时，区间从它那一行的 `history_starts_at` 开始，旧会话与旧事件的 canonical 归属是原 Person（或已被清退），不在删除范围内。遗忘后同一账号再入站时，按普通入站建立新 Person 与新行，起点是新行的创建时刻，前任时期的内容不会因此重新开放。

**平台历史工具按真实绑定的拥有区间过滤。** `read_conversation_history` 的 person 模式经 OneBot 按平台账号读取，不能由今日账号反建旧事件归属。当前绑定有 `history_starts_at` 时，只返回严格晚于该起点所在秒的平台记录；无可解析时间的记录不返回并计入 `withheld_unattributed`。operator 转移后的旧 Binding 为 `transferred`，不能被新主人用于读取原主人的历史或旧 `operation_id` 锚点。同人归并则保留原 Binding 与原起点，不能伪造一次 transfer 或重置区间。群历史沿原 Space 授权；账本搜索、插件读取及会话查询使用 canonical Conversation，跨入口授权按当前人物的归并集合核验，不拼接各入口的公共历史。

所有“按平台＋账号”查绑定的地方都改为排除 `transferred` 行：`find_identity_binding`、Memory 分区与投影、管理解析等（G11 列出的同一批位置，P5 一并改）。`disabled` 行仍然参与查找，入站继续按 `canonical_owner_disabled` 失败关闭，不会被当成新账号。

**各入口如何得到身份：** App、`yuki client`、ACP 适配器每次请求都带设备 token，服务端按 token → 设备 → Person → 该 Person 的 `app`（或 `acp`）Binding → 入口会话解析；`acp` 入口再按 `sessionId` 找到该 session 的会话，并核对它属于这个 Person。请求体不接受 Person、绑定、平台账号或 session；路径里的会话 ID、Work ID 只是查询目标，先核归属，不满足即 `not_found`。平台入口的身份来自网关认证的账号。operator 凭据只授予管理能力，不代表任何 Person 发言。

### 5.4 关键数据流

**交办任务（电脑端，App 主会话）**

1. 客户端生成 `request_id`，在本地记录后发送 `POST /client/v1/messages`。
2. Client API 认证设备 → Person → `app` Binding，入账消息号为 `<app Binding 外部 ID>:<request_id>`，不同 Person 的同名请求号互不冲突。先查 `(app Presence, message, 该消息号)` 是否已有入账：**已有**先核对原事件的作者是该 Person、属于其 App 主会话且当前可读，再比较本次请求与原事件的规范化正文和附件；无权返回 `not_found`，不得返回原事件或会话 ID；有权且内容相同才返回重放，不同返回 `request_conflict`，不构造新的 `InboundMessage`。**没有**才构造 `InboundMessage`，`received_at` 取服务器本次接纳时刻，segments 由服务器规范化。提前返回仍保留原入站的身份与会话校验，不能只凭同一消息号和正文判断。
3. 交给 `app` Gateway 入站，沿原 canonical 入账写 `canonical_event_receipts`，按 `app` Binding 落在该 Person 的 App 主会话。App 普通消息在现有 Processor 中**先完成 canonical 入账，仅首次创建事件时再调用 `notify_message` 并进入 Main**；重复请求不推进轮次、不取消原执行，也不再次进入 Main。当前 Processor 在入账前通知轮次，P6 必须调整 App 普通消息的这项顺序，不能只在 API 捕获异常后返回重放。若两个并发请求都通过第 2 步，后到者在原入账处因时间不同收到 `receipt_conflict`，此时重新执行第 2 步的全部授权与内容核对；只有确认是有权读取的同一请求才返回重放，身份或内容冲突不转成成功。复用原入账与轮次协调器，不新增去重队列；QQ 与 `/ai new` 的原合同另行回归核对。
4. 原 `MessageProcessor` → Main（主会话的冻结声明）。Main 自行决定是否 `task_control.accept` 建立 Work，是否 `send_message` 回复。回复省略 target 即发往当前 App 主会话，由 Social 本地投递并结算出站账本。
5. 响应返回 `{event_id, conversation_id, replay}`；Work 是否建立由后续状态投影体现，不在提交响应里猜。

**关闭电脑端**：什么都不发生。SSE 断开；Work 继续；后续回复照常写入 App 主会话账本。

**手机接回（同一 App 入口）**

1. 手机用自己的设备凭据 `GET /client/v1/home`，得到 App 主会话的 `latest_event_id`、该 Person 的其他入口列表、进行中与最近的 Work（`id`、所属会话、`state`、`revision`、等待类型）。
2. `GET /client/v1/conversations/{id}/events?after=<cursor>` 补读主会话消息；打开 `GET /client/v1/stream` 接收提示。
3. 补充要求：在主会话直接发消息（Work 等待中的问题按原会话匹配），或 `POST /client/v1/works/{work_id}/inputs {request_id, text}`。
4. 完成：Main 用 `send_message` 发结果与 artifact 到 App 主会话；手机通过账本看到出站事件，用 `GET /client/v1/artifacts/{artifact_id}?version=` 取原文件。电脑重连后按游标补读同一结果。

**跨入口接续 Work（在 QQ 私聊或 QQ 群里交办，手机查看、补充、取结果）**

1. **查看。** `/home` 按 `actor_person_id` 列出本人发起的 Work，私聊与群聊都在内。卡片标明来源（哪个 QQ 账号的私聊，或哪个群）、结果投递位置（原会话，即原私聊或原群）、状态与等待中的问题。等待问题只取该 Work 自己发出的问题事件；群 Work 只给这个 Work 的投影、问题与结果，不开放整段群历史。
2. **接纳补充或回答。** `POST /works/{id}/inputs {request_id, text}`，私聊与群 Work 共用，不另设群 Work 接口：
   - 授权在执行处：设备 → Person；Work 存在、未终结，且 `source.actor_person_id` 是该 Person（原授权就是发起人）。不满足返回 `not_found`；已终结返回 `precondition_failed` 并附原终态。
   - 在**一个短写事务**里提交三件事：① 在本人 App 主会话写一条入站事件（作者是 Person，来源是 App，消息号 `<app Binding 外部 ID>:<request_id>`，沿原入账去重）；② 在原 Work mailbox 插入一行，`event_id` 就是这条 App 事件，`source_key` 为 `client-input:<app Binding 外部 ID>:<request_id>`，`ready=1`，payload 为 `{text, origin: "client_input", source_conversation_id, device_id}`；③ 写命令回执：`principal_id` 为设备，`operation_kind=client.work_input`，`operation_ref` 为目标 Work ID，`payload_hash` 取（操作种类、Work ID、规范化正文）的哈希，`result_resource_id` 为事件 ID，`effective_state_json` 记 `{event_id, input_id}`。任何一步失败整笔回滚，不会出现“事件已写、补充未入队、查询却报成功”。
   - **payload 必须随插入一起写入。** 现在的 `WorkRepository.enqueue` 只有 resume 分支序列化传入内容，非 resume 分支写 `{}`（[work_repository.py#L1058](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/runtime/work_repository.py#L1058)）；普通消息靠先插入 `ready=0` 行、再由 `prepare_input` 在另一个事务发布内容（[#L1149-L1200](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/runtime/work_repository.py#L1149-L1200)）。P7 对 `enqueue` 做两处小改：增加可选 `payload` 参数，非 resume 分支也用它序列化写入 `payload_json`，`ready=1` 与正文同一条 `INSERT` 提交；增加可选的调用方 `session`，与 App 事件、命令回执同事务。重复的 `source_key` 沿现有 `on_conflict_do_nothing` 读回原行，`matches` 同时比较 `payload_json`，不同即 `WorkConflict`，不覆写已接纳的输入。第一版只有文字，不需要 `prepare_input` 的图片外置；不会出现“先发布 `ready` 的空 payload、再补内容”。`take_inputs` 照常从 payload 读 `text`，`WorkSourceGuard` 从同一 payload 读 `origin` 与来源会话。
   - 原 Work 正在执行时只入队，由运行中的执行在下一次 `take_inputs` 取走；处于等待时，先按现有 `acquire` 取原租约，再在同一事务里入队并按 `enqueue` 的 resume 语义转为可运行，resume 携带的就是上面同一份 payload。取不到租约就不写任何东西，返回 `unavailable`，客户端用同一 `request_id` 重试。
   - 重试与查询按命令回执核对**完整原操作**，不另建去重表：同一消息号已入账时，先核原事件作者是该 Person 且当前可读，再读引用该事件的命令回执，`operation_kind`、`operation_ref`（Work ID）与 `payload_hash`（含规范化正文）三者都一致，才读同一 `source_key` 的 mailbox 行，返回原 `{event_id, input_id, replay=true}`。同一请求号原来是普通消息（事件没有 `client.work_input` 回执），或改投另一个 Work、或正文不同，一律返回 `request_conflict`；反过来，`POST /messages` 遇到原事件是 `work_input` 时同样返回 `request_conflict`。响应丢失走 `GET /requests/{request_id}`，它按同一规则返回原操作种类与结果。
   - 不伪造来源：不在原私聊或原群会话补写事件，不生成 QQ 入站事件；App 事件就是这条输入的真实来源。也不在 App 主会话另起一次 Main 轮次：这条事件的入账只服务于补充，不调用 `notify_message`。
3. **通过来源核验（G13）。** `WorkSourceGuard` 对不属于原 Work 会话的追加事件，只在以下条件同时成立时接受，并照常把事件摘要记入 `additional_events`：本 Work 的 mailbox 有一行 `event_id` 等于它、payload 为 `origin=client_input`、来源会话 ID 等于该事件所在会话；该事件仍是 `keeper` 入站事件，作者是 Work 的 `actor_person_id`；所在会话是该 Person 的私聊。之后正文变化、被隐私遗忘或撤回，摘要比对失败，按原来源失效处理。原 Work 自身会话的 generation、`starts_after_event_id`、`prompt_source_revision`、可见事件、观察来源与 `privacy_generation` 检查一项不改；不把检查放宽成“同一 Person 的任意事件”。
4. **继续执行。** 原 Work 在原会话、原 generation、原工具声明与原预算下继续，工具调用与效果回执沿原执行身份；重启后按原 Work ID 恢复，mailbox 行与 `additional_events` 都已持久，来源核验按同一规则重做。
5. **结果。** 沿原投递规则：省略 target 时发往原会话，群 Work 就是原群。手机通过 Work 投影里的结果事件与 artifact 引用读取原结果与原版本文件。App 补充不会自动发成群消息，但原 Work 可能按任务内容向原群输出，补充里的信息因此可能出现在群里；卡片要说明结果投递位置，不承诺“补充内容不会出现在群里”。
6. **取消。** `POST /works/{id}/cancel` 按原领域规则（`manage_work` 的 revision 与权限）处理，群 Work 不另设规则。

手机在 App 主会话里随口说的话不会被当作对 QQ 私聊或群里那个问题的回复；回答原 Work 的问题必须走上面的接口。第一版只支持文字补充，不把个人端扩大成群聊客户端。

### 5.5 Conversation 与共享边界

| 情况 | 规则 |
| --- | --- |
| 同一 Person 的不同入口（QQ 账号 A、QQ 账号 B、Telegram、App 主会话） | 各自一个私聊 Conversation，各自 generation、公共历史、compact 检查点与模型 session；不合并，不拼接 |
| ACP 入口（方向 A） | Person 与 `acp` 绑定决定身份和入口；入口内每个 ACP session 是独立 Conversation；`session/new` 新建会话，不重建、不取消其他 session 或其 Work；同时执行多个模型请求沿现有按会话的协调，不新增调度器 |
| App 主会话的多台设备 | 同一入口、同一 Conversation；设备只是凭据，不按设备拆会话 |
| `/ai new`、手动 compact、generation | 只作用于执行命令的那个 Conversation（现有实现按 Conversation 推进，拆分后自然只影响该入口）；其他入口的 session 与运行中 Work 不受影响 |
| 隐私遗忘 | 按 Person 执行，覆盖该 Person 的全部入口会话（P4 把现有“取唯一私聊”改为遍历） |
| 主会话读取其他入口 | 显式工具调用，只读本人其他入口的账本；结果带平台、绑定、会话 ID 与事件 ID，标 `untrusted_data`；只作为本次工具结果，不写入被读会话，也不进入任何会话的公共历史；读到的历史指令不是本次用户的新授权 |
| 主会话向其他入口发送 | 必须明确目标 Person 与 `binding_id`；出站账本记在目标入口会话，SocialOperation 记来源主会话；`uncertain` 不重发 |
| 平台入口（QQ、Telegram） | 维持现有能力，包括按明确目标经 OneBot 读取历史；不声明跨入口账本读取工具 |
| Work | 属于建立它的 Conversation 与 generation；本人在任何入口可看、可显式补充或回答，补充事件留在 App 会话、进原 mailbox、由原 session 继续（§5.4） |
| QQ 群里交办的 Work | 本人发起的群 Work 在个人端显示卡片：状态、等待问题、结果与原版本文件，可文字补充、回答与按原规则取消；补充不自动发成群消息，原 Work 仍按原群、原 generation、原工具合同与预算执行；不显示群聊天记录 |
| Memory | 按 Person／SELF 作用域保存带证据的事实，不是会话历史；沿现行合同跨入口检索，入口拆分不复制或迁移 Memory |
| 主动消息 | 沿 Person 主动路由（指向一个 Binding）；拆分后主动消息记在该 Binding 的入口会话。`app` 绑定可以作为路由目标，默认不变 |

### 5.6 工具声明按入口类型冻结

现在每个部署只冻结一套工具声明，所有会话共用（G12）。主会话需要平台入口没有的跨入口读取工具，又不能在同一 session 中切换工具集合，所以部署初始化时冻结两套：

- **平台入口**：现有完整清单，`send_message` 的 person 目标增加可选 `binding_id`。QQ、Telegram 与 `acp` 入口使用这一套。
- **主会话**：平台入口的全部声明，加一个只读工具，按 `binding_id` 或会话 ID 读取本人其他入口的账本窗口，参数是内部事件 ID 游标与条数。

入口类型由会话所属绑定的平台得出（`app` → 主会话，其他 → 平台入口），会话一经建立就不变，不新增配置或注册中心。两套声明各有合同 revision；按现行合同，声明变更需重启并开始明确的新请求链。执行处照常核验权限：读取要求当前会话是该 Person 的主会话、目标会话属于同一 Person；跨入口发送要求显式 `binding_id`，目标是本人以外的 Person 时仍走现有目标授权。声明稳定只保证同一 session 内工具集合不变，不承诺模型缓存命中。

### 5.7 手机的两个角色：个人客户端与设备执行器

| 角色 | 做什么 | 凭据与授权 | 交付 |
| --- | --- | --- | --- |
| 个人客户端 | 登录、聊天、任务接续、结果与文件 | `client_devices` 设备 token，属于 Person；只授予个人 API | #299 交付服务端；Android UI 属于 S4 |
| 设备执行器 | 接受 Yuki 已授权的操作，用手机实际具备的能力执行，回传可查证的结果 | 单独配对的执行器凭据，属于同一 Person，按能力项授权；手机主动连接常驻核心（Memoh 的连接方向，§3.2），派发前设备端再核本地开关、权限与前台条件（OpenClaw，§3.4） | S6 |

两个角色可以在同一个 App 里，但登录聊天不授予手机操作权，撤销操作能力也不撤销聊天登录；本次的 `client_devices` 只承载个人客户端，不加执行器字段，S6 再加自己的凭据与能力声明。理解要求、选择工具、接续工作仍由现有 Main、Work 与效果回执负责；手机只承接设备操作，不把 Eta 的 AgentLoop 搬过来做第二个规划者，也不为每个简单操作强制建立复杂任务流程。下面用“帮我在手机设定明早七点的闹钟”说明 S6 的接入方式，本次不实现其中任何设备代码、协议或工具：

1. **提出要求。** 用户可以在 App、QQ 或其他入口说。身份照常由后端鉴权确定；这句话进入的是该入口自己的会话，由那个会话的 Main 处理。手机操作只能作用于**请求者本人**的执行器，群里其他人不能借此操作你的手机。
2. **确定目标与参数。** Main 解析“明早七点”为具体时间，并在本人已授权“闹钟”能力的执行器中选择设备。只有一台就直接用；有多台且确实无法从上下文判断时，才用现有 Work 等待问用户，不为单台设备多问一次。
3. **优先用系统能力。** Android 提供 `AlarmClock.ACTION_SET_ALARM` 等系统 Intent，可直接交给用户的闹钟应用（Android 官方文档：[AlarmClock](https://developer.android.com/reference/android/provider/AlarmClock)；真机行为待 S6 验证）。能用系统 API／Intent 完成目的就不走截图点击。
4. **必要时才操作界面。** 只有系统接口达不到目的（例如要在其他 App 里填写内容）时，才走“观察 → 点击／输入 → 观察结果”。每次操作带观察版本，画面变化就重新观察（OpenClaw 的快照 ID 与 `uiEpoch`，§3.4）；Accessibility 观察可参考 Eta（§3.4）。
5. **操作身份与回执。** 每个设备操作挂在原工具调用上，简单请求在普通轮次里完成；需要等待设备或用户时，才沿现有 Work 等待。操作 ID、目标设备、派发时间与结果先登记再派发，沿现有效果回执合同保存。已派发但确认丢失时，先按原操作 ID 向设备查询原操作与实际效果（例如读取下一个闹钟，或观察闹钟列表），不换后端、不换 ID 重做；这与 Eta “只有确认未派发才允许换 root 重放”的规则一致（§3.4）。
6. **结果状态分开。** 至少区分：**已交给系统**（Intent 已被接收）、**等待用户处理**（系统界面要求确认或授权）、**已确认设定成功**（有可查证的读回或观察）与**结果未知**。不能因为 Intent 或点击已送出就说“闹钟已设好”。
7. **之后由手机本地承接。** 闹钟设好后由手机系统负责响铃，不依赖聊天画面或 Yuki 后端在线；不重写闹钟应用，也不在后端另建计时服务。

设备离线不代表原工作取消：依赖它的操作按原操作 ID 等待或保持未知，重连后先查证再决定。已授权的操作范围、用户中途停止、人工接手与交回，按路线图 S6 与原执行规则处理（`manage_work` 的取消与续跑、Work 等待），不另加层层审批。手机控制始终沿同一个 Person、原执行身份与原回执接续，请求来自哪个会话都不另建任务系统。发行方式会影响能力：Google Play 版本对 Accessibility 自主操作有政策限制，OpenClaw 用 Play 版与 thirdParty 版区分（§3.4）。S6 的建议发行方式是先做不经 Play 的自用安装包，界面操作只在该版本提供；系统 Intent 类能力不依赖 Accessibility。这只是 S6 的候选方案，开始 S6 时再按实际能力与当时的分发政策确定，不是 #299 的前置决定，本次也不搭建两套发行版本。

**P4 迁移的回填规则：** 每个已有私聊会话的 primary alias 键是 `bot:<Yuki 账号>:private:<对方账号>`，取对方账号在同一 Person 下的 Binding 作为所属绑定。找不到或不唯一时迁移中止并列出会话 ID，不猜测。同一 Person 的其他绑定不回填，它们下次入站时新建自己的会话；旧会话里已有的事件、Work、回执、检查点和 `conversation_id` 一律不改。这些绑定的旧 transport alias 仍留在原会话上作历史定位；alias 键全局唯一，新会话改用 `binding:<binding_id>` 作 primary alias，不搬迁旧 alias。上线前用生产库副本统计多绑定 Person 数与 alias 冲突数（待验证）。

**P4 读取端的最小改法：** 只改写入端不够，因为读取端也用 transport `scope.key` 反查 alias（G9）。P4 把私聊会话解析收成一处：新增 `conversation_for_binding`，按“Yuki 账号所属 Presence 的平台＋对方账号 → 非 `transferred` 的绑定 → 该绑定的会话”解析，群聊仍按 alias。具体：

- 入站 hydrate 与出站 writer（[scoped_event_uow.py#L699-L715](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/persistence/scoped_event_uow.py#L699-L715)）用它找会话；新会话以 `binding:<id>` 作 primary alias。`ensure_legacy_alias` 遇到 transport key 已属于其他会话时，私聊不再追加该 alias，也不再报 `canonical_owner_mismatch`；群聊行为不变。
- 已有 turn 或读版本的路径直接用其中的 Conversation ID，不再按 `scope.key` 反查：`ConversationScopeRepository.get` 与 `load_prompt_snapshot` 取 `expected_turn.conversation_id`，无 turn 的私聊调用走 `conversation_for_binding`；`EventLedgerRepository` 的 `_read_version` 在复核时按 `ConversationReadVersion.conversation_id` 读，`_conversation_id_for_scope`、列表与搜索的 scope 子查询改为调用同一解析；隐私范围 `_canonical_conversation_for_privacy_scope` 同样处理。
- 进程内协调键本来就是 turn 的 primary alias（[scope.py#L56-L72](https://github.com/YuanYeYouTao/Yuki/blob/0aea047d42a9650fcc64c690bd8fae8014b73dc8/src/qq_ai_bot/conversation/scope.py#L56-L72)），transport key 只作围栏比较，不需要改。
- `/ai new`（`bump_canonical_generation`）、手动 compact、工具结果记录都按入账得到的 Conversation ID 工作，入站解析正确后自然只作用于该入口。

alias 表保留：primary alias 仍是 runtime key 与插件兼容键；私聊 transport alias 只作历史定位，不参与解析。不新建映射表。

### 6.2 个人客户端 API（`/client/v1`）

认证分两类：`POST /pair` 只凭一次性绑定码授权（不带、也不接受设备 token），成功后签发设备 token；**其余所有个人接口**必须带 `Authorization: Bearer <device token>`。客户端不得自报 Person、平台账号归属或权限。Binding／Conversation／ACP session ID 只用于选择目标；后端按设备凭据核实际平台、绑定与本人会话，不把这些 ID 当作主体证明。

| 方法 | 说明 | 复用 |
| --- | --- | --- |
| `POST /pair` `{code, device_label}` → `{device_id, token}`（**无需设备 token**） | 一次性绑定码授权；同一短事务内标记码已用、创建设备、必要时创建 `app` Binding。响应丢失时码已作废，用户重新签发绑定码；旧的未领取设备无 token 可用，可在设备列表撤销 | 新表；canonical 身份仓库 |
| `POST /link-codes` → `{code, expires_at}` | 为本人签发绑定码，用于配对新设备或在新平台账号上发送 `/ai link <code>` | 新表 |
| `GET /me` | 当前 Person 展示名、原设备来源、所选实际入口与原请求 namespace、本人的绑定列表（平台、展示名、状态）；人物归并保留多个原 App 入口 | identity readers |
| `GET /home` | 快照：`main{conversation_id, generation, latest_event_id}`、`entries[]{binding_id, platform, display_name, conversation_id, latest_event_id}`、本人发起的 Work 列表（含私聊与群 Work，标所属会话与结果投递位置）、`snapshot_at` | Work 查询按当前人物归并集合授权，保留原 `actor_person_id` |
| `GET /conversations/{id}/events?after=&before=&limit≤50` | 本人任一入口的私聊会话，按 `chat_events.id` keyset；只返回公开字段、附件引用与来源（平台、绑定）。读取不写入、不改变该会话 | 从旧 `list_chat_events` 提炼查询，不保留旧游标格式 |
| `POST /messages` `{request_id, text, attachments[]}` | 提交到本人所选入口；默认沿设备原 App，显式选择使用 `X-Yuki-Entry` 或 ACP 的 `X-Yuki-Conversation`。返回 `{event_id, conversation_id, replay}`；重试沿同一原入口 namespace 复用原入账（§5.4 第 2–3 步），不以新时间重建输入 | 实际 `app`／`acp` Gateway 入站 → `MessageProcessor` |
| `GET /requests/{request_id}` | 查原请求：`found`、操作种类（普通消息或 `client.work_input` 等命令）、目标（如 Work ID）、`event_id`／`input_id` 或命令回执状态；先核归属与可读范围，跨设备查询不重新派发 | `canonical_event_receipts`、`control_command_receipts` |
| `GET /works/{id}` | 公开投影：来源（私聊入口或群）、结果投递位置、state、revision、goal 摘要、等待类型与等待问题正文（只取该 Work 发出的问题事件）、子 Work 数、预算已用／上限、结果事件与 artifact 引用；不含群聊其他消息 | Work 仓库 |
| `POST /works/{id}/inputs` `{request_id, text}` | 补充要求或回答等待问题，私聊与群 Work 共用：所选本人 App／ACP 入口事件、原 Work mailbox 行（正文与来源随插入写入）与命令回执同一事务提交，返回 `{event_id, input_id, replay}`；同一原 namespace 内请求号的操作种类、目标 Work 或正文不同返回 `request_conflict`（§5.4）。原 Work 的会话、generation、session 与工具声明不变 | `WorkRepository.enqueue`＋原 canonical 写入器＋命令回执 |
| `POST /works/{id}/cancel` `{request_id, expected_revision}` | 取消 | `manage_work` ＋命令回执 |
| `POST /uploads` `{request_id, sha256, size}`＋文件 | 上传附件，返回媒体引用供 `messages` 使用；文件 I/O 与数据库登记分开处理，见 §6.5 | `ConversationMediaService` |
| `GET /artifacts/{artifact_id}?version=` | 下载原版本 | `WorkspaceStore` |
| `GET /activity?conversation_id=` | 本人某个会话是否有执行、来源、开始时间、步骤类别（不含提示词与工具参数） | 从 `read_conversation_execution` 提炼公开投影 |
| `GET /stream`（SSE，`Last-Event-ID`） | 提示：`conversation{id, latest_event_id}`（本人各入口）、`work{id, revision}`、`activity{conversation_id}` | 进程内提示中心 |
| `DELETE /devices/{id}` | 撤销本 Person 的设备 | 新表 |

**授权规则（在执行处核验）：** 读取的 Conversation 必须是当前人物归并集合内的私聊，保留原 `person_id`；operator 真正换主人不会使旧 Person 或旧会话进入新主人的集合。群会话事件不开放读取。新消息写入本人所选实际 App／ACP 入口，以及 §5.4 的 Work 补充；Work 按原 actor 或所属私聊与当前人物集合核权，不要求原 Person ID 与当前最终 Person 字面相等，不重写原作者或执行归属。群 Work 只给该 Work 的投影、等待问题与结果；artifact 必须被本人可读的出站事件或其 Work 结果引用。不满足一律返回 `not_found`，不透露存在与否。

原请求查询与重放也遵守同一授权：先核当前人物归并集合、原事件及所选入口的可读性，再按原请求 namespace 查回执并核对 `operation_kind`、`operation_ref` 与 `payload_hash`，不改原 device actor 或指纹。App 沿原 `request_person_id`，ACP 沿原 Conversation scope，旧 NULL 回执沿现行合同读取。另一台获准设备只有选择同一原入口 namespace 才能用同 UUID 重放原操作；归并后不同原 App 或不同 ACP session 的同 UUID 仍可各自成立。查询或重放不产生新的派发资格，无权请求不比较私人正文、不返回事件或回执。Work 补充仍只认本 Work mailbox 已接纳的那一条跨入口事件，不能仅凭当前人物相同放宽来源；触发事件与执行身份沿原合同保留。

### 6.4 状态投影与重连收敛

- **先订阅，再核对**：客户端打开 `/stream` 后，服务器先把该连接登记到提示中心，**登记完成后**再读一次该 Person 各入口会话的当前 `latest_event_id` 与 Work `revision`，作为第一条 `sync` 消息发出。客户端拿它和手里的快照比较，落后就按游标或 revision 补读。这样“快照之后、订阅之前”提交的结果必然被这条 `sync` 覆盖；之后的提交都会发出提示。SSE 只说“X 变了”，不承载事实。客户端也可以先开流再取 `/home`，两种顺序都以 `sync` 为准。
- **消息不会漏**：`chat_events.id` 持久且单调，`after=<cursor>` 可以完整补读；出站事件在提交后才发提示。
- **Work 不会错**：比较 `revision`；看到更大的 revision 就重读 `/works/{id}`。
- **丢提示就重连核对**：某订阅的提示无法投递或因慢消费者被丢弃时，结束该 SSE 连接，不保留表面在线但已缺更新的订阅。客户端自动重连，重新登记后接收首条 `sync`，按游标与 revision 补读；即使丢掉的是最后一条提示、之后没有新事件，也能收敛。进程重启同样走重连；回到前台再做快照比对。提示失败不撤销已提交事实，也不阻塞模型结果或 Work 完成；不新增持久事件日志。
- **不做的事**：不补造中间状态，不缓存流式 token（Yuki 的可见输出本来就是离散的 `send_message`），不把“正在执行”的诊断记录当事实——活动投影只说“有证据显示在执行”或“证据不足”。

### 6.5 错误与未知结果

| 码 | 含义 | 客户端应做 |
| --- | --- | --- |
| `unauthenticated` | 凭据无效或已撤销 | 重新配对 |
| `not_found` | 不存在或无权访问（两者不区分） | 停止重试 |
| `request_conflict` | 同一 `request_id` 内容不同 | 换新 `request_id` 前先让用户确认 |
| `version_conflict` | `expected_revision` 过期 | 重读后再决定 |
| `precondition_failed` | Work 已终结等 | 展示原终态 |
| `unavailable` | 服务器明确未写入任何东西（例如数据库 BUSY 后已回滚） | 可用**同一** `request_id` 重试 |
| 传输中断／超时（客户端侧） | **未知**，不是失败 | 用 `GET /requests/{request_id}` 查原请求，不换 ID 重发 |

服务器侧分两类处理：

- **数据库命令**（消息入账、补充入队、取消、配对、签发绑定码、撤销）：数据库写入与对应回执在短事务内完成；消息的模型、媒体准备与其他外部执行留在事务外。被拒绝时不写入；数据库 BUSY 且确认回滚后才返回 `unavailable`；提交确认丢失时服务器自己也不确定，沿现有合同保留原 ID，下次按原 ID 查回。
- **文件上传**：文件 I/O 不进入写事务。顺序为：① 流式写入按 `(device_id, request_id)` 命名的暂存文件，边写边算 SHA-256 与长度；② 与客户端声明的 `sha256`／`size` 比较，不符即删暂存并返回校验错误；③ 原子改名到内容寻址路径（同内容已存在则直接复用）；④ 短事务登记媒体记录与命令回执。失败语义：①②失败没有任何登记，客户端用同一 `request_id` 重传；③后④前崩溃只留下未被引用的文件，不影响事实，由现有“删除前核实际引用”的维护清理；④提交确认丢失时客户端查 `GET /requests/{request_id}`，已登记就直接取原引用，未登记就重传（③会复用已有内容）。上传成功不代表消息已发送，消息仍走 `POST /messages`。

### 6.6 三种“离线”分别意味着什么

| 情况 | 意味着 | 不意味着 |
| --- | --- | --- |
| 客户端关闭／断网 | 视图暂停；未发出的草稿留在客户端；已发请求结果未知 | 任务取消、Work 所有权变化 |
| 服务器重启 | SSE 断开；Work 由原调度器按持久状态恢复；`app` 投递若停在 Social 已认领、尚未结算，沿原 operation ID 处理，账本与回执同事务，有事件就有成功回执 | 重跑模型、重发 QQ 消息、重置预算 |
| 执行设备离线（S6） | 依赖该设备的步骤以原操作 ID 等待；已派发未回执的操作为未知 | 换设备或换后端再执行一次 |

## 9. 升级、回退与后续边界

### 9.1 升级与切换

1. **P1 合并**：无数据变化。
2. **P2 上线**：新管理 API 与旧 WebUI 并存最多一个版本，只为让 operator 切换 CLI；operator 用同一 TOML 声明。
3. **P3 上线**：确认退出条件后删除旧入口。宿主 `yuki-sandbox` Manager 与 Bot 镜像同版本更新；先更新 Manager 会让旧 Bot 的上传动作被拒，先更新 Bot 则无影响，所以**先换 Bot，再换 Manager**。

### 9.2 回退

- 0121 的新表旧代码会忽略；回退后个人设备不可用，但消息、Work、文件与回执都在原表里，不丢失。只要发生过一次绑定转移，同一平台账号就有两行，旧代码的全表唯一约束与按账号单行查找都不成立，此后不能降级 0121，只做前向修复。

- 不把“恢复旧数据库”当默认回退；回退期间 App 产生的消息仍属于原 App 主会话，回到新版后照常可见。

### 11.2 执行事实与接口修订

方向 B 的调用者是原 Work；外部 Agent 不是 Person、另一个 Yuki 或社交发送者。它的 session、prompt、进程和返回值归原调用与执行来源，不替代 Conversation、Work journal、原预算和效果回执。外部工具可自行产生的真实文件或网络效果按实际证据报告；Agent 陈述、进度 update 与正常退出不独立证明这些效果成功。对用户发信仍经原 Social，外部输出不会自动落成聊天回复或公共记忆。

现有环境由所有入口共用 Linux、`/home/yuki` 与 `/workspace`。B 复用该环境、Manager 和 Supervisor；不另建按 Person 的文件沙箱、共享宿主执行器、通用任意 RPC 或第二套任务调度。协议 stdout 必须保留字节与消息边界，stderr 用于日志；现有可轮转、可标记丢失的 `terminal_read` 输出不能充当无损 JSON-RPC 通道。环境不得因此取得宿主 Docker、Bot 数据库或 QQ 凭据。

权限判断认原来源、当前实际授权和所选 Agent 提供的能力。环境内已获准操作不叠加一律人工审批；确需用户决定的请求沿原 Work 等待与输入回接，绑定原 prompt 和选项，取消后迟到回答不取得派发资格。能力声明与执行授权分开，不因发现目录、read callback 或设备登录扩大权限。MCP 已退役，本轮不恢复 Yuki MCP 服务或动态工具；不向外部 Agent 注入一套任意 Yuki 工具，也不把 A 的非空 MCP 限制写成已解决。

标准 ACP 的 JSON-RPC ID 不提供跨重启业务幂等。先登记原意图和稳定调用 ID，再启动进程或提交 prompt；断连先查原 Manager run、原 journal 与已持久结果。已完成且配对未观察的结果只交原模型接续；已提交而无法证明完成的 prompt 保留未知，不因进程死亡、session 不一致或 load 不可用而换号重发。外部 session 的 load/resume 仅按实际协商能力使用，回放内容不当作新请求或已确认效果。原未知只约束该调用，不封死无关新任务。

#### 11.2.1 SDK、配置与原资源

宿主使用已锁定的 Python SDK `agent-client-protocol==0.12.1`、wire `protocolVersion=1`。隔离环境实读 SDK 的 `stdio.py`、`transports.py`、`_transport.py` 与 `connection.py`：`spawn_agent_process` 可通过 `transport_kwargs` 分开 stderr；`NdjsonTransport._read_line` 会拼接 `LimitOverrunError` 分片，不新增固定协议帧长门槛。SDK 的坏 JSON 行默认写日志后继续接收，不承诺另一套严格 parser；有效原响应、SDK 错误、缺失响应与进程退出各按真实事实处理。SDK 的进程内 JSON-RPC 计数和 pending future 不是跨重启业务幂等键，observer 也不是持久提交屏障。

Manager 增加 operator 的 `--acp-config` TOML 配置，按 `agent_id` 解析实际程序、argv、环境内 cwd、环境及凭据引用。模型工具固定为 `external_agent(action=list|prompt|get|respond|cancel|close)`，使用 `agent_id`、`prompt`、`peer_id`、`run_id`、`permission_id`、`option_id`／真实 outcome 与 cursor；所需字段由实际 action 决定。模型不提交 command、argv、env 或 cwd，不按配置数量生成工具、动态更换声明或按正文选 Agent。`list` 只返回配置的 ID、说明和有来源的能力信息，不启动进程、握手、认证或付费探测；协商能力只能来自真实初始化，缺失保持未知。

环境内新增一个薄 SDK peer，由原 Manager jobs、execd 和 Supervisor 管理。它使用独立 PIPE 连接外部 Agent，持有原 SDK connection、session 与 callback future；没有另一个业务规划循环或任务调度器。Bot 或 Manager 重启只重新观察原 peer，不关闭它的 SDK connection、不重做 initialize/new/prompt。外部 Agent 自身或 peer 真正死亡时，按原结果和退出事实收尾；不能找回的已派发 prompt 保未知，不自动拉起新 peer 重买。保留原 session 复用与协议上下文，不以一 prompt 一进程作为默认替代。

原 `jobs`／`environment_jobs` 中区分 `acp_peer` 进程资源与 `acp_prompt` 单次原执行，不另建任务表或预算。peer 记录真实 execd session 和环境代际，prompt 记录自己的稳定调用与结果；只有 prompt 对应 Bot 的原 `sandbox_task_runs` 和原 `CompletionOutbox`。peer 的空闲存活不算 Work 活动执行，peer 退出也不制造一条查无 Bot owner 的完成消息。单次 prompt 的完成与其是否已被 Main 观察继续分开。

| `acp_peer_open` | 原资源 `request_id`＋`agent_id`；返回原 `peer_id` 与 `peer_metadata`，初始化尚无确认时如实 pending，不重复建进程／session |
| `acp_prompt_submit` | 原 effect `request_id`＋`peer_id`＋prompt；先登记单次 prompt job，再交原 peer，返回原 `run_id` |
| `acp_prompt_query` | 按原 `run_id` 或原 request 查询 prompt；不是再次提交，也不因 unknown 获取重派发资格 |
| `acp_peer_events` | `peer_id`、`after_cursor` 与可选 `ack_cursor`；返回可靠事件页及 `next_cursor/has_more`，只确认 Bot 已持久接纳的位置 |
| `acp_permission_reply` | 本次原回答 effect `request_id`＋`peer_id/run_id/permission_id`＋实际 option/outcome；只回应原 callback，重复、拒绝与迟到回答沿原结果 |
| `acp_prompt_cancel` | 原 `peer_id/run_id`；核该 run 仍拥有活动 prompt 后向原 session 发原生 cancel，原 SDK prompt future 继续收拢，不用 future.cancel 丢弃原响应，不按今日 session owner 取消后来 prompt |
| `acp_peer_close` | 显式释放原 peer 资源；不能把本地接纳 close、断开或 OS 终止反写成未知 prompt 已成功／已取消 |

prompt 视图沿 `{request_id, run_id, peer_id, session_id, status, pending, peer_metadata, permission_requests, result?, error?, uncertain?}` 返回。`status` 复用原 jobs 的 queued/running/succeeded/failed/cancelled；真实执行已失联可有失败／中断事实且 `uncertain=true`，不能据此声称业务效果未发生。权限回调不是 prompt 终态，本地接纳 reply/cancel 也不是 Agent 已确认。`peer_metadata` 保原 session、初始化响应、Agent 信息和协商能力，敏感配置值不进入公开视图。

现行 `chat.py` 的 child resolver 仍用 `terminal_read(run_id)`，`subagent_execution.cancel_commands` 仍用 `terminal_control(cancel, run_id)`。Manager 必须按保存的 job kind 对 `acp_prompt` 读取／取消原 prompt，`get_code_run_by_request` 同样读原件；不能把这些原消费者误接成 OS kill peer，或在 Bot 复制工具名分流。`acp_prompt` 不进入 PTY 进程 launch/reconcile；`acp_peer` 沿原 Manager 进程链按实际 kind 启动和接回，不能被退役工具判断取消，也不使用 `environment_service` 的新 UUID 自动重启来恢复未知调用。

#### 11.2.3 原 runtime 挂载中的可靠协议原件

SDK peer 与 Manager 复用 `/var/lib/yuki-runtime/<peer_id>` 的原 runtime 挂载。Manager 不从 `terminal_read`、execd live 消息或诊断 stdout 解析 ACP。拟定文件 wire 如下；这些是原调用的协议原件，不是另一份 Work／完成台账。

| 原件 | 内容、写入者与读取者 |
| --- | --- |
| `spec.json` 的 `acp_peer` | Manager 从 operator 配置解析 `agent_id/command/args/cwd/env`；Supervisor 用固定 argv 启动只读 peer 代码，不经模型传来的启动命令 |
| `peer_metadata.json` | peer 原子保存真实 `peer_id/session_id/agent_info/agent_capabilities/initialize_result`；Manager/Bot 重查，不因缺少元数据猜已初始化 |
| `rpc/inbox/<sha256(operation_id)>.json` | Manager 在原 jobs 登记后原子写入请求；hash 只供文件命名，正文保原 operation ID、方法及参数 |
| `rpc/accepted/<hash>.json` | peer 在调用 SDK 前原子接纳原 inbox；重复读取沿 accepted/result，不再次调用 Agent。peer 死亡且只有 accepted 时不能证明未执行 |
| `rpc/results/<hash>.json` | peer 原子持久化该原调用的真实响应／错误后才交 Manager；Manager 将 prompt 终态与原 CompletionOutbox 同事务保存，再沿既有 Bot 持久接收后 ACK |
| `rpc/events.jsonl` | peer 将权限／进度等必要协议事件完整追加并 fsync，cursor 使用实际字节位置；原件不作轮转日志，不替换 UTF-8、不按经验帧长或 TTL 丢弃 |
| `rpc/events.ack` | 只记录 Bot 已持久处理的协议位置；权限事件先进入原 Work mailbox 再 ACK，丢确认按原事件身份重读，不重问、不重做效果 |

请求 wire 为 `{version:1, operation_id, method, peer_id, run_id?, payload}`；peer 方法为 prompt／permission_reply／cancel／close，结果保原 operation、peer、run、session、status/pending、result/error/uncertain。事件页为 `{peer_id, events:[{cursor,event_id,run_id,request_id,session_id,type,permission_id?,payload}],next_cursor,has_more}`；payload 保原 SDK 请求、选项或更新，不由自然语言还原协议事实。文件准备与外部 SDK 等待不进入 Bot SQLite writer。

权限 callback 的内部 question UUID 与 pending future 由存活 peer 持有，SDK 原 future 不被 Manager 的 HTTP／socket 等待者取消。Bot 以原 run 的 `sandbox_task_runs.source_json` 定位同一 Work，沿现有可靠接收链保存幂等的权限信号，不伪造 `ChatEvent`。Main 按实际已有授权直接回答；只有确需用户决定时才经原 Social 询问并进入原 Work 等待。回答只回原 permission，权限到达和恢复不能自行授权新操作；具体接续与竞争按 §11.2.5。

第二轮实核的反例是：现 Supervisor 的非 TTY 也合并 stdout/stderr，Manager output 会轮转并 UTF-8 替换，execd drain 丢 live 帧；常驻 run 会被 Work 的 `_owned_execution_clause` 当作未完活动执行；旧 completion 对同 run 只允许一个一致终态；服务 restart 会创建新请求与 run。因此上面的独立 PIPE、可靠原件、peer/prompt 分离及原调用恢复是必要修正，不是新增日志解析器、守护协调系统、辅助计数或完成门槛。源码落点为 `sandbox/persistent.py`、`environment_supervisor.py`、`db_models.py`、`task_repository.py`、`runtime/work_repository.py` 及现行 child resolver。

#### 11.2.4 Bot 派发、原来源与 peer 归属

`external_agent(action=prompt)` 是新派发，必须接在当前真实 Work 上，沿原 lease、generation、`WorkSourceGuard` 和执行处授权核验；不能以任意 Person、Conversation、peer 或 session 参数代替接纳 Work。首次调用先用原 effect 键和完整工具参数准备 `sandbox_task_runs` 的原来源与 hash，再以派生的稳定资源操作键打开 peer，并把原 `peer_id/session_id` 引用接回该记录的 progress，随后提交本次 prompt。崩溃在 open 与 submit 之间时查原资源操作与原 prompt request，不能另开 peer 或重提已未知的 prompt。启动参数和凭据由 Manager 的 operator 配置解析，不进入模型工具参数或公开目录。

续用 peer 核其原记录对应的同一 Work，不按 Agent 名称、当前 Person 或正文建立全局会话池；另一 Work、另一 Conversation 或另一人的同名 Agent 不能取得该协议上下文。父子仍沿真实 Work 树归属与根预算，派生子 Work 有自己的原调用，不因同属一人就复用父／兄弟的 peer。人物归并沿现行同人集合核授权，保原 `actor_person_id`、来源、已付请求与回执，不用今日 Person 字符串相等或平台账号重建 owner。

`list` 只读已配置 Agent；`get/respond/cancel/close` 管理原资源时先由 Bot 按原 run／peer 引用找到原 Work，再沿该操作已有的读取、回答或管理权限核验，不无故要求先 accept 一项新 Work。读取不取得续跑权；`respond` 只回答仍有效的原问题，不能借回答为已结束／撤权 Work 派发新 prompt。operator 管理权也不伪装为原 Person。Manager 不查询人物或自行赋予这些业务权限，持久 peer 更不因持有 SDK 连接就取得新的 Yuki 授权。

同一 peer 的当前 prompt 由真实协议资源约束；已有活动 prompt 时不自动并发塞入第二轮或换新 peer绕过，也不按经验增加进程或任务数量门槛。原 session 空闲时可继续同 Work 的新意图；外部进程失联、初始化缺失或 Agent 不支持 load/resume 时保原事实，不按品牌猜测恢复方法。

#### 11.2.5 权限信号、原等待与接纳竞争

现代码的 `WorkWaitRepository._observe_due` 只把终态／未知 run 作为 `owned_run` 的匹配结果；`route_child_completion` 遇到 active wait 不直接唤醒，普通 `enqueue(control)` 也不自动改变 Work 状态。因此只保存权限列表或 mailbox，仍会在 Agent 等权限、Work 等完成之间死锁。第三轮按以下规则接原等待，不新增问题协调器、完成计数或等待状态：

1. **先入账再确认。** 事件接收先按原 request/run/source 定位 owner，准备来源核验与 payload 后，在同一短 writer 内幂等写原 Work control mailbox，并完成必要的原 wait 投递；提交后才 ACK 该 peer 的实际 cursor。source key 使用原 peer／协议 event ID，不按正文去重；同一事件重读沿原 input，不重复问用户、不重复唤醒或回答。若 run 绑定确认尚未返回，可按已准备的原 request 核对并补接 run；owner 不明或写入失败不能先 ACK。已知原来源真正清退时按原清退回执处理并确认，不将其当成未知 owner 重建 mailbox／私人正文。只处理该 peer 的原位置，不让一处未知阻塞无关 peer。
2. **需要动作不等于完成。** 属于该 Work 的真实未决权限是 `requires_action` 控制信号；关联的 `owned_run` 正在 `any` 或 `all` 等待时，都经原 wait 投递路径及时返回 Main，reason 保为 `requires_action`。保留原条件、已匹配事实和其他 run，不把权限写成 prompt 终态，不伪造该 run 完成或 `all` 已满足。沿现有 delivered wait 与 `retire_fulfilled_wait` 收拢原 accepted wait；Main 回答原 callback 后，可按原 run ID 再等待剩余工作，没有自动重发 prompt 或另一条等待循环。
3. **先到事件也不能丢。** 权限到达、wait 注册和本 activation 结算可相互交错。注册原 wait 的 writer 必须同时观察已提交、尚待处理的原权限信号；不能仅在网络查询后再登记，也不能让较晚的 `waiting_external` 结算覆盖已经投递的原输入。测试分别覆盖事件先于注册、注册后到达及已提交未 ACK，不以轮询间隔证明不会丢唤醒。
4. **暂停与结束照原决定。** `running/queued` 的原 Work 在安全边界接输入；只有对应 `waiting_external` 才因原权限信号排队。`waiting_user` 不因辅助事件代替用户回答，显式 `suspended` 保留原问题等待明确 resume，terminal／失效 generation／真实撤权不复活。已派发事件和晚到结果仍是原事实，不能因不唤醒而伪称它们从未发生；隐私清退按原授权删除，不靠重读外部原件恢复被删内容。
5. **回答认原问题与授权。** 多个相同文本的真实 callback 各有原 permission ID；回答绑定 peer/run/permission 与 Agent 原选项，并沿本次原回答 effect 保存。已有人回答、prompt 已结束、取消或来源被撤销时，只读原结果或返回实际失效事实，不回答后来问题。Main 可按已有授权自动选原选项，确需用户决定才询问；拒绝与 ACP 的 cancelled outcome 分清，不把无效回答伪装成人类批准。向原问题补充输入不重置预算、不重建 session，也不取得任意 Yuki 工具或社交发送权。

进度 chunk、thought 和普通 session/update 留在原协议证据与按需结果中，不逐条创建 Work mailbox 或新的 Main 激活。权限信号进入的是原 Work 私有执行资料，不是公共聊天或记忆；只有原 Social 成功回执才证明对用户已送达。

#### 11.2.6 固定工具、回调、计量与取消消费者

固定 schema、调用分派与回执消费者一并修改，不能只把 `external_agent` 加进工具列表：

| 现行落点与反例 | 拟实施修正 |
| --- | --- |
| `environment_tools.EXECUTION_TOOLS`、`SandboxClient.execute/_stage_result` 与 `AgentTools.execute` 目前按工具名判断新后台执行 | 使用实际 action 的统一执行判断，只将 `external_agent(action=prompt)` 准备为新 sandbox task。`get/list/respond/cancel/close` 不另建 prompt task；它们的真实工具调用与回答／控制效果仍沿原 kernel、journal 与预算记账，不把只读动作另造为免费预算入口 |
| `work_control.reconcile_completed_children`、`work_repository.resolve_run_effects` 与 `work_journal.effect_result` 按原执行工具／request/run 恢复 | 保存并消费原 prompt 的执行角色与 run 引用；同名工具的目录、读状态、回答权限和关闭 peer 不冒充一次新 prompt。原终态只解决原关联效果；配对但未观察的结果沿原调用返回，不重放外部执行 |
| `capabilities.results.process_receipt` 目前只识别 terminal/code 类工具，artifact 化还会取独立进展摘要 | 识别带真实 prompt `run_id` 的 ACP 结果并保 peer/session、pending、stop reason、权限引用及原结果入口；`list` 成功、reply 被本地接纳或 close peer 不算 prompt 成功。大正文沿现有私有工具 artifact／分页，原回执与完整协议证据不被模型展示摘要覆盖 |
| `CoreCapabilityProvider`、`MainAgentContract`、`codemode/tool_visibility` 与插件 Main 入口分别消费固定声明及批准交集 | `external_agent` 只有一项固定声明和原执行实现，direct、Code、Main、子 Work 与获准插件共用。Code 只是调用语法，目录不追加工具；沿现有 sandbox 执行能力核验，不另造 Agent 名字权限、裸 SDK／任意 RPC 入口或插件绕过。只读 action 不因返回某个 run 就获得它的变更权 |
| `chat.resolve_child`、`subagent_execution.cancel_commands` 与原 completion receiver 仍使用通用 run 读／控制和完成 outbox | 按 §11.2.2 的 Manager 原 job kind 接原 prompt，Bot 不复制品牌／协议路由；peer 与 prompt 分离后，idle peer 不加入活动效果、owned_run 完成条件或 Work 收尾门槛 |

fs／terminal callback 只广告实际实现的 client 能力，操作通过原环境／Supervisor 路径完成，不落到宿主 Python 进程直接读写／执行。callback 沿已绑定的原 prompt 与实际授权，不以 Agent 的路径、标题、工具 kind 或 permission 选项自行扩大能力；普通环境文件操作不另恢复 CRUD 产品或一律命令审批。只读 fs 不暗带 write，terminal 能力须有真实 create/output/wait/kill/release 生命周期；本次读取／socket observer 的取消不能误杀原命令，真正 release／显式取消或关闭按确切资源收拢；普通 prompt／Work 完成不自动杀后台 terminal。操作已入外部执行后，Bot 撤权不会使其既有文件／网络效果自动消失，也不能声称所有 Agent 内部工具都可由 callback 逐次拦截。

根预算继续按 Yuki 原模型请求与工具派发计量，跨段／重启／父子树不重置。一次 ACP prompt 是一次委托工具调用，不能虚增一条“实际外部模型请求=1”冒充内部多轮已计量；Agent 报告的 tool call、token、cost 与 Yuki 自身的派发计数分开。稳定 ACP `usage_update` 只提供当前 context 使用量／容量及可选累计 cost；逐 input/output/cache token 的 prompt usage 不属于稳定 v1 统一保证，SDK／适配器扩展只有实际返回时才按原来源保存。缺失保持未知，不从上下文差、正文长度或本地 hash 推出 cache 命中，不把累计值重复加作逐次耗用，也不因不可观测新增拒绝门槛。原有模型／工具上限只约束 Yuki 可计量的调用，不能宣称覆盖外部 Agent 内部总消耗。

逻辑 Work cancel／fail 仍由原短事务撤销所选子树的新效果权并提交原管理回执；不等待所有外部取消确认，也不以历史效果全成功才允许结束。事务外按原 prompt run 发送 native cancel 并接回原 future，已发送不等于外部实际停止。成功完成、原生 cancelled、真实进程退出及未知分别保存；收到原结果仍可解决旧效果，不复活 Work、不抹去既有 Social／文件回执。重复／迟到 cancel 只查原 prompt，不能停止同 peer 的后来 prompt；关闭 peer 是资源操作，不把本地 close ACK 当作未知 prompt 的业务终态。

#### 11.2.7 会话寿命、真实撤权与隐私清退

idle peer 不阻止 Work 完成，但仍是同一原 Work 可继续使用的协议资源。原 `sandbox_task_runs.source_json` 保 Work、Conversation、generation 和原 actor，progress 保 peer/session 与资源操作引用；不能只从仍 waiting 的 prompt 查 peer，已 completed 的 prompt 也可能是存活 session 的唯一关联。普通 completed 不自动 kill Agent 工具／后台任务或抹清会话；直到显式 close、原 Work 真正归档或隐私清退才回收原 peer，不增加固定 idle TTL。cancel／真实 source 撤销先撤原新效果权，收拢其活动 prompt 与必要资源；仍保留的原会话不因此得到续跑权，也不能丢掉 owner 引用而成为环境里的无主 peer。

Person forget 按现有同人归并集合及受影响 Conversation／Work 树处理；disabled、来源撤销及回答核权沿当前真实身份事实，不用今日 Person 字符串相等把原作者换掉。现 `PeopleRepository.prepare_person_forget` 已在 writer 前读取受影响 Conversation 的全部 sandbox request ID，不限 status；`apply_person_forget` 却会在 `purge_scope` 后删除 sandbox continuation/run。`AdminCommands.forget_person` 和 `PeopleRepository.delete_person_id` 两个实际调用入口都缺 writer 外的 Manager 收拢。子 Work 的 `SubagentRepository.maintain` 也会在真正 archive 时清 journal/effects/source，必须在清引用前捕获原 peer。若直接沿用这些删除，将失去仍活 peer 的 source/progress 关联；不能只修模型 cancel 工具：

1. 复用现有 prepare 快照，在首次写入前准备受影响 Work／子树、prompt request/run 和全部 peer/session 引用，包括 completed prompt 所关联的 idle peer。`SandboxTaskRunModel` 只有参数 hash，没有参数正文，peer 从已确认的 progress/completion 或原 Manager job／稳定资源操作查回，不能从 hash 还原，也不新增空 task 或全局 peer 影子表。准备清退所需的外部 I/O 在 writer 外完成；不扫描整个 HOME 猜 owner。
2. writer 外以原 forget／archive 操作派生的稳定 close ID，把这些精确资源的清退意图交 Manager 原 jobs／可靠 rpc inbox 持久接纳；存活 peer 独立消费，ACK 丢失查同一原 intent，不换号重提。不新增 Bot 清退轮询／台账或另一业务任务。Manager 是否已持久接纳尚未确认时保原关联并返回实际未知，不能先删 Bot owner；这只约束本次隐私删除，不阻塞无关 Work，也不改变普通 Work cancel 不等远端确认的合同。
3. 只在持久接纳已有事实后进入原短 Bot writer，复核实际隐私／撤权依赖，停止原 Work 的新效果并删除原关联；绝不在 writer 等 Manager／SDK。原管理回执可保必要 peer／close ID 及 pending 事实，不保要清退的聊天正文。持久接纳不等于物理已退出／已删净，实际 close 结果沿原操作查询；Bot 在这些边界重启仍查原件，未知或部分完成如实报告，不增加 Bot 后台清退协调器。

上述准备／接纳 hook 必须由两个 forget 入口共用，覆盖 Admin 独立构造的 `PeopleRepository`、容器及 `/ai` 路径，不能只注入一处实例。最终 writer 的来源快照复核若与准备时不同，不能继续删除新范围；原精确旧 peer 的 close 已是该次获准操作的实际效果，保其原 ID 和结果，不冒充整个删除成功、不改目标或自动再执行新范围。第四轮确定复核依赖包括原同人集合、受影响 Conversation／Work 来源与待删 sandbox request/peer 关联；不是行数或今日 Person 字符串。清退接纳后 peer 标为 closing，不再接受该资源的新 prompt。最终 writer 如发现 prepare 后新增的原执行或归属已改变，则保留引用并报实际冲突；不在 writer 重新做外部 close，不吞掉新范围。若删除先提交，后来的新派发仍须经原 Work/source/generation 核验，不能由已准备的 peer 引用绕过。close 精确原件、外部 I/O 与短 writer 的回归覆盖两个顺序；不新增全局隐私锁或辅助准入状态。

至少关闭原活 peer，并按现隐私范围清退明确关联的协议目录／私有上下文；不删除共享 HOME、operator 凭据、无关 peer 或既有交付 artifact。外部 Agent 自有历史若另存于 SDK 默认目录，须按实际所选适配器核清退入口及覆盖范围，不能假定 ACP close 会删除磁盘历史；可用的 session/delete 按真实能力使用，不要求所有 Agent 必须支持，也不无证据宣称完整外部擦除。本次实际适配器不统一保证远端或其 HOME 内历史擦除；close 仅证明原进程和本项目受管协议私有内容按原清退结果收拢。Manager 保必要原 operation/peer/终态及清退事实，按实际引用清受管 spec、prompt/result/event 正文；不宣称完成供应商侧全量擦除，不扫描共享 HOME 或按品牌猜历史路径。operator 保留的 Agent 自有登录／历史目录按其独立隐私策略处理，文档明确覆盖范围。隐私清退后的晚到 events／completion 只完成原清退和投递确认，不恢复已删的 Work、人物或正文。

实施阶段沿原事实补核两处消费者细节：首次 open 在网络途中而隐私删除先到时，仅查询“尚无 peer”并不足以清退。Bot 必须在 open 前保存原 `resource_request_id`；Manager 允许该原资源的关闭意图先到，复用原 jobs 的 closing/取消事实，后来同号 open 不启动进程。已完成 open 仍按精确 peer 清退，不加全局锁、清退台账或重派发。另 SDK `PromptResponse` 通常只有 stopReason，正文／工具／文件实际来自 `session/update`：原 prompt 结果保存自身 event cursor 范围，query 返回该原 run 的更新及分页位置，不能只把 end_turn 交给 Main 冒充任务结果。
