## 当前源码事实

1. **历史为倒序，结果未明确最新端。** [Codex `_turns`](../../../../packages/yuki-agent-connector/src/yuki_agent_connector/drivers/codex.py#L339) 固定 `sortDirection=desc`，分页按返回顺序 yield；[历史组装](../../../../packages/yuki-agent-connector/src/yuki_agent_connector/drivers/codex.py#L744) 不反转，也没有明确排序字段。[工具合同](../../../../src/yuki/external_agents/tools.py#L15) 只说明读取历史，未说明方向。Git 历史中 `9c676280` 已有这一路径；10 月 25 日前主线 `865bc6af` 的排序与当前一致，但这不单独证明当时安装 wheel 的版本。
2. **查询当前状态缺少当前行动的直接结果。** 原生 get 使用 `thread/read(includeTurns=false)`；活跃/指定轮可查询状态，但默认不返回其行动 items。`include_history=true` 才展开全部历史页。空闲时未指定 execution，也不会自动选出最近已结束轮。因此“只要再 get 一次”不足以回答具体做到哪。
3. **Artifact 只认原数组位置。** [数组读取](../../../../src/yuki/tool_results/artifacts.py#L1088) 保原顺序切片，未将尾部改成最新。不能为 Codex 改通用切片含义。百万字符结果转 Artifact 后，[短结果投影](../../../../src/yuki/capabilities/results.py#L393) 也不会自动保留历史方向和最新行动；只在巨大原文加提示仍可能不可见。
4. **操作确认与实时会话查询不同。** [服务 `_get`](../../../../src/yuki/external_agents/service.py#L202) 的 operation/run 路线查原回执及重要事件；[Connector](../../../../packages/yuki-agent-connector/src/yuki_agent_connector/connector.py#L142) 通常读 journal，unknown 才进入 recovery。session 路线才读原生会话。服务器事件 `cursor=0` 的[第一页](../../../../src/yuki/external_agents/repository.py#L861)为升序最早 100 项，也不能默认当最新。本次重点旧历史误读不能被另一条尚未命中的查询路线替代。
5. **Yuki Work 与原生会话分开。** [Work 查询](../../../../src/yuki/runtime/work_queries.py#L106) 主要给目标、生命周期、等待和计数，不直接提供最近执行步骤。原 Work 接续已有私有执行证据，客户端也有原步骤投影，不能说所有入口都没有事实。若用户问的是 Yuki 自己的工作，要沿原 Work 和现有获准回执定位，不套用本次 Codex 个案。

将主动追问列为 T14，与 #514 同次完成但独立定位。沿原 `list/get`、native turn、工具结果投影和原回执补最短查询：按问题区分当前活跃轮、最近已结束轮、明确指定的旧 execution、原操作确认及持续监督目标。返回最新相关 turn 的真实 ID、时间、状态及必要行动内容，历史方向和后续读取入口在短结果/截断结果中仍可见；保原数组 offset 语义，历史按游标续读，不默认遍历完整 transcript。
