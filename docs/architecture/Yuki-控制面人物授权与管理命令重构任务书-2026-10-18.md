## 2. 人物授权定稿

### 2.1 唯一事实源

在现有 `persons` 表增加一个默认 `false` 的 `is_superuser` 属性，直接保存人物资格。不建 role/grant/scope 表，不建角色注册中心、权限缓存或授权版本系统，也不把 `SUPERUSERS` 换成另一串持续参与运行鉴权的 Person UUID。

`identity.authority` 按内部 Person ID 解析当前 root，读取当前人物资格；不再查询 QQ Binding、平台账号、昵称、Presence 或环境变量来推导资格。共同的有效超管查询保留原 actor Person ID，核原人物与最终 root 均启用后读取 root 资格，不能先改成 root 而丢失原来源停用事实。没有账号的人仍可被授予资格；Binding、设备与 Work 来源有效性继续沿原执行链核验，无效来源不能据此执行。

授予、撤销沿现有共同管理操作、Person revision、短事务、`control_command_receipts` 和审计完成。操作对象只能是明确的内部 Person ID。具有对应管理能力的 operator 或超级管理员 Person 可执行；不让请求方自报的 `is_superuser` 成为调用者授权。

现有 `ControlPrincipal` 继续表示已解析主体；Person 资格映射到明确的有限能力集合。现有集合缺少部分身份管理能力，实施时显式补齐 Person/Binding/Presence 读写与恢复、资格授予/撤销及现有 admin 领域所需项；能力声明、执行消费者和实际角色映射必须对应，不用角色名称隐含授予任意新能力。

operator 保留当前独立 Bearer 主体和显式 capabilities，不被称作 Person 超管，不因持有 operator 凭据取得某个 Person 的发言身份。升级 policy 示例显式授予本次必需的新操作能力；“独立恢复路径”指具备对应能力的 operator，不宣称任意旧凭据都自动获新权限。不给这两类凭据再叠一套鉴权框架。

### 2.2 生命周期

| 操作 | 人物资格与原事实 |
| --- | --- |
| 修改昵称、换平台、换网关 | 不改变 Person 资格 |
| 账号关联、停用、恢复、解绑或转移 | 不改变原 Person 资格；账号转给另一人不携带资格 |
| 设备撤销、Presence 停用 | 不改变人物资格；原失效入口仍不可用 |
| Person 停用、恢复 | 保留资格，只暂停或恢复该人物的活动，不把停用等同撤销资格 |
| 显式撤销资格 | 当前 root 的 `is_superuser=false`；后续新效果按撤销后事实执行 |
| Person 遗忘 | 随人物清退资格；同账号以后创建的新 Person 默认无资格 |
| 同一人的显式合并 | 只合并操作前两个当前 root 尚未撤销的资格，目标取逻辑 OR；以后只认最终 root，不从历史成员捞旧值 |

同人合并保资格不等于恢复来源：不改两侧既有 `enabled`，不恢复旧设备、Binding、执行或被撤销的委托。停用是暂停使用，撤销是删除资格，不能混成一个布尔含义。禁用来源原入口继续被拒绝；目标合法入口按合并后的当前人物资格工作。对最终人物撤销后，历史非 root 的旧 `true` 永远不作为 fallback。

不新增“最后一个超管不可撤销”“超管不可停用”“必须至少有一名超管”等保护门槛。全部 Person 超管失效时，已有独立 operator 仍能执行明确的授予和恢复操作。

### 2.3 升级与首次初始化

1. 冻结数据库迁移只增加默认 `false` 的字段及必要 schema，不读取运行环境、不调用可变 ORM、不在 migration 中解析 QQ 账号。
2. 升级前，用旧配置与当前库只读生成一次 `旧 SUPERUSERS QQ → 已有 Binding → 候选 Person` 清单。清单是迁移材料，不是新权限源；发生过转移、退役或无法确认时，不静默授权今日账号持有人。
3. 保存候选清单后，先清除实际 `.env`、Compose 与进程环境中的旧 `SUPERUSERS`，再启动已删除旧配置桥的新代码。不能把旧 CSV 留给 NoneBot 重新解析，否则可能在取得管理入口前启动失败。随后按明确 Person ID，经具备相应能力的 operator 路径显式授予，保原请求号和回执；重启、重放旧请求、重新绑定账号均不能重新 seed 资格。
4. 新安装由既有 server-owned operator 创建可无账号的 Person、授予资格，再绑定 QQ/TG 或配对个人设备。不依赖第一条 QQ 消息，不要求安装者必须有 QQ。
5. 迁移清单和准备动作不冒充已授权、已上线；实际赋权、重启复核分别记录。保留原事件、执行、预算、请求指纹、会话和回执。

### 2.4 当前权限与已付历史

`AdminActor.is_superuser`、`ToolRuntime.actor_is_superuser`、自动化 authority snapshot 等不再是独立权限来源。已有历史布尔可以保留为当时执行证据；UI 与当前执行上下文可使用共同解析的资格。模型工具声明仍按部署及既有入口类型冻结，不能按 Person、设备或角色动态增删声明；资格只在实际操作执行处核验。

真正管理员写入在原短事务内使用已有 session 和原 actor Person ID 核当前授权，外部特权效果在原派发边界核当前授权；受保护读取也在原读 session 内核当前授权，不为读取取得 writer。撤销后不能靠长执行中的旧 `true` 继续读取他人正文/证据或产生新特权效果。授予也不扩大原委托范围或插件批准；已经读取、已发生的效果、paid 输入与原回执不倒改、不重发，不为取得新资格重买模型请求。复用同一准备阶段已解析的主体，不在每个适配层重复查人，不新增授权 worker、定时缓存或版本协调器。

### 2.5 Person 资格与入口行为

QQ/TG 等平台真实入站先解析 Person，再执行该入口支持的显式命令。App/ACP 个人消息正文继续作为普通输入，不解析 `/ai` 管理命令或插件直达命令；不因属于超管 Person 就把设备 token 变成 operator 凭据，也不通过伪造“普通人”来掩盖入口错误。

现有模型工具仍按自己的真实执行授权工作，本任务不另加内容门禁。个人设备若要使用显式管理能力，仍需现有管理入口及其真实凭据；不在本次隐式扩张个人 token 权限。

## 4. 管理命令与应用层结构

### 4.1 调用方向

```text
QQ/TG 真实入站 -> 原身份/事件接纳 -> 聊天命令适配
                                      | 解析、调用、呈现
operator CLI -> HTTP 认证与 DTO --------+-> admin 共同应用操作
                                           | 当前授权、原回执、事务边界
                                           v
                              人物领域 / PluginManager / 配置服务
                              manage_work / Memory / Emoji / 原仓库

App/ACP -> 原个人 API -> 原 Processor/Main/Work/Social
           不经聊天管理员命令解析

普通接纳前：真实连接/账号 -> 原关联码或群恢复适配 -> 同一身份/管理操作
            不要求先建立普通聊天事件，不创建第二套身份或授权
```

共同应用操作不属于 `admin_api`，HTTP 只是适配器。聊天与 HTTP 按各自真实身份调用明确方法；没有“把聊天字符串转发给 HTTP”或“HTTP 调聊天 execute”的反向依赖。

停用/未登记群不能依赖普通入账后的 parser 才获恢复。原 QQ pre-ingress 恢复迁到明确的 `/ai admin group current enable`，复用同一叶操作解析和共同 Person 授权，保当次真实连接、群目标与原路由证明。已登记群沿内部 Space；首次登记只认当前真实平台事件提供的群，不开放任意外部群号冒充目标。该共同操作不内置 QQ 名单，平台差异留在接入证明适配；对应的其他平台入口一并核查，不复制一套 QQ 业务逻辑。原 `/ai link` 的接纳前关联码路径同样保留，不因命令总分派搬迁而先自动建另一个 Person。

### 4.2 聊天语法收拢

管理入口统一为 `/ai admin <领域> <操作> ...`。普通会话控制和本人自助命令保留其本来职责，不把普通用户功能全搬到管理员命名空间。

| 入口 | 范围 |
| --- | --- |
| `/ai help`、`ping`、`status`、`whoami` | 当前可用信息与本人资料 |
| `/ai capabilities` | 现有能力说明；不因查询修改固定工具声明 |
| `/ai link [code]` | 既有本人配对/同人关联码流程；兑换保原接纳前边界，不进入 Main |
| `/ai forgetme` | 本人隐私删除；保取消执行、会话边界、受管资源清退和独立回复策略，不当作普通管理写入 |
| `/ai new`、`compact`、`stop` | 当前 Conversation/执行；沿真实作用域和已有授权，不新建运行时 |
| `/ai memory`、`preference`、`automation` | 本人已授权的自助操作；跨人物维护走 admin |
| `/ai plugin run ...` 与已批准插件直达命令 | 原插件明确注册的调用；仍按实际叶操作权限和插件批准执行 |
| `/ai admin person ...` | 人物发现、资料、启停、合并、遗忘与显式超管资格变更 |
| `/ai admin binding ...` | 账号发现、关联、恢复、停用、转移；原历史不迁给新账号持有人 |
| `/ai admin presence ...` | 既有 Yuki 账号的查看、enable/disable 和接入资格设置；不把 Presence 转成 Person |
| `/ai admin group ...` | 真实 Space 启停与现有管理动作；参数认内部 Space ID，当前群快捷目标来自已解析上下文 |
| `/ai admin config ...` | 现有运行配置读取与修改 |
| `/ai admin plugin ...` | 发现、批准、启停、配置与诊断，与 plugin run 分开 |
| `/ai admin work ...` | Work 发现、详情、取消与恢复 |
| `/ai admin model ...`、`memory ...`、`emoji ...` | 各领域现有、适合聊天的管理能力 |

删除旧 `/ai on`、`off`、`private`、管理用途的旧 `group/config/model/emoji/plugin` 分支，以及自助命令中混入的跨人物管理解析。帮助直接说明新用法，不叠兼容 alias 或维护两套 parser。`/ai private` 的实际能力改成明确的 `admin person enable/disable`，不增加 private-only 状态。

共享应用操作不等于每项操作都要开放聊天：模型密钥仍使用现有 CLI 环境输入和私有 HTTP 保存，不设计把密钥粘进聊天正文的命令。原 operator HTTP 合同默认保留，本次只增加完成角色、恢复和查询闭环所必需的有限方法，不顺手新增所有领域的远程 API。

### 4.3 拆分原则

- `CommandService` 退出万能服务职责；总路由只识别有限的会话、自助、admin 和插件命令组。
- 会话、人物、配置、Memory、Automation、插件、Emoji 各自有聊天适配模块，只处理参数与中文呈现。已有 `ConfigCommandHandler`、`AutomationCommandHandler` 等能整理复用的继续复用。
- `ProfileCommandHandler` 的本人资料与管理员 Memory 解析拆开；`EmojiAdminService.execute/_execute/help_text` 的字符串解析与呈现移出领域服务，实际表情操作保留明确方法。
- 原 `admin_api/commands.py` 的应用操作搬到 `admin/`，按身份、插件、模型、Work 等真实领域组织。已有 `_database_command`、`_external_command` 和 replay 语义复用，不为文件行数搭空壳或拆一层转发一层。
- 一个实际叶操作只解析一次，用法与帮助说明靠近该操作；总 help、现有 capability 展示读取相同说明。有限静态映射足够，不建立命令总线、动态注册中心、通用基类、DSL、任意 RPC 或反射执行器。
- 授权归共同应用/领域执行边界，聊天适配器不另存管理员名单。删除顶层 `command_requires_superuser` 粗集合对混合子命令的代判；自助 owner 校验与真正管理员能力仍按原事实执行。
- `AdminActor` 的授权职责收回 `ControlPrincipal`，审计来源使用原 `ControlAuditRef`，外部账号仅作真实来源资料。不能仅把可传入布尔换一个名字。
- 删除 `may_write`、`image_blocks_command`、emoji import 绕行及对应“有图不能写”提示与测试。附件存在不改变命令授权；各领域仍处理自己的真实参数与附件。

### 4.4 装配与回执

由 ApplicationContainer 在原装配位置构造一次 `ClientIdentityService`、人物仓库和相关共同 owner，再分别注入个人 API、关联命令与管理操作。删除 `ClientApi(self.admin_api.commands.identities)` 及管理适配器内部自行 new 这些 owner 的反向依赖；生产路径的后备组装移出，测试显式组装所需依赖。

`forgetme` 与 operator forget 各自真实入口汇入共同人物删除领域操作；保 `Processor._handle_privacy_command` 原有相关执行取消、scope 边界与 writer 外资源清退。共享回执包装不吞掉隐私准备、并发复核和清理，删除后的回复不重新建立被遗忘的正文或人物。

不重命名原持久 operation 值，不重算旧请求 hash，不另开 receipt 表。HTTP 沿原 principal/request UUID，聊天沿可信内部事件和原命令回执关联；平台消息号不参与重建业务身份。同一次管理修改只有一个真实效果 writer 和对应原回执，不双写两套完成事实。

共同操作明确接收 principal、原 request UUID、目标、规范参数及该操作实际使用的 revision。普通已入账聊天命令首次接纳时在原回执/审计链持久关联一个请求 UUID 与原内部事件 ID，重复处理查回该关联；不得每次 `RequestId.new()`。如现有字段不能证明关联，只补原表必要关联字段，不建立映射表。聊天适配准备一次当前 revision，与该原请求一起保留；重放不重新读取今日 revision、重算指纹或强制覆盖。显式给出 revision 的 HTTP/CLI 沿现有行为；原本仅按请求号的关联/合并等操作不强加 revision。

pre-ingress 恢复沿原已持久化接入请求及回执关联，不伪造内部聊天事件，不拿平台消息号重建已有业务身份。新增 enable、资格授予/撤销、Presence 等操作同时补 `CommandOperation`、能力表、回执/审计投影与 replay reader；旧枚举值、旧参数和旧 hash 保持原义。命令语法迁移不删除真实升级 reader。

running/unknown、确认丢失、重复请求和外部效果的原语义继续保留。共享服务与消息呈现分开，不能因为中文提示发送失败而再次执行已经完成的管理操作。
