## 3. 第 5 项：没有原生 continuation 的唤醒改为追加原链

### 3.1 现状【实证】

精确恢复（沿原链追加）与业务续跑（`rebase_business`，换新链）由两处判定决定：

- `runtime/context_preparation.py:45-49`：准备阶段只在暂停重放、原检查点带 continuation、或子 Work 带压缩状态时选择精确恢复；其余情况先组装新的公共上下文。
- `runtime/work_session.py:279`：`exact_recovery |= transcript.continuation is not None`；`:296`：子 Work 带压缩状态时也算精确恢复。
- `runtime/work_session.py:404-418`：原响应已配对、没有待执行调用、不是暂停重放时调用 `rebase_business`；`:445-494` 在 `exact_recovery` 为真时直接返回。
- `services/turn_execution.py:332-339`：待执行调用续跑完之后，再试一次 `rebase_business`。

于是没有 continuation 的根 Work 每次唤醒都会：以新准备的公共上下文为前缀，接上一轮未观察的工具轮（可移植证据）、Host 选中的媒体和一份 `work_current_material`，换一条新链（`chain_links.reason = "business_resume"`）。Provider 缓存只命中到公共历史为止。

**测试也有同样的缺口**：`tests/integration/test_external_agent_prompt_prefix_e2e.py` 的 Claude Messages 场景用 `FakeLLMProvider` 直接返回 `ChatResponse`，不经过适配器解析，所以也不带 continuation。这个测试对唤醒只断言“共同前缀不短于公共历史”，Chat Completions 和 Claude Messages 两个场景都在走 rebase。生产中 Claude Messages 与 Gemini 适配器每次都返回 continuation（`llm/anthropic_messages.py:479`、`llm/gemini.py:480`），不受影响。

### 3.2 方案（删除优先）【决定】

所有者规则：rebase 只留给合同变化、来源失效和压缩。合同变化与来源失效原本就不走 `rebase_business`，而是由 `journal.load` 返回 `contract_changed` / `source_changed` 并换新链（`work_session.py:156-262`）。所以要做的只是**不再按 continuation 分流**：

1. 精确恢复不再看 continuation。凡是 `resume` 检查点，一律沿原链追加；新聊天按原生协议现有的公共观察边界补在末尾（`services/turn_execution.py:533-560`，依据原链保存的 `source_guard` 可见事件）。
2. 唯一保留的 `rebase_business` 调用是压缩本身：根 Work 在恢复中采用一份已付、有效、未配对的**公共**压缩（`context_compaction.public` 存在）。公共压缩改变了共享前缀，本次激活要接到采用后的公共历史上。准备阶段对这一种情况照旧组装新的公共上下文，两处判定写成同一条件。
3. 删除：
   - `WorkSession.exact_recovery` 字段。恢复后它与 `uses_recovery_transcript` 恒等，两处读取（`turn_execution.py:344`、`:799`）改读后者。
   - `rebase_business` 的门槛判断、子 Work 分支和 `append_material` 参数。
   - `turn_execution.py:332-339` 待执行调用续跑之后的那次 rebase。
4. 不新增状态、阈值、开关或迁移；Provider 请求格式不变。

对 Chat Completions 链，行为变化与 Responses 现行完全相同：

- 唤醒的首个请求不再追加 `work_current_material` 和参与资料。Work 材料已经在原链里（`main-agent-runtime.md:354-357`）。
- 执行压缩之后的唤醒接着压缩链追加，不再重建公共前缀。
- system 前缀整体保留，直到压缩或合同变化换链：
  - 名称或 SOUL 热更新不再在每次唤醒生效（`main-agent-runtime.md:84`）；
  - 常驻记忆段与经历目录也一样（#681/#227 的 F17、G17 用例此前用不带 continuation 的测试 Provider，断言的是“续接后按新水位渲染”，与生产 Responses 的实际行为不同）。
- 旧链未观察的工具轮以原生 tool 消息留在链中，不再转写成可移植证据。可移植证据仍用于公共压缩采用与合同变化。

### 4.2 Provider 支持与价格

- **OpenAI Responses，GPT-5.6 及以后（生产在用）**（官方 prompt caching 指南，2026-11-23 读取）：
  - **寿命设置**：
    - 请求级 `prompt_cache_options.ttl` 可选 `"30m"`（默认）或 `"12h"`，作用于隐式断点和没有自带 ttl 的显式断点。
    - **断点级** `prompt_cache_breakpoint.ttl` 可单独覆盖某一个显式断点。
    - 显式断点可以和隐式断点并存（“add explicit breakpoints without turning off the implicit breakpoint”）。所以“只给前缀设 12h”可行：只在首个 developer 块的断点上写 `"ttl": "12h"`。
  - **计费**：
    - 写入为普通输入的 1.25 倍（30m）或 2.5 倍（12h），读取在 `gpt-6.1-terra` 上为 0.05 倍。
    - 一个断点覆盖它之前的整段前缀；已被有效 12h 条目覆盖的部分仍按读取计费。
    - 把有效的 30m 覆盖升级到 12h，要按 12h 重新写一次。
  - **缓存位置**：
    - 前缀包含工具定义和 developer 消息。
    - 每个请求最多 4 次缓存写入（隐式断点占一个）。
    - 缓存在单台机器上；每分钟超过 15 个请求可能溢出路由到别的机器，路由由负载和前缀开头 token 的哈希决定。
  - 旧模型用的 `prompt_cache_retention` 对这些模型无效。
  - Yuki 现在只在首个 developer 块与少数消息上写 `prompt_cache_breakpoint: {"mode": "explicit"}`（`llm/deepseek_responses.py:153-216`），不发 `prompt_cache_options`，也不设 ttl。
- **Claude Messages**：`cache_control: {"type": "ephemeral", "ttl": "1h"}`，默认 5 分钟。5 分钟写入约 1.25 倍，读取约 0.1 倍。1 小时写入的倍数【假设，2 倍，未本次核对价格页】。
- **Gemini**：隐式缓存没有寿命控制；显式 `cachedContents` 按存储时长另计费【假设，未核】。

### 4.4 稳定前缀测量与结论（2026-11-23 补测）【实证】

窗口：11-20 21:20 至 11-23 16:00 UTC（2.76 天），`chat_agent` 成功调用 3139 次，涉及 8 个会话。只读聚合 `model_invocations`；稳定前缀大小取自 `execution_trace_entries` 中保存的请求体，只计长度，不读正文。

**稳定前缀大小**：

| 部分 | 大小 | 依据 |
| --- | --- | --- |
| 工具定义（27 个） | 约 13.3k token | 不同会话、跨链的首请求反复命中恰好 13,320（另一工具版本为 13,377）；请求总字节减去不含工具的请求体约 32.9 KB |
| 首个 developer 块（SOUL、程序规则、常驻段、经历目录） | 约 9.2k token（11-23 私聊，12,925 字）；11-21 约 7.1k（9,759 字） | 按生产标定的系数估算：ASCII 2.2 字符/token，非 ASCII 0.8 token/字 |
| 合计 S | 约 22.5k token | — |

**稳定前缀被重复写入的次数**：

- 窗口内有 212 次请求没有命中 developer 块，其中 118 次连工具定义也没命中。按同会话距上一请求的间隔分成两类：
  - **间隔 ≥ 30 分钟（缓存寿命到期）**：125 次，重写 developer 块 1.15M token、工具定义 1.12M token。
  - **间隔 < 30 分钟**：87 次，重写 developer 块 0.51M、工具定义 0.45M。这类不是寿命问题，主要是路由到没有缓存的机器，或 developer 块内容变化（常驻段、经历目录在 Dream 后更新）。
- 其中同链长等待唤醒（≥ 60 分钟）63 次，56 次重写了 developer 块。
- 按“同会话每 12 小时写一次”计，12h 方案下窗口内的基础写入为 24 次（日均活跃会话约 2.9 个）。
- `model_invocations.cache_creation_input_tokens` 显示，未命中部分几乎全部按写入计费（写入 13.27M，未命中 13.31M）。

**每天成本**（单位为普通输入 token 当量；同期 Main 输入总成本约 8.36M/天）：

| 做法 | 稳定前缀部分成本/天 | 与现状的差 |
| --- | ---: | ---: |
| A 维持现状（30m） | 2.59M | — |
| B 稳定前缀 12h，路由未命中时工具与 developer 块都按 2.5 倍重写（保守） | 2.51M | 省 0.07M（约 0.9%） |
| B 稳定前缀 12h，工具定义始终被其他 12h 条目覆盖，只重写 developer 块（乐观） | 1.83M | 省 0.76M（约 9%） |

计算口径：

- 现状：未命中的稳定前缀按 1.25 倍计，命中按 0.05 倍计。
- 12h：每会话每 12 小时写一次 S，按 2.5 倍计；间隔 < 30 分钟的 87 次重写在 12h 下仍会发生，改按 2.5 倍计；其余按 0.05 倍读取计。

**结论**：【推荐】**维持现状，不实施**。

- 结论取决于“间隔 < 30 分钟”那 87 次重写的成因。如果主要是路由（工具定义也一起未命中的有 45 万 token，支持这一点），12h 让每次重写更贵，净节省不到 1%。
- 缓存只在单台机器上，长等待后被路由到别的机器时 12h 也命中不了，所以乐观估算还会再打折扣。
- 为不到 1% 的节省新增一项 Profile 配置并进入 Profile revision，不符合删除优先。
- 以后如果长等待占比明显上升，或请求量把路由稳定下来，再按本节口径重算；公式和查询口径不变，不另设阈值。
