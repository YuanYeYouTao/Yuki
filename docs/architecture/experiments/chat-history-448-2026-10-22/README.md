## 完整词元、磁盘、WAL 与内存

合成语料为 10,000 条、4 个交错 Conversation、8 个原作者；正文 96 字符，主要是确定性随机汉字，部分带真实格式的 current ASR。每个目标会话中约四分之三消息属于同一个作者。词元来自真实完整 OpenCC/NFKC/1、2、3-gram 实现，未只保探针词。

| 项目 | 实际结果 |
| --- | ---: |
| 去重 gram 总数 | 3,680,691 |
| 原作者 tag 总数 | 20,000，即每事件两个 |
| 完整命名词元累计输入字节 | 182,821,503 |
| FTS 各 shadow 表所占页字节之和 | 37,486,592，约 35.75 MiB |
| 装载后的整个数据库 | 54,980,608，约 52.43 MiB |
| 显式 checkpoint 前 WAL 文件 | 8,371,872 |
| checkpoint 后 WAL | 0，返回 `(0,0,0)` |

装载约 9.77 秒，其中 gram 准备累计约 2.59 秒。为了构造规模，装载器使用真实 schema/触发器及词元，64 行一批直接 SQL 导入，不经过逐消息身份接纳/receipt 路由；批次含取锁和提交的中位数约 32.92 ms、观测最大 88.27 ms。它不是普通消息 writer 的单次耗时。

随机汉字制造了较多不同词元，不能由这个体积按消息数直接估算真实群聊；重复表情、自然句子、长 ASR、正文长度和并发数都会改变结果。加入后续长文本压力后，本 Python 进程的 `ru_maxrss` 峰值约 210.7 MiB；不含完整 Bot、模型客户端、独立 worker 或其他服务的内存。JSON 同时保存 `/proc/self/status` 的瞬时 VmRSS；两者是不同采样口径。

## 真实仓库与元数据组合

每项六次，以下为带观测计数的中位耗时。计时包含实际异步仓库、作者族解析、SQLite progress callback 和原文精确验证，不等于一个纯 SQL 的时间。

| 同一目标作者/会话中的查询 | 返回事件 | 原文验证行数 | 中位 ms |
| --- | ---: | ---: | ---: |
| 稀有词 | 1 | 1 | 5.18 |
| 不存在的词 | 0 | 0 | 4.36 |
| 常见词，取 20 条 | 20 | 21 | 6.40 |
| 稀有词＋覆盖全部记录的日期范围 | 1 | 1,875 | 252.92 |

原作者 tag 让普通“作者＋文字”继续使用一次 MATCH。日期/媒体路径目前优先元数据，宽日期＋稀有词仍可能线性读取和转换原文；这是真实取舍，不能宣称所有组合都与命中数成正比。

`sql_alternatives` 另外保存了同一原生 SQLite 连接上的两个 SQL 形状。在单次 SQL 中追加 `id IN (SELECT rowid ... MATCH ...)`，宽日期稀有词可把 1,875 次正文验证变成一次；样本约 26.06→0.31 ms，空日期两者都约 0.003 ms。这个对照没有异步仓库/完整 DTO 成本，不能拿它与上表直接相除声称产品提速。

### 为什么没有采用这个 IN 改法

对候选全部是假阳性的完整 N+1 循环进一步反证：查询短语 `ababa`，每条原文都是 `aba x bab`。全部 gram 都有，但精确匹配全部失败，必须真正穷尽范围，不能只测第一条 SQL。

| 规模 | 完整页数，每页候选 21 | 普通元数据游标 ms / 约 VM | 每页重做 FTS IN ms / 约 VM |
| --- | ---: | ---: | ---: |
| 5,000 | 239 | 30.32 / 84,000 | 429.13 / 13,904,000 |
| 20,000 | 953 | 95.27 / 337,000 | 6,702.61 / 219,799,000 |

此反证使用相关列/索引的独立最小表，匹配与词元仍来自产品代码；不是另一份完整领域库验收。另有强制相同作者索引的控制组，仍出现约 21.49→86.46 ms 对 503.90→8,082.89 ms 的差异。重复物化大集合会把完整循环放大，不能凭稀有词首 SQL 的优势替换全部策略。本次保留任务书明示的最坏扫描，不增加候选缓存、阈值、统计门槛或策略协调器。

VM 以 100/1000 条指令回调计数，**不包含 FTS 内部全部 posting/页访问**；小于一个粒度的 SQL 可能计为零。零 VM 不等于没有物理工作，以上数值不是复杂度硬上界。

## 真实 writer：锁外准备与锁内成本

出站/ASR 使用产品 `ScopedEventLedgerUnitOfWork`；入站通过本地 fixture 连接真实 resolver 和 canonical writer，没有网络、模型或平台发送。下表为原方法从调用到返回，以及出站/ASR 从成功取得 `BEGIN IMMEDIATE` 到提交/清理返回的时段。普通长度每项八次，32,768 字符压力每项仅两次，不能把小样本最大值称作延迟上界。

| 正文字数 | 出站整个方法 ms | 出站持锁 ms | 入站整个方法 ms | ASR 整个方法 ms | ASR 持锁 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 48 | 13.20 | 11.40 | 16.71 | 9.50 | 4.02 |
| 512 | 15.01 | 12.10 | 17.81 | 12.20 | 5.38 |
| 4,096 | 40.98 | 25.69 | 42.13 | 31.00 | 13.32 |
| 32,768 | 254.27 | 138.78 | 220.69 | 255.85 | 135.16 |

入站使用既有 deferred `BEGIN`/首 DML 接纳路径，表中没有把整个方法冒充精确持锁时间。首次新建私聊 Conversation 的 512 字符出站另测一次，整个方法 27.39 ms、持锁 23.92 ms，namespace 使用 writer 实际裁定的 ID。

- NFKC/OpenCC/gram 准备在 writer 外的线程执行；探针未观察到在显式 writer 内调用准备函数。正常 48 字符实际 ASR 准备中位约 0.21 ms，32,768 字符约 112.38 ms。空语音入账的准备已分列为 `asr_seed:*`，没有拿其零内容耗时拉低 ASR 数值。
- **namespace 封装仍在 writer 内。** 独立封装对照中，48 字符约 0.034 ms，32,768 字符约 19.43 ms、107,264 个 gram、约 5.44 MB 命名词元。后续 FTS 插入/合并同样占有 writer；不能把“正文转换锁外”写成“全部工作锁外”或“写锁 O(1)”。
- 1 ms asyncio 心跳只在实际方法窗口采样，排除额外的 namespace 对照；32k 压力中的最大额外间隔约 31.74 ms。独立后台线程仅做 prepare、将合成正文生成放到采样窗口外后，32k 四次准备的心跳最大额外间隔约 30.69 ms。线程隔离避免同步 I/O 阻塞，并不消除 Python/GIL、C++ 调用和调度带来的所有延迟。

## 物理取消与再次使用

通过产品 `_history_read` 路径运行有界的二百万步递归只读 SQL，在实际 SQLite progress callback 开始后取消。此次取消到清理约 0.71 ms，随后同一 Database 的 `SELECT 1` 约 1.31 ms；回调 VM 计数从取消时约 1000 到清理后约 2000，未把整项递归继续跑完。

这验证实际 `interrupt`、等待原操作退出和连接/事务清理后的可用性；不是普通搜索耗时，也不证明任意系统负载下的固定取消上限。原文线程匹配的取消另由产品行为测试覆盖，不以这个 SQL 样本代替。

## 后续生产升级前应核对的事实

1. 实际运行镜像的 SQLite/OpenCC 及本次测试包一致，并验证 FTS5 contentless-delete 能力；开发容器成功不替代完整镜像验证。
2. 0144 为修复整数事件 ID 复用，会原子复制 `chat_events` 并恢复其原触发器/索引/约束；离线完整装载还需要新 FTS 和 WAL 的磁盘空间。应基于届时数据库与正文/ASR分布核实际峰值，不能按本样本消息数套固定容量线。
3. 所有业务 writer 停止到 0145 完成。0144 中断只重建这个派生阶段，不能以部分索引或手工 stamp 冒充完成；不启动第二个 Bot 共写数据库。
4. 长文本命名封装与 FTS 合并的实际持锁、RSS、后台 CPU 和事件循环压力仍须按真实负载观察。保留真实成本，不为掩盖它增加长度帽、候选预算或“超时当空集”。
5. 升级保原事件、原回执与现存可证水位；过去已经丢失的原 ID/Conversation 不猜测回填。逻辑删除不等于 SQLite/WAL 字节已完成取证级擦除。

本目录没有执行生产迁移、替换容器、发送消息或发布操作。

## 实际数据库的迁移 DDL 保真终审

`migration_schema_probe.py` 只以 `mode=ro`、`query_only=ON` 读取线上 0143 与另行升级完成的隔离快照 0145 的 schema 元数据，每库使用独立读快照。它不读取聊天、账号、配置或凭据行，不执行迁移；`migration_schema_results.json` 记录此次比较结果。主机 Python 的元数据读取器使用 SQLite 3.45.1，不能把它误报为执行升级的容器 SQLite 版本。

- 两库各有 565 个 schema 对象，554 个共同对象的类型、名称、所属表和 SQL 逐字节一致。退出的八个对象仅为旧 FTS 表、四个影子表与三个维护触发器；新增的八个对象仅为新 FTS 表、四个影子表、一个删除触发器和两个普通索引。
- 共同对象中只有三个表的 SQL 有差异：`chat_events` 改用原生 `AUTOINCREMENT`，反射调整了约束排列并将三个空字符串默认值写为 `('')`；另两表仅追加任务书要求的原发送锚与检索来源列。去除这项默认值的括号后，原 ChatEvent 列元数据一致，七个命名 CHECK 的内容一致。
- 全部共同表的外键语义一致，全部共同索引的 `index_xinfo` 一致。ChatEvent 原十五个索引全部保留，原来没有表达式索引；十三个原触发器仅退出三个旧 FTS 触发器，其他十条原 SQL 完整保留。
- 递归反射曾警告的 `runtime_work` JSON 表达式索引、`canonical_conversations` 两个 `coalesce` 唯一索引均逐字节保留。这些关联表没有被 batch 重建。`uq_memory_facts_active_canonical_self_key` 在两个库中都不存在，不能归为本次迁移丢失。

本次只读比较没有发现未计划的 DDL、外键、索引或触发器变更，不增加启动检查或兼容机制。数据完整性与行级保真由隔离升级演练另行核验，本探针的结果不替代它们。
