## 1. 要解决什么，不解决什么

### 1.1 现象【实证】

- 所有者的工作规则都已存进记忆，但主动查记忆的轮次只有 1.4%（35/2582，#681），规则在工作时没有出现在提示词里。#678 的写审循环到第 7 版才停，违反 fact 3975。
- 每轮提示词里的记忆依据规则第一句是"当前请求不自动附带长期记忆"（`memory/context.py:17-18`），没有任何东西承担"少量稳定内容常驻"这一层。
- PR #683 评估集 21 例中，有 8 例的事前依据是一条按可见范围本可以放在眼前的记忆（架构书 §7.2）。

### 1.2 P1 做

每一轮主 Agent 请求的当前消息里，多出一段**常驻记忆**，内容是确定性渲染的少量 active 事实：

1. 会话对象本人的明确事实（所有者的工作规则就是所有者的明确事实）。
2. 每个人物、每个群由 Dream 批次后的挑选步骤维护的核心集，最多 10 条。
3. 所有者确认的 SELF 原则。
4. 群聊里，发言人与被原生 @ 的人可在本群出现的那部分。

### 1.3 P1 不做

- 不做经历目录与标题（P2）。
- 不改提取提示（P3）。新提取的一次性指令仍会进按需层，但不会因此进常驻层。
- 不放进 system 消息，不新增缓存断点或稳定档。
- 不改 Dream 的聚类、分区、簇上限、调度时间和现有 6 种操作。
- 不改 `search_memory`、`save_memory`、`edit_memory` 的声明与行为；固定工具清单的修订号不变。
- 不改身份、授权、按需读取的可见范围（`docs/architecture/memory-v2.md:84` 不动）。
- 子 Agent 与插件轮不带常驻段。
- 不引入通用策略引擎、可插拔排序器或通用缓存层。

## 4. 数据模型与迁移

### 4.1 新表 `memory_resident_sets`（schema `0162`）

一行一个主人。明确事实不入表。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | |
| `owner_kind` | TEXT NOT NULL | `person` / `space` / `self` |
| `owner_person_id` | TEXT NULL，FK `persons.id` ON DELETE CASCADE | `owner_kind='person'` 时必填，存人物根 ID |
| `owner_space_id` | TEXT NULL，FK `spaces.id` ON DELETE CASCADE | `owner_kind='space'` 时必填 |
| `fact_ids_json` | TEXT NOT NULL DEFAULT `'[]'` | 有序的 fact ID 数组，最多 10 个 |
| `source` | TEXT NOT NULL | `dream`（挑选步骤写）/ `owner`（所有者 CLI 写，挑选步骤跳过） |
| `considered_through_fact_id` | INTEGER NOT NULL DEFAULT 0 | 挑选步骤已看过的最大候选 fact ID |
| `revision` | INTEGER NOT NULL DEFAULT 0 | 列表内容每变一次加 1 |
| `selected_at` | DATETIME NULL | 最近一次挑选或所有者改写的时间 |
| `created_at`、`updated_at` | DATETIME NOT NULL | |

约束：
- `ck_memory_resident_sets_owner`：`(owner_kind='person' AND owner_person_id IS NOT NULL AND owner_space_id IS NULL) OR (owner_kind='space' AND owner_space_id IS NOT NULL AND owner_person_id IS NULL) OR (owner_kind='self' AND owner_person_id IS NULL AND owner_space_id IS NULL)`。
- `ck_memory_resident_sets_source`：`source IN ('dream','owner')`；`owner_kind='self'` 时 `source` 必须是 `owner`。
- 唯一索引 `uq_memory_resident_sets_owner`：`(owner_kind, coalesce(owner_person_id,''), coalesce(owner_space_id,''))`。

表里只有 ID，没有记忆正文。不在 `memory_facts` 上加列，不建第二张表。

为什么一行一个主人、而不是一条事实一行：挑选步骤需要记下"这个主人看到哪了"和"选了空集"。架构书 §7.2 的模拟里有主人两次都选了空集；没有这一行，这些主人每天都会被重选。

### 4.2 迁移

- 文件 `migrations/versions/0162_memory_resident_sets.py`，`revision = "0162"`，`down_revision = "0161"`。按仓库约定写成冻结迁移，不引用可变 ORM。
- `upgrade`：建表、两条 CHECK、唯一索引。不回填任何行。
- `downgrade`：删索引、删表。表是派生数据，删掉不丢事实。

- `docs/architecture/README.md:34` 的迁移 head 改为 `0162`。

### 4.3 回滚

1. 运行时开关 `memory.resident_enabled` 设为 false：下一轮起不再渲染常驻段，挑选步骤不再运行。
2. 需要回退代码时，先回退应用，再执行 `0162` 的 downgrade。旧代码不读这张表，所以也可以保留表不降级。
3. 记忆依据规则的文字随代码回退变回原文，在途 Work 的合同哈希再变一次，按 S4 处理。

### 4.4 与现有生命周期的关系

| 事件 | 处理 |
|---|---|
| 事实失效、被取代、被标争议、被隐私删除 | 渲染时过滤（§5.3）；表不用同步改 |

## 5. 渲染器

### 5.1 位置与接口

新模块 `memory/resident.py`：

```python
@dataclass(frozen=True, slots=True)
class ResidentAudience:
    kind: Literal["private", "group"]
    person_id: str | None          # 私聊对象的人物根 ID
    space_id: str | None           # 群的 space ID
    speaker_person_id: str | None  # 群聊里当前消息的作者；没有消息的轮次为 None
    mentioned_person_ids: tuple[str, ...]  # 当前消息里被原生 @ 的人物根 ID

@dataclass(frozen=True, slots=True)
class ResidentRender:
    text: str                      # 空串表示这一轮没有常驻段
    fact_ids: tuple[int, ...]      # 实际渲染出的 fact ID，按出现顺序
    omitted_explicit: int          # 因上限没有渲染的明确事实条数

class ResidentMemory:
    async def render(self, audience: ResidentAudience) -> ResidentRender: ...
```

`ResidentAudience` 由 `ContextAssembler.assemble` 从会话行得出：按 `ConversationScope.conversation_id` 读 `canonical_conversations` 的 `kind`、`person_id`、`space_id`；发言人取当前入站事件的 `author_person_id`；被 @ 的人取当前消息里原生提及解析出的人物。它只取决于会话与当前消息，不取决于入口类型或平台。

渲染只用一个只读会话，不发起模型调用，不写库。

### 5.2 输出格式

```
常驻记忆（少量稳定条目；其余记忆用 search_memory 查，可按 fact 编号读取。条目之间冲突时以编号大的为准，并告诉所有者）
[对方明确要求记住的]
- <正文>（fact:3975）
[关于对方]
- <正文>（fact:1597）
[我自己的原则]
- <正文>（fact:3920）
```

群聊：

```
常驻记忆（……同上……）
[本群]
- <正文>（fact:2127）
[我自己的原则]
- …
[这条消息的发言人]
- …
[被 @ 的人：<与消息正文里相同的提及标签>]
- …
```

- 每行是事实的 `content`，把连续空白折成一个空格、去首尾空白，后接全角括号里的 `fact:<id>`。不截断、不改写、不合并。
- 没有条目的小节整节不输出；所有小节都空时 `text` 为空串，不输出标题行。
- 明确事实超过上限时，在该小节末尾加一行"（另有 N 条明确记忆未常驻，可用 search_memory 查）"。

### 5.3 过滤规则（确定性）

**所有条目共同的条件**
- `status='active'`、`conflict_state='clear'`、`review_state!='quarantined'`、`valid_until` 为空或未到。
- `kind` 是 fact 或 preference。
- 人物事实的 `authority` 是 explicit 或 self_report；群事实只在本群。
- 主人人物 `enabled=1`。
- 核心集列表里的事实，其主人必须就是这一行的主人（人物行只收该人物的 person / person_group 事实，群行只收该群的群事实，SELF 行只收 SELF 事实）。

**按会话**

| 小节 | 候选 | 额外条件 |
|---|---|---|
| 私聊 · 对方明确要求记住的 | 主人是对方的 person / person_group 事实，`source_type='explicit'` 或 `authority='explicit'` | 没有任何证据来自别人的私聊 |
| 私聊 · 关于对方 | 对方那一行的 `fact_ids_json` | 同上；没有证据行的事实允许（架构书 Q14） |
| 群 · 本群 | 本群那一行的 `fact_ids_json` | "本群证据条件" |
| 群 · 发言人、被 @ 的人 | 该人物的明确事实，接着是该人物那一行的 `fact_ids_json` | "本群证据条件"；person_group 事实还要求属于本群；该人物是本群现有成员 |
| 我自己的原则 | `owner_kind='self'` 那一行的 `fact_ids_json` | `visibility_type='global'`，或 private 且可见人物是私聊对象，或 group 且可见群是本群；群聊里再加"本群证据条件" |

**本群证据条件**：该事实至少有一条证据；每一条证据的 `event_id` 都不为空，且事件所在会话的 `space_id` 等于本群。任何一条不满足就排除。

**被取代的条目**：列表里的 ID 不再 active 时，先找后继：`memory_facts.supersedes_id` 指向它的 active 事实；找不到再经 `memory_dream_operation_sources` → `memory_dream_operations.output_fact_id`（已提交、未回滚）。沿链走到 active 的那一条，再对它套用本节全部条件。找不到后继就跳过。渲染出的永远是当前 active 的 ID。

**去重**：同一个 fact ID 在一段里只出现一次，先出现的小节保留。

### 5.4 排序（确定性）

- 小节顺序固定，如 §5.2 所示。群聊里"发言人"和"被 @ 的人"永远在最后，发言人变化不影响前面的小节（用例 11）。
- 明确事实按 fact ID 升序。
- 核心集与 SELF 原则按 `fact_ids_json` 的数组顺序。
- 被 @ 的人按人物根 ID 升序。
- 渲染结果只取决于数据库里这些行的内容，不取决于查询返回顺序、插入顺序、进程或时间（用例 7、27）。

### 5.5 上限

| 项 | 上限 | 超出时 |
|---|---|---|
| 核心集每个主人 | 10 条 | 写入时拒绝（挑选步骤与 CLI 都校验） |
| SELF 原则 | 10 条 | 同上 |
| 明确事实 | 30 条 | 按 ID 升序取前 30，末尾加一行说明；`omitted_explicit` 计数 |
| 群聊里每个发言人或被 @ 的人 | 5 条 | 按 §5.4 的顺序取前 5 |
| 被 @ 的人 | 3 个 | 按人物根 ID 升序取前 3 |

这些是提示词篇幅的预算，不是记忆的准入门槛：超出的事实仍在按需层。按架构书 §7.7，所有者私聊在这些上限内约 2300 字。

### 5.6 渲染失败

`ContextAssembler.assemble` 调用渲染器时，渲染器抛出的异常在这一处接住：这一轮 `resident_text` 为空串，其余照常，记一条 `memory_resident_render_failed` 日志并计数。只在这一处处理，渲染器内部不做兜底。

system 消息、会话历史、compact 检查点都不变。

### 6.2 与缓存断点的关系

- 新增断点 0 个。Claude 方言的 3 个断点、Responses 方言的前导断点与历史断点都不动（E6）。
- 常驻段位于现有所有缓存前缀之后。它每轮首次请求不命中缓存；同一轮后续请求里，它随当前消息一起进入会话前缀并命中。
- 架构书 §7.7 的估算：所有者私聊每轮等价未命中 token 约 +4.7%，主群约 +7.5%；缓存命中率的变化在 ±1 个百分点内。实测阈值见 §11。

### 6.3 与恢复哈希的关系

- `memory.resident` 不加入 `invariant_contributions()`（`services/prompt_composer.py:65-79`），所以 `work_contract` 的哈希不含它（S4）。常驻内容变化、开关切换都不改变哈希（用例 18）。
- 当前消息连同常驻段在一个 Work 的首次请求时进入 transcript。同一个 Work 的后续请求与续接沿用原 transcript，Work 期间常驻段不变（用例 17）。【假设：续接还原 transcript 的细节没有逐行追到底，由用例 17 确认】
- 记忆依据规则的文字要改（§9），它在哈希范围内。部署当次所有在途 Work 的哈希变一次：换新链继续，带上任务材料，未决调用按原回执审计（`runtime/work_session.py:160-213`）。例外只发生在没有当前 Work 的执行读到自己的公共压缩回执时（`services/turn_execution.py:402-425`）：回执处于已派发阶段，无论合同变没变都抛 `context_compaction_outcome_unknown`；回执存在、不在已派发阶段而合同已变，抛 `context_compaction_contract_changed`。只有后一种与本次改字有关。上线步骤据此安排（§12.1 第 2 步）。

### 6.4 与 compact 切片的关系

- 公共压缩的输入是 `composition.messages[:-1]`（S5），常驻段在最后一条消息里，不会被压进检查点（用例 23）。
- `static_count` 仍是 1，因为没有新增 system 消息。
- Work 内的公共压缩保留 `messages[public_count:]`，执行压缩的边界不早于初始消息之后（S5），所以长 Work 压缩之后常驻段仍逐字在场。
- 压缩之后的下一轮照常重新渲染，只出现一次。

### 7.2 挑选步骤

新模块 `memory/resident_selection.py`，由 Dream worker 调用。

**接入点**。`memory/dream/worker.py:178-181`：`claim_next_cluster` 返回空、调用 `finalize_run` 之前，调用一次 `ResidentSelection.run(run)`。开关 `memory.resident_enabled` 为 false 时 Dream worker 不调用它。开关只管两件事：每轮是否渲染常驻段、Dream 批次后是否自动挑选。CLI 的 `select`、`set`、`render`、`check` 不看开关，开关关闭时照常可用（上线第 5、6 步依赖这一点）。簇的规划、处理、预算与收尾都不改。挑选步骤抛出的异常记日志后照常收尾，不影响这次 Dream 运行的状态。

**哪些主人到期**（确定性）
- 人物或群有符合候选条件的事实，其 ID 大于该主人那一行的 `considered_through_fact_id`（没有行时视为 0）；或
- 该主人现有列表里有条目不再满足 §5.3 的共同条件且找不到后继。
- `source='owner'` 的行跳过。SELF 不参加挑选。
- 挑选与渲染都不看 `spaces.enabled`：它们只取决于事实和会话身份。已停用的群在生产里不会再有轮次，所以不会被渲染；但它仍可以被挑选，也可以用 `render --conversation` 离线渲染。人物的 `enabled` 仍按 §5.3 处理。

到期的主人按 `considered_through_fact_id` 升序、再按主人 ID 升序排队，本次运行最多处理 `memory_resident_max_selections_per_run` 个（新配置，默认 12）。没处理到的留到下一次运行。架构书 §7.3：两周内每天到期的主人最多 9 个。

**候选条件**：§5.3 的共同条件，且不是明确事实（明确事实已经常驻）。

**一次调用的输入**
- 该主人现有列表里仍有效的条目（别名 `kept_N`，带正文）。
- 该主人的明确事实（别名 `pinned_N`，带正文；只作参考，不可选）。
- 新候选：ID 大于 `considered_through_fact_id` 的候选，按 ID 升序（别名 `new_N`，带正文）。总字数超过现有 `memory_dream_max_input_characters` 时只取前面放得下的部分，其余留到下次。
- 模型用途沿用 `ModelTask.MEMORY_DREAM`，结构化输出，只允许引用别名，不输出数据库 ID。

**指令要点**
- 输出一份有序列表，最多 10 条，只能来自 `kept_N` 与 `new_N`。
- 没有明确理由就保持现有列表不变。新候选只有在比现有条目更稳定、更重要，或与现有条目同义且更完整时才换入。
- 选：身份与关系、称呼、长期稳定的喜恶与边界、长期目标或长期状况、长期有效的互动方式要求。
- 不选：一次性任务指令、当次事件、时效性强的状态、琐碎细节、玩笑、与 `pinned_N` 同义的条目。
- 不选健康、性、财务类内容（架构书 Q15）。
- 可以少于 10 条，可以为空。

**提交**（一个短写事务，事务内不等待模型）
- 程序校验：每个别名都在本次输入里；条数不超过 10；每条在提交时仍满足候选条件（含主人一致）。任一条不满足，整次结果作废，该主人这一轮不变，留到下次。
- 列表与原来不同：写 `fact_ids_json`，`revision` 加 1，更新 `selected_at`。
- 无论列表是否变化，把 `considered_through_fact_id` 推进到本次输入里最大的候选 ID。
- 挑选步骤不改任何事实，不产生 Dream 操作行，也不参与 Dream 的回滚。

**可观测**。`DreamHealth`（`memory/dream/models.py:252` 起）新增两个字段：`resident_pending_owners`（到期但未处理的主人数）与 `resident_oldest_pending_at`（其中最早一条未看候选的创建时间）。CLI `status` 输出同样内容。挑选步骤长期不运行或一直轮不到时，这两个值会持续增长（用例 21）。

## 12. 上线与回滚

### 12.1 上线步骤

1. **所有者决定**架构书 §8.2 的各项，确认附录 A 的文字。
2. **合并与部署**（需所有者明确授权）。部署会让在途 Work 的合同哈希变一次（§6.3）。部署前确认没有执行持有未收尾的公共压缩回执，只读查法：

   ```sql
   select source_key, json_extract(payload_json,'$.phase') as phase, created_at
   from model_context_observations
   where source_key like 'compact:%' and created_at >= datetime('now','-1 day')
   order by created_at desc;
   ```

   `source_key` 形如 `compact:<执行 ID>:…`（`services/context_compaction.py:172-181`）。按执行 ID 看最新一行：阶段是 `dispatched` 的，重启后无论合同变没变都会报结果未知，这是现有行为；阶段不是 `dispatched`、且该执行还没结束的，部署后会报合同已变。有这样的执行就等它结束再部署。【假设：阶段取值只核对了源码里出现的 `dispatched`、`paired`、`invalidated`，"执行是否已结束"要对照执行记录判断，实施时把查法补完整】迁移 `0162` 随 `yuki init-db` 执行。此时 `memory.resident_enabled=false`，渲染与挑选都不发生；记忆依据规则的新文字已经生效，它在常驻段为空时同样成立。

## 14. 假设与未核实之处

- 生产 Dream 模型（`deepseek-flash`）按 §7.2 的指令挑选的质量没有测过；研究里的模拟用的是 Claude。应对：§12.1 第 5 步的预览。
- 增量挑选（以现有列表为基础）的稳定性没有模拟；研究只测了从头挑选两次的重合度（中位数 0.80）。应对：§11.4 的变动指标。
- "规则在眼前就会被遵守"没有证据。应对：§11.3。
- token 数按字数估算，缓存价格比按 10% 估。应对：§11.4 实测。
- 遗忘是否物理删除 `persons` 行、群成员关系在退群时如何变化，都只读到了入口，没有追到底。用例 9、25、29 会暴露不一致。
- 被 @ 的人：入站消息已有 `mentioned_person_ids`（`domain/tool_actor.py:28`、`memory/targets.py:58`，第 1 轮审查指出），`ResidentAudience.mentioned_person_ids` 直接取它。第 1 轮把这写成未追到底的假设，现已消掉；它给出的是否已是人物根 ID，实施时确认。
- "明确事实"的范围比字面宽（S6）。小节标题"[对方明确要求记住的]"在主 Agent 自发保存的条目上不准确；是否改标题取决于架构书 Q17。
- 插件轮的装配路径只读到 `assemble_plugin`，P1 不带常驻段，所以不依赖它的细节。
- Anthropic 单请求 4 个断点的上限没有实测；P1 不新增断点，不依赖它。
- 评估集的行为重放是否可行取决于 trace 保留期；不足时按 §11.3 记为无结论。
