## 3. 已核实的缺口

### 3.1 默认段截断

- 默认值 `agent_max_tool_calls=32`、`agent_max_model_requests=24`：`config.py:262-263`、`settings_domains.py:116-117`、`admin/config_specs_hot.py:284-310`、`admin/config_service.py:1616-1618`、`admin/models.py:220-224`、`.env.example:220-222`；生产 compose 显式设置 `AGENT_MAX_*=24/32`，数据库无覆盖行。
- 无 Work 时的截断来自循环上界：`turn_execution.py:367` 传入 `agent_core/loop.py:68-69`，耗尽后进入 `exhausted()`（`turn_execution.py:1683-1703`）抛 `agent_segment_budget_exhausted`。`begin()` 中 `:565-571` 的 STOP 只对有 Work 的激活生效。普通聊天失败不向平台插入报错（`main-agent-runtime.md:656-657`），表现为静默。
- `runtime/work_control.py:173` 的 `segment_model_limit=24` 会在 `agent_runner.py:342` 被配置覆盖，只在 `:338-339` 预留准备阶段请求时使用默认值；`SegmentBudgetReached`（`work_control.py:558-561`）限制 HTTP 重试、原生搜索和嵌套插件会话请求。
- #560：24/32 来自 2026-09-13 的经验调值，无基准。

### 3.2 私聊插话作废正在执行的轮次

- 每条直接消息都推进会话版本（`services/turn_coordinator.py:139`）；`preempt_private`（`processor.py:805-811`、`turn_coordinator.py:100-117`）只额外取消尚未 `effect_started` 的任务。
- 终止已开始执行的轮次的是版本校验：每次工具调用前 `before_model_request`（`services/main_agent_backend.py:255-256`）进入 `chat.py:1274-1275`；效果闸门 `chat.py:1299-1327` 同样检查。无 Work 时要求版本一致；有 Work 时豁免（`chat.py:1301-1302`）。生产 trace：#135131、#135132、#135141 三轮的最后一次 `terminal_exec` 都返回 `TurnSupersededError, mutation_committed=false`。
- 现行合同 `main-agent-runtime.md:499-511` 写明普通私聊新输入可抢占旧轮，这是现行行为。
- 有 Work 时，`processor.py:797-802` 的 `preserve_active` 不推进版本，新消息进入 Work 输入：同批有副作用的工具返回 `new_input_before_execution`（`main_agent_backend.py:263-289`、`invocation_service.py:152-153`），收尾回复遇新输入时重做（`turn_execution.py:1456-1468`）。

### 3.3 直接私聊不走“普通补充”；抢不到会话的一方被静默丢弃

- 无 Work 时的补充入口是 `begin()` 的 `observation_boundary`（`turn_execution.py:540-563` → `main_agent_turns.py:285-349` → `commit_to_activation` `:442-455`），只采纳带 `ordinary_reason` 的观察事件（`processor.py:1172-1178`），这类事件只在非直接对话分支登记（`:971`、`:580`）。直接私聊在 `_prepare_foreground` 中先提交自己的 admission（`:1612`），再排队等会话锁（`chat.py:714-718`），自成一个 Main。只删除版本校验，旧轮会看到新消息但不拥有它，结束后新消息再跑一遍。
- 自动化不会与用户 Main 并行：自动化取得会话的 Work 作用域租约（`automation/worker.py:218`）并绑定激活（`:284`），普通 Main 在 `chat.py:850-851` 争同一租约。**抢不到的一方报 `conversation_activation_busy`，在 `processor.py:1677` 被当作 `turn_interrupted`，消息静默丢弃。** 近 30 天生产 65 条（64 群聊、1 私聊）；那条私聊发生在 11-02 16:02:49，正落在自动化 run 220 运行期间（16:02:11–16:02:57），而 run 220 自己也因 TurnSuperseded 终止，两边都丢。近 30 天 5 条 uncertain 自动化运行中有 4 条（196/220/223/225）为 TurnSuperseded。

### 3.4 普通轮的工具记录不进入后续上下文

- 生产请求核对：轮次 3 首个请求中前两轮的设备 ID、base64、命令出现 0 次；轮次 4 首个请求中，正常结束的轮次 3 的 8 次工具同样 0 次；自动化 162 首个请求没有任何工具消息。
- `runtime_context` 在**没有活动 Work** 时附 `recent_work` 与 `available_work`（`runtime/work_control.py:1122-1133`），有活动 Work 时只给 work_id 与 goal（`:1118-1120`）。事故中为空，是因为这些轮次根本没有 Work。
- journal、effects、protocol refs 的 `work_id` 都是指向 `runtime_work.id` 的外键（`work_schema_v1.py:98,112`、`protocol_schema.py:21`）；`WorkJournal`、`WorkLease`、WorkScheduler 都以 Work 为 owner。无 Work 的执行没有可恢复的执行记录，只有终端与 Social 的领域回执。

### 3.5 自动化计量与到期指令

- 只有正常返回时写 `llm_calls=result.model_requests`（`automation/worker.py:319-323`）；异常路径由 `settle_interrupted_occurrences` 以插入时的初值 0 结算（`automation/repository.py:721,777`）。`failed_model_requests` 只写不读（`main_agent_backend.py:116-118`），而且异常路径拿不到 backend 上的值。所有 uncertain 运行都记 0。
- 到期指令“继续完成这次发生尚未完成的工作”与 compact 检查点中的“待决操作”一起，使提醒类自动化接手了会话里未完成的传文件请求（推断）。接手本身不是问题，问题是它不知道前几轮已经做过什么（见 3.4）。

## 4. 目标

已获准的私聊多步执行能持续完成；用户中途补充进入同一执行；下一次激活知道上一次实际做过什么；同一会话抢不到执行的一方排队而不是被丢弃；自动化只做自己的目标，计量与实际一致。不新增 TaskEngine、关键词式复杂度判断或第二套状态账。

## 5. 方案

### 5.1 私聊多步执行由 Host 自动接纳 Work（路线 A）

**接纳时机。** 无活动 Work 的私聊直接对话，在模型响应返回后、执行其工具批次之前（`agent_runner._execute_tool_batch` 中 save_response 与直接调用之前，含 `execute_code`），若批次含 `send` 以外的任何工具调用，Host：

1. 先以 `validate_turn_snapshot` 核对版本；版本已失效则按现行抢占处理，不接纳。
2. 版本有效时，以预生成的 Work ID，在同一 writer 事务中提交 accept、接纳前已付的模型计量与首份 `phase=response` journal（经 `WorkJournal.save` 的 publication）。
3. 然后才绑定调用身份并执行整批。

goal 记原触发事件引用，不复制用户正文（避免在账本之外多一份需隐私清退的副本）；模型可用 update 改写。纯 `send` 或无工具的轮次不接纳。

**为什么不能在 `invocation_service.py:150` 接纳**（初稿位置）：同批调用的身份在接纳前已绑定临时 owner（`invocation.py:134-138`），接纳后的调用在 `invocation_service.py:122-124` 抛 `invocation_owner_conflict`，触发接纳的调用也带着错误 owner 落入 effect，恢复时 `work_session.py:961` 判为损坏；response 的保存（`agent_runner.py:1018-1019`）发生在接纳前，`_save` 无 Work 时直接返回（`work_session.py:1028`），接纳后的 T1/T2 没有对应 response；首份 journal 要等整批执行完才写，窄窗口被拉长为整批执行时长；并行批次会被分成接纳前后两部分。模型自己调用 accept 时，`agent_runner.py:801-846` 把控制调用当作屏障拆分批次并重新绑定身份、重新保存 response，Host 自动接纳必须达到同样效果。现有 Host 预接纳先例（`subagent_repository.py:82`、`notification_repository.py:1713`、`semantic_participation.py:1464`）都在激活开始前，不是中途。

**接纳后的行为与边界：**

- 插话：版本豁免（`chat.py:1301-1302`），新消息经 `preserve_active` 进入 Work 输入，副作用工具在新输入后拒执行，收尾遇新输入重做。
- 结算不新增门槛：模型给出最终文字时 `turn_execution.py:1477-1480` 自动 `complete_final`；未作决定即退出时 `work_supervisor.py:214-250` 记为 suspended 或 waiting_external。**策略扩大须写入合同**：可重试失败转 RETRY，按 2/10/30 秒自动重排；私聊原来失败即静默，现在会在后台重试。
- 空档期：Work 处于 queued、waiting_external 或 suspended 时没有活动激活（`chat.py:574-576`），新消息只匹配同一触发事件的 Work（`work_activation.py:36-37`），会另起 Main。“插话进入同一执行”只在激活期间成立。
- 重启恢复走原 journal：只有 dispatched 时报 `work_response_not_persisted`，不重购请求；未知发送不重发。`/ai stop` 在 `command_service.py:184` 取消 Work。
- 提示词：`task_control` 说明（`work_control.py:54-60`）仍让模型对持续目标调用 accept；自动接纳后再 accept 会得到 `work_already_active_use_update`（`:1068-1069`），有新输入时会另排独立 Work。说明必须同步改为“已在工作中时用 update”。
- 依赖 `RUNTIME_WORK_ENABLED`；关闭时路线 A 不生效，须写明。
- 群聊不受影响。待核实（推测）：`stage_work_input` 只按 Person 匹配（`chat.py:612-633`），若自动化在私聊里已成为 Work，用户私聊消息可能并入提醒任务；会话中有 SELF Work 时，`preserve_active` 不推进版本但消息不属于 SELF，可能既不进入 Work 也拿不到租约。
- 规模：近 30 天 435 个私聊轮次中 194 个用到 `send` 以外的工具（约 45%）；journal 平均约 22 KB。
- 须改写 `development-contract.md` §2“普通聊天不强制登记 Work”：仍不要求模型 accept，但 Host 为私聊多步执行登记。

**不采用路线 B**（journal 改为以执行 ID 为 owner）：需迁移 3–4 张表外键、双 owner 与新的执行恢复调度，等于第二套状态账。

### 5.2 删除段机制

删除 `agent_max_model_requests` / `agent_max_tool_calls` 及其配置、热配置、校验、env 示例与生产 compose 中的显式设置。

**更彻底的做法（推荐）**：插件显式上限现在实际是“每段大小”（恢复时每段重新取最小值，`plugin_host/facades.py:1568-1583`、`main_turn.py:718-723`），并非总量。把它写入根 Work 预算的 `model_limit` / `tool_limit`——这两列已有执行处（`runtime/work_budget.py:36-43`），生产 1297 行全为空，正好给 D2 一个真实的写入方。之后整套删除分段机制：`segment_model_limit`、`SegmentBudgetReached`、`begin()` 的 handoff 提示（`turn_execution.py:573-604`）与 `segment_handoff_index`、`exhausted()` 的 queued 分支、`coordinator.py:186-200` 的 `tool_limit_exceeded`。所有返回 STOP 的位置（`turn_execution.py:532,571,584,1020,1030`）都依赖这两个上限，删除后不存在“仍保留的分段来源”。Code Mode 侧（`agent_runner.py:697-708` 断言 `tool_limit`、`codemode/driver.py:647-648` 遇 None 会 TypeError、CodeHost 的让出）本期不改其设计（#573），只保证上限为 None 时不出错。

完整改动清单：

- 运行时：`chat.py:1284-1285`、`agent_runner.py:324-342`、`work_control.py:173,558-561`、`turn_execution.py:367,526-606,1015-1030,1508-1520,1683-1703`、`invocation_context.py:21-39`、`session_facade.py:65`、子任务 `subagent_execution.py:368-369`。
- 插件与 SDK：`plugin_host/facades.py:1568-1583,2436-2437`、`main_turn.py:388-389,551-556,718-723`、`plugin_sessions.py:188-191`、`yuki_plugin_sdk/context.py:136-143`（Protocol 签名）、`sessions.py:43`、`sdk/testing/fake_services.py:316-324`；插件文档 `facades.md:95`、`results.md:68`、`service-facades.md:94,110`、`api-7.0-migration.md:13`。
- 旧 Work 来源中持久保存的 `max_*` 字段在恢复时仍被读取（`main_turn.py:718-723`），须按原事实只读兼容。
- 若删除根预算列（D2 选择删除时）：`schema_guard.py:121,357` 与迁移。
- 测试：34 个测试文件引用这两个名字，按 grep 全量核对。

### 5.3 自动化

- 互斥已由租约保证，不新增机制。要改的是抢输方被丢弃：自动化与 Work 恢复进入已有的 `_concurrency.conversation(key)` 会话锁，用户 Main 排队等待而不是报 busy 后丢弃；自动化不再受用户输入版本栅栏约束，只受 generation 约束。
- 到期指令（`execution_sources.py:175`）不改，不限制自动化可以做什么。自动化 162 接手的是用户本人未完成的请求；它删掉正确文件，根因是激活看不到前几轮的真实工具事实，由 5.4 解决。
- 计量：把已发生的模型请求数挂在异常上带出，在异常路径结算时写入 `llm_calls`；这是一处新增连线，不新增状态。
- 重复创建相同提醒属于模型行为，本期不加门槛；5.4 落地后复查。

### 5.4 上一次执行的事实进入下一次激活

effect 中没有调用参数原文，只有 `arguments_digest`（`capabilities/invocation.py:85`），因此不提供“关键参数摘要”。工具结果正文与步骤已可通过 `task_control get` 读取（`work_queries.py:176-205`）。先用 E2E 验证“`recent_work` 给出 work_id，模型再 get”是否足够；不够时再在 `recent_work` 内联已有字段：tool、ok / pending / uncertain、status、run_id、error_code、artifacts / delivered。执行诊断 trace 是可丢资料，不作为来源。

### 5.5 参照 SuInk/Diana

对照 `SuInk/Diana@71db9cb0`（只读源码，未运行）：主回复默认不限步数（`model/agent/types.go:15-16`）；补充在每步规划前接入同一轮，已有工具结果保留，正在进行的模型请求不打断，收尾步遇补充则重做（`model/agent/interjection.go:8-21`）；已对外发言或产生副作用后不再整轮重来；下一轮接在上一轮实际请求之后，工具调用与结果成对保留。语义与本文方案一致。不照搬：Diana 的续接与进度只在内存中，依赖 10 分钟、2 分钟等经验窗口；时间耗尽时额外购买一次强制收尾请求，与 Yuki“模型请求失败不另外购买一次请求来解释错误”冲突。

## 6. 作者决定（2026-11-07）

- **D1：采用路线 A**——Host 在工具批次执行前自动接纳私聊多步执行（5.1）。
- **D2：插件显式上限迁入根 Work 预算**的 `model_limit` / `tool_limit`，并整套删除分段机制（5.2）。

## 8. 验证

以 E2E 为主：隔离 SQLite、假 Provider、假设备，重放本次事故形态。产物为 JSON：请求序列、admission 归属、Work 与 journal、工具回执、送达事件、自动化计量。

隔离验证先列可能失败的情况：

**C02 接纳**：接纳事务提交后、执行首个工具前崩溃；首个工具 T1/T2/T3 各阶段崩溃；并行批次全部归属同一 Work；含 `execute_code` 的批次；插话在版本核对与接纳提交之间到达；接纳后再调用 accept；`RUNTIME_WORK_ENABLED=false`。

**C04 插话**：新消息到达时旧轮正在等待模型 / 正在执行副作用工具 / 同批还有未执行的副作用调用 / 落在收尾请求期间；连续两条消息；第二条带媒体或需 ASR；`/ai stop` 插在中途；`/ai new` 后旧轮仍尝试产生效果；App 入口；群聊直接 @ 不受影响；消息只被采纳一次、不另开 Main；Work 处于 waiting / suspended 空档期时的插话；隐私删除与插话并发。

**C03 段机制**：超过 24 次请求或 32 次工具后仍能完成；插件显式上限经根预算仍生效；辅助请求不再受写死的 24 限制；重启后不重复购买模型请求、不重复发送；旧 Work 来源中的 `max_*` 只读兼容。

**C05 自动化**：用户消息在自动化运行期间到达时排队而非丢弃；异常路径 `llm_calls` 等于实际次数；到期执行能看到会话前几轮的真实工具事实，不重复已完成的操作；自动化 Work 续段仍能继续自己的发生。

**C06**：执行结束后用户追问“刚才做了什么”，模型能从 `recent_work` 与 `task_control get` 得到真实工具事实。
