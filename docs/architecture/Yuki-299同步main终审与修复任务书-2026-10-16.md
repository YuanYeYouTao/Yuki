### 2.1 会话隔离与工具讨论的范围

当前私聊按 `IdentityBinding` 建立独立 Conversation：同一 Person 的 QQ 账号 A、B 不共用历史、generation 或模型 session；QQ 和 App 也不共用。App 多台设备共用该 Person 的一个 App 绑定与主会话，设备不是另一个会话入口。旧迁移保留既有历史的原归属，不把新入口导回旧 transport alias。群聊继续按真实 Space 保存原公共会话，这与把同一 Person 的多个私聊入口合并不是一件事。

“一个入口一个 session”是隔离关系，不是一个入口永远只有一条物理模型链。当前模型标识包含 `Conversation + generation + main/Work 分支`，形如 `yuki:<conversation>:g<generation>:main` 或 `…:work:<work_id>`。独立插件 `agent_sessions` 另有自己的 UUID；共享 HTTP 连接池每次请求设置真实执行 metadata，不会用池实例把不同入口变成一个 session。源码落点为 `canonical_db_models.py:202–212`、`hydrate.py:99–118/169–177`、`identity/ingress.py:460–472`、`turn_execution.py:899–924` 和 `llm/json_http.py:104–106`。

App 主会话目前是在平台完整合同上增加 `read_personal_entry`，不是一个已经完成工具精简的新 Agent。工具是否删减或合并另作讨论，见[工具设计与 Memoh 参考报告](Yuki-工具设计与Memoh参考报告-2026-10-16.md)。用户尚在考虑方案；该报告不授权修改模型工具清单、Code API 或既有请求链。F02 修的是所属入口合同被遗漏，不以此擅自重做工具设计。

### F01 / P1：App 子 Agent 配置读取仍按 QQ 账号解析

**现象。** App 的真实消息已入账，父 Work 接纳并启动子 Agent 后，子任务在首次模型请求前以 `CanonicalIdentityError` 失败；没有模型调用，也没有完成实际任务。

**原因。** [来源恢复](../../src/qq_ai_bot/services/execution_sources.py) 已按 `presence.platform` 接受 App Binding，保留正确的 App 外部账号和 canonical Person；[子执行器](../../src/qq_ai_bot/services/subagent_execution.py) 第 221–222 行仍把 `recovered.actor_user_id` 交给 runtime config。配置 owner resolver 的旧账号入口按 QQ Binding 查找，正常的 App UUID 不是 QQ 账号。同分支 [WorkResumer](../../src/qq_ai_bot/services/work_resume.py) 已使用 `actor_person_id`，这里漏迁移。

**最小改法。** 子执行器沿已恢复、已核权的 `actor_person_id` 读取配置。保留外部账号在原传输及证据中的实际值；不把 App 外部账号强改成 Person ID，不补跨平台搜索或 QQ fallback。

**验收。** 用真实 App HTTP 入账与生产同构执行器启动子 Agent，实际进入假 Provider 并完成；同一个 Person 的 QQ/App 使用同一人物配置，Conversation、触发事件、原来源、generation、根预算和效果回执保持各自事实。不能用替换 owner resolver 的测试桩冒充修复。

- [ ] 修复并补真实 App 子执行回归。

### F02 / P2：App 子 Agent 未继承所属入口的冻结工具合同

**现象。** 在私有诊断中仅纠正 F01 的配置入参，子任务可执行，但实际模型请求中没有 `read_personal_entry`。这项验证隔离了第一处错误，不代表未修改分支已经成功运行 App 子任务。

**原因。** [MainAgentContract](../../src/qq_ai_bot/services/main_agent_contract.py) 已拆出 App/platform 的工具清单、revision 和 ScriptApi；`SubagentExecution.prepare()` 与 container 的 `load_tools` 仍无参调用，整个执行器只缓存一套默认 platform 清单/API。后续直接把它作为 `fixed_tools` 传给 Runner，绕过正常 Main 已有的入口选择。

**最小改法。** 按原 Work 的 Conversation 绑定确定入口，复用部署时已冻结的对应清单、ScriptApi 与 revision；子执行器不要再用一份全局 platform 缓存覆盖所有入口。不按用户或权限裁剪已提交声明，不临时添加工具，不新建注册中心。

**验收。** direct 与 Code Mode 分别交错执行 QQ/App 子任务，并冷恢复原 Work：App 有跨入口只读工具，平台入口没有；对应 API 与恢复合同一致，原协议链的工具声明不变。读取仍在执行处核本人及目标会话归属。

- [ ] 修复两类入口的子执行准备、API 与恢复合同，并补交错及冷恢复回归。

### F03 / P2：普通消息未在接纳事务内核验共享请求号

**现象。** 一台设备的普通消息通过预查、尚未入账时，另一台同 Person 设备以同 UUID 上传文件或取消 Work。命令先提交后，原消息仍可提交并触发 Main，两个操作都被接纳。消息 ACK 丢失时，原请求查询优先返回命令回执，SDK 报 `request_conflict`，已执行消息停在本地 `submitted`，无法按原请求恢复。

**原因。** [ClientMessages](../../src/qq_ai_bot/client_api/messages.py) 第 76–78 行的 `_previous()` 是事务外检查，95–97 行才进入 Gateway；canonical 消息接纳 writer 没有与同 Person 的命令回执一起核对请求号占用。仅用 HTTP 前置检查，不能保证同一原请求只对应一种操作。

**最小改法。** 在原 canonical 接纳短事务内、首次消息写入前，核验同 Person 的既有命令占用；沿现有消息与命令回执返回原结果或冲突。删除会被误当成最终接纳依据的重复判断；不加进程锁、持久队列、请求登记表或新的重试 ID。

**验收。** 真实 HTTP 屏障覆盖消息与 cancel/upload 的两种提交顺序、同设备及跨设备；一个请求号只接纳一种操作，另一种返回 `request_conflict` 且无新效果。模拟消息确认丢失及 SDK 冷启动，原 UUID 能恢复已接纳事实，不盲发第二次。保留现有 Work-input 与普通消息的冲突、同操作跨设备重放语义。

- [ ] 修复原消息接纳边界，补并发与 SDK 恢复回归。

### F04 / P2：App 文件及正文成功回执在重放时被降级

**现象。** App 的“不可变 artifact＋正文”首次返回 `succeeded`，具有实际出站事件与正文；相同 turn/call 重放却变为 `failed / file_sent_caption_unconfirmed`，其中 caption 为 `not_sent`。数据库里的原成功事实没有改变。

**原因。** [SocialService._replay_send](../../src/qq_ai_bot/social/service.py) 第 1657–1658 行仅根据 `attachment_kind=file` 和正文存在，调用 QQ 专用 `_file_result`。App 本来就是一次本地原子交付，没有独立 caption 操作；缺少 QQ 子回执不是失败。

**最小改法。** 按原投递渠道与原持久回执恢复结果。App 读取原原子投递成功事实；QQ 文件与附言继续分别核实际回执。去掉 App 不适用的 caption 门槛，不补发 caption，不制造假回执或重传 artifact。

**验收。** App 文件有/无正文的同调用重放与确认丢失恢复保留原 operation/event ID、成功状态和实际正文；原文件不重传。QQ 文件与附言成功、失败、未知的原分段语义不退化。

- [ ] 修复回执投影分支，补 App 重放与 QQ 对照回归。

**验收。** 旧请求因合法清退不可读时，新 home/sync、其他请求恢复和后续 watch 可继续；原未知或已接纳效果不被重试。覆盖另一成员遗忘、原 Work 清退与有效设备仍在线的真实服务路径。
