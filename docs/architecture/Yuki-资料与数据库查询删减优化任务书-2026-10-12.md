## 0. 最高开发约束

**禁止防御性编程。能通过删除、放宽条件或复用已有查询解决的问题，不新增替代机制。** 先删重复读取、逐条查库、重复解析、无消费者的数据和经验上限，不把它们换成可配置上限、缓存服务、第二套身份解析、队列或调度器。

注重可扩展性和可维护性，不把代码写死，为未来变化留出必要空间。优化应当减少真实工作量，不能靠少返回人物、少读证据、遗漏候选或截断指令来制造“更快”。

身份、授权、内部事件、已提交历史、原执行 ID 和真实回执继续按事实处理。同一次准备可以复用已经查到的数据；不同时间的授权复核不能凭旧缓存跳过。写前完成查证，SQLite writer 内不等待网络、模型、终端，不扫描历史。

## 2. “最省时间复杂度”的准确目标

一次 SQL 不等于 O(1)。同时记录 SQL 往返数、数据库访问的行/索引、传回字节、Python 解析/排序、writer 占用及网络等待，不用其中一个代替其他指标。

本文符号：`n` 为本次唯一人物/附件/请求 ID 数，`G` 为有关群成员数，`A` 为实际需要的别名数，`F` 为有关事实数，`E` 为有关事件数，`W` 为 Work 数，`C` 为不同声明名字数，`R` 为真正返回的行数，`L` 为读取/处理的总文本或 JSON 长度，`D` 为有关表规模，`P` 为数据库分页大小。下文只在适用处使用这些符号。

| 工作 | 可达目标与下界 | 不能宣称的结果 |
| --- | --- | --- |
| 去重、筛选、一次准备中的投影 | 哈希实现通常为 `Θ(n + L)`；输入与输出都必须读完 | 删除 5 人上限后仍靠重新构造集合，或把完整输出说成 O(1) |
| 已知 ID 的索引批量读取 | 删除 `n` 次应用往返；数据库通常仍有 `O(n log D + R)` 的索引/结果工作 | 用“一个 IN”把 DB 成本写成 O(1)，或为小批 ID 扫整张表 |
| 全群名字的完整模糊检索 | 至少访问有关标签；同次准备只加载/规范化一次，结果选择按消费者需要处理 | 靠固定前 5/20 人消除真实歧义；声称保持原模糊评分却无需看候选 |
| 完整事件/事实/协议材料 | 对实际使用的原件，读取与解析下界为 `Ω(L)` | 不做完整性验收就以截断正文获得线性增长 |
| 只需要存在、数量、ID、版本的查询 | 在 SQL 使用 `EXISTS`、聚合或窄列；避免正文传输和 JSON 解析 | 把有副作用的重新执行当作查询优化 |
| 分页与维护 | 以索引候选/游标逐页完成，内存随有效页或结果增长 | 只处理第一页、建立“超过多少不再处理”的新门槛 |

复杂度是查询形状的目标，不是生产毫秒承诺。是否需要索引，先看实际 ORM/SQL 的 `EXPLAIN QUERY PLAN`；先改重复查询和错误枚举，再考虑索引。真实索引新增时同时计入写入、迁移、体积和维护成本。

## 3. 已核实的资料链与实验

### 3.1 查询超时和断连不是同一个问题

在该轮历史基线中，`services/user_profiles.py:23` 的 `PROFILE_LOOKUP_TIMEOUT_SECONDS = 0.25` 被 `capture:107` 和 `services/processor.py::_observe_group_metadata:1491` 共用。它在 NoneBot 原生 API 等待外又增加一次提前取消。OneBot resolver 当时只对缺失字段补查，并没有每条消息都拉成员列表；`adapters/onebot/profiles.py:24/44` 分别读群资料和缺失的人物资料。

这项 250ms 经验限制来自 `eb8851b`（2026-10-01）：群资料旧 3 秒等待被换为 250ms，人物补全被加上同一外层等待。没有找到要求这个数字的协议合同。P01 当时删除这个数字与两处外层包装，没有换另一个数或新配置。

10-11 线上记录有资料 `TimeoutError`、NoneBot `ResultStore.add_result` 的 `future.set_result` 抛 `InvalidStateError`，随后发送 `ApiNotAvailable` 与自动重连；同时另有 Gemini 503。没有证据把这些都归因于数据库、内存泄漏或同一个 echo。

同镜像 NoneBot OneBot 2.4.6 的隔离实验能分别以取消后清理前到达的回执、清理前重复回执复现 `InvalidStateError`。线上日志没有留下具体 echo，不能宣称已经确认触发的是哪一种。删除外层提前取消能去掉本项目的多余触发条件，但不能据此宣称修复依赖库的全部迟到/重复回执问题；后者单列 Q03。

### 3.3 “5 人”有不同来源，不要混成关系评分

P10 的 `SequenceMatcher` 在长/重复字符串上并非固定成本：本镜像 Python 标准库说明其最坏为二次、最好为线性，平均行为依共同元素。设query长q、各标签长ℓ_i，完整模糊评分最坏可按 `O(Σ(q+ℓ_i)²)` 上界描述，另计别名与候选排序。只有真实模糊消费者才做这件事。保持原评分时不能承诺整体线性，且有序返回本身有成本。先删除 P09 的无用模糊计算，再测有意义的候选选择优化，不为“极致复杂度”新增预计算字段、相似度库或新名字数据库。

资料算法成本对照：P04 目前为 `O(n)` 次 SELECT 往返加各人的索引/别名读取；P06 原为逐账户 Presence/Binding/Person 查询；P07 集合构造为 `O(nk)`，在旧 `k≤5` 时看似线性，删上限后 `k≈n` 即二次；P08 一次全群约 `4G+3` 条 SELECT（无额外 nickname fallback 的夹具），并读取/排序有关别名与 Bindings。P09 当前 C 个声明名可重复上述全群过程和评分。对应目标是一次准备内按有关 ID 批量查、一次规范化、按真实结果组装；DB 索引工作和完整别名输出仍存在，不与 SQL 往返减少混淆。

### 5.2 实测与复杂度目标

以下均为当前原生仓库、纯内存合成 SQLite 的 SELECT 捕获，不含 DDL/连接 PRAGMA/BEGIN/COMMIT，不是运行套件通过或生产计时。

| 路径 | 合成输入与结果 | SELECT |
| --- | --- | --- |
| Dream candidates，SELF/global | F=1/4/8，候选完整返回 | 5/17/33，即此夹具 `1+4F` |
| Dream candidates，Group | F=8、同一真实 canonical Space | 57，即此夹具 `1+7F` |
| Dream cluster / 首次 `_input` | 各 8 条 SELF 事实 | 各 8 |
| Dream 原事务已 prepare_evidence_rows 后 `_input` | 同 8 条 | 0，已做好的复用，不重写 |
| SELF visible facts | 3 status×global/current-group，各一条，返回 6 条 | 15 |
| 到期维护 | 8 条 SELF/global、无矛盾关系，8 项真实失效 | 36 |

- M01/M02 当前应用查询往返 `O(F)`，目标 `O(实际批次页数)`；候选正文 hash、完整来源与向量解码仍有 `Ω(L + F×向量维度)` 工作。需要返回全集的 Dream caller 仍要持有候选/向量，不能把读取分页说成整个 Dream 内存 O(P)。
- M03 state 往返从本页事件数降为 distinct owner 数，最终批量后随页而非消息增长。每条事件的实际 pending/last_seen/水位贡献仍处理，不能少算旧 generation 或过滤页就直接推进。
- M04 合并 SQL 不得让某类 status/visibility 被总 LIMIT挤掉。literal20 是当前实现经验截断，现行合同没有要求每桶20；它不能成为这次的新验收不变量。实际输入超容量沿现有分页/容量合同处理，不能另建全量事实缓存。
- M05 设待处理 state 数为 s、有关未 completed run 数为 r，应用匹配从 `O(sr)` 降为 `O(s+r)`；cycle 正文从 24h 全部报告变为一条原 baseline。原 usage/真实发送统计继续从真实来源聚合。
- M06 异常 J 个 job 目前 J 次 writer，目标按原工作页取得短 writer；每 claim 的 CAS 条件与真实状态变更仍存在，不能用一条无条件 UPDATE 吞掉新的 claim。重复文本处理减半，但对实际文本的下界仍是 `Θ(L)`。
- M07 当前多层逐 fact 读取，先消除同事务重复装载，再批量有关当前事实；每事实的必要状态事件不会因优化消失。M08 相关点与 counterpart 的逐点 SELECT 改为有关两跳集合读取，不能扫描任意全事实关系图。
- M09 必须覆盖 B 条真实 pending 尾部，CPU/证据解析仍 `O(B+L)`；峰值目标为流式页及必要 Run/state，而非全部完整事件。音频 JSON 的长度不等于实际 evidence_content 长度，不能以 SQL length(audio_transcript) 替代真实转写文本。
- M10 每候选正常 Person+PersonGroup 约 4+6 条 SELECT，且重复 requester/membership；批量后 DB 关系与返回 targets 的成本仍存在。历史直接共同群政策不改为朋友的朋友，也不改为网络群探针。
- M11 SQL 扫描仍 `O(有关 jobs)`，Host 传输/内存改为有关 owner/category 组数；SQL 次数可能增加，不拿“一个 SQL”当唯一裁决。M12 的 target×hits、receipt×events 重扫分别由 `O(TH)`/`O(UE)` 降为一次分组/映射的 `O(T+H)`/`O(U+E)`。

### 5.3 事务与恢复的具体核验

M02 模型前准备与模型后 commit 复核不是同一时刻；后者不能删除。首次输入批读完整可读证据，写前复核原 facts/source/signature；action 后的实际输出和最新来源需从本事务真实状态读，不拿写前对象替代。保原 operation/mutation ID、预算、同一完整 input fingerprint 与已确认模型/效果回执，不重做付费调用。

M01 的 legacy-NULL 来源拒绝与 bot provenance 歧义统计需要各自原有的完整来源，不能直接用 readable_evidence_predicate 的已过滤子集替代。M04 的 valid_until 过滤在 `list_facts:449` 只用于 ACTIVE，不给 CONTESTED/INVALIDATED 同套 ACTIVE 到期条件；原 run checkpoint 继续从原持久 payload/fact_map 恢复，不用新查询重建历史输入。

M03 先读本页 state/Conversation 再逐条计数，已有 staged_states 仅服务该页。未知/hidden 来源的排除继续按原水位规则记录，不能把业务过滤移到扫描 LIMIT 前使后续范围被误当处理。

M06 保 `_claim_guard:302` 的 id/fact/profile/hash/status/updated_at/attempts；迟到 fail/skip/complete 不覆盖重新认领。时钟回拨仍产生原合同的新 claim 身份，取消传播，纯 DB 回滚重备不重复 Provider embed。

M09 不泛称所有 complete 都已经在 writer 中扫描：普通 complete/单项 recover 的 session 为 autoflush=False，赋值 run.status 本身不是 DML。确切的混合路径是 `recover_stale_runs:888–909` 同 session 先恢复 initiative，`_recover_processing_run:954` 调 `advance_cursor` 直接 UPSERT，再遇普通 run 的 `:978` 大尾扫描。先完成整个原恢复页准备，再应用既有 cursor/status，不按猜测的“普通在前”排序避开问题。

M09 另有易漏事实：原 Run 先在 ORM 中被置 completed，gaps 查询拿到同实例时能看到未 flush 的本次完成。改成只读数据库 status 的裸 SQL 汇总会把该范围误当 processing。可保原 session 的 Run 实例、仅 load 所需字段，完成全部 tail/window 计算后再应用原写入；不新增持久准备状态、缓存或另一套恢复流程。

`session.begin()` 不自动等于 SQLite 的完整读快照。SELF 这几条派生水位/领取/收尾链保原事务边界和 `autoflush=False`，整页准备后才写；不追加会在并发提交后升级失败的显式 `BEGIN`，也不为此持 writer 扫历史。真实 Memory 变更仍沿原独立读快照与 `apply_evidence_write` 核来源、owner 和 generation；SELF 水位不冒称新增了全链并发来源围栏。普通 failed retry 复用原状态条件更新单次领取，真实条件写未接纳即退出并释放 writer。

M07/M08 复用已实现的完整 evidence/read snapshot、两跳依赖及原 writer。prepare不是最终授权，来源状态、valid_until、矛盾 counterpart 和未知 commit 继续按本事务事实处理；删的是冗余查询和无用 payload，不是审计或事实事件。

### 6.2 当前成本与证据

- R01 两秒轮询内，同 root 的多 run 条件重复展开后代树。当前局部原方法对 1/100 个合法形状、未满足 owned_run 条件分别做 2/200 次查询，返回 unchanged。目标是每页及不同 root 的批量查询，仍逐条件解释 ANY/ALL/partial/deadline；发现事实不能代替取得 writer 后的当前复核。

- R04 当前一个 SQL 读全部大 Work，不能仅因变为两个 SQL 就拒绝改进。DB 仍要找资格元数据和可派发 scope；减少的是未派发 goal/checkpoint/counters 的传输/装载。**保 D47 反例**：同一忙 scope 有超过 8 个 Work，后面的独立 scope 仍可进入；不恢复全局行 LIMIT8 或只扫一页。正式 acquire/activate 仍读当前源与租约。

### 6.3 不改的事实与最小验证
