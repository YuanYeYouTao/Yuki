# 上下文与压缩成本敏感性模拟（2026-10-01）

结论：96k 聊天/128k Work 可作为保守启动政策，不能宣称成本或信息保持全局最优。政策窗口使用本地保守估算 token，生产 usage 使用 Provider token，二者不能直接等同。当前群聊实测最大输入 54.6k usage tokens，但真实同链小样本的 native-wire 估算/usage 比例约 1.77–1.78；按 1.8 敏感性计算，96k/0.85 水位不再是零触发。真正持续数百轮的 Work 没有生产样本；以下是实际增量驱动的合成模拟，不证明全部重要信息能保留。上线默认值仍需任务资料、近期回合、否定要求、未决证据的保持验收。

## 取数与数据边界

- Yuki 数据库只读 `model_invocations` 最近三天、最多 5000 条，实际 2629 条；时间范围 2026-09-28 13:08 至 2026-10-01 12:57 UTC。没有提取聊天正文、提示词、工具结果、人物姓名或凭据。
- 全部 chat_agent 1729 条，其中 Gemini 3.8 Flash 1679 条；模拟仅使用 Gemini 成功且输入 usage 已知的 1573 条，避免将失败或缺失 usage 当真实窗口。
- Gemini 输入 min/median/p95/max：17,366 / 31,374 / 43,472 / 54,592 tokens。缓存字段缺失 227 条，明确等于 0 的记录为 0。已知缓存样本的输入加权命中比例 85.13%；将未知全部按 miss 计算的保守下界 73.86%，不是观测到的真实 miss 比例。
- 同一 runtime_turn 的成功请求中有 432 个多请求回合，最多 24 次请求。正输入增量 722 个，median/p95/max 为 601 / 1883 / 9181 tokens。它包含工具结果和当前真实序列变化，不是正文字符增量，也不包含可证明的无限 Work。
- 现有 Conversation compaction 54 次，已记录输入合计 354,619、输出合计 38,990 tokens；它是群聊 Rollup，不能当作 Work 执行摘要的质量或输出大小实测。
- AGM 当前只读 `request_logs` 最近 2000 条，模型都为 `gemini-3.8-flash`，mapped model 为 `gemini-3.8-flash-tiered`，协议 Gemini。缓存字段 NULL 781 条，明确 0 条为 0。另取 token_usage 最近 2000 条，缓存没有 NULL、810 条为 0；两个表不能逐条直接视为同一窗口，不能据此把 810 条全部认定为缓存未命中。

额外读取 20 条 AGM 请求的 JSON 结构，只输出字段集合、contents/tools 数量和 cache usage 数字：客户端是 Gemini native `contents/systemInstruction/tools`；上游增加 model/requestId/sessionId/safetySettings，样本中的 toolConfig 未保留。没有显式 cachedContent 引用或 cache_control。缓存已知时响应出现匹配的 cachedContentTokenCount；缺失样本没有该字段。这证明 usage 缺失与 0 必须区分，不能保证代理的全部请求都采用某一种缓存策略。

AGM 当前公开源码 token_stats 将 cached_tokens 保存为 NOT NULL 数值，统计层不表达 unknown；这是公开实现参考，不冒充当前部署二进制的逐行源码证明。[官方仓库](https://github.com/lbjlaq/Antigravity-Manager/blob/main/src-tauri/src/modules/token_stats.rs)

## 价格与公式

2026-10-01 核对 Google 官方 Gemini 3.8 Flash Standard：截至 2026-12-31，input/cached input/output 为 $0.75/$0.075/$3.75 每百万 tokens，output 包含 thinking。2027-01-01 起对应价格翻倍。[官方价格](https://ai.google.dev/gemini-api/docs/pricing)

实际路径是 AGM 的 tiered 上游，不是已确认的 Gemini Developer API 付费路径；本报告不把公开价格乘积当实际订阅额度或账单。用 input 单价归一化为 1，cached 单价为 0.1，output 为 5；另外扫 cached 单价 0.25/0.5/1、命中比例 0.5/0，以及辅助摘要命中 0/0.5。Google 官方说明隐式缓存不保证节省，不能把当前命中率当永久承诺。[官方缓存说明](https://ai.google.dev/gemini-api/docs/generate-content/caching)

```
相对成本 = [非缓存业务输入 + cached_price × 缓存业务输入
          + 非缓存摘要输入 + cached_price × 缓存摘要输入
          + 5 × (业务输出 + 摘要输出)] / 1,000,000
```

压缩后第一次请求只假设固定前缀仍可命中；摘要默认按无命中计费。额外敏感性把压缩后首次完全当冷请求。不能在“全文上下文更短”之外漏算摘要请求和重建缓存。

## 群聊窗口：观测阈值分析

候选热输入预算 64/96/128/160/192/256k **估算输入 tokens**，trigger 为 0.75/0.80/0.85/0.90，target 为 0.40/0.50/0.60/0.65。k 是十进制千，不是 KiB 或字符。政策预算、Profile 独立输入上限、Profile 联合上下文上限分别处理：独立输入预算不再次扣输出；只有显式联合上下文上限才扣输出预留。脚本默认没有已认证的模型容量上限，不能把候选当上游容量认证。

本次修正模拟中隐含的 `context + 6144 > window` 拒绝条件：原 window 已定义为活动输入预算，不能再暗扣 4096 输出和 2048 误差。脚本将输入估算 margin（默认 0）与可选 `model_input_limit`/`model_context_limit` 分开；4096 输出预留只用于显式联合 context limit。成本与增长始终用真实 usage 单位，只有政策 admission/trigger/target 乘估算比例。

| --- | ---: |
| 0.75 | 9 |
| 0.80 | 4 |

仅比例 1.0 时，96k 及以上的全部候选 trigger 在本样本均为 0。不能用这份样本宣称 128k 比 96k 更省钱，也不能把“超过水位一次”当实际只需一次压缩：调整 Rollup 后后续输入和缓存会改变，需要真实回放才可因果评估。

## 长任务：800 次执行请求的条件模拟

使用上述 722 个真实正增量按固定顺序重采样，构造 800 次执行请求。初始目标、来源与媒体构成不模拟。固定前缀 12k、结构化任务资料 4k、近期八回合保留预算 `8 × p95增量` 均为 usage 单位的政策假设，最低保留量为 31,064 usage tokens；不是实测必要信息量。target 政策预算除以估算比例后低于该保持约束的候选直接拒绝，不能靠裁掉必要资料获得低价。

摘要输出假设 2000 tokens；每次执行输出假设 46 tokens，各政策保持一致。真实长任务有 thinking、大输出、媒体、缓存过期、空响应和失败重试，当前模型没有这些实测标签。摘要后保留到 target 对应的 usage 量，随着增量增长，估算输入达到 trigger 再摘要；下一请求核对独立输入预算及显式输入 margin。如提供模型独立输入/联合 context 上限，再分别检查；输出只在联合上限中预留一次。

下表是比例 **1.0** 基准条件下**每个窗口内部**的最低相对成本，不是推荐值。删除错误输出双扣后，这些最低成本候选数值未变；其他候选的可行性判定已按输入预算修正。成本单位为百万 input 单价，不能写成实际美元。

| 热预算 | 最低成本 trigger/target | 摘要次数 | 执行输入百万 tokens | 摘要输入百万 tokens | 相对成本 |
| --- | --- | ---: | ---: | ---: | ---: |
| 64k | 0.90/0.50 | 25 | 35.83 | 1.418 | 10.642 |
| 96k | 0.75/0.40 | 19 | 43.97 | 1.350 | 12.421 |
| 128k | 0.75/0.40 | 13 | 58.78 | 1.240 | 15.704 |
| 160k | 0.75/0.40 | 11 | 72.04 | 1.299 | 18.902 |

仅比例 1.0 的这组保持约束下，64k 最便宜；256k 减少摘要次数但重复携带更多热输入。比例 1.0 的 24 组价格/命中率/摘要命中场景以 64k 成本最低；本次扩为五比例共 120 场景，不能将旧 64k 结论跨比例套用。

提高必须保留的任务资料后，选择会变：

| 最低保留预算 | 摘要输出假设 | 条件成本最优 | 相对成本 |
| --- | ---: | --- | ---: |
| 31,064 | 2000 | 64k，0.90/0.50 | 10.642 |
| 48k | 2000 | 96k，0.75/0.50 | 14.426 |
| 64k | 2000 | 128k，0.75/0.50 | 18.174 |
| 48k | 8000 | 96k，0.85/0.50 | 15.141 |

这也是不能只选最短窗口的原因：信息保持下限必须先确定。最低保留量 48k 时，64k 所有 target 候选均不合格。更长、更贵的摘要会使频繁压缩更不划算；最优 trigger 会变化。压缩后首次完全 miss 会提高成本，但没有改变这些条件下的最优窗口级别。

| 2.0 | 128k，0.90/0.50 | 160k，0.90/0.60 | 256k，0.75/0.50 |

这些候选只在合成资料保持下限和离散网格内最优。最终 Work 使用独立初值 128k/0.90/0.50、摘要输出按完整上限 8192 计费，在五比例下均满足假设 31,064 usage 保留量：800 次请求分别压缩 11/15/19/23/25 次；比例 1.8 时保留约 35.6k usage、执行峰值约 63.9k usage、相对成本 12.367。若真实资料需保留 48k/64k usage，初值仍不够，不能将容量暂停说成无损摘要完成。

同一合成保持下限用于聊天初值的压力敏感性，96k/0.90/0.60 在比例 1.8 下保留 32k usage，高于 31,064 假设下限；比例 2 下只保留 28.8k，判为不可行。这不是普通群聊真实必须保留 31k 的证明，只用于避免以同一条件把不可行候选称为建议。比例 1.8 的自然 usage 阈值分析，96k/0.90 超水位 9 条，旧 0.85 为 49；二者都不是实际压缩次数。

聊天 target 提至 0.60 是为满足所用保持假设；Work 已有较大窗口，不必照搬，保持独立 0.50。
比旧 Work 0.85/0.50，新 0.90/0.50 的 trigger-target 间距从 0.35 扩至 0.40，在本次合成序列减少压缩；更久携带输入也可能增加费用：

| 估算/usage 比例 | 旧 Work 压缩/相对成本 | 新 Work 压缩/相对成本 |
| --- | --- | --- |
| 1.0 | 13 / 18.489 | 11 / 18.587 |
| 1.25 | 17 / 15.671 | 15 / 15.921 |
| 1.5 | 21 / 13.783 | 19 / 13.952 |
| 1.8 | 26 / 12.251 | 23 / 12.367 |
| 2.0 | 29 / 11.543 | 25 / 11.416 |

比例 1.8 下少三次压缩（26→23，约降 11.5%），费用约升 0.94%；比例 2 费用约降 1.10%。这是保持下限与压缩调用/延迟约束下的 Pareto 启动权衡，不能宣称全面省钱、全局最优或实际延迟已改善。仅费用优先时可热选择 Work 0.85/0.50；若要保留约 48k/64k usage，则 ratio=1.8 网格给出 160k/192k 可配置候选，仍须保持与硬容量验收。

## 实施建议与后续验收

本轮选定开发初值：聊天 **96,000 估算 tokens、0.90/0.60**；Work **128,000 估算 tokens、0.90/0.50**，两种摘要输出上限各 **8,192 tokens**。热配置为 `context.window_tokens`/`context.work_window_tokens`，聊天 `context.compaction_trigger_ratio`/`context.compaction_target_ratio`，Work `context.work_compaction_trigger_ratio`/`context.work_compaction_target_ratio`，及 `context.compaction_output_tokens`/`context.rollup_output_tokens`。两对水位独立热更并验证跨作用域继承；均受所选 Profile 的输入/联合窗口与输出上限约束。

选择独立政策，使约 1.8 估算比例下聊天/Work 目标分别保留约 32k/35.6k usage，而不是让聊天目标低于所用 31k 假设下限，或替 Work 增加无依据热携带量。0.90 利用保守计量的 Provider usage 余量，完整请求硬 Profile 检查始终先行，预计越界可提前整理。8,192 是摘要上限，不要求填满。本模拟不证明全局语义、费用或完成率最优；尤其比例 2 的聊天保持假设仍失败，线上生效、资料保持和自然成本须分别验收。

1. 真实模型窗口与偏好的热窗口预算分开。普通群聊与持久 Work 可以采用不同热预算，但共用容量估算、事实引用和模型执行边界；不增加内容分类路由。
2. 群聊先按实际估算计量验证 96k，Work 先验证 128k；不能将 ratio=1 的 64k 条件最优直接当本地政策。在 ratio=1.8 假设下，31k usage 保持量的低价网格候选为 96k，但 48k/64k 保持量分别需要更高政策预算（本网格为 160k/192k）。256k 可作为重资料工作显式配置候选，不因取消累计步数而成为默认值。
3. 聊天 0.90/0.60、Work 0.90/0.50 是启动政策，不保证所有大图/协议帧都有固定误差。观察真实请求形状，target 由必要资料、近期回合与低水位决定，阶段/未决事实在冷证据层精确回查。若估算比例/保持需求变化，独立热调整，不能借保守计量绕过硬容量检查。
4. 压缩质量验收包括真实追加限制、否定条件、近期完整 call/result、未决状态和来源水位；某候选缺一项便不参加“省钱”排序。重试、cache missing、summary失败和 output/thinking 实际 usage 需独立记录，不能用全局 token 总和猜原因。
5. 旧共享64 MiB证据配额不能触发无关 Work 的模型摘要；字节存储、字符展示、token热窗口各自计量。摘要开销少不代表存储压力小。估算比例应按真实请求形状/工具/媒体分布持续校准，不能把同链三请求的比例写死为 tokenizer，更不能据此上调实际模型容量声明。

## 复现

脚本 `scripts/context_cost_simulation.py` 只读取内容无关的 JSON 元数据，不连接生产、不调用模型、不做测试消息。私有取数与全部网格留在忽略的 `.cache/`，不提交实际会话标识和请求记录。

```powershell
uv run python scripts/context_cost_simulation.py `
  --yuki .cache/context-cost-yuki-usage.json `
  --agm .cache/context-cost-agm-usage.json `
  --output .cache/context-cost-grid.json `
  --estimate-ratios 1 1.25 1.5 1.8 2
```

脚本另支持 `--input-margin-tokens`（本地估算输入单位，默认 0）、`--model-input-limit`、
`--model-context-limit`（仅对已认证的 Provider usage 容量作条件分析）和
`--output-reserve-tokens`（默认 4096，只用于显式联合 context limit）。默认不传模型上限，
不借列表常量或这份模拟认证生产容量；成本核算不会把本地保守估算比例当实际计费倍率。

原始自然流量只读采集，不改变线上配置。本次修正后重跑生成 120 价格/命中/比例场景、90 资料保持/摘要/前缀/比例敏感性结果及各五组当前 Work/旧 Work/聊天初值保持敏感性，均留忽略的 `.cache/`。结论为条件敏感性分析；开发初值不代表线上配置已生效或线上质量已验收。
