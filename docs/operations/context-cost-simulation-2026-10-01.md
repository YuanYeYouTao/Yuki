# 上下文与压缩成本敏感性模拟（2026-10-01）

结论：256k 不宜因为“长任务”直接成为默认热窗口。当前群聊实测最大输入 54.6k，64k–96k 已覆盖这份样本；真正持续数百轮的 Work 没有对应生产样本。以下长任务结果是实际增量驱动的合成模拟，能比较成本与压缩频率，不能证明某窗口能保留全部重要信息。上线默认值必须同时经过任务资料、近期回合、否定要求、未决证据的保持验收。

## 取数与数据边界

- Yuki 数据库只读 `model_invocations` 最近三天、最多 5000 条，实际 2629 条；时间范围 2026-09-28 13:08 至 2026-10-01 12:57 UTC。没有提取聊天正文、提示词、工具结果、人物姓名或凭据。
- 全部 chat_agent 1729 条，其中 Gemini 3.8 Flash 1679 条；模拟仅使用 Gemini 成功且输入 usage 已知的 1573 条，避免将失败或缺失 usage 当真实窗口。
- Gemini 输入 min/median/p95/max：17,366 / 31,374 / 43,472 / 54,592 tokens。缓存字段缺失 227 条，明确等于 0 的记录为 0。已知缓存样本的输入加权命中比例 85.13%；将未知全部按 miss 计算的保守下界 73.86%，不是观测到的真实 miss 比例。
- 同一 runtime_turn 的成功请求中有 432 个多请求回合，最多 24 次请求。正输入增量 722 个，median/p95/max 为 601 / 1883 / 9181 tokens。它包含工具结果和当前真实序列变化，不是正文字符增量，也不包含可证明的无限 Work。
- 现有 Conversation compaction 54 次，已记录输入合计 354,619、输出合计 38,990 tokens；它是群聊 Rollup，不能当作 Work 执行摘要的质量或输出大小实测。
- AGM 当前只读 `request_logs` 最近 2000 条，模型都为 `gemini-3.8-flash`，mapped model 为 `gemini-3.8-flash-tiered`，协议 Gemini。缓存字段 NULL 781 条，明确 0 条为 0。另取 token_usage 最近 2000 条，缓存没有 NULL、810 条为 0；两个表不能逐条直接视为同一窗口，不能据此把 810 条全部认定为缓存未命中。

额外读取 20 条 AGM 请求的 JSON 结构，只输出字段集合、contents/tools 数量和 cache usage 数字：客户端是 Gemini native `contents/systemInstruction/tools`；上游增加 model/requestId/sessionId/safetySettings，样本中的 toolConfig 未保留。没有显式 cachedContent 引用或 cache_control。缓存已知时响应出现匹配的 cachedContentTokenCount；缺失样本没有该字段。这证明 usage 缺失与 0 必须区分，不能保证代理的全部请求都采用某一种缓存策略。

AGM 当前公开源码 token_stats 将 cached_tokens 保存为 NOT NULL 数值，统计层不表达 unknown；这是公开实现参考，不冒充当前部署二进制的逐行源码证明。[官方仓库](https://github.com/lbjlaq/Antigravity-Manager/blob/main/src-tauri/src/modules/token_stats.rs)

## 价格与公式

2026-10-01 核对 Google 官方 Gemini 3.8 Flash Standard：截至 2026-12-31，input/cached input/output 为 $0.75/$0.075/$3.75 每百万 tokens，output 包含 thinking。2027-01-01 起对应价格翻倍。[官方价格](https://ai.google.dev/gemini-api/docs/pricing)

实际路径是 AGM 的 tiered 上游，不是已确认的 Gemini Developer API 付费路径；本报告不把公开价格乘积当实际订阅额度或账单。用 input 单价归一化为 1，cached 单价为 0.1，output 为 5；另外扫 cached 单价 0.25/0.5/1、命中比例 0.5/0，以及辅助摘要命中 0/0.5。Google 官方说明隐式缓存不保证节省，不能把当前命中率当永久承诺。[官方缓存说明](https://ai.google.dev/gemini-api/docs/generate-content/caching)

```
相对成本 = [非缓存业务输入 + cached_price × 缓存业务输入
          + 非缓存摘要输入 + cached_price × 缓存摘要输入
          + 5 × (业务输出 + 摘要输出)] / 1,000,000
```

压缩后第一次请求只假设固定前缀仍可命中；摘要默认按无命中计费。额外敏感性把压缩后首次完全当冷请求。不能在“全文上下文更短”之外漏算摘要请求和重建缓存。

## 群聊窗口：观测阈值分析

候选热输入预算 64/96/128/160/192/256k tokens，trigger 为 0.75/0.80/0.85/0.90，target 为 0.40/0.50/0.60/0.65。这里的 k 是十进制千 tokens，不是 KiB，也不是字符。候选是热请求政策预算，仍必须小于实际 Profile 窗口扣除输出/误差预留的容量；不能为省钱篡改模型声明的硬窗口。

| 64k trigger | 超过水位的成功实测输入数 /1573 |
| --- | ---: |
| 0.75 | 9 |
| 0.80 | 4 |
| 0.85 | 1 |
| 0.90 | 0 |

96k 及以上的全部候选 trigger 在本样本均为 0。不能用这份样本宣称 128k 比 96k 更省钱，也不能把“超过水位一次”当实际只需一次压缩：调整 Rollup 后后续输入和缓存会改变，需要真实回放才可因果评估。

可先以 64k–96k 为群聊热预算候选；64k/0.85 的触发覆盖样本较充分，96k 提供媒体、大输入和估算偏差余量。target 不由这个阈值表决定，必须保留连续 raw tail 和关键开放事项；不统一改成最短窗口或固定 256k。

## 长任务：800 次执行请求的条件模拟

使用上述 722 个真实正增量按固定顺序重采样，构造 800 次执行请求。初始目标、来源与媒体构成不模拟。固定前缀 12k、结构化任务资料 4k、近期八回合保留预算 `8 × p95增量` 均为政策假设；所以最低 target = 31,064 tokens。目标低于该保持约束的候选直接拒绝，不能靠裁掉必要资料获得低价。

摘要输出假设 2000 tokens；每次执行输出假设 46 tokens，各政策保持一致。真实长任务有 thinking、大输出、媒体、缓存过期、空响应和失败重试，当前模型没有这些实测标签。摘要后保留到 target，随着增量增长，达到 trigger 再摘要；下一请求同时检查 4096 输出 +2048 估算误差预留。保留预算大于模型可执行容量时明确不可行。

下表是基准条件下**每个窗口内部**的最低相对成本，不是推荐值。成本单位为百万 input 单价，不能写成实际美元。

| 热预算 | 最低成本 trigger/target | 摘要次数 | 执行输入百万 tokens | 摘要输入百万 tokens | 相对成本 |
| --- | --- | ---: | ---: | ---: | ---: |
| 64k | 0.90/0.50 | 25 | 35.83 | 1.418 | 10.642 |
| 96k | 0.75/0.40 | 19 | 43.97 | 1.350 | 12.421 |
| 128k | 0.75/0.40 | 13 | 58.78 | 1.240 | 15.704 |
| 160k | 0.75/0.40 | 11 | 72.04 | 1.299 | 18.902 |
| 192k | 0.75/0.40 | 8 | 86.04 | 1.144 | 21.946 |
| 256k | 0.75/0.40 | 6 | 110.03 | 1.149 | 27.546 |

64k 在这组保持约束下最便宜，256k 减少摘要次数但重复携带更多热输入。24 组价格/命中率/摘要命中场景仍以 64k 成本最低；这只证明公式中成本结构的趋势，没有衡量更大窗口多保留信息的收益。

提高必须保留的任务资料后，选择会变：

| 最低保留预算 | 摘要输出假设 | 条件成本最优 | 相对成本 |
| --- | ---: | --- | ---: |
| 31,064 | 2000 | 64k，0.90/0.50 | 10.642 |
| 48k | 2000 | 96k，0.75/0.50 | 14.426 |
| 64k | 2000 | 128k，0.75/0.50 | 18.174 |
| 48k | 8000 | 96k，0.85/0.50 | 15.141 |

这也是不能只选最短窗口的原因：信息保持下限必须先确定。最低保留量 48k 时，64k 所有 target 候选均不合格。更长、更贵的摘要会使频繁压缩更不划算；最优 trigger 会变化。压缩后首次完全 miss 会提高成本，但没有改变这些条件下的最优窗口级别。

## 实施建议与后续验收

本轮实际选定的开发初值为：聊天活动输入预算 **96,000 tokens**、Work 活动输入预算 **128,000 tokens**、压缩触发水位 **0.85**、整理目标水位 **0.50**，Work 与群史摘要输出上限各为 **8,192 tokens**。对应热配置是 `context.window_tokens`、`context.work_window_tokens`、`context.compaction_trigger_ratio`、`context.compaction_target_ratio`、`context.compaction_output_tokens` 与 `context.rollup_output_tokens`；这些政策仍受所选 Profile 的输入/联合窗口与输出上限约束。

选择 96k/128k 是为当前自然群聊样本和较重 Work 资料提供初始余量；0.85/0.50 降低频繁重建的概率并留下增长空间。8,192 是摘要输出预算上限，不要求每次填满。本报告的条件成本模拟没有证明这一组合在语义保持、实际费用或长期任务完成率上最优；热配置可调也不构成语义最优的实证。当前选值是开发初值，线上生效、真实资料保持与自然流量成本仍须分别验收。

1. 真实模型窗口与偏好的热窗口预算分开。普通群聊与持久 Work 可以采用不同热预算，但共用容量估算、事实引用和模型执行边界；不增加内容分类路由。
2. 群聊先验证 64k–96k，Work 先验证 96k–128k。若资料保持验收只需约 31k，可试 64k；若必须保留约 64k，应选至少 128k。256k 作为重资料工作显式配置候选，不因取消累计步数而成为默认值。
3. 不直接采纳表中的 0.90：本模拟没有大图及 tokenizer 系统偏差。可先以 0.80–0.85 提供预留，target 由必需资料、近期回合与低水位共同决定；阶段/未决事实在冷证据层精确回查。
4. 压缩质量验收包括真实追加限制、否定条件、近期完整 call/result、未决状态和来源水位；某候选缺一项便不参加“省钱”排序。重试、cache missing、summary失败和 output/thinking 实际 usage 需独立记录，不能用全局 token 总和猜原因。
5. 旧共享64 MiB证据配额不能触发无关 Work 的模型摘要；字节存储、字符展示、token热窗口各自计量。摘要开销少不代表存储压力小。

## 复现

脚本 `scripts/context_cost_simulation.py` 只读取内容无关的 JSON 元数据，不连接生产、不调用模型、不做测试消息。私有取数与全部网格留在忽略的 `.cache/`，不提交实际会话标识和请求记录。

```powershell
uv run python scripts/context_cost_simulation.py `
  --yuki .cache/context-cost-yuki-usage.json `
  --agm .cache/context-cost-agm-usage.json `
  --output .cache/context-cost-grid.json
```

原始自然流量只读采集，不改变线上配置。脚本扫完每个候选与不可行状态；结论为条件敏感性分析。上文记录的开发初值不代表线上配置已经生效或线上质量已验收。
