# Work 协议与证据的完整备份

Work 的私有模型协议、完整工具正文和工作区文件属于恢复证据。数据库中的 manifest
和哈希引用不能代替对应文件；升级到 0088 后，仅备份 SQLite 不能完整恢复工作。
本文补充现行生产运行维护手册，部署仍只替换 Bot，不改 SnowLuma。

## 一致性快照

1. 从当前 Bot 的 Compose labels 读取实际配置文件和数据挂载，记录原镜像 digest、
   Git revision、数据库迁移版本及活动 Work 的原 ID/状态。
2. 用这些实际 Compose 文件停止 `bot`，等待原执行结束并保存检查点。其他服务保留。
3. 在停止期间，用 Python `sqlite3.Connection.backup` 生成一致性数据库备份，复制同一
   数据挂载中的 `work-protocol/`、`tool_artifacts/`、工作区及其他现行证据目录；
   保存配置文件。已有备份目录使用新的时间戳，不能覆盖上次快照。
4. 对备份运行 `python scripts/verify_work_backup.py <备份数据库> <备份数据目录>`。
   它只读检查 SQLite 完整性、外键和数据库引用的协议对象/工具正文的大小及哈希。
   校验失败时先恢复原 Bot，不能把不完整快照记成可回滚备份。
5. 按目标包执行迁移，固定目标镜像并只启动 Bot。校验迁移 head、健康、网关和管理
   入口；按原 Work ID 对比状态、回执和待处理输入，不重建工作或重发已确认投递。

## 恢复与回收

回滚需要核对数据库、引用文件和配置的兼容性。已经产生新执行或投递事实时，应保留
新数据库及文件，使用兼容新存储合同的修复镜像；不能用旧快照覆盖新事实并诱导重发。
只有确认迁移后未执行工作、未接纳新输入且无需保留新事实时，才可以停止 Bot 并恢复
完整旧快照和原固定镜像。旧版本不能直接读取新格式数据。

活动 Work 及其树保有协议对象和工具正文引用，终态本身不会立刻删除它们。归档或
隐私清理释放所有权后，现有维护循环才可回收无主文件。磁盘配额是存储资源围栏，
与上下文窗口、语义压缩水位分别配置和管理；不能清空活动引用来腾空间。

`verify_work_backup.py` 不检查自由文本摘要是否准确，也不替代工作区原有校验。
升级前尚无 0088 表的数据库仍做 SQLite 完整性检查并复制完整数据目录；迁移后
再核验新 manifest 引用。
