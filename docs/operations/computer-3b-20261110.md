# 本人电脑按窗口后台操作（阶段 3b，2026-11-10）

依据[统一 Computer Use 与 Browser Use 任务书](../architecture/Yuki-统一ComputerUse与BrowserUse任务书-2026-11-09.md)
§5.5 第 2 层、§5.7、§6 的 3b 行，[3b spike 记录](computer-3b-spike-20261110.md)的结论与 §6 设计建议，以及
[阶段 3a 记录](computer-browser-device-3a-20261110.md)。本人 2026-11-10 对 spike §8 的决定均为“按建议”：

1. 接受 macOS 未公开接口，但只作后备：先在目标窗口自己的 AX 子树里用 AX 动作；点击与滚轮的后备是盖章
   post-to-pid（窗口字段加私有 `CGEventSetWindowLocation`，Cua 的做法）；按键先经 AX 聚焦目标输入框，再普通
   post-to-pid。
2. 后台送不到时明确失败，绝不自动退回前台或全局输入；模型可自行省略 `window` 改用前台。
3. 只在真正冲突时让出：目标窗口所属 App 是本人的前台 App（或本人指针下的窗口属于它）时，按 3a 的
   `owner_active` 方式让出（等本人停手 1.5 秒、最多 10 秒，然后拒绝且不执行、要求重新截图）；投给其他 App 的
   后台输入不等待。Desktop「停止」（`holder=owner`）仍拒绝一切输入（`control_held`），读照常。
4. 允许对 Yuki 正在操作的 Electron/Chrome App 开启完整无障碍（`AXManualAccessibility`），只在操作它时开启。
5. 最小化窗口保持 `window_unavailable`，不存在的窗口 `window_not_found`。

另据 spike R1：建 ScreenCaptureKit 窗口过滤器之前必须先有一次 CoreGraphics 调用（`CGMainDisplayID()`），否则
`CGS_REQUIRE_INIT` 中止整个连接器；3a 的整屏路径一并修正。任何时候都不用系统级 AX 命中测试找目标。

本记录先列出写代码前的失败情况，再记录设计、测试对照与待实机项。

## 1. 写代码前列出的可能失败情况

每条写明错误行为，括号内为本次应有的行为。编号接续任务书 §7 与 3a 记录，新增项用 W 前缀。

### 截图与窗口身份

- W1 连接器进程在第一次窗口截图时被 `CGS_REQUIRE_INIT` 断言中止，Python 无法捕获，正在执行的输入落成
  `unknown`（`MacScreen` 构造时先调用 `CGMainDisplayID()`；整屏与窗口两条路径共用这一初始化）。
- W2 `screenshot` 的 `windows` 仍是空列表，或列出连接器自己、无标题、非普通层（菜单栏、Dock、浮层）的窗口；
  列出的 `id` 不能原样作为 `window` 使用（macOS：ScreenCaptureKit 全部窗口中 layer 0、有标题、不属于连接器进程，
  `id` 为 CGWindowID 十进制字符串；Windows：可见、有标题、非工具窗口、未被 DWM 隐藏、不属于连接器进程的顶层
  窗口，`id` 为 HWND 十进制字符串；整屏截图与窗口截图都返回同一列表）。
- W3 给出 `window` 时截了整屏、截到遮挡它的其他窗口，或被遮挡的窗口截成黑图（macOS 只用 ScreenCaptureKit
  单窗口过滤器加 `ignoreShadowsSingleWindow`；Windows 用 `PrintWindow(PW_RENDERFULLCONTENT)`，不用屏幕 DC）。
- W4 最小化窗口被截成旧画面或被操作；不存在的 `id`、已关闭的窗口、非数字或非顶层窗口被当成别的窗口
  （最小化、不可见 → `window_unavailable`，以 `AXMinimized`／`IsIconic` 为准，不靠像素判断；找不到 →
  `window_not_found`；两者都在任何输入之前）。
- W5 macOS 没有辅助功能权限时，窗口截图因无法读取 `AXMinimized` 而截出最小化 Chrome 的旧画面
  （按窗口操作需要屏幕录制与辅助功能两项：缺屏幕录制 `screen_permission_required`，缺辅助功能
  `input_permission_required`，截图也一样；整屏截图仍只需屏幕录制）。
- W6 窗口结果仍带 `display`，或不带 `window`，模型分不清坐标属于哪张图（窗口结果为
  `{width,height,window,control}`，不带 `display`）。

### 坐标

- M6（窗口）图像像素没有按窗口原点与 Retina 倍率换算，或按截图时保存的窗口位置换算——窗口在截图与点击之间被
  本人移动后点到旧位置（执行时按**当下**的窗口几何换算：macOS 全局点 = 窗口原点 + 像素 × 点宽／像素宽，像素宽
  = 点宽 × `pointPixelScale`；Windows 物理像素，窗口取 DWM 可见边框 `DWMWA_EXTENDED_FRAME_BOUNDS`；与 3a 共用
  `frame()`／`to_global()`，按服务端的 `max_dimension`／`max_pixels` 在来源处产出最终尺寸）。
- W7 盖章事件的窗口位置在 macOS 27 与更早版本上用同一种坐标，点击偏移一个窗口原点（macOS 27 起
  `CGEventSetWindowLocation` 写窗口内坐标，更早版本写全局点，按 Cua `window_location_is_window_local`）。

### 投递

- W8 用系统级 `AXUIElementCopyElementAtPosition` 或 App 级命中测试找元素，点到遮挡它的窗口或另一个 App
  （spike R2；只遍历目标窗口自己的 AX／UIA 子树，取包含该点的最小元素，再向上找可操作的祖先）。
- W9 后台动作移动了本人光标、改变了前台 App 或窗口层级、抢走焦点（AX 动作、盖章 post-to-pid、UIA 模式都不经
  全局光标；不调用 `AXRaise`、`SetFocus`、`SetForegroundWindow`、不还原最小化窗口；Windows 不用 `PostMessage`／
  `SendInput`）。
- W10 普通 `CGEventPostToPid` 的点击与滚轮被静默丢弃却回执 `submitted`（spike R5；点击在 AX 找不到可按元素时、
  滚轮、双击、右键在 AX 没有 `AXShowMenu` 时、移动、拖拽一律用盖章事件：mouseMoved 引子、字段
  7=3、40=pid、51／91／92=窗口号、58=点击组，`CGEventPostToPid` 只投一次）。
- W11 按键落在同一 App 的另一个窗口（spike R6；`type`／`key` 给出 `x,y` 时先对该处输入框设 `AXFocused`；
  不给时投给 App 当前焦点，说明里写明）。
- W12 后台送不到时自动退回前台或全局输入（决定 2）：Windows 的 `key`、`double_click`、`right_click`、`move`、
  `drag` 没有不用 `PostMessage` 的后台途径，`click`／`scroll`／`type` 在该处找不到 Invoke、Toggle、SelectionItem、
  ExpandCollapse／Scroll／可写 Value 模式时也没有——都返回 `device_not_supported`（说明可省略 `window` 改用前台），
  不投递任何事件；能在执行前判断的（按动作）在打 `activity` 行之前拒绝。
- W13 Chromium／Electron 的网页内容 AX 树为空，点击退化成被丢弃的像素点击；或对 Yuki 没有操作的 App 也开启了
  完整无障碍（决定 4：只在向某 App 投递输入时对它设 `AXManualAccessibility`，首次开启后等网页树出现、最长
  4 秒，spike R12；本进程内不重复设置）。
- W14 回执声称“已核实”，或没有附动作后的窗口截图（一律 `submitted:true` 加该窗口的新截图；截图失败只带
  `capture_error`，输入照常是已投递）。
- W15 AX 动作返回错误码却回执 `submitted`，或返回错误时盲目改用另一种途径重复投递（AX 返回非 0 视为投递失败，
  与 3a 的 `OSError` 一样：已投递过事件则 `status:"unknown"`，否则 `failed`；不再换途径重试）。

### 让出、叫停与恢复

- W16 后台输入沿用 3a 规则：本人在别的 App 里打字时 Yuki 的后台输入也被让出（决定 3：只有冲突时让出——
  目标窗口所属进程是前台 App，或本人指针下的窗口属于该进程，并且基准之后有本人输入）。
- W17 冲突时 Yuki 照常投递，按键与本人的输入交错（冲突且基准之后有本人输入 → 等本人停手 1.5 秒、最多 10 秒，
  然后 `owner_active` 拒绝，不投递、不打 `activity` 行、不改 holder）；冲突但本人没有新输入时被拒绝
  （照常执行）。
- W18 Desktop「停止」后后台输入仍执行，或窗口截图被拒绝（输入 `control_held`，截图照常）。
- W19 后台动作被当作本人输入而让 Yuki 自己下一次输入让出（spike Q4：后台事件不推进系统的输入计时；基准照旧在
  每次截图与输入之后读取）。

### 合同、恢复与事实

- W20 窗口输入同键重试重新投递，执行中崩溃后报成功或重跑（沿用 3a journal：同键返回原回执，崩溃为 `unknown`）。
- W21 新连接器没有在能力事实里说明支持按窗口操作，旧连接器（0.5.0）给出 `window` 时服务端报成含糊错误
  （新连接器 `device_capabilities.computer.windows = true`；0.5.0 自己返回 `device_not_supported`，服务端原样透传）。
- W22 工具说明仍写“本人电脑暂不支持按窗口”，或改动了冻结参数（只改说明文字；合同 revision 哈希随之变化）。
- W23 Desktop 无法区分后台与前台操作，在后台操作时仍提示“你操作时它会暂停”（`activity` 行增加
  `mode:"background"|"foreground"`，旧 Desktop 忽略多出的字段）。

## 2. 设计落实

### 连接器（0.5.0 → 0.6.0，协议仍为 4）

- **边界**（`screen.py`）：新增 `Window`（与 `Display` 同样是输入坐标中的矩形加原生像素尺寸）、`Target`
  （一次调用解析出的一个窗口：`capture`、`collides`、`elevated`、`focus` 与 `click`／`move`／`drag`／`scroll`／
  `key`／`type`，外加 `actions`——该平台能在后台投递的动作）与 `Refused`（这次调用什么也没投递的拒绝）。
  `Backend` 增加 `windows()` 与 `window(id)`。`frame()`／`to_global()` 改为接受任意矩形，窗口与显示器共用同一换算。
- **`Desk`**（`desk.py`）：给出 `window` 时先要求两项权限（W5），再 `screen.window(id)` 解析（`Refused` →
  `window_not_found`／`window_unavailable`，W4）；输入依次检查叫停（W18）、平台是否支持该动作（W12，打
  `activity` 行之前）、冲突让出（W16、W17：`last_input` 晚于基准**且** `target.collides()`）、提升权限（`target_elevated`），
  然后经 `Target` 投递；投递中抛出的 `Refused` 只撤销这一次计数（W12、W15）。`type`／`key` 给出 `x,y` 时先
  `focus`（W11）。动作后截该窗口（W14）；结果带 `window`、不带 `display`（W6）；截图与 `resume` 一律带
  `windows` 列表（W2）。`activity` 行带 `mode`（W23）。能力事实加 `windows: true`（W21）。
- **macOS**（`screen_macos.py`）：
  - 构造时先 `CGMainDisplayID()`（W1）。
  - 列表与解析都用 `SCShareableContent(excludingDesktopWindows:true, onScreenWindowsOnly:false)`：layer 0、有标题、
    不属于连接器进程；`id` 为 CGWindowID。解析时用 `_AXUIElementGetWindow` 在 `AXWindows` 中找到同号的 AX 窗口，
    `AXMinimized` 为真则 `window_unavailable`；`SCContentFilter(desktopIndependentWindow:)` 的 `pointPixelScale`
    给出像素尺寸（Retina 换算，M6）。截图同一过滤器，`ignoreShadowsSingleWindow`、不画光标（W3）。
  - 定位：只遍历该 AX 窗口自己的子树，取包含该点的最小元素；只下探包含该点或没有尺寸的节点（W8）。从该元素向上：
    `click` 遇到输入框类（`AXTextField`／`AXTextArea`／`AXComboBox`／`AXSearchField`）设 `AXFocused`，遇到有
    `AXPress` 的元素就 `AXPress`；`right_click` 找 `AXShowMenu`；都没有时盖章点击。`double_click`、`move`、`drag`、
    `scroll` 直接用盖章事件（W10）。AX 返回非 0 → `OSError`（W15）。
  - **实测补充**：从未激活过的 App 没有 key window，`AXFocused` 返回 0 却不生效（读回仍为假），随后按键全部丢失；
    因此设 `AXFocused` 后读回，为假则在该点盖章点击一次——盖章点击会让该输入框在后台成为焦点且不激活 App
    （本机实测，见 §4）。
  - 按键：普通 `CGEventPostToPid`（Yuki 的私有事件源与标记），落在 App 的焦点（W11）。
  - 盖章：mouseMoved 引子后等 30 ms，按下与抬起间隔 30 ms；字段 7=3、40=pid、51／91／92=窗口号、58=本次调用的点击组；
    `CGEventSetWindowLocation` 在 macOS 27 起写窗口内坐标，更早写全局点（W7，按 Cua `window_location_is_window_local`）。
    私有函数用 `objc.loadBundleFunctions` 加载。
  - Chromium（W13）：向某 App 投递点击、聚焦前，对它设一次 `AXManualAccessibility`；成功（Electron／Chrome）则
    等该窗口出现 `AXWebArea`，最长 4 秒；本进程内按 pid 只做一次。不设 `AXEnhancedUserInterface`：它对原生 App
    也会“成功”，决定 4 只允许 Electron／Chrome。
  - 冲突（W16）：前台 App 用 `lsappinfo front` 读取。**实测补充**：系统级 AX 的 `AXFocusedApplication` 在前台 App
    响应慢时返回 -25204（本机 Finder 在前台时稳定复现），`NSWorkspace.frontmostApplication` 又只在 run loop 中刷新，
    连接器没有 run loop。指针下的窗口由 `CGWindowListCopyWindowInfo(OnScreenOnly)` 按前后顺序取第一个包含指针的
    layer 0 窗口，比较其进程。
- **Windows**（`screen_windows.py`，纯 ctypes 加 comtypes 1.4.x 的 UI Automation）：
  - 列表：`EnumWindows` 中可见、有标题、非 `WS_EX_TOOLWINDOW`、`DWMWA_CLOAKED` 为 0、不属于连接器进程的顶层窗口；
    `id` 为 HWND。解析：非顶层或不存在 → `window_not_found`；`IsIconic` 或不可见 → `window_unavailable`；几何取
    `DWMWA_EXTENDED_FRAME_BOUNDS`（物理像素，进程为 per-monitor-v2）。
  - 截图：`PrintWindow(PW_RENDERFULLCONTENT)` 到窗口矩形大小的位图，再把可见边框部分缩放到最终尺寸（W3）。
  - 动作只经 UIA：`ElementFromHandle` 后 `FindAllBuildCache(TreeScope_Subtree)` 缓存外框，取包含该点的最小元素，
    再沿 `RawViewWalker` 向上（W8，不用 `ElementFromPoint`）。`click` 依次找 Invoke、Toggle、SelectionItem、
    ExpandCollapse；`scroll` 找 Scroll 模式按行 `SmallIncrement`／`SmallDecrement`；`type` 需要 `x,y`，`focus` 记下该处
    可写的 Value 模式，`type` 把文字接在原值之后 `SetValue`。都找不到 → `device_not_supported`（W12）。`key`、
    `double_click`、`right_click`、`move`、`drag` 在 Windows 窗口模式不在 `actions` 中，执行前即拒绝。不调用
    `SetFocus`（UIA 会把窗口带到前台）、不用 `PostMessage`／`SendInput`（W9）。COM 错误 → `OSError`（W15）。
    UIA 线程为 MTA（`sys.coinit_flags = 0`，每个工作线程 `CoInitializeEx`）。
  - 冲突：`GetForegroundWindow` 或 `WindowFromPoint(GetCursorPos)` 的根窗口属于同一进程；提升权限按目标进程完整性级别
    （UIPI 同样阻止 UIA）。
- **依赖**：darwin 加 `pyobjc-framework-applicationservices` 13.x；win32 加 `comtypes>=1.4,<1.5`（锁定 1.4.17；
  1.5.0 发布仅一天，没有采用）。`build_runtime.py` 的导入探针加入二者。

### 服务端

不改路由与校验：`LocalDeviceService.screen_action` 原样把 `window` 交给连接器，0.5.0 连接器自己返回
`device_not_supported`，服务端透传（W21）；结果中的 `window`、`windows` 原样进入模型数据。只改 `computer` 工具说明
（W22）：`window` 取自 `windows[].id`；本人电脑上给 `window` 即后台操作、不动光标和前台；`type`／`key` 可给 `x,y`
先聚焦；后台投递不了时 `device_not_supported`，需要时省略 `window` 改前台；`owner_active` 在窗口模式下只算本人正用该
应用。参数不变，合同 revision 哈希随说明变化（与 #599 相同，不升合同版本号）。

### Desktop（Yuki-Desktop）

`connectorLine` 解析 `mode`，`supervision.activity` 增加 `background`；「這台電腦」页显示“Yuki 正在背景操作一個視窗，
不動你的滑鼠和前台視窗；你在同一個 App 裡操作時它會暫停。”，托盘显示“Yuki 正在背景操作電腦”，「停止」不变。
没有 `mode` 的 0.5.0 行按前台显示（W23）。

## 5. 需本人确认的取舍

1. **滚轮走盖章事件，不走 AX。** 决定 1 写“点击与滚轮先 AX”，但 AX 没有“按行滚 N 格”的动作（只有滚动条比例与
   按页动作），spike 实测盖章滚轮在 AppKit、Electron、Chrome、WKWebView 上都送达；所以 `scroll` 直接盖章。
2. **Windows 窗口模式只支持 `click`、`scroll`、`type`。** 不用 `PostMessage` 时 `key`、双击、右键、移动、拖拽没有后台
   途径，返回 `device_not_supported`；`type` 必须给 `x,y`，文字接在输入框原值之后（UIA Value 只能整体设值，无法在
   光标处插入）。
3. **macOS 按窗口截图也需要辅助功能权限**（用来读 `AXMinimized`，避免截到最小化 Chrome 的旧画面）；整屏截图不变。
4. **Windows 经典 Win32 按钮的 Invoke 会抢前台**（CI 实测，见 §3）。可选：照常（光标不动，但前台被换），或对
   `FrameworkId` 为 `Win32` 的元素拒绝 Invoke（`device_not_supported`，经典程序的按钮就只能前台点）。本次照常。
5. **不设 `AXEnhancedUserInterface`。** 只用 `AXManualAccessibility`（Electron 与现代 Chromium 都支持）。若实机发现
   某个 Chromium App 只认前者，再按 App 补。
