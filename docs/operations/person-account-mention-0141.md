# Person、Account 与提及统一升级记录

日期：2026-10-19。开发基线 `ebc83163661dceb5b83c9b9182b18b2fdba6bde4`，目标迁移 `0141`、Plugin API `6.0`。

对应[任务书](../architecture/Yuki-人物合并账号归属与提及统一重构任务书-2026-10-19.md)。本记录分别列出实现、隔离验收和生产操作；副本演练不代表生产已升级。

## 实现与删除范围

账号唯一认 `Account(platform, external_account_id)`；归属只存一份 `AccountAssignment`。原 Binding、Presence UUID 成为有类型的归属阶段编号，原事件、Conversation、设备、执行、预算和效果回执不重新编号。暂停保归属，结束释放归属；转回原人也建立新阶段。

人物当前资料按同人族查询，原 actor 按原授权来源处理。配置合并保目标显式值、完整插件对象和原行版本；冲突输家归档后从当前表删除，unset 不再露出隐藏旧值。Memory、SELF、资料管理、路由、自动化、插件与客户端沿相同边界消费。

原生提及保存原位置、逐账号目标、原归属阶段、重复和未知关系。Main、JEV、历史与 SDK 消费同一快照。发送正文在原位置写自然 `@名字`，重名时使用目录提供的 `@{account:UUID}`；QQ、Telegram 和后续适配器只承担原生编码与实际物理分条。普通文字先发送，表情后台追加。

已删除的运行链包括旧双归属表、跨表互斥、无位置账号列表反推人物、旧 OneBot 事件投影、发送 `mentions` 数组、已见白名单、无消费者的账号 refs、旧最终投递执行器及解析器、通知在线反拼旧发布、万能资料 owner 启用检查和无人消费的自动化管理旁路。旧版本原件只在冻结迁移及原记录的只读归档中保留，不挂回执行路径。

## 四轮贯穿复审

1. 事实模型和写入：唯一当前归属、真实时间、角色外键、原 actor、同人关联与账号转让；迁移保原阶段 UUID。
2. 最广消费者检查：控制面、配置 CAS、设备与绑定码、自动化、插件、Memory、SELF、隐私清退、目录与 SDK；删除资料 owner 的停用门槛。
3. 深入执行与传输：原消息去重、迟到与未知作者、私聊原入口、QQ/TG 跨度和引用、物理 part ACK、后台表情、通知以及原付费响应恢复。
4. 交叉终审和真实副本：再次发现并修复资料管理残余门槛、收件人与 actor 混用、通知准备无限挂起、Account 作者变化未触发源失效、目录排序，以及同合同原生响应和 compact 恢复丢原链的问题。

同合同原生 continuation、已付 compact 和尚待执行的原调用保原协议；可移植的已结算普通工具轮次可按当前业务资料接续。退役 manifest 在离线升级中封存，Work 保原身份和累计预算进入新合同。没有恢复旧工具执行器，也没有按 `work_id` 一律恢复整段协议。

## 迁移副本验收

在生产仍运行 `0140` 时，使用 SQLite backup 创建隔离副本；未启动第二个 Bot、未调用模型或发送测试聊天。

最终完整副本演练耗时 506.64 秒：75 个原归属阶段 UUID 全保留，生成 76 个 Account、216 条可证姓名观察和 91 条账号群资料；旧 `identity_bindings`、`presences` 两张物理表均已删除，外键检查通过。以下记录的完整原行校验值在迁移前后相同：

| 原记录 | 行数 |
| --- | ---: |
| Work / 效果 / 累计预算 | 772 / 1224 / 759 |
| 协议对象引用 / 子任务 | 307267 / 12 |
| 控制命令回执 | 193 |
| Memory facts / 自动化执行 | 2757 / 172 |

设备和绑定码原表亦保持相同。副本演练后只追加 Account 作者元资料的当前触发器；冻结 `0140→0141` 升级测试同时核对当前 schema guard、角色约束和源失效，历史迁移定义不随当前模型改变。

原库有一条早已应解绑的 Yuki 阶段与人物账号同时存在。升级使用原阶段 ID、原 revision 和已有明确解绑指令作为离线证据，未知结束时间保持未知。通用迁移不写死这个账号，也不以 `updated_at` 猜结束时间。

## 查询与等待

本地隔离 Linux / Python 3.12，分别放入 100、1000、10000 个账号、姓名及相关资料，捕获实际绑定 SQL 并执行 `EXPLAIN QUERY PLAN`：

- 账号当前阶段沿原生唯一键和当前阶段部分唯一索引定位；固定人物资料沿 owner / family 索引查询。
- 普通文字准备不查询身份；仅精确 Account 引用按主键批读；自然姓名一次读取目标入口的完整观察集合，不逐个提及查询或远端补查。
- 群目录在 SQL 中沿 `(space_binding_id, account_id)` 索引分页，再批读本页阶段，不再先排序全群；管理绑定目录也批读本页人物代表。
- 姓名前缀索引构建与跨度扫描按本次资料规模增长。101 / 1001 / 10001 个姓名配合 100 / 1000 / 10000 次提及，解析加分条的三次中位数约为 0.0003 / 0.0051 / 0.0885 秒；这是该隔离环境的诊断值，不设生产耗时门槛。

原成功回执在其他 writer 持有时仍走纯读；外部查证和准备在 writer 外，真正关系变更、效果接纳及回执提交保持原子性。不能从总耗时反推精确 SQLite 等待。

固定新工具合同、原冻结历史及原协议资料分别验证。Provider 的实际缓存命中仍须认上游 usage；隔离回归和字节相同不能冒充真实命中率。

## 生产切换顺序

1. 以审核后的准确源码和 `uv.lock` 构建镜像，核独立 JEV 精确 revision、SDK 6.0 和实际插件 manifest；旧覆盖源码镜像不能代替依赖升级。
2. 只停止 Bot，保存停机后的数据库、必要配置和插件代码；独立环境、外部运行及 SnowLuma / 代理保持原实例。
3. 使用新镜像离线运行 Alembic `command.upgrade(config, "head")`。若原库存在上述真实归属冲突，按已核实的原阶段证据设置本次 `Config.attributes["identity_assignment_endings"]`；普通启动不能替代这次离线操作。版本记录与 DDL 在同一显式事务提交。
4. 替换 API 6.0 插件代码，沿现有管理 API 恢复原来批准的权限和原启用状态，不扩大权限。Bot 使用新镜像启动，只检查真实健康、连接、插件和原回执。
5. 健康确认后清理本次及旧备份、部署临时文件、旧镜像和可重建缓存。数据库、媒体原件、表情库、共享工作区及当前独立环境 / checkpoint 继续保留。

最终单测、集成、CI、合并和实际上线结果以对应 PR 和交付记录为准；本文件不提前宣称线上验收。
