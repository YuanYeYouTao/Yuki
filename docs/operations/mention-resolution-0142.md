# 提及解析与最近发言索引修复

2026-10-20，开发基线 `8368c286`。迁移 `0142`，Plugin API 继续为 `6.0`，发送参数继续为 schema `4`。本记录区分实现、隔离验证、合并和生产交付。

## 原问题

数字生命研究所的原始工具轨迹确认：内部事件 `111340` 的原调用带有 `@远野`，解析回执却给出两个相同 Account ID 的候选并去掉 `@`；`111347`、`111352` 对 Ice 发生相同错误。昵称观察携带当前 Assignment，被提及时留下的观察没有 Assignment，解析器按两者组合计数，误把同一个账号当成两个收件人。Diana 有两个真实账号，但被重复计成四个候选。

另有短名称与长名称前缀混算、`@` 后空格静默漏识别、旧归属阶段阻止给账号发送原生提及等问题。原引用使用精确 Account 后可发送，说明实际平台能力正常。

## 实现边界

正文一次扫描保留原位置、邮箱、链接、转义和精确 Account 引用。待匹配片段先去重，再沿既有名称长度合同生成前缀；SQLite 用名称与入口索引定点批查。先选最长实际命中的名称，再按 Account 去重，历史观察的 Assignment 只保来源资料，不成为新的收件资格。

仅当最长名称仍对应多个不同 Account 时，合并本次发送的候选，在目标 Conversation 中批取各账号最新真实 `message`，按 `(occurred_at, id)` 排序。均无记录时按 Account ID 稳定选择；显式 `@{account:UUID}` 直接指定账号。同一人的多个账号分别排序，不按 Person、今日归属或被提及次数推算发言。

名字和最近发言查询均在独立读会话中完成，读会话关闭后才接纳发送。普通文字零提及查询；精确引用主键批读；唯一自然名只查名字；真重名额外一次活动批查。没有逐次更新的活动表、常驻名册缓存或平台补查。原发送登记、来源授权、claim 与 ACK 继续各自处理真实事实。

无法解析的原文保留 `@`，不再主动剥字符。查询结果进入原 prepared message，拆分、通知恢复、重试和原回执读取复用该账号与原跨度，不在 ACK 时重新选择最近发言者。回执从已准备且实际送达的消息投影内部账号引用，重复目标去重，不额外查询今日身份。

迁移一次规范历史名称列；规范化冲突只在原 Account、Assignment、SpaceBinding 组合内合并，按实际 UTC 时刻保最早与末次观察，原时间字符串保留。名称截断后去尾空白，使规范化保持幂等。原事件、冻结正文、发送计划及回执保持原件。

名字增加 `(name, space_binding_id, account_id)` 索引，群目录原有 scope/account 索引继续服务自己的查询。旧会话发送者时间索引由限定真实 `message` 的部分索引替代，聊天表不叠加第二棵同用途索引；插件外部事件无需维护该消息索引。索引随原入账维护，不另开维护写事务。

## 性能证据与验证范围

设计阶段在本机隔离 Linux 容器 CPython 3.12.15、SQLite 3.46.1 的简化合成投影表比较，全量读与建树处理单个自然名字，在 1000／10000 个账号时分别约为 3.20／35.13 ms；正文定点查询约为 0.038／0.057 ms。先合并重复待匹配片段后，1000 次重复提及的局部处理从 11.81 降至 0.97 ms。两入口作用域分支的执行计划均按 `(name, space_binding_id)` 查覆盖索引。

真实当前 schema 的隔离实验中，同一发送者 10000 条插件外部事件会使旧最近消息查询执行约 50022 个 VM 步骤；限定 `keeper` 与 `message` 的部分索引使其降至 17 步。以上是隔离原型数据，不包含 ORM、异步连接池、生产磁盘或网络发送，不能证明线上尾延迟或没有 SQLite 写锁等待。

实施期间真实调用捕获的 SQL 又暴露出 JOIN 重排：即使有名字索引，优化器仍可能先遍历平台 Accounts。最终查询用请求中的 JSON 名称／ID 驱动固定 `CROSS JOIN`，绑定数据、不拼接模型内容，不依赖 `ANALYZE`、索引 hint 或缓存。

最终查询在平台账号 10／1000／10000、名称观察 20／2000／20000 时，固定单个显式 Account 查询在两种环境均为 47 个 VM 步骤。固定两个同名账号，Windows CPython 3.12.13／SQLite 3.53.1 的名称查询均为 253 步，活动查询均为 168 步；Linux CPython 3.12.15／SQLite 3.46.1 分别均为 226／176 步。跨目标发送没有携带 Conversation ID 时，在同一活动查询内按原 Binding、Presence 与默认线程查找已存在的目标 Conversation，分别均为 189／197 步，不创建会话或增加查询轮次。再加入同一候选发送者的 10000 条插件事件，各环境的活动查询步数仍不变。这里排序的是两个真实候选，没有扫描全历史。

实施验证覆盖同账号重复观察、真重名与迟到消息、精确引用、原位置与 QQ／Telegram／第三适配器编码、跨群与跨私聊的真实目标、原回执、拆条与部分失败恢复、通知、历史名称升级，以及查询期间并发 writer。原生发送开始前准备 reader 已关闭，另一连接持有写事务时也能完成提及读查询。实际发送登记与 ACK 仍是写入，不能把这些验证表述成整条发送链路完全没有写锁。

其他 SQLite 查询的只读扫描结果见 [热查询扫描审计](sqlite-query-scan-audit-20261020.md)，其中未修复项不属于本次提及实现。
