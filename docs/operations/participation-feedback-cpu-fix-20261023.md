# 过时参与反馈反复重放导致 CPU 忙转

2026-10-23。此次修改处理短期参与反馈的重放成本，不更改真实任务、累计预算或发送回执。

## 故障证据

生产 Bot 在容器仍显示 healthy 时，主线程持续接近一核满载，`/livez` 与 `/healthz`
曾超过 10 秒未返回。非阻塞采样的主线程停在
`reconcile_page → _replay → observe_committed_effect → _prune`，反复解析参与检查点。
这不需要出现单个不退出的 while：终态任务每次巡回重新读取历史，已裁掉的旧效果再次插入，
每条效果触发全局整理后又被删除，下次巡回重复同样工作。

旧实现把反馈完整恢复当作必要目标。对于会衰减的调节信号，这项工作没有对应的实时收益，
却占住了处理消息、健康请求和连接握手的事件循环。连接握手超时是同期表现，
本记录不据此断言所有连接异常都只有这一个原因。

## 删除与保留

- Host 删除终态 run 的全历史轮转查询及游标，只推进真实活跃任务的进展。
- 控制器只消费本次新增反馈；不为冷启动、保存失败或丢失确认补齐已登记的刹车。
- 已越过原 `replay_after` 边界、且不再保留的效果直接退出，不再插入后删除。
- 新鲜效果沿原身份入账，由正常 advance 整理；删除逐效果的全局裁剪。
- 反馈到期且没有近期效果就退休，包括未收到结束信号的 accepted，防止失去最终信号后永久占位。
- 正常整理只解析一次参与检查点，内容变化才保存；恢复时仍完成旧字段迁移。

没有增加批处理机制、持久游标、恢复队列或跨调用缓存。真实 Work、预算、Social 与工具
回执仍在原领域账本；终态任务不重跑、不补发。旧任务近期才确认的本群发送仍通过现有
Social 近窗路径按原 run 和 generation 接入。参与关系与表达证据继续保存，不当作短期刹车删除。

这是明确的语义取舍：少量未保存的调节信号可以在进程退出时丢失，已有完整领域回执不丢失。
本次没有迁移删除历史反馈表，也没有宣称整份控制器状态已经改成纯内存。
开发约束补充“刹车信号不重要，刹车的行为才重要”，不再以完整恢复这些信号作为验收目标。

## 离线对照与验收边界

只读取得的私有故障快照包含 64 个参与单元和 139 条已过时 compute 效果；私有正文未加入 Git。
同一台本机运行三轮旧算法，每轮耗时 15.12、16.03、17.02 秒，触发 139 次裁剪、
278 次检查点解析和 278 次无变化保存。删除过期重放后，同样三轮均小于 0.1 毫秒，
裁剪、解析和保存均为零；这份样本的最终完整 State 哈希相同。

上述比较只覆盖这一份过时 compute 样本，不表示所有行为保持逐条重放语义，
也不是生产端到端延迟或自然聊天验收。新鲜效果、身份冲突、迟到发送、
未收到终态的 accepted 退休，以及 Host 不再扫描终态历史另由回归覆盖。
