## 1. 改代码前列出的可能失败

### 1.1 入口核对（前提）

- E1 Main 直调的生命周期控制（`get_tasks`、`manage_task`、`wait`、`start_subtask`、`message_task`）经 `AgentRunner._execute_control_call` 进入 `WorkControl.execute`。若这里不跑冻结 schema，`work_control.py` 的手写检查就不是重复，而是唯一校验；删除后畸形参数会进入 writer（例如非字符串 `deadline` 在 `work_wait._timestamp` 中抛 `AttributeError`，越过 `execute` 的 `ValueError/WorkConflict` 分支直接打断本轮，而不是返回拒绝）。
- E2 Code Mode 子调用的控制经 `CodeHost.execute_control` 走同一个 `_execute_control_call`；业务子调用经 `execute_call` 校验 schema，不代表控制子调用也校验。
- E3 恢复：`agent_runner` 对 journal 中没有回执（或只有未派发意图）的调用，以原存储参数重新进入 `_execute_tool_batch`，控制调用同样到达 `_execute_control_call`。
- E4 Host 直调：`WorkControl.admit_goal`（Host 自动接纳）不经 `execute`，自带 `goal` 检查。
- E5 测试与 Host 代码直接调用 `WorkControl.execute`（如 `test_work_tool_surface_e2e` 依赖 `execute` 自己拒绝畸形 `for` 项）。
- E6 Dream：`mutate_dream` 唯一的生产调用方是 `DreamService._commit_cluster_decision`，其 `DreamOutput` 来自 (a) `_run_model` → `StructuredTaskRunner.run` → `DreamOutput.model_validate`，(b) `ready_preview` → `DreamOutput.model_validate_json(proposal_json)`。若存在 `model_construct`、`model_copy(update=…)` 或手工构造 `DreamAction` 的路径，pydantic 保证不成立。
- E7 pydantic 只保证形状，不保证当前事实：来源事实状态、分区、显式记忆锚点、别名是否仍在 `current_map` 都是写入时与当前事实比较，必须保留。
- E8 `normalize_memory_text` 会把控制字符替换为空白再压缩：只含控制字符的正文能通过 pydantic 的 `min_length=1` / `strip()`，归一化后为空；归一化后为空的检查不是重复。
- E9 锚点存在性：`mutate_dream` 的 `anchor` 由调用方 `_anchor` 在当前来源中选出（显式记忆、RESOLVE 的 `anchor_ref`、或 `select_dream_anchor`），只有 RESOLVE 的 `anchor_ref ∈ source_refs` 是 pydantic 保证；其余由调用方构造保证，不属 B5。
- E10 错误码与先后顺序：删除一个检查后，同一输入若同时有多处错误，报告的第一个错误码可能改变；这属于模型可见结果变化，除非被删检查在任何输入上都不可能先于保留检查触发。
- E11 异常类型：删除 `select_dream_anchor` 的空集检查后，空输入由 `min()` 抛 `ValueError`（消息不同），类型不变。
- E12 MemoryFact 与 MemoryFactCreate 的两个 model validator 合并为一个函数后，字段集合须两边都有（`authority`、`scope_type`、`valid_from/until`、身份与生命周期字段）；mypy strict 需接受联合类型。

### 1.2 局部 import 提升（B1 遗留，仅 `work_control.py`）

沿用 B1 记录 §1.2 的 I1–I11。本文件特有：

- I3′ `work_budget.limit` 与 `_get_tasks` 的局部变量 `limit` 同名；提升后 `_get_tasks` 内为局部变量（先赋值后读取，不会 `UnboundLocalError`），但模块全局 `limit` 与局部同名易误读。
- I1′ `work_control` 被 `work_supervisor`、`effect_outcomes`、`capabilities.results` 等反向顶层导入；判环用 B1 的静态图方法，并逐模块独立进程导入复核。

## 2. 入口核对结论

| 入口 | 是否经冻结 schema / pydantic | 依据 |
| --- | --- | --- |
| Main 直调控制 | **否** | `_execute_control_call` 只核声明名、`work_control_allowed`、JSON 是对象、只读授权，然后调用 `control.execute`；`TurnCapabilityRuntime.validate_call_result` 只在业务工具的 `MainAgentToolBackend.execute_call` 中调用 |
| Code Mode 控制子调用 | **否** | `CodeHost.execute_control` → 同一 `_execute_control_call`（`tool-kernel.md` “Code Mode 子调用按完整 API 核验名称和原 schema”对控制子调用不成立） |
| 恢复重派 | **否** | 原参数重入 `_execute_tool_batch` → `_execute_control_call` |
| Host `admit_goal` | 否（不经 `execute`） | 自带 `goal` 检查 |
| Dream `mutate_dream` | **是** | 唯一生产调用方的 `DreamOutput` 只来自 `model_validate` / `model_validate_json`；模型冻结，`src` 中没有 `model_construct`，`model_copy` 只用于 `DreamInput` |

因此 `work_control.py` 中与 JSON Schema 相同的类型、长度、枚举检查（`get_tasks` 的 limit/cursor/id/status/parent，`manage_task` 的 action/id/text/goal/result，`wait` 的 all/deadline 与 `for` 项形状）**都不是重复**，本批全部保留。
