# 参与状态重复计算修复

## 问题与范围

2026-10-16 线上 `9e6f6147` 固定参与库 `d85bb39`。普通消息入口与后台推进都在
事件循环内执行参与状态投影；15 秒非阻塞采样取得 136 个有效样本，其中 123 个包含参与库调用，
另有 9 个采样错误。同期出现 SQLite 写锁超时，部分普通入口在入账阶段失败。
Bot-only 重启后同一热点再次出现，因此重启不能替代算法修复。

Host 为排列 SELF 锚点，给每条新投影调用完整 `participating_units`；这份查询又为每个单元
计算无人读取的 belief，并重复解码整个参与检查点。自主评分与历史折叠也各自逐单元扫描同一批事实。
问题不需要无限循环或无限增长才能触发；换页会放大同步计算的延迟。

本次从当前 main 独立修复，不包含 issue 299 与多平台分支的未提交修改。

## 实现

- Host 删除为了候选排序读取完整参与状态的调用，SELF 候选沿现有历史时间排序，保留全部合法候选。
- 独立库删除 `UnitParticipation.belief` 展示字段及两处提前计算；它不属于持久 UnitState 或 Jev 外发合同。
- 参与视图、来源核验、观测冻结、评分与历史折叠复用当次已解析的检查点；按讨论/对象归集真实事实。
- 已解析单元直接提供原退休来源证明，表达锚点和关闭边界使用调用内索引，消除重复反序列化及交叉扫描。

真实自主 belief、概率公式、quiet、语义纠偏、原来源修订和撤销仍按原合同处理。
局部索引只活在一次同步计算内，不跨修改缓存；没有清空参与数据库、增加 TTL、调用上限或自动降级。
同一来源 revision 的原事件投影与既有在途 Snapshot 保留原候选键，不重建已提交请求。
