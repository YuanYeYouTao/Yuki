# Yuki 3.8.0 发布说明（待发布）

> 状态：代码与发布资料已切到 `3.8.0`，但尚未创建 `v3.8.0` tag、GHCR 镜像或 GitHub
> Release。本文是发布候选说明，不代表 3.8.0 已可供生产拉取。

Yuki 3.8.0 把“Yuki 是一个永久主体”落成正式数据与运行时合同：账号、QQ Gateway、平台连接
不再拥有人格、记忆或会话。NapCat 与 SnowLuma 同为正式 OneBot v11 Provider；换 Provider 只
替换内存 GatewayConnection，不创建新的 Yuki，也不重置 Conversation、Memory 或路由。

## 主要变化

### 永久 Yuki 与 canonical identity

- 新增 Person、IdentityBinding、Space、SpaceBinding、Presence 与 canonical Conversation。
- 一个数据库对应一个永久 Yuki；SELF、关系、偏好、自动化、插件状态和长期记忆不随 QQ 号或
  Provider 变化。
- 私聊按 Person 聚合，群聊按 Space 聚合；多个旧 scope alias 可以指向同一个 canonical
  Conversation。
- OneBot 入站增加 canonical receipt、作者四态与 ingress Presence provenance；Yuki Presence、
  人类 Person、第三方机器人和 system 不再混为同一种身份。
- 主动私聊、主动群聊和群 ingest 分别使用三张确定性路由表。路由接管只增加
  RouteGeneration，连接重建只增加 ConnectionGeneration，二者都不改 ConversationGeneration。

### transport-neutral 控制面

- 新增不依赖 QQ matcher、CLI renderer、HTTP 或 ORM model 的控制面合同与应用服务。
- 提供稳定 Principal、Capability、Cursor Page、Problem、幂等 Command Receipt、乐观并发和
  OperationRef。
- Person、Space、Presence、Binding、三类路由、Conversation、Config、Audit、Memory、
  Automation、Plugin、MCP、Emoji 与 Speech 均有可供未来 WebUI 复用的查询或命令投影。
- 本版不提供管理 HTTP API、登录系统或前端，也不新增管理端口。

### NapCat 与 SnowLuma 正式 Provider

- NapCat、SnowLuma 位于同一 Provider 层；OneBot Adapter 根据入口路径提供真实 Provider ID。
- NapCat 保留 `/onebot/v11/` 与 `/onebot/v11/ws`；SnowLuma 使用
  `/onebot/v11/snowluma/ws`。
- 不同 QQ 可以通过不同 Provider 同时在线；同一 QQ 的同 Provider 或跨 Provider 重复连接均
  拒绝新连接，旧连接不受影响。
- Compose 增加 `napcat`、`snowluma` profiles。SnowLuma 的 noVNC 与 WebUI 默认只绑定
  `127.0.0.1`，OneBot HTTP/WS 和 VNC 不暴露给宿主公网。
- 安装器用可重试 `gateway-action.json` 保证先停止被取消选择的 Provider，再启动目标 Provider；
  停止失败时不会启动新服务。
- 新增无 secret 的 `qq-ai-bot-cli gateway doctor --provider ...`，冻结 Yuki 使用的 OneBot 核心
  action 合同。Provider 私有 action 不属于跨 Provider 保证。

### Prompt 与模型请求兼容性

- 首轮工具集合和 native web 形状被冻结，消息 origin 不再让公共 Prompt 前缀分叉。
- 自主群聊在通过准入后获得与显式 @ 相同的受控写能力，仍受真实 Principal 与 capability 边界约束。
- Responses 请求不再发送 `temperature`；关闭思考时显式使用 `none` effort。

## 数据库与兼容性

- Alembic head：`0048`，新增 `0043`–`0048`。
- Identity runtime epoch：`v2`。
- Plugin API：仍为 `2.0`。
- Genie-TTS Worker 内部版本：仍为 `1.9.0`。
- 公共 `/healthz` 字段与敏感信息边界不变。
- 没有 Yuki 表，也不把 GatewayConnection、Bot 句柄、token 或 Cookie 写入数据库。

3.7.1 数据不能在升级 schema 后直接启动 3.8.0。必须停机执行 canonical backfill 与
`identity-cutover --plan/--apply`；完整流程见 [3.8.0 升级指南](../upgrade-3.8.0.md) 和
[Identity Cutover 细节](../upgrade-identity-cutover.md)。

## 当前发布阻断项

在真正创建 `v3.8.0` tag 前，至少还需要完成：

1. 在生产等价副本上演练 3.7.1 → 3.8.0 停机回填、plan/apply 与快照恢复。
2. 补齐并认证全新数据库的首个 Yuki Presence bootstrap；当前预发布流程只适合已有 Yuki 数据
   的升级演练，不能宣称 fresh install 已完成。
3. 使用真实 NapCat QQ A 与 SnowLuma QQ B 验证并存收发，再验证同一 QQ 停旧后启新。
4. 在最终 main SHA 上通过完整 Quality、Memory Release Check、release smoke 与匿名镜像拉取。

在这些项目完成前，不应创建 tag、推送不可变 3.8.0 镜像或发布 GitHub Release。

## 回退

Identity cutover 后不能靠 `git revert`、改镜像 tag 或 Alembic downgrade 回退数据。停止所有 Bot
和 Provider，恢复 plan 记录的同一时点 DB/WAL/SHM 快照及配置，再启动对应旧版本。cutover 后
产生的消息与配置不会存在于恢复后的快照中。
